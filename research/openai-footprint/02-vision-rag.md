# OpenAI: vision-распознавание и векторный поиск — факты на 26.08.2026

Область: Проект 04 (ИИ-трекер калорий по фото) и Проект 06 (ИИ-продавец на данных клиента,
pgvector). Все цифры и идентификаторы — по официальной документации OpenAI
(`developers.openai.com/api/docs/...`), дата фиксации — **26 августа 2026**. Цены и id моделей
у OpenAI меняются часто (пример: Sol подешевел на 20% 22.08.2026) — проверять перед бюджетированием.

## 1. Vision-модели сейчас — модели, которые я помню (gpt-4o, gpt-4-vision), НЕ устарели по
доступности API, но НЕ являются актуальной рекомендацией. Актуальное поколение — **GPT-5.6**
(Sol/Terra/Luna), GA с 09.07.2026.

| Модель (id) | Приём изображений | Токенизация картинки | Лимит запроса | Structured Outputs |
|---|---|---|---|---|
| `gpt-5.6-luna` | да | patch-based, множитель ×1.2 | до 512 МБ / 1500 изображений на запрос | да |
| `gpt-5.6-terra` | да | patch-based, множитель ×1.2 | то же | да |
| `gpt-5.6-sol` | да | patch-based, множитель ×1.2 | то же | да |
| `gpt-4.1-mini` | да | patch-based, множитель ×1.62 | то же | да |
| `gpt-4o` / `gpt-4o-mini` | да | tile-based (база 85 / 2833 ток. + токены на тайл 512px) | то же | да (с `gpt-4o-2024-08-06` и новее) |

Форматы: PNG, JPEG, WEBP, non-animated GIF. `gpt-5-2025-08-07` / `gpt-5-mini` / `gpt-5-nano`
**выводятся из эксплуатации 11.12.2026**, официальная замена — `gpt-5.6-sol` / `-terra` / `-luna`
соответственно. `gpt-4o`, `gpt-4o-mini`, `gpt-4.1`, `gpt-4.1-mini` в API пока НЕ в таблице
депрекации (в отличие от ChatGPT UI, откуда `gpt-4o` убрали 13.02.2026) — но это устаревающая
линейка, для нового проекта курса брать `gpt-5.6-*`.

**Формула токенов картинки (patch-модели)**: делим изображение на патчи 32×32 px, считаем
`ceil(w/32) × ceil(h/32)` патчей, применяем детализацию (`low` = вписать в 512×512,
`high` = вписать в 2048×2048 с бюджетом ≤2500 патчей, `original`/`auto` — свои лимиты),
итог = `ceil(патчи × множитель)` токенов.

Задокументированные примеры (для семейства с множителем ×1.2):
- 1024×1024, `high`, без ресайза: `32×32=1024` патча → `ceil(1024×1.2)=1229` токенов.
- 512×512, `low`: `16×16=256` патчей → `ceil(256×1.2)=308` токенов.
- Верхняя граница `high`-детализации из-за бюджета патчей: `ceil(2500×1.2)=3000` токенов
  независимо от того, насколько крупнее фото.

Для тарелки с едой `low`-детализация (308 токенов) рискованна — мелкие компоненты блюда
(соус, гарнир) могут не распознаться; `high` (1229–3000 токенов) — реалистичный выбор.

## 2. Стоимость распознавания одной фотографии еды — расчёт для 10 000 фото/мес

Компоненты запроса: изображение (`high`) + текстовый промпт-инструкция (~250–350 токенов) +
структурированный JSON-ответ (список блюд/продуктов с граммовками, ~150–300 токенов).

Модель `gpt-5.6-luna` (актуальная замена `gpt-5-nano`, самая дешёвая с vision):
$0.20 / 1M input, $1.20 / 1M output (Standard tier, цены на 26.08.2026).

| Сценарий | Input (img+prompt) | Output | Цена/запрос | 10 000 запросов/мес |
|---|---|---|---|---|
| Компактное фото (1024×1024, high) | 1229 + 300 = 1529 ток. | 200 ток. | $0.000546 | **≈ $5.46** |
| Верхняя граница бюджета патчей (крупное/детальное фото, high) | 3000 + 300 = 3300 ток. | 300 ток. | $0.00102 | **≈ $10.20** |

Для сравнения (та же нагрузка, другая модель — если нужна точность выше, а не только цена):

| Модель | Цена вход/выход за 1M | 10 000 запр./мес (компактный сценарий) |
|---|---|---|
| `gpt-5.6-luna` | $0.20 / $1.20 | ≈ $5.46 |
| `gpt-5.6-terra` | $2.00 / $12.00 | ≈ $54.58 |

**Вывод по цифрам**: даже на топовой Sol 10 000 фото/мес — это ~$100, на Luna — единицы
долларов. Стоимость LLM-вызова для проекта 04 не является узким местом бюджета курса.

## 3. Структурированный вывод (Structured Outputs)

- Механизм: `text: { format: { type: "json_schema", strict: true, schema: {...} } }`
  (актуальный Responses API синтаксис; для чат-эндпоинта — `response_format`).
- Гарантия: документация прямо утверждает, что модель **всегда** вернёт ответ, соответствующий
  переданной JSON Schema — в отличие от старого `json_mode`, который гарантирует только
  валидный JSON, но не соответствие конкретной схеме.
- Поддержка: начиная с `gpt-4o-2024-08-06` и новее; для новых проектов документация
  рекомендует `gpt-5.6`. SDK даёт нативную типизацию через Pydantic (Python) / Zod (JS).
- Ограничения схемы: корень — только `object` (не `anyOf`), **все поля обязательны**
  (опциональность эмулируется через `null` в типе), поддерживаемые типы —
  string/number/boolean/integer/object/array/enum/`anyOf` (не в корне); для строк —
  `pattern`/`format`; для чисел — `multipleOf`/`minimum`/`maximum`; для массивов —
  `minItems`/`maxItems`.
- Единственное официально описанное исключение из гарантии — отказ модели (refusal) на
  небезопасный запрос: в этом случае схема не применяется, нужно отдельно обрабатывать это поле.

**Для проекта 04**: это ровно тот механизм, который нужен — модель возвращает
`[{name, grams, confidence}, ...]`, а калории/БЖУ доклеиваются из справочника продуктов (RAG)
по `name`, а не генерируются моделью. Structured Outputs гарантирует форму, но НЕ гарантирует,
что название продукта точно совпадёт со строкой в справочнике — сопоставление (fuzzy-match /
embedding-поиск по названиям) остаётся на стороне приложения.

### Расчёт стоимости индексации для проекта 06

Вход: сайт на 200 страниц + 50 PDF по 20 страниц = 200 + 1000 = **1200 «страниц» контента**.

Допущение (страница веб/PDF текста ≈ 500–800 токенов после очистки от разметки) —
**это оценка, а не задокументированное OpenAI число**; беру диапазон, а не одну цифру.
Плюс типичный оверхед RAG-чанкинга с перекрытием (+20–30% токенов относительно сырого текста).

- Нижняя граница: 1200 × 500 × 1.2 ≈ **720 000 токенов**
- Верхняя граница: 1200 × 800 × 1.3 ≈ **1 248 000 токенов**

Стоимость (`text-embedding-3-small`, $0.02/1M): **$0.014 – $0.025** за полную индексацию.
Стоимость (`text-embedding-3-large`, $0.13/1M): **$0.094 – $0.162**.
С Batch API — ещё вдвое дешевле в обоих случаях.

**Вывод по цифрам**: индексация для проекта 06 стоит копейки независимо от выбора модели —
экономия на этом шаге не имеет значения, важнее качество поиска и совместимость с pgvector
(ниже).

## 5. Совместимость с pgvector — вот где реальный подводный камень

pgvector документирует жёсткий лимит: **HNSW-индекс (и IVFFlat) не может быть построен на
векторе с более чем 2000 измерений** — ограничение упирается в размер страницы Postgres (8 КБ)
на тюпл индекса. Вектор с > 2000 измерений можно **хранить** в колонке `vector`, но **нельзя
проиндексировать** — поиск скатится в полный перебор (seq scan), что на масштабе документов
проекта 06 (сайт + 50 PDF, тысячи чанков) уже заметно медленнее.

Практические последствия для наших моделей:

| Модель эмбеддингов | Размерность по умолчанию | Влезает в HNSW (≤2000) без доп. действий? |
|---|---|---|
| `text-embedding-3-small` (1536) | 1536 | ✅ да, напрямую |
| `text-embedding-ada-002` (1536) | 1536 | ✅ да, напрямую |
| `text-embedding-3-large` (3072) | 3072 | ❌ нет — превышает лимит на 1072 |

Обходные пути для `text-embedding-3-large`, если он всё же нужен:
1. **Усечь через параметр `dimensions`** до ≤2000 (например, 1024 или 1536) прямо при вызове
   API — самый простой и рекомендуемый OpenAI путь (см. п.6).
2. Сменить тип колонки на **`halfvec`** (pgvector) — лимит HNSW удваивается до 4000 измерений
   при вдвое меньшем размере хранения на вектор.
3. Для >4000 измерений — тип **`bit`** (бинарная квантизация, лимит до 64 000) — не наш случай.
4. **DiskANN** (сторонняя альтернатива HNSW/IVFFlat) нативно поддерживает `vector` до 16 000
   измерений — если он доступен в используемом дистрибутиве Postgres/pgvector.

**Рекомендация для проекта 06**: не тянуть `text-embedding-3-large` в дефолтных 3072 —
это создаёт скрытую ловушку (индекс либо не строится, либо требует `halfvec`, которую
рядовой Docker Compose стек курса скорее всего не настраивает). Проще и надёжнее взять
`text-embedding-3-small` (1536, уже ≤2000) как значение по умолчанию.

## 6. Усечение размерности (dimension truncation)

Обе модели v3 официально поддерживают параметр `dimensions` — обучены техникой, позволяющей
обменивать часть качества на меньший размер вектора (matryoshka-подобный приём). Задокументированный
в гайде пример: `text-embedding-3-large`, усечённый до **256** измерений, всё ещё превосходит
**полный** (1536-мерный) `text-embedding-ada-002` по MTEB. При ручном усечении (не через API,
а пост-фактум обрезкой вектора) документация требует повторной L2-нормализации, иначе
свойства эмбеддинга теряются.

Практический вывод: `text-embedding-3-large` с `dimensions=1536` (укладывается в лимит HNSW
без `halfvec`) должен по качеству быть не хуже, а вероятно лучше полного `ada-002` — это
легитимный путь получить качество large-модели и совместимость с обычным HNSW-индексом
одновременно, если `text-embedding-3-small` окажется недостаточно точным на реальных
PDF/сайтах клиентов.

## 7. Self-hosted альтернативы (для контекста — не по докам OpenAI)

**Vision (проект 04, распознавание блюда):**
- `Qwen2.5-VL` / `Qwen3-VL` (Alibaba) — 7B версия при INT4-квантизации помещается в
  ~6–8 ГБ VRAM (RTX 4060 Ti / 3090 достаточно); есть готовая динамическая обработка
  разрешения изображений.
- `InternVL3` — 8B в FP8 ≈ 7.8 ГБ VRAM (RTX 4090); 72B-вариант требует уже 2×H100.
- Более лёгкие модели (moondream, PaliGemma 2, LLaVA-OneVision) — вплоть до CPU/малого GPU
  для самых компактных вариантов.
- Качество: научные обзоры 2025–2026 годов прямо отмечают, что открытые VLM всё ещё уступают
  топовым закрытым моделям именно в **тонком распознавании еды** — путают похожие блюда и
  способы приготовления; кроме того, self-hosted модель не даёт официальной гарантии
  Structured Outputs — JSON нужно вытягивать через grammar-constrained decoding
  (например, `outlines`/`guidance`), что добавляет инженерной сложности.
- Когда оправдано: объём на порядки выше учебного (не 10 000, а сотни тысяч/млн фото в месяц)
  либо жёсткое требование не отправлять фото пользователей во внешний API. При 10 000 фото/мес
  и цене API ≈$5–10/мес аренда/владение GPU-сервером для self-hosted VLM экономически не
  оправдана для курса.

**Embeddings (проект 06):**
- `Qwen3-Embedding` (0.6B/4B/8B) — по открытым таблицам занимает верхние строки MTEB на
  начало 2026 года, поддерживает **пользовательскую размерность от 32 до 1024** — то есть
  укладывается в HNSW-лимит pgvector без всяких `halfvec`.
- `bge`/`nomic-embed` семейства — сравнимое с `text-embedding-3-small` качество, размерности
  768–1024, тоже без проблем с индексом.
- Эти модели на порядок легче LLM (сотни млн параметров) и по факту нормально живут даже на
  CPU для скромного трафика — если задача курса — «максимум внутри одного провайдера»,
  self-hosted embeddings этому не мешают технически, но противоречат цели владельца
  «сократить число провайдеров» только в узком смысле (embeddings — не отдельный провайдер
  API-ключей, а локальный контейнер), поэтому это разумная опция для снижения стоимости
  без роста числа внешних интеграций.

## Вывод по проекту 04 (трекер калорий)

- Брать **`gpt-5.6-luna`** (актуальная замена уходящего 11.12.2026 `gpt-5-nano`) с
  `detail: "high"` и Structured Outputs (`strict: true`) для JSON-списка `{name, grams}`.
- Стоимость на масштабе курса (10 000 фото/мес) — **≈$5–10/мес**, не узкое место бюджета.
- Критическое требование проекта («калории — из справочника, а не от модели») механизмом
  Structured Outputs подтверждается лишь частично: гарантирована **форма** JSON, но не
  гарантировано, что `name` точно совпадёт со строкой в справочнике продуктов — нужен
  отдельный слой сопоставления (например, embedding-поиск по номенклатуре продуктов в том же
  Postgres/pgvector).
- Self-hosted vision для масштаба курса не оправдан ни по деньгам, ни по качеству
  распознавания еды.

## Вывод по проекту 06 (продавец на данных клиента)

- Брать **`text-embedding-3-small`** (1536 измерений) как основной вариант — размерность
  сразу укладывается в лимит HNSW-индекса pgvector (≤2000), стоимость индексации сайта+PDF
  копеечная (**$0.01–0.03**).
- **Не брать `text-embedding-3-large` в дефолтных 3072 измерениях** — это не пройдёт
  HNSW-индексацию в обычном pgvector без дополнительной настройки (`halfvec` или урезание
  через `dimensions`). Если нужно качество large-модели — обязательно указывать
  `dimensions=1536` (или меньше) при вызове API, а не урезать вектор постфактум без
  повторной L2-нормализации.
- Ссылка на источник у каждого ответа (обязательное требование проекта) реализуется на уровне
  приложения (метаданные чанка → страница/PDF), это не функция ни embeddings, ни
  Structured Outputs как таковых — эмбеддинги OpenAI не решают и не мешают этому требованию.
- Self-hosted embeddings (Qwen3-Embedding, bge) — жизнеспособная опция снижения стоимости, не
  ломает требование «данные и вектора в нашем Postgres», но добавляет ещё один контейнер с
  моделью — стоит того только если объём документов клиентов курса вырастет на порядки.

## Не подтверждено

- Точный процент MTEB/оценка качества **при усечении** `text-embedding-3-large` до конкретно
  1536/1024 измерений (в докладе OpenAI явно назван только пример с 256 измерениями против
  полного `ada-002`) — по officially задокументированным числам для промежуточных размерностей
  цифр не нашёл, экстраполяция моя.
- Точное среднее число токенов на страницу сайта/PDF (500–800 ток./стр.) — это инженерная
  оценка по опыту работы с текстовым контентом, не число из документации OpenAI; для проекта
  06 стоит замерить на реальном контенте клиента после первого прогона индексации.
- Доступна ли `DiskANN` для pgvector в конкретном образе Postgres, который курс поднимает в
  Docker Compose, — не проверял (это вопрос к используемому образу/расширению, не к OpenAI).
- Официальные бенчмарки OpenAI по распознаванию именно еды/порций (accuracy на реальных
  тарелках) — в открытой документации OpenAI такого раздела нет; фраза про «approximate counts
  for objects» и трудности со «spatial localization» — общая оговорка для vision-моделей, не
  специфичная для еды.
- Множитель ×1.62 для `gpt-4.1-mini` подтверждён одной цитатой из фетча документации, но я не
  нашёл отдельного официального worked-example с числами специально для этой модели (в отличие
  от группы ×1.2) — стоит перепроверить перед использованием этой модели в проде.
