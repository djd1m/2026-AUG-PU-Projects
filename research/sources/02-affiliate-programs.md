### 1.2 Модельные различия — коротко

- **Rewardful / FirstPromoter / Tolt / Post Affiliate Pro** — «чистые» affiliate-трекеры,
  заточенные под SaaS-подписки, интеграция через Stripe/Paddle webhooks. **HIGH** [S-01][S-03][S-05][S-09].
- **PartnerStack / Impact.com** — шире, чем affiliate: partner ecosystem / partnership
  automation (reseller, co-marketing, affiliate — всё в одной платформе), поэтому
  дороже и сложнее в настройке. **HIGH** [S-04][S-07].
- **Refersion** — заточен под e-commerce (Shopify/WooCommerce), а не под подписочный SaaS;
  явная revenue-share модель (% от продаж поверх подписки) — отличается от
  Rewardful/Tolt/Post Affiliate Pro, где комиссии платформы нет. **HIGH** [S-08].
- **Admitad/ePN/Actionpay** — CPA-сети «полного цикла»: не софт для установки на свой
  сайт, а маркетплейс рекламодатель↔вебмастер с собственным трекингом,

  рекламодателя сверх выплат вебмастерам (конкретный % не раскрыт публично). **MEDIUM** [S-12][S-13].

## 2. Механика трекинга

### 2.1 Referral link + cookie: стандартные сроки

- Индустриальный «дефолт» — **30 дней** cookie lifetime; диапазон предложений на
  рынке: от 1 дня (импульсные покупки, Amazon-подобная модель) до 60-90 дней
  и «lifetime» cookie. **HIGH** [S-14][S-15].
- Для **SaaS/B2B** типично **60-90 дней**, так как цикл принятия решения длиннее
  (несколько стейкхолдеров, trial-период, сравнение вариантов). **MEDIUM** (общее
  утверждение из блогов affiliate-индустрии, не из первичного отраслевого
  стандарта/органа) [S-14][S-15].
- Логика выбора: короткое окно (7-30 дней) больше подходит last-click атрибуции
  (фокус на «последнем касании»); длинное окно (60-90+ дней) — first-click
  атрибуции, чтобы не терять партнёра, который «посеял» интерес, но конверсия
  случилась значительно позже. **MEDIUM** [S-15].

### 2.2 First-touch vs last-touch attribution

- **Last-click (last-touch)** — комиссия у партнёра, чья ссылка была последней
  перед конверсией. Проще реализовать технически (последняя перезаписанная
  cookie), но легко эксплуатируется (см. §7 — brand bidding, cookie stuffing). **HIGH** [S-15][S-19].
- **First-click (first-touch)** — комиссия у партнёра, который первым привёл
  визитора. Справедливее для «top-of-funnel» контента (обзоры, сравнения), но
  требует более долгого окна хранения атрибуции и сложнее реализовать без
  server-side решения. **MEDIUM** [S-15].
- Большинство коммерческих платформ (Rewardful и аналоги) по умолчанию используют
  last-touch с перезаписью cookie при повторном клике по другой партнёрской
  ссылке — это стандартная, но не единственная настройка. ⚠️ НЕ ПОДТВЕРЖДЕНО для
  Rewardful конкретно (не нашёл прямого заявления в официальной документации в
  ходе этого ресёрча — нужна дополнительная проверка страницы doc.rewardful.com).

### 2.3 Self-referral fraud

- Определение: партнёр покупает/оформляет подписку сам на себя (или через
  подставные аккаунты), чтобы получить комиссию с собственного платежа. **HIGH** [S-16][S-17].
- Rewardful заявляет встроенную защиту — self-referral detection как часть
  продукта. **MEDIUM** (упомянуто в маркетинговых материалах компании, не
  раскрыт технический механизм детекции) [S-01].
- Общие механизмы защиты по индустрии: сверка email/платёжных данных партнёра с
  данными реферала, блокировка одинаковых IP/device fingerprint между
  партнёром и «его» рефералом, ручная модерация подозрительных
  конверсий перед выплатой. **MEDIUM** [S-16][S-17].

### 2.4 Cookie-less реальность: ITP/Safari, блокировщики

- Safari ITP (Intelligent Tracking Prevention) с определённого момента истекает
  first-party cookie, установленный через JS, в течение **7 дней** после
  клика по рекламной/партнёрской ссылке — то есть конверсия через 8+ дней после
  клика в Safari **не будет атрибутирована** при JS-cookie-подходе. **MEDIUM**
  (утверждение из вторичного индустриального блога, не из документации Apple
  напрямую — стоит перепроверить у Apple WebKit) [S-18].
- Safari и Firefox блокируют third-party cookies по умолчанию и вместе
  составляют, по разным оценкам, **25-35% веб-трафика**. **MEDIUM** [S-18].
- Chrome Privacy Sandbox — по индустриальным прогнозам на 2026 год third-party
  cookies в Chrome должны быть полностью депрекейтed к Q3 2026, что затронет
  ещё ~65% трафика. ⚠️ ЧАСТИЧНО ПОДТВЕРЖДЕНО — сама дата неоднократно
  переносилась Google в прошлом, и точный статус на конкретный день ресёрча
  (26 августа 2026) не верифицирован из первоисточника Google в рамках этого
  ресёрча — помечаю **LOW** для точной даты, **MEDIUM** для общего тренда
  «cookies as attribution deprecating» [S-18].

### 2.5 Обходы: server-side tracking, промокод, postback/S2S, UTM+coupon fallback

- **Server-to-server (S2S) postback**: конверсия подтверждается вызовом с
  бэкенда продавца напрямую на сервер партнёрской платформы (не через браузер
  пользователя) — после подтверждённого события (оплата, регистрация).
  Иммунен к блокировщикам, ITP, отсутствию cookie в браузере. **HIGH** [S-18][S-19].
- **Промокод / coupon-код как атрибут**: каждому партнёру присваивается
  уникальный промокод; конверсия атрибутируется по факту применения кода при
  оплате, а не по cookie клика. Работает без браузерных cookie вообще —
  стандартный cookie-less метод. **HIGH** [S-20][S-21].
- **UTM + coupon fallback**: комбинация — партнёру даётся и уникальная
  UTM-ссылка, и уникальный промокод; трекер сначала проверяет клик/cookie,
  а если сигнала нет — использует применённый промокод как fallback-атрибут.
  Пример многоуровневого приоритета из индустрии (порядок атрибуции):
  1) совпадение купона/promotion code → 2) referral-код в session metadata →
  3) client reference ID → 4) subscription metadata → 5) email-fallback.
  **MEDIUM** (пример конкретной реализации от одной инди-платформы Refgrow, а
  не универсальный стандарт) [S-21].
- Что ломается конкретно: чистый JS-cookie трекинг теряет атрибуцию через
  7 дней в Safari, полностью не работает при VPN/incognito/ad-block с
  агрессивной блокировкой скриптов; чинится комбинацией S2S + промокод как
  primary или fallback, а не только через cookie. **MEDIUM** [S-18][S-20].

## 3. Модели вознаграждения

### 3.1 One-time vs recurring

- **One-time** — фиксированная выплата или % с первого платежа реферала,
  дальше комиссия не начисляется.
- **Recurring** — комиссия начисляется с каждого последующего платежа
  подписчика, пока подписка активна (или пока не истечёт ограниченный срок
  — см. ниже). Recurring — стандарт для SaaS-партнёрок именно потому, что
  выравнивает интерес партнёра с LTV клиента, а не разовой продажей. **HIGH** [S-22][S-23].

### 3.2 Типичные ставки для SaaS (с источниками)

- **20-30%** от выручки — базовый диапазон, наиболее часто цитируемый как
  «industry standard» для recurring SaaS-affiliate программ. **HIGH**, повторяется
  в нескольких независимых источниках [S-01][S-22][S-23].
- До **40%** — для топ-партнёров/высокого объёма (tiered-модель, см. ниже). **MEDIUM** [S-01].
- Более широкий диапазон в B2B SaaS в целом: **15-40%** от суммы подписки
  реферала. **MEDIUM** [S-22].
- Экономическое обоснование: типичная валовая маржа SaaS-стартапа — 75-80%,
  что делает 30% комиссию партнёру устойчивой без разрушения unit-экономики. **MEDIUM** [S-01].

### 3.3 Fixed vs % — bounty за лид

- Fixed bounty за лид (например, фиксированная сумма за квалифицированный
  триал/демо-звонок) чаще используется на входе воронки, когда монетизация
  реферала ещё не подтверждена; % от выручки — когда есть прямая привязка к
  оплате. **MEDIUM** (общее знание индустрии, отдельного цитируемого
  количественного источника на "bounty за лид ставки" в рамках этого ресёрча
  не найдено — ⚠️ ЧАСТИЧНО НЕ ПОДТВЕРЖДЕНО, конкретные диапазоны bounty не
  верифицированы отдельно).

### 3.4 Lifetime vs N месяцев, tiered

- **Lifetime recurring** (пока клиент платит) — самая щедрая, но и самая
  рискованная для unit-экономики модель: при высокой % ставке (например,
  30% lifetime) она "съедает" бюджет на масштабе. **MEDIUM** [S-23].
- Стандартная защита: ограничение recurring-периода **12-24 месяца**, либо
  гибридная модель (меньший % recurring + больший one-time бонус), либо
  ступенчатое снижение ставки после первого года. **MEDIUM** [S-23].
- **Tiered** — ставка растёт с объёмом приведённых партнёром клиентов/выручки
  (например, 20% → 25% → 30% по мере роста MRR от рефералов партнёра),
  цель — удержание топ-партнёров. Общее знание индустрии, отдельно
  количественно не процитировано в данном ресёрче — **LOW** на конкретные пороги.

### 3.5 Hold-период и защита от refund/chargeback

- **Hold-период** — время, на которое платформа задерживает начисленную
  комиссию до выплаты партнёру, чтобы дать возможному возврату/чарджбэку
  «проявиться» до того, как деньги выплачены партнёру. Типичная
  рекомендация — задержка выплаты на **30-45 дней**. **MEDIUM** [S-24].
- **Clawback** (возврат уже выплаченной комиссии): если refund произошёл
  до выплаты — комиссия просто аннулируется (voided); если после выплаты —
  решение платформы/бизнеса — либо вычитать из будущих начислений партнёра,
  либо списывать как убыток. **MEDIUM** [S-24].
- Recurring-модель требует полноценного commission-management (не разовой
  выплаты), так как churn или refund клиента должен автоматически
  остановить/скорректировать будущие начисления партнёру — иначе платформа
  переплачивает. **MEDIUM** [S-24].

## 4. Интеграция с биллингом

### 4.1 Stripe: обязательные webhook-события (по официальной документации Stripe)

Список ниже подтверждён напрямую фетчем страницы `docs.stripe.com/billing/subscriptions/webhooks` — **HIGH**, первоисточник [S-25]:

| Событие | Когда триггерится | Зачем нужно для affiliate-биллинга |
|---|---|---|
| `checkout.session.completed` | При завершении Checkout-сессии | Момент "провижининга" подписки — можно связать сессию с referral-кодом через `client_reference_id` или metadata и создать первую комиссию |
| `invoice.created` | Создан инвойс для новой/продлевающейся подписки | Ранний сигнал о предстоящем платеже |
| `invoice.finalized` / `invoice.finalization_failed` | Инвойс финализирован / не удалось финализировать | Контроль корректности биллинг-цикла |
| `invoice.paid` | Инвойс успешно оплачен | **Основное событие для начисления recurring-комиссии** — каждый успешный платёж = потенциальная комиссия партнёру |
| `invoice.payment_failed` | Платёж не прошёл | Не начислять комиссию; уведомить о риске churn |
| `customer.subscription.created` | Подписка создана | Связать подписку с партнёром-рефералом на старте |
| `customer.subscription.updated` | Подписка изменилась (продление, апгрейд/даунгрейд, купон, trial→active и т.д.) | Пересчёт суммы recurring-комиссии при апгрейде/даунгрейде |
| `customer.subscription.deleted` | Подписка завершена/отменена | Остановить будущие начисления комиссии |
| `customer.subscription.paused` / `resumed` | Пауза/возобновление | Приостановить/возобновить начисления |
| `charge.refunded` | Возврат средств | Триггер clawback-логики (см. §3.5) |

Официальная документация Stripe явно указывает алгоритм связывания
`charge.refunded` → `PaymentIntent` → `InvoicePayment` → `Invoice` →
`Subscription`, так как сам webhook о рефанде не содержит напрямую subscription
ID — это нужно выяснять через цепочку связанных объектов. **HIGH**, дословно
из документации [S-25].

### 4.2 Идемпотентность (Stripe)

- Каждое событие Stripe может быть доставлено **более одного раза** (retries,
  дублирование сети) — обязательно использовать `event.id` для идемпотентности:
  хранить обработанные event ID в таблице с уникальным ограничением и
  проверять/вставлять перед обработкой; если insert падает на unique-violation
  — событие уже обработано, пропустить. **HIGH**, стандартная практика,
  подтверждена несколькими независимыми источниками [S-26].
- Обязательна верификация подписи (`Stripe-Signature` header + webhook
  signing secret `whsec_...`) до какой-либо обработки полезной нагрузки, и
  использование **raw body** запроса (не распарсенного middleware) для
  верификации — иначе подпись не сойдётся. **HIGH** [S-26].
- Рекомендуемый паттерн: верифицировать подпись → положить событие в очередь
  (background job) → сразу вернуть 200 → обрабатывать асинхронно (чтобы не
  тормозить Stripe retry-логику долгими операциями). **MEDIUM** (best-practice
  из вторичных источников, логично согласуется с офиц. документацией
  о повторных попытках Stripe) [S-25][S-26].
- Если Stripe не получает успешный ответ на `invoice.created`, финализация
  всех инвойсов с автоматическим сбором платежа задерживается **до 72 часов**
  (кроме случаев с кастомным временем финализации). В live-режиме Stripe
  повторяет попытки доставки webhook **до 3 дней** с экспоненциальным
  backoff. **HIGH**, дословно из официальной документации [S-25].

### 4.3 Как считать recurring-комиссию и обрабатывать возвраты/даунгрейд

- Recurring-комиссия считается **на каждый `invoice.paid`**, а не один раз при
  подписке — то есть система должна отслеживать подписку на всём её
  жизненном цикле, а не только момент оформления. **HIGH** (следует напрямую
  из структуры Stripe webhook-модели) [S-25].
- При даунгрейде — сумма следующего инвойса меньше, значит и % от неё меньше;
  система должна пересчитывать комиссию от **фактической суммы оплаченного
  инвойса**, а не от суммы на момент привлечения клиента. Явно подтверждено
  как фича Rewardful ("автоматически подстраивает комиссии под даунгрейды,
  апгрейды, трайлы, отмены и возвраты") — **MEDIUM**, маркетинговое заявление
  вендора, механизм не раскрыт технически [S-01].
- При рефанде — см. §3.5 (clawback) и цепочку связывания рефанда с
  подпиской из официальной документации Stripe (§4.1). **HIGH** [S-25].

### 4.4 Российская специфика: ЮKassa, CloudPayments, Продамус

| Провайдер | Webhook-механизм | Ключевые события | Источник |
|---|---|---|---|
| **ЮKassa** | `notification_url`, настраивается в личном кабинете продавца | Уведомление отправляется при переходе платежа в статус `waiting_for_capture` (двухстадийный платёж) или `succeeded` (одностадийный) | **HIGH**, официальная документация [S-27] |
| **CloudPayments** | Webhook/callback на адрес, настраиваемый в Back Office | Несколько типов: `Pay` (успешный платёж), `Fail`, `Recurrent` (изменение статуса подписки на рекуррентных платежах), `Cancel`, `Confirm`, `Refund`. При недоступности сервера продавца или ошибке — до **100 повторных попыток** с нарастающим интервалом (1, 2, 5, 10, 30 минут) | **HIGH**, официальная документация developers.cloudpayments.ru [S-28] |
| **Продамус** | Webhook с проверкой подписи (HMAC) через секретный ключ платёжной страницы | Уведомления об оплате, а также отдельные уведомления об активации/деактивации/реактивации подписки | **MEDIUM** — подтверждено через вторичные интеграционные документы (Salebot, help.prodamus.ru), не через полный прямой фетч официальной документации в рамках этого ресёрча [S-29] |

Важно для дизайна биллинг-интеграции: у ЮKassa и CloudPayments в отличие от
Stripe **нет единого события уровня "invoice.paid" для подписок**, что
характерно для Stripe Billing — рекуррентные платежи и их отслеживание
реализованы иначе (CloudPayments — через `Recurrent`-уведомления,
подписки как отдельная сущность). Это означает, что переносить архитектуру
"один-в-один со Stripe" на российский стек напрямую нельзя — нужен отдельный
слой абстракции. **MEDIUM**, вывод по совокупности найденных данных, не
процитирован дословно ни в одном источнике.

## 5. Дашборд партнёра

### 5.1 Минимальный обязательный набор

По совокупности нескольких независимых источников (индустриальные блоги
affiliate-платформ, не единый стандарт), минимальный набор для партнёрского
дашборда:

1. **Реферальная ссылка** (+ возможность создавать доп. ссылки под конкретные
   кампании/каналы) [S-30]
2. **Клики** — счётчик в реальном времени, историческая динамика (30/60/90 дней) [S-30]
3. **Регистрации / конверсии** — сколько кликов превратилось в лид/триал [S-30]
4. **Платящие клиенты** — сколько из зарегистрированных стали платящими [S-30]
5. **MRR от рефералов** — recurring-метрика, критично для SaaS-модели (не
   найдено как отдельно называемый пункт в источниках, но логически следует
   из recurring-модели — ⚠️ частично экстраполяция, не дословная цитата)
6. **К выплате** — разбивка на три статуса: pending (начислено, не
   подтверждено) / approved (подтверждено, ожидает выплаты) / paid
   (выплачено) [S-30]
7. **История выплат** — лог прошлых транзакций [S-30]
8. **Маркетинг-ассеты** — библиотека креативов (баннеры, тексты) для скачивания [S-30]

**HIGH** для всего пункта 5.1 в целом (список многократно повторяется в
нескольких независимых блогах affiliate-платформ) [S-30][S-31].

### 5.2 Что реально влияет на активацию партнёра

- Прозрачность отчётности напрямую связана с удержанием: по данным одного из
  источников (Fluent Affiliate / индустриальный блог), программы с
  прозрачным дашбордом видят **до 40% более высокое удержание** активных
  партнёров по сравнению с программами с ограниченной видимостью данных.
  **MEDIUM** — цифра из вторичного источника без ссылки на первичное
  исследование/методологию, требует дополнительной проверки [S-30].
- Автоматизация онбординга сразу после регистрации (например,
  автоматическая выдача уникальной ссылки/промокода сразу после подписания
  оферты, без ручного одобрения) и визуализация прогресса по tiered-уровням
  комиссии (badges, progress bar) — называются драйверами вовлечённости в
  нескольких источниках. **MEDIUM** [S-30][S-31].
- Уведомления о новых начислениях/выплатах/обновлениях программы — снижают
  количество вопросов в поддержку и повышают доверие. **MEDIUM** [S-30].

## 6. Юридическое и налоговое в РФ

> ⚠️ **Это справочная информация, собранная из открытых источников, а не
> юридическая или налоговая консультация.** Конкретная схема выплат зависит
> от статуса партнёра, объёма выплат и юрисдикции — обязательна консультация
> с бухгалтером/юристом перед запуском реальных выплат.

### 6.1 Способы оплаты в зависимости от статуса партнёра

- **Самозанятый (плательщик НПД)**:
  - Ставка налога — **6%** при работе с юрлицами/ИП (и по некоторым
    источникам самозанятый может договориться о том, чтобы компания
    компенсировала эти 6% сверху вознаграждения — это предмет договорённости
    сторон, не требование закона) [S-32].
  - Договор с самозанятым может быть заключён в письменной форме **или в
    виде оферты**, а также через обмен электронными документами [S-32].
  - Ограничение: НПД действует, пока годовой доход самозанятого не превышает
    **2,4 млн рублей** в календарном году (с 1 января по 31 декабря,
    независимо от даты регистрации); при превышении — статус плательщика
    НПД теряется до начала следующего года [S-33]. Есть законодательная
    инициатива по повышению лимита до 4,3 млн рублей — на момент ресёрча
    это **предложение**, не принятый закон (⚠️ статус принятия не
    верифицирован дальше уровня "рассматривается Госдумой") [S-33].
  - Компания, выплачивающая самозанятому по чеку НПД, **не является
    налоговым агентом** — самозанятый сам платит налог через приложение
    "Мой налог". **MEDIUM** (логическое следствие природы режима НПД,
    подтверждается общей структурой закона 422-ФЗ, но не процитировано
    дословно в найденных источниках отдельно для affiliate-контекста).

- **Физическое лицо без статуса ИП/самозанятого** (договор ГПХ):
  - Компания, выплачивающая вознаграждение физлицу по гражданско-правовому
    договору, **становится налоговым агентом по НДФЛ** (ст. 226 НК РФ) и
    обязана удержать **13% НДФЛ** в момент выплаты [S-34].
  - Доход от affiliate-выплат физлицу подпадает под ст. 208 НК РФ
    (вознаграждение за оказанные услуги/выполненные действия на территории
    РФ) [S-34].
  - Дополнительно — страховые взносы: по договору ГПХ обычно начисляются
    взносы на ОПС и ОМС (но не на ВНиМ), детали ставок в рамках этого
    ресёрча не проверены отдельно — ⚠️ ЧАСТИЧНО НЕ ПОДТВЕРЖДЕНО, требует
    отдельной проверки у бухгалтера.

- **ИП**: платит налоги самостоятельно по своей системе налогообложения
  (УСН/ОСН и т.д.); компания не выступает налоговым агентом. ⚠️ Общее
  знание налогового законодательства РФ, отдельно не процитировано в
  найденных в рамках этого ресёрча источниках — **LOW** по прямому
  цитированию, но общеизвестный факт налогового статуса ИП.

### 6.2 Что нужно в оферте для партнёра (общие пункты, не юридическая консультация)

На основе общей структуры описанных источников по договорам с самозанятыми и
общей практики affiliate-офert (не найдено единого шаблона "affiliate offer
agreement" под РФ-юрисдикцию в ходе этого ресёрча — раздел ниже частично
экстраполирован из общей практики договоров возмездного оказания услуг,
**LOW/MEDIUM**, требует юридической проверки перед использованием):

- Предмет договора: продвижение продукта по уникальной реферальной
  ссылке/промокоду в обмен на комиссионное вознаграждение
- Условия начисления комиссии (% или fix, от какой суммы, recurring/
  one-time, срок recurring)
- Условия hold-периода и порядок клоубэка при возврате/чарджбэке клиента
- Порядок и периодичность выплат, минимальный порог для выплаты
- Запрет на self-referral, cookie stuffing, brand bidding, incentivized
  traffic — с правом аннулирования начисленной комиссии при нарушении
  (см. §7)
- Статус сторон (не трудовые отношения — договор ГПХ/оферта, не наём)
- Порядок расторжения и удержания уже начисленных, но не выплаченных сумм
  при нарушении правил программы

### 6.3 Риск переквалификации в трудовые отношения

Один из найденных источников упоминает, что налоговые органы получили
критерии для переквалификации отношений с самозанятым в трудовые:
регулярность выплат, единственный заказчик, фиксированный размер
вознаграждения, личное выполнение работы, подчинение внутреннему распорядку
[S-32]. Для типичной affiliate-схемы (много партнёров, вознаграждение прямо
пропорционально приведённым продажам, не фиксированное, не единственный
заказчик у партнёра) риск низкий, но это стоит явно прописать в оферте.
**MEDIUM** — вывод на основе общего упоминания критериев, не специфичен для
affiliate-кейса напрямую.

## 7. Anti-fraud минимум

| Тип фрода | Определение | Типичный сигнал детекции |
|---|---|---|
| **Self-referral** | Партнёр покупает у самого себя (лично или через подставные аккаунты), чтобы получить комиссию с собственного платежа | Совпадение email/платёжных данных/IP между аккаунтом партнёра и "рефералом"; общий device fingerprint [S-16][S-17] |
| **Cookie stuffing** | Установка партнёрского tracking-cookie в браузер пользователя без реального клика по ссылке — часто через скрытые iframe (1x1 px) на сторонних страницах, чтобы "присвоить" органическую конверсию | Анализ referrer-цепочки (last-touch без легитимного referrer), время срабатывания пикселя относительно реального взаимодействия пользователя, аномальное соотношение impression/click [S-19] |
| **Brand bidding** | Партнёр покупает контекстную рекламу по брендовым/трейдмарк-запросам компании, чтобы перехватить трафик, который и так пришёл бы органически/напрямую | Мониторинг выдачи (SERP monitoring) специализированными инструментами или скрапингом + логи рекламных сетей [S-19] |
| **Incentivized traffic** | Партнёр стимулирует пользователей переходить/покупать через кэшбэк, подарки, "заработай деньги" схемы, не раскрытые в условиях программы | Аномально высокий conversion rate у конкретного партнёра, специфичные паттерны трафика [S-19] |
| **Дубликаты / фиктивные лиды** | Множественные регистрации с одинаковыми/похожими данными для накрутки метрик | Одинаковые user-agent, IP, временные метки кликов у "разных" пользователей [S-19] |

Общие индикаторы фрода по индустрии (агрегировано из источников): внезапный
всплеск affiliate-расходов без соответствующего роста выручки; необычно
высокий conversion rate у отдельных партнёров; пустые/подозрительные
HTTP Referrer заголовки; подозрительные паттерны трафика (совпадающие
user-agent/IP/временные метки). **MEDIUM** — обобщение из специализированных
блогов по anti-fraud в affiliate-индустрии, не из академического/
регуляторного источника [S-19].

Минимальный набор защитных мер для собственной реализации (вывод по
совокупности §2.3 и §7, не отдельная цитата):
1. Сверка email/платёжных данных партнёра с рефералами
2. Hold-период перед выплатой (см. §3.5) — даёт время на обнаружение
3. Ручная модерация крупных/аномальных начислений перед approve
4. Явный запрет в оферте на цитируемые виды фрода с правом аннулировать
   комиссию и заблокировать партнёра

## Пробелы и что не удалось проверить

1. **Rewardful — конкретный механизм self-referral detection.** Заявлено
   маркетингово ("built-in self-referral detection"), но техническая
   реализация не раскрыта в открытых материалах, официальная документация
   Rewardful (`docs.rewardful.com`) не была прочитана напрямую в ходе этого
   ресёрча — требуется отдельный визит.
2. **Rewardful — first-touch vs last-touch по умолчанию.** Не найдено прямого
   заявления в официальных материалах компании о том, какая модель
   атрибуции используется по умолчанию и настраивается ли она.
3. **Точный статус дедлайна Chrome Privacy Sandbox на дату ресёрча (26 августа
   2026).** Использован вторичный источник (индустриальный блог), не
   первоисточник Google/Chromium — история переносов этого дедлайна делает
   вторичные источники ненадёжными без прямой проверки blog.google/chromium.
4. **Официальные комиссии платформы для Admitad, ePN, Actionpay.** Не
   найдены публично раскрытые проценты комиссии сети с рекламодателя —
   вероятно, они индивидуальны по договору и не публикуются.
5. **Расхождение цифр Admitad** (2000-3000 рекламодателей; 35 000-300 000
   вебмастеров в разных источниках) — не удалось найти единый официальный
   пресс-релиз с актуальными на 2026 год цифрами для устранения расхождения.
6. **Продамус — полная официальная документация по webhook-событиям.**
   Прочитана только через вторичные интеграционные материалы (Salebot),
   не напрямую через полный текст `help.prodamus.ru` — список событий может
   быть неполным.
7. **Конкретные диапазоны bounty-выплат за лид** (fixed CPL) для SaaS —
   не найдено количественного индустриального бенчмарка в рамках этого
   ресёрча, только общее качественное описание модели.
8. **Страховые взносы при выплате физлицу по ГПХ** (ОПС/ОМС ставки,
   освобождения) — не проверялись отдельно, общий факт налогового агентства
   по НДФЛ подтверждён, но полная картина страховых взносов требует
   отдельной проверки у бухгалтера.
9. **Цифра "40% выше удержание партнёров при прозрачном дашборде"** — взята
   из одного вторичного блога без ссылки на первичную методологию/выборку
   исследования; не удалось верифицировать первоисточник этой статистики.
10. **PartnerStack/Impact.com/Refersion — публичные данные ARR/funding.**
    Не найдено достоверных публичных цифр по выручке/финансированию этих
    частных компаний (кроме заявленных на сайте PartnerStack клиентских
    метрик) — вероятно, эти компании не раскрывают финансовые показатели
    публично.
