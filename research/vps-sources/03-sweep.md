## djd1m/dgx-setup
**Ссылка:** https://github.com/djd1m/dgx-setup
**Доступ:** получен (публичный, клонирован)
**Тип:** набор bash/python-скриптов + Markdown-инструкции (для человека и для AI-кодера параллельно)
**Свежесть:** последний коммит 2026-07-24
**Что даёт:** установка AI-агентов (Ollama, Claude Code, NemoClaw, Hermes, Ouroboros, OpenClaw) на
NVIDIA DGX Spark, но в `scripts/` лежат самодостаточные, платформонезависимые установщики:
`install-claude-codex.sh`, `install-claude-fm.sh` (Claude Code через Cloud.ru Anthropic API, без
докера/туннеля), `install-lm-studio.sh`, `dgx-claude-bootstrap.sh` (VLESS-прокси + LiteLLM за один
проход), плюс `docker-compose.litellm.yml` и `litellm.config.example.yaml` — готовый LiteLLM-роутер
поверх Docker Compose. Каждый факт в документации подписан ссылкой на первоисточник (заявленный
режим "paranoid"), отдельно перечислены найденные риски (неподписанный тег установщика NemoClaw,
неофициальный npm-пакет `hermes-agent`, отсутствие LICENSE у Ouroboros и т.д.).
**Какую задачу VPS решает:** запуск Claude Code / прокси-обвязки на удалённой машине (в т.ч. как
паттерн для обычного VPS — скрипты сами определяют ОС/архитектуру), учёт расхода при работе через
свой прокси.
**Как использовать:** `bash scripts/dgx-claude-bootstrap.sh` — диагностика → xray-прокси → Claude
Code + LiteLLM за один запуск; `bash scripts/install-claude-fm.sh` — Claude Code на моделях Cloud.ru
напрямую, без Docker/туннеля.
**Требования:** Linux-хост (скрипты определяют ОС/архитектуру сами), для части инструкций — aarch64
(GB10), но большинство `scripts/` — платформонезависимые.
**Осторожно:** сами авторы помечают весь стек (кроме Claude Code и Ollama) как экспериментальный
софт, выполняющий произвольные команды в фоне; раздел «Риски» в каждой инструкции — не формальность.
**Пригодность для курса:** высокая — готовые, самодиагностирующиеся установочные скрипты и
LiteLLM/Docker Compose роутер, которые применимы к любому VPS, не только к DGX.

## djd1m/dgx-remote-access
**Ссылка:** https://github.com/djd1m/dgx-remote-access
**Доступ:** получен (публичный, клонирован; репозиторий — один HTML-файл, `index.html`)
**Тип:** единый интерактивный runbook (self-contained HTML) по удалённому доступу и split-VPN
**Свежесть:** последний коммит 2026-06-12
**Что даёт:** пошаговый playbook «доступ К серверу / доступ С сервера / локальные модели» с тремя
уровнями (минимальный/оптимальный/максимальный): WireGuard-сервер на роутере, SSH-хардненинг
(`PasswordAuthentication no`, смена порта, `AllowUsers`), xrdp по VPN (включая фикс «чёрного экрана»
на GNOME/Wayland), **WireGuard-exit на облачном VPS** (реальные команды `wg genkey`,
`iptables MASQUERADE`, `sysctl net.ipv4.ip_forward=1`, systemd-юнит), UFW firewall с конкретными
правилами, vopono (split-tunnel для одного процесса через netns), fail2ban, self-hosted NetBird на
втором VPS как control plane.
**Какую задачу VPS решает:** ровно то, что нужно курсу на «переключение на VPS в облаке» —
подключение к арендованному VPS, защита SSH, организация egress-прокси для Claude Code через VPS
(если регион счёта требует внешний exit-node), firewall/fail2ban.
**Как использовать:** файл самодостаточен — открыть `index.html` (переключатель уровней
min/opt/max), копировать команды блоками; независимая часть (VPS WireGuard-exit, UFW, fail2ban) не
привязана к DGX и переносится один в один на обычный VPS.
**Требования:** Ubuntu на VPS для секции 2.5 (`apt install wireguard`), домашний роутер Keenetic для
части про inbound-доступ (для другого роутера — общий принцип тот же, детали интерфейса другие).
**Осторожно:** упоминает конкретных провайдеров VPS по имени роли (не адресам) — «VPS Нидерланды»
и «VPS cloud.ru» без реальных IP/доменов в тексте инструкции.
**Пригодность для курса:** высокая — по сути готовый чек-лист «получил VPS → защитил SSH → поднял
firewall → (опционально) WireGuard-exit», который прямо ложится на этап курса «перешёл на VPS».

## djd1m/crypto-miner-monitor
**Ссылка:** https://github.com/djd1m/crypto-miner-monitor
**Доступ:** получен (приватный, добавлен через add_repo, клонирован)
**Тип:** разбор реального инцидента безопасности + systemd-watchdog скрипт
**Свежесть:** последний коммит 2026-08-25 (файлы диагностики датированы 2026-05-03)
**Что даёт:** полный постмортем реальной компрометации VPS с курсовыми проектами: два
PostgreSQL-контейнера, поднятые в `docker-compose.yml` с портом `0.0.0.0:PORT:5432` и дефолтным
паролем `postgres`, были взломаны через `COPY ... TO PROGRAM`, внутрь залит XMRig-майнер под видом
`/tmp/mysql`, потребивший ~780% CPU из 800% (8 ядер). Есть: сводка диагностики, полный реестр всех
26 Docker-контейнеров на сервере (по всем проектам курса), разбор бинарника майнера, пошаговый план
устранения (пересоздать контейнер, сменить пароль **и в docker-compose.yml, и в самой БД** через
`ALTER USER`, привязать порт к `127.0.0.1`), и настройка systemd-сервиса `crypto-watchdog`, который
каждые 60 секунд проверяет контейнеры/`/tmp`/`/dev/shm` на сигнатуры майнеров (`xmrig`, `kinsing`,
`cnrig`, `/tmp/mysql` и т.п.) и автоматически лечит заражение.
**Какую задачу VPS решает:** это готовый набор мер и мониторинг для защиты Docker Compose проектов
курса на общем VPS от ботов-сканеров — прямое практическое дополнение к общей архитектуре
«Distributed Monolith + Docker Compose на VPS».
**Как использовать:** `monitor/crypto-miner-watchdog.sh` + `.service`-юнит из `07-watchdog-setup.md`
ставится на любой VPS с Docker; `06-fix-plan.md` — чек-лист «что проверить в своём docker-compose.yml
перед деплоем» (не биндить БД на `0.0.0.0`, сложные пароли, `ALTER USER` при смене пароля в
существующем volume).
**Требования:** Docker + systemd на сервере; скрипт написан под Linux-хост, к которому есть root.
**Осторожно:** ⚠️ в файлах присутствуют реальный домен и факт скомпрометированного API-ключа
стороннего сервиса (замаскированного в тексте самого репозитория) — деталей не привожу; репозиторий
приватный и должен таким остаться.
**Пригодность для курса:** высокая — единственный источник во всей выборке, который документирует
реальную атаку именно на курсовую инфраструктуру (Docker Compose на VPS) и даёт конкретный,
воспроизводимый watchdog для защиты.

## djd1m/aicoding-space-site
**Ссылка:** https://github.com/djd1m/aicoding-space-site
**Доступ:** получен (приватный, добавлен через add_repo, клонирован)
**Тип:** реальный продакшн-проект (Astro-сайт) с полным ADR-пакетом фичи `aicoding-mvp`
**Свежесть:** последний коммит 2026-04-16
**Что даёт:** альтернативный (не-Docker) паттерн деплоя на VPS, обоснованный вдумчивым ADR:
- `ADR-002: Host on Russian VPS (Timeweb Cloud, Moscow)` — сравнительная матрица (Timeweb / Selectel
  / REG.RU / Cloud.ru / CDN-прокси) с причиной: Cloudflare/Vercel/Netlify троттлятся или блокируются
  российскими провайдерами с середины 2025, целевая аудитория — в РФ. Итог: Timeweb Cloud, Ubuntu
  24.04, 1 vCPU/2GB/30GB NVMe.
- `ADR-008: CI/CD — GitHub Actions + rsync + PM2` — вместо Docker Compose: сборка на GHA,
  `easingthemes/ssh-deploy` (rsync `dist/` на VPS), `appleboy/ssh-action` (`pm2 restart`), с явным
  сравнением против варианта «Docker + GHCR» (проигравшего по простоте для команды из 1 человека).
- `ops/ci/` — шаблоны воркфлоу `ci.yml.template`/`deploy.yml.template` (не активные `.github/workflows`
  — по причине нехватки scope `workflow` у токена CI) и `ops/ci/README.md` со списком нужных GitHub
  Secrets (`VPS_SSH_KEY`, `VPS_HOST`, и т.д.).
- `ops/nginx/*.conf` — реальный nginx reverse-proxy конфиг.
- `ecosystem.config.cjs` — PM2-конфиг процесса (память-лимит, пути логов).
**Какую задачу VPS решает:** показывает вариант деплоя статического/SSR-сайта на VPS **без Docker**
(rsync + PM2 + nginx) — актуально для курсовых проектов, которым не нужен полный docker-compose
стек, а также подсвечивает РФ-специфичное соображение о выборе VPS-провайдера (доступность без VPN).
**Как использовать:** `ops/ci/README.md` описывает активацию — скопировать шаблоны в
`.github/workflows/`, задать секреты; `ADR-002`/`ADR-008` — как референс при выборе между Docker
Compose и rsync+PM2 для конкретного типа проекта.
**Требования:** SSH-доступ к VPS, PM2 и nginx на сервере, GitHub Actions.
**Осторожно:** ⚠️ в `ops/nginx/*.conf` присутствует реальный домен проекта — факт отмечаю, содержимое
не привожу.
**Пригодность для курса:** высокая — единственный найденный пример альтернативного (не Docker)
деплоя на VPS с явным обоснованием выбора провайдера под РФ-аудиторию; хорошо дополняет базовый
Docker Compose паттерн курса вариантом «для лёгких сайтов».

## djd1m/2026-PU-APR-LESSON-01
**Ссылка:** https://github.com/djd1m/2026-PU-APR-LESSON-01
**Доступ:** получен (публичный, клонирован)
**Тип:** курсовой проект (Next.js + Prisma), но с полноценным продакшн-деплой-стеком
**Свежесть:** последний коммит на момент `pushed_at` 2026-04-08
**Что даёт:** рабочий пример `docker-compose.prod.yml` с лимитами памяти по сервисам
(`deploy.resources.limits.memory`) и сервисом **Watchtower** (`containrrr/watchtower`) для
автоматического обновления образов на сервере; `Caddyfile` с автоматическим HTTPS/Let's Encrypt,
редиректом на WebSocket upgrade, security-заголовками (HSTS, X-Frame-Options) и ротацией логов —
альтернатива nginx, требующая меньше ручной настройки TLS. Плюс три конкретных «грабли» в
`myinsights/`: `node:20-alpine` требует `apk add openssl` для Prisma-движка (`INS-006`),
обязательный `.dockerignore` с `node_modules` (иначе Docker копирует host-бинарники под неверную
платформу поверх `npm ci`, `INS-008`), и отсутствие `DATABASE_URL` в `.env.example` ломает Prisma
молча (`INS-003`).
**Какую задачу VPS решает:** типовые проблемы докеризации Node/Prisma-приложения перед деплоем на
VPS + паттерн авто-обновления контейнеров через Watchtower вместо ручного `docker compose pull`.
**Как использовать:** взять `docker-compose.prod.yml` + `Caddyfile` как шаблон вместо связки
nginx + certbot; проверить свой `.dockerignore` и `.env.example` по списку insights.
**Требования:** Docker + Docker Compose v2, переменные `DOMAIN`/`ACME_EMAIL` для Caddy.
**Осторожно:** Watchtower смонтирован на `/var/run/docker.sock` — даёт контейнеру полный доступ к
Docker-демону хоста, это осознанный компромисс ради автообновления, а не бесплатная опция.
**Пригодность для курса:** средняя-высокая — хороший образец готового prod docker-compose с
Caddy+Watchtower и конкретный список докер-граблей для Node/Prisma стека, который встречается в
нескольких курсовых проектах.
