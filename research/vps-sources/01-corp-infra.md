# Кластер corp-infra (djd1m) — путеводитель по настройке VPS

Шесть приватных репозиториев одного набора: превращают чистый VPS в рабочую
корпоративную инфраструктуру (git, трекер, вики, сайт, VPN, обратный прокси,
мониторинг, бэкапы, AI-оператор). Все шесть — свежие (единственный коммит от
2026-07-29, "Initial commit"), т.е. это цельный, недавно спроектированный набор,
а не заброшенный старый код. Признаков реального боевого использования (issues,
история изменений, багфиксы) нет — судя по всему, это подготовленный дизайн/каркас,
ещё не обкатанный на реальном VPS.

Порядок применения жёстко зафиксирован и одинаков во всех шести README:

```
security → vpn-proxy → backup → ent-infra → pop-agents
```

(`bootstrap` — умбрелла/оркестратор над всеми пятью этапами.)

## djd1m/corp-infra-bootstrap
**Ссылка:** https://github.com/djd1m/corp-infra-bootstrap
**Доступ:** получен
**Тип:** bash-скрипты + JSON-конфиги (профили, провайдеры, схемы) + документация
**Свежесть:** последний коммит 2026-07-29 (единственный, "Initial commit")
**Что даёт:** умбрелла-репозиторий набора. Сам почти ничего не устанавливает — это
оркестратор: разведка окружения (`recon.sh`), профили размещения сервисов по
RAM/диску (`profiles/*.json`), каталог ограничений хостинг-провайдеров
(`providers/*.json`), общая shell-библиотека (`lib/common.sh`), которая
байт-идентично вендорится в остальные пять реп, и state-машина пяти этапов
(`bootstrap.sh`).
**Какую задачу VPS решает:** отвечает на вопрос «какой профиль (набор сервисов)
влезет в мою машину» и запускает остальные пять репозиториев в правильном
порядке, не давая перейти к следующему этапу, пока предыдущий не подтверждён
живой проверкой (а не просто маркером).
**Как использовать:**
```bash
git clone https://github.com/<org>/corp-infra-bootstrap.git /opt/corp-infra/bootstrap
/opt/corp-infra/bootstrap/scripts/recon.sh --json | python3 -m json.tool
sudo /opt/corp-infra/bootstrap/scripts/bootstrap.sh --profile core-16
# проверка арифметики профиля без установки:
./scripts/sizing-check.sh --static --all
# сводная проверка "всё ли на месте", ничего не меняет:
./scripts/doctor.sh
```
Профили: `all-in-one-32` (8 vCPU/32GB/500GB, всё включая OpenProject),
`core-16` (по умолчанию, 8/16GB/350GB, без OpenProject), `two-vps-split-a/b`
(разнесение на две машины). `minimal-8` официально не поддерживается.
**Требования:** VPS (bare), root для `bootstrap.sh`; recon и sizing-check можно
гонять без root — они ничего не меняют.
**Осторожно:** сам `bootstrap.sh` вызывает установочные скрипты остальных пяти
реп с правами root — то есть транзитивно правит firewall, ssh, systemd,
секреты. Прямых опасных операций в самой репе немного (recon/sizing —
безопасны, только `bootstrap.sh --yes` мутирует систему через остальные репы).
Секретов, реальных IP или доменов в репозитории не обнаружено — только
плейсхолдеры и описания политики провайдеров (adminVPS KZ/RU, Yandex KZ).
**Пригодность для курса:** высокая — это готовая точка входа и понятная карта
всего процесса; `recon.sh --json` и `sizing-check.sh --static` можно безопасно
дать студентам как первый шаг «посмотреть на свою VPS», не рискуя ничего сломать.

## djd1m/corp-infra-security
**Ссылка:** https://github.com/djd1m/corp-infra-security
**Доступ:** получен
**Тип:** bash-скрипты + документация + `.sops.yaml`
**Свежесть:** последний коммит 2026-07-29 (единственный, "Initial commit")
**Что даёт:** базлайн защиты чистого VPS (этап 1 из 5) и схему шифрования
секретов для всего набора. Два независимых блока: (1) hardening хоста — sshd,
ufw (с цепочкой DOCKER-USER), fail2ban, unattended-upgrades, sysctl, auditd; (2)
политика секретов — генерация age-ключа, `.sops.yaml` с тремя ролями
(prod/ci/break-glass) и обязательная процедура key-escrow с человеком.
**Какую задачу VPS решает:** первое, что делается на чистой машине — запирает
периметр (SSH keys-only, deny-by-default firewall) и настраивает шифрование
секретов (sops+age), от которого зависят все остальные пять репозиториев.
**Как использовать:**
```bash
# 1. Диагностика без изменений
sudo ./scripts/harden.sh --check
# 2. Применение базлайна (только на выделенном VPS!)
sudo ./scripts/harden.sh --yes --profile core-16
# 3. Человек кладёт age-ключ в два места (вне этой машины) и подтверждает
sudo ./scripts/age-escrow.sh --attest <fingerprint> \
     --add-location 'team-password-manager:<сейф>:2' \
     --add-location 'offline:<где лежит>:1'
# 4. Проверка закрытия этапа
sudo ./scripts/harden.sh --check && echo STAGE-1-OK
```
Дополнительно: `scripts/request-port.sh` — единственный разрешённый способ
открыть порт (напрямую `ufw allow` использовать нельзя), `scripts/secrets-init.sh`
— инициализация/ротация sops-политики.
**Требования:** root; отдельный (не shared, не dev) VPS — сам README прямо
предупреждает не запускать `harden.sh` на общей машине.
**Осторожно:** ОЧЕНЬ опасный скрипт. `harden.sh --yes` перезагружает sshd,
включает ufw и запускает fail2ban на той машине, где вызван — при ошибке можно
потерять доступ к серверу. Порт 22 намеренно остаётся открытым на `0.0.0.0`
до готовности VPN (`vpn.ready`), сужение до VPN-подсети требует явного
break-glass IP или консоли провайдера — без него скрипт откажется сужать.
Секретов в репозитории нет: `.sops.yaml` содержит только плейсхолдеры
получателей, реального `AGE-SECRET-KEY-...` в коде нет (наоборот, есть grep-guard
в CI и в самих скриптах, которые проверяют отсутствие приватного ключа в git).
**Пригодность для курса:** высокая, но с предупреждением — отличный образец
дисциплины (проверки перед мутацией, break-glass), но студентам нужно явно
объяснить необратимость `harden.sh --yes` без подготовленного запасного доступа
(альтернативный SSH-ключ/консоль провайдера) до запуска.

## djd1m/corp-infra-vpn-proxy
**Ссылка:** https://github.com/djd1m/corp-infra-vpn-proxy
**Доступ:** получен
**Тип:** bash-скрипты + docker-compose (Caddy) + шаблоны конфигов + документация
**Свежесть:** последний коммит 2026-07-29 (единственный, "Initial commit")
**Что даёт:** сетевой периметр (этап 2 из 5) — WireGuard-хаб как единственный
вход в админ-зону и два инстанса Caddy (публичный + VPN-only внутренний) как
единственный способ опубликовать любой сервис. Три сетевые зоны: PUBLIC,
VPN-ONLY, LOCALHOST-ONLY — разделены топологией docker-сетей, а не только
авторизацией.
**Какую задачу VPS решает:** даёт защищённый удалённый доступ (VPN) и
безопасную публикацию веб-сервисов с автоматическим TLS через Caddy, не
открывая внутренние панели (GitLab, Grafana и т.п.) напрямую в интернет.
**Как использовать:**
```bash
sudo ./scripts/install-wireguard.sh --check
sudo ./scripts/install-wireguard.sh --profile core-16 --yes
sudo ./scripts/wg-user.sh --qr add anna     # добавить пира ДО сужения SSH
sudo ./scripts/install-proxy.sh --domain example.com --yes
sudo ./scripts/install-proxy.sh --check && sudo ./scripts/register-vhost.sh --check
```
`register-vhost.sh` — единственный способ опубликовать новый сервис (прямая
правка Caddyfile запрещена конвенцией репозитория).
**Требования:** предполагает, что этап 1 (`security`) уже закрыт (маркер
`security.hardened`); root; открытые исходящие домены/DNS для ACME (Let's
Encrypt).
**Осторожно:** порядок шагов «поднять wg0 → добавить пира → потом сужать SSH»
нельзя переставлять — иначе после сужения SSH можно остаться отрезанным от
сервера без работающего VPN-пира. Также специально отказались от веб-UI для
WireGuard (упоминают CVE-2026-44343 в WGDashboard, CVSS 9.3) — управление
только через CLI-скрипты. VPN-хаб запрещён офертой adminVPS в локациях
Беларусь/Казахстан — это прочитано из `providers/*.json`, а не зашито в код.
Секретов в репозитории нет — `secrets/wg.enc.env.example` явно плейсхолдер,
реальные приватные ключи и домены (`example.com`, `wiki.corp.example.com`)
только в документации как примеры.
**Пригодность для курса:** высокая — WireGuard + Caddy с автоTLS — практически
универсальный паттерн для любого VPS-курса, а трёхзонная модель сети хорошо
иллюстрирует принцип "security by topology, не только by auth".

## djd1m/corp-infra-backup
**Ссылка:** https://github.com/djd1m/corp-infra-backup
**Доступ:** получен
**Тип:** bash-скрипты + один Python-скрипт (`dr-coverage-check.py`) + systemd
timers/units + документация
**Свежесть:** последний коммит 2026-07-29 (единственный, "Initial commit")
**Что даёт:** инфраструктуру резервного копирования по схеме 3-2-1 на базе
restic: локальная копия на VPS + offsite (Backblaze B2 по умолчанию, либо
Yandex Object Storage KZ, либо Hetzner Storage Box), systemd-таймеры, реестр
манифестов бэкапа для отдельных сервисов, скрипты восстановления и
"тренировки" (test-restore) с журналом `drills.jsonl`.
**Какую задачу VPS решает:** делает потерю сервера обратимой — при условии, что
age-ключ и пароль restic escrow-ированы отдельно от VPS. Устанавливается
специально ДО появления реальных данных (этап 3 из 5), чтобы ни один сервис не
"забыли" добавить в бэкап.
**Как использовать:**
```bash
sudo ./scripts/install-backup.sh --check
sudo ./scripts/install-backup.sh --yes --offsite b2
sudo ./scripts/backup.sh --yes                       # первый прогон
sudo ./scripts/test-restore.sh --scenario single-file # обязательные "учения"
sudo ./scripts/backup.sh --check
```
**Требования:** зависит от закрытого этапа `security` (нужен подтверждённый
escrow age-ключа, маркер `secrets.escrow.ok` — иначе `install-backup.sh`
физически не стартует); offsite-провайдер и его credentials.
**Осторожно:** `scripts/restore.sh --apply` — деструктивная операция
(перезаписывает данные на месте). Осознанно жёсткая политика: отсутствие
offsite-цели — это ошибка (exit 1), а не "работаем в одну копию"; `forget`/
`prune` на offsite никогда не выполняется программно (offsite-креды не имеют
права delete — защита от ransomware). Секретов не обнаружено:
`secrets/backup.enc.env.example` — только плейсхолдеры, реальный
`RESTIC_PASSWORD` в примерах отсутствует.
**Пригодность для курса:** высокая — restic 3-2-1 с обязательными "учениями
восстановления" (test-restore) — редкая для учебных курсов, но крайне ценная
дисциплина; хорошо ложится на модуль про надёжность/DR.

## djd1m/corp-infra-ent-infra
**Ссылка:** https://github.com/djd1m/corp-infra-ent-infra
**Доступ:** получен
**Тип:** docker-compose + bash-скрипты + документация
**Свежесть:** последний коммит 2026-07-29 (единственный, "Initial commit")
**Что даёт:** сами бизнес-сервисы (этап 4 из 5) — GitLab CE + CI-раннер,
observability-стек (Prometheus/Loki/Grafana/Alertmanager/Alloy/node_exporter/
cAdvisor/blackbox), трекер (OpenProject CE, опционально по профилю), wiki
(BookStack), статический сайт (Hugo через Caddy). Каждый сервис — это
compose-файл + backup-манифест + vhost-регистрация ("service unit" — единица
установки, неполный набор из трёх частей считается провалом `--check`).
**Какую задачу VPS решает:** разворачивает "рабочее место команды" —
git-хостинг, CI, трекер задач, вики и мониторинг, — интегрированное с бэкапом
и внутренним прокси из предыдущих этапов.
**Как использовать:**
```bash
./scripts/install-gitlab.sh --check
./scripts/install-gitlab.sh --yes --domain example.com \
    --external-url https://gitlab.corp.example.com
./scripts/install-observability.sh --yes --domain example.com
./scripts/install-wiki.sh --yes --domain example.com
./scripts/install-tracker.sh --yes --domain example.com
./scripts/install-site.sh --yes --domain example.com --build
```
**Требования:** этапы 1-3 (`security`, `vpn-proxy`, `backup`) должны быть
закрыты — маркеры `backup.ready`, `proxy.ready`, `vpn.ready` проверяются живой
проверкой, а не просто наличием файла; профиль ≥16GB RAM (в `core-16`
OpenProject не ставится — недостаточно памяти, это штатное поведение, а не
баг); docker, docker compose.
**Осторожно:** `external_url` GitLab, по словам README, нельзя менять после
установки — важное предупреждение перед первым запуском. Сам репозиторий не
трогает firewall/VPN напрямую (публикация только через vhost-скрипт
`vpn-proxy`), но поднимает тяжёлые сервисы (GitLab потребляет 8-12GB RAM) —
неверный профиль приведёт к OOM. Секретов не обнаружено — все `secrets/*.env.example`
только плейсхолдеры.
**Пригодность для курса:** средняя-высокая — полезно как референс "что вообще
можно поднять", но GitLab CE тяжёл для учебного VPS с ограниченным бюджетом;
для курса вероятно интереснее как источник паттернов (service-unit контракт,
backup-манифесты), чем как то, что каждый студент разворачивает целиком.

## djd1m/corp-infra-pop-agents
**Ссылка:** https://github.com/djd1m/corp-infra-pop-agents
**Доступ:** получен
**Тип:** bash-скрипты + sudoers-конфиг + runbooks (документация)
**Свежесть:** последний коммит 2026-07-29 (единственный, "Initial commit")
**Что даёт:** AI-оператора (`opsagent`) с жёсткой моделью привилегий —
пять root-обёрток (`inspect.sh`, `doctor.sh`, `service.sh`, `backup-inspect.sh`,
`restore-file.sh`) и три тира прав: R1 (только чтение, делает сам агент), R2
(недеструктивные изменения после `--check`), R3 (деструктивное/необратимое —
физически недоступно агенту, команд просто нет в sudoers). Плюс набор
runbook'ов на типовые алерты (диск, бэкап устарел, сертификат истекает,
контейнер упал и т.д.).
**Какую задачу VPS решает:** даёт возможность безопасно подключить
AI-агента/автоматизацию к продакшн-VPS для диагностики и рутинных операций, не
рискуя тем, что агент сможет удалить бэкапы, поменять firewall или получить
root через docker-группу.
**Как использовать:**
```bash
sudo ./scripts/install-agent.sh --check   # на чистом хосте вернёт exit 1 — это ожидаемо
sudo ./scripts/install-agent.sh --yes
sudo ./scripts/install-agent.sh --check   # 7 гейтов должны быть зелёными
```
**Требования:** этапы 1-4 должны быть закрыты (маркер `agents.ready` ставится
последним); учитывается, что `opsagent` НЕ должен быть в группе `docker`
(иначе это эквивалент root — прямо назван "единственный недосмотр, который
молча обнуляет всю модель", INV-POP-1).
**Осторожно:** это репозиторий именно про безопасность привилегий — сам
sudoers-файл (`sudoers/60-opsagent`) читал: там ровно 5 команд без wildcard-
аргументов, "deny by omission" для всего остального. Обнаружил в
`scripts/scrub-log.sh` тестовые строки-образцы вида
`restic password=hunter2hunter2` и `-----BEGIN OPENSSH PRIVATE KEY-----` — это
не реальные секреты, а тестовые данные для проверки работы лог-скраббера
(маскировки секретов в логах перед отправкой в Loki), но при переиспользовании
кода стоит убедиться, что это не спутают с настоящими значениями.
**Пригодность для курса:** высокая для продвинутого модуля — отличная
демонстрация принципа "минимальные привилегии по построению" (команды
физически отсутствуют в sudoers, а не просто запрещены политикой), но требует,
чтобы все четыре предыдущих этапа уже стояли — не самостоятельный кусок для
новичков.

## Итог по цепочке для курса

Для 8-недельного курса, где студенты рано или поздно переходят с Claude Code
Web/Codespaces на VPS, естественная последовательность внедрения кусков этого
набора:

1. `corp-infra-bootstrap` (recon + профиль) — безопасно показать всем, ничего
   не ломает.
2. `corp-infra-security` (`harden.sh`) — обязательный, но с явным
   предупреждением о risk of lockout.
3. `corp-infra-vpn-proxy` — WireGuard + Caddy, второй базовый навык курса.
4. `corp-infra-backup` — restic 3-2-1 с обязательными "учениями"
   восстановления, хорошая тема для отдельного занятия про надёжность.
5. `corp-infra-ent-infra` и `corp-infra-pop-agents` — тяжелее и специфичнее
   (GitLab, AI-оператор), скорее опциональный/продвинутый трек, чем
   обязательный для всех.
