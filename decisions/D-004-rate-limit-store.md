# D-004: Где живут счётчики anti-fraud

**Дата:** 2026-08-26 · **Проект:** 01-testimonials-senja · **Статус:** принято агентом-архитектором

## Контекст

Валидация нашла системный пробел (W-1): три Must-требования — rate limit формы (5/IP/час),
детект накрутки по партнёрскому коду (>50 регистраций/10 мин), защита от массового создания
проектов (>20/час) — существовали только как Gherkin-сценарии и не имели места в архитектуре.

Все три — один класс задачи: счётчик событий в скользящем окне.

## Варианты

| Вариант | За | Против |
|---|---|---|
| **Таблица Postgres** ← выбрано | Ни одного нового контейнера; b-tree индекс отдаёт `COUNT` за доли мс на нашем масштабе | Растёт таблица, нужна очистка |
| Redis | Естественный инструмент для счётчиков и TTL | Четвёртый контейнер, новый режим отказа, новая зависимость |
| In-memory в приложении | Нулевая цена | Не переживает рестарт, ломается при нескольких инстансах |

## Решение

**Таблица `rate_limit_events (scope, key, created_at)`** с индексом `(scope, key, created_at)`.
Единый помощник `insert + count over window` в `packages/db`, вызывается из трёх API-роутов.
Очистка старых строк — раз в час силами существующего `services/worker`, без нового сервиса.

## Обоснование

Ключевое — **прецедент в самом документе**: для очереди видео уже был выбран Postgres
`SKIP LOCKED` вместо Redis/BullMQ. Добавлять Redis теперь означало бы завести четвёртый
контейнер и новый режим отказа ради `COUNT`, который на масштабе «одна неделя, один VPS»
индекс отдаёт мгновенно.

Агент нашёл этот прецедент сам и остался последователен, вместо того чтобы притащить
привычный стек.

## Когда пересмотреть

Если появится несколько инстансов приложения под нагрузкой либо окна станут секундными —
Redis станет оправдан. На масштабе курса это не наступит.
