# D-005: TLS-терминация и раздача виджета

**Дата:** 2026-08-26 · **Проект:** 01-testimonials-senja · **Статус:** принято агентом-архитектором
**Формализовано:** `docs/ADR.md` → ADR-007

## Контекст

Валидация нашла (W-3): Caddy стоял в docker-compose без ADR, хотя решение критично.

Настоящая причина, а не «нужен HTTPS»: **виджет грузится на чужие сайты, которые на HTTPS.**
Скрипт по HTTP браузер заблокирует как mixed content — молча, только в консоли.
То есть badge loop, единственный канал роста продукта, физически не запустится.

## Варианты

| Вариант | Вердикт |
|---|---|
| **Caddy** ← выбрано | Автоматический Let's Encrypt из коробки, конфиг в несколько строк |
| nginx + certbot | Тот же результат, но выпуск и обновление сертификатов настраиваются руками |
| Traefik | Тоже автоTLS, заметно сложнее конфигурация |
| Cloudflare Tunnel | Отклонён: уводит компонент во внешнее облако — тот же класс конфликта, что с Supabase |
| Без reverse-proxy | Отклонён: TLS негде терминировать |

## Решение

**Caddy** как reverse-proxy с автоматическим TLS. Он же отдаёт `widget.js` с агрессивным
`Cache-Control` (файл версионируется по content-hash, поэтому кэш не мешает релизам).

Согласуется с существующим паттерном владельца: Caddy уже используется в его
`corp-infra-vpn-proxy`.

## Что описано отдельно

Поведение при провале выпуска сертификата Let's Encrypt: backoff, что видит посетитель,
требование к порядку DNS→деплой, риск упереться в лимиты при потере тома `caddy_data`.

## Как переиграть

Замена сервиса в `docker-compose` + правка ADR-007. Не затрагивает код приложения.
