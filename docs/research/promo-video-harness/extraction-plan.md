# promo-video-harness — план выделения

Дата: 2026-10-02. Статус: минимальное направление согласовано владельцем; реализация и публикация ещё не выполнены.
Исходная ревизия: `3b84e9ef5ce68fdbdcf34e0d1671bace8006aff4`.
Байты выбранных `promo/`, `.claude/skills/promo-video/` и исследований
совпадают с текущей рабочей веткой N6b на момент анализа.

## Рекомендация

Выделить небольшой самостоятельный harness для промороликов веб-продуктов:
сценарий → разрешённые входы → запись экрана → монтаж → проверки → отчёт.
Сохранить Remotion и существующие проверки. Для первого релиза не строить SaaS,
новый движок оркестрации, npm-сервис или универсальный видеоредактор.
Название репозитория: `promo-video-harness`; имя навыка остаётся `promo-video`.
Владелец ответил «согласен» на предложение минимального standalone-варианта.
Это фиксирует направление; аудит прав и готового export остаётся этапом релиза.

Начальная версия репозитория: предлагается `v0.1.0`, beta, на основе навыка 1.2.

Практический результат для пользователя: из чистого clone воспроизводится
45-секундный ролик одного локального демо-продукта в 16:9, 9:16 и 1:1.
Человек либо агент пользуется одним набором сценариев, конфигов и проверок.
Первая заявленная платформа — Linux + Docker + Bash; другие ОС не объявлять
поддержанными до проверки. Голос и музыка остаются отдельными будущими решениями.

Установка одного `SKILL.md` не устанавливает runtime. В quickstart нужны две
раздельные операции: получение полного harness и подключение навыка выбранному
агенту. Конкретные команды установки проверяются на чистой машине перед релизом.
Перенос канонического навыка в `skills/` можно сделать отдельным последующим
изменением; две расходящиеся копии навыка не поддерживать.

## Подтверждённые связи со старой средой

1. `promo/remotion/shared/render.sh:15–19`: абсолютный каталог assets, имя образа,
   общий lock и `/var/log/crypto-watchdog/watchdog.log`. На новой машине рендер
   откажет без частного журнала, даже если все видео-инструменты установлены.
2. `scripts/capture.sh:15–33`, `stills.sh`, `gate-config.sh`, `render-run.sh`:
   вычисление корня через четыре уровня, частичные override-переменные,
   фиксированные образы и пути. Сейчас override описан как испытательный.
3. `scripts/gate-dirty.sh:16–23` и `gate-git.sh:12–24`: правила Git привязаны
   к `promo/*`. Это ещё одна причина сохранить поддерево в первом переносе.
4. `shared/scripts/in-container.sh:9`: путь конкретной сборки Chromium.
   Проверять доступность согласованной пары Playwright/браузер; не скачивать
   произвольный latest во время capture/render.
5. `SKILL.md:42–49` и `modules/06-swarm-protocol.md:97–104`: роли назначены Claude/Codex, а ссылки ведут на внутренние
   правила, исследования и исторические результаты. В публичной версии нужны
   роли coordinator/producer/independent reviewer и локальные документы.
   Проверка не должна зависеть от чужого codex-companion plugin: подтверждать
   реальный reviewer attempt и квитанцию через доступный adapter.
6. Полный сквозной запуск именно навыка 1.2 ещё не подтверждён
   (`SKILL.md:160–178`). Перенос файла не устраняет этот пробел.

## Небольшой контракт среды

Один общий загрузчик настроек для существующих скриптов, а не новый конфиг-движок.
Пути разрешаются относительно harness или явно заданного workspace; валидация
не допускает выход за разрешённые каталоги. Настройки: каталог assets/output,
образ capture/render, lock, CPU/memory/concurrency, способ наблюдения за
контейнером и разрешённый адрес capture. Значения записываются в квитанцию прогона.
Профиль текущего VPS становится дополнительным адаптером.

Отсутствие частного watchdog не должно притворяться `watchdog=clean`.
В переносимом профиле фиксируются exit/timeout/OOM/restart события Docker;
отдельный host watchdog явно `not_applicable` или `unavailable`. Проверки,
зависящие от включённого адаптера, при отсутствии данных возвращают 2.
Сохранить контракт кодов 0/1/2: проверено / дефект / не выполнено.

Предлагаемый интерфейс, пока **не реализован**:

```text
bin/promo-video doctor
bin/promo-video capture demo
bin/promo-video render demo
bin/promo-video verify demo
```

CLI вызывает существующие скрипты и возвращает их исходы. Истина о результате —
полученный отчёт и квитанция конкретного прогона, а не успешный запуск оболочки.

## Публичный код, данные и лицензии

Экспортировать только явный список файлов в новый репозиторий с новой историей.
Перед экспортом проверить сами файлы, symlink-цели, адреса, metadata и примеры;
`.gitignore` не удаляет уже отслеживаемые материалы. Не включать `.env`, cookies,
фикстурные пароли, API-ключи, сырые записи, логи реальных клиентов и чужие бренды.
Это план проверки, а не заключение, что весь существующий набор уже проверен.

Для собственного кода предлагается MIT после подтверждения права на публикацию;
лицензия корневого репозитория в проверенной инвентаризации не обнаружена.
Remotion подключается зависимостью и сохраняет отдельные условия лицензирования;
его код не перелицензируется нашей LICENSE. Правила бесплатного использования и
Company License нужно описать ссылкой на актуальные официальные условия.
Лицензии шрифтов сохраняются; для FFmpeg/кодеков и Docker-образа фиксируются
происхождение и необходимые notices. Лицензия кода не выдаёт права на сторонние
видео, музыку, интерфейсы или товарные знаки.

`project.config.ts` и recorder — исполняемый код, а не безопасные данные.
Исполнять только доверенные конфиги/скрипты в выделенной среде; контейнерам не
давать Docker socket, домашний каталог или секреты хоста. Capture — только по
разрешённому адресу, с локальными synthetic данными в CI и без provider spend.
Чужие контейнеры не останавливать, публикуемые host-порты — только loopback.
При переносе исправить `capture.sh:35–37`: отсутствующий lockfile не генерируется
молча, release требует проверенный lockfile. Установку зависимостей отделить
от записи; lifecycle scripts оставлять только после проверки необходимости.
Не запускать untrusted config/npm manifest с доступом к секретам или
на общем privileged self-hosted CI runner.

## Последовательность выделения и критерии принятия

| Этап | Результат и обязательная проверка |
|---|---|
| A. Export | Allowlist snapshot и карта происхождения; отсутствие внутренних ссылок, секретов и непредусмотренных assets |
| B. Portability | Параметризованные скрипты и переносимый профиль; отсутствующая среда даёт 2, дефект даёт 1 |
| C. Demo | Собственный локальный UI, recorder, пять сцен, три раскладки, явная маркировка демонстрационных данных |
| D. Clean-clone | Новый каталог/чистая Linux среда; установка из lockfile, реальный capture, полный render 1.2, media/log/receipt/transition gates |
| E. Review | Независимый обзор всех форматов и опасных стыков; доказательства кадров и титров привязаны к SHA256 результата |
| F. Public beta | README EN/RU, ограничения, notices, release tag и короткий проверенный quickstart |

Обязательны отрицательные случаи: потерянный input, испорченный media/config,
устаревшая квитанция, verdict от другого SHA, нарушение demo-interval и ошибка
рендера. После восстановления того же входа положительный случай проходит.
Проверка на чистом окружении должна работать без путей и watchdog нашего VPS.

CI: сначала быстрые проверки и сценарии ворот; отдельно полный synthetic render.
Зафиксированные зависимости и минимальные права workflow; никаких capture
секретов в PR. Не исполнять предоставленные извне конфиги с доверенными токенами.
Скриншоты, сырые записи и тяжёлые видео — временные artifacts/локальный output;
дистрибутивный demo публикуется только как отдельный разрешённый release asset.

Повторный SHA256 проверяется внутри закреплённого окружения. Побайтное совпадение
на разных ОС/CPU не обещается. Визуальный просмотр остаётся отдельным шагом:
автоматические ворота не доказывают отсутствие цены/бренда или правдивость титра.

## Независимые выводы роя и измерения

Два независимых read-only прохода подтвердили жизнеспособность минимального
переноса. Portability: удалить частные пути/watchdog и plugin/vendor-зависимость,
перенести полный runtime closure, сохранить layout и gates. Publication review:
проверить права/точный export, доверие к исполняемым TS-конфигам, lifecycle scripts,
лицензии и свежий полный запуск 1.2. Нового движка оба прохода не требуют.

Фактические модели: **gpt-6.1-sol high** (portability, 156.399 с) и
**gpt-6-astra high** (publication review, 113.853 с); подтверждены отдельными
host rollout `turn_context`, а не пожеланием в промпте. Сумма ограниченных
проходов: 270.252 с. Полное время координатора, чтения до запуска, согласования
и подготовки отчёта не измерено; стоимость подписки и usage координатора null.

Профиль: read-only extraction analysis, без реализации фичи и E2E.
Проверки: независимая статическая инвентаризация и source-map; оба исполнителя
exit 0. Изменения кода, реальные release gates и runtime тесты не выполнялись.
Это согласованный план, а не сертификат готовности public-пакета.
Машиночитаемые host-счётчики: [analysis-run.json](analysis-run.json).
