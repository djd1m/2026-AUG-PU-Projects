## 1. Что ЗАСТАВЛЯЕТ агента фазы 3 прочитать документы фичи

**Механизма нет. Есть только текст инструкции.**

- `.claude/commands/feature.md:103` — «1. Read SPARC docs from Phase 1»
- `.claude/rules/feature-lifecycle.md:91-93` — «Identify independent work units from
  Phase 1's Architecture» / «Each Task: read SPARC sections + implement + test + commit»

Это предложения в markdown-файле, адресованные модели. Ни хука, ни гейта, ни скрипта,

- `.claude/settings.json` — все хуки (`SessionStart`, три `Stop`) занимаются вставкой
  инсайтов и автокоммитом roadmap/insights/plans. Ни один не смотрит на `docs/features/`.
- Гейт качества фазы 3 — `.claude/rules/feature-lifecycle.md:97` и таблица `:118`:
  **«tests pass, lint clean, build succeeds»**. Все три условия выполнимы кодом,
  написанным без единого взгляда в `01_specification.md`: тесты пишет тот же агент
  фазы 3, что и код.
- `scripts/check-pipeline-gaps.sh` — единственная детерминированная проверка трассировки
  в репозитории. Она сверяет `docs/Specification.md` ↔ `docs/Pseudocode.md`

  и **никогда не смотрит в код**. Про `docs/features/<slug>/` она не знает вовсе.

Вывод: связь «документ → код» на фазе 3 держится на добросовестности агента. По лестнице
стоимости обнаружения (корневой `CLAUDE.md`) это **слой 4-5** — «агент прочитает, если
вспомнит», при том что предмет проверки (упомянуто ли требование в реализации/тесте)

которых **ни один не вызывал HTTP-маршрут** — покрывался только `lib/login.ts`. Дыру

### Сценарий отказа для дыры в NFR-009.2

`warmUpDummyHash` в продакшене не вызван, значит `dummyPromise` создаётся при **первом
запросе с несуществующим email после каждого перезапуска процесса** (деплой, рестарт
контейнера, масштабирование реплики). Этот запрос платит **два** argon2 (построение
заглушки + `verify` по ней), запрос с существующим email — **один**. Разница ≈×2 при
argon2 ≈50 мс, то есть десятки миллисекунд — измеримо снаружи.

Практически: атакующий, знающий график деплоя (или просто шлющий пары запросов
регулярно, дожидаясь рестарта), получает одноразовый оракул «существует ли учётка».
Окно узкое, но требование сформулировано без оговорок, а тест его увидеть не может **по
построению**: `apps/web/tests/login.test.ts:69` греет заглушку в `beforeAll` — то есть
тест измеряет ровно тот режим, которого в проде на первом запросе нет.

Второй эффект того же дефекта: построение заглушки происходит **внутри транзакции и под
захваченным advisory-локом** (`login.ts:119` — после `:98`), то есть первый такой запрос
держит соединение пула вдвое дольше. Это ровно тот класс, ради которого писался NFR-009.9.

### Отдельно: критерий приёмки, которому код противоречит

`docs/features/fr-009-login/01_specification.md:73`:
«Пароль в 201 символ отвергается `401` на входе… **argon2 при этом не вызывается**
(проверяется подменой функции)».

Код: `apps/web/src/lib/login.ts:118-120` — длинный пароль подменяется пустой строкой,
после чего `verifyPassword` вызывается **всегда**. argon2 отрабатывает.

Здесь код прав, а документ неверен: пропуск argon2 на этой ветке вернул бы ровно тот
таймингов оракул, который запрещает NFR-009.2 (только различающий не «есть учётка», а
«пароль длиннее 200»). Но:
- документ после этого **не исправлен** — критерий приёмки в `01_specification.md`
  до сих пор требует обратного;
- теста «подменой функции» не существует: `apps/web/tests/login.test.ts:130` проверяет
  только `{ ok: false, tooMany: false }`, вызов argon2 не наблюдается;
- **ничто не сообщило, что критерий приёмки разошёлся с реализацией.** Валидация
  (фаза 2) прошла по документу, реализация (фаза 3) прошла по здравому смыслу, и
  расхождение осталось незамеченным в обе стороны.

### Критерии приёмки без реализующего теста

Из `01_specification.md:55-77` четыре параллельных критерия не имеют ни одного теста —
в `login*.test.ts` нет ни одного `Promise.all`, ни одного одновременного прогона:

- «20 одновременных попыток по одному ключу дают не более 5 обращений к argon2» (`:59`)
- «число одновременно занятых соединений пула не превышает числа СЧИТАЮЩИХ попыток» (`:60`)
- «при занятом локе параллельный запрос отвечает быстрее времени argon2» (`:61`)
- «30 одновременных входов с одного IP по разным email проходят без 429» (`:62`)

То есть механизм NFR-009.8 реализован, но **свойство, ради которого он введён
(лимит не обходится `curl --parallel`), не проверено поведенчески ни разу**. Его
замещает страж по исходнику (`login.test.ts:294`), который проверяет наличие строки
`pg_try_advisory_xact_lock` и отсутствие ждущей формы — это проверка написания, а не
работы. Сценарий отказа: любая будущая правка, оставляющая вызов лока на месте, но
выносящая `exceeded`/`record` из-под него (например, «оптимизация» — считать лимит до
открытия транзакции), пройдёт зелёной и вернёт обход лимита параллельными запросами.

## 4. Ссылки на номера требований в комментариях: проверяется ли машинно

**Нет. Это добросовестность автора, ничем не подкреплённая.**

Факты:

- В `apps/web/src` 17 ссылок вида `NFR-009.N` / `FR-009.N` (по `grep -rno`), распределены
  по 8 файлам. Пример: `lib/login.ts:13,16,19,21,53,116`, `route.ts:1,3`,
  `lib/session.ts:67`, `lib/project.ts:38,43`, `lib/password.ts:13`.
- В `apps/web/tests` — **ноль** таких ссылок. То есть даже связи «требование ↔ проверяющий
  его тест» в артефактах не существует: `login.test.ts` и `login-route.test.ts` описывают
  свойства прозой (`'верная пара -> ok, токен и проекты'`), не идентификаторами.
- Ни один скрипт репозитория не разбирает эти идентификаторы применительно к коду:
  `scripts/check-pipeline-gaps.sh` сверяет ID только между двумя markdown-файлами
  проектного уровня (`:29-35`); `projects/01-testimonials-senja/scripts/` содержит
  `check-cjm.sh`, `check-compose-buildable.sh`, `check-env-wiring.sh`,
  `check-port-conflicts.sh`, `init-test-env.sh` — ни один не касается требований.
- Ни один хук `.claude/settings.json` не проверяет комментарии.

Что это значит на практике. Комментарий `// NFR-009.4` — не утверждение, а украшение:
- ссылка на **несуществующее** требование не будет замечена;
- ссылка, ставшая неверной после правки требования, не будет замечена;
- требование **без единой** ссылки из кода (то есть, возможно, нереализованное) не будет
  замечено. Проверено: в коде нет ни одной ссылки на NFR-009.3 (два лимита), NFR-009.5,
  NFR-009.7, NFR-009.11 и FR-009.1/2 — при этом NFR-009.3 и NFR-009.11 реализованы
  (`login.ts:34-39`, `db/src/index.ts:20`), а NFR-009.5 — тоже (`route.ts:53`).
  Отсутствие ссылки не отличимо от отсутствия реализации без ручного чтения кода.

Именно эту проверку лестница стоимости обнаружения относит к слою 1: «каждый ID из
`01_specification.md` встречается хотя бы в одном файле `src/` или `tests/`» — пять строк
`grep`, детерминированно, без модели. Сейчас она не выполняется вообще.

## 5. Если документ изменится ПОСЛЕ написания кода — заметит ли что-нибудь расхождение

**Нет. Ни один механизм не связывает документ фичи с кодом после фазы 3.**

- Тесты читают код, а не документы. Единственное исключение — три «стража по исходнику»

Это не гипотеза — расхождения уже накопились в этом самом прогоне, и все три живы прямо

1. **Порог тайминг-теста.** `05_completion.md:47` фиксирует «не более чем в 2 раза»;

3. **Тип отказа.** `03_architecture.md:28` фиксирует `{ ok: false }` как реализацию

Сценарий отказа в чистом виде. Требование NFR-009.3 меняется с «5 в час по паре» на,
скажем, «3 в час» — правка одной ячейки в `01_specification.md`. Код
(`login.ts:35`, `PAIR_THRESHOLD = 5`) не изменится; тесты
(`login.test.ts:209`) вычисляют ожидание **из той же константы кода**
(`${PAIR_THRESHOLD + 1}`), поэтому останутся зелёными при любом её значении. Прогон

заметить, что система работает не по требованию, — чтобы человек открыл оба файла рядом.
