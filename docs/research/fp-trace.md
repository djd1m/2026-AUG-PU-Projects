## Вопрос 1. Механизм, заставляющий `02_pseudocode` опираться на `01_specification`

**ЕСТЬ МЕХАНИЗМ НА БУМАГЕ — НА ЖИВОМ ПРОГОНЕ НЕ СРАБОТАЛ НИ РАЗУ.**

## Вопрос 4. Нумерация FR-009.1 / NFR-009.3 как машинный ключ

**МАШИННО ИСПОЛЬЗУЕТСЯ РОВНО В ОДНОМ МЕСТЕ — И ЭТО МЕСТО НЕ ВИДИТ НИ ФИЧЕВЫХ ДОКУМЕНТОВ, НИ
ПОД-НОМЕРОВ, НИ NFR.**

`scripts/check-pipeline-gaps.sh:28-35`:

```bash
if [ -f "$DIR/Specification.md" ] && [ -f "$DIR/Pseudocode.md" ]; then
  miss=$(comm -23 \
    <(grep -ohE 'FR-[A-Z-]*[0-9]{3}' "$DIR/Specification.md" | sort -u) \
    <(grep -ohE 'FR-[A-Z-]*[0-9]{3}' "$DIR/Pseudocode.md" | sort -u))
```

Четыре ограничения, каждое проверено:

1. **Гранулярность — фича целиком, не требование.** Регулярка `[0-9]{3}` обрывается на трёх
   цифрах. Прогон по фичевой спецификации:
   ```
   $ grep -ohE 'FR-[A-Z-]*[0-9]{3}' 01_specification.md | sort -u
   FR-009  FR-010  FR-011
   ```
   Пять различных требований `FR-009.1 … FR-009.5` схлопываются в один токен `FR-009`. Одной
   ссылки где угодно достаточно, чтобы «трассировка» показала ✅ для всех пяти.
2. **Только `FR`, не `NFR`.** В fr-009 несущие свойства (побайтово одинаковый ответ, тайминг,
   атомарность счётчика, единственная точка выдачи сессии) — все `NFR-009.*`. Ни одно из них
   для скрипта не существует.
3. **Только уровень проекта.** Пути жёстко `$DIR/Specification.md`, `$DIR/Pseudocode.md`, где
   `DIR="${1:-.}/docs"` (`:6`). `docs/features/**` не обходится.
4. **Не блокирует.** Ветка расхождения печатает `⚠️` и, в отличие от соседних проверок,
   **не выставляет `FAIL=1`** (`:33-35`).

**Killer-сценарий, который этим и пропущен.** Живой прогон:

```
$ bash scripts/check-pipeline-gaps.sh projects/01-testimonials-senja
PR-003 трассировка Spec→Pseudo ✅
```

Зелёный. При этом:

```
$ grep -c "FR-009" docs/Specification.md   → 0
$ grep -c "FR-009" docs/Pseudocode.md      → 0
$ grep -ci "логин\|вход в систему\|/api/auth/login" docs/Specification.md → 0
```

Вход в систему **не существует как требование проекта** (`FR-001…FR-008`, дальше `FR-GROWTH-*`).
При этом `docs/Architecture.md:455` на него опирается («тот же контракт „владелец залогинен →
есть `account_id`“»), а `docs/Refinement.md:188` строит на нём интеграционный тест («войти
владельцем A»). Это ровно та формулировка, которую фича записала о себе сама:
`01_specification.md:17-19` — «вход **потерян между документами**: архитектура его
предполагала, требование не описало, псевдокод не реализовал».

Проверка `comm -23 Spec Pseudo` направлена вперёд и по построению не может это увидеть: она
ищет требования, не дошедшие до алгоритмов, а здесь архитектура опирается на требование,
которого нет. Пропущенное требование лежит в направлении, которое проверка не проверяет, — и
скрипт отвечает ✅ именно потому, что искать нечего.

В самих документах фичи нумерация работает как **украшение с одним исключением**:
`03_architecture.md:45-53` — таблица «Что фича меняет в существующем коде» с колонкой «Почему
обязательно», где стоят `NFR-009.6`, `FR-009.4`, `FR-009.3`, `NFR-009.10`, `NFR-009.11`. Это
единственный в фиче случай ID-как-ключа. Он появился в ревизиях **[v2]** и **[v5]**, то есть
задним числом после разбора блокеров, а не по требованию пайплайна.

## Вопрос 6. Что происходит при ревизии документа

**НЕТ МЕХАНИЗМА. Ничто не перепроверяет соседей после правки — и это единственная причина, по
которой цикл fr-009 остановился.**

Ревизий было пять: `46b734b` (рев. 2) → `185a613` (рев. 3) → `4e4cd43` (рев. 3.1) →
`faccc52` (рев. 4) → `56d4e9a` (цикл остановлен) → `09bd3ff` (рев. 5, D-010) → `0589bd8`
(правка после ревью). Пометки `[v2]…[v5]` — единственный след ревизии; они проставляются
руками автора, машинно не собираются и не сверяются между документами.

Что сказал сам пайплайн (`validation-report.md:294-303`):

| Ревизия | Вердикт | Блокеры | Кто их внёс |
|---|---|---|---|
| 1 | 🔴 | 4 | исходный план |
| 2 | 🔴 | 3 | **2 из 3 — правки ревизии 1** |
