## Проверка здравости чисел (решение координатора: неверные числа в кадр не берём)

Перед сценами 3–4 скрипт читает `GET /api/v1/scans/{id}` и требует для каждой сопоставленной позиции запись
USDA из ожидаемого набора и ккал/100 г в окне (яблоко 45–65, банан 80–100). Итог: **пройдено** — одна позиция
«Яблоко», 200 г, `Apples, raw, with skin (Includes foods for USDA's Food Distribution Program)`, FDC 171688,
52 ккал/100 г → 104 ккал; после +50 г — 250 г, 130 ккал, Б 0,8 / Ж 0,5 / У 34,5 г. Числа здравые.

Счётчик `paid_total` — в `.state-n4.json` (600), переживает перезапуск; при `paid_total ≥ 3` новое распознавание
не запускается. После отказа prep новое распознавание запускается только с `ALLOW_AFTER_PREP_FAIL=1`.

## Находка: синонимы стенда сдвинуты

Проверка координатора (read-only, с разрешения владельца, 2026-09-29): `food_item` — 7 928 строк, `food_synonym` —
253; модель отработала (2,6 с, ok). Отказ prep `no_food_matched` — потому что распознанным названиям («блины с
ягодами», «авокадо») нет синонимов. Хуже: часть синонимов сопоставлена НЕ с теми позициями USDA:

| Синоним | Указывает на | Ожидаемо (по смыслу, не сверено с базой) |
|---|---|---|
| яйцо варёное | Butter | Egg, whole, cooked, hard-boiled |
| гречка варёная | Oats | Buckwheat groats, cooked |
| мёд | Buckwheat | Honey |
| морковь | Cabbage | Carrots, raw |

Верные (использованы для выбора фото): яблоко → «Apples, raw, with skin», банан → «Bananas, raw», апельсин →
«Oranges, raw, navels», груша → «Pears, raw», сыр → «Cheese, cheddar», лук → «Onions, raw». Поэтому в кадре
яблоко, а не салат. Дефект данных поднят владельцу координатором; стенд и данные исполнитель не трогал.

## Что НЕ снято / замечания для монтажа

- **Бейдж на карточке — «Тарелка»** (плашка с логотипом в верхней зоне), а не текст «распознано в Тарелке».
  Титр сцены 4 обещает ровно то, что видно (см. SCENARIO.md).
- **Карточка обрезает фото** (`object-fit: cover` 9:16): яблоко видно частично, тарелка слева — свойство продукта.
- **Итог дня — одно блюдо** (130 ккал): prep не дал второй записи. Стрик «1 день».
- **После правки порции появляется плашка расхождения** «Оценка по фото: 104 ккал · Из базы: 130 ккал» с кнопками —
  честное поведение продукта, в кадре сцены 3 mobile около 1 с до прокрутки вверх.
- **Строка степпера на 390 px не помещается**: «применить» обрезано до «прим», «+10 +50» прижаты к краю
  (видно на mobile и в узкой колонке desktop). Дефект вёрстки продукта; код продуктов не меняли — «не снято
  чисто, нужна правка», на кадр пускать коротко.
- Diary desktop после «минус 50 г» показывает 130 ккал: запись дневника фиксируется при первом «в дневник»
  (mobile, 250 г), повторное подтверждение её не пересчитало. В ролик брать diary только mobile.
- Не показывали: `/pro`, оплату, кабинет, партнёрку, `/r/…`, вход — заблокированы маршрутом (срабатываний 0).
  На главном экране в навигации видна надпись «кабинет» — это ссылка, экран не открывался.
- Голых IP в кадре нет.

## Как повторить

```bash
cd promo/capture
docker run --rm --memory=1500m --cpus=2 --shm-size=1g --name promo-capture-n4 \
  -v "$PWD:/work" -v /home/dz-projects-2026/.promo-assets/n4:/assets -w /work/n4 \
  mcr.microsoft.com/playwright:v1.60.0-noble \
  bash -c "npm ci --no-audit --no-fund && node record-n4.mjs"
```

Без публикации портов. `STEPS=probe` — только кадры `/` (бесплатно). По умолчанию `prep,mobile,desktop,card`.
При существующем `.state-n4.json` скан не повторяется: перезапись сцен идёт по сохранённому `scanId` без
платного вызова. Отличие скрипта в git от прогона 08:20: ожидание экрана результата опрашивает элементы с
таймаутом 200 мс (в прогоне — 30 с, отсюда хвост `capture-*`) и подпись счётчика «mobile: яблоко».
