# PR-014: Сгенерированный compose не пробрасывает переменные, от которых зависит выдаваемое наружу

**Класс:** неполная генерация + отсутствует верификационный слой · **Приоритет:** P0
· **Найдено:** пользователем на развёрнутом стенде, прогон `/run mvp`

## Проблема

Пайплайн сгенерировал `docker-compose.yml`, где у сервиса `web` в `environment`
перечислены `DATABASE_URL`, `SESSION_SECRET`, `S3_*`, `PAYMENT_*` — но **нет `BASE_URL`**,
хотя код читает его для построения КАЖДОЙ выдаваемой наружу ссылки, а `.env.example`
эту переменную объявляет.

Симптом на живом стенде: владелец регистрируется на `https://proofwall.example.com`,
и дашборд выдаёт ему

```
Форма сбора   http://localhost:3000/f/aicoding-space
Стена любви   http://localhost:3000/w/aicoding-space
Виджет        <script src="http://localhost:3000/widget.782bc3db.js" ...>
```

То есть ссылки на машину ПОСЕТИТЕЛЯ. Форма сбора не откроется у клиента, виджет не
загрузится на сайте владельца, а `badge_url` — единственное звено, которым продукт
попадает к новым людям, — ведёт в никуда. Для продукта, вся ценность которого в петле
роста, это отказ функции, а не косметика.

## Почему это не поймал ни один существующий контроль

Разбор честный, потому что он и есть суть заявки:

| Контроль | Почему промолчал |
|---|---|
| Старт контейнера | Переменная НЕ обязательна для запуска: код падает на разумный дефолт `http://localhost:3000`. Приложение здорово |
| Юнит-тесты (376 шт.) | Проверяют функции. `buildProjectUrls('acme')` с подставленным BASE_URL работает верно — сломана не функция, а то, что до неё не доехало значение |
| Проверка сборки compose | Смотрит, собираются ли образы и есть ли исходники. Полноту `environment` не смотрит никто |
| Браузерная UI-проверка | Открывала страницы ПО ОТДЕЛЬНОСТИ и каждая отвечала 200. Ссылки при этом были неверные — но их никто не открывал |

Общая черта: **все контроли проверяли компоненты, и ни один — согласованность
конфигурации с тем, что продукт отдаёт наружу.**

## Исправление, часть 1: полнота проброса — проверяемо машинно

Правило генерации: если переменная читается кодом сервиса, она обязана быть в
`environment` этого сервиса — либо стоять в ЯВНОМ списке исключений.

Готовая реализация — `scripts/check-env-wiring.sh` (проверена на проекте 01, ловит
именно этот дефект и возвращает 1). Две ошибки, допущенные при её написании и потому
описанные здесь отдельно — генератор воспроизведёт их, если не предупредить:

**1. Опираться на `.env.example` нельзя.** Первая версия сверяла три множества и
требовала, чтобы переменная была объявлена в `.env.example`. На этом же прогоне
выяснилось, что **`BASE_URL` отсутствовал и в нём** — то есть проверка, опирающаяся
на этот файл, исходный дефект пропустила бы. Сверять надо ДВА множества: что читает
код и что передаёт compose. Неполный файл нельзя брать опорой.

**2. Регулярное выражение обязано включать цифры.** `process\.env\.[A-Z_]+` обрезает
`S3_ENDPOINT` до `S` и даёт ложное срабатывание. Нужно `[A-Z][A-Z0-9_]*`.

Ядро проверки:

```bash
# что код сервиса читает (с ЦИФРАМИ в имени)
used=$(grep -rhoE 'process\.env\.[A-Z][A-Z0-9_]*' "$svc_dir/src" | sed 's/.*env\.//' | sort -u)
# что compose ему передаёт
passed=$(docker compose config | sed -n "/^  ${svc}:/,/^  [a-z]/p" \
         | grep -oE '^[[:space:]]+[A-Z][A-Z0-9_]*:' | tr -d ' :' | sort -u)
# разница минус ЯВНЫЙ список исключений (NODE_ENV и т.п.)
comm -23 <(echo "$used") <(echo "$passed") | grep -vxE "$ALLOWED"
```

Список исключений должен быть явным: молчаливое «ну эта переменная и не нужна» —
ровно тот механизм, которым дефект и проходит.

Проверено в обе стороны: с убранными `BASE_URL`/`APP_DOMAIN` — два ❌ и код 1;
с восстановленными — зелено.

## Исправление, часть 2: отсутствует сквозная проверка пути клиента

Одной проверки полноты мало: она поймала бы эту ошибку, но не поймает следующую того же
класса (неверный `APP_DOMAIN`, прокси, срезающий заголовок, опечатка в домене). Нужен
контроль, который проверяет ПРОДУКТ, а не его части.

Пайплайн такого слоя не имеет вовсе: `requirements-validator` проверяет документы,
`brutal-honesty-review` — код, `verify` — наличие артефактов. **Никто не проходит путь
пользователя на развёрнутом экземпляре.**

Предлагаемый артефакт — `scripts/check-cjm.sh`, генерируемый Phase 3 под CJM проекта.
Реализация и проверка на проекте 01 — 14 шагов:

```
регистрация → выданные ссылки указывают НА ЭТОТ ЖЕ адрес → ссылки ОТКРЫВАЮТСЯ
→ клиент оставляет отзыв → до модерации на витрине пусто → владелец одобряет
→ отзыв появился → badge ведёт сюда же с метками источника
```

Ключевая проверка — не «ссылка есть», а **«ссылка ведёт сюда»**. Именно её отсутствие
и пропустило дефект.

Проверено в обе стороны: с контейнером без `BASE_URL` скрипт даёт пять ❌ с точным
диагнозом и подсказкой причины (код возврата 1); с исправленным — проходит целиком.

### Отдельная находка внутри самой проверки

Первая версия скрипта считала карточки на витрине через `grep -c`, то есть СТРОКИ.
HTML приходит одной строкой, поэтому и одна карточка, и пять давали единицу — проверка
«отзыв виден» проходила бы независимо от результата. Считать надо совпадения
(`grep -o | wc -l`), и с `-i`, потому что React отдаёт атрибут как `itemType`, а grep
регистрозависим.

Это стоит записать в сам шаблон проверки: генератор, который создаст такой скрипт,
воспроизведёт ошибку, если её не предусмотреть.

## Почему P0

Дефект не ломает ни один зелёный индикатор и при этом делает продукт неработоспособным
для пользователя. Ровно тот профиль, против которого написана лестница стоимости
обнаружения: пропуск не оставляет следов.

Обнаружен он не пайплайном и не агентом, а **владельцем продукта, открывшим ссылку
руками** — то есть самым дорогим из возможных способов.
