# PR-034: Граница «4+ файла → /feature» одномерна, и потому не исполняется

**Класс:** правило без градаций подменяется вкусом исполнителя · **Приоритет:** P1 · **Найдено:** 2026-09-01…02, реализация проекта 02

## Проблема

`feature-lifecycle.md` задаёт единственный порог: фича, трогающая 4+ файла, обязана идти
через `/feature` (PLAN → VALIDATE → IMPLEMENT → REVIEW). Порог одномерный — только число
файлов, — и практика показала два следствия:

1. **Он ложно-положителен.** После полного SPARC-комплекта Phase 1 фичи на 5–8 файлов
   корректно делались напрямую: их план уже существовал в Specification и Pseudocode,
   и фаза PLAN внутри /feature дублировала бы готовое.
2. **Он ложно-отрицателен по рискам.** Число файлов не отличает CSS-правку от новой
   роли СУБД. Пять дефектов стыка прогона 02 (гранты, RLS, ON CONFLICT) жили в фичах,
   чей файловый счёт не выделял их из остальных, — а выделили бы признаки «новая роль»,
   «новый грант», «внешний вызов».

В результате решение «через /feature или напрямую» принимает исполнитель на вкус —
то есть правило живёт на слое 4 и не исполняется как правило.

## Прецедент решения

`@dzhechkov/skills-feature-adr` содержит Complexity Router (Step 0): тиры S/M/L/XL,
классификация по шести измерениям, принудительный тир через `args.tier`, артефакт
`00_complexity_assessment.md`. Механика проверена в другом харнессе и переносима.

Одна правка при переносе обязательна: измерения там **балльные** (1–4 каждое), то есть
суждение. По урокам PR-018/PR-030 признак обязан быть **да/нет-проверяемым чтением
диффа или постановки**: «трогает ли схему» — факт, балл «риск 3 из 4» — вкус.

## Что предлагается

Шаг-роутер перед `/feature` и `/go` в самом p-replicator:

1. **Таблица признаков, сверху вниз, первое «да» задаёт тир; сомнение = «да».**
   XL: деньги · несущий инвариант · необратимая миграция данных.
   L: новая таблица/роль/грант/политика · новый публичный путь · новый внешний вызов ·
   пересечение границы контейнера.
   M: смена существующего публичного контракта или поведения.
   S: остальное. T: тривиальное.
2. **Маршрутизация:** XL → /feature + остановка на плане; L → /feature; M → напрямую с
   обязательным набором (страж+мутация, конкурентный тест при разделяемом ресурсе,
   перекрёстное чтение пары документов, полный прогон всех наборов); S → код+тест+мутация.
3. **Скидка за свежие документы:** если SPARC-комплект моложе недели и FR с алгоритмом
   существуют — L опускается до M (PLAN уже сделан). XL не опускается никогда.
4. **Принудительный тир** словами владельца, фиксируется в артефакте как forced.

## Способ проверки

Ретро-классификация реализации проекта 02 (таблица в `complexity-router.md`): роутер
относит к L ровно те четыре работы, где случились все пять дефектов стыка, и к S/M —
те, где прямой путь оказался верным. Разделение совпало с фактическим исходом.
