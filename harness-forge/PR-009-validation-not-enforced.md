# PR-009: Phase 2 и ре-валидация не запускаются автоматически

**Класс:** gate объявлен, но не исполняется · **Приоритет:** P0 · **Найдено:** прогон проекта 01

## Проблема

Пайплайн объявляет валидацию обязательной, но **не запускает её сам** и **не проверяет,
что она была выполнена**. Оба гейта держатся на дисциплине оператора.

## Доказательство — Phase 2 не форсируется

`.claude/commands/replicate.md`, раздел Critical Rules:

> ### NEVER
> - Never skip validation — toolkit is built on validated docs

Правило есть. Механизма нет: ничто не мешает перейти от Phase 1 сразу к Phase 3.
Ни проверки существования `docs/validation-report.md`, ни проверки вердикта в нём.

На прогоне проекта 01 Phase 2 была запущена **вручную координатором**. Если бы оператор
её пропустил, пайплайн отчитался бы об успехе, а Phase 3 построила бы тулкит на
непровалидированных документах — ровно то, что правило запрещает.

**Цена пропуска, измеренная на этом прогоне:** Phase 2 нашла **4 блокера**, среди них
stored-XSS в контенте, который рендерится на чужих сайтах (одна отравленная запись = JS
на каждом сайте клиента), и полное отсутствие сценариев для мульти-арендной изоляции.

## Доказательство — ре-валидация не предусмотрена вовсе

`.claude/rules/feature-lifecycle.md` описывает возврат на Phase 1 при вердикте 🔴 и
«max 3 retries». Но после итерации правок **повторная проверка не предусмотрена** —
ни как шаг, ни как правило.

На прогоне это привело к конкретному дефекту: блокер B-4 (проверка подписи платёжного
вебхука) был «закрыт» добавлением Gherkin-сценария в `Specification.md`, тогда как в
`Pseudocode.md` не было **ни строки** проверки, а секрета не было ни в архитектуре, ни в compose.

Обнаружила это только **специально запущенная** ре-валидация со скептической установкой
«искать сценарии, которые выглядят проверкой, но ничего не проверяют». Штатный пайплайн
считал блокер закрытым.

Дополнительно: при ручной починке выяснилось, что дефект был глубже — подпись обязана
проверяться **до** записи идемпотентности, иначе поддельный вебхук с угаданным `event.id`
блокирует настоящий. Ни сценарий, ни алгоритм этого не выражали.

## Исправление

### 1. Гейт входа в Phase 3 (слой 1)

```bash
test -f docs/validation-report.md || { echo "Phase 2 не выполнялась"; exit 1; }
grep -qE '🟢|🟡' docs/validation-report.md || { echo "вердикт 🔴 или отсутствует"; exit 1; }
```

Три строки. Делают объявленное правило исполняемым.

### 2. Обязательная ре-валидация после итерации правок (слой 3)

Добавить в цикл: правки → **ре-валидация** → вердикт. Ре-валидатор получает установку
искать не отсутствие требований, а **фиктивное закрытие**: сценарий есть, реализации нет.

Формулировка установки, которая сработала на прогоне:
> «Типовой способ обмануть валидацию — добавить сценарий, который выглядит как проверка,
> но ничего не проверяет. Ищи именно это.»

Без такой формулировки ре-валидатор склонен подтверждать закрытие по факту наличия текста.

### 3. Счётчик итераций

`feature-lifecycle.md` называет «max 3 retries», но механизма подсчёта нет. Завести
явное поле в отчёте валидации: `Итерация: N из 3`.

## Связь с другими заявками

Дефект «сценарий есть, реализации нет» описан отдельно в
[PR-003](PR-003-scenario-without-implementation.md) — там предлагается grep-diff трассировки
`Specification` ↔ `Pseudocode`. Настоящая заявка про другое: про то, что сам цикл проверки
не замкнут.

## Проверка исправления

Пропустить Phase 2 и попытаться запустить Phase 3 — гейт должен остановить.
Закрыть блокер текстом без реализации — ре-валидация должна поймать.
