# PR-005: Параллельные агенты разъезжаются — нет фиксации канона до старта

**Класс:** отсутствует синхронизация · **Приоритет:** P1 · **Найдено:** итерация правок проекта 01

## Проблема

Пайплайн поощряет параллельную работу агентов над разными файлами — это правильно и быстро.
Но когда агенты правят **связанные** документы, они принимают несогласованные решения об
именах сущностей, и рассинхрон обнаруживается только постфактум.

Правило «каждый агент пишет только в свои файлы» защищает от конфликтов записи,
но **не защищает от расхождения содержания**.

## Доказательство

Три агента параллельно правили `Specification`, `Architecture`+`ADR`, `Pseudocode`+`Refinement`.
Агенту по архитектуре было поручено зафиксировать канонические имена — он создал раздел
«Канонические имена» с таблицей.

Агент по псевдокоду закончил **раньше** и честно отметил:

> «Отдельного раздела "Канонические имена" в Architecture.md пока нет — использованы имена
> из основного текста, это отмечено во врезке»

В результате: `Architecture` установила канон `transcript` / `transcript_status` /
`transcript_source`, а `Pseudocode` остался на `video_transcript` / `pending_transcription`.
Расхождение устранял человек вручную.

**Второй случай в том же прогоне:** архитектура спроектировала единый механизм счётчиков
`rate_limit_events`, чтобы не дублировать логику, а псевдокод использовал три несвязанных
стора — потому что писался параллельно.

## Дополнительное наблюдение

Расхождение имён было не косметическим. Канон вводил `transcript_status enum(pending,
completed, failed)` вместо булева `pending_transcription` — и в псевдокоде стоял комментарий:
«Architecture не описывает отдельный failed-статус, наблюдаемость через logError, не через
схему». То есть **неудачная транскрипция существовала только в логах**, потому что автор
алгоритма не знал о принятом решении. Рассинхрон имён скрывал рассинхрон возможностей.

## Предлагаемое исправление

### 1. Фаза фиксации канона ДО параллельного запуска (слой 3)

Перед фан-аутом агентов — отдельный короткий шаг: зафиксировать имена сущностей, таблиц,
полей, путей и событий в одном месте (`Architecture.md` §Канонические имена или отдельный
`GLOSSARY.md`). Агенты стартуют **после** этого и обязаны ссылаться на канон.

### 2. Grep-guard на запрещённые имена (слой 1)

Как только канон зафиксирован, список «не использовать» становится машинно-проверяемым:

```bash
# из таблицы канона: колонка "Не использовать"
grep -rn 'video_transcript\|pending_transcription\|widget_install_events' docs/ && exit 1
```

### 3. Правило для координатора

Если агент сообщает «раздела X ещё нет, использовал своё» — это **сигнал рассинхрона**,
а не примечание. Координатор обязан проверить расхождение после завершения всех агентов.

В прогоне это сработало: агент честно предупредил, и человек проверил. Но полагаться на
внимательность координатора — слой 4.

### 4. Порядок зависимостей при фан-ауте

Агент, устанавливающий канон, должен завершаться **до** тех, кто им пользуется.
Либо канон выносится в отдельный предварительный шаг (см. п.1) — это надёжнее.

## Проверка исправления

Запустить два агента параллельно на связанных файлах без предварительной фиксации канона
и убедиться, что guard ловит расхождение имён.
