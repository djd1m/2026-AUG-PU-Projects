# Паттерн: приёмка сквозным путём клиента на развёрнутом стенде

## Maturity: 🔴 Alpha · Извлечено: 2026-08-27 · Источник: `projects/01-testimonials-senja` · v1.0

## Когда применять

Всегда, когда система **выдаёт наружу артефакт, которым потом пользуются**: ссылку,
код для встраивания, письмо, QR, вебхук-адрес, файл. Такой артефакт содержит куски
конфигурации, и конфигурация — единственное место, которое юнит-тест не видит.

## Задача, которую паттерн решает

Отличить два состояния, неразличимые для тестов и для healthcheck:

- система работает;
- система **работает, но выдаёт наружу нерабочее**.

Реальный случай: `BASE_URL` не был объявлен в compose. Приложение стартовало (тихий
дефолт), 407 тестов зелёные, все страницы открывались, контейнеры здоровы — и при этом
**каждая** выданная владельцу ссылка вела на `http://localhost:3000`, то есть на машину
посетителя. Дефект нашёл пользователь, а не проверка.

## Несущее правило

> Проверка обязана **пользоваться тем, что система выдала**, а не запрашивать адрес,
> который она знает сама.

Это единственное, что отделяет CJM-проверку от набора «открылась ли страница». Проверка,
которая сама конструирует `$BASE/f/$SLUG` и дёргает его, зелёная при сломанном `BASE_URL`.
Проверка, которая **берёт ссылку из ответа API и идёт по ней**, — красная.

Отсюда же следует, что запускать надо на том адресе, по которому системой будут
пользоваться (внешний домен), а не на `localhost`: внешний адрес — часть конфигурации,
и ломается ровно он.

## Скелет

```bash
set -uo pipefail
BASE="${1:?укажите базовый адрес}"; BASE="${BASE%/}"
FAIL=0; SLUG="cjm-$(date +%s)"          # уникальный прогон, следов не оставляет
ok()   { printf '  ✅ %s\n' "$1"; }
fail() { printf '  ❌ %s\n' "$1"; FAIL=1; }

# 1. Пройти вход в систему как настоящий пользователь — получить сессию и ответ
RESP=$(curl -s -i -m 20 -X POST "$BASE/api/…" -d '…')
COOKIE=$(grep -i '^set-cookie' <<<"$RESP" | sed 's/.*session=\([^;]*\).*/\1/' | tr -d '\r')
BODY=$(grep '^{' <<<"$RESP")

# 2. ГЛАВНЫЙ ШАГ: выданные ссылки указывают НА ЭТОТ ЖЕ адрес
for field in submission_form public_page dashboard; do
  url=$(python3 -c "import sys,json;print(json.loads(sys.argv[1])['urls']['$field'])" "$BODY")
  case "$url" in
    "$BASE"/*) ok "$field ведёт на $BASE" ;;
    *)         fail "$field ведёт на $url — конфигурация не доехала" ;;
  esac
done

# 3. Пройти ПО ВЫДАННОЙ ссылке, а не по сконструированной
[ "$(curl -s -o /dev/null -w '%{http_code}' -m 20 "$url")" = 200 ] \
  && ok "выданная ссылка открывается" || fail "выданная ссылка не открывается"

# 4. …остальные шаги пути: отправить, промодерировать, увидеть результат,
#     встроить виджет на СТОРОННЮЮ страницу, пройти по реферальной ссылке…
exit $FAIL
```

## Подводные камни

| Камень | Что происходит |
|---|---|
| `grep -c` для счёта вхождений | Считает СТРОКИ, а не вхождения. Одна карточка и пять карточек дают `1`. Нужно `grep -oi … \| wc -l` |
| Проверка ищет строку в SSR-разметке фреймворка | React отдаёт атрибуты в camelCase (`itemType`), а не так, как написано в JSX. Сверять с реальным ответом, не с исходником |
| `curl` как подтверждение работы виджета | `curl` не применяет политику браузера. Сломанный CORS отвечает `200`. Виджет проверять браузером (headless) |
| Прогон на `localhost` | Проверяет всё, кроме той конфигурации, которая ломается |
| Прогон оставляет мусор в боевой БД | Уникальный `SLUG` на прогон + отдельный шаг очистки, либо отдельный стенд |
| Передать переменные через `docker run -e` для проверки | Обходит compose — то есть ровно тот слой, где живёт дефект |
