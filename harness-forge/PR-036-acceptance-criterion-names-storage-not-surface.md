# PR-036: Критерий приёмки назван состоянием хранилища, а не тем, что видит пользователь

**Класс:** критерий зелен при неверном продукте · **Приоритет:** P1 · **Найдено:** фича оплаты, проект 02, 2026-09-02

## Утверждение

Шаблоны Refinement и Completion порождают критерии приёмки в терминах, доступных коду:
поле в таблице, статус записи, счётчик. Между этим полем и тем, что наблюдает пользователь,
почти всегда стоит **ещё один механизм** — кэш, очередь, сборка, второй контейнер, CDN.

> Критерий, записанный как состояние хранилища, зеленеет ровно тогда, когда транзакция
> закоммитилась, — то есть **до** и **независимо от** того, изменилось ли что-нибудь для
> пользователя.

Это не педантизм формулировок: механизм между хранилищем и поверхностью — самое частое место
дефекта (`deployment-seams`), и критерий, останавливающийся перед ним, не проверяет именно ту
часть, которая ломается.

## Доказательство

Фича: оплата снимает бренд-строку «Сделано на ReviewQR» с гостевых страниц аккаунта.

Как критерий был записан изначально (мной, по шаблону):

```
AC-5: после оплаты у ВСЕХ точек аккаунта branding_required = false
```

Что стоит между этим полем и глазами гостя:

| Звено | Как отказывает | Виден ли отказ критерию |
|---|---|---|
| Кэш страницы, TTL 60 с | отдаёт старую разметку | нет |
| HTTP-вызов сброса кэша в **другой контейнер** | сеть, опечатка в имени, контейнер лежит | нет |
| Обработка отказа сброса | ошибка логируется и **проглатывается** намеренно | нет |

Последняя строка решает дело: сброс кэша сделан безопасным для транзакции — его отказ не
роняет оплату, а лишь пишется в журнал. Значит при сломанном сбросе продукт ведёт себя так:
**деньги списаны, поле в БД верное, критерий зелёный, гость по-прежнему видит чужой бренд.**

Проверка живой страницы (`curl` по выданному адресу, поиск строки в теле) прошла — но она
была моим ручным действием, а не требованием критерия. Автоматический тест `P-5` проверял
именно поле и список слагов, то есть останавливался ровно перед механизмом.

## Почему существующие проверки молчат

- **Валидатор требований** проверяет измеримость критерия. `branding_required = false`
  измеримо идеально — и потому проходит.
- **Интеграционный тест** написан по критерию: он проверяет то, что в критерии названо.
- **`deployment-seams` / PR-014** предлагают сквозной прогон по стенду, но как **отдельный
  скрипт для всего продукта**, а не как форму записи критерия конкретной фичи. Скрипт
  покрывает главный путь; фича, добавленная позже, в него не попадает.

## Что предлагается

**1. Правило записи критерия в шаблоне Refinement.** Критерий приёмки называет **наблюдаемую
поверхность**; состояние хранилища допустимо только как уточнение, никогда как сам критерий:

```
❌ AC-5: branding_required = false у всех точек аккаунта
✅ AC-5: GET /r/<slug> НЕ содержит строки «Сделано на ReviewQR» — для каждой точки
        аккаунта, не позднее 60 с после оплаты (в БД при этом branding_required = false)
```

Проверяемо механически: в критерии обязан присутствовать либо HTTP-путь, либо имя экрана,
либо исходящее сообщение — то есть **адресат снаружи системы**.

**2. Гейт на фичу, а не на продукт.** Для каждой фичи, меняющей то, что видно пользователю,
в наборе обязан быть хотя бы один тест, обращающийся к поверхности (страница, ответ API,
отправленное сообщение), а не только к БД. Формально: тест, чей вход — публичный адрес.

**3. Отдельная строка про промежуточный механизм.** Если между записью и поверхностью есть
кэш/очередь/второй сервис, шаблон требует назвать **срок** («не позднее N секунд») и
**поведение при отказе механизма** (деградация до TTL — приемлемо; бесконечная выдача старого —
нет). Сейчас это остаётся в голове автора.

## Способ проверки

На фиче с кэшем: сломать сброс кэша (например, подменить адрес внутреннего маршрута) и
прогнать набор.

```
критерий по полю БД        ->  зелёный   ❌ продукт при этом неверен
критерий по поверхности    ->  красный   ✅
```

Если оба зелёные — критерий не дошёл до механизма.
