# PR-016: Тестовый compose без явного `name` вытесняет боевой стек

**Класс:** коллизия имён в scaffold · **Приоритет:** P1 · **Найдено:** прогон `/run mvp`, проект 01

## Проблема

`docker compose` без явного `name` берёт имя проекта из **имени каталога**. Если рядом
с боевым `docker-compose.yml` лежит `compose.test.yml` — а он там и должен лежать, это
корень проекта, — оба файла дают ОДНО имя проекта.

Последствие не «два стека рядом», а **замена**: `docker compose -f compose.test.yml up`
и `docker compose -f docker-compose.yml up` управляют одним и тем же набором контейнеров.
Поднятый стек молча вытесняет другой.

Воспроизведено буквально:

```
1. поднят тестовый стек        -> proofwall-test-postgres на 127.0.0.1:55432
2. поднят демо-стек (боевой)   -> контейнеры ЗАМЕНЕНЫ
3. npm test                    -> 117 тестов легли с ECONNREFUSED 127.0.0.1:55432
```

Диагноз при этом уводит в сторону: `ECONNREFUSED` читается как «БД не поднялась»,
а не как «её подменил соседний стек». На разбор ушло время, которого стоила одна строка.

## Исправление

Одна строка в шаблоне тестового compose:

```yaml
name: proofwall-test    # ← без неё compose берёт имя каталога — то же, что у боевого

services:
  postgres:
    ...
```

Проверено: после явного имени оба стека сосуществуют
(`proofwall-test-postgres-1` и `01-testimonials-senja-postgres-1` одновременно),
376 тестов проходят при поднятом демо.

### Общее правило для генератора

Любой ДОПОЛНИТЕЛЬНЫЙ compose-файл (тестовый, для нагрузки, для e2e), кладущийся в тот же
каталог, обязан объявлять `name`. Это относится и к самому боевому файлу: явное имя
защищает от переименования каталога, после которого стек «теряется» и остаётся висеть
осиротевшими контейнерами.

### Детерминированная проверка

```bash
for f in $(ls compose*.y*ml docker-compose*.y*ml 2>/dev/null); do
  grep -qE '^name:' "$f" || echo "❌ $f без явного name — возьмёт имя каталога"
done
```

## Связь с PR-012

Тестовый compose появился как закрытие `[GAP]`, разобранного в
[PR-012](PR-012-db-never-published.md): до него `packages/db/README.md` предписывал
поднимать БД командой `docker run -p 5432:5432 -e POSTGRES_PASSWORD=postgres`, что и
привело к компрометации.

То есть заявка описывает дефект **в артефакте, созданном для устранения другого
дефекта**. Это стоит держать в виду при правке: новый шаблон тестового окружения
обязан приезжать сразу с `name`, иначе одна проблема меняется на другую.
