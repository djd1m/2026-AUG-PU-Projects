# PR-035: Мутация может не примениться — и тогда доказательство стража недействительно, а выглядит проведённым

**Класс:** мета-проверка отказывает молча · **Приоритет:** P0 · **Найдено:** прогон оплаты, проект 02, 2026-09-02

## Утверждение

PR-018 требует принимать стража только вместе с доказательством, что он падает: внедрить
дефект, увидеть красное, восстановить. Рецепт верен и **у него есть собственный тихий отказ**,
который PR-018 не закрывает:

> Если внедрение дефекта **не применилось**, прогон остаётся зелёным — и этот зелёный читается
> как «страж дефект НЕ ловит», хотя дефекта в коде не было ни секунды.

Отказ направлен в худшую сторону. Ошибка не в том, что плохой страж примут за хороший, — её
PR-018 ловит. Ошибка в том, что **хороший страж будет объявлен негодным**, а вслед за этим
переписан «чтобы наконец ловил», хотя ловить было нечего.

Мета-проверка страдает ровно той болезнью, которую лечит: у неё нет проверки, что она
выполнилась.

## Доказательство: обе половины отказали в одном прогоне

Шесть мутаций против тракта оплаты (`MP-1…MP-6`), внедрялись скриптом на Python по
подстроке-якорю.

**Половина первая — мутация не легла.** Первый прогон `MP-1` дал `Tests 13 passed`. Читается
однозначно: «подмена подлинности не ловится ни одним тестом». Настоящая причина — якорь
`str.replace` не совпал ни с одним фрагментом файла (текст в исходнике отличался от того,
что я держал в голове), `replace` вернул строку без изменений и **молча записал её обратно**.
Тесты честно проверяли неизменённый код.

Разница между двумя мирами не видна в выводе вообще:

```
мутация внедрена, страж слеп   ->  Tests  13 passed     ← дефект стража
мутация НЕ внедрена            ->  Tests  13 passed     ← дефект процедуры
```

После добавления `assert s != orig, 'мутация НЕ легла'` те же шесть мутаций дали
`1 failed`, `1 failed`, `2 failed`, `1 failed`, `1 failed`, `6 failed` — то есть страж был
исправен с самого начала.

**Половина вторая — восстановление уничтожило работу.** Для отката мутаций применялся
`git checkout <файл>`. На двух файлах из шести это сработало не так, как предполагалось:

| Что случилось | Почему |
|---|---|
| `error: pathspec ... did not match any file(s)` ×4 | файл был **новым и неотслеживаемым**: `git checkout` не восстанавливает то, чего нет в индексе — мутация осталась в коде |
| Затёрты незакоммиченные правки соседнего файла | `git checkout` возвращает состояние индекса, а не состояние «до мутации» |

Итог: после серии мутаций рабочее дерево содержало **остатки трёх мутаций одновременно**, и
контрольный прогон дал `2 failed | 13 passed` — красное, которое я едва не принял за
настоящую находку. Разбор занял три итерации.

## Почему существующие средства молчат

- **PR-018** проверяет, что страж способен упасть. Он не проверяет, что **вход изменился**.
- **Тестовый раннер** не знает о существовании мутации: для него это обычный прогон.
- **Число тестов** не меняется — меняется только вердикт, а он в обоих случаях зелёный.
- **`git status`** между мутациями никто не смотрит: процедура выглядит замкнутой.

Общая форма: процедура доказательства не оставляет **квитанции о собственном выполнении**.

## Что предлагается — три требования к протоколу мутации

**1. Внедрение обязано подтверждать, что изменило файл.** Любая мутация, применяемая
автоматически, сравнивает содержимое до и после и **отказывает**, если они совпали:

```python
s2 = s.replace(ANCHOR, MUTATION)
assert s2 != s, f"мутация не легла: якорь не найден в {path}"
```

Ровно та же форма, что вендорное правило `guard-must-be-able-to-fail` требует от стражей
(«нечитаемый вход — отказ, а не „нарушений нет"»), применённая к самой процедуре мутации.

**2. Восстановление — копией, а не `git checkout`.** Снимок делается до серии, возврат —
побайтовым восстановлением снимка:

```bash
cp src/target.ts "$TMP/target.bak"      # до серии
...                                      # мутация → прогон
cp "$TMP/target.bak" src/target.ts       # возврат, независимо от состояния индекса
```

`git checkout` непригоден по построению: он возвращает **состояние индекса**, а не состояние
до мутации, и не знает о неотслеживаемых файлах. Для нового файла фичи — а мутируется чаще
всего именно новый код — он не работает вовсе.

**3. Квитанция чистоты после серии.** Прогон после восстановления обязан подтверждать, что
рабочее дерево вернулось: `git diff --stat` пуст (или равен состоянию до серии) **и**
контрольный прогон зелёный. Без этого шага остаток мутации уходит в коммит.

Все три — слой 1: это код процедуры, а не правило для чтения.

## Способ проверки

Мета-тест на самой процедуре: подать заведомо несуществующий якорь и потребовать **отказа**
процедуры мутации, а не зелёного прогона.

```
якорь верный      ->  мутация легла, страж красный      ✅ доказательство состоялось
якорь неверный    ->  ОТКАЗ процедуры                    ✅ отличимо от предыдущего
якорь неверный    ->  Tests N passed                     ❌ так быть не должно
```

Третья строка — текущее поведение.
