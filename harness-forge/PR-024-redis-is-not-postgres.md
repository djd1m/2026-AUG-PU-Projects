# PR-024: Правило №0 равняет Redis с Postgres, а цена экспозиции у них разная на порядок

**Класс:** правило верно, но не ранжирует — и потому его нарушают в самом дорогом месте · **Приоритет:** P1 · **Найдено:** 2026-08-29, живая машина

## Что говорит правило сейчас

`docker-ports.md` перечисляет хранилища одной строкой:

> Postgres, MySQL, MariaDB, MongoDB, Redis, Elasticsearch/OpenSearch, MinIO, RabbitMQ,
> Memcached, ClickHouse.

Дальше всё изложение опирается на единственный разобранный случай — Postgres с паролем
`postgres`, взломанный через `COPY … TO PROGRAM`. Вывод, который делает читатель: *открытая
БД опасна, потому что подберут пароль.*

## Почему это неверно ровно для двух пунктов списка

Для **Redis** и **Memcached** пароля по умолчанию **нет вовсе**. Не «слабый», не
«дефолтный» — его нет как понятия, пока не задан `requirepass`.

Это меняет не степень риска, а его механику:

| | Postgres (случай 26 августа) | Redis без `requirepass` |
|---|---|---|
| Что нужно атакующему | учётные данные | **ничего** |
| Что защищает при экспозиции | стойкий пароль | **ничего** |
| Путь к выполнению кода | `COPY … TO PROGRAM` после входа | `CONFIG SET dir` + `dbfilename` → запись в `authorized_keys` / `cron` |
| Кто эксплуатирует | сканер + перебор | сканер, одним проходом, без перебора |

Стойкий пароль — единственное, что спасло два Postgres на этой машине: оба публиковались
наружу четверо суток, но с 33-символьными случайными паролями. Redis рядом с ними имел
`requirepass` пустым, и для него длина пароля не была фактором, потому что пароля не было.

То есть **мера, которая вытянула два случая из трёх, к третьему неприменима в принципе** —
а правило подаёт все три как один класс.

## Наблюдение, подтверждающее, что это не теория

```
$ docker exec pulse-redis redis-cli CONFIG GET requirepass
requirepass
                       # пусто

$ docker exec pulse-redis redis-cli INFO stats
total_connections_received:37069
```

37 тысяч подключений при `DBSIZE = 1` и трёх внутренних потребителях с пулами соединений.
Числу можно дать невинное объяснение, и forensics его искал; но само сочетание «открыт
наружу, пароля нет, десятки тысяч подключений» — это то, что оператор обязан увидеть
**из правила**, а не выяснять постфактум.

Контрольные признаки исполненного захвата (`CONFIG GET dir` переставлен на `/root/.ssh`
или `/var/spool/cron`, посторонние ключи вида `crackit`) на момент проверки отсутствовали:
`dir` был `/data`, `dbfilename` — `dump.rdb`. То есть дыра была открыта и не была
использована — но не потому, что что-то мешало.

## Что предлагается

**1. Разделить список на два по механике, а не по алфавиту.**

> **Хранилища с обязательной аутентификацией** (Postgres, MySQL, MariaDB, MongoDB,
> ClickHouse, MinIO, RabbitMQ, Elasticsearch): экспозиция опасна, стойкий пароль —
> смягчающий фактор.
>
> **Хранилища, БЕЗ аутентификации по умолчанию** (Redis, Memcached): экспозиция сама по
> себе есть предоставление доступа. Смягчающего фактора не существует; «за необычным
> портом» и «пароль зададим потом» здесь не работают вовсе.

**2. Второй инвариант рядом с правилом №0, проверяемый той же командой:**

> Redis и Memcached обязаны иметь заданную аутентификацию, **даже когда не публикуются**.
> Публикация — не единственный путь наружу: контейнер в общей сети compose доступен
> соседям, а состав соседей меняется.

**3. В `check-ports.cjs` — отдельный вывод для этого класса.** Сейчас нарушение печатается
одинаково для любого образа. Для Redis/Memcached сообщение обязано называть механику:

```
🔴 pulse-redis (redis:7-alpine) — 0.0.0.0:11379
   Redis по умолчанию БЕЗ пароля: публикация = выдача доступа, а не риск подбора.
   Проверьте: docker exec pulse-redis redis-cli CONFIG GET requirepass
```

Разница не косметическая. «Нарушено правило публикации» оператор откладывает на потом;
«доступ уже выдан» — нет.

## Испытание на способность падать

| Вход | Ожидание |
|---|---|
| `redis:7` с `--requirepass <случайный>`, без публикации | `0` |
| `redis:7` без пароля, без публикации | `1` по второму инварианту, с текстом про аутентификацию |
| `redis:7` без пароля, `-p 127.0.0.1:16379:6379` | `1` — петля не оправдывает отсутствие пароля |
| `redis:7` без пароля, `-p 16379:6379` | `1`, оба нарушения названы отдельно |

Третья строка — та, которую легко упустить: правило №0 её разрешает, второй инвариант нет.
