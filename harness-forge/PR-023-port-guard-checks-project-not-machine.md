# PR-023: Страж портов проверяет ВАШ проект, а не машину — и зеленеет, пока рядом три открытые БД

**Класс:** страж отвечает не на тот вопрос, который читатель ему задаёт · **Приоритет:** P0 · **Найдено:** 2026-08-29, живая машина с публичным адресом, на которой уже был инцидент 26 августа

## Наблюдение в одну строку

```
$ node .claude/hooks/check-ports.cjs .
✅ ни одно хранилище не публикует порт наружу, обходов reverse-proxy нет   (код 0)

$ ss -tlnH | grep -E ':(11432|11379|5480)$'
0.0.0.0:11432   [::]:11432      # Postgres, публичный адрес
0.0.0.0:11379   [::]:11379      # Redis, БЕЗ ПАРОЛЯ
0.0.0.0:5480    [::]:5480       # Postgres
```

Обе команды говорят правду. Страж проверил проект, в котором его позвали, и в нём
действительно чисто. Три открытые базы принадлежат **соседним** проектам на той же машине.

## Почему это дефект пакета, а не оплошность оператора

Правило `docker-ports.md` формулирует инвариант в терминах **машины**: «Тестовый Postgres,
поднятый с `-p 55432:5432`… был взломан из интернета примерно за час», «цена ошибки здесь —
компрометация машины». Компрометируется машина, а не проект.

Проверка же реализована в терминах **каталога**: она читает `docker compose config` того
проекта, на который её натравили.

Разрыв между областью правила и областью проверки не назван в документации. Читатель,
получивший `✅`, делает единственный естественный вывод — «правило №0 соблюдено», — и он
неверен ровно в том случае, ради которого правило написано: на машине, где живёт больше
одного проекта. Это и есть класс «страж, отвечающий не на тот вопрос»: он не молчит и не
падает, он **уверенно подтверждает не то**.

Заметьте разницу с PR-019 и PR-012: там страж мог не запуститься или не увидеть конфиг.
Здесь он отработал полностью и корректно — дефект в границе области, а не в исполнении.

## Второй слой: соблюдение соседнего правила выглядит как защита

Открытый Postgres проекта `genai-pulse-discovery` был объявлен **ровно так, как предписывает
локальное правило** о хостовых портах:

```yaml
ports:
  - "${DB_PORT:-11432}:5432"     # переменная, не число — правило соблюдено
```

И при этом публиковался на все интерфейсы публичного адреса.

Правило `${VAR:-default}` решает **конфликт портов**. Правило №0 решает **экспозицию**. Это
ортогональные свойства, но текстуально они соседствуют, и соблюдение первого читается как
причастность ко второму. Автор этого compose сделал всё, что от него просили, и остался
полностью открыт.

Формулировка, которой не хватает: *переменная в левой части ничего не говорит о том, на каком
адресе окажется публикация; адрес — это отдельный, третий элемент, и по умолчанию он
`0.0.0.0`.*

## Чего именно не хватает пакету

Режим проверки **машины**, а не каталога:

```bash
node .claude/hooks/check-ports.cjs --machine
```

Что он обязан делать:

1. перечислить запущенные контейнеры (`docker ps --format ...`), а не файлы;
2. опознать хранилища по образу (`postgres`, `redis`, `mysql`, `mariadb`, `mongo`,
   `elasticsearch`, `opensearch`, `minio`, `rabbitmq`, `memcached`, `clickhouse`) —
   образ надёжнее имени сервиса, которое произвольно;
3. для каждого сопоставить публикацию и `host_ip`; нарушение — всё, кроме отсутствия
   публикации, `127.0.0.1` и `::1`;
4. назвать **владельца** нарушения: из меток `com.docker.compose.project` и
   `com.docker.compose.project.config_files` — иначе оператор получит номер порта и не
   найдёт, где его править. Обе метки Docker проставляет сам, доставать их ниоткуда не надо;
5. три кода возврата, как у существующей проверки: `0` чисто, `1` нарушение, `2` **проверка
   не выполнена** (нет docker, нет прав к сокету). Без третьего кода машина без доступа к
   docker отрапортует «чисто».

Один аргумент, никакой новой инфраструктуры: те же метки, тот же разбор, другая область.

## Почему `ufw` не является ответом на это

Предвосхищая возражение «пусть оператор включит межсетевой экран»: на этой машине `ufw`
был `inactive`, но включение его **не закрыло бы** ни один из трёх портов. Docker пишет
правила публикации в цепочку `DOCKER`, которая обрабатывается раньше пользовательских
цепочек `ufw`. Публикация контейнера обходит `ufw` штатно, это его документированное
поведение, а не дефект.

Отсюда следует, что compose — **единственное** место, где эта дыра лечится, и потому
проверка compose-слоя обязана покрывать всю машину. Совет «включи firewall» здесь не
смягчающая мера, а ложное успокоение.

## Как проверить, что реализация работает

По правилу «страж обязан быть испытан на способность падать»:

| Вход | Ожидаемый код |
|---|---|
| машина, где все хранилища на петле или без публикации | `0` |
| поднять `docker run -d -p 127.0.0.1:15432:5432 -e POSTGRES_PASSWORD=$(openssl rand -hex 24) postgres:16` | `0` — петля законна |
| то же с `-p 15432:5432` | `1`, и в выводе назван контейнер |
| то же с `--network host` | `1` |
| docker недоступен (`DOCKER_HOST=tcp://127.0.0.1:1`) | `2`, сообщение в stderr, НЕ `0` |

Последняя строка — главная: именно она отличает проверку от её видимости.

## Цена промедления

На этой машине к моменту находки: два Postgres со случайными паролями (это спасло) и
**один Redis без пароля вовсе**. Открытый Redis без `requirepass` не требует подбора
учётных данных — `CONFIG SET dir` плюс `dbfilename` пишут произвольный файл, и это
эксплуатируется массовыми сканерами автоматически. Порт был открыт не менее четырёх суток.
Разбор этой асимметрии — отдельная заявка PR-024.
