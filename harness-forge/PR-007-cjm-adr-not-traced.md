# PR-007: Интеграция CJM и ADR в спецификацию не проверяется

**Класс:** тупик слоя 4/5 · **Приоритет:** P0 · **Найдено:** аудит проекта 01

## Проблема

Пайплайн производит CJM (Phase 0) и ADR (Phase 1), но **ничто механически не проверяет**,
что они дошли до `Specification.md` — документа, по которому пишется код.

Это тот же класс дефекта, что PR-001 (growth-engine): артефакт создаётся, он качественный,
и у него нет принудительного пути в требования.

## Доказательство — CJM

```bash
$ grep -rn -i "cjm\|customer journey" .claude/skills/sparc-prd-mini/ \
    .claude/skills/requirements-validator/ .claude/skills/cc-toolkit-generator-enhanced/
# ни одного совпадения
```

Ни генератор SPARC, ни валидатор требований, ни генератор тулкита не знают слова CJM.

**Живое следствие в проекте 01.** `CJM_Variants.md` описывает для варианта A элемент
**Core Loop** — «еженедельный дайджест: 3 новых отзыва найдено → one-click approve».
В `Specification.md` его нет. При этом другой элемент того же варианта — Onboarding с
автосканом — исключён **явно**, в PRD §1.2 «НЕ входит», с обоснованием.

Разница показательна: что исключили осознанно — задокументировано; что выпало молча —
выпало молча. Механизма, который бы это различил, нет.

## Доказательство — ADR

Матрица «ADR → обратная ссылка из Specification» для проекта 01:

| ADR | Тема | Ссылка из Specification |
|---|---|---|
| ADR-001 | Shadow DOM | нет |
| ADR-002 | Серверная проверка тарифа | **есть** ← добавлена вручную по итогам аудита |
| ADR-003 | Приоритет промокода над cookie | нет |
| ADR-004 | Порог индексируемости | нет |
| ADR-005 | Граница Claude под FTC | нет |
| ADR-006 | Идемпотентность вебхуков | нет |
| ADR-007 | TLS-терминация | нет |

**6 из 7 без обратной ссылки.** Единственное исключение появилось не от пайплайна,
а от разового ручного аудита.

Плюс отдельный баг маршрутизации — см. [PR-006](PR-006-has-adr-dead-branch.md):
генератор тулкита физически не видит `docs/ADR.md`.

## Что уже существует, но не подключено

В соседнем пакете `@dzhechkov/skills-feature-adr` есть **настоящий** machine-checkable gate:
`check-plan-completeness.mjs`, проверки C1/C2 — каждое решение ADR обязано иметь подтверждение
в плане. Но он работает со структурой `features/<slug>/03_adr/` и к `docs/ADR.md` неприменим.

То есть механизм написан, доказал работоспособность и просто **не подключён** к SPARC-ветке.

## Предлагаемые gates

### G1. Обратная трассировка ADR (слой 1)

```bash
# каждый ADR-NNN должен упоминаться хотя бы в одном из документов реализации
for adr in $(grep -ohE 'ADR-[0-9]{3}' docs/ADR.md | sort -u); do
  grep -qrn "$adr" docs/Specification.md docs/Architecture.md docs/Pseudocode.md \
    || echo "$adr: нет обратной ссылки"
done
```

### G2. Чек-лист переноса CJM (слой 3)

При переходе Phase 0 → Phase 1: для каждого элемента выбранного варианта CJM
(Aha Moment, Entry Hook, Onboarding, Core Loop, Paywall, Invite) — либо требование
в Specification, либо явная запись в «НЕ входит» с обоснованием. Молчание запрещено.

### G3. Секция трассируемости в Specification (слой 2)

Добавить в шаблон обязательную таблицу «ADR → требование» и «элемент CJM → требование»
по образцу существующей §5 «Трассируемость» в проекте 01.

### G4. Фикс `has_adr` (слой 1)

См. [PR-006](PR-006-has-adr-dead-branch.md). Без него любой gate по ADR в генераторе
тулкита бесполезен.

### G5. Перенос C1/C2 из feature-adr

Адаптировать `check-plan-completeness.mjs` под структуру `docs/ADR.md`. Механизм готов,
нужна только поддержка второго формата хранения ADR.

## Проверка исправления

Удалить из `Specification.md` требование, реализующее одно из решений ADR, и убедиться,
что G1 это ловит.
