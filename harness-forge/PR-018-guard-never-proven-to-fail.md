# PR-018: Пайплайн принимает стражей, ни разу не показавших красное

**Класс:** отсутствует мета-проверка · **Приоритет:** P0 · **Найдено:** `/harvest full`, проект 01

## Проблема

Пайплайн умеет требовать наличие проверки и умеет запускать её. Он не умеет спросить
**«а она вообще способна упасть?»** — и потому принимает стража, который печатает ✅
независимо от входа.

Пять независимых случаев в одном проекте. Каждый — проверка, молча зеленевшая ровно там,
где была нужна:

| Страж | Как зеленел | Цена |
|---|---|---|
| Проверка портов (**безопасность**) | `docker compose config` нечитаем → пустой вывод → «нарушений не найдено» ✅ | Именно этот страж должен был предотвратить компрометацию VPS майнером |
| Проброс переменных | Опора на `.env.example`, который сам был неполон | Унаследовал пробел проверяемого и подтвердил его |
| Проброс переменных | Регэксп `[A-Z_]+` резал `S3_ENDPOINT` до `S`; совпадение с `S` находилось всегда | «Всё проброшено» при потерянных переменных |
| Проверка CJM | `grep -c` считает СТРОКИ, а разметка приходит одной | Одна карточка и пять карточек давали `1`; порог «≥1» проходил всегда |
| Перенос стража в тулкит | Каталог сервиса из `build.context`, одинакового в монорепо | Обратный отказ: 32 «потери» там, где их не было. Такого стража отключают через неделю |

Общая механика: **отсутствие проверки заметно, видимость проверки — нет.** Зелёный отчёт
читается как «проверено», хотя означает «проверка не сработала». Это худший вид отказа
из возможных: он не оставляет следов и накапливает ложную уверенность.

## Почему это дефект пайплайна, а не проекта

Проект написал пять стражей — больше, чем требовал пайплайн. Ни разу пайплайн не
потребовал доказать, что они падают. Требование «добавьте проверку» без требования
«докажите, что она ловит» переносит проверку с **слоя 1** (детерминированный тест) на
**слой 4** (суждение автора о собственном коде), сохраняя видимость слоя 1.

Это тот же класс, что PR-009 («валидация объявлена, но не форсируется»), но на уровень
ниже: там не исполняется гейт, здесь не проверяется сам инструмент гейта.

## Исправление

### 1. Мета-тест: страж принимается только вместе с доказательством падения

Для каждого стража — прогон с **внедрённым** дефектом и ожидаемым ненулевым кодом.
Автоматизируется обёрткой, которая портит вход и требует красного.

Как это выглядит (проверка починки вебхука в проекте-источнике):

```
дефект возвращён  ->  Tests  2 failed | 35 passed
код восстановлен  ->  Tests  37 passed
```

Две строки. Без них неизвестно, проверяет ли тест починку или просто существует рядом.

### 2. Нечитаемый вход — явный отказ, а не «нарушений нет»

Обязательная форма для любого генерируемого стража:

```bash
if [ -z "$CONFIG" ]; then
  echo "❌ конфиг нечитаем — проверка НЕ выполнена" >&2
  exit 2      # отдельный код: «не проверено» ≠ «проверено, чисто»
fi
```

Три состояния вместо двух: `0` — чисто, `1` — нарушение, `2` — проверка не выполнена.
Сейчас генератор выдаёт стражей с двумя, и третье молча сливается в первое.

### 3. Критерий приёмки при переносе стража в поставку

Прогнать на проекте-источнике и **сверить результат с проектной версией**. Расхождение
означает, что обобщение изменило поведение, а не только форму. Без этого в тулкит уезжает
страж с 32 ложными срабатываниями.

### 4. Запретить формы, дающие ложный зелёный

Грепом по сгенерированным стражам:

| Форма | Чем плоха |
|---|---|
| `grep -c` там, где считаются вхождения | Считает строки; HTML приходит одной |
| `[A-Z_]+` для имён переменных | Режет имена с цифрами |
| Порог «≥ 1» на счётчике, который всегда ≥ 1 | Проходит независимо от реальности |
| `set -e` без обработки пустого `grep` | Пустой результат — код 1, скрипт «успешно завершён» |
