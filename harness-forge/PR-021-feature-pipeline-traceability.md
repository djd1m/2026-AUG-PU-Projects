# PR-021: В пофичевом контуре `/feature` трассировка не работает — гейты адресуют файлы, которых там нет

**Класс:** гейт не срабатывает по построению · **Приоритет:** P0 · **Найдено:** аудит роем из трёх агентов, доказательная база — полный прогон FR-009

## Нулевая находка, от которой зависят остальные

`/feature` фаза 1 требует пять файлов `01_specification.md … 05_completion.md` в
`docs/features/<feature>/` (`.claude/commands/feature.md:72-77`).

Скилл, который их производит, **не знает ни этих имён, ни этого каталога**:
`sparc-prd-mini/SKILL.md:76-88` перечисляет `PRD.md`, `Specification.md`, `Pseudocode.md`,
`Architecture.md`, `Refinement.md`, `Completion.md` — одиннадцать файлов **уровня проекта**.
Поиск по всем 43 КБ скилла даёт **ноль** вхождений `01_`, `02_`, `features/`, «per-feature».

Отображение «Phase 3 Specification → `01_specification.md`» не записано нигде. Его каждый раз
придумывает модель.

## Почему это ломает именно трассировку

В скилле **есть** два настоящих гейта трассировки, и оба адресуют файлы **по имени**:

| Гейт | Что требует | Куда смотрит |
|---|---|---|
| Шаг 4.9 «Покрытие сценариев» (`SKILL.md:486-506`) | Блок `## Scenario Coverage` с двумя таблицами — непокрытые сценарии и висячие ссылки — «в каждом случае, включая тот, где всё покрыто» | `Pseudocode.md` |
| Шаг 5.9 «Сверка» (`SKILL.md:659-694`) | Блок `## Reconciliation`, сверка модели данных с алгоритмами | `## Data Structures` / `## Core Algorithms` |

`/feature` переименовывает файлы — и оба гейта адресуют то, чего в пофичевом каталоге нет.

**Точная формулировка** (важно, иначе заявка преувеличивает). Это не программы, читающие файл
по пути: это инструкции модели, которая держит перед собой оба документа сразу. Несовпадение
имён не делает пропуск неизбежным — оно снимает единственную опору, по которой гейт можно
адресовать, и переводит его из «проверить блок в файле X» в «вспомнить, что такой блок нужен».
То есть со слоя 3 на слой 4. Наблюдаемое следствие ниже.

На живом прогоне FR-009 (пять ревизий документов, четыре прохода валидации, доведён до кода)
блок `## Scenario Coverage` **не появился ни разу**.

Общая форма дефекта — та же, что проект вывел из этого же прогона:
**критерий написан на форму механизма, а не на свойство, ради которого механизм введён.**

## Что из этого следует по всей цепочке

### Фаза 1 → фаза 1: девять связей, две с механизмом

| Связь | Сейчас | Могла бы быть |
|---|---|---|
| 01→02: у требования есть алгоритм | слой 4 (гейт есть, адресует не тот файл) | **1** — `comm -23` по ID |
| 02→01: у алгоритма есть требование | слой 5 (нигде) | **1** — обратный `comm` |
| 02→03: модель данных сверена с хранилищем | слой 4 (гейт адресует не те заголовки) | **3** |
| 03→04: у компонента есть краевой случай | слой 5 | **1** |
| 04→05: «все критерии закрыты тестами» | слой 5 (одна фраза) | **1** |
| ID требования как ключ | слой 1, **но мимо**: `check-pipeline-gaps.sh:28-35` не знает про `NFR` и не заходит в `docs/features/*/` | **1** |
| Ограничения проекта → документы фичи | слой 5 (память модели) | **2 или 3** |
| Ревизия → перепроверка соседей | слой 5 | **1** |
| Отчёт валидации ↔ ревизия, против которой написан | слой 5 | **1** |

На FR-009 отчёт валидации ревизии 3.1 был написан против текста ревизии 2 — это заметил
человек, ни один механизм на несовпадение не отреагировал.

### Фаза 3: ничто не заставляет читать документы

Единственные упоминания — текст инструкции (`feature.md:103`, `feature-lifecycle.md:91-93`).
Механизма нет. Ссылки на номера требований в комментариях кода — добросовестность автора,
машинно не проверяется.

### Фаза 4: скилл ревью не знает слова «критерий приёмки»

В `brutal-honesty-review/SKILL.md` словосочетание **не встречается ни разу**. Фаза 4 судит по
своей рубрике. На FR-009 ревью сверилось со списком критериев только потому, что это было
явно написано в задании агенту — то есть человеком, а не пайплайном.

### Итог по проверкам: 6 механизмов из 21, к пофичевому циклу относятся 3

> Оговорка: перечень из 21 связи составлен аудитом вручную и **воспроизводимого реестра с
> правилами подсчёта не имеет**. Число иллюстрирует пропорцию, а не является метрикой.
> Первый шаг к исправлению — сам реестр: список связей с ID, где у каждой записан слой и
> способ проверки.

Связь «каждый критерий приёмки закрыт тестом» существует как **10 баллов из 100** в рубрике
фазы 2 (`scoring-system.md:34`), явно выведенных из-под блокировки. Она не сработала ни разу.
На FR-009 ревью нашло **более десяти** критериев, не покрытых ничем, при том что определение
готовности пунктом 1 требует обратного.

## Доказательство, что это не теория: расхождения накопились в самом прогоне

Три штуки, все живы на момент подачи заявки, все возникли **после** того, как фича получила
статус `done`:

| # | Документ говорит | Код/тест делает |
|---|---|---|
| 1 | `05_completion.md:47` — порог тайминга «не более чем в 2 раза» | `login.test.ts` — `toBeLessThan(4)` |
| 2 | `01_specification.md:73` — argon2 НЕ вызывается при 201-символьном пароле | `login.ts:118-120` — вызывается всегда (и правильно делает) |
| 3 | `03_architecture.md:28` — `{ ok: false }` как реализация NFR-009.1 «формой типа» | `login.ts:55` — `{ ok: false; tooMany: boolean }` |

Ни одно не поймано ничем: правка документа фичи — обычный коммит, `Stop`-хуки на
`docs/features/**` не реагируют.

### Сценарий отказа в чистом виде

Требование меняется с «5 попыток в час» на «3 в час» — правка одной ячейки в
`01_specification.md`. Код не изменится. Тесты **вычисляют ожидание из той же константы кода**
(`${PAIR_THRESHOLD + 1}`) и останутся зелёными при любом её значении. `npm test` подтвердит
«всё в порядке», фича будет числиться `done`, и заметить расхождение сможет только человек,
открывший оба файла рядом.

## Исправление

### 1. Записать отображение имён (пять минут, снимает нулевую находку)

`sparc-prd-mini` должен знать про пофичевый режим: принимать целевой каталог и набор имён,
либо `/feature` должен переименовывать выход явно и документированно. Сейчас это делает модель
по наитию, и потому два существующих гейта промахиваются.

### 2. Дать требованиям ID и проверять их машинно

Идентификаторы (`FR-<slug>-<n>`, `NFR-<slug>-<n>`, `AC-<slug>-<n>`) уже фактически пишутся
моделью — но как украшение текста. Достаточно `comm -23` между множествами ID соседних
документов. Расширить `check-pipeline-gaps.sh`: знать про `NFR`, заходить в `docs/features/*/`,
возвращать ненулевой код.

### 3. «Критерий закрыт тестом» — из баллов в гейт

Пронумеровать критерии приёмки и потребовать в `05_completion.md` **перечень** «критерий → тест»,
а не утверждение «все закрыты». Сегодня у FR-009 двадцать семь критериев и **ни одного ID**.

### 4. Отчёт валидации привязать к ревизии

Заголовок отчёта несёт номер/хеш ревизии документов. Несовпадение — отказ, а не примечание.

### 5. Порог требования и порог теста

Для **порога** тест обязан прибивать число независимо, а не брать константу из кода. В FR-009
этот приём применён к одной константе из десяти (`login-route.test.ts` — `EXPECTED_LIMIT = 4096`,
с объяснением). Для функции-производной — наоборот, тест обязан звать производственную
реализацию. Разницу стоит записать правилом.

## Способ проверки

Минимальный E2E, которого заявке не хватает и который стоит сделать первым: прогнать чистый
`/feature` на фикстуре, где одно требование НЕ имеет алгоритма, и убедиться, что пайплайн
это называет. Сегодня такой фикстуры нет, и утверждение «гейт не срабатывает» опирается на
один наблюдённый прогон, а не на отрицательный тест.

```bash
# нулевая находка
grep -c '01_specification\|features/' .claude/skills/sparc-prd-mini/SKILL.md   # ожидается > 0

# гейт трассировки в пофичевом каталоге
grep -c '## Scenario Coverage' docs/features/*/02_pseudocode.md                # ожидается > 0

# ID как ключ
bash scripts/check-pipeline-gaps.sh <проект>                                   # обязан заходить в docs/features/
```
