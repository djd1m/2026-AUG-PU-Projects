# PR-029: Защита пишется против первого экземпляра класса и молча не покрывает остальные

**Класс:** страж зелен на непроверенном коде · **Приоритет:** P0 · **Найдено:** четыре случая, два проекта, 2026-08-30 … 09-02

## Утверждение

Когда свойство безопасности относится к **классу** объектов — маршрутам, файлам провайдеров,
модулям с внешними вызовами, — страж пишется против того экземпляра, с которого начали.
Второй и последующие остаются **вне покрытия, и страж об этом не сообщает**: он зелёный,
потому что проверяет то, что ему перечислили.

Отказ невидим по построению. Отсутствие проверки заметно; **видимость проверки — нет**.

## Четыре случая

**1. Один роут защищён типом, соседний — прозой.** Проект 02, 2026-09-01. Инвариант «ответ
зависит только от слага» доказан для `GET /r/:slug` **сигнатурой**: у функции рендера нет
аргумента, куда подать контекст. Для соседнего `GET /go/:slug/:platform` тот же инвариант был
записан **утверждением в тексте**.

Формулировка автора, когда дыру предъявили:

> «Утверждение в прозе — это и есть слой 4. Разница между двумя роутами держалась не на
> конструкции, а на том, что до второго у меня не дошли руки. Ровно тот дефект, который вся
> конструкция закрывает, — и он оказался внутри неё самой.»

**2. Страж таймаутов со списком файлов литералом.** Проект 01. Проверка «число `fetch` равно
числу `signal`» перечисляла файлы явно: `['lib/sso.ts', 'lib/email.ts', 'lib/payment.ts']`.
Новый файл провайдера под неё не попадал — то есть первый же добавленный внешний вызов
оказывался без обязательного таймаута, при зелёном страже.

**3. Девять стражей, прибитых к пути первого провайдера.** Тот же проект. Девять проверок
читали файл по литеральному пути `app/api/auth/yandex/callback/route.ts`. Они стерегли
несущее: сеть вне транзакции, единственную точку выдачи сессии, отсутствие токена в журнале.

Самый быстрый способ добавить второго провайдера — скопировать каталог. И тогда **все девять
остаются зелёными и перестают покрывать новый маршрут**. Не падают. Не предупреждают.

**4. Матрица прав СУБД отстала от фичи на пять таблиц и целую роль.** Проект 02,
2026-09-02, фича оплаты. Страж `check-db-grants.sh` перечислял права трёх ролей литеральным
списком строк вида `has app_render private_feedback SELECT no`. Фича добавила пять таблиц
(`checkout_sessions`, `webhook_events`, `subscriptions`, `partners`, `commissions`) и ввела в
работу **четвёртую роль** — `app_owner`, которой в страже не было ни одной строки.

Страж остался зелёным. Он и не мог покраснеть: перечисленное было в порядке.

Обнаружено не проверкой, а **при подготовке коммита** — пункт DoD «страж расширен новыми
строками матрицы» я собирался отметить выполненным, не выполнив его. Между «фича трогает
таблицу» и «страж проверяет таблицу» нет ни одной связи, кроме памяти автора.

Особенность этого случая, которой не было в первых трёх: недостающие строки **выводятся
механически**. Список таблиц, которые трогает сервис, есть в его исходниках; список ролей — в
compose (по одной на контейнер). Страж, собирающий ожидаемую матрицу из этих двух источников
и отказывающий, когда код трогает таблицу вне матрицы, невозможно оставить позади фичи.

Второе наблюдение того же случая — про **форму** строк матрицы. Все существующие строки были
положительными («роль имеет право»). Такой список отвечает на вопрос «работает ли», но не на
вопрос «а больше ничего не может?» — а для матрицы прав несущий именно второй. При расширении
добавлены отрицательные строки (`app_render checkout_sessions SELECT no`, `app_intake
webhook_events INSERT no`), и мутация «выдать гостевой роли SELECT на платежи» покраснела
только благодаря им.

## Почему обычные средства не ловят

| Средство | Почему молчит |
|---|---|
| Прогон тестов | Зелёный: страж проверяет перечисленное, и оно в порядке |
| Ревью правки | Видит новый файл, не видит, что старый страж его не охватил |
| Покрытие кода | Меряет строки, а не то, применён ли к ним инвариант |
| Мета-тест «страж падает» | Ловит поломку стража, а не сужение его области |

## Что предлагается

**1. Страж над классом обязан перечислять класс ИЗ РЕАЛЬНОСТИ, а не из литерала.** Не список
файлов, а `glob`; не путь роута, а таблица маршрутов; не имена провайдеров, а содержимое
каталога. Литеральный перечень внутри стража — сам по себе находка.

**2. Мета-тест на расширение класса.** Добавить фиктивный второй экземпляр (пустой файл
провайдера, новый роут-заглушку) — **страж обязан упасть**, пока экземпляр не покрыт. Если не
упал, он не про класс, а про один файл, и это надо знать до, а не после.

**3. Правило в навык ревью.** Утверждение об инварианте, записанное прозой рядом с
конструкцией, доказывающей тот же инвариант, — сигнал асимметрии. Спрашивать не «верно ли
утверждение», а «почему здесь текст, если рядом тип».

## Способ проверки

```
Взять проект со стражем над классом. Добавить второй экземпляр класса, не трогая страж.
Прогон зелёный — воспроизведение дефекта.
```

## Дополнение 02.09.2026 (вечер): пятый случай — и он про сам ПРИЁМ, а не про область

Четыре случая выше — про **область** стража: перечислили один экземпляр, забыли остальные.
Пятый другой и, кажется, более общий: страж по исходнику **читает комментарии как код**.

За один прогон это повторилось **три раза подряд**, у трёх разных стражей, написанных одним
автором в течение часа:

| Страж | Что искал | Что нашёл на самом деле |
|---|---|---|
| «виджет не использует `innerHTML`» | вызов | строку в шапке файла, где `innerHTML` **ЗАПРЕЩЁН словами** |
| «форма не отправляет `project_id`» | поле запроса | комментарий «`project_id` НЕ отправляется» |
| «снимок не в слоте аватара» | класс в разметке | соседний блок, попавший в слайс до позиции класса |

Первые два — один механизм: **чем внимательнее написан комментарий, тем вероятнее он сломает
стража**. Файл, где инвариант объяснён словами рядом с кодом, гарантированно содержит
запрещённую строку — именно потому, что автор её назвал. То есть страж тем чаще ложно краснеет,
чем лучше документирован проверяемый код.

Направление отказа при этом **обратное** привычному: не «пропустили дефект», а «объявили
дефектом верный код». Последствие то же, что у PR-030: ложное красное отключают вместе с
настоящим.

### Что предлагается

**1. Срезание комментариев — часть ПРИЁМА, а не забота автора стража.** Общий помощник, а не
строка, которую каждый раз вспоминают:

```ts
/** Текст файла БЕЗ комментариев. Страж проверяет код, а не рассуждения рядом с ним. */
export function sourceCode(text: string): string {
  return text.replace(/\/\*[\s\S]*?\*\//g, '').replace(/(^|[^:])\/\/.*$/gm, '$1');
}
```

Тонкость, которую легко потерять: `[^:]` перед `//` нужен, чтобы не срезать `https://…` внутри
строкового литерала. Первая редакция этого помощника без него ломала проверки адресов.

**2. Границы блока задаются НАЧАЛОМ следующего блока, а не позицией искомого.** Слайс «от
находки до позиции класса X» захватывает всё между ними, если X лежит ниже по файлу. Правильно —
резать по началу следующей известной конструкции.

**3. Мета-требование к жанру.** Страж по исходнику принимается только вместе с прогоном на
файле, где искомая строка **присутствует в комментарии и отсутствует в коде**. Это тот же приём,
что PR-018 требует для стражей вообще, но нацеленный на конкретный режим отказа этого жанра.

### Почему это в PR-029, а не отдельной заявкой

Класс тот же: **страж проверяет не то, что имел в виду автор**. В первых четырёх случаях
расходились область и намерение, здесь — форма и смысл. Лечение в обоих случаях одно: свойство
выводится механически, а не перечисляется руками.
