# PR-026: Каждая починка вносит дефект того же класса — шесть повторений подряд, и пайплайн этого не видит

**Класс:** цикл ревизий не имеет гейта на регрессию собственного класса · **Приоритет:** P0 · **Найдено:** 2026-08-29/30, один прогон трёх фич · **Предложение испытано на восьмой итерации, поправка ниже**

## Наблюдение

Не «иногда случается», а **восемь раз подряд без единого исключения**, в трёх фичах одного прогона:

| # | Что чинили | Что внесли той же правкой | Общий разделяемый ресурс |
|---|---|---|---|
| 1 | FR-009 ред. 1→2: лимит без чисел | разбор тела переехал ВНУТРЬ транзакции | пул соединений |
| 2 | FR-009 ред. 2→3: DoS пула | ждущая блокировка — очередь тоже держит соединения | пул + блокировки |
| 3 | FR-009 ред. 3→3.1: очередь за локом | try-лок по IP — все за одним NAT получают ложные `429` | блокировка, общая для многих |
| 4 | FR-010 ред. 2: argon2 держал соединение | argon2 вынесен за транзакцию и оказался **до лимитера** — бесплатное жжение CPU | CPU и память процесса |
| 5 | FR-010 ревью 1→2: гонка на строке | TRY-лок по аккаунту — **лотерея**, вор запирает владельца | строка `accounts` |
| 6 | FR-011 ред. 1→2: ложный `429` за NAT | ключ лока разведён с ключом счётчика — **атомарность счётчика исчезла** | счётчик попыток |
| 7 | FR-011 ред. 2→3: атомарность | ждущий лок + две транзакции → **вложенный `withService`, самоблокировка пула** | соединения пула |
| 8 | FR-014: разбор вынесен из транзакции (верно) | предел строк проверялся **после** разбора — цена ограничена размером файла, а не числом строк | **поток событий Node** |

Числа, где они измерены: №5 — успехов владельца **0 из 15** под потоком вора против **5 из 5**
без него; №6 — **40 одновременных попыток при пороге 30 проходят все сорок**, с прежним ключом
проходила одна.

## Форма, одна и та же во всех шести

1. Правка написана против конкретного, названного дефекта.
2. Она его действительно закрывает — это проверено.
3. Проверка построена **на сценарии самой правки**.
4. Ресурс, который правка при этом задела или создала, не проверяет **никто**.

Шаг 4 — не небрежность. В каждом случае автор держал в голове предыдущий дефект и целился
именно в него; ровно поэтому взгляд не расширялся.

## Почему существующие механизмы это пропускают

| Механизм | Почему не ловит |
|---|---|
| Валидация требований | смотрит документ против документа; новый ресурс в требованиях не назван, потому что его создала реализация |
| Ревью реализации | ловит — но **после** того, как правка написана и закреплена. Из шести случаев ревью поймало два, и оба уже были в коде |
| Тесты предыдущей ревизии | зелены по построению: они написаны против старого дефекта, а новый лежит в другом ресурсе |
| Правило `shared-resource-verification.md` | **существует, верно сформулировано и не исполняется**. Оно живёт на слое 4 — «автор вспомнит четыре вопроса». Шесть раз подряд не вспомнил |

Последняя строка — суть заявки. Правило есть, оно правильное, у него есть список из четырёх
вопросов, и оно **ни разу не сработало**, потому что ничто не заставляет его открыть.

## Что предлагается: гейт «дельта ресурсов» между ревизиями

Не новое правило — **исполнение существующего**, перенесённое со слоя 4 на слой 3.

При переходе ревизии N → N+1 любого документа фичи пайплайн обязан потребовать заполненную
таблицу, и без неё не пропускать дальше:

```markdown
## Дельта разделяемых ресурсов (ревизия N → N+1)

| Ресурс | Было | Стало | Кто ещё в очереди | Кого наказывает насыщение |
|---|---|---|---|---|
| соединение пула | удерживается на argon2 (~40 мс) | не удерживается | вход, дашборд, витрина, виджет | — |
| CPU/память | 1 argon2 на попытку | **2 argon2 на попытку** | argon2 входа | любого, кто входит |
```

Правая половина последней строки — и есть найденный дефект №4. Он виден в таблице **до**
написания кода, потому что таблица требует назвать не «что я починил», а «что стало с каждым
ресурсом».

Четыре колонки — дословно четыре вопроса из `shared-resource-verification.md`. Заявка не
придумывает содержание; она требует его записать.

### Почему таблица, а не пункт чек-листа

Пункт «проверил разделяемые ресурсы ✔» ставится не глядя и ничего не стоит. Таблица требует
**назвать ресурс поимённо** и заполнить четыре клетки. Пустая клетка — видимый пробел; галочка
— нет. Это разница между «проверка выполнена» и «проверка существует».

### Дешёвая машинная часть

Полностью автоматизировать нельзя — «какие ресурсы задеты» есть суждение. Но два условия
детерминированы и стоят десяти строк:

```bash
# ревизия N+1 существует, а таблицы дельты нет
grep -q '## Дельта разделяемых ресурсов' docs/features/*/0*.md || exit 1
# в таблице есть строка, где «Было» ≠ «Стало», и колонка «кто ещё в очереди» пуста
```

Второе — тот самый случай: ресурс назван, изменение признано, а вопрос «кто ещё» не отвечен.

## Испытание предложения на живом прогоне — и его поправка

Таблица дельты была заполнена **заранее** для восьмой фичи, до написания кода. Результат
двойственный, и обе половины важны.

**Помогла.** Из неё сразу стало видно единственное место, где длительность зависит от входных
данных, и предел был назван числом, а не «разумным значением». Разбор вынесен из транзакции
там же, по строке «соединение пула».

**И всё же пропустила** — по двум причинам, обе исправимы:

| Что пропущено | Почему |
|---|---|
| **Поток событий Node** — единственный ресурс, который фича насыщала ПЕРВЫМ | В шаблоне таблицы его не было. Автор перечислял то, о чём привык думать: пул, память, строки БД. Синхронный посимвольный цикл по двум мегабайтам останавливал приложение целиком за 294 мс, и пул из тридцати соединений здесь ни при чём — приложение вставало раньше, чем кончались соединения |
| Строка «память процесса: границей предел тела» | **Неверна.** Предел ограничивает ВХОД; выход разбора больше входа в сто раз (+217 МиБ heap на 2 МиБ тела) |

**Поправка к предложению.** Колонка «Ресурс» не должна быть свободным полем — она должна быть
**списком с обязательным перебором**:

```markdown
| Ресурс | Было | Стало | Кто ещё в очереди | Кого наказывает насыщение |
|---|---|---|---|---|
| соединение пула      |  |  |  |  |
| ПОТОК СОБЫТИЙ (синхронная работа) |  |  |  |  |   ← пропускался чаще всего
| CPU (хеширование, разбор, сжатие) |  |  |  |  |
| память процесса: ВХОД и ВЫХОД отдельно |  |  |  |  |
| блокировки строк и advisory |  |  |  |  |
| счётчики и квоты     |  |  |  |  |
| внешние вызовы       |  |  |  |  |
```

Строка, к которой нечего написать, отмечается «не задет» — и это тоже ответ. Пустая строка —
пробел; отсутствующая строка — слепое пятно, а слепое пятно не видно по определению.

Два уточнения, заслуженных тем же прогоном:

- **вход и выход считаются раздельно.** «Ограничено пределом тела» ложно всякий раз, когда
  обработка порождает структуру больше входа;
- **синхронная работа — отдельная строка, а не подвид CPU.** Разница наблюдаема: занятый CPU
  замедляет, занятый единственный поток **останавливает**.

## Отдельное следствие: тест, красный на УЛУЧШЕНИИ

Побочно найден смежный класс, стоящий отдельной строки. Тест, проверяющий **механизм** вместо
**свойства**, краснеет, когда механизм заменяют на лучший:

```
AC-010.26 утверждал:  ok.length === 1  И  busy.length === N - 1
правка, устранявшая блокер, уронила его ВТОРЫМ утверждением при зелёном первом
```

Такой страж учит сохранять худший вариант. Вред тот же, что от зелёного по построению, только
с обратным знаком, и `guard-must-be-able-to-fail.md` его не покрывает: там речь о страже,
который не может покраснеть, здесь — о страже, который краснеет не на том.

Формулировка для правила: **критерий приёмки утверждает наблюдаемое свойство системы, а не
использованное средство.** «Ровно одна операция успешна» — свойство. «Остальные получили
`busy`» — средство.
