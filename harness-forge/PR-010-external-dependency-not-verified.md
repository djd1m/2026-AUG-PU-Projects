# PR-010: Пайплайн не проверяет, существует ли внешняя зависимость

**Класс:** валидация против документов, а не против реальности · **Приоритет:** P0
**Найдено:** генерация кода по провалидированной документации, проект 01

## Проблема

Все фазы валидации проверяют документы **друг против друга**: согласованность, полноту,
INVEST/SMART, покрытие сценариями, трассировку. Ни одна не задаёт вопрос:
**а существует ли внешний API, на котором держится требование?**

В результате требование может быть внутренне непротиворечивым, полностью прослеживаемым,
покрытым Gherkin-сценариями — и при этом невыполнимым.

## Доказательство

Проект 01 требовал транскрипцию видео-отзывов через Claude API. Это прошло:

| Проверка | Результат |
|---|---|
| FR-003 в `Specification.md` с AC | ✅ |
| Алгоритм в `Pseudocode.md` §1.1 | ✅ |
| Сервис в `Architecture.md` §5, ADR-005 | ✅ |
| Валидация Phase 2, пять линз | ✅ 🟢 READY, 89.4 |
| Ре-валидация со скептической установкой | ✅ |
| Финальный гейт | ✅ 0 незакрытых пунктов |
| `check-pipeline-gaps.sh` | ✅ зелёный |

**Claude API не принимает аудио.** Поддерживаемые типы content-блоков: `text`, `image`,
`document`. Аудио прямо назван неподдерживаемым — SDK выбрасывает `UnsupportedMCPValueError`
для «unsupported content types like audio».

Вся ветка транскрипции — сервис, ADR, алгоритм, тесты, Dockerfile — построена на пути,
которого не существует.

## Кто это нашёл

Не пайплайн. Агент, который сел **писать код** сервиса, не смог найти формат content-блока
для аудио и честно пометил `[GAP]`: «no documented audio content type exists in the current
Anthropic API surface», поставив base64-заглушку. Заглушка не заработала бы.

Подтверждение потребовало отдельной проверки по документации SDK — вне пайплайна.

## Это не единичный случай

На том же прогоне тем же способом нашлись ещё два дефекта — и оба нашёл автор кода,
а не валидатор:

- **Схема БД недостаточна для описанных запросов.** `projects.deactivated` используется
  в `Pseudocode.md` §5.1, но отсутствует в схеме `Architecture.md` §3.
  `referral_attributions.status`: архитектура перечисляет 3 значения, псевдокоду нужны 5.
- **Роль ffmpeg назначена не тому сервису.** Dockerfile ставил ffmpeg в `worker`, тогда
  как `Architecture.md` §5 отдаёт извлечение аудио сервису `mcp-claude`.

Общая черта: валидация сверяет **утверждения документов между собой**. Она структурно
не способна поймать то, что расходится с внешним миром или не выдерживает попытки исполнения.

## Предлагаемое исправление

### 1. Инвентаризация внешних зависимостей (слой 3)

Новый обязательный артефакт после Phase 1 — `docs/External_Dependencies.md`:

| Зависимость | Что от неё нужно | Подтверждено | Источник |
|---|---|---|---|
| Claude API | приём аудио, возврат текста | ❌ **НЕТ** | docs.anthropic.com, типы блоков: text/image/document |

Пустая колонка «Подтверждено» — блокер Phase 2, а не примечание.

### 2. Правило: возможность API подтверждается ссылкой (слой 2)

Требование, опирающееся на внешний API, обязано нести ссылку на документацию, где эта
конкретная возможность описана. Не на главную страницу продукта — на раздел, где сказано,
что нужный тип входа поддерживается.

### 3. Проверка исполнением там, где это дёшево (слой 1)

Для критичных зависимостей — минимальный вызов на этапе Phase 2:

```bash
# один реальный запрос: принимает ли API этот тип входа вообще
```

Дороже grep, но дешевле, чем обнаружить это на неделе реализации.

### 4. Установка для валидатора архитектуры

Добавить в его чек-лист прямой вопрос: **«Для каждой внешней зависимости — подтверждено ли
документацией, что она умеет ровно то, что от неё требуется?»**

Сейчас валидатор архитектуры проверяет соблюдение Architecture Constraints и покрытие
требований — но исходит из того, что названные API умеют заявленное.

## Цена бездействия

На этом прогоне дефект вскрылся на Phase 2 команды `/start`, то есть до реализации.
Повезло: код писал агент, который читает документацию. Человек, доверившийся
провалидированной спецификации, потратил бы день недельного проекта на сервис,
который не может работать.

## Проверка исправления

Внести в постановку требование, опирающееся на несуществующую возможность внешнего API,
и убедиться, что Phase 2 его останавливает.
