# PR-004: Метрика без целевого значения проходит валидацию

**Класс:** неполный шаблон · **Приоритет:** P1 · **Найдено:** прогон проекта 01

## Проблема

Шаблон требует назвать метрику успеха, но не требует назвать **целевое число**.
Формулировка «число установленных виджетов на внешних доменах» проходит как валидная
метрика — хотя по ней невозможно определить, удалась неделя или нет.

## Доказательство

Агент, генерировавший `Completion.md`, честно пометил это `[GAP]`:

> «Числовой целевой показатель метрики недели (сколько установленных виджетов = успех) —
> не задан в исходных документах»

То есть модель заметила пробел и корректно его отметила. Но пайплайн на этом не остановился:
документ с неизмеримой метрикой прошёл дальше, а `[GAP]` остался внутри файла, который
никто не обязан читать перед следующей фазой.

## Почему это важнее, чем кажется

Метрика без порога создаёт иллюзию измеримости. В конце недели любой результат можно объявить
успехом или провалом задним числом — что делает всю дисциплину growth-требований декоративной.

## Предлагаемое исправление

### 1. Формат метрики (слой 2)

В шаблоне PRD и в блоке growth-требований: метрика записывается как
**`<название> — цель <число> за <срок>`**. Без числа — не метрика.

### 2. Проверка SMART (слой 3)

`requirements-validator` уже штрафует vague-термины. Добавить в ту же таблицу: метрика успеха
без числового значения — минус баллы, как за неизмеримое требование.

### 3. Grep-guard (слой 1)

```bash
grep -A3 'Метрика недели' docs/PRD.md | grep -qE '[0-9]+' || echo "метрика без целевого числа"
```

### 4. Интерпретация результата

Полезная практика из прогона: вместе с целью задавать **диапазоны интерпретации**.
Пример из проекта 01: «цель 10; меньше 5 — loop не запустился; больше 20 — проверить
на накрутку». Это превращает число в инструмент принятия решения, а не в галочку.

## Проверка исправления

Прогнать `/replicate` с постановкой, где метрика названа без числа, и убедиться,
что валидация это отмечает.
