# PR-003: Сценарий есть, реализации нет — нет трассировки Gherkin → Pseudocode

**Класс:** отсутствует трассировка · **Приоритет:** P0 · **Найдено:** ре-валидация проекта 01

## Проблема

Требование с Gherkin-сценарием считается закрытым. Но сценарий живёт в `Specification.md`,
а алгоритм — в `Pseudocode.md`, и **ничто не связывает их механически**.

В результате возможна ситуация: сценарий описывает проверку, которой в алгоритме нет вовсе.
Инженер, реализующий буквально по псевдокоду, пропускает требование целиком — и оба документа
при этом выглядят корректными.

## Доказательство

Блокер B-4 (проверка подписи платёжного вебхука) был предъявлен валидацией, «исправлен»
в итерации 1 и закрыт. Ре-валидация обнаружила:

- в `Specification.md` FR-GROWTH-002 есть `@security`-сценарий: вебхук с неверной подписью
  отклоняется, комиссия не начисляется, попытка пишется в audit log;
- в `Pseudocode.md` функция `onPaymentWebhook` **не содержит ни строки** проверки подписи;
- секрета для HMAC нет ни в `Architecture.md`, ни в docker-compose.

Блокер был закрыт **на бумаге**. Обнаружил это только специально запущенный скептический
ре-валидатор с прямой установкой «искать сценарии-пустышки».

Дополнительно при ручной починке выяснилось, что дефект был глубже: важен ещё и **порядок** —
подпись обязана проверяться до записи идемпотентности, иначе поддельный вебхук с угаданным
`event.id` блокирует настоящий. Ни сценарий, ни алгоритм этого не выражали.

## Второй случай того же класса

Ре-валидация нашла сценарий-пустышку в FR-NFR-SEC-001: проверка обращалась к эндпоинту,
которого нет ни в архитектуре, ни в алгоритмах. Тест без цели.

## Предлагаемое исправление

### 1. Grep-diff трассировки (слой 1)

После Phase 1 — сверка множеств:

```bash
# все ID требований со сценариями
grep -ohE 'FR-[A-Z]*-?[0-9]{3}' docs/Specification.md | sort -u > /tmp/spec-ids
# все ID, упомянутые в алгоритмах
grep -ohE 'FR-[A-Z]*-?[0-9]{3}' docs/Pseudocode.md | sort -u > /tmp/pseudo-ids
comm -23 /tmp/spec-ids /tmp/pseudo-ids   # требования без алгоритма — находка
```

### 2. Требование к формату Pseudocode

Каждый алгоритм обязан нести ссылку на ID требования, которое реализует. Сейчас это
делается непоследовательно.

### 3. Gate на `@security`-сценарии особо

Сценарий с тегом `@security` описывает **защиту**. Его отсутствие в алгоритме — не стилистика,
а дыра. Проверять отдельно и строже:

```bash
# каждый FR с @security должен иметь упоминание в Pseudocode
```

### 4. Установка для ре-валидатора

Если в пайплайн добавляется повторная проверка после правок — её агенту нужно давать прямую
установку «искать сценарии, которые выглядят проверкой, но ничего не проверяют». Без такой
формулировки ре-валидатор склонен подтверждать закрытие по факту наличия текста.

## Проверка исправления

Удалить из `Pseudocode.md` любую проверку, оставив соответствующий сценарий в `Specification.md`,
и убедиться, что guard это ловит.
