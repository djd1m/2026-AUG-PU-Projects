# PR-017: В тулките нет слоя проверенных артефактов — каждый проект выводит их заново

**Класс:** неполный pre-shipped контракт · **Приоритет:** P1 · **Найдено:** `/harvest full`, проект 01

## Проблема

`npx @dzhechkov/p-replicator init` поставляет пять видов артефактов: **скиллы, команды,
агенты, правила, хуки**. Все пять описывают, **как работать**. Ни один не поставляет то,
**чем работать** — ни одного исполняемого стража, ни одного проверенного фрагмента кода,
ни одного шаблона окружения.

Следствие видно на прогоне проекта 01. Проект самостоятельно вывел пять стражей:

| Страж | Что ловит | Сколько стоило вывести |
|---|---|---|
| `check-port-conflicts.sh` | БД опубликована наружу; прокси обходится; порт занят | Компрометация VPS майнером |
| `check-env-wiring.sh` | Переменная читается кодом, но не проброшена в compose | Все выданные ссылки вели на localhost |
| `check-cjm.sh` | Путь клиента рвётся на развёрнутом стенде | Тот же дефект, найденный владельцем продукта |
| `check-compose-buildable.sh` | Compose не собирается | — |
| `init-test-env.sh` | Тестовая БД с предсказуемым паролем | Та же компрометация |

Ни один из них не был подсказан пайплайном. Каждый написан **после** того, как
соответствующий дефект уже случился. Проект 02 начнёт с того же нуля.

Правила это не закрывают: правило `docker-ports.md` говорит «проверить занятость
скриптом `check-port-conflicts.sh`» — **скрипта, которого в поставке нет**. Правило,
ссылающееся на несуществующий инструмент, исполняется ровно настолько, насколько модель
захочет написать инструмент сама. Это слой 4 по лестнице стоимости обнаружения, хотя
проверка по своей природе принадлежит слою 1.

## Исправление

### 1. Расширить pre-shipped контракт тремя каталогами

```
.claude/patterns/     — архитектурные приёмы как документы
.claude/snippets/     — исполняемые фрагменты (bash/, typescript/)
.claude/templates/    — шаблоны файлов окружения
```

Это не новая механика: `04-integrate.md` скилла `knowledge-extractor` **уже** описывает
эти три категории и их целевые пути. Не хватает только того, чтобы `init` их поставлял,
а `verify` — проверял.

### 2. Поставлять стражи как исполняемые файлы, а не как упоминания в правилах

Каждое правило, требующее проверки, обязано поставляться **вместе с проверкой**.
Правило без исполняемого стража — это слой 4, выдающий себя за слой 1.

### 3. Добавить в `verify` проверку соответствия

```
✗ .claude/rules/docker-ports.md ссылается на scripts/check-port-conflicts.sh — файла нет
```

Это ровно тот класс дефекта, который `verify` уже умеет ловить для остальных артефактов.

### 4. Не обобщать то, что обобщается в пустоту

`check-cjm.sh` намеренно **не** вошёл в поставку как скрипт: он завязан на конкретные
эндпоинты, и обобщённая версия была бы пустой оболочкой, которая выглядит готовым
инструментом, но требует дописывания с нуля. Поставляется **метод** — паттерн
`cjm-acceptance-gate.md` со скелетом и списком граблей.

Это правило для генератора вообще: артефакт, от которого после обобщения остаётся одна
оболочка, вреднее отсутствия артефакта — он создаёт ложное ощущение покрытия.

## Урок, который стоит забрать отдельно

При обобщении `check-env-wiring.sh` наивный перенос определял каталог сервиса по
`build.context`. В монорепо `context` одинаков у всех сервисов — проверка насчитала
**32 «потери» на проекте, где их не было**. Страж, который кричит всегда, отключают
через неделю; молчаливый ложноположительный страж хуже отсутствующего.

Отсюда требование к переносу любого стража в поставку: **прогнать на проекте-источнике
и сверить с проектной версией**. Совпадение результатов — критерий приёмки обобщения.

## Способ проверки

```bash
npx @dzhechkov/p-replicator init
test -d .claude/patterns && test -d .claude/snippets && test -d .claude/templates
bash .claude/snippets/bash/check-env-wiring.sh   # должен запускаться сразу после init
npx @dzhechkov/p-replicator verify               # ловит правило без стража
```
