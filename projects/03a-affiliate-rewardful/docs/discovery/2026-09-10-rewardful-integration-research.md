# Rewardful, N3 и N3a: универсальность интеграций

Дата исследования: 2026-09-10. Статус: результаты зафиксированы; дальнейшая работа приостановлена владельцем. Это исследование документации и исходников, не независимая эксплуатационная проверка Rewardful или новая приёмка интеграции N3.

## Главный результат

Rewardful предоставляет готовые интеграции для определённых платформ и платёжных сценариев. Подключение произвольного магазина с произвольной платёжной системой без разработчика не подтверждено. Цель владельца N3a — самостоятельное подключение магазинов — шире исходного продукта; её следует реализовывать через проверяемые комбинации платформы, версии, checkout и платёжного модуля. Универсальный API сам по себе не обеспечивает установку без разработчика.

Прямых экспериментов с закрытым кабинетом Rewardful, его платёжными аккаунтами и production-транзакциями не было. Доступны утверждения производителя и инструкции. Ссылки не являются архивными снимками: содержание может измениться; перед реализацией существенные возможности перепроверяются.

## Как устроена цепочка оригинала

Партнёрская ссылка → tracking/referral ID → передача ID в поддерживаемый checkout → событие платёжной системы → связь покупателя с партнёром → комиссия → корректировка по возврату. Готовые платформенные интеграции скрывают от владельца часть настройки; кастомные сайты требуют соответствующего подключения. Здесь расширяемость достигается в том числе общей платёжной платформой, а не отдельным индивидуальным денежным API для каждого магазина.

## Сравнение двух наших подходов

| Вопрос | N3: прямая проверка ЮKassa | Первоначальный N3a: подтверждение в N1 и подписанный обмен |
|---|---|---|
| Готовность сейчас по прочитанным исходникам | Есть referrals, customer binding, external order/event API и тестовый bridge | Приняты foundation и identity/program/partner; bridge ещё не реализован |
| Откуда доказательство оплаты | N3 самостоятельно читает канонический объект провайдера | N1 проверяет провайдера и передаёт attestation; N3a доверяет этой границе |
| Секреты провайдера | Требуются на стороне N3 | Для N1 остаются исключительно в N1 |
| Расширение на другие сайты | Проще переиспользовать общий provider adapter при совместимом checkout; остаётся связать referral с заказом | Общий формат событий допускает другие адаптеры; каждому нужен готовый установочный путь |
| Основная цена поддержки | Provider API, секреты, особенности checkout и магазина | Версии коннекторов, достоверность передаваемых фактов, доставка и сверка |
| Соответствие механике Rewardful | Ближе по прямой интеграции с платёжным провайдером | Более явно отделённая billing authority; это наше архитектурное решение |

Bearer против HMAC — отдельный выбор защиты канала, а не причина универсальности. Подпись доказывает отправителя и целостность сообщения; не доказывает независимо факт оплаты. Прямая проверка у провайдера тоже не подтверждает автоматически атрибуцию, согласие партнёра и условия комиссии.

Бизнес-вывод: N3 ближе к готовой первой интеграции сейчас; N3a можно расширить общим ядром и устанавливаемыми адаптерами. Ни один из текущих вариантов не даёт доказанного подключения любого магазина без доработок. Решение владельца — продолжать именно N3a — сохранено; миграции обратно в N3 не предлагалось и не выполнялось.

## Найденные донорские модули

Пути относительно корня репозитория; это прочитанные кандидаты, не подтверждение совместимости или завершённого переноса:

- N3 `projects/03-affiliate-rewardful/shared/referrals/service.mjs`: visit/bind, срок перехода, промокод выше ссылки, запрет саморефералов, повторная привязка клиента.
- N3 `shared/domain/referral-attribution.mjs`: использование сохранённой customer binding для повторных покупок (путь внутри N3).
- N3 `shared/integrations/merchant-client.mjs`: фиксированные маршруты, ограничения ответа, timeout и cookie parser; авторизация и DTO потребуют адаптации.
- N3 `shared/payments/service.mjs`, `apps/api/referrals.mjs`: внешний заказ/события, прямая provider verification. Не переносить provider credentials или целиком чужую модель tenants.state.
- N3 `tests/referral-service.test.mjs`, `tests/referral-payment.test.mjs`, `tests/referral-client.test.mjs`, `tests/e2e/proofwall-bridge.mjs`: сценарии атрибуции, дублей, concurrency, checkout и возврата.
- N1 `projects/01-testimonials-senja/services/worker/src/n3-outbox.ts`: durable очередь, lease, повторная доставка, ACK; `apps/web/src/lib/n3-referral.ts` и `n3-payment.ts`: сохранение источника и связка оплаты с outbox (пути внутри N1).

Часть исходников просмотрена целиком, часть — по относящимся к интеграции участкам. Полный compatibility/security audit и запуск тестов доноров в этом исследовании не выполнялись. Источники активно меняются в других сессиях: перед переносом нужно зафиксировать актуальные commit/SHA конкретных файлов и минимальные зависимости. Хеши прошлых чтений не восстанавливаются задним числом.

## Предварительное исследование торговых платформ

- [WooCommerce webhooks](https://woocommerce.com/document/webhooks/): доступны события и подпись; после более пяти последовательных ошибок webhook отключается. Требуются диагностика и отдельное восстановление пропусков, а не обещание бесконечных retry.
- [WooCommerce gateway API](https://developer.woocommerce.com/docs/features/payments/payment-gateway-api): различаются online/offline способы и интеграция обычного/block checkout. Все gateways одной платформы нельзя объявить поддержанными одной проверкой.
- [InSales API](https://api.insales.ru/?doc_format=XML): официальный каталог найден и открыт; установка, полномочия, достоверная оплата/возвраты и replay пока не исследованы достаточно для выбора.
- [Tilda payment systems](https://help.tilda.cc/online-store/payment-systems): настройка платёжных систем подтверждена; достаточность payment/refund API для нашей гарантии не установлена.
- 1С-Битрикс упомянут как возможный приоритет владельца; отдельное исследование в этом проходе не выполнялось.

Первая внешняя платформа не выбрана. Вопрос о приоритете не разрешает начинать конкретный plugin или включать платные услуги автоматически.

## Решения и открытые вопросы на паузе

Принято: N3a, самостоятельное подключение, N1 как первый проверочный адаптер, ЮKassa для N1, ручные переводы 5-го за прошлый календарный месяц. N3 — исключительно read-only донор, его параллельная сессия не затрагивается.

Открыто: первый сегмент/платформа; конкретный gateway/version; merchant ownership и recovery; guest checkout и надёжная идентичность повторного покупателя; база комиссии с доставкой/налогами/скидками; распространение plugin/app; подробный trust/reconciliation контракт. Предложенный usability target 4 из 5 владельцев за ≤10 минут — ещё не утверждённый измеренный результат. D7 остаётся отдельным нерешённым вопросом.

Связанные артефакты: [план расширения](../plans/2026-09-10-self-service-expansion.md), [PRD0.3](../PRD.md), [проверка scope](../telemetry/p-replicator/20260910T100054Z-self-service-expansion/scope-review.md). План проверен как план, не как готовая реализация.

Указание владельца: «Зафиксируй результаты ресерча в артефактах проекта, пока не будем продолжать». После сохранения/commit/push не запускать дальнейшую разработку, исследование или агентов до нового указания. Эта пауза приоритетнее прежних разрешений продолжать автоматически.
