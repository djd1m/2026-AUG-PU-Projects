# ADR — N3a, CJM A

Дата: 2026-09-09. Статус решений: **предложены для конкретного XL-checkpoint до кода**. Прямые решения владельца — N1, YooKassa, CJM A, ручные выплаты 5-го за предыдущий календарный месяц — уже приняты; технические подробности ниже не изображаются реализованными.

## ADR-001 — Отдельный модульный монолит

**Контекст:** один первый клиент N1; учёт денег требует локальных атомарных операций.
**Решение:** отдельные процессы N3a web и worker из одного проекта, собственный PostgreSQL, внутренние модули identity, programs, attribution, intake, ledger, registry, tax, growth. Никаких shared DB или runtime imports N1/N2. Identity-only session precedes partner consent; owner enrollment is trusted bootstrap, operator scopes owner-granted; partner acceptance atomically creates Membership/assets. Node 22, TypeScript и Next.js — предлагаемый совместимый с донорами стек; точные пакеты/образы фиксируются после аудита текущих donor lockfiles перед foundation.
**Альтернатива:** микросервисы усложняют атомарный ledger; копирование всей N1 схемы сохраняет чужую модель долга.
**Последствия:** отдельные web/worker пулы, миграционная роль, backup и operational ownership; перенос только минимального замыкания пригодных блоков с provenance и тестами.

## ADR-002 — N1 billing + local outbox и cutover

**Контекст:** сбой N3a не должен задержать активацию оплаченного N1. У N1 нет нужного outbox/refund feed; существующие комиссии одноразовые.
**Решение:** N1 проверяет объект у YooKassa **до** транзакции; customer/project получает из локального checkout. В одной N1 транзакции — claim, billing update и неизменный outbox. Отправка только после commit. Стабильный event UUID сохраняется при повторах; reconcile feed доступен по cursor. Это новая работа интеграционного адаптера, а не внешняя подтверждённая возможность N1.
**Cutover:** подписанный оператором отчёт сверки фиксирует точку и правила eligibility. N1 legacy commission bypass включается атомарно с authority-флагом подключения; N3a допускает только платежи по договорённой границе. Долг до cutover остаётся N1, не импортируется; возврат такого платежа — legacy exception. Не допускается интервал двух активных источников обязательств. Старые pending checkout и существующие атрибуции требуют явного решения в cutover manifest; неизвестные соответствия блокируются.
**Последствия:** после начала N3a-ledger откат UI не включает автоматически старую комиссию N1. Интеграционный владелец повторно аудирует текущий N1 до изменения кода: соседний проект меняется параллельно.

## ADR-003 — Раздельные границы доверия и повторов

**Контекст:** уведомление, подтверждённая продажа и попытка доставки имеют разные идентификаторы.
**Решение:** внутренний N1→N3a HMAC SHA-256 по raw body и подписанным timestamp/method/path/connection; constant-time проверка до JSON, затем freshness ±300 s. На повторе новое время доставки, прежние event ID и bytes. Ключ ограничен одним connection/environment, ротация с key ID. YooKassa не получает вымышленной подписи: N1 проверяет опубликованные CIDR и canonical API через merchant credentials; N3a проверяет подписанную N1 attestation и её соответствие configured merchant/mode/checkout/amount, сверяет пробелы через N1 до ledger claim. Только N1 хранит YooKassa credentials и делает canonical API GET; N3a их не копирует. Доверие к подписанному N1 как billing authority явно является границей пилота.
**Последствия:** unique receipt(connection,event_id) плюс независимые unique payment(connection,provider_payment_id) и refund(connection,provider_refund_id). Несовпадение payload hash при том же event ID — конфликт и review. Auth failure не занимает receipt. Redis/process-memory не источник дедупликации.

## ADR-004 — Неизменный ledger и кумулятивные возвраты

**Контекст:** повторные оплаты N1 — самостоятельные продажи; изменение условий и частичные возвраты не должны переписывать историю.
**Решение:** pilot every eligible payment/lifetime с frozen registration rate; first-only/finite limits отклонены как не требовавшаяся сложность, first_paid_at=min eligible event time только проекция. Комиссия по каждой допустимой подтверждённой оплате с frozen policy; деньги — целые minor units, ставки — basis points, без float. Все refunds привязаны к parent payment и исходной положительной комиссии. Под parent lock canonical sort ВСЕХ durable refunds по occurred_at/provider_refund_id задаёт marginal cumulative rounding и целевые суммы по event month. Каждый новый refund и prefreeze recompute сравнивают targets с ledger; новые signed refund_reallocation differences исправляют открытые периоды, старые записи неизменны. Замороженный basis month получает correction только в next open period. Semantic registry hash использует canonical business inputs, отдельный audit hash включает историю доставок. Полный возврат отменяет ровно исходную комиссию; сумма возвратов больше оплаты — exception, не clamp ложных данных.
**Последствия:** refund-before-payment ставится в ожидающее сверки состояние, не подтверждается как обработанный финансовый факт. Перестановка независимых refund ID не меняет итог; старые mutable версии не откатывают состояние. Возврат после оплаты партнёру создаёт новый долг/корректировку.

## ADR-005 — Calendar close, allocations и ручное подтверждение

**Контекст:** владелец платит 5-го за прошлый месяц без 30–45-дневного hold.
**Решение:** предлагаемая зона Europe/Moscow, immutable после первой активации/атрибуции/ledger даже при pause; календарный месяц — [начало, начало следующего). Provider occurred_at сохраняется отдельно от accounted_month. Учётный месяц закрывается 5-го после сверки; опоздавшее после закрытия событие учитывается в следующем открытом месяце с исходной датой. Закрытие и posting используют один program mutex/transaction lock; источник включён до snapshot или идёт поздней корректировкой, никогда теряется между ними.
**Реестр:** предварительный просмотр изменяемый; frozen receipt и allocations неизменны. Повтор close возвращает тот же register ID/hash. Отрицательный net переносится одной carry-записью, у которой не более одного successor; исходные ledger allocations уже потреблены и не включаются снова. Нулевой net не создаёт перевод. Блокировка строки не переносит её автоматически в следующий месяц; прежнее обязательство остаётся видимым.
**Подтверждение:** оператор фиксирует собственный факт перевода, сумму, фактическую дату и reference; unique confirmation(row) и request key. CSV и повторное нажатие не создают перевод. Срок самого перевода — due date5-го, не только подготовки таблицы. Обычная подготовка/confirm требуют эту дату; подготовка просроченного погашения требует отдельного approval владельца, причины и актуальной налоговой проверки, исходный срок остаётся; ранний/поздний состоявшийся перевод сохраняется observation→сверка, с derived early/late и исходным сроком. Просрочка/выходной не сдвигают due date; поздняя запись факта5-го не является просрочкой перевода.
**Последствия:** банковская отправка/ack/получение не утверждаются. Сомнительный уже совершённый перевод — reconciliation lock, а не новый платёж. Изменения после freeze оформляются связанной корректировкой, история остаётся.

## ADR-006 — Налог как проверяемый учёт, а не flat 13%

**Контекст:** обязательная прогрессивная шкала и ручные выплаты; категория договора и плательщик ещё проверяются.
**Решение:** versioned rules + eligibility evidence, payer/person/tax-year/base-category YTD с подтверждённым opening balance и удержаниями. Для применимой базы нарастающий налог по диапазонам и разница, налоговый год определяется фактической выплатой. До реального перевода бухгалтер утверждает применимость, округление/вычеты, договор и обязанности плательщика. Неизвестное YTD не ноль.
**НПД:** 6% для дохода от организаций/ИП — налог получателя, не автоматическое удержание N3a. Проверка статуса, допустимости договора и заявления о совокупном лимите 2,4 млн; внутренний оборот N3a не доказывает общий доход. Неподтверждённость блокирует готовность строки, начисленное видно.
**Конкурентность:** persistent PayerYearGuard unique(payer,person,year) хранит один live reserve и observation blockers для ВСЕХ моделей, включая НПД и разные base categories/programs. Per-base TaxYTD — только расчёт удержаний. NPD declared baseline фиксирует уже включённый внутренний доход; новые known internal paid/reserved amounts учитываются без double-count; чужие внешние доходы неизвестны без evidence. Налоговый snapshot замораживается при подготовке операции; смена фактической даты/статуса до перевода требует отмены подготовки и новой версии. Поздняя запись оценивает validity на actual transfer date, не report time. После состоявшегося перевода observation-only route доступен даже under restore/no preparation; accountant evidence transaction locks old/actual years sorted, supersedes old preparation и создаёт corrected snapshot+одну confirmation, consumes/moves reservation атомарно без окна нового перевода.
**Историческая сверка (V3):** historical tax вычисляется из immutable approved балансов непосредственно ДО перевода и доказанного порядка, исключающего позднейшие платежи. Независимый current counter plan фиксирует inclusion/delta для guard total, NPD internal, NPD coverage, base и withheld; current totals или current−gross не заменяют историю. Если декларация уже включает НПД-перевод, отсутствующий internally, одновременно добавляются internal и coverage без повторного роста known total. Оба typed inputs сохраняются в TaxSnapshot; неизвестная история/включение оставляет review и резерв.
**Последствия:** нет обещания автоматической отчётности ФНС или полного расчёта всех налогов/взносов. Это не отменяет обязательный progressive/YTD engine в принятой области.

## ADR-007 — Изоляция, provenance и восстановление

**Контекст:** данные нескольких ролей/программ и финансовые receipts переживают рестарты.
**Решение:** tenant/program принадлежность проверяется по server session и composite FK во всех финансовых связях; partner видит лишь своё. RLS с role-specific regression — defense in depth. Append-only ledger/audit/frozen artifacts; исправления новыми записями. Секреты и реквизиты шифруются/маскируются, не попадают в CSV сверх минимально нужного и в логи.
**Restore:** после restore RecoveryGate shared-lock/check закрывает payment/refund/rounding/freeze/ordinary prepare/confirm commits и outbound replay до сверки; observation-only и narrowly authorized evidence reconciliation доступны под закрытым gate для фиксации реальных фактов. До разблокировки сверяются watermark, N1 outbox и отдельно сохранённые подтверждения/receipts. Сверяются внешние ручные переводы, которые могли произойти после backup. Старый snapshot не разрешает повторный перевод; неизвестность остаётся блокировкой.
**Последствия:** restore drill, concurrency, mutation и negative tenant tests — обязательные ворота реализации; документ не заменяет их выполнение.

## ADR-008 — Честные метрики, growth и dogfooding

**Контекст:** выбран incentivized путь A; у N1 ручные renewals и неизвестный MRR.
**Решение:** projections строятся из того же ledger; MRR N1 = unknown. Первая реальная комиссия исключает test payments. Sharing только добровольная подготовка текста/копирование, без отправки. Free badge проверяется сервером на публичной странице программы; платная entitlement не возникает от query/localStorage. Собственная программа платформы и программа N1 — разные program contexts; платные продажи N3a не подменяются оплатами N1.
**Последствия:** предлагаемая staged граница для review владельцем (не завершённый денежный dogfooding): собственная программа платформы даёт добровольное вступление, ссылку/код и отдельный учёт N3a leads (purpose=platform_leads). Её денежные начисления ждут собственной подтверждённой billing source и цены; N1 оплаты их не заменяют. Второй connector не считается частью N1-only пилота. Нет неявного переноса scope старого N3.
