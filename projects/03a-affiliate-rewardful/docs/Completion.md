# Completion — N3a, план приёмки и эксплуатации

Статус: план, приложение не реализовано и не развёрнуто. Выбор CJM A разрешает подготовку требований; конкретный XL-план должен быть одобрен перед кодом. Production rollout требует отдельного применимого разрешения.

## Deployment Plan

### Pre-Deployment

- Все согласованные AC связаны с реально исполняемыми тестами, обязательные регрессии N1/N3a зелёные.
- Завершены независимые денежное и security review, нет blocker/high.
- Сверены donor hashes и concurrent изменения N1; согласован один источник комиссий после cutover.
- Секреты новые, вне git; compose namespace/volumes/networks отдельные; DB не публикует host port.
- Проверены миграция и восстановление из резервной копии, подписанный outbox replay не начисляет повторно.
- Утверждены условия программы, плательщик, налоговый контур, начальные YTD и баланс обязательств.
- Документы актуальны; владелец дал применимое разрешение на релиз.

### Deployment Sequence

1. Integration owner фиксирует commit/SHA, прогоняет `bash scripts/check-port-conflicts.sh 03a-affiliate-rewardful`, проверяет env без вывода секретов, создаёт изолированный тестовый стенд и применяет новые миграции. Конкретные compose/CI-команды будут созданы и проверены в foundation, сейчас они не существуют.
2. Выполняет E2E на раздельных origin N1/N3a в тестовом режиме ЮKassa: атрибуция, первая и повторная оплата, возврат, повтор/перестановка, сбой доставки, реестр и ручная отметка. До cutover комиссии N3a только тестовые/сверочные, без второго реального долга.
3. После разрешения на релиз включает N1 bridge для единственной пилотной программы по согласованной границе, сверяет события и задолженности. Первая реальная комиссия считается метрикой пилота только по реальному подтверждённому платежу.

### Rollback Procedure

Остановить новые регистрации/изменения программы и потребление новых событий, сохранить durable outbox и финансовую историю, вернуть совместимую версию приложения. Не удалять ledger, receipts и миграции с данными. Не включать прежний N1 commission writer автоматически: сначала сверить границу владения и непогашенный outbox. При повреждении данных восстановить копию в отдельный namespace, сверить платежи/переводы с внешними источниками и только затем переключать сервис. Восстановление N3a не должно повторно запускать банковские переводы.

## CI/CD

План стадий `test → build → deploy`. В foundation определить реальные команды `npm test`, `npm run lint`, `npm run build` и release-entrypoint `deploy.sh` либо документированную замену. Наличие этих строк не является доказательством доступности команд. Deploy закрыт до одобрения релиза; документационные коммиты проверяются доступными корневыми стражами и `git diff --check`.

## Monitoring

| Метрика | Предлагаемый порог | Источник | Реакция первого этапа |
|---|---|---|---|
| Возраст старейшего недоставленного события | >15 минут | наша БД | Видимое предупреждение оператору, ручной разбор без потери очереди |
| Несверенные оплаты/возвраты перед реестром | >0 | наша БД | Реестр помечен неполным, сумма к переводу не подтверждается |
| Просроченные неперечисленные строки | После5-го, >0 | наша БД | Список для владельца; автоматических переводов нет |
| Дубликаты business posting | >0 невозможны при constraint | наш журнал | Инцидент инварианта, остановить финансовый write-path |
| Response time p99 | >500ms, проектная цель | наш журнал | Ручной разбор оператором |
| Error rate | >1% за5мин, проектная цель | наш журнал | Ручной разбор оператором |
| CPU usage | >80% за5мин, проектная цель | ручное измерение: метрики контейнера | Ручной разбор оператором |

Стандартные назначения шаблона SPARC (`Response time p99 >500ms → PagerDuty`, `Error rate >1% → Slack`, `CPU usage >80% → Email`) здесь **не подключены**. На первом этапе их заменяет локальная наблюдаемость и оператор; внешние рассылки/новые сервисы не входят в авторизацию. Пороги — предложения, не обещанный SLA и не результаты измерений.

## Logging

Уровни info/warn/error с correlation/event id и кодом результата. Не писать тела с реквизитами, секреты и платёжные credentials. Предлагаем хранить операционные логи14дней с ограниченным доступом; срок финансовых документов определяется бухгалтерским контуром, автоматическое удаление до его фиксации не включать. Финансовый audit append-only; операционные логи не заменяют ledger. Агрегация сначала локальная, внешнего log-vendor нет.

## Handoff

| Получатель | Владелец шага | Что передаётся / когда |
|---|---|---|
| Development | Integration owner | Подтверждённый XL-план, role map, donor hashes, env guide и file ownership до IMPLEMENT |
| QA | Независимый QE | Версия исходников, сценарии, test fixtures и способ сообщения о дефектах до REVIEW |

| Бухгалтер/оператор | Владелец программы | Реестр, YTD, версия налоговых правил, основания удержаний до первой выплаты |

## Состояние готовности

HTML CJM A выбран; прежние110 браузерных проверок относятся только к прототипу. Runtime build, DB integration, нагрузка, security regression, миграции, rollback и реальная ЮKassa/N1 E2E ещё не выполнены. Это запланированные критерии завершения реализации, не отчёт о готовом продукте.
