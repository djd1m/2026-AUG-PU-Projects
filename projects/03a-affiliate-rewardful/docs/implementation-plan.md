# N3a — план для согласования

Дата: 2026-09-09. Статус: владелец выбрал CJM A без уточнений. PRD, спецификация, алгоритмы и архитектурный пакет подготовлены; независимая валидация выполняется. Обязательные условия подтверждены: N1, ЮKassa, ручные выплаты 5-го числа за предыдущий месяц. Следующая остановка — конкретный XL-план перед реализацией денежных функций.

## Основание и границы

- Исходная постановка: `../../../start/REPLICATE-PROMPTS-PROJECTS.md`, раздел 03, плюс универсальный блок `../../../start/REPLICATE-PROMPTS.md`.
- Поправки владельца: ЮKassa вместо Stripe; сначала повторное использование подходящего кода N1/N2, затем реализация недостающего.
- PROJECT_ROOT: `projects/03a-affiliate-rewardful`. Документы, код, тесты и телеметрия только внутри этого проекта. Общий toolkit — корневая `.claude/`, без второго оркестратора.
- Это самостоятельный запуск первоначального MVP. Четыре приложения A–D, MCP/A2A-продукт и разрешения старого N3 автоматически не наследуются. Внутренние API для UI и входящие вебхуки необходимы; публичный developer API вне MVP.
- На этапе планирования N1/N2 используются как read-only источники. После одобрения реализации N1 также является первой интеграцией: необходимые изменения на его стороне размещаются в N1 по его локальным правилам, с отдельным владением файлами и регрессией; основной код N3a остаётся в N3a. N2 остаётся донором кода. Переносимые модули и нужные тесты фиксируются локально с исходным путём, ревизией/хешем и перечнем адаптаций. Runtime-импорты из соседних проектов не планируются.
- Архитектурная рамка: распределённый монолит, Docker Compose, PostgreSQL в контейнере, VPS. Предлагаемый стек: TypeScript/Node 22, pg; UI-фреймворк закрепить после CJM и аудита совместимости N1/N2.
- У нового проекта собственные compose namespace, тома, сети и секреты. БД без host ports. Порты проверяются до compose/up; секреты существующих проектов не переносятся.

## Результат MVP

Регистрация владельца и партнёра; настройка программы; ссылка и промокод; клик → регистрация → подтверждённая оплата; повторные комиссии; кабинеты владельца и партнёра с кликами, регистрациями, платящими клиентами, MRR и суммой к выплате; месячный реестр ручных выплат 5-го числа за предыдущий месяц.

Вне MVP: массовые банковские выплаты, мультивалютность, индивидуальные тарифные сетки партнёров, публичный API, агентный интерфейс. Перечисление денег физлицам не запускается автоматически.

Основной growth loop: собственная партнёрская программа сервиса (dogfooding). Вторичная тактика: брендированная публичная страница программы. FR-GROWTH-001..004 переводятся в проверяемые требования, по три сценария happy/edge/security на каждый. Share в момент первой подтверждённой комиссии, без отправки от имени человека без отдельного согласия. Badge обязателен на free, снятие — серверное правило платного тарифа.

Метрика недели: число программ с первой засчитанной комиссией. Первый этап ограничен одной интеграцией — N1. Предлагаемый критерий пилота: программа N1 с первой подтверждённой комиссией по реальной оплате. Прежнее предложение подключить 5 программ за неделю отложено до расширения интеграций. Тестовые платежи в бизнес-метрику не входят. Приёмка кода и достижение рыночной метрики учитываются отдельно. Измеряются приглашения и конверсии раздельно; проценты при n < 30 не используются как доказательство роста.

## Первая интеграция — N1 (Proofwall)

- Решение владельца: на первом этапе подключаем `projects/01-testimonials-senja`. N1 — действующий продукт, чьи продажи учитывает N3a; N2 на этом этапе только источник готового кода.
- Сквозной сценарий: партнёрская ссылка или промокод → клиент N1 → регистрация в N1 → подтверждённая оплата N1 через ЮKassa → комиссия в N3a → таблица за месяц → самостоятельный перевод владельцем 5-го числа.
- До реализации зафиксировать контракт N1↔N3a: идентификаторы программы, партнёра, клиента, заказа/платежа и периода подписки; передача атрибуции, оплат, продлений и возвратов; аутентификация, повторная доставка и восстановление после недоступности N3a. Конкретный транспорт выбирается при архитектурном проектировании.
- Биллинг N1 продолжает обслуживать N1. Для подключённой программы целевой источник истины о партнёрских начислениях и реестрах — N3a. Существующий механизм комиссий N1 учесть в плане перехода: один платёж не создаёт две независимые задолженности партнёру. Исторические начисления не импортируются и не изменяются молча.
- Интеграция через согласованный контракт, без прямого доступа к таблицам соседнего проекта и без runtime-импортов его исходников. Отказ N3a не должен срывать оплату/активацию N1; нужны надёжная доставка и последующая сверка.
- На первом этапе не строить универсальные коннекторы ко всем SaaS. Минимальный серверный контракт для N1 входит в MVP, публичный developer API остаётся вне scope.
- Первый исследовательский этап включает аудит реального пути регистрации, checkout, вебхуков, продлений и текущей атрибуции N1. Архитектор Astra high отвечает за границы интеграции; reviewer независимо проверяет отсутствие двойных начислений.
- Приёмка охватывает оба проекта: переход между реальными origin, регистрацию/оплату N1 и отражение в N3a, продление, возврат, повтор события, восстановление после сбоя связи и месячный реестр. Обязательна регрессия затронутых функций N1.

## ЮKassa: проектируем контракт, а не переименовываем Stripe

- Оплата и возврат: `payment.succeeded`, `payment.canceled`, `refund.succeeded`; окончательный перечень закрепляется по текущей документации провайдера.
- До начисления: проверка объекта через API ЮKassa, соответствия магазина, внутреннего заказа, суммы, валюты и финального состояния. Данные запроса не устанавливают tenant authority.
- Дедупликация: предлагаемый ключ `(merchant_connection_id, event_type, object_id)`, атомарный unique constraint и отдельная уникальность комиссии на платёж. Возвраты имеют собственные object_id.
- Повторы, конкурентная доставка и произвольный порядок событий — обязательные сценарии, включая возврат раньше локальной обработки оплаты и частичные возвраты.
- Подлинность уведомлений проверяется механизмом ЮKassa. Не придумывать Stripe-подобную подпись. Конфликт общего signature-oriented guard с протоколом провайдера оформить явно и проверить эквивалентные гарантии; не изображать прохождение неподходящей проверки.
- Разделить биллинг самой платформы и платежи клиентов подключённого бизнеса: комиссии относятся ко второму. На архитектурном этапе зафиксировать подключение магазина и способ надёжной связи customer/subscription/payment.
- Рекуррентная комиссия не требует превращать платформу в биллинг-движок. Базовый план: учитывать повторные подтверждённые платежи подписки бизнеса; расписание списаний остаётся у бизнеса. Сохранённый платёжный метод сам по себе не доказывает наличие подписки и периода MRR.
- Для MRR необходимы явные сумма и период подписки, её состояние и идентичность клиента; не выводить MRR из произвольной разовой оплаты. При нехватке данных показывать неизвестность.
- Предлагаемые правила для фиксации в спецификации: промокод приоритетнее cookie; срок cookie 30 дней с настройкой 60/90; ежемесячный расчёт и ручная выплата 5-го числа за предыдущий месяц; денежные суммы в минимальных единицах или decimal с определённым округлением.
- Налоговые утверждения исходной постановки требуют актуальной проверки до реализации расчётов: статус получателя, YTD в доступном системе объёме, обязанности налогового агента и смена режима. Не считать выплаты одной платформы известным совокупным доходом человека.

## Расчёты с партнёрами — решение владельца от 2026-09-09

- На первом этапе каждого 5-го числа владелец самостоятельно перечисляет партнёрам вознаграждения за предыдущий календарный месяц по сформированной системой таблице начислений. Например, начисления за сентябрь выплачиваются 5 октября.
- Система рассчитывает суммы и формирует реестр; банковские переводы выполняет человек вне системы. Создание или экспорт таблицы не означает, что деньги перечислены.
- Предлагаемые поля реестра: партнёр, расчётный месяц, начислено, возвраты/корректировки, применимые удержания с основанием, итог к перечислению, статус и дата фактической выплаты. После перевода владелец вручную отмечает выплату; история изменений сохраняется.
- Повторное формирование реестра не создаёт повторную задолженность и не сбрасывает отметки уже выполненных выплат. Поздние возвраты оформляются отдельными корректировками с привязкой к исходному начислению; оплаченный реестр не переписывается незаметно.
- Этот календарный график имеет приоритет над прежним предложением обязательного hold 30–45 дней для каждого начисления: такой hold задержал бы часть выплат за прошлый месяц и не включается в первый этап. Это не отменяет учёт возвратов и применимых удержаний.
- В спецификации зафиксировать часовой пояс и границы месяца; дата выплаты — именно 5-е число, без автоматического переноса на рабочий день без отдельного решения владельца.
- Приёмка: в реестр на 5 октября попадают подтверждённые начисления сентября с корректировками; начисления октября не попадают; экспорт не помечает строки оплаченными; ручное подтверждение сохраняет дату и не допускает повторного учёта выплаты.

## Порядок и параллелизм

1. После одобрения: аудит N1/N2 и уточнение discovery параллельно. Координатор фиксирует границы, источники и телеметрию. Использует имеющиеся исследования старого N3 как источники с проверкой актуальности, не как автоматически принятый scope.
2. Затем профиль оригинала и CJM; минимум три различающихся growth loop. Основной рекомендованный вариант сохраняет incentivized referral. Решение владельца о CJM фиксируется, альтернативы сохраняются.
3. После выбора — единый план архитектуры и денежных правил. Требования → алгоритмы → схема/контракты согласуются последовательно; не раздавать противоречивые версии разработчикам.
4. Детерминированная полнота → шесть валидаторов волнами по два → агрегация → исправления → повторная валидация. Для серьёзного плана отдельный challenge.
5. После принятия плана: foundation/auth/tenant → атрибуция N1↔N3a → подтверждённые платежи N1 и первая комиссия → повторные платежи/возвраты/месячный реестр → кабинеты/рост/реестр → итоговая приёмка.
6. UI и независимые модули можно разрабатывать параллельно с ядром только после фиксации API. Fixtures допустимы для разработки UI, но не считаются итоговой интеграцией.
7. Денежное/безопасностное ревью и браузерные проверки могут идти параллельно на одной зафиксированной версии. Интеграция, миграции общего стенда, сборка итогового кандидата и финальный вердикт последовательны.

Топология: координатор + не более двух активных дочерних агентов по умолчанию. Рой нужен для независимой валидации, не для неконтролируемой одновременной разработки всего проекта. У каждого пишущего агента отдельный worktree, список принадлежащих ему файлов, версия входов и уникальный receipt внутри N3a. Интеграция общих файлов у одного владельца. У ревьюеров нет права менять исходники; их отчёты принадлежат им отдельно.

## Проверки и критерии завершения

- Прослеживаемость каждого FR/AC к сценарию и тесту; обязательные packaged gates реально разрешаются и запускаются. Недоступная проверка не считается зелёной.
- Build, typecheck, unit, PostgreSQL integration, независимое ревью.
- Деньги: конкурентные дубли, перестановки, частичные/полные возвраты, повторные платежи, округление, смена ставки, границы расчётного месяца и даты выплаты, сбой между API и commit, повтор после рестарта.
- Безопасность: поддельные уведомления, неверные магазин/сумма/валюта, межарендный доступ, self-referral, накрутка и дубликаты; mutation checks подтверждают, что защиты способны провалить тест.
- Браузер: владелец запускает программу, партнёр получает ссылку/код, клиент регистрируется и платит, оба кабинета показывают согласованное начисление, возврат корректирует его. Cookies проверяются на реальном отдельном origin.
- Цель UX: настройка программы за ≤15 минут при готовом тестовом магазине/доступах. Время регистрации/активации магазина провайдером учитывается отдельно.
- Внешняя приёмка ЮKassa проводится в тестовом магазине с настоящим API и уведомлением. Отсутствие доступа блокирует только соответствующую внешнюю приёмку, а не выдаётся за успешно проверенную production-интеграцию.
- Бизнес-цель по реальным программам требует пользователей и наблюдения; синтетические результаты в неё не включаются.

## Согласования и измерения

Владелец отдельно разрешил commit и push материалов N3a в GitHub и потребовал частые коммиты/пуши: фиксировать небольшие логически завершённые проверенные изменения и отправлять их после завершения этапов. Это разрешение не снимает остановку перед PRD до выбора CJM и не разрешает production deployment или финансовые операции.

Владелец одобрил запуск этого плана командой «отлично, запускай». После начала сохраняется продуктовый выбор CJM; XL-план с конкретными денежными/правовыми решениями предъявляется перед кодом, если его решения не покрыты данным одобрением. Обычные обратимые действия внутри принятого плана повторных разрешений не требуют. Публикация и реальные финансовые операции не подразумеваются одобрением разработки.

Для каждой фичи журнал `docs/telemetry/p-replicator/<RUN_ID>/`: выбранная/фактическая модель, effort, fallback, попытки, проверки, elapsed и доступный usage. Нет данных — null с причиной. Экономия без сопоставимого baseline не заявляется. Начальная запись подготовки содержит честный пробел: предварительное чтение до создания журнала не было хронометрировано.

Точную длительность и стоимость реализации до CJM, аудита совместимости и внешних доступов не обещаем. Недельный MVP — ограничение scope, а не доказанный срок поставки.

## Конкретные решения XL-плана после выбора A

Это предложения к реализации; N1, ЮKassa, A и график выплат уже одобрены. Числовая ставка заполняется владельцем при активации, дополнительного согласования каждого поля на стадии проектирования не требуется.

| Решение | Предлагаемое поведение | Документ |
|---|---|---|
| D1 — граница N1 | N1 проверяет ЮKassa и пишет outbox вместе с биллингом; N3a принимает подписанные факты без копирования credentials | ADR-002/003 |
| D2 — комиссии | Процентная ставка явно задана, фиксируется при атрибуции; повторная подходящая ручная оплата даёт новую комиссию по условиям. Для пилота — все подходящие оплаты без конечного срока, без необязательных режимов first-only/finite | ADR-004 |
| D3 — календарь | Europe/Moscow; прошлый календарный месяц, срок5-го без переноса с выходного и без30–45-дневного hold | ADR-005 |
| D4 — реестр и исправления | Без минимального порога; отрицательный остаток переносится один раз. Freeze неизменен, поздние записи — отдельные корректировки; CSV не меняет статус | ADR-005 |
| D5 — налоги | Версии правил, проверенные начальные YTD и фактический год выплаты; unknown блокирует подготовку, уже случившийся перевод сохраняется как факт для сверки | ADR-006 |
| D6 — переход | Исторические обязательства остаются N1; manifest определяет границу новых, никакого двойного commission writer | ADR-002/007 |
| D7 — собственная партнёрка | На первом пилоте предлагаются вступление, ссылка/код и учёт лидов N3a. Денежная dogfooding-комиссия отложена до собственной цены и billing source; продажиN1 ей не подменяются | ADR-008 |

**D7 — явное ограничение первоначального incentivized dogfooding**, предлагаемое к рассмотрению владельцем. Оно не считается уже одобренным выбором A. Альтернатива — включить собственный биллинг N3a в начальный scope и отдельно специфицировать его цену/оплаты до кода.

## Очередность реализации после принятия конкретного плана

| Шаг | Результат | Исполнители/навыки | Что можно параллелить |
|---|---|---|---|
| 1 | Повторный audit текущих N1/N2, версии доноров, foundation/session/tenant | Terra medium сбор; Sol high адаптация; корневой feature/toolkit | Независимые donor audit и подготовка тестовых данных |
| 2 | Зафиксированный N1 bridge/cutover и сквозная атрибуция | Astra high, архитектурный контракт и security-operation-order | UI по утверждённому API; измененияN1 у отдельного integration owner |
| 3 | Первая/повторная комиссия, refund и идемпотентность | Astra high; monetary QE/мутации/конкурентный PostgreSQL | Только независимые read projections и UI; общий ledger у одного владельца |
| 4 | Месячный freeze/carry, налоги, ручная отметка | Astra high; tax evidence и approved rules, shared-resource checks | Кабинеты и export по стабильному контракту |
| 5 | Growth A, badge, реальнаяN1 E2E, regression/review | Sol high UI; Astra high QE; frontend-design/requirements-validator | Независимые browser и money/security review одной версии |
| 6 | Интеграция, полная сборка/регрессия и отчёт | Координатор; независимый финальный reviewer | Последовательно: один итоговый кандидат |

Не запускать кодовые шаги по черновому контракту. Стек/lockfiles выбираются по текущим донорам после re-audit; общую vendor `.claude/` не редактировать. До каждого runtime шага выполняются реальные обязательные проверки, перечисленные в Completion/Refinement. Механическая проверка документов не заменяет их.
