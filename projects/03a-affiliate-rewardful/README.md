# N3a — реферальная платформа для самостоятельного подключения магазинов

**Статус на 10 сентября 2026 года: работа приостановлена по просьбе владельца.**
Сохранены реализация первых двух этапов, исследование интеграций и план расширения.
Продолжать разработку, исследование или запуск агентов только после нового указания.
Обновление этого README не возобновляет работу.

## Цель и принятые решения

N3a должна позволять владельцу магазина подключить реферальную программу без
разработчика за несколько минут: установить готовую интеграцию, настроить условия,
проверить передачу событий и пригласить партнёров. Это цель продукта, а не уже
доступная возможность. Поддержка будет подтверждаться для конкретных сочетаний
платформы, версии, checkout и платёжного модуля.

- Выбран CJM A — «Через вознаграждение».
- N1 Proofwall остаётся первой проверочной интеграцией; продукт больше не ограничен одним N1.
- Для N1 используем ЮKassa. Её секреты и каноническая проверка платежей остаются в N1;
  N3a должна получать подписанные события через согласованный контракт.
- Выплаты партнёрам — **вручную 5-го числа за предыдущий календарный месяц**.
  CSV не переводит деньги; отметка отправки не доказывает зачисление получателю.
- Комиссия возникает только по подходящей подтверждённой оплате, не по регистрации.
  Повторная оплата может дать повторную комиссию; автоматические списания не обещаются.
- Код N1/N2/N3 можно использовать после проверки совместимости и фиксации происхождения.
  Runtime-импорты, базы и секреты соседних проектов не объединяются.
- **Проект `03-affiliate-rewardful` развивается в другой сессии.** Он только источник
  для чтения: не менять его файлы, настройки, процессы, контейнеры, сети или порты.

## Что ещё не реализовано

- Общая модель подключения магазинов и готовые устанавливаемые plugin/app.
- Самостоятельная регистрация владельца магазина с подтверждением администрирования,
  восстановлением аккаунта и безопасным повторным подключением.
- N1 attribution bridge: tracking, подписанные события, надёжная доставка, сверка и
  переход без двойного начисления в N1/N3a.
- Денежный ledger, обработка возвратов и восстановление финансового состояния.
- Месячный реестр, налоговая проверка и запись факта ручного перевода.
- Полные финансовые кабинеты, growth/share/badge и собственная партнёрка платформы D7.

## Выводы исследования

Rewardful поддерживает конкретные интеграции и ориентирован прежде всего на SaaS
со Stripe/Paddle. Его прямая интеграция с платёжным провайдером ближе к механике N3.
Для собственного checkout может потребоваться код; обещание «любой магазин без
разработчика» шире возможностей, подтверждённых документацией оригинала.

В N3 найдены referrals, привязка покупателя, внешний заказ/события, HTTP-клиент и
сквозные тесты Proofwall; в N1 — очередь доставки с lease/retry/ACK. Это донорские
кандидаты, а не готовый совместимый bridge для N3a. Перед переносом нужно повторно
проверить конкретные файлы и сохранить их commit/SHA: соседние проекты меняются.
Подробные ссылки на код и официальные источники — в [исследовании](docs/discovery/2026-09-10-rewardful-integration-research.md).

## Открытые решения

1. **Первая внешняя платформа и целевая аудитория.** Обсуждались InSales/Tilda,
   WooCommerce и 1С-Битрикс; выбора пока нет. Уровень предварительного исследования
   различается; ни одна комбинация не объявлена поддерживаемой.
2. **Платёжный модуль и версии.** Нужны доказанные оплаты, полные/частичные возвраты
   и восстановление пропусков. Установка plugin или статус `paid` не доказывают оплату.
3. **Покупки без регистрации и база комиссии.** Нужно определить надёжную идентичность
   повторного покупателя, скидки, доставку, налоги и частичные возвраты товарных заказов.
4. **Merchant ownership и восстановление.** Подтверждённый email не равен владению
   магазином; необходимы отдельный install/authorization контракт и канал восстановления.
5. **D7 — собственная партнёрка N3a.** Lead-only пилот либо денежная программа с
   собственной ценой и billing source; продажи N1 их не заменяют.
6. **Реальные выплаты и выпуск.** Перед ними нужны юридический плательщик,
   применимые договорные/налоговые основания, подтверждённые исходные данные и
   отдельное разрешение на соответствующие реальные операции.

Цель подключения ≤10 минут для минимум 4 из 5 владельцев предложена в плане,
но ещё не измерена. Время регистрации, получения доступов и ожидания платформы
нужно показывать отдельно; нельзя выдавать тестовую комиссию за первую реальную.

## Следующие шаги после возобновления

1. Подтвердить стартовый сегмент, платформу и проверяемую платёжную комбинацию.
2. Начать `merchant-connector-foundation`: подготовить и независимо проверить
   подробные требования, алгоритмы, архитектуру и критерии connection/ownership,
   capabilities, guest checkout и базы комиссии. Актуализировать общие технические
   документы под PRD0.3; прежнее ревью N1-only scope не подтверждает расширение.
3. После фиксации контракта реализовать `n1-attribution-bridge` как первый адаптер:
   использовать подходящие донорские блоки, проверить подписи, повторы, сверку,
   историческую атрибуцию и отсутствие второго долга. Изменения N1 вести отдельно
   с учётом его активных работ и регрессией.
4. Реализовать самостоятельное подключение: account recovery/verification,
   подтверждение магазина, каталог, мастер установки и первый готовый plugin/app.
5. Реализовать денежную цепочку по зависимостям:
   `payment-commission-ledger → refund-reconciliation → monthly-registry-tax-gate → manual-transfer-record`.
   Подключённый магазин не становится готовым к денежным операциям раньше этих этапов.
6. Завершить финансовые кабинеты CJM A, затем growth/share/badge; D7 вести по отдельному решению.
7. Провести сквозную приёмку N1 и выбранной внешней платформы, проверки отказов,
   возвратов, изоляции, восстановления и независимое денежное/security review.
   Отдельно измерить подключение владельцем без помощи разработчика.

Плагин и денежные модули могут разрабатываться независимо после согласования
контрактов; денежные этапы сохраняют свои зависимости. Один writer на worktree;
общие миграции и манифесты интегрирует координатор. Порядок и модели подробно
описаны в [плане расширения](docs/plans/2026-09-10-self-service-expansion.md),
машинные зависимости — в [roadmap](.claude/feature-roadmap.json).
**Сейчас эти шаги не выполняются: действует пауза владельца.**

## Проверка разработки — справка на будущее

Проверенная среда: Node 22.22.0, Docker Compose, PostgreSQL 16; для браузерного
сценария дополнительно Firefox и geckodriver. Из каталога проекта:

```sh
npm ci --ignore-scripts
npm run verify
npm run test:isolated -- --mutations --image
```

Для полного браузерного сценария вместо последней команды:

```sh
npm run test:isolated -- --mutations --browser
```

Команды выполнять последовательно: smoke использует законченный build. Harness
создаёт свежие тестовые секреты и собственный namespace, проверяет порты и запускает
PostgreSQL без host port. Web имеет собственный ingress с loopback-публикацией;
БД и тестовый контейнер остаются во внутренней сети. После завершения убираются
контейнеры/сети только своего запуска; диагностический volume сохраняется.

`npm start` требует подготовленную БД и явные `DATABASE_URL`, `SESSION_SECRET`,
`IDENTITY_SECRET`, `ADMISSION_SECRET`, `APP_ORIGIN`. Пилотный пользователь автоматически
не создаётся. `/api/health` означает только живой процесс. Полная инструкция и
границы offline bootstrap — в [руководстве](DEVELOPMENT_GUIDE.md) и
[приёмке onboarding](docs/features/identity-program-partner/05_completion.md).

Эти команды приведены для будущего возобновления, а не как поручение запустить
сервисы во время паузы. Production rollout, реальные платежи и переводы не выполнены.
