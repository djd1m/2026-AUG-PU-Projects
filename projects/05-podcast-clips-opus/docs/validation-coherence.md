### Находки

#### V2-R02 · blocker · `UNIQUE (video_id, stage, attempt_no)` несовместим с нумерацией попыток рендера

**Где.** `Architecture.md` → `## Data Architecture`, строка `job_attempt`, против `Pseudocode.md` →
`## Data Structures` (`job_attempt`) и `### Algorithm: LeaseAttempt`, шаг 1.

Architecture: «`job_attempt` | PostgreSQL | `UNIQUE (video_id, stage, attempt_no)`».

Pseudocode, `LeaseAttempt` шаг 1: «прочитать `max(fence)` по всем попыткам ЭТОГО видео и
`max(attempt_no)` по этой стадии **(и клипу, если стадия `render`)**».

Рендер идёт по клипам: `clip_id: UUID?` («у стадии `render` — клип»). Запись даёт 3–8 клипов, у
каждого первая попытка получает `attempt_no = 1`. Восемь строк `(video_id, 'render', 1)` нарушают
объявленный `UNIQUE` — **первая же запись с двумя клипами не проходит вставку второй попытки
рендера.** Ограничение и алгоритм по отдельности разумны; вместе они неисполнимы.

Второй слой той же ошибки: `RetryVideo` шаг 6а (DEC-A-009) — «счётчик `attempt_no` автоматических
повторов этой стадии **обнуляется**, и потолок „не больше двух“ начинает действовать заново внутри
новой серии». Обнулённый `attempt_no` сталкивается с уже существующей строкой предыдущей серии по
тому же `UNIQUE`. **Понятия «серия» нет ни одним полем** — ни в `Pseudocode.md` § Data Structures,
ни в `Architecture.md`. Решение DEC-A-009 записано в прозе и не представлено в данных.

**Предложение.** Либо `UNIQUE (video_id, stage, clip_id, series_no, attempt_no)` с явной колонкой
`series_no: int NOT NULL DEFAULT 1` (и `clip_id` в ключе через `COALESCE`/частичный индекс, потому
что `NULL` в `UNIQUE` не дедуплицирует), либо отказаться от `attempt_no` как от части уникальности
и оставить уникальным только `fence`, который уже монотонен на видео. Выбор — за arch-writer, но
поле «серии» обязано появиться в обоих документах, а не остаться абзацем.

**Владелец.** `Architecture.md` → arch-writer; `Pseudocode.md` → algo-writer; согласование —
координатор (это правка после DEC-A-009).

#### V2-R03 · blocker · колонка `quota_counter.limit` снята решением, но оператор списания её читает

**Где.** `Architecture.md` → `## Reconciliation with Pseudocode`, строка `quota_counter.limit`,
против `Pseudocode.md` → `### Algorithm: CheckAndConsumeQuota`, шаг 3.

Architecture: «`quota_counter.limit` | отсутствующая колонка | **НЕ добавлена как хранимое
значение**: предел приходит из окружения при старте … в строке счётчика хранится только `used`.
Pseudocode читает `limit` как параметр алгоритма, не как колонку — **семантика сохранена**».

Pseudocode шаг 3: «`INSERT INTO quota_counter (scope, scope_key, day, used, **limit**) VALUES (…,
:n, :limit) ON CONFLICT (scope, scope_key, day) DO UPDATE SET used = quota_counter.used + :n WHERE
**quota_counter.used + :n <= quota_counter.limit** RETURNING used»`.

Оператор вставляет колонку `limit` и сравнивает с `quota_counter.limit` — то есть читает её именно
как колонку. Утверждение «семантика сохранена» ложно: без колонки оператор не компилируется. Это
худший вид расхождения — строка сверки, объявляющая расхождение закрытым.

**Предложение.** Выбрать одно и записать в обоих документах: либо колонка остаётся (тогда правится
строка Reconciliation и появляется вопрос, что делать со строками, созданными при старом пределе),
либо предел подставляется параметром `:limit` в обеих ветках оператора (тогда правится SQL в
Pseudocode). Второе предпочтительнее: предел из окружения, валящий запуск при отсутствии
(FR-LIMIT-002), и хранимая копия того же числа в каждой строке суток — два источника истины.
Попутно: `limit` — зарезервированное слово SQL, потребует кавычек либо переименования (см. V2-L2).

**Владелец.** `Architecture.md` → arch-writer; `Pseudocode.md` → algo-writer.

### Находки

#### V2-R01 · blocker · ветка `INSERT` атомарного оператора квоты не проверяет потолок

**Где.** `Pseudocode.md` → `### Algorithm: CheckAndConsumeQuota`, шаг 3.

```sql
INSERT INTO quota_counter (scope, scope_key, day, used, limit) VALUES (…, :n, :limit)
ON CONFLICT (scope, scope_key, day) DO UPDATE SET used = quota_counter.used + :n
  WHERE quota_counter.used + :n <= quota_counter.limit
RETURNING used
```

Условие `WHERE` принадлежит ветке `DO UPDATE` и **не действует на вставку**. Первый за календарные
сутки запрос по данному ключу строки не находит, вставляет `used = :n` без единой проверки и
возвращает непустой результат — то есть `granted`.

Это не теоретический случай, а основной:

- Канон §7 допускает запись **2–90 мин**, а `user_minutes` — **60 в сутки**. Первая за сутки
  загрузка 90-минутного выпуска даёт `n = 90` при пределе 60 → `INSERT … used = 90` → **`granted`**.
  Вызов Whisper на 90 минут оплачен, потолок не сработал.
- То же для `global_minutes` и `global_llm` в первый запрос суток.

Специфицированное поведение прямо противоположное. Specification FR-LIMIT-001: «ОДНИМ атомарным
оператором с условием `used + :minutes <= :limit`; **пустой результат оператора И ЕСТЬ отказ**».
Сам же Pseudocode в шаге 4: «IF ЛЮБОЙ оператор вернул пустой результат THEN … `refused`». Оператор,
который на переполнении возвращает строку, отказа не даёт никогда.

Классификация по правилам проекта: `fail-closed-defaults.md` — отсутствие строки (нет данных)
трактуется как «ограничений нет»; `model-call-cost.md` Правило №0 — потолок, который не связывает,
не потолок. Отказ необратим по деньгам: счёт поставщика уже выставлен.

**Предложение.**

```sql
INSERT INTO quota_counter (scope, scope_key, day, used) SELECT …, :n
  WHERE :n <= :limit                                   -- ветка вставки тоже под условием
ON CONFLICT (scope, scope_key, day) DO UPDATE SET used = quota_counter.used + :n
  WHERE quota_counter.used + :n <= :limit
RETURNING used
```

и отдельный **тест на границу суток**: первый запрос суток с `n > limit` обязан дать `refused`.
Этого теста нет ни в `Refinement.md` («Обязательные конкурентные прогоны», п. 1 проверяет только
границу при уже существующей строке), ни в списке Test Cases. Конкурентный прогон здесь не
помогает: дефект виден и последовательным, но только если первым запросом суток идёт превышение.

**Владелец.** `Pseudocode.md` → algo-writer; тест в `Refinement.md` → ops-writer.

Новая строка расхода — это `RecordModelSpend`, то есть **журнал**. `CheckAndConsumeQuota` при этом

Specification FR-TRANSCRIBE-002 обещает другое: «Повтор ОДНОЙ части после таймаута **списывает
минуты этой части повторно** — это и есть счёт по попыткам». `CheckAndConsumeQuota` шаг 7 обещает
то же: «Счёт ведётся по ПОПЫТКАМ: повтор после таймаута списывает снова».

В итоге потолок ограничивает **заявленные** минуты, а поставщик берёт за **фактические**. Часовая
запись из пяти чанков, где каждый ретраится дважды, стоит как три часа, а счётчик показывает один.
Потолок 600 мин/сутки перестаёт быть потолком расхода — а он объявлен именно им
(`model-cost-contract.md`: «Счёт ведётся по: попыткам»).

**Предложение.** В `Transcribe` шаг 4 перед каждым повтором вызывать
`CheckAndConsumeQuota(reason = minutes, n = минуты ЭТОЙ части)`; отказ по потолку на повторе — это
`failed(refused_*)`, а не тихое продолжение. Либо, если решено считать потолок «по заявленному»,
исправить формулировки в FR-TRANSCRIBE-002, `CheckAndConsumeQuota` шаг 7 и
`model-cost-contract.md` — но тогда расход перестаёт быть ограниченным, и это надо написать.

**Владелец.** `Pseudocode.md` → algo-writer; `Specification.md` → spec-writer;
`model-cost-contract.md` → координатор.

#### V2-R15 · high · `deferred(no_disk)` неотличим от молчания для сторожа и будет убит как `stalled`

**Где.** `Pseudocode.md` → `RenderClip` шаг 2 против `WatchdogTick` шаг 2 и `Pseudocode.md` →
`## Error Handling Strategy`, строка «Нет места на диске».

`RenderClip` шаг 2: «IF меньше THEN `job_attempt.status = deferred` … задание возвращается в
очередь с задержкой». `updated_at` при этом **не двигается** — шаг его не трогает.

Error Handling: «`deferred(no_disk)` … **состояние остаётся `выполняется`: ожидание очереди — это
работа, а не поломка**».

`WatchdogTick` шаг 2: «Видео в активном статусе с `updated_at` старше **30 мин** — `failed(stalled)`,
его незавершённые клипы — `failed`».

Отложенное по диску задание молчит ровно так же, как мёртвый воркер. Через 30 минут ожидания
свободного места сторож объявит отказ — при полностью исправной системе, которая делает ровно то,
что ADR-006 предписывает: «задание **откладывается**, а не падает». ADR-006 называет это
преимуществом; сторож это преимущество отменяет.

Вероятность не умозрительная: резерв — 3× размера оригинала (до 6 ГБ на файл 2 ГБ), на VPS 18 ГБ

восьми клипов одной записи занимает диск целиком на 8–15 минут.

**Предложение.** `deferred` обязан быть видимым состоянием ожидания, а не молчанием: либо шаг 2
`RenderClip` двигает `video.updated_at` с пометкой причины ожидания (`stage_progress` /
`no_response` уже есть в контракте `video.get`), либо `WatchdogTick` шаг 2 исключает видео, у
которых последняя `job_attempt` в статусе `deferred`. Первое лучше: пользователь тогда видит
«ждём свободного места», а не пустой прогресс.

**Владелец.** `Pseudocode.md` → algo-writer.

#### V2-R16 · high · `RetryVideo` повторяет запись, которая никогда не была загружена

**Владелец.** `Pseudocode.md` → algo-writer.

**Где.** `Pseudocode.md` → `ApplyPartnerCode` шаги 4–5.

#### V2-R04 · blocker · две Must-способности не имеют маршрута ни в одном из двух ЗАКРЫТЫХ списков

**Где.** `canon.md` §5 («ровно 9 публичных путей», «Процедуры tRPC: … ровно 14») ↔ `Pseudocode.md`

разморозке на Phase 2») и добавить `POST /api/auth/register` в публичные пути (10) и `guest.revoke`

`/api/auth/login` с полем действия, а отзыв — через `guest.send` с каналом `revoke`. Любой вариант

**Владелец.** `canon.md` → координатор; `Pseudocode.md` `## API Contracts` → algo-writer;

#### V2-R05 · blocker · контракт `POST /api/auth/login` описывает отменённый механизм одноразовой ссылки

**Где.** `Pseudocode.md` → `## API Contracts`, строка 7, против `Specification.md` FR-AUTH-001,

предписывает `AuthRegisterAndLogin` шаг 4) и `429`. Ветку `{ token }` удалить целиком.

#### V2-R06 · blocker · публичный домен нигде не назван переменной и не защищён от значения по умолчанию

#### V2-R22 · high · потолок минут на сутки меньше максимальной допустимой длительности записи

**Где.** `canon.md` §7 (две соседние строки) ↔ `Specification.md` FR-INGEST-002 и FR-LIMIT-001.

**Предложение.** Либо поднять `user_minutes` до 90 (тогда `global_minutes` 600 допускает ~6,7

суточного остатка» до загрузки. Третий вариант не убирает противоречие чисел, но убирает его цену.

`Specification.md` §1 делает лимит частоты ПЕРВОЙ из пяти обязательных последовательностей: «Лимит
частоты — ДО валидации тела запроса (30 запросов/мин на IP для мутирующих, 120/мин для чтения).
Иначе перебор невалидными телами бесплатен». На нём стоит защита FR-AUTH-001 («иначе перебор
адресов и паролей … не стоит атакующему ничего») и FR-PARTNER-003. Исполнитель назван однозначно:
`Architecture.md` «Прокси | `proxy` | TLS, HSTS, **лимит частоты ДО тела запроса**», канон §6,
C4 уровень 2.

Ограничение частоты **не входит в стандартную поставку Caddy** — это сторонний модуль, который
надо вкомпилировать в образ. Значит, это внешняя зависимость ровно в том смысле, который задаёт
шапка инвентаря: способность, которую продукт берёт у чужого кода и без которой названное
требование не выполняется. Строки нет, вердикта нет, и в `Completion.md` → Deployment Sequence
шаг 1 («собирает `web` и образ воркера») сборка кастомного образа `proxy` не упомянута вовсе.

Отмечу границу собственной проверки: наличие или отсутствие директивы ограничения частоты в
стандартной сборке Caddy я **не проверял выборкой страницы** — эта строка требует такой же проверки
WebFetch'ем, как четыре сделанные выше, и именно поэтому она должна стать строкой инвентаря, а не
остаться допущением в трёх документах.

**Предложение.** Три новые строки с вердиктами и цитатами: (а) Telegram Bot API — доставка
видеофайла в личный чат, с предельным размером; (б) Telegram Bot API — доставка текстового
сообщения (операционный канал Completion); (в) ограничение частоты на обратном прокси — что именно
его исполняет, стандартная поставка или модуль, и как он попадает в образ. Строка (а) может
остаться `UNCONFIRMED` — FR-RESULT-003 помечен `Should` и тогда честно выпадает из Phase 3, как уже
сделано с FR-INGEST-003. Строки (б) и (в) `UNCONFIRMED` оставаться не могут: (в) несёт защиту
Must-требования.

**Владелец.** `Architecture.md` → arch-writer; `Completion.md` Monitoring и Deployment Sequence →
ops-writer.

#### V2-R26 · medium · у строки Usage & Cost Admin API не записано условие, без которого она не работает

**Где.** `Architecture.md` → `## External Dependencies`, строка «отдаёт расход и токены по
организации за период», и `Specification.md` §8, строка «Сверка нашего журнала расхода с отчётом о
стоимости поставщика | расхождение ≤ 10 % | **внешний API: /v1/organizations/cost_report**».

Цитата в строке содержит собственное ограничение: «**The Admin API is unavailable for individual
accounts**». Вердикт `CONFIRMED` верен для способности, но метрика недели зависит от условия,
которое нигде не зафиксировано: у владельца должна быть организация и админ-ключ. Ключ при этом
отсутствует и в каноне §6 (распределение секретов), и в `Completion.md` Pre-Deployment (список
ключей), и в C4 («Ключи по контейнерам»).

Если организации нет, метрика «расхождение ≤ 10 %» не измеряется ничем, а `Specification.md` §8
отдельно и правильно настаивает, что вторая половина расхода сверяется РУКАМИ и так и называется.
Тогда обе половины ручные, и это надо сказать, а не обнаружить в конце недели.

**Предложение.** Дописать в строку инвентаря предусловие («требуется организационный аккаунт и
Admin-ключ; у индивидуального аккаунта способность недоступна»), внести имя переменной ключа в
канон §6 и в Pre-Deployment `Completion.md`, а в `Specification.md` §8 добавить запасной источник
на случай индивидуального аккаунта — ручная сверка, названная ручной.

**Владелец.** `Architecture.md` → arch-writer; `canon.md` → координатор; `Completion.md` →
ops-writer; `Specification.md` §8 → spec-writer.

## Что эти четыре линзы НЕ проверяли

Границу стоит записать рядом с находками, а не подразумевать. Три линзы из четырёх сравнивают наш
текст с нашим текстом и не могут обнаружить, что чужой сервис делает не то, что мы предположили —
это умеет только четвёртая, и она сделала ровно четыре обращения наружу, перечисленных выше.
Остальные двенадцать `CONFIRMED`-строк приняты по цитате в документе, не перепроверены на странице.

Ни один алгоритм не исполнялся, ни одна схема не применялась к базе: утверждения вида «этот `UNIQUE`
столкнётся» (V2-R02) и «эта вставка пройдёт мимо потолка» (V2-R01) выведены чтением SQL, и первым
делом реализации их надо подтвердить тестом, который сначала показывает красное. Уложится ли часовая
запись в 20 минут, читается ли метка на телефоне, находит ли модель три самодостаточных фрагмента в
настоящем выпуске — вопросы живого прогона, и они остаются открытыми независимо от вердикта Phase 2.
