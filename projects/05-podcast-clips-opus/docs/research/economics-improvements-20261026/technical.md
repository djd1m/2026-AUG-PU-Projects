## Что уже сделано и не является новой экономией

- `apps/worker/src/llm/prompts/selection.ts`: модели уже уходят сегменты, а не words. Комментарий содержит исторический пример 88 минут: ~39k вместо ~385k токенов. 30k/час — допущение, реальный billable tokenizer другой модели надо измерить. Нельзя повторно заявлять десятикратную экономию относительно нынешнего кода.
- `src/workers/stt.ts`, `packages/db/src/transcription.ts`: авторизация каждого чанка/повтора до вызова, журнал попыток, до 3 попыток; неизвестный после crash исход не разрешает бесплатный replay. Общий STT deadline 30 минут; один вызов 120 секунд.
- `src/workers/select.ts`: принятые DB attempts уже служат outbox, сторож восстанавливает потерю Redis publish. Fence/ownership проверки, атомарные квоты и неизменяемые render-объекты уже имеются. `src/render/storage.ts`: IfNoneMatch '*' и adoption только совпадающего contract. Это защита, не гарантия exactly-once оплаты внешнего API.
- LLM `SELECT_TIMEOUT_MS = 240_000`; текущий provider жёстко вызывает OpenRouter с provider allowlist. Перестановка имени на Cloud.ru не является совместимой миграцией: нужны endpoint/auth, модель/режим, проверка JSON-schema и таймкодов. Этот анализ Cloud.ru интеграцию не проверял.

### VAD: обязательна обратная карта времени

Сейчас extract.ts применяет silencedetect лишь для выбора границ чанков: тишина НЕ вырезается, API получает всю длительность. Chunker: 180 секунд и overlap 2 секунды. Более низкий MP3 bitrate уменьшает bytes, но не оплату секунд. Избавление от всех ~40 overlap секунд даст всего 0.244 ₽ API/ч (~0.268 с резервом), с риском потери речи на швах — низкий приоритет.

Для VAD хранить интервалы исходного времени с padding, строить карту сжатое время → исходное; отдельно преобразовывать start/end каждого слова и сегмента, особенно на швах. Затем выполнять существующие validate/merge и рендерить по исходному времени. Простое прибавление одного offset после нескольких вырезанных пауз неверно. Детерминированные тесты: тишина в начале/конце, несколько пауз, слово на шве, тихая речь, пересечение чанка. Проверять границы и синхронизацию субтитров на разрешённом корпусе. Реализация [SpeechTimestampsMap в faster-whisper](https://github.com/SYSTRAN/faster-whisper/blob/master/faster_whisper/vad.py) — первичный пример такого mapping, не готовый Cloud.ru адаптер.

### CPU STT: считать прирост VM, а не «бесплатную локальную модель»

[Официальный faster-whisper README](https://github.com/SYSTRAN/faster-whisper) поддерживает CPU INT8, word timestamps и VAD. Его benchmark: 13 минут аудио, small, 8 threads Intel i7-12700K: INT8 1m42s, batch8 51s, RAM 1477/3608MB. Это не large-v3, не Cloud.ru shared vCPU, не доказательство качества русской речи. Репозитарий также предупреждает, что segments — lazy generator: benchmark обязан материализовать его. Прямой перенос скорости на N5 недопустим.

Порог: если r — VM-hours на час аудио, P — цена добавочной VM-hour, то P×r + RAM/storage/ops < 22.204 ₽/аудиочас. Для r=0.25/0.5/1: P<88.82/44.41/22.20 ₽/VM-hour до накладных. Для постоянно включённого дополнительного CPU пула F ₽/мес: H > F/22.204 часов/мес до прочих затрат. Например F=10000: >450.37 ч/мес. VAD уменьшит API baseline и повысит порог окупаемости локальной STT; обе экономии нельзя просто сложить.

100/1000 пользователей по 1ч/неделю дают 428.571/4285.714 аудиочасов за 30 дней (30/7 недели); по 1ч/день за те же 30 дней — 3000/30000 ч. Максимально вытесняемая API STT: 9516/95160 ₽ и 66612/666120 ₽ за 30 дней соответственно; это верхняя граница бюджета добавочной CPU STT, не чистая прибыль. На одном постоянно занятом lane доступно ~720/r аудиочасов за 30 дней без запаса. При r=.5 это 1440 ч: weekly100/weekly1000 занимают 0.297619/2.97619 lane по среднему; daily100/daily1000 — 2.08333/20.83333 lanes. Требуемое число исполнителей округляется вверх с запасом на очереди и SLA. Локальная STT может жить на той же VM; её CPU/RAM надо ограничить, чтобы не вытеснять web/DB/render. Две VM не обязательны архитектурно, масштабировать по загрузке и SLA.

### Кэш, повторы, рендер и хранение

Ключ STT: account_id + source content SHA/version + extraction/VAD map version + ASR model/version/language/settings/dictionary. Не полагаться на original filename, duration или только object_key/bytes. Ключ selection: account_id + canonical transcript hash + prompt/schema/model/route/settings version + длительность/ограничения. Ключ rerender дополнительно содержит границы/words, crop/face plan, font/subtitles/glossary, watermark/plan/origin, music+gain/cuts, title/CTA и renderer version. Сохранять владельца и проверять доступ перед lookup; не делать cross-tenant existence oracle, общие ссылки или повторное использование пользовательского контента между аккаунтами. Кэш инвалидируется erasure/истечением разрешённого срока.

withSource сейчас скачивает полный объект в новый private temp и удаляет после каждого задания; каждый render concurrency=1 делает это заново. Для 252MB исторического файла 8×252=2016MB против 252MB (или504MB) без повторов. Вводить bounded local cache на одну VM: immutable source version/hash, tenant ownership, refcount/lease на активных читателей, TTL/byte cap/eviction, singleflight на загрузку, очистка после erasure. Сохранить резерв свободного диска: текущий withSource резервирует 3×source bytes. Cache не отменяет эту проверку. Range GET полезен только после проверки seek/container layout; обещать произвольную нарезку MP4 диапазонами нельзя.

Успешные STT chunks сейчас накапливаются в памяти до общего acceptTranscript. Crash близко к концу может потребовать повторной обработки/оплаты; versioned per-chunk checkpoint может сэкономить завершённые чанки после fencing, но unknown paid requests не считать успехом. Provider idempotency/request-status использовать только при документированной поддержке; такой поддержки Cloud.ru здесь не проверено. Ошибки параметров/схемы не исправлять бесконечным платным retry. Резерв 10% не является измеренной частотой отказов и не является верхней границей: до трёх chunk attempts способны дать больше.

Критичное несовпадение плановой модели хранения: tariff.ts clipExpiry возвращает null для действующего paid; plan.ts даёт бесплатные72ч после GREATEST(video.finished_at, account.plan_paid_until), showcase исключён. Продлевающийся paid может накапливать клипы дольше30дней. Поэтому 1.1GB×30d — сценарий экономики, не текущая гарантия ограниченного объёма. [Cloud.ru Lifecycle](https://cloud.ru/docs/s3e/ug/topics/concepts__lifecycle) существует; его [действия](https://cloud.ru/docs/s3e/ug/topics/concepts__lifecycle__action?source-platform=Evolution) надо привязать к корректным prefixes/tags и контрактам продукта, не ставить blanket30d на всё. При сохранении 30ч/мес и1.1GB/ч добавляется33GB/user-month; при отсутствии удаления6мес —198GB/user, 19.8/198TB для100/1000users (до дедупликации/прежних удалений). Это чувствительность к сценарию, не измеренный объём действующего стенда.

## Ночная акция и нижняя граница себестоимости

Night Pro122/292.8 ₽/M даёт4.2456 ₽, экономия2.7084 API или2.97924 с резервом: ~32.02 ₽/ч при прежних прочих допущениях. [Условия акции](https://cloud.ru/documents/promotions/active/night-tariff-foundation-models): 22:00–07:00 МСК, 1 октября–31 декабря2026, зарегистрированные в РФ лица/ИП/юрлица, договор и отсутствие задолженности; только позиции с пометкой night, условия могут прекратить/изменить. Whisper ночной скидки в проверенном тарифе не имеет. Задержать задачи до ночи можно лишь при согласованном SLA; постфактум переключить дешёвый маршрут при исчерпанной квоте нельзя. Ночную экономию не складывать со сменой того же LLM на gpt-oss/Flash.

На990 ₽/30дней и30ч/месяц gross33 ₽/аудиочас уже ниже35 ₽ переменных расходов: −60 ₽/user-month до VM/эквайринга/налогов/выплат. Даже бесплатный выбор оставляет22.204 ₽ STT, ~24.424 ₽ с резервом, плюс плановое хранение2.926 — ~27.35 ₽/ч. Это ещё не прибыль: ~169.5 ₽/user-month остатка до VM и остальных затрат. Нельзя сделать ежедневное часовое использование экономически надёжным одной оптимизацией VM; нужны измеренные лимиты/цена/месячный пакет и уменьшение STT/повторов.

Последовательность следующего разрешённого этапа: сначала billable usage и сверка прайса/провайдера; затем сравнение дешёвого RF route и VAD на фиксированном разрешённом корпусе, cache/source reuse; CPU STT только после замера качества/RTF/ресурсов. Исторический88.4мин→12:39 активного времени не является p95, throughput тестом или прогнозом конкурентной нагрузки.
