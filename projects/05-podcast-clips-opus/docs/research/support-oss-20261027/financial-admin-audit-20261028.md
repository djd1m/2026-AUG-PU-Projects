## Кредиты и платежи

- Публичного/админского API либо CLI произвольного или фиксированного ручного credit grant нет. В `credits.ts` есть только trial при signup, ограниченная миграция free-аккаунта, fulfillment подтвержденной покупки и recovery технически неуспешной обработки. `optInCredits` экспортирована как функция БД (`credits.ts:20–36`), но вызывающего UI/CLI нет; это не универсальный бонусный грант. Ограничения: enabled credits_v1, active effective-free, без незавершенного legacy intent; один lifetime trial, operator+reason, аудит.
- Новая регистрация в credit-mode получает 30 кредитов один раз. Подтвержденная покупка создает credit_grant и окна прав: Старт 990 ₽/300 кредитов/30 дней, Про 3990 ₽/1800/30 дней, доппакет 1490 ₽/600/30 дней; 1 кредит=60 секунд, учет посекундный. Базовые пакеты планируются после уже оплаченных периодов, addon начинает свое окно сразу. Это исходники и согласованные решения, не доказательство активации на проде (`packages/shared/src/tariff.ts:11–18`, `credits.ts:103–129`, `docs/features/credit-packages/owner-decisions.md`).
- Цены — константы кода, экран управления ценами отсутствует. У исторических intent сохраняется snapshot цены/SKU/выдачи: менять исторические оплаты ради нового тарифа нельзя.
- Денежный факт приходит от ЮKassa после проверки у провайдера, затем атомарно подтверждает intention/grant с защитой от повторов (`payments.ts:88–139`). Success URL сам кредитов не дает.
- Возврат инициируется вне текущего продукта, например владельцем в кабинете ЮKassa. В адаптере есть createPayment/getPayment/verifyNotification, нет createRefund (`provider.ts:76–82`). Проверенное refund.succeeded запрашивает refund/payment у ЮKassa, записывает payment refunded + needs_review, но НЕ снимает уже начисленные кредиты/paid windows и не запускает денежный возврат (`yookassa.ts:279–286`, `payments.ts:154–177`). D15 сохраняет ручной разбор без автоматического отрицательного баланса/clawback. Отдельного CLI reconciliation/review resolution не найдено; текущая support-карточка даже не возвращает needs_review/review_reason/provider_payment_id.

## Минимальная следующая админка (предложение, не реализация)

1. Развести support_operator (просмотр) и отдельную owner/billing_admin роль (финансовые действия), без автоматического наследования доступа из support.
2. В карточке владельца добавить одну ограниченную операцию «Начислить компенсацию»: фиксированный согласованный размер/пресеты, причина и ticket, предварительный просмотр результата, серверная проверка роли, idempotency key, атомарная запись grant и неизменяемого аудита actor/target/reason/before/after. Явно согласовать срок и дает ли компенсация paid-права; не выдавать paid window неявно. Для новой source потребуются совместимые схема и чтения.
3. Добавить очередь needs_review и сверку платежа по provider ID через ЮKassa API с показом локального и проверенного удаленного состояния. Подтверждение через тот же идемпотентный verified-payment тракт; не «поставить succeeded» вручную. Для аномалий, уже отмеченных обработанным event, нужен явный audited reconciliation path, а не слепой replay.
4. Возврат: сначала безопасный owner-flow «открыть/проверить возврат у провайдера», затем отдельно согласованный идемпотентный createRefund API при необходимости. Фиксировать actual refund ID, сумму, остаток/holds/потребление и решение по правам/кредитам; частичный возврат требует собственной политики. Самовольное обнуление баланса/редактирование paid-полей непригодно.

Реализация денежной админки относится к XL по `.claude/rules/complexity-router.md`: полный feature lifecycle и утверждение конкретного плана владельцем.
