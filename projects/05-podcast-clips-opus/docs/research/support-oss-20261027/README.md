# N5: готовая админка и система обращений

Исследование27.10.2026. Рекомендуемый минимальный вариант: **операторский доступ
и каркас из N6b, компактные UI-компоненты N4, готовые email/reset из N1 с guards N3,
Libredesk для обращений**. React-admin Community оставляем вариантом для будущих
сложных списков/фильтров, а не обязательной новой зависимостью первого этапа.
Собственный код ограничиваем адаптацией готовых компонентов к N5, чтением его
данных и связью обращения с проблемным заданием.
Сервисы не установлены; это исследование и конкретный план, не готовая поддержка.

Это уточняет первоначальную OSS framework-оценку: для начального небольшого
раздела собственный готовый каркас уменьшает новый код и зависимости.
Выбирать стабильную версию/digest для пилота; версия исследования не означает
проверенную production-сборку. У React-admin EE-компоненты RBAC/audit платные,
но они не обязательны для собственного небольшого серверного разграничения N5.

пригоден для mail-first работы, но API/portal/SSO — приобретаемые модули.
Peppermint архивирован. Проверенная текущая лицензия Directus — MSCL-1.0-GPL,
а не старый BSL; его не включаем в строгий OSS-выбор. Подробные ссылки в отчётах.

## Как будет выглядеть работа

1. Пользователь видит «Поддержка» на экране ошибки и открывает готовый виджет.
2. Обращение получает безопасные идентификаторы записи/задания, время и код ошибки.
3. Оператор отвечает в Libredesk; статусы, назначения и переписку ведёт готовый helpdesk.
4. Из обращения оператор переходит в карточку N5: тариф, баланс/резерв, стадия,
   технические попытки и состояние оплаты. Доступ проверяет N5 на сервере.
5. Разрешённое действие, например повтор обработки, проходит существующий доменный
   метод N5 с отдельными полномочиями, причиной, идемпотентностью и аудитом.

Изначально админка **только читает**. В N5 уже есть readCreditBalance,
readAccountBilling, VideoRetryService и отдельные операторские функции; это reuse.
Общего метода произвольной коррекции кредитов нет. Кнопка редактирования строки
БД не заменяет такую операцию. Возвраты сначала показываем как состояние оплаты,
не создаём поддельный webhook или платёжное начисление.

## Какой код всё равно нужен

- Адаптация staff-доступа N6b: operator membership по account_id и проверка
  SSR/API/DB к сессиям N5, закрытое назначение сотрудника. Подтверждённый email
  не даёт staff-права. Email allowlist N4 без mailbox proof не переносится.
- Компактные UI/forms/result states N4 и N5 read DTO/API: списки/карточки по
  allowlist, пагинация и фильтры, безопасные поля. Если позже выбран React-admin,
  его dataProvider/authProvider подключаются к этим же разрешениям сервера.
- Widget/JWT bridge и Context Links: привязка к immutable account_id, отдельный
  контакт helpdesk, разрешённые video/job IDs, переход в защищённую админку.
- Адаптация готового N1 email-proof/reset к N5: сопоставить таблицы и HMAC сессии,
  взять существующие одноразовые токены/TTL, API/UI и тестовые сценарии; использовать
  дополнительные guards N3. Реальный отправитель/домен/почтовый транспорт нужны отдельно.
- Связь удаления аккаунта с данными/вложениями helpdesk и сроками хранения переписки.

Собственный ticket engine, редактор переписки, механизм назначений, поиск и UI
общего inbox писать не нужно. Для первого пилота используем готовый виджет,
а не отдельный клиентский портал поверх его API.

### Подтверждение почты уже реализовано в других проектах

| Донор | Что готово | Что брать в N5 |
|---|---|---|
| N1 `01-testimonials-senja` | issueEmail/verifyEmail, account/email/session binding, SHA-256/TTL/one-use и блокировки; send/confirm API, явная кнопка UI; отдельный password-reset; HTTP mail adapter; unit/integration/browser scenarios | Основной email-proof/reset сервис, схему proof/token, небольшой mail adapter, API/UI и негативные сценарии |
| N3 `03-affiliate-rewardful` | Verified registration, forgot/reset/contact, sticky verification policy, purpose/version/expiry/concurrency guards, HTTP/UI/доставка | Дополнительные ограничения и тестовые сценарии; не переносить wholesale другую JS/custom-HTTP auth-систему |

Аудит проверил11каталогов проектов1–8 с вариантами на одном Git pin. Наличие
реализации и тестов подтверждено исходниками; сами тесты этим аудитом не запускались,
реальная доставка на адрес не подтверждалась. Первичный поиск N5/N6/N7 был
недостаточен для вывода по всем проектам; его результат не используется как
основание писать новый механизм токенов с нуля.

У N1 `accounts/sessions/token_hash` нужно сопоставить с N5
`account/session/cookie_token_hash`. Хеш сессии берётся через существующий N5 HMAC;
его нельзя подменять SHA-256 от email-token. Cookie `__Host-n5_session`, bcrypt,
действующие аккаунты, кредиты, платежи и tenant-проверки N5 сохраняются.
Реферальный/agent-payments runtime N1 ради подтверждения переносить не нужно.
N1 proof привязан к исходной сессии: сценарий открытия письма на другом устройстве
нужно явно решить в контракте N5, а не молча переносить или ослаблять эту проверку.
У N3 contact подтверждает только passwordless account, поэтому этот маршрут
не подходит для прямого переноса к уже существующим password accounts N5.

У доноров есть маленький HTTP-адаптер Resend: собственный SMTP/campaign engine
N7 не нужен. Это не решение автоматически отправлять данные через Resend из
нового российского N5; разрешённый поставщик, домен и runtime-настройки выбираются
для целевого окружения. Подтверждение почты для helpdesk-истории само по себе
не меняет согласованные правила начисления30кредитов при регистрации.

## Важная граница идентичности

У N5 пока нет подтверждения email. Libredesk JWT требует email и
external_user_id; первый sync может присоединить email-only контакт с прежней
историей. Это установлено по [стабильному исходнику](https://github.com/abhinavxd/libredesk/blob/5668a2a2c503b9304404d8f3620131b2990cbb99/internal/user/contact.go#L162).
Поэтому подписать неподтверждённый email недостаточно. По умолчанию открываем
идентифицированную историю только после проверки email в N5. До этого возможен
новый anonymous/unlinked запрос без открытия прежней истории; этот путь тоже
нужно проверить. Не принимать user_id, email и actor из произвольных полей браузера.

Staff OIDC Libredesk и JWT посетителя — разные механизмы. N5 сейчас не OIDC IdP;
первые операторы могут иметь отдельные локальные учётки helpdesk. Context Link,
даже зашифрованный, не заменяет серверную авторизацию N5. Выход, reset, истечение
и удаление аккаунта должны проверяться для обеих сессий: JWT expiry не доказывает
отзыв уже созданной сессии виджета.

В обращение не передаём автоматически видео/аудио, транскрипт, промпты, ключи,
cookies и сырые логи. Оператор получает минимальный контекст и разрешённый доступ
к данным через N5. Helpdesk не получает write-доступ к таблицам денег и аккаунтов.

## Одна ВМ и стоимость

План пилота остаётся одной ВМ в РФ. Встроенный операторский раздел не добавляет
самостоятельную БД или backend; резервный React-admin также является UI.
Libredesk — отдельное приложение Go + PostgreSQL/Redis; можно
проверить совместное размещение с отдельной логической БД/владельцем, без доступа
к схеме N5. Переиспользование Redis требует проверки namespace/ACL/persistence;
разные logical DB сами по себе не изолируют память и отказы.

Работа N5+helpdesk на2vCPU/4ГБ **не измерена**. Публичное наблюдение разработчика
Libredesk180–560МБ относится к приложению и не является бюджетом всей ВМ.
Chatwoot требует минимум4ГБ сам по себе и не служит более лёгким fallback.
При нехватке ресурсов сначала пересматриваем размер той же ВМ по замерам;
обязательную вторую ВМ исследование не обосновывает.

[Экономика N5](../unit-economics-20261026/unit-economics-summary.md) использует
условный F3000 ₽ и переменный бюджет57 ₽/час обработки. Дополнительные RAM/SSD,
вложения helpdesk, почтовые сообщения и труд оператора в этот бюджет не включены.
Без замера нельзя объявить, что новая поддержка точно укладывается в прежний F.

AGPL не является общим запретом коммерческого N5. Для покрываемого кода сохраняются
обязательства лицензии, включая источник изменённой сетевой версии; отдельный
HTTP-сервис снижает сцепление, но сам по себе не является юридической гарантией.
Форк Libredesk для первого этапа не планируется; точные ссылки и условия в отчёте.

## Минимальный план реализации и приёмка

| Этап | Результат | Проверяемое условие |
|---|---|---|
| 1. Staff + read-only admin reuse | Guard/schema/SSR N6b, компактный UI N4 над N5 read DTO/API | Обычный пользователь не читает staff API; нет хешей/ключей/чужих приватных файлов; поиск/пагинация работают |
| 2. Email/recovery reuse | Адаптация готового N1 proof/reset и guards/tests N3 к N5 через выбранный транспорт | Однократность/expiry/отзыв сессий, одинаковый ответ на запрос для существующего/несуществующего email; настоящая доставка |
| 3. Ограниченный Libredesk pilot | Виджет, ответы оператора, Context Links и выбранная идентичность | Два аккаунта не видят чужую историю; новый anonymous запрос не открывает старую; logout/reset/удаление проверены |
| 4. Контекст и безопасный retry | Обращение связано с video/job, разрешённый повтор через N5 | Подмена IDs и чужой ресурс отвергаются; повтор запроса не создаёт второй запуск/списание; durable audit |
| 5. Совместная эксплуатация | Проверенный размер ВМ, backup/restore и данные helpdesk | Пик с рендером, расход SSD/вложений, восстановление, удаление/обезличивание и сбой helpdesk проверены |

Для UI/E2E используется уже существующий Docker с Playwright, два синтетических
клиентских аккаунта и отдельные staff-права. Сначала обычный риск-маршрут и
контракт новой фичи: здесь появляются права/таблицы/внешний сервис, это отдельная
реализация от текущего STT-адаптера. Исследование не запускает установку/деплой,
платные модули, почтовый аккаунт или отправку сообщений третьим лицам.

До внедрения остаются продуктовые решения: реальный контакт/ответственный и
режим ответа, нужен ли email при отсутствии клиента, срок хранения обращений,
разрешённый staff-состав и целевая ВМ. Это не заменяется выбором OSS-пакета.

Проверены первичные документы/лицензии и исходники N5/N6/N7; установки,
браузерной совместимости и нагрузочного приёмочного прогона не было.
Профиль model-routing-econom: три исследовательских агента Sol/high, четыре
ограниченных задания с учётом source-аудитов email и операторских доноров;
фактическая модель и usage/cost недоступны. Телеметрия:
[20261027-n5-support-oss](../../telemetry/p-replicator/20261027-n5-support-oss/run.json).
