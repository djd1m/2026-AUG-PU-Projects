План размещения без второго сервера: отдельный процесс/контейнер helpdesk и собственная логическая БД с отдельным владельцем в существующем PostgreSQL, если версии/расширения совместимы. Не давать helpdesk доступ к таблицам N5. Redis можно переиспользовать только после проверки prefix/DB index, ACL, persistence и eviction: разные logical DB не изолируют память и отказ процесса; отдельный небольшой Redis часто проще изоляции. PostgreSQL/Redis/Elasticsearch не публиковать наружу. Для вложений — отдельный каталог/бакет и credential; Cloud.ru S3 совместимость выбранной версии не проверена. Нужны backup/restore обеих БД, вложений и ключей шифрования, ротация логов и запас места на upgrade.

**Как интегрировать с минимальным кодом**

1. Сначала готовый self-hosted Libredesk widget, кнопка «Поддержка» из всех состояний ошибки и `/g/`, понятный ответственный и часы ответа. Для вошедшего пользователя N5 backend подписывает HS256 JWT. Обязательные claims буквально: `external_user_id`, `email`, `first_name`, `exp`; email **не optional**. Для N5 `external_user_id = account.id`, отображаемое имя может быть нейтральным. Секрет inbox остаётся на сервере, при logout N5 вызывать `Libredesk.logout()`. [Документация widget](https://support.libredesk.io/en/articles/livechat). Это идентичность сессии N5, **не доказательство владения email**.
2. Агент работает в Libredesk; два начальных сотрудника могут использовать отдельные локальные учётки. Бесплатный [OIDC](https://support.libredesk.io/en/articles/sso) подключать лишь при наличии нужного IdP: SSO не создаёт агентов автоматически, email должен совпасть с заранее созданным аккаунтом. Не ставить Keycloak только ради двух операторов. N5 не является готовым OIDC IdP.
3. В [Context Links](https://support.libredesk.io/en/articles/context-links) сделать переход к read-only карточке N5 по `external_user_id` / `conversation_uuid`. Простой deep link требует авторизации сотрудника в админке N5. Есть встроенный `{{token}}`: ограниченный по времени AES-256-GCM payload с agent/contact/conversation и `iat/exp`. Его можно проверять в узком bridge, но это не готовая модель полномочий N5: обязательны срок, allowlist сотрудника, текущая роль и серверная проверка допустимой карточки. Не передавать email/секреты открытым query string, не превращать bearer из URL в постоянную сессию.
4. Для обращения о конкретном видео backend автоматически связывает **данное обращение** с `account_id`, принадлежащими ему `video_id`, `job/attempt_id`, `failure_reason`, стадией/временем, сводкой кредитов и статусом платежа; агент видит контекст или ссылку, пользователь пишет только сам вопрос. Все значения из N5, а не доверенный клиентский JSON. Отдельный `video_id` на contact как «последнее видео» недостаточен: две вкладки/два обращения могут перепутать контекст. [Conversation custom attributes API](https://support.libredesk.io/en/articles/update-conversation-custom-attributes) и [private messages API](https://support.libredesk.io/en/articles/send-message) позволяют обогащение без форка helpdesk. Точный механизм получения UUID от готового виджета — оставшаяся проверка пилота, а не обещание имеющегося JS callback.
5. Если обязательна собственная форма «Сообщить об ошибке» с точным контекстом с первого POST, N5 backend делает создание и привязку через [widget API](https://support.libredesk.io/en/articles/widget-api): `/auth/exchange`, `/conversations/init`, список/сообщения под contact session. Обычный [POST /api/v1/conversations](https://support.libredesk.io/en/articles/create-conversation) требует **enabled email inbox** и email контакта, поэтому для сценария без почты использовать его нельзя. Клиентский экран журнала потребует дополнительного UI; виджет уже даёт историю переписки и экономит этот код. API оператора/agent credentials в браузер не выдавать.
6. Для двусторонней синхронизации включить только необходимые [webhook events](https://support.libredesk.io/en/articles/webhooks). Задать обязательный secret; проверить `X-Libredesk-Signature` HMAC-SHA256 по исходным байтам постоянным по времени сравнением; после проверки — timestamp/freshness, привязка к разрешённому inbox/contact/conversation, идемпотентность по event/message ID (или устойчивому ключу доставки) и защита от циклов. Статусы обрабатывать как повторяемые/возможные не по порядку события; подтверждать после надёжной записи/очереди. Не давать вебхуку начислять кредиты, менять тариф, выполнять произвольный SQL или отправлять команды рендера.

**Проверка исходника выявила обязательную оговорку идентичности.** В stable v2.9.0 [`cmd/chat.go`](https://github.com/abhinavxd/libredesk/blob/5668a2a2c503b9304404d8f3620131b2990cbb99/cmd/chat.go#L358) проверяет все четыре обязательных claims; [`resolveUserFromClaims`](https://github.com/abhinavxd/libredesk/blob/5668a2a2c503b9304404d8f3620131b2990cbb99/cmd/chat.go#L978) ищет по external ID, если не передан положительный `user_id`. Наш signer должен формировать claims сам и никогда не принимать `user_id` от браузера. Но при первом входе [`syncContact`](https://github.com/abhinavxd/libredesk/blob/5668a2a2c503b9304404d8f3620131b2990cbb99/internal/user/contact.go#L162) сначала ищет **email-only contact без external ID** и присваивает ему новый external ID. Поэтому подписание JWT с непроверенным реальным email N5 может присоединить чужую прежнюю историю email-контакта. Два уже существующих разных external ID в этой ветке непосредственно не сливаются; это не устраняет риск первой привязки. Контакты глобальны в БД: отдельный inbox сам по себе не доказывает изоляцию.

Рекомендуемый production путь: **подтверждать email N5 до связывания с общей почтовой историей**, без форка Libredesk. До этого разрешать анонимное несвязанное новое обращение, не раскрывая существующую историю по введённому email. Альтернатива для режима без почты — строго уникальный технический email на account ID, не предназначенный для доставки, без смешивания с реальными email-only контактами; это **гипотеза интеграции**, требующая теста API и всех веток matching/смены email. Реальный непроверенный адрес не подставлять автоматически. Пилот вести только на синтетических аккаунтах. Нужен отрицательный тест: существующий контакт по тому же email без external ID не должен отдать историю новому аккаунту. Подмена email, смена account и две сессии должны проверяться отдельно. Обнаруженная граница может увеличить оценку glue; одного JWT endpoint недостаточно для принятия безопасности.

`exp` ограничивает обмен JWT, но созданная widget session имеет собственную TTL: документация указывает default idle duration 10 часов, исходник хранит отдельный Redis token. Нельзя обещать отзыв helpdesk-доступа одновременно с отзывом сессии N5 без отдельной проверки/интеграции. На logout, блокировке и удалении account проверить очистку widget state и прекращение доступа, а не только срок JWT.

Для Chatwoot запасная схема такая же: готовый widget + backend HMAC `identifier_hash` по `account.id`, обязательная identity validation и очистка виджета при выходе; [официальная инструкция](https://www.chatwoot.com/hc/user-guide/articles/1677587479-how-to-enable-identity-validation-in-chatwoot). API channel позволяет отдельную N5-форму без email канала. Подпись webhook имеет другой контракт: `HMAC-SHA256(secret, timestamp + '.' + raw_body)`, заголовки timestamp/delivery; [описание](https://www.chatwoot.com/hc/user-guide/articles/1677693021-how-to-use-webhooks). На выбранной версии проверить, что выданный секрет действительно верифицирует доставку; документация не заменяет такой тест.

Вложения разрешать по размеру/MIME и сознательному действию пользователя: скриншот и безопасный диагностический текст. Не пересылать автоматически исходное аудио/видео, транскрипт, промпты, cookies, ключи S3/моделей, платёжные реквизиты и сырые логи. Для кредитов/платежа достаточно ID и состояния; карточка оператора читает только нужные поля. Существующие денежные команды остаются в защищённых процедурах N5 с отдельным аудитом. Сам helpdesk не заменяет админку.

Удаление account в N5 должно охватывать вторую копию ПДн: contact email/имя/custom attributes, тексты и вложения, поисковые индексы, экспорт и цикл резервных копий helpdesk. Нужен собственный mapping `account_id ↔ contact_id`, политика допустимого срока хранения обращений и повторяемая операция удаления/обезличивания с квитанцией. Простой delete contact может не доказать уничтожение всей истории и файлов: семантика API выбранной версии здесь не проверена. Не переносить сырьё заранее, а затем пытаться компенсировать это ручным удалением.

**Что означает «без почты»**

Libredesk live chat работает как канал общения в приложении, email continuity включается отдельно через настроенный email inbox. Без неё клиент читает ответ после возвращения в виджет; уведомление на email не обещается. Для незалогиненного гостя сохраняется анонимная browser session, но это слабее подписанного account identity. Утеря сессии/пароля требует отдельного доступного контакта оператора.

FreeScout Portal создаёт ticket без отправки письма при submit, но **вход для просмотра/ответа — по ссылке из email**. Поэтому портал не решает сценарий полного обслуживания без почты. [Portal](https://www.freescout.net/module/end-user-portal/). У Zammad готовая [форма](https://admin-docs.zammad.org/en/7.0/channels/form.html) также пишет ticket напрямую, но её ограниченные поля не заменяют безопасную передачу N5-контекста.

Восстановление пароля и подтверждение email N5 — отдельная обязательная работа: токены со сроком и однократностью, защита от перебора/раскрытия аккаунтов, отзыв сессий при нужных изменениях. Для писем нужен разрешённый провайдер/relay и домен. [Libredesk email](https://support.libredesk.io/en/articles/connecting-inboxes) документирует IMAP/SMTP и OAuth; [Chatwoot production email](https://developers.chatwoot.com/self-hosted/configuration/environment-variables) — SMTP. Покупать именно SMTP не обязательно, если уже есть подходящий relay; HTTP mail API можно использовать из N5, но для helpdesk без native connector потребуется SMTP relay/адаптер. Прямую доставку с VPS через порт 25 не считать работающей. SPF/DKIM/DMARC, возвраты и доставку проверить после выбора поставщика. Новые аккаунты/оплаты этим исследованием не разрешены.

Перед реализацией нужен обычный риск-маршрут проекта: новые HTTP границы и права не являются мелкой текстовой правкой; деньги/тарифы через эту интеграцию не менять.

Если измерения не позволят совместить Libredesk и N5 на неизменных 4 ГБ, временный минимальный шаг — реально настроенный контакт/ящик оператора и ручные read-only ссылки на N5. Сейчас такого подтверждённого ящика нет. FreeScout core допустим как сознательный mail-first вариант без API/portal/SSO, но это сокращает результат и требует почтового канала; его нельзя выдать за завершённую in-app поддержку. Chatwoot здесь запасной по функциям, **не по экономии памяти**. Любое увеличение VM — отдельное решение по замерам.

Без программирования сначала назначить оператора/резерв и публичный контакт, утвердить время ответа, RU-домен/TLS, правила хранения/удаления переписки и вложений, доступы сотрудников и резервное копирование; выбрать, должен ли клиент получать email offline. Если такой ответ нужен, нужен и почтовый транспорт. Затем один ограниченный пилот Libredesk на изолированном тестовом контуре с синтетическими аккаунтами, измерением пиков RAM/CPU/диска вместе с рендером N5 и restore-тестом. Провал обязательного контекста или нагрузки — основание проверить Chatwoot на увеличенной общей VM, а не молча писать собственный helpdesk.
