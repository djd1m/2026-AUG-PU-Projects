## ADR-001 · Очередь заданий — BullMQ на Redis из клона, с фенсом попыток

**Контекст.** Конвейер «STT → выделение → рендер» состоит из заданий длительностью минуты. В
январском клоне очередь BullMQ на Redis 7 с четырьмя воркерами уже написана и отлажена (27
записанных граблей). Соседний проект N4 держал очередь в PostgreSQL (`FOR UPDATE SKIP LOCKED` +
аренда с fence), но там задания длились секунды и кода не было. Второе мнение (gpt-6-astra,
квитанция `receipts/codex-astra-second-opinion.md`): длительность заданий сама по себе Postgres не
дисквалифицирует; честный аргумент — наличие кода; но пароля и закрытых портов недостаточно.

**Решение (OWN-003).** BullMQ на Redis 7 в compose. Условия, без которых решение не действует:
1. Redis: AOF на томе, `maxmemory-policy noeviction`, пароль из `${REDIS_PASSWORD:?…}`, без `ports:`.
   Документация BullMQ: «it is very important to configure the maxmemory-policy setting to
   noeviction»; «We recommend enabling AOF».
2. Воркеры на ioredis с `maxRetriesPerRequest: null` (требование BullMQ для Worker).
3. `removeOnComplete` / `removeOnFail` с числовым потолком хранимых заданий.
4. Источник истины о задаче — PostgreSQL (`video.status`, `job_attempt`), Redis — только транспорт.
   Постановка в очередь выполняется ПОСЛЕ фиксации строки `video`; сторожевой цикл раз в минуту
   находит `queued`-строки без активного задания и ставит их заново.
5. Фенс попыток: каждая попытка стадии — строка `job_attempt` с монотонным `fence`; воркер пишет
   результат `UPDATE … WHERE fence = :mine`; ноль затронутых строк = попытка устарела, результат
   отброшен, в аудит — `stale_attempt_result`. Причина: BullMQ возвращает «зависшее» задание в
   очередь («that job is moved back to the waiting list»), и без фенса старая попытка дописала бы
   результат поверх новой.
6. ffmpeg запускается дочерним процессом с таймаутом 15 мин и `SIGKILL`; рендер не блокирует event
   loop воркера (иначе задание объявляется stalled через 30 с по умолчанию BullMQ).
7. Не больше 2 попыток на стадию; после второй — `video.status = failed` с причиной.

**Последствия.** Один лишний контейнер и один секрет; протокол долгой задачи
(`long-job-contract.md`) исполняется поверх BullMQ: `video_id` выдаётся до постановки в очередь.
Повторное исполнение зависшего задания не может испортить результат: оно либо продолжает с
актуальным фенсом, либо отбрасывается.

**Альтернативы.** Очередь в PostgreSQL как в N4 — отвергнута на неделю: переписывание рабочей
очереди ради одного контейнера меньше; остаётся кандидатом, если Redis на VPS окажется лишним ртом
по памяти (замер в первой фиче).

**Confirmation.** (а) Интеграционный тест: две попытки одного `render` с фенсами 1 и 2; попытка 1
пишет результат ПОСЛЕ попытки 2 — её `UPDATE` затрагивает 0 строк, результат попытки 2 не тронут,
в аудите `stale_attempt_result`. Внедряемый дефект: убрать `WHERE fence = :mine` → тест красный.
(б) Страж по compose: `docker compose config` содержит у `redis` `command` с `--appendonly yes` и
`--maxmemory-policy noeviction`, `requirepass` из переменной с `:?`, и НЕ содержит `ports:`.
Внедряемый дефект: опубликовать `6379:6379` → `check-ports.cjs` код 1.

## ADR-002 · Файлы — Cloud.ru Object Storage в боевом профиле, MinIO только в тестах

**Контекст.** Постановка §05 говорила «файлы — том Docker, не внешнее хранилище». Клон несёт
S3-код в 21 файле (пакет `@clipmaker/s3`: клиент, presign, multipart, операции; загрузчик в
браузере; воркеры; отдача клипов) и был настроен на `https://s3.cloud.ru`, регион `ru-central-1`.
На VPS свободно 18 ГБ из 158. Второе мнение (gpt-6-astra, раунд 2): согласен с Cloud.ru на неделю,
но условий координатора недостаточно; предложенный «том + холодный архив» сам отверг.

**Решение (OWN-004).** Боевой профиль — Cloud.ru Object Storage (S3, SigV4, регион `ru-central-1`);
тестовый профиль compose — MinIO без публикации портов, тот же код через `S3_ENDPOINT`. Условия:
1. Бакет приватный; ключи `S3_ACCESS_KEY/S3_SECRET_KEY` только у `web` (подпись ссылок для
   браузера), `worker-stt`, `worker-video`; у `proxy`, `db`, `worker-llm` — нет.
2. Числовые лимиты ДО выдачи подписанной ссылки: `user_uploads` 2/сутки, размер ≤ 2 000 000 000
   байт; multipart завершает СЕРВЕР (`POST /api/upload/complete`) с проверкой суммарного размера
   частей и `ffprobe`-длительности ДО списания минут. Подпись сама размера не ограничивает.
3. Срок подписанной ссылки ≤ 15 мин (Cloud.ru допускает до 604800 с; берём минимум достаточный).
   Подписи не попадают в логи; ключи объектов только серверные с проверкой владельца.
4. Lifecycle на бакете: `AbortIncompleteMultipartUpload` (`DaysAfterInitiation: 1`) — Cloud.ru
   тарифицирует хранение незавершённых частей; `Expiration` для клипов free — 3 дня после `done`
   исполняет приложение (у объектов свой префикс), lifecycle — страховка на 7 дней. `Transition`
   не используется: у Cloud.ru «не поддерживается в текущей версии».
5. CORS на бакете под публичный origin приложения (`PUT`, `POST`, `GET`, `HEAD`; заголовки
   `content-type`, `x-amz-*`; `ETag` в `ExposeHeaders`).
6. Воркер скачивает оригинал во временный каталог тома ОДИН раз (`s3-download.ts`), рабочая область
   резервируется до скачивания (≥ 3× размера оригинала) и очищается после успеха И после отказа.
7. Совместимость Cloud.ru (SigV4 с ключом `<tenant_id>:<key_id>`, multipart complete/abort, Range
   GET, CORS preflight) подтверждается ручной приёмкой на РАЗВЁРНУТОМ стенде по выданному адресу;
   тесты в MinIO совместимость Cloud.ru не доказывают.

**Последствия.** Диск VPS не накапливает оригиналы и клипы; трафик наружу в пределах льготы
(Cloud.ru: «не тарифицируются первые 10 ТБ исходящего трафика» в месяц); появляется счёт, который
крутят посетители — он связан лимитами п. 2 и `FR-LIMIT-*`. Строка постановки пересмотрена
владельцем (запись в `start/REPLICATE-PROMPTS-PROJECTS.md`).

**Альтернативы.** MinIO в проде — те же грабли подписей и CORS плюс двойной диск на VPS; том без S3 —
переделка 21 файла (оценка: два дня из семи). Обе записаны в квитанциях второго мнения.

**Confirmation.** (а) Страж по compose: сервис `minio` присутствует ТОЛЬКО под `profiles: [test]`,
у него нет `ports:`; боевой `web` получает `S3_ENDPOINT` из `${S3_ENDPOINT:?…}` без дефолта на
MinIO. Внедряемый дефект: дефолт `http://minio:9000` → страж красный. (б) Тест: `video.create` при
`user_uploads = 2` за сутки возвращает `refused(user_uploads)` и НЕ выдаёт ссылок; `upload/complete`
с суммой частей > 2 000 000 000 байт → `422`, объект удаляется, минуты не списаны.

## ADR-003 · STT — `whisper-1` с таймкодами слов; интерфейс поставщика не закрывает диаризацию

**Контекст.** Без таймкодов нарезка невозможна в принципе (постановка). Документация OpenAI: «Use
whisper-1 when you need word or segment timestamps»; «The timestamp_granularities[] parameter is
only supported for whisper-1». `gpt-4o-transcribe-diarize` отдаёт сегменты со спикером, но не
слова; в CJM D диаризации нет, в полном B она нужна.

**Решение.** `whisper-1`, `response_format=verbose_json`, `timestamp_granularities=[word,segment]`.
Поставщик STT скрыт за интерфейсом `Transcriber` с двумя реализациями: живой клиент и
детерминированный фейк для тестов; контракт результата — слова с `start/end`, сегменты, язык;
поле `speaker` — необязательное, чтобы diarize-модель подключалась без смены контракта.
Файлы длиннее лимита («Files can be up to 25 MB») режутся на аудиочанки по тишине, не посреди
фразы («Avoid splitting in the middle of a sentence»), таймкоды чанков сдвигаются на смещение.

**Последствия.** Цена 0,006 $/мин (страница тарифов OpenAI, 2026-09-21) → 600 мин/сутки ≈ 3,6 $.
Субтитры и границы клипов режутся по словам, а не по сегментам. Переход на diarize — смена
реализации, не контракта.

**Альтернативы.** `gpt-4o-transcribe` — нет таймкодов, отвергнута; `diarize` — нет таймкодов слов,
отложена до полного B.

**Confirmation.** Юнит-тест контракта: результат `Transcriber` без `words[].start/end` отвергается
до постановки в очередь выделения (`failed(no_timestamps)`); внедряемый дефект: принять результат
без таймкодов → тест красный. Страж по исходнику: строка `timestamp_granularities` присутствует
в живом клиенте ровно один раз.

## ADR-004 · Метка — часть тарифной архитектуры, несёт короткую ссылку с кодом клипа

**Контекст.** Метка на free — основная петля роста (FR-GROWTH-003) и решение, подтверждённое у
источника (тарифная страница: «Has watermark» / «Remove Watermark»). Метка без адреса — показ без
измерения: метрика недели считается по переходам.

**Решение.** Метка вшивается ffmpeg на этапе рендера (клон: цепочка `scale → ASS → CTA →
watermark`), текст «КлипМейкер · <домен>/c/<code>», где `code` — `clip_link.code`, созданный ДО
рендера. Позиция — нижний левый угол внутри safe zone сторис, высота ≥ 3,5 % кадра, подложка с
контрастом ≥ 4,5:1. Решение «метка или нет» принимается сервером по `account.plan` fail-closed:
всё, что не ровно `paid`, получает метку. Гостевые клипы — всегда с меткой (гость не `paid`).
Снятие метки — отдельный рендер без фильтра, доступный только `paid`; в неделе ведёт на экран
интереса.

**Последствия.** Один рендер на клип в неделе (free); `clip_link` существует у каждого клипа;
`/c/{code}` — публичная страница с атрибуцией и счётчиком уникальных переходов по `ip_prefix`.
Читаемость на телефоне проверяется на устройстве (FR-GROWTH-005), не в браузере.

**Альтернативы.** Метка без ссылки (как у источника) — не измерима; метка оверлеем плеера — не
уходит с файлом на площадку.

**Confirmation.** (а) Тест fail-closed: для `plan ∈ {null, '', 'PAID', ' paid', 'premium', 0, true}`
функция `watermarkRequired` возвращает `true`; внедряемый дефект: `!== 'free'` вместо `=== 'paid'`
→ красный. (б) Интеграционный: рендер клипа free содержит фильтр `drawtext` с текстом, содержащим
`/c/<code>`, и `clip_link` создан до `job_attempt(stage=render)`; внедряемый дефект: создать ссылку
после рендера → красный.

## ADR-005 · Оплата в неделе — экран интереса; ЮKassa из клона остаётся спящим кодом

**Контекст.** У клона есть `yookassa.ts`, вебхук и тарифы; постановка оплату в неделю не включала,
владелец подтвердил план (OWN-005).

**Решение.** Тариф `paid` существует в модели и в fail-closed-правилах, но в неделе недостижим:
«снять метку» и «больше минут» ведут на `interest.create` (`pro_interest`). Код ЮKassa и вебхук не
удаляются и не подключаются к маршрутам; `webhook-contract.md` отвечает «вебхуков нет».

**Последствия.** Атрибуция партнёра до платной конверсии остаётся `pending`/`activated` без
`paid`-события; комиссии не начисляются. Вторая волна включает ЮKassa вместе с контрактом вебхуков
(три класса отказа).

**Альтернативы.** Включить ЮKassa в тестовом режиме сразу — тянет контракт вебхуков и деньги в
неделю; отвергнуто владельцем.

**Confirmation.** Страж по маршрутам: в боевом профиле нет зарегистрированного обработчика
`/api/webhooks/yookassa` (тест роутера возвращает 404); внедряемый дефект: подключить маршрут →
красный.

## ADR-006 · Одна тяжёлая задача одновременно; резерв и очистка рабочей области

**Контекст.** Один VPS, 18 ГБ свободно, ffmpeg-рендер и скачивание 2 ГБ конкурируют за диск, CPU и
канал. Второе мнение: «рабочая область 20 ГБ при свободных 18 невозможна», Docker-том размер не
ограничивает.

**Решение.** `worker-video` с `concurrency: 1`; перед скачиванием оригинала — проверка свободного
места ≥ 3× размера файла (`statvfs`), иначе задание откладывается с причиной `no_disk`, а не
падает; временный каталог на именованном томе с очисткой в `finally`; отдельный лимит
длительности 90 мин и разрешения (не выше 1080p на входе, иначе даунскейл до рендера).
`worker-stt` и `worker-llm` — `concurrency: 2`, они не пишут на диск больших файлов (аудио
извлекается потоково в чанки ≤ 25 МБ и удаляется после отправки).

**Последствия.** Пропускная способность недели ≈ 10 записей в сутки (NFR-SCALE-001) — достаточно
для метрики; масштабирование — второй `worker-video` на другой машине, не на этой.

**Альтернативы.** Параллельный рендер — упирается в диск и CPU раньше, чем в очередь.

**Confirmation.** Тест: при свободном месте < 3× размера задание получает `deferred(no_disk)` и
не скачивает объект (счётчик вызовов S3 GET равен 0); внедряемый дефект: убрать проверку → красный.
Страж по коду: `concurrency` у `worker-video` — литерал `1`, не переменная окружения.

## ADR-007 · Явный код партнёра сильнее cookie; гостевая ссылка — третий источник атрибуции

**Контекст.** N4 ADR-008 и N1 `referral.ts`: код сильнее cookie, недействительный код не
откатывается к cookie. В D появляется третий источник — гость, пришедший по `/g/{guest_code}`,
атрибутируется ведущему.

**Решение.** `attribution.source ∈ {explicit, guest_link, cookie}`, ровно одна строка на аккаунт
(`UNIQUE (account_id)`), но строка изменяема по правилу: `explicit` побеждает всё; `guest_link`
побеждает `cookie`; равные и более слабые источники дают `409`; замена пишет `replaced_source`.
Недействительный явный код — `422`, без отката. Самопереходы владельца по своим `/c/` и `/g/`
ссылкам не создают ни атрибуции, ни `growth_event`.

**Последствия.** Метрики гостя и блогера не смешиваются; кабинет партнёра считает только свой
источник.

**Confirmation.** Интеграционный тест трёх исходов `code.apply`: `cookie → explicit` = `200` +
`replaced_source = cookie`; `explicit → любой` = `409`; `guest_link → cookie` = `409`; недействительный
код = `422` и строка не тронута. Внедряемый дефект: разрешить откат к cookie при `422` → красный.

## ADR-008 · Согласие гостя фиксируется ведущим до создания гостевой страницы

**Контекст.** Гостевая страница передаёт клипы с изображением гостя третьему лицу и делает их
скачиваемыми. Изображение гражданина охраняется (ст. 152.1 ГК РФ); запись принадлежит ведущему,
согласие гостя на публикацию обычно есть в договорённости о выпуске, но у нас его нет в системе.

**Решение.** `guest.create` принимает `consent_confirmed: true` обязательным полем; без него —
`422`, страница не создаётся. Текст чекбокса версионирован (хэш в `guest_pack.consent_version`).
Страница приватная по коду (≥ 128 бит энтропии), `noindex`, 14 дней, отзыв ведущим удаляет
страницу и объекты гостевых копий немедленно. На странице — контакт для жалобы; снятие по
требованию — не позже 72 ч.

**Последствия.** Ответственность за наличие согласия — на ведущем, и это записано в момент
действия; мы храним факт и версию текста.

**Confirmation.** Тест: `guest.create` без `consent_confirmed` или с `false` → `422`, строк
`guest_pack` не появилось; внедряемый дефект: сделать поле необязательным → красный.
