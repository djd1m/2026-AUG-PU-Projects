## Acceptance criteria (six)

1. Authenticated active account can create a campaign code from its partner dashboard without sending a guest pack. Strict custom `[A-Za-z0-9_-]{6,12}` campaign code doubles as label; no new campaign table. Code is owned by session account only; caller cannot supply partner/account owner. Repeating same code for same owner returns that existing code; collision with other owner gives generic 409, no owner data. Existing blocked code stays blocked. Multiple campaigns may have distinct codes; no silent minting around antifraud restrictions.
2. Dashboard shows each code's full canonical `N5_PUBLIC_ORIGIN + '/r/' + code` URL, status and explicit copy action/success/error. At least per-code selection/filter plus all-owned totals; no other partner's codes or customer/payment PII. Empty state offers code creation. Creation/copy work on mobile with keyboard/screen-reader labels.
3. `GET /r/{code}` validates exact code, rate-limits with existing infrastructure, accepts only active code whose owner account is active, excludes self visit/cookie, records one direct visit per code + trusted IP prefix + Moscow day under concurrent GETs, then fixed 302 to `/` with signed existing cookie and no-store. Invalid/unknown/blocked/deleted-owner code gives same 404 and no event/cookie; no user-controlled redirect. Existing guest/first-touch priority and cookie TTL/tamper behavior unchanged.
4. Signup through that landing and existing AuthForm creates existing non-rejected attribution; same-account retry cannot add registrations. Retain explicit > guest > cookie replacement matrix, invalid explicit no-cookie-fallback, immutable explicit attribution, self-referral rejection, guest precedence, blocked-code checks and 50-account antifraud threshold. Do not rewrite these rules to make a demo pass.
5. Own dashboard adds `purchases` and integer `revenue_minor` (RUB display) from existing accepted **package** payments: payment provider yookassa, status succeeded, needs_review false; valid non-rejected attribution owned by selected code(s); matching payment_intent account/intent/provider identity, intent status succeeded/fulfilled_at non-NULL and package sku start_v1/pro_v1/addon_v1. Require **payment_intent.created_at >= attribution.created_at** and paid_at >= attribution.created_at, so prior purchases or late webhook for an old intent never become campaign sales. Count financial facts once; no join multiplication, no success-page/event count, no operator grants/free trials/fake/unknown intent/amount mismatch/unfulfilled/duplicate intent identity cases. Revenue is SUM payment.amount_minor before provider fees, excluding entire refunded payment (existing refund policy, including partial refund marks whole payment refunded). Existing current-attribution model remains; no historical payout ledger implied. Compare counts directly against isolated DB fixtures.
6. Deterministic gates and isolated E2E pass with source-bound evidence. Browser proof: account A creates/copies a code; fresh B follows link → landing → signup → package checkout → verified accepted provider fixture/webhook → A sees +1 unique visit/+1 registration/+1 purchase/exact RUB amount, account C cannot inspect A code. Repeat GET and webhook unchanged; refund removes purchase/revenue. Actual YooKassa test-shop E2E is a distinct pending stage until private test credentials and isolated public HTTPS fixture are ready; fixture success is not claimed as an actual provider payment.
