# Проверка плана — фича 26 `clip-card`

Проверил постановку (`00_brief.md`) против кода, тестов, ADR-008, FR-RESULT-002/FR-GROWTH-001/FR-GUEST-*
и прибора `check-responsive`. Код не менял.

## Вердикт: READY WITH FIXES

Реализуемо без нарушения ADR-008 и без переделки `GuestPacks` сверх нужного. Но постановка молчит о
нескольких местах, где исполнитель почти наверняка ошибётся, и одно из них (тестируемость клика без
jsdom) способно сорвать весь пункт «Страж-мутация» брифа. Ниже — ответы на 6 вопросов и обязательные
правки.

## 1. «Гостю»: реализуемость, подъём состояния, тестируемость

**ADR-008 не нарушается.** ADR-008 — про `guest.create` (сервер, `consentHash`/`consent_confirmed`).
Кнопка «Гостю» на `ClipCard` вообще не вызывает `guest.create` — она только отмечает чекбокс в уже
существующей форме `GuestPacks` и скроллит/фокусирует. Граница ADR-008 (`согласие ДО создания
guest_pack`) физически не задета: между кликом «Гостю» и записью в БД нет ни одного вызова.

**Подъём состояния — вариант из брифа (б), а не (а).** Не поднимать `selected` целиком в
`VideoDetail` (это означало бы делать `GuestPacks` полностью controlled-компонентом — реальная
переделка сверх нужного, задета `create()`/`send()`/`update()`, которые читают `selected` напрямую).
Вместо этого: `GuestPacks` получает новый проп `preselect?: { clip_id: string; nonce: number }`,
эффектом добавляет `clip_id` в свой внутренний `selected`, если его там ещё нет, скроллит к своей
секции и фокусирует поле имени. `nonce` — счётчик из брифа: без него повторный клик на уже
отмеченный клип не создаст новой ссылки эффекта (тот же `clip_id`, тот же массив), и скролл/фокус не
сработают повторно.

`VideoDetail` держит `[guestPreselect, setGuestPreselect] = useState<{clip_id,nonce}|null>(null)` и
передаёт `onSendToGuest={clipId => setGuestPreselect(p => ({ clip_id: clipId, nonce: (p?.nonce ?? 0) + 1 }))}`
в каждый `ClipCard`, а `GuestPacks` — только когда `consentHash` есть (уже так по строке 74).

**Тестируемость — это и есть главная находка.** В проекте **нет jsdom/happy-dom/testing-library**
(`vitest.config.ts` не задаёт `environment`, дефолт — `node`; `package.json` не содержит
`@testing-library/*` вовсе). Существующие тесты `ClipCard`/`ClipMusicChoice`
(`tests/clip-music-choice.test.ts:55-66`, `tests/progress-screen.test.ts:56-65`,
`tests/clip-music-review-fixes.test.ts:60-68`) рендерят разметку **только** через
`renderToStaticMarkup` (SSR, статика, без событий) и проверяют `toContain`/regex по HTML. Клик по
кнопке нигде не симулируется; там, где нужно проверить эффект вызова (`startClipDownload`,
`tests/progress-screen.test.ts:143-149`), функция вызывается **напрямую как обычный JS**, а
`document` подменяется вручную через `vi.stubGlobal('document', {...})`.

Следствие: «нажатие «Гостю» отмечает клип в форме и не вызывает `guest.create`» **нельзя** проверить
рендером `<ClipCard onSendToGuest=.../>` и симуляцией клика — рендерить и кликать в этом стеке нечем.
Пункт брифа «Страж-мутация: убрать вызов отметки клипа в обработчике «Гостю» → тест красный» будет
невыполним, если вся логика останется inline-замыканием внутри JSX `onClick`.

**Обязательная правка плана:** вынести саму логику отметки в чистую экспортируемую функцию без DOM,
по образцу `packages/shared` (например `addGuestPreselect(selected: string[], clipId: string):
string[]` рядом с `guest-contract.ts`, либо метод `GuestPackService`-соседа на клиенте). Тест дергает
функцию напрямую (как `effectiveMusic`/`resolveMusicTrack` в `clip-music-choice.test.ts:32-36`), а
страж-мутация портит именно её тело (`writeFileSync`/find-replace по образцу
`tests/run-clip-music-choice-mutations.mjs`), а не обработчик `onClick`. Остальное (disabled-состояние
кнопки, наличие `aria-label`) проверяется как обычно через `renderToStaticMarkup` на разных `clip`/
`onSendToGuest` пропсах — это тестируется штатно, без DOM.

## 3. Плашка оценки поверх `<video controls>`

Безопасно **при условии** размещения строго в левом верхнем углу, как и просит бриф — это не
совпадает ни с одной из трёх зон:

- **Нативные контролы** `<video controls>` браузер рисует внизу по всей ширине (полоса
  прогресса/кнопки) — верхний левый угол их не касается.
- **Метка (watermark)** вшита в пиксели и всегда снизу: `packages/shared/src/watermark.ts:24,33`
  — `bottom = height * 0.12`, `y: height - bottom - plateHeight`, `left = width * 0.05` (нижняя
  полоса, не верхняя).
- **Субтитры** (ASS) в этом проекте традиционно тоже нижние/центральные (рендер вписывает их в
  нижнюю треть кадра, как и метку) — верхний угол свободен.

**R3 прибора** (`scripts/responsive/rules.mjs:65-71`) проверяет перекрытие только для «целей»
(`button,a[href],[role=button],summary,select,input,textarea,[tabindex],[onclick]`) — плашка (`div`/
`span`, `aria-hidden`) в этот список не попадает, значит R3 не будет ругаться НА неё саму. Но если
плашка визуально перекроет соседнюю кнопку — R3 поймает это как перекрытие ТОЙ кнопки. Поскольку в
новом порядке (бриф §4) кнопки лежат ПОД кадром, а не над ним, соседних целей рядом с плашкой нет.

**Обязательная CSS-правка, не названная в брифе:** `.clip-preview` сейчас не имеет
`position:relative` (`apps/web/src/app/globals.css:67`) — без неё `position:absolute` у плашки
всплывёт к ближайшему спозиционированному предку выше по дереву, а не к рамке превью. Добавить
`position:relative` в `.clip-preview` и `position:absolute; inset-block-start:...; inset-inline-start:...`
у плашки, `z-index` выше `<video>` (или просто ставить плашку после `<video>` в разметке).

**Контраст ≥4,5:1 — прибор его НЕ проверит.** R4 (axe) на `aria-hidden` элементах контраст не
считает (axe исключает недоступные для AT узлы из большинства правил, включая `color-contrast`).
Значит зелёный `check-responsive` не будет доказательством выполненного контраста для плашки — это
нужно посчитать/проверить вручную (или взять уже проверенную пару токенов, например
`--btn-bg`/`--btn-fg`, вместо изобретения новой) и явно зафиксировать коэффициент в отчёте фичи.

## 4. FR-GROWTH-001: выполняется ли сейчас, не сломает ли новая панель

**Сейчас НЕ выполнено** (бриф сам это признаёт: «третьей кнопки на карточке сейчас нет»). Критерий
`docs/Specification.md:433-437` / `docs/test-scenarios.md:42` требует «скачать» и «отправить гостю»
видимыми без прокрутки на ПЕРВОЙ карточке — сейчас «отправить гостю» на карточке нет вовсе, только
чекбокс в форме `GuestPacks` далеко внизу страницы под сеткой клипов.

**Новая панель действий (бриф §3-4, кнопки сразу под кадром, до оценки/музыки) правильно нацелена на
закрытие этого критерия** — минимизирует путь скролла для первой карточки.

**Но она не будет автоматически ПОДТВЕРЖДЕНА прибором.** `FIRST_SCREEN_ACTIONS`
(`scripts/responsive/rules.mjs:149-152`) содержит селекторы только для `/` и `/c/{code}`; маршрут
`/dashboard/videos/[videoId]` (где живёт `ClipCard`) в R9 не участвует. Более того, R9-цикл в
`check-responsive.mjs:110-127` создаёт контекст БЕЗ `storageState` (в отличие от основного цикла
сценариев, `check-responsive.mjs:97`), то есть даже добавление строки в `FIRST_SCREEN_ACTIONS` для
этого маршрута сходу упадёт на логине. Значит зелёный `check-responsive` **не доказывает**
FR-GROWTH-001 для этого экрана — это нужно проверить скриншотами (`first-screen-375x667` и т. п. по
методичке навыка, раздел «Код 0 — необходимое, не достаточное условие») и зафиксировать вручную в
отчёте фичи, а не полагаться на код 0.

## 5. Контейнерные запросы и `.clip-grid`

Конфликтов по существу нет — `container-type: inline-size` на `.clip-card` и переключение колонок
`.clip-grid` по ширине окна (`apps/web/src/app/globals.css:65,105,138,144`) намеренно ортогональны:
внешняя сетка решает, СКОЛЬКО колонок, `@container` решает, КАК layout карточки реагирует на итоговую
ширину своей колонки (именно это и просит бриф §5 — карточка узкая в сетке из трёх на 1024,
широкая на телефоне). Это не баг, а весь смысл требования.

**Единственный реальный конфликт — существующее правило `.clip-body button { width:100%; }`**
(`apps/web/src/app/globals.css:72`). Ряд из трёх кнопок (`cluster`: `display:flex; flex-wrap:wrap`)
под этим правилом развалится в три кнопки по 100% ширины друг под другом (`width:100%` на flex-item
задаёт `flex-basis`, кнопки не встанут в ряд ни на одной ширине). Это надо явно переопределить —
например, дать панели действий свой класс (`.clip-actions`, cluster) с `.clip-actions button { width:auto; }`,
а `.clip-body button { width:100%; }` оставить только там, где реально нужна полная ширина (кнопка
музыки/повтора — там её сейчас и применяет `.clip-body button` глобально). Бриф этого не называет.

## 6. Пробелы постановки — вероятные ошибки исполнителя

1. **`.clip-body button { width:100%; }` ломает ряд из трёх кнопок** (см. §5) — не названо в брифе,
   исполнитель почти наверняка получит зелёный `npm run build`/`lint`, но кнопки друг под другом на
   всех ширинах.
2. **`.clip-preview` без `position:relative`** — плашка уедет не туда, куда рассчитывали (см. §3).
3. **Нет jsdom/testing-library** — если логику отметки клипа оставить inline-замыканием в
   `onClick={() => ...}` внутри JSX, страж-мутация из брифа буквально невыполним в этом стеке (см.
   §1). Нужна чистая функция без DOM.
4. **Строгая парность токенов в `theme.test.ts`** (см. §2) — забытый light-блок для
   `--score-bg`/`--score-fg` уронит ВЕСЬ набор темы, а не только новый тест; диагностировать причину
   по логу непросто, если не знать про этот страж заранее.
5. **`prefers-reduced-motion` для `scrollIntoView`** — глобальное правило
   `apps/web/src/app/globals.css:146` (`scroll-behavior:auto!important` под медиа-запросом) действует
   на CSS-триггеры прокрутки (якоря, `scroll-behavior`), но JS-вызов `element.scrollIntoView({behavior:
   'smooth'})` с явным параметром не гарантированно откатится к CSS во всех движках. Бриф прямо
   требует «без плавности» — нужен явный `matchMedia('(prefers-reduced-motion: reduce)').matches` в
   коде, а не расчёт на глобальный CSS.
6. **Фокус в поле «Имя гостя»** — у `<input>` в `GuestPacks.tsx:35` сейчас нет `id`/`ref` для
   программного `focus()`; понадобится добавить (например `id="guest-name"` + `document.getElementById`
   либо `ref`, прокинутый через `forwardRef`). Бриф говорит «ставит фокус», но не говорит, каким
   механизмом — решение оставлено исполнителю, стоит явно выбрать `ref`, а не завязываться на глобальный
   `id`, чтобы не плодить связность через DOM.
7. **Порядок для `rerender_failure`/`copyMessage`/`error`** — новый порядок карточки (бриф §4)
   называет 6 блоков, но не говорит, куда деть три существующих статусных узла
   (`clip.rerender_failure`, `copyMessage` от копирования ссылки, `error` от скачивания). Разумное и
   низкорисковое решение: статусы кнопок («Скопировано», ошибка скачивания) — сразу после панели
   действий; `rerender_failure` — рядом с музыкой (он про пересборку по музыке). Стоит явно
   зафиксировать в постановке, иначе разные попытки исполнителя разъедутся.
8. **R9 (первый экран) не покрывает этот маршрут** (см. §4) — зелёный `check-responsive` не будет
   доказательством FR-GROWTH-001 для этой карточки; нужна отдельная ручная строка в отчёте со
   скриншотом, а не ссылка на код 0.
9. **Контраст плашки не проверяется автоматически** (см. §3) — `aria-hidden` выводит её из-под axe;
   нужен ручной расчёт/проверенная пара токенов и явная запись коэффициента в отчёте.

## Обязательные правки (нумерованный список)

1. Логику «отметить клип для гостя» вынести в чистую экспортируемую функцию без DOM (например
   `addGuestPreselect(selected: string[], clipId: string): string[]` рядом с `guest-contract.ts`);
   `GuestPacks` использует её в эффекте на изменение `preselect`. Тестировать и мутировать эту
   функцию напрямую, а не клик по кнопке.
2. `GuestPacks` получает проп `preselect?: { clip_id: string; nonce: number }` (не полный подъём
   `selected` в `VideoDetail`); эффект добавляет клип, скроллит к секции, фокусирует поле имени по
   `ref`/`id`, добавленному к `<input>` (`GuestPacks.tsx:35`).
3. Добавить CSS-класс для панели действий (например `.clip-actions`), явно снять
   `.clip-body button { width:100%; }` внутри него (`width:auto`), чтобы ряд из трёх кнопок реально
   переносился, а не складывался в столбец.
4. Добавить `position:relative` на `.clip-preview` (`globals.css:67`) под плашку с
   `position:absolute`, z-index выше `<video>`.
5. Токены `--score-bg`/`--score-fg` добавить В ОБА блока (`:root` и `:root[data-theme=light]`) с
   одинаковыми именами и разными значениями — иначе `tests/theme.test.ts` падает целиком.
6. Прокрутку к форме гостя делать с явной проверкой
   `matchMedia('(prefers-reduced-motion: reduce)').matches` в коде (не полагаться на глобальный CSS).
7. Зафиксировать в реализации место трёх существующих статусных узлов (`rerender_failure`,
   `copyMessage`, `error`) в новом порядке карточки — рекомендация в §6 п.7 выше.
8. В отчёте фичи (`07_code_report.md`) явно отметить: (а) коэффициент контраста плашки посчитан
   вручную (число), потому что axe его не проверяет из-за `aria-hidden`; (б) «без прокрутки на
   первой карточке» (FR-GROWTH-001) подтверждено скриншотом `/dashboard/videos/...` при 375×667/
   390×844/360×740, а не только кодом 0 `check-responsive` — маршрут не входит в R9.
9. Не трогать байт-в-байт подстроки, охраняемые существующими тестами/мутациями:
   `tests/short-link.test.ts:100-103`, `tests/run-clip-music-choice-mutations.mjs` записи
   `review-player`/`review-failure` (см. таблицу §2).
