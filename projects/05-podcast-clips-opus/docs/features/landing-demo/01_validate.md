## 1. Третий путь к файлу — безопасность и трафик

- **Перечисление/подмена кода:** закрытый список `SHOWCASE_CLIPS` в коде + строковое сравнение —
  предсказано брифом, дыры нет, если проверка ИМЕННО членство в списке, а не формат кода (нужен тест
  «чужой код того же формата → 404», как и просит бриф).
- **Кэширование подписанной ссылки:** существующий паттерн `clip-file.ts`/`short-link-handler.ts`
  всегда отдаёт `Cache-Control: private, no-store` на редирект — правильно, переносить один в один.
  `private` для публичного клипа семантически странно, но безвредно (`no-store` уже исключает любое
  кеширование) — не блокер.
- **CORS:** не нужен, подтверждено — `<video src>`/`<img>` не требуют CORS для воспроизведения/показа
  без `crossorigin`; редирект ведёт на S3 напрямую, браузер сам ходит туда.
- **Лимит частоты:** переиспользование `allowRead` (120/мин на IP-префикс) — существующий механизм,
  подходит; НО он общий с `/c/{code}` и гостевыми чтениями с того же IP/подсети — при заметном трафике
  на лендинг с одной корпоративной/мобильной подсети возможны ложные 429 на превью/демо. Не блокер
  (бриф сознательно выбрал этот лимит), но стоит наблюдать после выкатки.
- **Механизм отдачи — выбрать ПРОСТОЙ редирект, не двойной ticket-проброс.** В `clip-file.ts` есть
  ДВА разных механизма: прямой 302 на подписанную ссылку (путь владельца) и двухшаговый
  `guestFileTicket` + `deps.stream()` (путь `guest_pack`, байты идут ЧЕРЕЗ сервер `web`). Для витрины,
  которую будет дёргать КАЖДЫЙ посетитель лендинга, второй механизм — трата полосы и CPU `web`
  впустую. Использовать первый (прямой редирект), как и допускает формулировка брифа «либо отдача тем
  же механизмом» — она не обязывает именно к ticket-проходу.
- **Стоимость трафика, `preload=none`:** достаточен. `preload=none` не тянет 23 МБ при загрузке
  страницы — данные пойдут только по тапу «play». Постоянная нагрузка от лендинга — постер
  (`thumbnail_key`, уже существует в пайплайне), не видео. Отдельная облегчённая версия НЕ нужна;
  нужен только рабочий постер (`poster=".../thumbnail"`) и `controls`, чтобы у пользователя вообще
  была кнопка запуска (см. «Пробелы», п. 6).

## 2. Ретенция — ТОЧНЫЕ строки, вывод: НЕ защищает

`apps/web/src/server/retention.ts`, шаг «очистка клипов»:

```
const clips = await pool.query<...>(`SELECT c.id,c.object_key,c.thumbnail_key,c.video_id FROM clip c
  JOIN video v ON v.id=c.video_id JOIN account a ON a.id=v.account_id
  WHERE c.status='done' AND a.status='active' AND a.plan <> 'paid' AND v.status IN ('done','failed')
  AND v.finished_at <= $1 AND (c.object_key IS NOT NULL OR c.thumbnail_key IS NOT NULL)
  ORDER BY v.finished_at LIMIT $2`, [new Date(now.getTime() - 3 * 86400_000), batch]);
...
for (const clip of clips.rows) await step('удаление клипа', async () => {
  for (const prefix of ['clips/free', 'clips/paid', 'thumbs']) await storage.eraseClipPrefix(`${prefix}/${clip.video_id}/${clip.id}`);
  await pool.query('UPDATE clip SET object_key=NULL,thumbnail_key=NULL,expires_at=COALESCE(expires_at,$2) WHERE id=$1', [clip.id, now]);
});
```

`c.expires_at` **не участвует в WHERE вообще** — отбор идёт по `a.plan <> 'paid'` и
`v.finished_at <= now-3д`, а `expires_at` используется только ПОСЛЕ удаления (`COALESCE`, чтобы
проставить метку задним числом). Предположение брифа «`expires_at` NULL — проверить, что ретенция не
тронет» — **не подтверждается**: NULL здесь ничего не защищает, потому что колонка не в фильтре.
Единственное, что сейчас может уберечь витринный клип, — если `account.plan = 'paid'` у записи
`ec8b9021-…` (в репозитории этого не видно, только в базе стенда). Это НЕ гарантия: план может
измениться, а фича сама просит независимое исключение.

**Вывод:** без явного исключения по `SHOWCASE_CLIPS` объект клипа `/c/CTDUUG` (и остальные 6 клипов
той же записи, если они тоже смотрят на витрину) будет стёрт `retentionTick` (интервал
`RETENTION_INTERVAL_MS`=1 ч) через 3 дня после `video.finished_at` — ровно как и опасался автор
брифа. Нужна правка (см. обязательные правки, п.1).

## 3. Первый экран 375×667 (и 390×844, 360×740) — расчёт высоты

Токены: `--nav-h = 3.8125rem + max(1rem, safe-area-top)`; `.container` мобильный верхний паддинг
`1.5rem`; `.landing h1` на мобиле — `margin:0`, `font-size: clamp(2rem,4.2vw,3.875rem)` (на всех трёх
ширинах clamp упирается в МИНИМУМ 2rem=32px, т.к. `4.2vw` < 32px), `line-height` от базового `h1`
правила = 1.13. `<br>` в H1 скрыт на мобиле — текст льётся одной строкой без принудительного переноса.

| Величина | 375×667 | 360×740 | 390×844 (нотч, safe-area-top≈47px) |
|---|---|---|---|
| `--nav-h` | 77px | 77px | 108px |
| контент начинается на Y | 101px | 101px | 132px |
| доступно до низа экрана | 566px | 639px | 712px |
| ширина текста H1 (контейнер −32px паддинга) | 343px | 328px | 358px |
| символов в строке (≈18.6px/симв. на кириллице 32px) | ≈18–19 | ≈17–18 | ≈19 |
| строк H1 (текст «Хороший разговор заслуживает больше зрителей.», ≈45 симв.) | **≈3 (≈110px)** | ≈3 (≈110px) | ≈3 (≈110px) |

Это ОЦЕНКА по метрике шрифта, не измерение реальным рендером — число строк H1 — главный источник
неопределённости всего расчёта; проверить по факту скриншотом
`first-screen-375x667` из `--out` ПЕРЕД тем, как замораживать размеры.

Бюджет на 375×667 (самый тесный случай) после H1 и трёх зазоров grid-gap (`--space-4`=16px каждый:
H1↔демо, демо↔кнопка) и кнопки `.landing-cta` (`button` в проекте `min-height:2.875rem`=46px, беру
48px с запасом): `566 − 110 − 16 − 16 − 48 = 376px` на блок «демо» (видео + подпись + ссылка «Открыть
клип»).

Внутри блока демо: подпись «88 мин разговора → 7 клипов» (~24px с интерлиньяжем) + зазор (~8px) +
ссылка «Открыть клип» (по конвенции проекта — цель ≥44px, R2) + зазор (~8px) ≈ 84px служебной высоты.
Остаётся на видео: `376 − 84 = 292px` высоты → при 9:16 это ширина `292×9/16 ≈ 164px`.

**Рекомендация (с запасом, а не впритык):** ограничить видео `width: clamp(7rem, 38vw, 9.5rem)`
(112–152px в зависимости от ширины экрана) → высота 199–270px. На 375px это даёт видео ≈142×253px —
блок демо ≈253+84=337px против бюджета 376px, **запас ≈39px** на неточность оценки H1. Постер
показывается ЦЕЛИКОМ (не половина) — при такой ширине это укладывается с запасом на всех трёх
ширинах; 360×740 и 390×844 существенно свободнее (449px и 522px бюджета на демо соответственно).
Число для документа: «видео 9:16, ширина `clamp(7rem,38vw,9.5rem)`, постер целиком».

## 4. Что сломается в тестах/стражах

1. **`tests/responsive-check.test.ts:169`** — жёстко ожидает
   `firstScreenSelector('/') === 'form.auth-card button:not([type=button])'`. Как только
   `FIRST_SCREEN_ACTIONS` для `/` меняется на новый селектор основного действия, эта строка красная
   — ожидаемо, но нужно поправить как часть фичи, иначе `--test` не проходит с самого начала.
2. **`scripts/responsive/rules.mjs` / `scripts/check-responsive.mjs` — архитектурная нехватка.**
   `FIRST_SCREEN_ACTIONS` и `firstScreenSelector(route)` возвращают РОВНО ОДИН селектор на маршрут;
   цикл в `check-responsive.mjs` (`for (const { w, h } of FIRST_SCREEN_VIEWPORTS) … const selector =
   firstScreenSelector(route); if (!selector) continue;`) вызывает `firstScreenRule` один раз. Бриф
   требует ДВЕ независимые R9-проверки на `/`: основное действие (`.landing-cta`) И видимость демо
   (`.landing-demo video`). Текущая модель данных этого не выражает — нужно расширить
   `FIRST_SCREEN_ACTIONS[i].selector` до `string | string[]` (или завести соседний список) и цикл в
   `check-responsive.mjs`, чтобы гонять `firstScreenRule` на каждый селектор отдельно. Без этой правки
   вторая проверка («демо в первом экране») физически некуда воткнуть, и она либо не будет
   выполняться, либо тихо подменит первую.
3. **`FIRST_SCREEN_ACTIONS` R9 на `/c/[code]` не задет** — `.cta` там свой (не пересекается с
   `.landing-cta`), регрессии нет.
4. **R6** (390×844/1440×900, превью по высоте) сработает автоматически на новом `<video>`, если он
   виден на этих ширинах — с рекомендованными размерами укладывается с большим запасом (см. п.3).
5. **Фикстура `.responsive-fixture/ui-fixture.json`** не нуждается в правке: маршрут `/` уже входит
   в `routes` безусловно (`validateFixture`), витринный код — код в коде, а не в фикстуре.
6. **`routePreconditions`** для `/` сейчас не делает ничего; добавление демо не требует ожидания (видео
   рендерится сервером статично, без клиентского фетча), так что можно не трогать — но полезно свериться
   визуально по скриншотам `first-screen-*`, что постер реально пришёл (сеть до S3/witness доступна со
   стенда, на котором крутится `check-responsive.mjs`).

## 5. Подмена основного действия — воронка/CJM

Технически R9 не нарушается: после обновления `FIRST_SCREEN_ACTIONS` в первом экране по-прежнему есть
ОДНА кликабельная основная цель, просто это кнопка-скролл, а не сама форма. НО это меняет воронку по
факту, а не только облик:

- **Сегодня** (до фичи) форма `AuthForm` уже находится в первом экране на мобиле (текущий селектор
  `form.auth-card button` проходит R9) — то есть 0 лишних касаний до заполнения email/пароля.
- **После фичи** первым экраном становится демо+кнопка «Попробовать бесплатно», форма уходит НИЖЕ
  сгиба — то есть +1 касание (тап → скролл → фокус в email) до начала регистрации.

Это явно СОЗНАТЕЛЬНОЕ решение брифа (ставка на то, что показанная ценность окупает лишний тап), а не
случайный побочный эффект, и FR-LOOK-011/OWN-016 его прямо предполагают. Указываю как контролируемое
изменение воронки, а не как блокер — но стоит зафиксировать ожидание и последить за конверсией после
выкатки.

Смежная нестыковка (не создана этой фичей, но обнажается ею): принятая `Specification.md` формулировка
FR-LOOK-007 описывает первый экран как «поле „ссылка на видео“ и кнопка „загрузить файл“» — то, что
сейчас РЕАЛЬНО не реализовано (сейчас это email/пароль форма, а после фичи — демо+CTA-к-форме). Раз
бриф просит закрыть FR-LOOK-007/011 в addendum как «воплощены», addendum обязан явно объяснить ЭТО
расхождение (почему решили не делать поле-ссылку), а не только зафиксировать добавление демо.

## 6. Пробелы

- Нет `controls` (или альтернативной кнопки play) — брифом не упомянуто, но без атрибута управления
  пользователь не сможет запустить видео при `preload=none`/без автовоспроизведения. Нужно явно.
- «Фокус в поле почты» по якорю невозможен ИЗ `page.tsx` (асинхронный Server Component, без клиентского
  кода) — обычный `<a href="#auth">` проскроллит, но не сфокусирует поле. Нужен клиентский код (эффект
  в `AuthForm` на `location.hash==='#auth'`, либо кнопка-CTA как маленький клиентский компонент,
  вызывающий `scrollIntoView`+`focus()`).
- `SHOWCASE_CLIPS` в брифе описан как «код → подпись + числа»; не названо явно, ЧЕМ код связывается с
  UUID клипа для витринного маршрута — нужно решить: хранить сам `clip_id`(UUID) в `SHOWCASE_CLIPS`
  напрямую (проще, без похода в `clip_link`) или короткий код с резолвом через `clip_link` (переиспользует
  существующую таблицу, но тянет лишний JOIN). Рекомендация: хранить UUID напрямую в `SHOWCASE_CLIPS` —
  короче путь и меньше связности с `clip_link`/`short_link` семантикой (которая про DIFFERENT вещь —
  персональные короткие ссылки пользователей).
- Не указано, где взять число долей поколонок для десктопа для нового блока `.landing-demo` относительно
  `.landing-copy` — просто «в левой колонке под текстом»; реализуемо без изменения текущей grid-разметки
  (см. расчёт DOM-порядка ниже), но стоит явно прописать в плане имплементации, а не полагаться на догадку.
- ADR-018 и правка `security.md` («РОВНО ДВА пути» → «плюс третий, закрытый список, только чтение,
  никаких мутаций/списков клипов пользователя») пока не существуют — блокер только для документации,
  не для кода, но должны появиться в этом же PR, как и просит бриф.

## Обязательные правки

1. **Ретенция (критично).** В шаге «очистка клипов» (`retention.ts`) добавить исключение по
   `SHOWCASE_CLIPS` (например `AND NOT (c.id = ANY($3::uuid[]))` с массивом id витрины, полученным из
   `packages/shared`) — иначе объект клипа `/c/CTDUUG` будет стёрт через 3 дня после
   `video.finished_at`, если план аккаунта не `paid`. Тест: клип из `SHOWCASE_CLIPS` с
   `finished_at` 4 дня назад переживает `retentionTick`; соседний НЕ витринный клип с теми же
   условиями — удаляется (мутация: убрать исключение → тест красный).
2. **Прибор `FIRST_SCREEN_ACTIONS`.** Расширить модель данных до `selector: string | string[]` (или
   параллельный список) в `scripts/responsive/rules.mjs`, обновить цикл в
   `scripts/check-responsive.mjs`, чтобы гонять `firstScreenRule` на каждый селектор `/` отдельно:
   `.landing-cta` (основное действие) и `.landing-demo video` (видимость демо).
3. **`tests/responsive-check.test.ts:169`** — обновить ожидание под новый селектор/структуру данных.
4. **Механизм выдачи файла витрины** — прямой 302 на подписанную ссылку (как путь владельца в
   `clip-file.ts`), НЕ `guestFileTicket`+`deps.stream()` (двойной проброс байт через `web`).
5. **Высота демо** — заложить `video { width: clamp(7rem, 38vw, 9.5rem) }` (постер целиком) как
   отправную точку и подтвердить фактическим скриншотом `first-screen-375x667` перед фиксацией числа
   в документах (расчёт из §3 — оценка по метрике шрифта, не измерение).
6. **Фокус в поле почты** — реализовать программно (клиентский эффект по `location.hash`), не
   полагаться на голый `<a href="#auth">`.
7. **`controls` на `<video>`** — добавить явно (бриф не называл, но без него видео нельзя запустить).
8. **Addendum FR-LOOK-007/011** — явно отметить и объяснить расхождение принятой формулировки FR-LOOK-007
   («поле ссылка + кнопка загрузить файл») с фактической реализацией (auth-форма → демо+CTA-к-форме),
   а не только фиксировать добавление демо.
9. ADR-018 + правка `.claude/rules/security.md` («ровно два пути» → добавить третий, закрытый список,
   read-only, обоснование и граница) — как и просит бриф.
