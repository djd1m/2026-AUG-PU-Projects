Рабочий каталог — корень проекта. Правь только код и тесты; `docs/` не трогай, кроме файла

## Блокер 1 (RV-001) · клиентский адрес берётся из последнего элемента `X-Forwarded-For`

`apps/web/src/server/ip.ts:6` — `headers.get('x-forwarded-for')?.split(',').at(-1)`.

Комментарий в файле предполагает, что перед `web` ровно один прокси (наш Caddy). **Топология
другая, и она записана в самих файлах проекта:** `docker-compose.yml` публикует Caddy на
`127.0.0.1:${N5_EDGE_PORT:-4181}`, а `proxy/Caddyfile` в первых строках объявляет, что TLS
терминирует ВНЕШНИЙ прокси машины. Значит звеньев минимум два, и последний элемент цепочки —
адрес внешнего прокси, одинаковый для всех пользователей.

Следствия, обе — отказ защиты, а не неточность метрики:
- ограничитель частоты вырождается в ОДНО общее ведро 30 запросов в минуту на весь продукт;
  тридцать первый пользователь получает отказ из-за чужой активности;
- `session.ip_prefix` одинаков у всех сессий, и anti-fraud по `ip_prefix` (FR-PARTNER-003,
  уникальность `link_view`/`guest_opened`) в следующих фичах будет считать всех одним человеком.

Это ровно тот дефект, который уже оплачен в соседнем проекте репозитория: правило
`../../.claude/rules/deployment-seams.md`, строка «Обходимый rate limit». Прочитай её.

**Что сделать.** Число доверенных звеньев — ЯВНАЯ конфигурация, а не догадка:
`N5_TRUSTED_PROXY_HOPS` (целое ≥ 1) в `packages/shared/src/config.ts`, объявляется в
`docker-compose.yml` у `web` и в `.env.example`. Клиентский адрес — элемент на позиции
`len - hops` (считая справа, пропуская доверенные звенья); при нехватке элементов — отказ, а не
подстановка первого попавшегося. Значение по умолчанию допустимо (`2` для нашей топологии), но
оно ОБЪЯВЛЕНО и документировано, а не спрятано в выражении `.at(-1)`.

Тест обязателен и должен быть КРАСНЫМ до правки: заголовок
`X-Forwarded-For: 203.0.113.9, 10.0.0.5, 172.18.0.2` при `hops = 2` даёт `203.0.113.9`, при
`hops = 1` — `10.0.0.5`; при `hops = 5` — отказ. Плюс тест ограничителя: 31-й запрос от ПЕРВОГО
адреса отклонён, а первый запрос от ВТОРОГО адреса в ту же минуту — разрешён (сейчас он был бы
отклонён, и это доказывает дефект).

## Блокер 2 (RV-002) · процесс живёт без обязательной переменной

Ревьюер собрал проект и запустил `next start` без `N5_PUBLIC_ORIGIN`: **процесс жив 25 секунд**,
`GET /health` и `POST /api/auth/login` отвечают `500`, Next печатает «error loading instrumentation
hook» и продолжает обслуживать. Комментарий в `apps/web/src/instrumentation.ts:4` утверждает
обратное, а `tests/health.test.ts` зелёный и описывает `503` — поведение, которого у развёрнутой
системы нет.

Инвариант `FR-RENDER-002 @security` и правило `silent-fallbacks.md` требуют, чтобы процесс НЕ
СТАРТОВАЛ. Instrumentation hook Next.js этого не обеспечивает: его исключение не убивает сервер.

**Что сделать.** Проверка конфигурации выполняется ДО запуска сервера, отдельным шагом, который
завершает процесс ненулевым кодом:
- скрипт `apps/web/src/preflight.ts` (собирается в `dist`/`.next/standalone` или запускается через
  `tsx`/скомпилированный js) читает ту же функцию `config.ts`, что и рантайм, и при ошибке печатает
  сообщение с последствием и делает `process.exit(1)`;
- команда запуска `web` становится двухшаговой: `node preflight.js && next start` — и в
  `apps/web/package.json` (`start`), и в `Dockerfile` (цель `web`, `CMD`). Правь `Dockerfile` В ЭТОТ
  РАЗ РАЗРЕШЕНО — только строку `CMD` цели `web`.
- Оставь instrumentation как второй рубеж, но не как единственный.

Тест обязателен и красный до правки: запуск собранного `preflight` без `N5_PUBLIC_ORIGIN` даёт код
выхода ≠ 0 и сообщение с именем переменной; то же для каждой из шести `N5_LIMIT_*` — **шесть
отдельных прогонов**. Тест `tests/health.test.ts`, описывающий `503`, привести в соответствие с
реальным поведением: `503` возможен только при недоступной БД при корректной конфигурации.

## High (RV-003) · ключ ограничителя по полному адресу, чтения не ограничены

Ключ строится из полного IP (`rate-limit.ts:12`), а `Pseudocode.md` (`AuthRegisterAndLogin` шаг 1)
говорит про `ip_prefix` /24. Полный адрес в ключе означает, что смена адреса в пределах подсети
обнуляет счётчик. Перевести ключ на `ipPrefix(clientIp(...))`. Отдельно: ограничены только
мутирующие маршруты; канон §7 требует и 120 чтений в минуту — добавь ведро для чтений либо запиши
в отчёте, почему в этой фиче читающих маршрутов ещё нет (кроме `/health`, который не ограничивается
намеренно — назови это явно).

## Medium, которые закрываем сейчас (остальные — в отчёт как хвост)

1. **`growth_event.ip_prefix` nullable** — оба частичных `UNIQUE` (`link_view`, `guest_opened`)
   обходятся значением `NULL`: `NULL` не конфликтует ни с чем. Architecture отдаёт уникальность
   базе (V2-R12). Сделать колонку `NOT NULL` для этих двух типов событий (частичный `CHECK` либо
   `NOT NULL` целиком, если у остальных типов адрес тоже есть) — решение назови в отчёте.
2. **Пул потоков libuv** — `bcrypt` занимает один из четырёх потоков процесса, `UV_THREADPOOL_SIZE`
   не задан. Пул соединений БД освобождён образцово, а этот разделяемый ресурс не назван никем.
   Задать `UV_THREADPOOL_SIZE` в `docker-compose.yml` у `web` (значение обосновать) и добавить
   конкурентный тест: N одновременных входов не деградируют сверх названного порога.
3. **Страж проброса сверяет `environment.ts`, а не `config.ts`** — переменная, забытая в
   `config.ts`, стражу невидима. Сверять с тем файлом, который объявляет обязательные переменные.
4. **`n5_test` не создаётся ничем в репозитории** — команда из README даёт шесть провалов на чистой
   машине. Добавить создание базы в скрипт (`scripts/test-db.sh` либо шаг в `db:migrate`), чтобы
   `docker compose --profile test run --rm test` работал с нуля.
