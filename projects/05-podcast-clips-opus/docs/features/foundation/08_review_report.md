## Находки

### RV-001 · `blocker` · последний элемент `X-Forwarded-For` в этой топологии НИКОГДА не адрес пользователя

`apps/web/src/server/ip.ts:3-9`

```ts
// Только сеть compose: Caddy добавляет адрес непосредственного клиента справа.
const candidate = headers.get('x-forwarded-for')?.split(',').at(-1)?.trim();
```

Комментарий верен для топологии «браузер → Caddy → web». Проект развёрнут не так, и это записано в
его собственных файлах:

* `proxy/Caddyfile:1-2` — «TLS терминирует **внешний прокси машины** (порт `127.0.0.1:${N5_EDGE_PORT}`)»;
* `docker-compose.yml:142` — `ports: ["127.0.0.1:${N5_EDGE_PORT:-4181}:80"]`, то есть снаружи машины
  контейнерный Caddy недостижим в принципе и перед ним ОБЯЗАН стоять ещё один прокси.

Caddy дописывает в `X-Forwarded-For` адрес того, кто подключился **к нему**, — а к нему подключается
внешний прокси (через петлевую публикацию — с адреса шлюза docker-моста). Значит последний элемент
постоянен для всех пользователей. Продемонстрировано исполнением на самой функции:

```
"203.0.113.9"                      -> 203.0.113.9
"203.0.113.9, 172.18.0.1"          -> 172.18.0.1     ← так будет в бою
"203.0.113.9, 10.0.0.5, 172.18.0.1"-> 172.18.0.1
```

**Два последствия, оба про безопасность:**

1. `rate-limit.ts:12` строит ключ из этого адреса → **все пользователи продукта делят ОДНО ведро
   30 запросов/мин**. Перебор паролей не ограничен ничем (атакующий один, ведро общее и большое
   относительно одного клиента), а любой посетитель 31-м запросом закрывает вход ВСЕМ остальным.
   Это прямое невыполнение критерия приёмки `FR-AUTH-001 @security`: «31-й мутирующий запрос
   **с одного IP** за минуту отклонён», канона §7 («30 запросов/мин **на IP**») и шага 1
   `AuthRegisterAndLogin`.
2. `auth.ts:24` кладёт `ipPrefix(ip)` в `session.ip_prefix` → у всех сессий продукта будет
   `172.18.0.0/24`. Поле, ради которого Pseudocode шаг 5 отдельно оговаривает «полный адрес не
   сохраняется, префикса достаточно», перестаёт содержать что-либо.

Это ровно `deployment-seams.md`: код корректен, `curl` доволен, юнит-тест зелёный
(`tests/auth.test.ts:104` утверждает поведение для ОДНОГО прокси), а условие отказа принадлежит
стыку. Исполнитель риск НЕ скрыл — `07_code_report.md` п. 4 пишет «реальная цепочка внешнего
прокси/XFF требует проверки на стенде». Проверка выполнена чтением топологии: цепочка всегда длиннее
одного звена, поэтому это не риск, а дефект.

**Правка.** Адрес клиента обязан вычислять Caddy, знающий, кому доверять, и передавать его ОДНИМ
заголовком:

```caddyfile
{ servers { trusted_proxies static 172.16.0.0/12 127.0.0.1/32 } }   # глобальный блок
reverse_proxy web:3000 { header_up X-Client-IP {client_ip} }        # {client_ip} уважает trusted_proxies
```

В `ip.ts` читать РОВНО `X-Client-IP`, при отсутствии — отказ (сейчас отказ уже реализован верно,
см. «проверено и верно» №14). `X-Forwarded-For` не читать вовсе: он остаётся клиентским вводом.

### RV-002 · `blocker` · непригодная конфигурация НЕ роняет старт `web` — доказано запуском

`apps/web/src/instrumentation.ts:4`

```ts
getRuntime(); // Ошибка конфигурации завершает запуск до приёма первого запроса.
```

Комментарий неверен. Я собрал проект и запустил `next start` без `N5_PUBLIC_ORIGIN`:

```
>>> ПРОЦЕСС ЖИВ после 25 с — старт НЕ упал
>>> GET /health = 500            (тело: "Internal Server Error", не JSON)
>>> POST /api/auth/login = 500
журнал: Error: An error occurred while loading instrumentation hook:
        N5_PUBLIC_ORIGIN отсутствует: он вшивается в метку каждого клипа… (повторяется на каждый запрос)
```

Next перехватывает исключение из `register()`, пишет его в журнал и **продолжает принимать
запросы**. Три следствия:

1. Критерий приёмки `FR-RENDER-002 @security` — «Then процесс **НЕ стартует** и называет
   ненастроенную переменную» — для `web` НЕ выполнен. Переменную он называет, не стартовать
   отказывается. (Для воркеров выполнен: `loadWorkerConfig` бросает на верхнем уровне модуля,
   процесс завершается кодом 1 — проверено.)
2. `tests/health.test.ts:11` утверждает, что при падении конфигурации `/health` даёт **503**. Живой
   сервер даёт **500**. Тест подменяет `getRuntime` моком и потому проверяет путь, которого в этом
   отказе не существует, а настоящий путь не покрыт ничем. Зелёный тест описывает поведение,
   которого у развёрнутой системы нет.
3. Контейнер остаётся `running` и `unhealthy` бесконечно: `restart: unless-stopped` реагирует на
   ВЫХОД процесса, а не на unhealthy. Наблюдаемо это как «сервис поднят, всё 500», а не как громкий
   отказ старта; `proxy` при этом не стартует вовсе (`depends_on: service_healthy`).

**Правка.** В `instrumentation.ts` перехватить и завершить процесс явно — Next не даёт исключению
сделать это за вас:

```ts
try { getRuntime(); }
catch (error) { console.error(String(error)); process.exit(1); }   // FR-RENDER-002: старт обязан упасть
```

Плюс тест, поднимающий собранный `next start` с непригодным окружением и требующий, чтобы процесс
завершился. Без него правка ляжет на тот же слой 4, на котором дефект и прожил.

### RV-003 · `high` · ограничитель считает по полному адресу, а не по `ip_prefix`; чтения не ограничены вовсе

`apps/web/src/server/rate-limit.ts:12` — ключ `HMAC(полный ip)`. Pseudocode шаг 1 требует

**Правка:** ключ `ipPrefix(ip)`; отдельное ведро 120/мин на `GET`; либо перенести оба в Caddy, как
записано в `security.md` (это решение владельца, а не исполнителя, — см. RV-018).

### RV-004 · `medium` · частичные `UNIQUE` у `growth_event` не дедуплицируют при `ip_prefix IS NULL`

`packages/db/migrations/001_init.sql:113,117,118`

```sql
ip_prefix cidr CHECK (masklen(ip_prefix) = 24),          -- NULL разрешён
CREATE UNIQUE INDEX growth_event_link_view_unique
  ON growth_event (clip_link_id, ip_prefix, day) WHERE type = 'link_view';
```

В PostgreSQL по умолчанию NULL-ы в уникальном индексе считаются РАЗЛИЧНЫМИ. Строка с
`ip_prefix IS NULL` (колонка это допускает) вставится неограниченное число раз, и `ON CONFLICT DO
NOTHING` промолчит. Architecture прямо отдаёт эту гарантию базе: «уникальные переходы и открытия
считает **база** (V2-R12)». Сейчас база считает их только тогда, когда значение не NULL, — то есть
ровно в том случае, который никто не проверял. Интеграционный тест
(`tests/database.integration.test.ts:66-79`) вставляет только `'192.0.2.0/24'` и этой дыры не видит.

**Правка:** `NULLS NOT DISTINCT` (PostgreSQL 16 это поддерживает) либо `CHECK (type NOT IN
('link_view','guest_opened') OR ip_prefix IS NOT NULL)`, плюс тест с NULL-префиксом.

### RV-006 · `medium` · страж проброса сверяет compose с `environment.ts`, а не с требованиями `config.ts`

`scripts/check-env-wiring.mjs:33-63` собирает имена из обращений `process.env.X` по графу импортов.
Для `web` все такие обращения живут в одном файле — `apps/web/src/server/environment.ts`, который
руками перечисляет 11 имён. Требования же объявлены в другом месте: `packages/shared/src/config.ts`
(`required(env,'SESSION_SECRET',…)`, `LIMIT_NAMES`, `url(env,'DATABASE_URL',…)`).

Отсюда слепое пятно: если завтра в `config.ts` появится `required(env,'S3_ENDPOINT',…)`, а в
`environment.ts` строку добавить забудут, страж не найдёт ни одного `process.env.S3_ENDPOINT` в
графе `web`, отчитается «потерь нет» и выйдет 0 — при том что процесс упадёт на старте. Корневое
правило предупреждает ровно об этом: «не опирается на `.env.example` — на прогоне он сам был
неполон»; здесь роль неполного файла играет `environment.ts`.

**Правка:** детерминированный тест «множество имён `environment.ts` == множество имён, которые
читает `loadWebConfig`» (второе извлекается из `LIMIT_NAMES` + литералов `required`/`url` разбором
`config.ts`, как уже делает `checkSqlEnums` для SQL).

### RV-008 · `medium` · пул соединений освобождён, но следующий разделяемый ресурс не назван — пул потоков libuv

Pseudocode шаг 2а разбирает ОДИН разделяемый ресурс (пул соединений) и требование выполнено
безупречно (см. «проверено и верно» №5–6). Но `bcrypt.hash`/`bcrypt.compare` асинхронной формы
выполняются в **пуле потоков libuv**, по умолчанию ровно **4 потока** на процесс, и удерживают поток
на всё время хэширования (~50–100 мс при cost 10). `UV_THREADPOOL_SIZE` нигде не задан, потолка
одновременных хэширований нет.

Четыре вопроса `shared-resource-verification.md`: удерживается поток пула на десятки миллисекунд;
всего их 4; в очереди за тем же пулом стоят `fs` и `dns` **всего процесса Next**, то есть отдача
статики и любой резолв имени; при насыщении страдают все маршруты. Ограничитель частоты этот ресурс
не защищает: он считает на ключ, а пул один на процесс — N разных ключей по 30 запросов/мин
складываются свободно.

Это ровно тот рецидив, который правило и описывает: правку проверили на дефекте, ради которого её
писали (пул БД), а соседний разделяемый ресурс не проверил никто. Интеграционный тест
«12 сравнений bcrypt не удерживают 4 соединения пула» (строка 40) мокает `bcrypt.compare` и потому о
пуле потоков ничего сказать не может.

**Правка:** назвать число (семафор на одновременные `bcrypt`, `UV_THREADPOOL_SIZE` явным значением в
compose) и конкурентный тест «N одновременных входов не увеличивают задержку отдачи `/`».

`bcrypt.hash` к тексту `persistence` — она доказывает способность упасть ТОЛЬКО у первого. Три
остальных ни разу не показывали красное внутри набора. `guard-must-be-able-to-fail`: непроверенное
утверждение стража — не страж. (В `07_code_report.md` заявлены мутации `pool.connect`/`BEGIN`/
`COMMIT`; их квитанции лежат в `tests/artifacts/foundation/*-red.txt`, но в самом наборе они не
воспроизводятся, а значит и не защищены от исчезновения при рефакторинге.)

### RV-013 · `low` · ветка IPv6 в `ipPrefix` никогда не встречалась с колонкой `cidr`

`ip.ts:14-19` собирает строку вида `2001:d00::/24`, а для `::1` — `0:0::/24`
(`tests/auth.test.ts:106-107`). Оба значения утверждены только юнит-тестом на строке; ни один
интеграционный тест не вставляет IPv6-префикс в `session.ip_prefix cidr CHECK (masklen = 24)`.
Приемлемость литерала `0:0::/24` для типа `cidr` остаётся непроверенной, а это путь входа любого
пользователя по IPv6. Сама маска (`& 0xff00` на второй группе) арифметически верна — я проверил.

### RV-014 · `low` · повторная регистрация выдаёт cookie, который ничего не авторизует

`auth.ts:27-33`: `register` возвращает `session.token` независимо от того, вставился ли аккаунт;
при занятом адресе `INSERT … ON CONFLICT DO NOTHING` не даёт строки, сессия не создаётся, а cookie
всё равно ставится. Это **соответствует** Pseudocode шаг 3 («наружу отдаётся ТЕМ ЖЕ ответом, что и
успех») и защищает от перечисления адресов. Последствие, которого документы не рассматривали:
владелец существующего аккаунта, повторно нажавший «зарегистрироваться», получает экран «готово» и
оказывается неаутентифицированным на следующей странице. Стоит явного решения на экране, а не в коде.

### RV-015 · `low` · `session.last_seen_at` не пишется никогда

Колонка объявлена `NOT NULL DEFAULT now()` (SQL строка 17) и присутствует в Pseudocode, но
`findSession` (`auth-store.ts:32-36`) её не двигает. Сейчас это «время создания» под чужим именем.

### RV-016 · `low` · `retryStrategy: () => null` превращает каждый сбой Redis в переподключение на запрос

`runtime.ts:13-14`. После разрыва ioredis не восстанавливает соединение сам; `allowMutation`
(`rate-limit.ts:10`) зовёт `redis.connect()` при статусе `end`. Поведение fail-closed верное (отказ,
а не пропуск), но при недоступном Redis каждый запрос платит до 2 с `connectTimeout`, и очередь
ожидающих растёт.

### RV-017 · `low` · `SESSION_SECRET` используется как ключ и для сессий, и для ключей ограничителя

`auth.ts:21` и `rate-limit.ts:12` берут один секрет для двух разных назначений. Разделение ключей
дешевле починить сейчас (`HMAC(secret, 'rate')` как производный ключ), чем после ротации.

### RV-018 · `low` · `proxy` вне профиля по умолчанию, ограничителя в Caddy нет

Канон §6: «ровно 7 сервисов в боевом профиле (web, три воркера, db, redis, **proxy**)»; в compose
`proxy` объявлен `profiles: ["edge"]` (строка 140), то есть `docker compose up` поднимает шесть.
README:64 документирует `--profile edge`, поэтому это расхождение формулировок, а не дефект. Вторая
половина серьёзнее и уже отмечена исполнителем: `security.md` помещает лимит частоты в Caddy, в
`Caddyfile` его нет, реализация в приложении. Класс отказа закрыт (кроме RV-001/RV-003), но не там,
где записано. Это решение владельца: подтвердить размещение в приложении и поправить `security.md`
либо перенести в прокси.

## Вердикт: **ВЕРНУТЬ**

Работа сделана на высоком уровне: порядок операций соблюдён там, где он несущий; fail-closed
реализован фактически, а не на словах; стражи в большинстве испытаны мутацией; исполнитель нашёл и
назвал два дефекта в самих документах-источниках (17 причин, `UNKNOWN` в `CHECK`) вместо того чтобы
подогнать код под ошибочный текст. Тридцать две проверенные позиции против восемнадцати находок —
это не список претензий.

Возврат узкий и вызван двумя находками, каждая из которых делает НЕВЫПОЛНЕННЫМ именной критерий
приёмки `@security` из `Specification.md`:

* **RV-001** — `FR-AUTH-001`: «31-й мутирующий запрос с одного IP» неисполним, потому что «одного
  IP» в этой топологии не существует; заодно обнуляется `session.ip_prefix`.
* **RV-002** — `FR-RENDER-002`: «процесс НЕ стартует» — стартует, доказано запуском.

По `feature-lifecycle.md` находка `blocker` обязана быть закрыта до слияния, поэтому «принять с
правками» здесь было бы подменой. Обе правки малы (несколько строк в `ip.ts` + `Caddyfile` и
`try/catch` + `process.exit(1)` в `instrumentation.ts`), но обе обязаны приехать **вместе с тестом,
который до правки красный** — иначе они лягут на тот же слой, на котором дефекты и прожили.

Рекомендуемая очередь второго раунда: RV-001, RV-002 (блокирующие) → RV-003, RV-004, RV-009
(дешёвые и с ясной правкой) → RV-005…RV-008 → `low` пакетом. RV-018 — не правка, а решение
владельца.
