## По находкам

| Находка | Вердикт и решение |
|---|---|
| RU-001 | **Исправлено в коде.** Убрано общее ограничение запроса из S3-клиента. У Complete константа `COMPLETE_REQUEST_TIMEOUT_MS = 300_000` рядом с вызовом: пять минут на команду, включая до трёх попыток SDK и чтение тела после HTTP 200. `requestTimeout` дополняется `AbortSignal.timeout`, потому что установленный Smithy снимает первый таймер после заголовков. HEAD/ListParts/Create/Abort/Delete имеют короткий таймаут 5 с; Range также имеет общий дедлайн 5 с. Подпись локальная, с фиксированными credentials, сетевого ожидания нет. При ошибке Complete проверяется HEAD; если объекта пока нет, возвращается 503, запись остаётся `uploading`, multipart не удаляется, повтор тем же ключом разрешён. Повтор уже поставленного `queued` также возвращает результат без повторного списания. Caddy `read_timeout` увеличен с 60 до 360 с. |
| RU-002 | **Исправлено в коде; реальный конкурентный прогон не выполнен.** Короткая транзакция заявляет ключ, сохраняет object_key/размер части и списывает квоту, затем освобождает соединение. Initiate/List/Sign выполняются отдельно. Условный `UPDATE … upload_id IS NULL` выбирает один upload_id; проигравший убирает свой multipart. Ошибка подписи оставляет сохранённый upload_id доступным для повтора. Complete/HEAD/Range идут без соединения БД; короткая финальная транзакция повторно читает строку с `FOR UPDATE`, проверяет статус/upload_id и атомарно фиксирует failed+refund либо queued. Enqueue и очистка идут после COMMIT. Добавлены сценарии N=1 и N=10, pool max=10 для initiate, sign, complete, head и bytes: idle-in-transaction=0, посторонний SELECT <500 мс. Это критерии теста, **не полученные измерения**. |
| RU-003 | **Исправлено.** Потолок 2 000 000 000 байт и срок 900 с сохранены. Повтор create делает ListParts с пагинацией, возвращает ETag завершённых частей и ссылки только на отсутствующие номера. Браузер отправляет до трёх PUT одновременно, сохраняет подтверждения и принимает callback `refresh`, повторяющий create с исходным ключом. Истечение ссылки/403 вызывает обновление; максимум два обновления для одной проблемной части, отмена останавливает повтор. Отправленные части заново не отправляются. URL и заголовки подписи не меняются. Это библиотечный контракт существующей фичи; браузерный E2E и реальная передача 2 ГБ не проведены. |
| RU-004 | **Исправлено в коде; PostgreSQL-проверка ожидает среды.** И лимит возвратов, и уменьшение uploads относятся к `upload_day`, сохранённому при создании заявки. Вчерашняя загрузка не тратит сегодняшнее право и не уменьшает сегодняшние загрузки. При пустом декременте savepoint откатывает расход права возврата. Вчерашний возврат не выдаёт дополнительный слот сегодня: дневные потолки не менялись. |
| RU-005 | **Не исправлено сейчас; перенесено в `retention-and-erasure`**, как разрешает 08_review_report. Конкретный контракт: отказанные `failed/refused_user_uploads` заявки хранятся 24 часа; обслуживание удаляет их не реже одного раза в час (задержка до 25 часов), с частичным индексом по created_at для таких строк. До реализации этой фичи очистителя нет, бессрочный рост этих строк остаётся известным дефектом. Это запись обязательства в разрешённом отчёте, а не заявление о работающем расписании. |
| RU-006 | **Исправлено.** Раздельные HMAC-ключи `account:<id>` и `anonymous:<prefix>`, каждый 30/мин. Upload определяет сессию коротким чтением, применяет лимит до чтения тела; logout также использует аккаунт действующей сессии. Login/register и запросы без действующей сессии остаются в анонимном ведре IPv4 /24 или IPv6 /64. Один аккаунт не получает новое ведро при смене IP, другой аккаунт за NAT независим. |
| RU-007 | **Исправлено в миграционном коде; реальное применение не проверено.** Добавлена `003_ipv6_legacy_cleanup.sql`, сортирующаяся до 004. Она удаляет только старые IPv6-префиксы с маской не /64 в session/growth_event; IPv4 сохраняется. Потерянные биты /64 нельзя достоверно восстановить из /24. Потребуется повторный вход старых IPv6-сессий; старые приблизительные growth events теряются. Уже применённая 004 и её SHA не меняются. На базе с 004 новая очистка — no-op. Добавлен upgrade-тест: миграции 001–003 → старые строки /24 → полный migrate → повтор migrate → новая /64. |
| RU-008 | **Исправлено.** Abort и Delete очищаются независимо, каждая ошибка журналируется без URL/секретов. Отказ abort не препятствует delete и не заменяет исходный 422. Повтор complete повторяет очистку без второго возврата. Локальный поведенческий тест и мутация прошли; конкурентный вариант на БД подготовлен. |
| RU-009 | **Исправлено альтернативным механизмом; применение lifecycle в Cloud.ru не проверено.** Перед CreateMultipartUpload код запрашивает lifecycle бакета и требует включённый AbortIncompleteMultipartUpload через 1 день, покрывающий весь бакет. Отсутствие правила, доступных метаданных или права GetBucketLifecycleConfiguration запрещает создание. Потерянный UploadId оставляет durable-заявку с object_key и upload_id=NULL; повтор не списывает квоту снова. Известные проигравшие CAS upload_id отменяются отдельно. Предложение «присвоить initiated до вызова и вызвать abort» **отклонено как технически невозможное без UploadId**. Серверный lifecycle покрывает неизвестные ID, включая сирот SDK-ретраев и аварий процесса. Через день загрузка становится кандидатом на очистку; точное время физического удаления зависит от хранилища. |
| RU-010 | **Исправлено этим отчётом.** Названы последствия сетевого таймаута, состояние повтора, пределы ожидания, недоказанные интеграционные свойства и условия запуска lifecycle. Старые отчёты не переписаны. |

Пять минут выбраны как ограниченный операционный бюджет для склейки до 2 ГБ / около 100 частей,
а не как измеренный SLA. AWS прямо допускает минуты на
[CompleteMultipartUpload](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CompleteMultipartUpload.html).
После исчерпания бюджета файл остаётся повторяемым. Абсолютная гарантия успешной загрузки при любой
скорости связи не заявляется: теперь исчезает общий барьер 900 с на весь файл, но отдельная часть
всё ещё зависит от связи и срока своей ссылки.

Для RU-009 интерфейс
[AbortMultipartUpload](https://docs.aws.amazon.com/AmazonS3/latest/API/API_AbortMultipartUpload.html)
требует UploadId; страховка неизвестного ID —
[lifecycle незавершённых multipart](https://docs.aws.amazon.com/AmazonS3/latest/userguide/abort-mpu.html).
Код не меняет настройки боевого бакета автоматически. В MinIO-фикстуре правило задаётся только в
тестовом бакете. Перед эксплуатацией нужны правило и право его чтения; иначе новые загрузки
предсказуемо отказывают, вместо создания неограниченно живущих сирот.
