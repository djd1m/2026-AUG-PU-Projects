## Находки

### RU-001 · blocker · загрузка уничтожается таймаутом завершения, слот не возвращается, повтор невозможен

**Файл:** `packages/s3/src/client.ts:11`, последствие — `apps/web/src/server/video.ts:101-113`.

```ts
// client.ts:9-11
maxAttempts: 3,
// Ограничиваем удержание соединения БД во время операции хранилища.
requestHandler: { connectionTimeout: 2000, requestTimeout: 5000, throwOnRequestTimeout: true },
```

`requestTimeout: 5000` — общий для клиента, то есть действует и на `CompleteMultipartUploadCommand`.
AWS прямо документирует, что обработка Complete может занимать **несколько минут**: хранилище
собирает объект из частей, а не подтверждает метаданные. Для 2 000 000 000 байт это 100 частей по
20 МБ.

**Измерено** (probe A, медленный HTTP-эндпоинт вместо S3):

```
A: elapsed_ms= 15092  error= TimeoutError
   @smithy/node-http-handler - [ERROR] a request has exceeded the configured 5000 ms requestTimeout.
```

15 092 мс — это `maxAttempts: 3` × 5 000 мс: SDK ещё и **повторяет** завершение трижды.

Что делает код дальше (`video.ts:101-113`): исключение не `UploadTooLarge` → `HEAD` объекта. Пока
хранилище объект собирает, `HEAD` даёт 404 → `abort` живой сборки + `status='failed',
failure_reason='stalled'`. `'stalled'` **не входит** в `FILE_FAILURES` (`quota.ts:41`), значит
возврата слота нет. Повтор упирается в `video.ts:98` (`status !== 'uploading'`) → 409.

**Измерено** (probe D, полный путь на настоящем PostgreSQL):

```
D: {"first":{"code":"unavailable","status":503},
    "row":{"status":"failed","failure_reason":"stalled"},
    "uploads_used":1,
    "retry":{"code":"conflict","status":409,"msg":"Загрузка уже завершена"}}
```

Повтор выполнялся против **здорового** хранилища — и всё равно 409.

**Почему дефект.** Пользователь отдал 2 ГБ своего канала (при 20 Мбит/с — четверть часа), файл в
хранилище **целый**, а продукт объявляет его потерянным, сжигает один из двух суточных слотов и
не даёт повторить. Это ровно то наказание добросовестного пользователя, против которого написан
DEC-A-014 («пользователь наказан за то, что его файл не подошёл, а не за использование продукта»,
`Pseudocode.md` шаг 5а) — только здесь файл подошёл. `Pseudocode.md` CompleteUpload шаг 3 разрешает
`failed` при отказе ХРАНИЛИЩА; клиентский таймаут на здоровом хранилище отказом хранилища не
является. Зелёные тесты этого не видят: MinIO завершает объект в 24 байта мгновенно.

**Правка.** (1) Снять общий `requestTimeout` с завершения: задавать его покомандно
(`client.send(cmd, { requestTimeout })`) либо отдельным клиентом для Complete с потолком, взятым из
максимального размера файла, а не из желания сократить транзакцию. (2) Сделать `stalled`
восстановимым: при `stalled` разрешать повтор `complete` (как уже сделано для
`queued && !upload_enqueued_at`, `video.ts:93`), либо включить его в возврат слота. Одно без другого
не закрывает: без (1) таймаут будет срабатывать, без (2) каждый срабатывает необратимо.

### RU-002 · blocker · сетевые вызовы S3 выполняются ВНУТРИ транзакции БД; десять одновременных загрузок кладут сайт

**Файл:** `apps/web/src/server/video.ts:36-70` (создание) и `video.ts:89-120` (завершение).

```ts
// create: внутри transaction(this.pool, async (tx) => { ... })
const uploadId = await this.storage.initiate(objectKey);            // video.ts:64  — сеть
const parts = await this.storage.sign(objectKey, uploadId, ..., now); // video.ts:66

// complete: внутри transaction(...), строка video взята FOR UPDATE (video.ts:90)
await this.storage.complete(row.object_key, row.upload_id, body.parts); // video.ts:101 — сеть
const bytes = await this.storage.head(row.object_key);                  // video.ts:114 — сеть
if (!isAllowedMedia(await this.storage.bytes(row.object_key)))          // video.ts:117 — сеть
```

**Измерено** (probe B, настоящий PostgreSQL, `pg_stat_activity` во время висящего `initiate`):

```
B: states= [{"state":"idle in transaction","held":{"seconds":1,"milliseconds":507.373}}]
```

**Измерено** (probe E, пул `max: 10` как в `packages/db/src/index.ts:6`, десять одновременных
`create` с висящим `initiate`, затем посторонний `SELECT 1`):

```
E: {"unrelated_query_error":"timeout exceeded when trying to connect","waited_ms":3001}
```

**Почему дефект.** `statement_timeout: 5000` не ограничивает `idle in transaction` — он про
оператор, а между операторами соединение просто удерживается. Пул `web` **общий с входом в
систему** (`runtime.ts:10-16`: `pool` отдаётся и `PgAuthStore`, и `VideoService`), поэтому
исчерпание пула десятью загрузками гасит и логин, и все страницы. Десять одновременных загрузок —
не нагрузочный сценарий, а обычный вечер.

Инвариант написан в документах ЭТОГО проекта и нарушен против собственного текста:

> `docs/Architecture.md:140-142` — «хэширование и проверка выполняются **ВНЕ транзакции БД** —
> десятки миллисекунд на попытку не должны держать соединение пула, правило
> `shared-resource-verification.md`».

Десятки миллисекунд bcrypt объявлены недопустимыми; сюда положен сетевой вызов, способный держать
соединение 15 секунд (RU-001, измерено). Корневые правила — `security-operation-order.md` («Сетевой
вызов ↔ транзакция → вызов ВНЕ транзакции») и `shared-resource-verification.md` вопрос 1 («время,
которым управляет не вы, — всегда красный флаг»).

**Отдельно стоит назвать механику появления дефекта.** Комментарий `client.ts:10` — «Ограничиваем
удержание соединения БД во время операции хранилища» — показывает, что автор проблему ВИДЕЛ и
выбрал лечить её таймаутом вместо выноса вызова. Полученный таймаут и есть RU-001. Это в точности
`shared-resource-verification.md`: «каждая ревизия вносила дефект того же класса, что чинила».
Поэтому правка одна на две находки.

**Правка.** Разбить обе процедуры на транзакции, между которыми хранилище вызывается БЕЗ
удерживаемого соединения:
- `create`: транзакция 1 — заявка ключа + списание `user_uploads` + `status='initiating'`, COMMIT;
  затем `initiate`+`sign` вне транзакции; транзакция 2 — записать `upload_id`/`parts`/`status='uploading'`.
  При падении между ними компенсация уже есть по смыслу: строка в `initiating` без `upload_id`
  повторяется по тому же идемпотентному ключу. Порядок «квота ДО ссылок» при этом сохраняется —
  а именно его требует `Architecture.md:138`, не «в одной транзакции».
- `complete`: взять строку, пометить переход, COMMIT; вызвать `complete`/`head`/`bytes` вне
  транзакции; транзакция 2 — `queued` либо `failed`+`RefundUploadSlot` атомарно (требование
  `Pseudocode.md` шаг 5а про «ту же транзакцию» относится к паре failed+refund, а не к вызовам S3,
  и оно сохраняется).

### RU-003 · high · при сроке ссылки 900 с и последовательной отправке заявленный потолок 2 ГБ недостижим

**Файлы:** `packages/shared/src/upload.ts:3` (`PRESIGNED_SECONDS = 900`),
`packages/s3/src/multipart.ts:10` (`Math.max(10 MiB, ceil(fileSize/100))`),
`apps/web/src/lib/upload-parts.ts:7-21` (цикл `for … of`, строго последовательный).

Арифметика: для 2 000 000 000 байт размер части = 20 000 000, частей 100, все ссылки подписаны
**одним** `now` (`video.ts:66`) и истекают одновременно через 900 с. Чтобы успеть, нужен устойчивый
исходящий канал 2 000 000 000 / 900 = 2,22 МБ/с ≈ **17,8 Мбит/с**. Ниже этого — часть ссылок
протухает посреди отправки, `upload-parts.ts:8` бросает «Срок ссылки истёк».

Восстановление формально есть: повтор `video.create` с ТЕМ ЖЕ ключом переподписывает
(`video.ts:49-52`). Но переподписываются **все** номера, включая уже загруженные
(`Math.ceil(declared_bytes / upload_part_size)`), а `uploadParts` начинается с первой части — то
есть медленный пользователь отправляет 2 ГБ заново и снова не успевает. Отчёт это признаёт
(«список недостающих частей для UI возобновления в этой фиче не реализован»), но признание не
закрывает: контракт возобновления живёт в `video.create`, то есть в ЭТОЙ фиче.

`INS-024-upload-slow-codespace.md` — это ровно те же грабли, и «оплачены» они были снятием потолка
части, а не сроком ссылки.

**Правка.** Срок 900 с трогать нельзя (NFR-SEC-001), поэтому ответ — возобновление: повторный
`video.create` по тому же ключу обязан вернуть **список недостающих частей** (`ListParts` даёт его
напрямую) и подписывать только их; `uploadParts` принимает этот список. Дополнительно — отправлять
части с небольшой конкурентностью (3–4), что само по себе убирает большую часть случаев.

### RU-004 · medium · возврат слота через сутки тратит сегодняшнее право, а уменьшает вчерашний счётчик

**Файл:** `packages/db/src/quota.ts:43-50`, вызов `apps/web/src/server/video.ts:81`.

```ts
const allowance = await checkAndConsumeQuota(tx, limits, account, 'upload_refund', 1, now); // сутки now
const result = await tx.query(`UPDATE quota_counter SET used = used - 1
  WHERE scope = 'user_uploads' AND scope_key = $1 AND day = $2 AND used > 0 ...`, [account, uploadDay]);
```

Право тратится за **текущие** московские сутки, а уменьшается счётчик за `upload_day` — сутки
создания загрузки. Пока это одни сутки, всё верно. Когда пользователь завершает вчерашнюю загрузку
сегодня — расходятся.

**Измерено** (probe C, настоящий PostgreSQL; вчера — одна загрузка, сегодня — две, потолок выбран):

```
C: {"returned":true,"refunds_today":1,"uploads_yesterday":0,"uploads_today":2}
```

Право возврата за сегодня потрачено, вчерашний счётчик уменьшен с 1 до 0 (вчерашние сутки уже
прошли — это ничего не даёт), сегодняшний счётчик остался 2. **Пользователь по-прежнему заблокирован
и вдобавок лишился одного из двух суточных прав возврата.**

Это опрокидывает названную причину DEC-A-014: «два слишком больших файла подряд сжигали бы оба
суточных слота, не дав ни одного клипа». Через границу суток именно это и происходит.

Отчёт решение упоминает («старый файл не уменьшает чужой счётчик нового дня»), но называет только
половину — что счётчик чужого дня цел; что право текущего дня при этом сгорает впустую, не сказано.

**Правка.** Либо уменьшать счётчик ТЕКУЩИХ суток (тогда возврат осмыслен, а «чужой день» —
осознанная цена, названная в решении), либо не тратить право, когда `UPDATE` вернул пусто/чужой
день, — сейчас `refundUploadSlot` возвращает `false`, но списанное право не откатывает
(`quota.ts:50`: нет `ROLLBACK TO SAVEPOINT` при неудачном декременте). Второе — минимум, первое —
ответ по существу; выбор владельца канона, потому что это правка числа в канонe, а не рефакторинг.

### RU-005 · medium · каждая отказанная попытка создаёт постоянную строку `video`, потолка нет

**Файл:** `apps/web/src/server/video.ts:38-41, 56-60`.

Заявка ключа (`INSERT … status='uploading'`) выполняется ДО проверки квоты; при отказе строка
переводится в `failed/refused_user_uploads` и транзакция **фиксируется** — иначе повтор по тому же
ключу не вернул бы тот же отказ (`Pseudocode.md` CreateVideo шаг 4 этого и требует). Подтверждено
тестом `tests/upload.integration.test.ts:126-133` («остальные failed/refused»).

Следствие: число строк `video` на аккаунт в сутки ограничено **не квотой**, а только ограничителем
частоты — 30 мутаций в минуту на префикс IP (`rate-limit.ts:14`), то есть до ~43 000 строк в сутки
с одного /24. Срока хранения у этих строк нет, чистильщика нет.

**Почему дефект, хотя поведение предписано.** Предписана идемпотентность отказа, а не бессрочное
хранение мусора. Отказ по квоте — единственная запись, которую может породить пользователь СВЕРХ
своего потолка, и именно у неё нет границы.

**Правка.** Частичный индекс + удаление отказов старше суток (после прохождения границы суток
повтор по старому ключу уже бессмыслен: новая попытка требует нового ключа), либо `deleted_at` по
расписанию. Достаточно строки в фиче обслуживания, но число должно быть названо здесь.

### RU-006 · medium · один ограничитель на вход и на загрузку, ключ только по префиксу IP

**Файл:** `apps/web/src/server/rate-limit.ts:10-15`; диффом ключ переименован
`n5:auth:rate:` → `n5:mutation:rate:` и теперь общий для `route.ts:10` (вход/регистрация/выход) и
`upload-handler.ts:11` (`video.create`, `upload/complete`).

Расширение на мутирующие процедуры постановка требовала. Незаданный вопрос — **гранулярность
ключа**: 30 в минуту делятся на весь /24 (IPv4) или /64 (IPv6). За одним корпоративным NAT или
CGNAT это десятки живых людей в общем ведре; при насыщении механизм наказывает добросовестных, а не
атакующего — `shared-resource-verification.md`, вопрос 4. Тот же класс, что RV-001, за который уже
заплачено.

Денежный потолок при этом в порядке: он привязан к аккаунту (`user_uploads`), а не к IP, — требование
`model-call-cost.md` («предел НА ПОЛЬЗОВАТЕЛЯ обязан уметь связать») выполнено. Поэтому medium, а не
выше: ломается доступность, не деньги.

**Правка.** Для аутентифицированных мутаций ключ по `account_id`, для анонимных — по префиксу IP.
Два ведра, не одно.

### RU-007 · low · миграция 004 отказывает на базе, где уже лежит IPv6-префикс /24

**Файл:** `packages/db/migrations/004_ipv6_prefix_masklen.sql:15-19`.

`ADD CONSTRAINT … CHECK` проверяет существующие строки. Старый `ipPrefix` выдавал IPv6 как
`2001:d00::/24` — семейство 6, маска 24, новому ограничению не удовлетворяет.

**Измерено** (probe, настоящий PostgreSQL):

```
A: вставка /64 под ограничением 001 -> session_ip_prefix_check      (миграция 004 действительно несущая)
B: 004 ОТКАЗАЛА на существующей строке 2001:d00::/24 ->
   check constraint "session_ip_prefix_check" of relation "session" is violated by some row
```

Первая строка — ответ на вопрос постановки «есть ли тест, который упал бы без неё»: да,
`tests/database.integration.test.ts:67-70` вставляет сессию с `2001:db8:1234::1`, и без 004 вставка
отвергается. Миграция обоснована и корректна по существу.

Вторая строка — риск развёртывания. `migrate()` оборачивает прогон в одну транзакцию
(`migrate.ts:9-24`), поэтому отказ 004 валит **всю** миграцию и деплой. Сегодня это недостижимо:
`foundation` нигде не развёрнут, IPv6-строк нет. Поэтому low — но комментарий самой миграции
(строка 12, «удалить строки с IPv6-префиксами») показывает, что категория известна, а шага данных
нет.

**Правка.** Перед `ADD CONSTRAINT` — `DELETE FROM session WHERE family(ip_prefix)=6 AND
masklen(ip_prefix)<>64;` и то же для `growth_event` (сессии восстанавливаются входом, счётчики
роста — приближение), либо `ADD CONSTRAINT … NOT VALID` + отдельный `VALIDATE` после очистки.

### RU-008 · low · отказ `abort` до `delete` оставляет объект в бакете и подменяет 422 на 503

**Файл:** `apps/web/src/server/video.ts:122-126`.

```ts
await this.storage.abort(outcome.objectKey, outcome.uploadId);
await this.storage.delete(outcome.objectKey);
throw outcome.error;
```

`abortMultipartUpload` намеренно не глушит инфраструктурные ошибки (`multipart.ts:46` — и это
правильно). Но если он бросит, `delete` не выполнится, а наружу уйдёт не `UploadError`, значит
`uploadFailure` отдаст 503 «Загрузка временно недоступна» — при том, что в базе уже лежит
`failed(not_media)` и возврат слота уже зафиксирован. Пользователь видит «попробуйте позже» вместо
«файл не является видео».

Самолечение есть: повтор `complete` попадает в ветку `video.ts:94-97` и доделает очистку без
второго возврата. Поэтому low, но первый ответ пользователю неверен.

**Правка.** Обе операции очистки — в `try/catch` с журналированием; наружу отдавать `outcome.error`
независимо от их исхода.

### RU-009 · low · клиентский таймаут `initiate` оставляет висящую multipart-загрузку

**Файл:** `apps/web/src/server/video.ts:64-65`.

```ts
const uploadId = await this.storage.initiate(objectKey);
initiated = { key: objectKey, id: uploadId };   // присваивается ТОЛЬКО после успеха
```

Если `initiate` оборвётся по `requestTimeout` (2 000/5 000 мс, RU-001), хранилище могло загрузку уже
создать — таймаут клиентский. `initiated` остаётся `undefined`, компенсирующий `abort`
(`video.ts:73`) не вызывается. Объект-сирота живёт до правила жизненного цикла бакета, которое в
чек-листе развёртывания названо, но не применено.

**Правка.** Ставить `initiated` до вызова (ключ известен заранее) и в компенсации глушить
`NoSuchUpload` — он там уже глушится (`multipart.ts:46`).

### RU-010 · low · отчёт называет механизм, но не его последствие

`07_code_report.md` честно перечисляет `maxAttempts: 3`, `requestTimeout: 5000` и объясняет
назначение («Ограничиваем удержание соединения БД»). Не сказано ни слова о том, что тот же потолок
действует на `CompleteMultipartUpload`, и что `stalled` не возвращает слот и не допускает повтора

## Вердикт

**Вернуть.**

Два blocker, и оба про один стык: сетевой вызов хранилища выполняется внутри транзакции БД
(RU-002), а выбранное лечение этого — общий пятисекундный потолок запроса — превращает штатное
долгое завершение multipart в необратимую потерю загрузки вместе со слотом (RU-001). Обе измерены
исполнением, обе невидимы на MinIO и обе бьют по тому, ради чего фича помечена XL: по деньгам и по
доверии пользователя к тому, что его файл не исчезнет.

Правка у них общая и локальная — разнести транзакции и убрать потолок с завершения. Всё остальное в
фиче сделано на уровне, который я не смог опровергнуть: форма списания, порядок, идемпотентность,
возврат слота, граница файла, владение, перенос из клона и конкурентные тесты проверены исполнением
и оказались верны. Это возврат на правку, а не отклонение работы.

К исправлению обязательны: **RU-001, RU-002** (blocker), **RU-003** (high — без ответа о
возобновлении объявленный потолок 2 ГБ остаётся обещанием, которое продукт не держит).
RU-004, RU-005, RU-006 — решение владельца канона, потому что затрагивают числа и тексты канона.
RU-007…RU-010 — в рабочем порядке.

Повторное ревью после правок обязано включать прогон на объекте, который хранилище завершает
дольше пяти секунд: без него RU-001 закрыть нечем.
