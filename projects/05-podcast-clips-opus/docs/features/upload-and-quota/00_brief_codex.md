# Постановка для Codex — фича 2 `upload-and-quota`

Рабочий каталог — корень проекта. Фундамент (`foundation`) готов и закоммичен: монорепо из пяти
workspace, миграция 15 сущностей, конфигурация с отказом при старте, вход по паролю, 91 тест
зелёный на настоящих PostgreSQL/Redis/MinIO. Ты продолжаешь эту базу, а не начинаешь заново.

**Тир XL по локальному роутеру сложности: фича трогает деньги** (платные вызовы ограничиваются
именно здесь). Каждое числовое решение берётся из канона, не изобретается.

## Пункт 0 — правка предыдущей фичи, делается ПЕРВОЙ

`apps/web/src/server/ip.ts` → `ipPrefix` усекает IPv6 до /24. Проверено исполнением:
`ipPrefix('2001:db8:1234::1')` и `ipPrefix('2001:db8:9999:abcd::5')` дают ОДИН И ТОТ ЖЕ
`2001:d00::/24`. Маска в 24 бита у 128-битного адреса — это аллокация регистратора, а не абонент:
несвязанные пользователи попадают в одно ведро ограничителя, то есть воспроизводится блокер
RV-001 на IPv6-трафике.

Решение владельца канона DEC-A-019: **IPv4 → /24, IPv6 → /64**. Канон §7 уже обновлён.
Тест обязателен и красный до правки: два разных `2001:db8:1234::1` и `2001:db8:9999:abcd::5`
дают РАЗНЫЕ префиксы; `2001:db8:1234:5678::1` и `2001:db8:1234:5678:ffff::9` — ОДИН.

## Что построить

### 1. `packages/s3` — наполнить каркас переносом из клона

Клиент, подпись, multipart, операции. Плюс наше: `getObjectBytes` с диапазоном первых байт для
определения типа, `abortMultipartUpload` для отката, конфигурация из `packages/shared/src/config.ts`
(без своего чтения `process.env`).

### 2. `video.create` — процедура создания записи

Порядок операций не переставляется (это защита, а не стиль):

1. лимит частоты (уже есть у auth — расширить на мутирующие процедуры);
2. Zod-валидация тела: заявленный размер ≤ 2 000 000 000, имя файла, `source: 'upload'`;
3. заявка `Idempotency-Key` — **атомарно**: `INSERT … ON CONFLICT (account_id, idempotency_key)
   DO NOTHING RETURNING id`; пустой результат означает повтор → вернуть ТУ ЖЕ строку и те же
   ссылки, не создавать вторую и не списывать квоту повторно;
4. `CheckAndConsumeQuota(user_uploads, 1)` — ДО выдачи ссылок; отказ → `refused(user_uploads)`
   без единого обращения к S3;
5. `initiateMultipartUpload` + подписанные ссылки частей (срок ≤ 900 с), размер части по размеру
   файла;
6. ответ `{ video_id, upload_id, parts: [...] }`.

### 3. `POST /api/upload/complete`

1. владение по сессии (чужой `video_id` → `404`, не `403`);
2. `CompleteMultipartUpload` на сервере;
3. `HEAD` фактического размера: > 2 000 000 000 → `failed(too_large)`, объект удалить,
   **слот вернуть** (`RefundUploadSlot`, DEC-A-014) в ТОЙ ЖЕ транзакции, что пишет `failed`;
4. тип по магическим байтам через `getObjectBytes` диапазоном первых байт (MP4, MOV, WebM, M4A,
   MP3): не тот → `failed(not_media)`, объект удалить, слот вернуть;
5. `status = queued`, постановка задания стадии `stt` **после** фиксации строки.

Длительность здесь НЕ измеряется: у `web` нет ffprobe, `moov` у MP4 часто в конце файла
(DEC-A-011). Это фича 3.

### 4. `CheckAndConsumeQuota` и `RefundUploadSlot` — ядро фичи

Единственная законная форма списания (`coding-style.md`):

```sql
INSERT INTO quota_counter (scope, scope_key, day, used) VALUES ($1,$2,$3,0)
  ON CONFLICT (scope, scope_key, day) DO NOTHING;
UPDATE quota_counter SET used = used + $4
  WHERE scope=$1 AND scope_key=$2 AND day=$3 AND used + $4 <= $5 RETURNING used;
```

`$5` — предел ИЗ ОКРУЖЕНИЯ, колонки `limit` в таблице нет. Пустой результат второго оператора И
ЕСТЬ отказ. Форма `INSERT … ON CONFLICT DO UPDATE … WHERE …` недействительна: её `WHERE` не
действует на вставку, и первый за сутки запрос прошёл бы мимо потолка.

Шесть scope: `user_minutes` (90), `user_uploads` (2), `user_upload_refunds` (2), `user_llm` (2),
`global_minutes` (600), `global_llm` (20). Отказ называет scope — пять пользовательских текстов;
у `user_upload_refunds` своего текста нет намеренно (исчерпание возвратов выглядит как обычный
отказ по загрузкам). Сутки календарные московские.

`RefundUploadSlot`: сначала списать право на возврат (`user_upload_refunds`), затем
`UPDATE … SET used = used - 1 WHERE … AND used > 0`; оба — в транзакции, пишущей `failed`.
Возврат ТОЛЬКО при отказах по свойствам файла, никогда при `refused_*`.

## Тесты, без которых фича не принимается

**Конкурентные (последовательный прогон зеленеет при обеих реализациях, различает только
параллельный):**

1. N параллельных `video.create` одного аккаунта при `user_uploads = 2`: ровно 2 создают запись,
   остальные `refused`, суммарное списание равно 2.
2. Два одновременных `video.create` с ОДНИМ `Idempotency-Key`: одна строка `video`, одно списание,
   обоим вернулись одинаковые ссылки.
3. Два параллельных отказа по свойствам файла при остатке возвратов 1: слот возвращает ровно один.
4. Разные аккаунты параллельно: добросовестный не блокируется чужой квотой.

**Граничные:** первый за сутки запрос с `n > limit` получает отказ (это дефект V2-R01 — тест
обязан быть красным на старой однооператорной форме); граница суток по Москве (23:59 → 00:01).

**Стражи по исходнику с внедряемым дефектом, обе строки в отчёт:** текст SQL списания (замена на
однооператорную форму → красный); `user_uploads` списывается ДО выдачи ссылок (перестановка →
красный); возврат слота только при свойствах файла (разрешить при `refused_*` → красный).

Интеграционные — на настоящих PostgreSQL и MinIO профиля `test`; они у нас работают, 91 тест уже
зелёный в контейнере.
