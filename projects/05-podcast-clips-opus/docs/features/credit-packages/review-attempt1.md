## Finding P2-1 — The checkout hides when a queued base package will start
**Location:** apps/web/src/app/upgrade/UpgradeScreen.tsx:48–54; apps/web/src/app/upgrade/page.tsx:24–29; packages/db/src/payments.ts:readAccountBilling.

**Broken behavior:** the credit-mode checkout displays the same generic “after already paid base periods”/“30 days” text for every account. It does not show a date and does not read `p.current`. The server page supplies neither the latest committed credit base-period end nor the prospective next window; readAccountBilling returns legacy plan_paid_until rather than committed credit periods. The provider redirect starts immediately on selecting a SKU. Dates appear only after successful payment on the return page.

**Concrete reproducer:** fulfill Start, then two distinct full-price Pro purchases, producing three committed 30-day base periods. Open /upgrade on mobile before the next purchase. The new Pro purchase starts after the third period (the ledger correctly serializes this), but the buyer is shown no calendar start/end date before paying. The checkout looks the same as that of a buyer with no committed base period. The existing catalog-render test uses a free fixture and checks only prices/hours; it cannot catch this omission.

**Contract:** FR-credit-packages-10 explicitly says “Checkout/return names exact package, effective dates and whether a renewal starts later.” AC-credit-packages-7 / SC-US-007-2 requires dates and the correct action when a future renewal is viewed on mobile. Final return metadata satisfies the return portion; it does not supply the missing checkout disclosure.

**Minimum fix:** read the server-authoritative latest committed base end using the same scheduling rule as fulfillCreditIntentTx, expose a prospective next start/end to the credit checkout, and render those dates beside the base purchase action before redirecting to payment. Clearly distinguish a prospective date from the final fulfillment date if another purchase can commit first. Preserve serialized final fulfillment and the exact dates already shown on return. Add one meaningful UI/server test with multiple committed future base periods. No quote engine, proration table, automatic upgrade or new commercial rule is required.

- **Seconds and attempts:** raw trusted probe seconds reach inputCreditSeconds before numeric(10,1) video-duration persistence. Retry duration cannot overwrite billable_seconds. Customer state is separated from minutes_charged/provider attempt costs. Extra provider retries keep existing user/global operational quotas; no spend cap increase is introduced.
- **Settlement/failure/retry:** current attempt validation precedes finalization in probe/STT/selection/render/worker retry and watchdog paths. A done partial result settles even while siblings remain pending. Stale terminal publication cannot release a newer accepted output; an already released explicit retry acquires a fresh reservation cycle before subsequent work. Quota refusal savepoints undo a newly created reservation rather than leaving a hold.
- **Recovery scope:** recovery funds have a same-video FK/filter, do not enter general available_seconds, and do not confer an account-wide paid period. Reserved/settled paid_render pins original processing rights. Regular paid rights remain a union of independent payment windows and ignore exhausted credit counters. - **Legacy/default/entrypoints:** absent mode defaults legacy; explicit empty/unknown fails loadWebConfig/loadWorkerConfig. Actual web environment projection, PgAuthStore runtime construction, billing dependencies, all three worker entrypoints and compose pass the typed mode. Mode gates new signup/opt-in/sales; processing and already persisted fulfillment use immutable video/account/intent policy after enrollment disable. Migration issues no old-account gifts and preserves original pending990intent meaning.
- **Time and retention:** base grants start at the greater of verified purchase time, committed base ends and protected legacy payment end; add-ons start at verified purchase time independently. Future grants cannot reserve before available_at and new reservations cannot consume expired grants. Paid expiry watchdog consults independent payment windows.
