## Находки

### [medium] Регресс `dashboard/error.tsx` — переопределение `.status-panel` не скоуплено и не учитывает старую разметку

`apps/web/src/app/globals.css:195-198` (вне `@media`, действует на ВСЕХ ширинах, включая десктоп):

```css
.status-panel { display:block; }
.status-panel > * + * { margin-top:var(--space-3); }
.status-panel h2 { margin-bottom:0; }
.status-panel p { margin-bottom:0; }
```

Эти правила написаны под НОВУЮ плоскую разметку `ProgressPanel` (h2/`ol`/p — прямые дети `<section
className="status-panel …">`), где `.status-panel > * + *` действительно даёт межблочный отступ.
Но класс `.status-panel` не принадлежит одному компоненту: `apps/web/src/app/dashboard/error.tsx:3-4`
использует ТУ ЖЕ разметку, что была ДО фичи — `<section className="status-panel failure"><div><h2>…
</h2><p>…</p><button>…</button></div></section>` — с вложенным `<div>`. У этого `<div>` ОДИН прямой
ребёнок в `.status-panel` (сам `<div>`), значит `.status-panel > * + *` не срабатывает вовсе; а
`h2`/`p` ВНУТРИ него получают `margin-bottom:0` от новых правил (были `0.5rem`/`0.75rem` до фичи —
строки 58–59, они же остаются в файле и по специфичности равны новым, поэтому проигрывают порядку).
Результат: заголовок «Не удалось загрузить данные», текст и кнопка «Повторить» на экране ошибки
дашборда (реальный кабинет — ровно тот экран, который просила проверить постановка ревью) рисуются
без отступов между собой, на ЛЮБОЙ ширине экрана, не только на телефоне.

`grep` подтверждает: `.status-panel` используется РОВНО в двух местах (`VideoDetail.tsx` и
`dashboard/error.tsx`), и на `dashboard/error.tsx` нет ни одного теста (снимка, разметки, чего угодно)
— поэтому регресс не поймал ни один прогон, включая полный набор 975/975 из отчёта исполнителя.

**Почему это регресс, а не всегда так было:** до фичи `.status-panel h2 {margin-bottom:0.5rem}` и
`.status-panel p {margin-bottom:0.75rem}` (строки 58–59) давали отступ ОБОИМ потребителям класса —
и старой `ProgressPanel` (тоже была с вложенным `div`), и `error.tsx`. Фича сменила разметку одного
потребителя и вслед за ней — общие правила, не заметив второго потребителя.

**Как чинить (любой из двух путей, не требует смены архитектуры):**
1. Дать новой ленточной разметке свой класс-модификатор (например `.status-panel.ribbon`) и
   писать блочные/margin-правила под ним, оставив базовый `.status-panel` как раньше (flex,
   `h2`/`p` с `margin-bottom`) для `error.tsx` и любых будущих простых потребителей; ЛИБО
2. Обновить `dashboard/error.tsx` на плоскую разметку без вложенного `div` (убрать `<div>`,
   `h2`/`p`/`button` — прямые дети `.status-panel`), чтобы он тоже получал `> * + *`.

Второй путь короче (1 файл, 1 строка), но проверить видимую верстку `error.tsx` (эмулировать
отказ загрузки) after the fix стоит вручную — тестов на этот экран нет ни до, ни после фичи.

### Проверено и подтверждено корректным (не находка, для доказательства аудита)

- **`failed_stage`/`failedStageOf` (A-2609-01) сверено с КАЖДЫМ реальным путём отказа, а не только с
  тестами исполнителя:**
  - `too_large`/`not_media` (`apps/web/src/server/video.ts`) — до создания `job_attempt` вовсе →
    `last_stage=null` → «Загрузка». Верно.
  - `no_audio`/`too_short`/`too_long`/`probe_timeout`/`refused_user_minutes`/`refused_global_minutes`
    (`packages/db/src/probe.ts:failProbeTx`) — помечают ТЕКУЩУЮ попытку `stage='stt'` как `failed`
    (не `succeeded`) → «Расшифровка» напрямую, без ветки «следующая стадия». Верно.
  - `refused_user_llm`/`refused_global_llm` в обычном потоке (`packages/db/src/selection.ts:58`) —
    попытка `stage='select'` уже существует (создаётся `acceptTranscript`, `packages/db/src/
    transcription.ts:93`, в той же транзакции, что помечает `stt` `succeeded`) и помечается `failed`
    напрямую → «Выбор» без ветки «следующая». Транзитное состояние «stt succeeded без select-попытки»
    внешне не наблюдаемо в этом потоке — оно возникает ТОЛЬКО через `video-retry.ts`, где квота
    LLM проверяется ДО создания новой попытки (`leaseAttemptTx`); именно там ветка «следующая стадия»
    и единственно нужна. Ровно это описывает A-2609-01 и подтверждает интеграционный тест
    (`tests/progress-screen.integration.test.ts`, кейс "Лимит LLM при повторе").
  - `stalled` (`apps/web/src/server/watchdog.ts:15-18`) — сторож помечает ВСЕ `running/deferred`
    попытки данного видео (кроме `rerender`) `failed` одним запросом ДО того, как читается экран —
    значит `last_stage_status` всегда `failed`, никогда `succeeded`, и ветка «следующая стадия» здесь
    не участвует; лента показывает именно ту стадию, на которой завис процесс. Единственное
    расхождение — документированное самим исполнителем (`07_code_report.md` п. «Чего фича не
    доказывает»): `queued`-видео с уже созданной, но не отражённой в `video.status`, попыткой `stt`
    может показать «Расшифровку» вместо «Загрузки» при стороже. Честно раскрыто, не скрыто.
  - Пересборки (`job_attempt.rerender`) корректно исключены (`NOT j.rerender`, `screen.ts:57`):
    подтверждено чтением `watchdog.ts` — отказ пересборки НИКОГДА не переводит `video.status` в
    `'failed'` (отдельная ветка сторожа для пересборок трогает только `clip`/`job_attempt`).
- **SQL: `UNIQUE(video_id, fence)`** (`packages/db/migrations/001_init.sql:150`) обеспечивает индекс,
  которым эффективно закрывается `ORDER BY j.fence DESC LIMIT 1` в `LATERAL`-подзапросе — не seq scan.
  **Изоляция по владельцу:** `job_attempt` не хранит `account_id`; `LATERAL`-подзапрос соединяется по
  `j.video_id=v.id`, а `v` уже отфильтрован `WHERE v.account_id=$1` во внешнем запросе — утечки между
  аккаунтами нет.
- **Мутационные якоря** (`scripts/test-progress-mutations.mjs`) сверены построчно с текущим исходником
  — все четыре (`distinct-states`, `ribbon-silence`, `ribbon-failed-stage`, `ribbon-collapse`) находят
  ровно одно вхождение и целят именно в проверяемый инвариант; red/green-логи в
  `tests/artifacts/progress-and-clips-screen/mutations/` подтверждают реальное падение (не
  `red=green=1`, чего чинит фикс с `test-skip-reporter.ts`).
- **Доступность ленты**: `<ol aria-label>`, ровно один `aria-current="step"` (проверено тестом),
  состояние — знак (`aria-hidden`) + видимый текст (`step-label`, `step-detail`) + `visually-hidden`
  текст статуса — цвет не единственный канал. AA-контраст нового набора тонов (включая `pending`/
  `--muted` на фоне каждого из failure/running/silent) закрыт отдельной мутацией

- **R9 для экрана записи**: `storageState` в цикле `FIRST_SCREEN_VIEWPORTS` (`check-responsive.mjs`)

- **Порог `22.5rem`**: `22.5rem × 16px = 360px`, `max-width` включительно — арифметически закрывает
  ровно заявленный дефект (360×740 не попадал под старые `22.49rem`=359.84px).
- **Числа первого экрана** (`07_code_report.md`) сверены с сырыми замерами `screens/chromium-dark-
  first-screen-375x667.json` побайтово (панель `569–616` из `667`, запас `51`) — не придуманы.
- **`.clip-preview { max-height:32svh }`** (`globals.css:219`) живёт внутри `@media(width<600px)` и
  затрагивает только `apps/web/src/app/videos/[videoId]/VideoDetail.tsx` (единственный потребитель
  `ClipCard`/`.clip-preview` в кодовой базе) — не течёт на лендинг (свой `landing-demo video`) или
  `/c/`, `/g/` (редиректы, не страницы).
- `tests/limits-retry.test.ts` (не тронут исполнителем) продолжает проходить: его ассерты — только
