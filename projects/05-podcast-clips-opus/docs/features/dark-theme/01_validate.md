## Ответы на вопросы

### 1. Серверное применение темы — форма и последствия для статики

Корневой `layout.tsx` сейчас НЕ читает `cookies()` и не помечен `dynamic`. Пробный `next build`
подтверждает: из всех маршрутов приложения **статически пререндерится только `/`** (и служебный
`/_not-found`):

```
○ /                 (Static)
ƒ /dashboard        (Dynamic) — уже force-dynamic + cookies() в dashboard/layout.tsx
ƒ /dashboard/videos/[videoId]  (Dynamic, наследует layout)
ƒ /c/[code]         (Dynamic) — уже export const dynamic='force-dynamic' в route.ts
ƒ /g/[guest_code]   (Dynamic) — то же
ƒ /health, /api/*   (Dynamic)
```

Добавление `cookies()` в корневой `layout.tsx` автоматически переводит `/` (и `/_not-found`) из
`○ Static` в `ƒ Dynamic` — это неизбежное следствие чтения `cookies()` в общем layout, не ошибка
реализации. Кэш/CDN это не ломает: у `/c/*` и `/g/*` уже `Cache-Control: no-store` и на Caddy, и в
коде; у `/` никакого кэширующего слоя нет (Caddy отдаёт её как обычный `reverse_proxy` без
`Cache-Control`). Единственная реальная цена — landing перестаёт обслуживаться как статический файл
из `.next` и рендерится на каждый запрос; тестов, зависящих от статики `/`, нет.

**Точная форма:**
```tsx
import { cookies } from 'next/headers';
import { themeFromCookie } from '../lib/theme';
export const dynamic = 'force-dynamic'; // явно: cookies() уже форсирует это неявно, но документируем
export default async function Layout({ children }: { children: ReactNode }) {
  const theme = themeFromCookie((await cookies()).get('n5_theme')?.value);
  return <html lang="ru" data-theme={theme}>...
```
Явный `export const dynamic` не обязателен технически (Next форсирует его сам при вызове `cookies()`),
но стоит оставить — так же, как уже сделано в `dashboard/layout.tsx`.

**Обязательная правка к постановке:** также нужен `generateViewport()` вместо статического
`export const viewport = {...}` — `theme-color`/`color-scheme` из пункта 5 постановки НЕ МОГУТ
зависеть от cookie, если `viewport` остаётся объектом-константой (текущее состояние). Next 15
поддерживает `export async function generateViewport()`; читает тот же `themeFromCookie`.

### 2. CSP и переключатель без inline-скрипта

Проверены три места, где вообще может быть CSP: `next.config.ts` (`headers()` — отсутствует),
`middleware.ts` (файла нет), `proxy/Caddyfile` (заголовки есть: HSTS, `X-Content-Type-Options`,
`Referrer-Policy`, но **CSP не установлен**). **Для страниц самого Next-приложения (`/`, `/dashboard`,
`/dashboard/videos/*`) CSP не существует вообще** — ни на уровне приложения, ни на уровне прокси.
Значит для клиентского компонента-переключателя нет ни `nonce`, ни `script-src`, ограничивающего
инлайн — их и не нужно вводить, обычный `'use client'`-компонент с `document.cookie = ...` работает
без изменений CSP. Тезис постановки «CSP не ослаблять» относится ТОЛЬКО к `/c/` и `/g/` (см. вопрос 3),
не к самому приложению — стоит явно развести это в коде/отчёте, иначе исполнитель может по инерции
искать несуществующий CSP-барьер для тумблера.

### 3. Фактическая ошибка в постановке про `/c/` и `/g/`

Постановка пишет: «На `/c/` и `/g/` переключателя нет ( … страницы без JS, CSP `script-src`
отсутствует)» — как ЕДИНУЮ причину для обеих страниц. Это верно только для `/c/`:

- `short-link-handler.ts`: `Content-Security-Policy: default-src 'none'; … ` — `script-src` в списке
  отсутствует, значит скрипты запрещены ПОЛНОСТЬЮ (правильно описано в постановке; тест
  `tests/short-link.test.ts:28` проверяет `expect(html).not.toContain('<script>')`).
- `guest-page.ts`: CSP содержит `script-src 'nonce-${nonce}'`, и страница УЖЕ несёт два инлайн
  `<script nonce="...">` блока («Скачать все», «Нужен тариф побольше»). `/g/` НЕ без JS.

Решение «тумблера нет ни там, ни там» может остаться в силе (единообразие с `/c/`, отсутствие
клиентского роутера для смены `data-theme` без каркаса React), но обосновывать его для `/g/`
отсутствием скриптов — неверно и введёт в заблуждение при следующей правке этой страницы. Нужно
поправить формулировку на «единообразие с `/c/` и отсутствие оправданной выгоды», либо явно спросить
владельца, не добавить ли тумблер на `/g/`, раз nonce-бюджет уже есть.

### 4. Прибор check-responsive.mjs — удвоение по теме

`scenarios()` (check-responsive.mjs:7) и `parseArgs`/`widths` — трогать НЕЛЬЗЯ: их тестирует
`tests/responsive-check.test.ts` (`toEqual([320,360,390,414,768,1024,1440])`,
`FIRST_SCREEN_VIEWPORTS`), но `scenarios()` напрямую не вызывается ни в одном тесте — риск для
самого `toEqual` НЕ подтвердился. Тема должна оборачивать существующие циклы СНАРУЖИ (`for (const
theme of ['dark','light'])` вокруг обоих проходов — основного и first-screen), а не менять форму
`scenarios()`.

Cookie для светлой темы: `context.addCookies([{ name:'n5_theme', value:'light', url: options.base }])`
сразу после `browser.newContext(...)` — форма `url:` (не ручной `domain:`/`path:`) не зависит от
порта/схемы `--base` и работает одинаково для контекстов со `storageState` (дашборд) и без. Кука
помечена `Secure` по контракту постановки — реальный движок Chromium/WebKit отправит её ТОЛЬКО по
https. Канонический вызов прибора всегда идёт с `--base https://...` (`SKILL.md`, `REPRODUCE.md`), так
что в проде/на стенде это не проблема, но нужно явно записать ограничение и положиться на
предусловие из постановки («на странице `/` … иначе код 2») как на защиту от тихого провала, если
кто-то когда-то передаст `--base http://localhost` — тогда светлая кука не долетит, но precondition
поймает это кодом 2, а не покажет ложный «0».

**Найден реальный дефект-ловушка в `summary()`:** ключ дедупликации R2/axe-target-size —
`${f.engine}|${f.scenario}|${f.route}|${f.selector}` (check-responsive.mjs, функция `summary`) —
**не включает `theme`**. Если тёмный и светлый прогоны используют одно и то же имя сценария (что и
требуется — `scenarios()` не трогаем), совпадение по остальным четырём полям объединит находки двух
тем в `Set`, и находка, реальная только в одной теме, тихо исчезнет из отчёта в другой. Обязательно
добавить `theme` в кортеж ключа одновременно с добавлением поля `theme` в сами находки/`meta`/имя
скриншота (постановка просит только последнее — этого недостаточно).

### 5. Пробелы постановки — вероятные ошибки исполнителя

1. **`select`-стрелка не поймает grep.** `globals.css`: `background:...url("data:image/svg+xml,...
   stroke='%23202a27'...")` — цвет закодирован как `%23202a27` (URL-encoded), обязательный grep
   `#[0-9a-fA-F]{3,8}` его НЕ найдёт. Стрелка останется цвета светлого `--ink` и станет почти
   невидимой на тёмной поверхности. `currentColor`/CSS-переменные внутри `data:`-URI не резолвятся —
   нужны ДВЕ версии data-URI (разный `stroke=`) под `:root` и `:root[data-theme=light]`.
2. **Автозаполнение WebKit/Chromium.** Правила `input:-webkit-autofill` в коде нет вовсе. При тёмной
   теме по умолчанию автозаполненное поле останется жёлтым/светлым с тёмным текстом независимо от
   `color-scheme`. Нужно добавить `-webkit-box-shadow:0 0 0 1000px var(--surface) inset;
   -webkit-text-fill-color:var(--ink);` (в обеих темах — через токены).
3. **`accent-color` не хватает чекбоксам/радио.** Есть только у `progress`. Без него нативные
   чекбокс/радио в обеих темах красятся акцентом браузера/ОС, а не `--green` — визуальная
   рассинхронизация с остальными брендовыми контролами. Добавить
   `input[type=checkbox],input[type=radio]{accent-color:var(--green)}`.
4. **Медиа-«леттербокс» вне 3-ступенчатой системы поверхностей.** `.clip-preview` сейчас — фиксированный
   тёмный блок (`#1d2822`/`#e2e7db`) независимо от темы страницы; это НЕ то же самое, что `--paper`/
   `--surface`/`--surface-2`. Если превратить его напрямую в один из этих трёх токенов, в тёмной теме
   он рискует слиться с фоном страницы и потерять рамку кадра, которая в светлой теме была «бесплатной»
   за счёт контраста тёмный-блок/светлая-страница. Нужен отдельный токен (например `--media-bg`/
   `--media-fg`), и его контраст должен попасть в таблицу отчёта — которой в постановке для него нет
   строки (перечислены только текст/фон, второстепенный/фон, акцент/фон, кнопка, рамка/поверхность).
5. **`.brand span` — отдельная пара токенов, не «кнопка».** Значок `◧` красится текстом `#dcefbb` на
   фоне `var(--green)` — это НЕ то же соотношение, что у основной кнопки (светлая заливка/тёмный текст,
   FR-LOOK-010, другое направление контраста). Обе пары должны попасть в таблицу отдельно, иначе
   немаркированная замена `--green`-фона под кнопку может тихо испортить контраст значка.
6. **Video-постер/`poster` не требует правок**, но убедитесь, что placeholder-фон `.clip-preview`
   (см. п.4) не путают с постером — постер приходит из реального thumbnail-изображения и токенов не
   касается.
7. **`:focus-visible`** уже названо в постановке («фокус-обводка» в списке «Что править») — но
   отсутствует как отдельная строка в требуемой таблице контраста отчёта; добавить
   обводка/фон-под-ней, раз WCAG 1.4.11 применяется и к состояниям фокуса, а не только к рамкам.
8. **Несогласованность с `SKILL.md` и планом.** `.claude/skills/responsive-ui/SKILL.md` («Токены и
   тема»): «по умолчанию тёмная, светлая — по `prefers-color-scheme: light` **и** явному выбору» —
   и `docs/plans/2026-09-25-mobile-ui.md` шаг 3: «`prefers-color-scheme` + тёмная по умолчанию» — оба
   противоречат решению A-2509-03 постановки («независимо от `prefers-color-scheme`… светлая — только
   по явному выбору»). Решение владельца в постановке имеет приоритет и оно самодостаточно, но
   формулировку `SKILL.md` стоит поправить в этом же PR, иначе следующий читатель навыка получит
   противоположную инструкцию.
9. **Инструмент «общий модуль» для SSR-токенов нереализуем без новой зависимости.** Постановка
   допускает вариант «вынеси токены в общий модуль строкой, импортируемый в оба SSR-файла и
   проверяемый тестом против `globals.css`» — но `globals.css` обрабатывается как обычный CSS-файл
   Next'ом, а не генерируется из TS; общего механизма «TS-модуль → CSS custom properties» в стеке нет,
   а вводить его — новая зависимость (запрещено границами постановки: «package.json/lockfile — новых
   зависимостей нет»). Единственный рабочий путь — дублирование значений в трёх местах и unit-тест,
   который парсит `:root`/`:root[data-theme=light]` regex'ом из `globals.css` и сравнивает с
   значениями, зашитыми в `short-link-handler.ts`/`guest-page.ts`. Рекомендую убрать альтернативу
   «общий модуль» из постановки как невыполнимую в этих границах.
10. **Что НЕ сломается (проверено grep'ом по тестам).** Ни один тест не проверяет CSP-строку,
    `<html lang=`, цвета или содержимое `<style>` целиком — только точечные подстроки:
    `tests/short-link.test.ts:26` и `tests/guest-pack.test.ts:80` требуют дословную подстроку
    `@media(max-width:600px)` в HTML `/c/` и `/g/` — сохранить её ПОСИМВОЛЬНО при переносе цветов на
    токены в этих файлах. Остальные ассерты (`КлипМейкер`, `Сделать свои клипы`, `width=device-width`,
    `<img`, отсутствие `<script>`/`<video>` на `/c/`, `noindex, nofollow`, `Скачать все`) тем/цветов не
    касаются и не пострадают.
