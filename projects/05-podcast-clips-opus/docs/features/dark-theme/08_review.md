## 2. Безопасность и fail-closed

- **`themeFromCookie`** (`apps/web/src/lib/theme.ts:10-21`): корректный закрытый разбор — собирает
  ВСЕ пары `n5_theme=...` из заголовка, возвращает `light` только если ровно одна пара и её значение
  **точно** `'light'` (регистр, пробелы после `=`, кавычки, `n5_theme=` пусто, второй похожий ключ
  `x_n5_theme=`/`n5_themes=` — всё даёт `dark`). Независимо прогнал мутацию (`values[0]==='dark'?'dark':'light'`)
  — красное `16 failed | 13 passed`, восстановление — `29 passed`. Совпадает с заявленным в отчёте.
- **XSS в `data-theme` на SSR-страницах `/c/`, `/g/` — не найден.** `theme: Theme` — тип `'dark'|'light'`,
  значение получено ТОЛЬКО через `themeFromCookie(...)`, которая физически не может вернуть ничего,
  кроме этих двух литералов. Сырое значение cookie в HTML никогда не попадает.
- **CSP `/c/` и `/g/` не изменена** — сверил дословно: `/c/` — `default-src 'none'; img-src https: http:;
  style-src 'unsafe-inline'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`; `/g/` —
  `default-src 'none'; ...; script-src 'nonce-${nonce}'; ...` — оба идентичны версии до диффа, кроме
  добавленных строк объявления самих заголовков (не значений).
- **Атрибуты cookie тумблера** (`themeCookie`, `theme.ts:23-25`): `Path=/; Max-Age=31536000; SameSite=Lax;
  Secure`, без `HttpOnly` (пишет клиент, как и требует постановка) — подтверждено юнит-тестом
  `tests/theme.test.ts:24-29`.

## 3. Корневой layout `force-dynamic`

Подтвердил независимой сборкой (`npm run build --workspace=apps/web`): `ƒ /` и `ƒ /_not-found` —
динамические (было `○ Static`), остальные маршруты не задеты, тот же неопасный warning про
`@valkey/valkey-glide` (существовал до фичи). Гидрационного рассинхрона нет: `ThemeToggle` получает
`initial` тем же значением, что сервер уже вставил в `data-theme`/`aria-pressed`, состояние не
меняется на монтировании — только по клику. `not-found`/`error` отдельного тумблера не имеют и
рендерятся внутри общего layout — тема на них распространяется корректно (кастомных
`not-found.tsx`/`error.tsx` в проекте нет).

## 4. Токены и контраст

Пересчитал 15 пар формулой WCAG (относительная яркость + `(L1+0.05)/(L2+0.05)`) — **все числа в
таблице `07_code_report.md` совпадают с моим независимым расчётом** (включая исправление фокуса в
светлой теме 4,90 вместо старых 2,68). SSR-токены `/c/`, `/g/` посимвольно совпадают со значениями
`globals.css` (сверил `grep`); `grep -nE '#[0-9a-fA-F]{3,8}|white|black|rgba?\(|%23'` вне блоков
токенов — пусто и в `globals.css`, и в обоих `.tsx`, и в SSR-файлах (только `THEME_TOKENS`).

**H-1 (medium) — риск из `01_validate` п.9 закрыт не полностью.** `--media-bg`/`--media-fg` —
отдельный токен создан (не переиспользован `--surface`/`--paper` буквально), формально правка
выполнена. Но контраст **media-bg/surface в тёмной теме = 1,22** (проверил: L=0,00228 vs 0,01396) —
рамка кадра `.clip-preview`, которая в светлой теме была «бесплатной» (12,10 — заметный тёмный блок
на белой карточке), в тёмной темы почти не видна на глаз (тёмно-серая карточка `#1a211d` vs
почти-чёрный плейсхолдер `#060807`). Это ровно тот риск, который сама правка №9 называла
(«рискует слиться с фоном страницы и потерять рамку кадра») — токен есть, а видимой рамки нет, и
отчёт это нигде не проверяет глазом (для 3-ступенчатой системы поверхностей такая проверка есть —
«различимы на снимке, проверено глазом» — а для этой пары её нет). **Исправление:** либо светлее
`--media-bg` в тёмной теме, либо `border:0.0625rem solid var(--line)` у `.clip-preview` — тогда рамка
не зависит от случайного попадания в контраст.

tests/theme.test.ts tests/responsive-check.test.ts` — 42/42 зелёных; `tests/short-link.test.ts` +
