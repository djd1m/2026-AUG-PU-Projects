# Дополнение к постановке фичи 3 — условия этого прогона

Читай ВМЕСТЕ с `00_brief_codex.md` в этом же каталоге. Ниже — только то, что меняет условия.

## Ты работаешь в изолированной копии репозитория

Это отдельный git worktree на ветке `feature/queue-and-probe`. Параллельно в ДРУГОЙ копии идёт
раунд исправлений фичи 2 — он правит `packages/s3` и `apps/web`. Твои правки и его сольёт
integration owner.

**Не трогай вовсе:** `packages/s3/**`, `apps/web/src/server/video.ts`,
`docs/features/upload-and-quota/**`. Если тебе нужна правка там — НАЗОВИ её в отчёте словами, но не
делай: иначе слияние потеряет одну из двух версий молча.

**Общие манифесты** (`package.json` корня, `package-lock.json`) правит обычно только integration
owner. Здесь исключение, без которого фича не собирается: тебе нужно добавить workspace
`packages/queue`. Сделай минимальную правку — ровно добавление workspace и его зависимостей — и
НАЗОВИ её отдельной строкой в отчёте, чтобы слияние было осознанным. Ничего другого в манифестах не
меняй: ни версий существующих зависимостей, ни скриптов чужих workspace.

**Миграции.** Применены 001–004. Новое — отдельным файлом `005_*.sql`. Файлы 001–004 не трогай:
они уже применены на стендах, правка существующей миграции не доедет до применённой базы.

## Шаг 0 — зависимости

`node_modules` в этой копии нет. Первым делом `npm install` (не `npm ci`: lockfile изменится из-за
нового workspace). Убедись, что установка прошла, прежде чем делать выводы о сборке.

## Интеграционные прогоны

Docker тебе недоступен — это известно и ожидаемо. Пиши юнит- и интеграционные тесты полностью, но
НЕ выдавай невыполненный прогон за выполненный: так и напиши «не выполнено, нет docker», как ты
честно сделал в прошлом раунде. Прогон на настоящих PostgreSQL и Redis выполнит integration owner.
