## Как читать средний балл

Среднее 94.5 — не потолок методики, а честный результат: документ писался с числами почти в каждом
предложении (единицы, пороги, `scope`, тайминги), что систематически поднимает `Specific`/`Measurable`.
Ниже я фиксирую, ГДЕ я делал интерпретирующий выбор при скоринге, чтобы координатор мог пересчитать
несогласившись, а не гадать, откуда взялось число:

- **Time-bound (SMART).** Засчитан ненулевым, если в SC истории есть ЛЮБОЕ явное числовое значение
  времени/длительности/окна (секунды, минуты, дни, дедлайн) — не только «время ответа сервера». Пример:
  длина фрагмента 20,0–75,0 с (US-003) или суточное окно подсчёта переходов (US-009) засчитаны как
  Time-bound = 5, хотя это не SLA на ответ. Без такого значения — 0, даже если есть качественное слово
  «немедленно» без числа (US-006, US-008, US-010, US-013).
- **Completeness bucket.** Рубрика знает только «happy / happy+errors / happy+errors+edges» и не
  предусматривает «happy + чистый edge без ошибки». Там, где второй-третий SC истории проверяет
  ОТРИЦАТЕЛЬНОЕ утверждение (что-то НЕ должно произойти — самопереход не считается, страница НЕ
  восстанавливается, дедлайн НЕ нарушен), я засчитывал это как заполняющее бакет «errors» (7/10), потому
  что по духу это тот же тип проверки — граница, а не повторение happy path другими словами. Там, где
  оба SC истории — чистые положительные варианты ОДНОГО и того же действия без границы (US-005, до
  правки — US-012), бакет остаётся «happy only» (4/10) — это и есть находки V1-R03/V1-R04.

## Security Acceptance Criteria

Применимо: аутентификация (FR-AUTH-001…003), хранилище объектов (NFR-SEC-001), согласие на особые
данные — публикация чужого лица без согласия (NFR-SEC-002, FR-GUEST-001), внешние API (whisper, Claude,
Telegram — `model-cost-contract.md`), anti-fraud по кодам (FR-PARTNER-003).

| Критерий | Проверка | Результат |
|---|---|---|
| Input Validation | тип файла по магическим байтам, а не Content-Type/расширению (FR-INGEST-002); порция/границы — везде числа | ✅ специфично |
| Authentication | bcrypt, сессия `session`, `logout` гасит серверную сессию (FR-AUTH-001) | ✅ специфично |
| Authorization / владение | подписанные ссылки только владельцу; гостевая страница — по непубличному коду, `noindex` (NFR-SEC-002) | ✅ специфично |
| Data Protection | бакет приватный, ссылки ≤ 15 мин, ключи хранилища только у `web`/воркеров (NFR-SEC-001, канон §6) | ✅ специфично |
| Secret Management | суточные потолки без дефолта, отказ запуска (FR-LIMIT-002, `model-cost-contract.md`) | ✅ специфично |
| Webhook Security | внешних вебхуков в продукте нет (только исходящие вызовы моделям) | не применимо |
| **Анти-энумерация и брутфорс входа** | FR-AUTH-001 ТЕКСТОМ описывает лимит частоты до разбора тела, одинаковый ответ на «занято»/«неверно», bcrypt-хэш — но НИ ОДИН SC/Gherkin в `Specification.md`, `Refinement.md` §Test Cases или `Pseudocode.md` §Scenario Coverage не называет сценарий для этого поведения (девять алгоритмов без `SC-US`, включая `AuthRegisterAndLogin`, `Pseudocode.md:712-714`, объявлены проверяемыми «Gherkin-сценариями growth, границами файла и сроками» — но авторизационный брутфорс ни туда, ни сюда не попадает) | ⚠️ **V1-R01** |

перенести их как постоянный `SC-US` или отдельный блок в сам `Specification.md`.

## Growth Traceability

Семя growth-требований в этом проекте — НЕ `docs/product-discovery-brief.md` (файла нет), а
постановка `/replicate` §05 и раздел «Growth-требования» `CJM_Variants.md`, что explicitly зафиксировано
в `canon.md` §2: «Манифеста `PD-*` нет: Phase 0 не выполнялась (вход `--from-docs`: постановка владельца
+ CJM). `check-growth-trace` и `check-handoff-manifest` ожидаемо отвечают `2`; семена growth берутся из
постановки и раздела «Growth-требования» `CJM_Variants.md` и промотируются вручную.»

`scoring-system.md` (requirements-validator, раздел Growth Traceability) читает это ровно так:
«`docs/product-discovery-brief.md` ОТСУТСТВУЕТ → applicable = no → **+0**, никогда не `-10`». Формально
применяю это правило: **+0**.

По существу, а не механически, трассировка ЗАКРЫТА полностью: каждый `FR-GROWTH-nnn` имеет строку в
таблице `Specification.md` §9 «Ответы на семена», называющую и семя, и место закрепления:

| Семя | Где закреплён (Specification §9) |
|---|---|
| FR-GROWTH-001 | §3 FR-GROWTH-001; FR-RESULT-002, FR-GUEST-002 |
| FR-GROWTH-002 | §3 FR-GROWTH-002; FR-PARTNER-001 |
| FR-GROWTH-003 | §3 FR-GROWTH-003; FR-RENDER-002, FR-TARIFF-001 |
| FR-GROWTH-004 | §3 FR-GROWTH-004; FR-PARTNER-002, FR-GUEST-002 |
| FR-GROWTH-005 | §3 FR-GROWTH-005; §8 строка читаемости |

Ни одна строка не пропущена и не отклонена без причины (`CJM_Variants.md`, раздел «Growth-требования»,
не перечитывался целиком этой единицей — трассировка проверена по конечной точке, Specification §9, что
достаточно для критерия «долетело или явно отклонено с причиной»). Зафиксировано как V1-R06 (low,
информационная) — не дефект, а объяснение расхождения между механическим скорингом и содержанием.

## Vague terms

Проверено `grep`-скан по списку из `SKILL.md`/`smart-criteria.md` (fast/easy/user-friendly/intuitive/
responsive/secure/robust/efficient/simple) и их русских эквивалентов (быстро, удобно, просто, легко,
интуитивно, надёжно, наглядно, разумно, адекватно) по всему `docs/Specification.md`:

```bash
grep -noE 'быстр[а-я]*|удобн[а-я]*|прост[оа][а-я]*|легк[а-я]*|интуитивн[а-я]*|надёжн[а-я]*|наглядн[а-я]*|разумн[а-я]*|адекватн[а-я]*' docs/Specification.md
```

Совпадений по искомым словам — ноль (три ложных попадания regex на «проставляется»/«проставлен» не
являются вхождениями искомых корней). Зафиксировано как V1-R08 (low, положительная находка): документ
последовательно заменяет качественные слова числами («≤ 1 с», «≥ 3,5 % высоты кадра», «контраст ≥ 4,5:1»,
«30 запросов/мин») — это системная черта стиля Phase 1, не случайность одной строки.
