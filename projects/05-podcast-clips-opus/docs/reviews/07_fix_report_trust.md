## Вердикт по каждой находке

| Находка | Вердикт и изменение |
|---|---|
| RT-001 | **Исправлено.** Тело `code.apply` больше не принимает `source`, включая все три ранее допустимых значения. Сервер проверяет HMAC cookie с доменным префиксом `referral:`, сроком 14 суток и существующим `SESSION_SECRET`. Cookie ставится после успешного открытия `/g/` или `/c/`, имеет HttpOnly/Secure/SameSite=Lax. Неподписанные старые, изменённые, просроченные и дублированные cookie не подтверждают источник. `{}` использует подписанный след; совпавший код сохраняет подтверждённый источник; другой явно введённый код получает `explicit`. Неверный явный код даёт 422 без fallback. HTTP-контекст передаёт cookie, браузер не вычисляет источник. Успех и явное `discard_referral: true` очищают cookie серверным заголовком. |
| RT-002 | **Исправлено в разрешённой части.** `code_applied` пишется после успешной записи атрибуции и только для несамореферала. Конфликты откатываются и не двигают счётчик. Блокировки аккаунта и кода сохраняют сериализацию; время окна берётся после получения блокировки кода. 50-е успешное применение коммитится вместе с блокировкой, последующие отвергаются. Порог 50, окно 10 минут и отсутствие разблокировки сохранены. **Вопрос владельцу:** «Считать различные аккаунты, успешно создавшие или изменившие атрибуцию, а не попытки/повторные применения; предусмотреть контролируемую разблокировку с причиной и уведомлением партнёра». Это изменение канона, не реализовано. |
| RT-003 | **Исправлено.** Применение своего кода при существующей атрибуции даёт 409, сохраняет всю прежнюю строку и пишет диагностический аудит `self_referral_rejected`. Без прежней строки остаётся `rejected/self_referral`; счётчик блокировки не растёт. |
| RT-004 | **Исправлено.** Сначала наблюдение `status=erasing AND erase_deadline < now`, затем стирание аккаунтов, затем остальные работы. Шаги и отдельные аккаунты/клипы изолированы; ошибка обновления очередности повторов тоже не останавливает соседей. Просрочка выводит `erase_deadline_overdue` с числом аккаунтов и делает тик неуспешным, даже если повторное стирание сейчас получилось. Это наблюдение в действующем журнале сторожа; внешняя доставка тревоги не добавлялась. |
| RT-005 | **Вопрос владельцу.** Действующий контакт оператора и ответственный за обращения не заданы. Во время работы запрошен адрес почты/URL формы, ответа пока нет. Выдуманный контакт не опубликован. Формулировка решения: «Утвердить контакт оператора, ответственного и процедуру отзыва гостевого пакета по жалобе с заявленным сроком до 72 ч». На гостевой странице пока остаётся прежний текст о ведущем; находка не устранена. |
| RT-006 | **Исправлено.** Уборка больше не ставит `revoked_at` по истечению срока. Срок проверяется существующими условиями доступа; существующий UI различает истечение и отзыв. Уже записанные исторические `revoked_at` не переписывались: надёжно восстановить их происхождение по одному полю нельзя. |
| RT-007 | **Исправлено.** Общий обработчик файла и thumbnail обязательно вызывает существующий `allowRead` по доверенной цепочке IP, до проверки ресурса, подписи и потока S3. Ограничитель действует также при повторном обращении по гостевому подписанному билету. Отказ — 429; ошибка инфраструктуры остаётся 503. Runtime передаёт общий Redis и действующий лимит 120/мин. |
| RT-008 | **Вопрос владельцу.** Без сессии сервер не может доказать, что посетитель — владелец; второй аккаунт также не тождествен первому. Формулировка: «Зафиксировать в ADR-007, что исключение самоперехода гарантируется для идентифицированной сессии; отдельно решить необходимость защиты от нескольких аккаунтов». Fingerprinting или связывание людей по IP не добавлялось. |
| RT-009 | **Вопрос владельцу.** При стирании партнёра текущая схема удаляет и атрибуции приглашённых живых аккаунтов: их источник исчезает, они могут снова применить код. Это следствие здесь зафиксировано, схема не менялась. Формулировка: «Сохранять обезличенный факт атрибуции после удаления партнёра: nullable partner_code_id, ON DELETE SET NULL и отдельный терминальный статус; определить влияние на повторное применение и кабинет». Требуются согласованная миграция и изменение закрытого набора статусов. |
| RT-010 | **Вопрос владельцу.** На публичном лендинге остаётся bearer-URL только на thumbnail, до 900 с после выдачи; отзыв короткой ссылки не отзывает ранее выданный URL. Третьего пути к файлу клипа нет. Формулировка: «Принять явно окно до 900 с для публичного превью либо согласовать его проксирование с повторной проверкой отзыва». Существующий контракт не менялся без решения по этой развилке. |
| RT-011 | **Исправлено.** Обязательный reporter печатает число пропусков, отсутствующие переменные/причину и разбивку по файлам. `N5_ACCEPTANCE=1` делает любой пропуск ошибкой процесса. `npm test` запускает wrapper, который сохраняет обязательный reporter даже при пользовательском `--reporter=dot`; прямой запуск Vitest по конфигурации также его подключает. Профиль compose `test` включает приёмочный режим. Страж запускает реальный дочерний процесс без DATABASE_URL: 9 skipped, предупреждение и exit 1; обычный режим даёт предупреждение и exit 0. |
| И-1 | **Исправлено.** `ShortLinkService.find` приводит код к верхнему регистру до валидации и SQL. `/c/k7m2xq9prt` и `/c/K7M2XQ9PRT` проверены через обработчик страницы как одинаковые ответы. |
| И-2 | **Реализовано за флагом; решение владельца теперь есть.** `N5_SHORT_CODE_LENGTH=6` создаёт новые шестисимвольные коды, по умолчанию остаётся 10. Другие значения отвергаются генератором. Флаг проброшен через compose, `.env.example` сохраняет 10. Обе длины читаются независимо от флага, старые коды не меняются; коллизии по-прежнему проверяются UNIQUE и повторяются. Бриф требовал решения владельца; во время работы в HEAD появился OWN-007: выбраны `clipmkr.ru` и длина 6. Повторного решения не требуется. Доменный rollout, изменение канона и включение флага в живом окружении остаются отдельной работой координатора по OWN-007. На старом домене сокращение хвоста само по себе не даёт ≤20 знаков; выбранный `clipmkr.ru/c/<6>` даёт 19. |

Подписанная cookie — переносимое подтверждение успешной выдачи сервером, а не доказательство
уникального человека. Копирование действительной cookie между браузерами и второй аккаунт
не устраняются подписью. Старые неподписанные следы не принимаются; повторное открытие страницы
выдаёт новый подписанный след.
