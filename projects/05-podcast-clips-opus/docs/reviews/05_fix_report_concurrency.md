## Решения по находкам

| Находка | Вердикт и изменение |
|---|---|
| RC-001 | **Исправлено в коде; PostgreSQL-подтверждение ожидается.** После блокировки `video` отдельный SELECT читает `job_attempt.stt_calls`. Условный UPDATE проверяет фенс, стадию, статус, прежний счётчик и потолок; только получивший строку может списать повторные минуты. Отказ квоты откатывает захват через savepoint и сохраняет терминальную причину. |
| RC-002 | **Исправлено в коде; интеграционный прогон ожидается.** Все 14 PostgreSQL integration-файлов и подготовка тестовой БД используют `createPool`: max=10, connectionTimeoutMillis=3000, idleTimeoutMillis=30000, statement_timeout=5000. Отличаются только изолированная схема и имя приложения для наблюдения теста. Фабрика не принимает переопределение таймаутов/размера пула. |
| RC-003 | **Исправлено.** `publish()` вызывается до получения соединения и начала транзакции. Приём в БД по-прежнему блокируется относительно retry и проверяет текущий `render_fence`. S3 сохраняет существующие `IfNoneMatch: '*'` и проверку неизменного контракта; устаревший результат не удаляет канонические объекты. |
| RC-004 | **Вне области по прямому указанию брифа.** Эксплуатационную ёмкость диска, общий резерв, ADR и тома не менял. |
| RC-005 | **Исправлено.** `N5_RENDER_CONCURRENCY` удалена из compose. Литерал `concurrency: 1` сохранён. |
| RC-006a | **Исправлено.** Только `TranscriptError` переводится в `no_timestamps`. Ошибка БД перебрасывается тем же объектом, транзакция откатывается, фиктивный терминальный диагноз не записывается. Внешний обработчик worker получает исходную причину. |
| RC-006b | **Исправлено.** Непригодный JSON/структура ffprobe дают `Error('Непригодный вывод ffprobe', { cause })`, а не `ProbeError`. Только убитый по таймауту дочерний процесс даёт `probe_timeout`. Другой ненулевой выход/ошибка запуска остаются операционной ошибкой с cause и не попадают в возврат слота. |
| RC-007 | **Исправлено.** Мёртвая `acceptRenderResult` и два дублирующих integration-теста удалены. Обязательные конкурентный и stale-fence сценарии остаются на настоящей `publishRenderResult` в render.integration. Статический страж ADR-001 также перенесён на рабочую функцию и испытан мутацией. |
| RC-008 | **Исправлено.** Отказ ROLLBACK не замещает исходную ошибку; клиент с неподтверждённым откатом уничтожается через `release(true)`. При успешном откате возвращается пригодный клиент. |
| RC-009 | **Исправлено.** Диагностика рендера проходит cause (до 8 уровней, с защитой от циклов), санирует каждый уровень, сохраняет общий предел 4096 символов. |
| RC-010 | **Исправлено.** Очистка чанка использует `rm(path, { force: true })`. Проверен уже удалённый чанк: исходная ошибка провайдера не заменяется ENOENT. |

### Почему одного свежего чтения для RC-001 недостаточно

При простом инкременте свежего счётчика второй воркер всё ещё получает право на следующий платный
вызов. Поэтому `authorizeSttCall` принимает ожидаемый предыдущий номер (по умолчанию 0).
Воркер повышает его только после наблюдаемого retryable-отказа провайдера. Два вызова с одинаковым
номером авторизуют ровно один переход; это та же форма условного захвата, что у `llm_dispatched`.

Следствие для восстановления: пере-доставка после неизвестного исхода уже захваченного вызова
не запускает его автоматически повторно на том же фенсе. Живой первый исполнитель может закончить;
при его потере остаётся завершение сторожем и повтор владельцем с новым фенсом. Это сознательная
семантика at-most-once для конкретного номера вызова, без обещания exactly-once у внешнего API.
Схема БД не менялась; платных вызовов при проверках не делалось.

### Какие ожидания тестов изменены

- В `render.integration.test.ts` прежнее «publication locks out retry until its acceptance»
  заменено проверкой, что retry завершается **пока PUT ещё удерживается**, а поздний результат
  старого фенса получает `false`. После приёма актуального результата retry получает `null`.
- При двух доставках рендера допустимы две попытки идемпотентной загрузки в S3, но только один
  приём в БД. Проверка «publish вызван ровно один раз» была свойством удалённой блокировки.
  Запрет перезаписи/удаления объектов отдельно проверяет `render-storage.test.ts`.
- Добавлен настоящий тест удержания строки: пул сообщает `statement_timeout=5s`, ожидающий
  `retryRender` получает ошибку драйвера `57014`; она не притворяется исходом `null`.
  Дополнительный предел 6.5 секунды нужен только для завершения теста при снятой защите,
  настройки самого пула не меняются.
- Тесты STT теперь явно различают повтор доставки и повтор после ошибки провайдера.
  Добавлены гонки первого вызова при достаточной квоте и повторов до потолка 3.
