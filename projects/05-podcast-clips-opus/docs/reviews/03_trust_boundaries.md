# Ревью 03 — границы доверия и правовые границы

**Область:** фичи 7 (экраны), 8 (`short-link`), 9 (`guest-pack`), 10 (`partner-codes`), 12 (`retention-and-erasure`).
**Режим:** cross-family review (OWN-002). Код и тесты написаны семейством OpenAI; это независимая проверка
семейством Anthropic.
**Базис:** рабочее дерево на коммите `90bc71d` плюс незакоммиченные изменения (см. `git status`).
**Что делалось:** читались исходники `apps/web/src`, `packages/db/migrations/*.sql`, `packages/s3/src`;
прогонялся набор тестов. Отчёты Codex читались как указатель, не как доказательство.

**Вердикт: вернуть.** Две находки высокой серьёзности (RT-001, RT-002) ломают целостность
партнёрской атрибуции — той самой величины, по которой считаются выплаты. Плюс RT-011: утверждение
«490 зелёных тестов» измерением не подтверждается.

## Находки

### RT-001 · высокая · Источник атрибуции приходит из тела запроса и нигде не сверяется

**Утверждение.** `code.apply` принимает поле `source` от клиента. Сервер не сверяет его ни с cookie
`__Host-n5_referral`, ни с фактом существования гостевого пакета. Значит вся асимметрия ADR-007
(«explicit > guest_link > cookie») держится не на сервере, а на добросовестности браузера.

**Доказательство.**

- `apps/web/src/server/partner.ts:6-7` — `source: z.enum(['explicit','guest_link','cookie']).default('explicit')`
  внутри схемы, разбирающей `raw` (тело запроса).
- `apps/web/src/server/trpc.ts:77-80` — `s.apply(ctx.account, input, ctx.ipPrefix)`; в контекст передаётся
  только префикс IP.
- `apps/web/src/app/api/trpc/[trpc]/route.ts:21` — `createContext` не кладёт в контекст ни заголовок
  `Cookie`, ни результат `readReferral`.
- `apps/web/src/app/AuthForm.tsx:21-23` — источник действительно вычисляется в браузере:
  `readReferral(document.cookie)`, и cookie намеренно без `HttpOnly`
  (`apps/web/src/lib/partner-referral.ts:11`), чтобы JS мог её прочитать.
- `apps/web/src/server/partner.ts:70-73` — при `input.source === 'guest_link'` пишется канонический
  `growth_event` типа `guest_registered`, без единой проверки, что гостевой пакет существовал.
- `apps/web/src/server/partner.ts:103` — кабинет партнёра считает «приглашённых гостей» ровно по
  `source='guest_link'`.

**Следствия, по возрастанию цены.**

1. Любой аутентифицированный аккаунт, знающий действующий код (а код партнёра публичен по назначению),
   одним запросом `{code, source:'guest_link'}` увеличивает счётчик «приглашённые гости» и создаёт
   `guest_registered`, ни разу не открыв ни одного `/g/{code}`.
2. Правило замены проверяется по объявленному, а не по фактическому источнику: клиент может объявить
   `explicit` для кода, полученного только из cookie, и тем запереть строку от последующих замен, —
   либо, наоборот, объявить `cookie` и разрешить себе будущую замену.
3. Заметить это можно только сверкой выплат — то есть тем способом, который постановка называет самым
   дорогим.

**Действие.** Выводить `source` на сервере: `explicit` — только когда код пришёл из явного поля формы;
`guest_link`/`cookie` — только из разобранной серверной стороной cookie `__Host-n5_referral`
(`readReferral(request.headers.get('cookie'))`), с требованием совпадения кода. Тело запроса не должно
уметь назвать источник.

### RT-002 · высокая · Один аккаунт навсегда блокирует любой известный ему партнёрский код

**Утверждение.** Антифрод считает ВСЕ попытки применения действующего кода, включая конфликтные,
и коммитит их. 50 вызовов `code.apply` с одного /24 за 10 минут переводят код в `blocked`
безвозвратно. Атака выполняется одним аккаунтом с одного адреса за пару минут.

**Доказательство.**

- `apps/web/src/server/partner.ts:48-49` — `INSERT INTO growth_event ... 'code_applied'` выполняется
  ДО проверки существующей атрибуции.
- `apps/web/src/server/partner.ts:58-59` — конфликт (`result = conflict()`) не выбрасывается сразу.
- `apps/web/src/server/partner.ts:76,79` — `COMMIT` выполняется и в случае конфликта; исключение
  бросается уже после коммита. То есть каждая отказная попытка остаётся в счётчике.
- `apps/web/src/server/partner.ts:50-56` — при `count >= 50` код переводится в
  `status='blocked', blocked_reason='antifraud_ip_burst'`.
- `apps/web/src/server/rate-limit.ts:11` — `allowMutation` разрешает 30 мутаций в минуту на аккаунт;
  50 вызовов укладываются примерно в две минуты.
- `apps/web/src/server/partner-code.ts:10-11` — «A blocked personal code is retained, never replaced»:
  заблокированный личный код не заменяется новым, снятия блокировки в коде нет вообще
  (`grep -rn "blocked_reason" apps` даёт только установку и чтение).

**Следствие.** После атаки: новые регистрации по коду получают `422 code_blocked`
(`partner.ts:44`), короткая ссылка и гостевые пакеты продолжают помечать события этим мёртвым кодом
(`short-link.ts:10-14`, `guest-pack.ts:63-65`), а вернуть партнёру рабочий код нечем. Это полный и
необратимый вывод партнёра из строя чужими руками.

**Оговорка честности.** Постановка формулирует правило именно так («50 применений кода с одного
префикса за 10 минут → блокировка»), и реализация ей соответствует. Дефект — в самом правиле:
счётчик считает действия ПОСТРАДАВШЕЙ стороны по инициативе атакующего.

**Действие.** Считать не попытки, а различные `account_id`, создавшие или изменившие атрибуцию;
блокировку делать снимаемой (владельцем кабинета или поддержкой) и не терминальной; при блокировке
уведомлять партнёра.

### RT-003 · средняя · Самореферал стирает уже действующую атрибуцию и делает её невосстановимой

**Утверждение.** Если у аккаунта есть атрибуция `cookie` или `guest_link`, а затем он применяет
СВОЙ собственный код, замена разрешается и строка переписывается в `status='rejected'`. Прежний
партнёр теряет регистрацию, и восстановить её невозможно никогда.

**Доказательство.**

- `apps/web/src/server/partner.ts:61-62` — при `self` в `values` подставляются
  `status='rejected', reject_reason='self_referral'`.
- `apps/web/src/server/partner.ts:65-68` — эти же `values` идут в `UPDATE attribution SET ... status=$4`;
  ветка `self` из UPDATE не исключена. Условие `replacementAllowed` (строки 19-26) для пары
  `cookie → explicit` возвращает `true` независимо от того, свой это код или чужой.
- `apps/web/src/server/partner.ts:21` — `if (existing.status === 'rejected') return false`: после
  перезаписи любая последующая попытка даёт `409` навсегда.

**Следствие.** Пользователь, пришедший по ссылке партнёра A, одним применением собственного кода
обнуляет регистрацию A — и своей атрибуции тоже не получает. Величина, влияющая на выплаты,
изменяется без следа о том, что она была.

**Действие.** При `self === true` не трогать существующую строку: отклонять попытку (409/422) и
записывать только аудит. Создание `rejected/self_referral` оставить только для случая, когда строки
ещё нет.

### RT-004 · средняя · Отказ на раннем шаге очистки навсегда останавливает стирание аккаунтов

**Утверждение.** Стирание аккаунта — последний шаг `retentionTick`, и все шаги до него не обёрнуты в
обработку ошибок. Детерминированная ошибка на любом раннем шаге означает, что стирание не выполнится
никогда, а просрочка `erase_deadline` (72 часа) нигде не наблюдается.

**Доказательство.**

- `apps/web/src/server/retention.ts:46-50` — цикл отзыва истёкших гостевых пакетов, без `try`.
- `apps/web/src/server/retention.ts:51-57` — `DELETE FROM video ... failure_reason='refused_user_uploads'`,
  без `try`. Внешние ключи `clip.video_id`, `transcript.video_id`, `job_attempt.video_id`,
  `guest_pack.video_id` объявлены без `ON DELETE` (`packages/db/migrations/001_init.sql:48,40,143,88`),
  то есть любая дочерняя строка делает этот DELETE неустранимой ошибкой FK.
- `apps/web/src/server/retention.ts:58-62` — выборка клипов, без `try`.
- `apps/web/src/server/retention.ts:70-78` — цикл стирания аккаунтов идёт ПОСЛЕ всего этого; только он и
  цикл удаления клипов защищены `try/catch`.
- `grep -rn "erase_deadline"` даёт только запись (`erasure.ts:18`) и показ пользователю
  (`erasure-page.ts:10-12`). Ни одной проверки «есть аккаунт `erasing` с просроченным `erase_deadline`».

**Оговорка честности.** Достижимость FK-ошибки сегодня низкая: у видео с `refused_user_uploads`
дочерних строк не возникает (`apps/web/src/server/video.ts:47-55` — отказ наступает до
`storage.initiate` и до любой постановки задачи). Находка о структуре, а не о наблюдённом падении:
порядок шагов делает юридическое обязательство заложником самого хрупкого соседа.

**Действие.** Каждый шаг тика обернуть в `try/catch` с накоплением `errors`; цикл стирания аккаунтов
поставить ПЕРВЫМ; добавить детерминированный страж «нет аккаунтов `status='erasing'` с
`erase_deadline < now()`» (слой 1 по лестнице стоимости обнаружения).

### RT-005 · средняя · ADR-008 обещает на гостевой странице контакт для жалобы; контакта нет

**Утверждение.** ADR-008 (`docs/ADR.md:248-249`): «На странице — контакт для жалобы; снятие по
требованию — не позже 72 ч». На странице нет ни адреса, ни формы: гостю предлагается обратиться к
ведущему — то есть к той самой стороне, чьё действие он оспаривает.

**Доказательство.**

- `apps/web/src/server/guest-page.ts:42` — единственная соответствующая строка:
  «Чтобы отозвать публикацию, свяжитесь с ведущим, который прислал эту ссылку».
- `docs/ADR.md:248-249` — текст решения.

**Следствие.** Обязательство по ст. 152.1 ГК РФ (снятие по требованию) не имеет канала исполнения,
если ведущий недоступен или отказывает. Это правовая граница, а не оформление.

**Действие.** Добавить на страницу адрес оператора (почта или форма) и объявленный срок реакции;
предусмотреть отзыв пакета по обращению гостя на стороне оператора.

### RT-006 · средняя · Истечение срока записывается тем же полем, что и отзыв ведущего

**Утверждение.** Автоматическая уборка проставляет `revoked_at` истёкшим пакетам. После этого
юридически значимое действие ведущего (отзыв) неотличимо от простого истечения 14 дней — ни в базе,
ни на экране.

**Доказательство.**

- `apps/web/src/server/retention.ts:46-47` — `UPDATE guest_pack SET revoked_at=$1 WHERE revoked_at IS NULL
  AND expires_at<=$1`.
- `apps/web/src/app/clips/GuestPacks.tsx:48` — ведущему показывается «Пакет отозван», потому что
  `revoked_at` проверяется первым, раньше `expires_at`.
- Доступ и без этого закрыт: `apps/web/src/server/guest-pack.ts:86` и
  `apps/web/src/server/clip-file.ts:31` независимо требуют `p.expires_at>$now`. То есть запись
  `revoked_at` ничего не защищает и только теряет различие.

**Действие.** Не трогать `revoked_at` при истечении (доступ закрыт сроком), либо ввести отдельное поле
`expired_at`. В UI различать «срок истёк» и «отозван ведущим».

### RT-007 · средняя · Маршрут файла клипа не ограничен по частоте, хотя именно он проксирует байты

**Утверждение.** `/api/clips/{clipId}/file` и `/thumbnail` — единственные маршруты, которые в гостевом
режиме читают объект из S3 и переливают его клиенту через наш процесс. На них нет ограничителя частоты,
хотя он есть на обеих соседних публичных страницах.

**Доказательство.**

- `apps/web/src/server/screen-runtime.ts:11-21` — `clipRoute` собирает обработчик без `allowRead`
  и без `clientIp`.
- `apps/web/src/server/clip-file.ts:47` — `return await deps.stream(await deps.sign(key, filename), request)`:
  сервер сам скачивает объект и отдаёт поток.
- Для сравнения: `apps/web/src/server/guest-page.ts:68` и
  `apps/web/src/server/short-link-handler.ts:45` вызывают `allowRead` (120/мин,
  `apps/web/src/server/rate-limit.ts:14`).

**Следствие.** Держатель одного действительного гостевого кода получает неограниченный по частоте
канал перекачки через наш сервер: трафик и соединения наши, ограничения нет. Перебором это не
эксплуатируется (код — 192 бита, `guest-pack.ts:49`), так что это отказ в обслуживании и счёт за
трафик, а не утечка.

**Действие.** Добавить `allowRead` в `clipRoute` для обоих видов, как на `/c/` и `/g/`.

### RT-008 · низкая · Самопереходы владельца не считаются только когда он вошёл

**Утверждение.** Исключение владельца проверяется по идентификатору сессии. Вышедший из аккаунта
владелец, открывший свою же ссылку, пишет `link_view` / `guest_opened` и получает referral-cookie со
своим же кодом.

**Доказательство.** `apps/web/src/server/short-link.ts:26` (`if (account === link.account_id) return`),
`apps/web/src/server/guest-pack.ts:93`, `apps/web/src/lib/partner-referral.ts:8`
(`self` приходит как `session?.account_id === ...`, при отсутствии сессии — `false`).

**Следствие.** ADR-007 («Самопереходы владельца … не создают ни атрибуции, ни `growth_event`»)
выполняется не полностью. Дальше: владелец, открыв свою ссылку без входа и зарегистрировав второй
аккаунт, получит атрибуцию на себя — проверка `self` сравнивает разные `account_id`
(`partner.ts:61`) и её не поймает.

**Действие.** Либо признать ограничение письменно в ADR-007, либо связывать самопереход не только
сессией.

### RT-009 · низкая · Стирание партнёра удаляет атрибуции ЧУЖИХ аккаунтов

**Утверждение.** При стирании аккаунта-партнёра удаляются строки `attribution`, принадлежащие другим,
живым аккаунтам.

**Доказательство.** `apps/web/src/server/retention.ts:31-32` —
`DELETE FROM attribution WHERE account_id=$1 OR partner_code_id IN (... коды этого партнёра)`.

**Следствие.** Технически это вынужденно: `attribution.partner_code_id` объявлен `NOT NULL`
(`001_init.sql:122`), а `partner_code` удаляется строкой 33. Но последствие — чужие аккаунты молча
теряют источник и после этого снова свободны применить любой код. Величина, влияющая на выплаты,
меняется у третьих лиц без записи.

**Действие.** Назвать это следствие в документе о стирании; рассмотреть `partner_code_id` nullable +
`ON DELETE SET NULL` со статусом `rejected`/`orphaned`, чтобы факт регистрации сохранялся обезличенно —
так же, как это уже сделано для `growth_event`.

### RT-010 · низкая · `/c/{code}` отдаёт прямой подписанный URL S3 на превью

**Утверждение.** Публичная страница короткой ссылки вставляет в `<img>` прямой presigned-URL объекта
хранилища на 900 секунд. Отзыв ссылки (`clip_link.revoked_at`) его не закрывает.

**Доказательство.** `apps/web/src/app/c/[code]/route.ts:21` (`generateDownloadUrl`),
`packages/s3/src/presign.ts:15-19`, `packages/shared/src/upload.ts:3` (`PRESIGNED_SECONDS = 900`),
CSP `img-src https: http:` (`short-link-handler.ts:39`).

**Оговорка.** Это превью (`thumbnail_key`), а не файл клипа; требование «ровно два пути» относится к
файлу и не нарушено. Но здесь раскрывается адрес хранилища и выдаётся неотзываемый bearer-URL — ровно
то, чего гостевой путь избегает сознательно.

**Действие.** Либо проксировать превью тем же способом, что гостевой файл, либо записать решение явно.

### RT-011 · высокая (о доказательности, не о коде) · «490 зелёных тестов» измерением не подтверждается

**Утверждение.** 490 — это ОБЩЕЕ число тестов, из них исполнено 356, а 134 пропущены. В моей области
пропущены ВСЕ интеграционные тесты — то есть ровно те, что проверяют свойства, ради которых написано
это ревью.

**Доказательство (измерено здесь).**

```
npx vitest run --reporter=dot
Test Files  45 passed | 16 skipped (61)
      Tests  356 passed | 134 skipped (490)
```

Поимённо по моей области — `npx vitest run` на четырёх файлах даёт 40 тестов, 0 passed, 40 skipped:

| Файл | Тестов | Исполнено |
|---|---:|---:|
| `tests/guest-pack.integration.test.ts` | 11 | 0 |
| `tests/partner.integration.test.ts` | 15 | 0 |
| `tests/retention.integration.test.ts` | 5 | 0 |
| `tests/short-link.integration.test.ts` | 9 | 0 |

Отчёты Codex это признают прямо (`docs/features/guest-pack/07_code_report.md`, таблица мутаций:
«Отзыв закрывает файлы — **NOT RUN**», «Два пути к файлу — **NOT RUN**», «Уникальность `guest_opened` —
**NOT RUN**»; `docs/features/partner-codes-and-dashboard/07_code_report.md`: все четыре исхода ADR-007
на настоящей БД — «NOT RUN»). Претензия «490 зелёных» принадлежит не отчётам, а пересказу.

**Действие.** Либо поднять стенд и исполнить 134 пропущенных, либо перестать называть число 490
зелёным. Свойства RT-уровня (атомарность `ON CONFLICT`, частичные уникальные индексы, `FOR UPDATE`,
фактическое удаление объектов в MinIO) чтением кода не доказываются.

## Проверено и верно

1. **`404` вместо `403` — выдержано на всех маршрутах ресурса.** `ScreenService` (`screen.ts:40,45,68`),
   `GuestPackService` (`guest-pack.ts:14,40,61,76,87`), `ShortLinkService` (`short-link.ts:9,22,49`),
   `createClipFileHandler` (`clip-file.ts:16`), страница записи (`dashboard/videos/[videoId]/page.tsx:12,18`),

   `apps/web/src` даёт ровно два места: `partner.ts:88` — кабинет партнёра, единственное разрешённое
   постановкой (и оно ничего не подтверждает: 403 выдаётся и на несуществующий UUID), и
   `upload-handler.ts:12` / `auth-handler.ts:36` — отказ по заголовку `Origin`, то есть CSRF, а не
   существование ресурса.
2. **Владение определяется сессией.** `ctx.account` в tRPC берётся только из `authorizeUpload`
   (`upload-handler.ts:9-17`) либо из `auth.authenticate` на GET (`api/trpc/[trpc]/route.ts:33-40`).
   Ни одна входная схема не содержит `account_id`, все схемы `.strict()`. `findSession` дополнительно
   требует `a.status='active'` (`auth-store.ts:33-35`), `login` — тоже (`auth.ts:37`).
3. **Путей к файлу клипа ровно два.** Единственный запрос в `clip-file.ts:25-31` выражает их одной
   дизъюнкцией: `($3 IS NULL AND v.account_id=$2)` либо `($3 IS NOT NULL AND EXISTS(... guest_pack
   JOIN guest_pack_clip ... p.code=$3 AND p.revoked_at IS NULL AND p.sent_at IS NOT NULL AND
   p.expires_at>$4))`. Третьей ветки нет; гостевой код без строки связи `guest_pack_clip` не даёт
   доступа; пакет чужого аккаунта отсекается `p.account_id=v.account_id`.
4. **ADR-008 выполнен.** `createSchema` (`guest-pack.ts:11-13`) требует `z.literal(true)`, точную
   версию текста и точный SHA-256; `safeParse` вызывается ДО `pool.connect()` и `BEGIN`
   (`guest-pack.ts:32-37`), поэтому при отказе строки не появляется вовсе. Отсутствующее поле и `false`
   неразличимы — оба валят `z.literal(true)`. Второй рубеж в базе: `CHECK (consent_confirmed = true)`,
   `consent_version <> ''`, `consent_text_hash <> ''` (`001_init.sql:90-92`). Других мест вставки в
   `guest_pack` в коде нет.
5. **Отзыв действительно закрывает файлы.** Гостевой `302` ведёт на НАШ же маршрут с HMAC-билетом
   (`clip-file.ts:49-54`), а не на объект: `guestFileTicket` подписывает `[id, kind, code, download, until]`
   (`guest-file.ts:4-6`), срок билета ограничен сверху и снизу (`guest-file.ts:8`, ≤900 с),
   сравнение постоянного времени (`guest-file.ts:10`). На КАЖДОМ обращении, включая повторное по уже
   выданному билету, сначала выполняется тот же запрос к БД (`clip-file.ts:24-32`) — то есть отзыв
   действует немедленно. Адрес S3 гостю не раскрывается: `streamGuestFile` читает объект сервером
   (`guest-file.ts:16`, `redirect: 'error'`, валидация `Range`, `private, no-store`). Прямой
   presigned-редирект остался только у владельца (`clip-file.ts:56`).
6. **Четыре исхода ADR-007 реализованы, и 422 не откатывается к cookie.** `replacementAllowed`
   (`partner.ts:19-26`): `explicit → любой` = false → 409; `guest_link → cookie` = false → 409;
   `cookie → explicit` = true, и `UPDATE ... replaced_source=source` (`partner.ts:66`) сохраняет
   прежний источник. Недействительный или неизвестный код бросает 422 (`partner.ts:32,43`) ДО вставки
   `code_applied` и до касания `attribution`; транзакция откатывается (`partner.ts:77`). Клиент тоже не
   ретраит (`AuthForm.tsx:21-23`). Условие `WHERE` в SQL-обновлении (`partner.ts:67-68`) совпадает с
   JS-предикатом — рассинхронизации двух правил нет.
7. **Стирание убирает объекты, а не только строки, и отзыв пакетов идёт первым.** В
   `ErasureService.request` порядок: сессии (`erasure.ts:19`), **гостевые пакеты (`:20`)**, короткие
   ссылки (`:21-22`), `video.deleted_at` + `fence+1` (`:24`). Хранилище трогается не раньше чем через
   час (`ERASURE_QUIET_MS`, `retention.ts:5,70-71`) — дольше, чем живёт любая выданная подпись
   (`PRESIGNED_SECONDS = 900`). Префиксы удаления совпадают с генерацией ключей побайтно:
   `videos/${account}/` ↔ `video.ts:43`; `clips/free|paid/${video.id}/` ↔ `workers/render.ts:35`;
   `thumbs/${video.id}/` ↔ `workers/render.ts:36`. `erasePrefix` (`packages/s3/src/erasure.ts`)
   отказывает на версионированном бакете (`:10-11`), обрывает незавершённые multipart (`:13-22`) —
   то есть закрывает и невидимые в листинге тарифицируемые части, — проверяет принадлежность каждого
   ключа префиксу (`:16,31`) и перечитывает первую страницу, а не идёт по курсору (`:24-33`).
8. **`growth_event` переживает удаление и обезличивается.** Все шесть внешних ключей объявлены
   `ON DELETE SET NULL` (`001_init.sql:107-112`); `grep -rn CASCADE` по миграциям и коду не даёт ни
   одного совпадения; `DELETE FROM growth_event` не встречается нигде. При стирании аккаунта
   `retention.ts:16-22` дополнительно занулляет и `ip_prefix`, покрывая шесть путей связи, а не только
   прямой `account_id`.
9. **Уникальность обеспечивает база.** `growth_event_link_view_unique` и
   `growth_event_guest_opened_unique` — частичные уникальные индексы по `(ссылка, ip_prefix, day)`
   (`001_init.sql:117-118`); код лишь пишет `ON CONFLICT DO NOTHING` (`short-link.ts:30-32`,
   `guest-pack.ts:97-100`) и увеличивает счётчик только когда вставка состоялась
   (`short-link.ts:33`, `guest-pack.ts:101`). Дыра «NULL не конфликтует с NULL» закрыта отдельным
   `CHECK`: для этих двух типов `ip_prefix` обязателен (`002_growth_event_prefix.sql:3-4`).
   `day` — московские сутки (`moscowDay`), а не UTC.
10. **Антифрод в объявленной форме присутствует.** Окно `(now − 10 минут, now]` и порог 50
    (`partner.ts:50-53`), блокировка и аудит коммитятся до ответа (`partner.ts:54-56,76`); самореферал
    даёт `rejected/self_referral` и не попадает в регистрации (`partner.ts:61-62`, `:96` —
    `status <> 'rejected'`); самопереходы вошедшего владельца не пишут событий
    (`short-link.ts:26`, `guest-pack.ts:93`). Ограничения этой конструкции — RT-002, RT-003, RT-008.

Попутно (вне списка из постановки, но в границах доверия): гостевая страница экранирует имя гостя и
заголовки клипов (`guest-page.ts:13-15,27,33`), отдаёт `noindex` и в заголовке, и в `<meta>`,
CSP с nonce и без `unsafe-inline` для скриптов (`guest-page.ts:63,73`), `Cache-Control: no-store`,
`Referrer-Policy: no-referrer`; код пакета — 192 бита (`randomBytes(24)`, `guest-pack.ts:49`) при
требуемых ADR-008 128; неотправленный, отозванный, истёкший и несуществующий пакет дают один и тот же
404 одним и тем же кодовым путём (`guest-pack.ts:85-87`).

## Не смог проверить

1. **Ничего не исполнялось против настоящих PostgreSQL 16 / Redis 7 / MinIO.** Все утверждения об
   атомарности (`ON CONFLICT DO NOTHING`, `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`), о
   срабатывании частичных уникальных индексов и о фактическом удалении объектов получены ЧТЕНИЕМ.
   Это принципиальное ограничение: конкурентные свойства чтением не доказываются. См. RT-011.
2. **Мутационные стражи трёх ключевых свойств не запускались** («Отзыв закрывает файлы», «Два пути к
   файлу», «Уникальность `guest_opened`») — по собственному признанию отчёта
   `docs/features/guest-pack/07_code_report.md`. То есть неизвестно, умеют ли соответствующие проверки
   краснеть.
3. **Поведение настоящего браузера на гостевой странице.** CSP `media-src 'self'` + `img-src 'self'`
   в связке с 302-редиректом на тот же origin и последующим стримом читается как рабочее, но ни один
   браузер этого не подтверждал. По правилу `embeddable-widget` вердикт здесь выносит только браузер.
4. **Фактическое стирание в хранилище.** `erasePrefix` разобран построчно, но `docker info` в этой
   среде недоступен; ни одного объекта не удалялось и не проверялось, что бакет непроверсионирован.
5. **Цена RT-001 и RT-003 в деньгах.** Выплат и балансов в коде нет
   (`docs/features/partner-codes-and-dashboard/07_code_report.md`: «Выплаты и балансы не добавлены»),
   поэтому оценка «влияет на выплаты» опирается на назначение счётчиков кабинета, а не на существующий
   расчёт.
6. **Достижимость FK-ошибки в RT-004** проверена только рассуждением по коду `video.ts:47-55`;
   прогон с настоящей базой не делался.
