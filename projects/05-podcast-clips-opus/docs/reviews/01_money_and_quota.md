### RM-001 — как воспроизведено и почему это деньги

Механизм. `lockCurrent` (`transcription.ts:8-14`) блокирует **только** `video`
(`FOR UPDATE OF v`). Присоединённая `job_attempt` строкой не блокируется, и когда вторая
транзакция дожидается блокировки `video`, PostgreSQL пересчитывает план (EvalPlanQual), подставляя
обновлённый кортеж ТОЛЬКО для заблокированного отношения, а для остальных переиспользуя копию,
снятую до ожидания. Условия на `v` при этом перепроверяются — поэтому `acceptProbe`
(`probe.ts:15-19`, условие `v.status='queued'`) от этого класса защищён, а `authorizeSttCall`,
у которого решение зависит от колонки `j.stt_calls`, — нет.

Отдельная проверка этого механизма на голых таблицах: транзакция A держала блокировку и записала
`{"0": 1}`; транзакция B, вставшая на той же блокировке до фиксации A, после разблокировки прочитала
`{}` и завершилась. Это не предположение о PostgreSQL, а наблюдение.

Прогон настоящего кода. Отдельный одноразовый контейнер `postgres:16.4-alpine` без публикации
портов, схема из `packages/db/src/migrate`, фикстура как в `tests/transcription.integration.test.ts`
(запись 120 с, первичное списание `acceptProbe` = 2 минуты). Третье соединение удерживало
`SELECT id FROM video … FOR UPDATE` 400 мс, пока обе транзакции `authorizeSttCall` вставали на
блокировку, — это и есть та одновременность, которую даёт повторная доставка задания:

```
{"авторизовано":[1,1],"минут_было":2,"минут_стало":2,"счётчик_попыток":{"0":1}}
```

Читается так: **два платных обращения к Whisper авторизованы, списано ноль минут, в счётчике
попыток единица.** Честный итог — 2 дополнительные минуты. Контрольный прогон тем же способом по
`authorizeSelection` (фича 5): `{"авторизовано_вызовов":1,"llm_было":0,"llm_стало":1}` — там защита
есть и работает, что и подтверждает: дефект не в стенде, а в `transcription.ts`.

Три следствия, и второе хуже первого:

1. Платная минута не списана — потолок `user_minutes`/`global_minutes` на эту величину не двигается.
2. Счётчик попыток затирается (`{"0":1}` вместо `{"0":2}`), поэтому и `STT_MAX_ATTEMPTS = 3` на этой
   паре не срабатывает. Повторение гонки НЕ приближает ни потолок минут, ни потолок попыток —
   число неоплаченных вызовов Whisper ничем сверху не ограничено.
3. `job_attempt.unit_count` тоже не растёт (`transcription.ts:53` выполняется только при
   `previous > 0`), поэтому расхождение не видно и по учёту попыток в БД.

Достижимость. Нужна вторая одновременная доставка того же `(video_id, fence)`. Она предусмотрена
самим проектом: `maxStalledCount: 1` при `concurrency: 2` у `worker-stt`
(`apps/worker/src/runtime.ts:64`) — это механизм BullMQ, возвращающий «зависшее» задание в очередь,
пока исходный обработчик ещё выполняется; `.claude/rules/coding-style.md` («Очередь») называет этот
сценарий прямо. Сторож дополнительно переставляет в очередь каждую попытку в статусе
`running`/`deferred` на каждом проходе (`apps/web/src/server/watchdog.ts:29-44`), а `enqueue`
пропускает только задание, живущее в очереди прямо сейчас (`packages/queue/src/queues.ts:34-42`):
задание в состоянии `failed`/`completed` перезапускается. Я не инсценировал настоящий stall на
живом стенде — поэтому «достижимо предусмотренным механизмом», а не «наблюдалось в проде».

Почему серьёзность blocker, хотя достижимость требует дублирующей доставки: ровно этот класс уже был
принят как блокер в соседней фиче (FS-001), защита от него в соседнем файле уже написана, счёт
поставщика откатить нельзя, а закрывается это одним условным `UPDATE`.

## Проверено и верно

Ниже — то, что я открывал и на чём сходится; отчёты Codex (`docs/features/*/07_code_report.md`)
использовались как указатель, ни одно утверждение не принято по отчёту.

1. **Единственная законная форма списания — единственная в коде.** `packages/db/src/quota.ts:28-31`:
   `INSERT … (used) VALUES (…,0) ON CONFLICT DO NOTHING`, затем
   `UPDATE … SET used = used + $4 WHERE … AND used::bigint + $4 <= $5 RETURNING used`, пустой
   результат — отказ. Запрещённой формы `INSERT … ON CONFLICT DO UPDATE … WHERE …` в коде нет:
   `grep -rn "ON CONFLICT (scope"` даёт одну точку, она же. Форма встречается только как
   подставляемый дефект в мутационном скрипте `scripts/test-upload-mutations.mjs:26-29` и как
   демонстрация в тесте `tests/upload.integration.test.ts:43-45` — в обоих случаях как ошибка, а не
   как реализация. Списание вызывается из шести мест, и все шесть идут через эту функцию:
   `video.ts:50`, `probe.ts:56`, `transcription.ts:47`, `selection.ts:53`, `video-retry.ts:28`,
   `quota.ts:50` (возврат).
2. **Предел — параметр окружения, в схеме его нет.** `001_init.sql:129-134`: колонки `limit` нет,
   `UNIQUE (scope, scope_key, day)` и `CHECK (used >= 0)` на месте; `$5` приходит из
   `limits[limitNames[scope]]` (`quota.ts:27`). Отсутствие колонки закреплено тестом
   `tests/database.integration.test.ts:31`.
3. **Пределы отказывают при старте, а не молчат.** `packages/shared/src/config.ts:17-33`: отсутствие,
   пустая строка, ноль, отрицательное, нецелое и значение вне `int` PostgreSQL — каждое бросает с
   названным внешним последствием. Ни одного `?? значение` на пути пределов нет. Переполнения
   `used + $4` быть не может: `WHERE` гарантирует `used + n <= limit <= 2147483647`.
4. **Порядок операций.** Квота `user_uploads` списывается ВНУТРИ транзакции заявки
   (`video.ts:44-56`), а `storage.initiate`/`sign` вызываются только после её фиксации
   (`:67`, `:87`) — подписанная ссылка не выдаётся до списания. Минуты списываются в `acceptProbe`
   (`probe.ts:56`) до `continueTranscription` (`workers/stt.ts:115-118`). Между вердиктом

   обращения наружу. Порядок STT-стадии дополнительно закреплён трассовым тестом

5. **Счёт по попыткам, а не по успехам.** `phase=attempt` пишется и синхронизируется (`file.sync()`)

## Не смог проверить

1. **Настоящий stall BullMQ на живом стенде.** Я доказал, что код небезопасен при одновременной
   доставке, и назвал предусмотренные механизмы такой доставки, но не инсценировал зависание
   обработчика в работающем `worker-stt`. Частота события в проде остаётся неизвестной; на вердикт
   это не влияет — защита обязана держать независимо от частоты.

## Как воспроизвести RM-001

Одноразовый PostgreSQL без публикации портов, случайный пароль:

```bash
docker run -d --name n5-review-epq -e POSTGRES_PASSWORD="$(openssl rand -hex 24)" postgres:16.4-alpine
```

Тест (vitest с конфигурацией, повторяющей алиасы `vitest.config.ts`) вызывает настоящие
`migrate`, `ensureInitialAttempt`, `acceptProbe` и `authorizeSttCall`; третье соединение удерживает
`SELECT id FROM video WHERE id=$1 FOR UPDATE` 400 мс, пока обе транзакции встают на блокировку:

```ts
const blocker = await pool.connect();
await blocker.query('BEGIN');
await blocker.query('SELECT id FROM video WHERE id=$1 FOR UPDATE', [f.video]);
const a = authorizeSttCall(pool, f.attempt, limits, 0, 120);
const b = authorizeSttCall(pool, f.attempt, limits, 0, 120);
await sleep(400);
await blocker.query('COMMIT'); blocker.release();
const [ra, rb] = await Promise.all([a, b]);
// ra === 1 && rb === 1, минут списано 0, stt_calls === {"0":1}
```

Утверждение, которое обязано держаться и не держится:
«сколько вызовов авторизовано — столько же платных единиц списано»
(`минут_списано === (число авторизованных − 1) × 2`, где −1 — покрытое первичным списанием `probe`).
