# Границы доверия N5

Шесть границ, через которые в продукт попадает чужое решение. У каждой — форма, которая её держит, и
внедряемый дефект, на котором соответствующий страж обязан покраснеть
([`guard-must-be-able-to-fail.md`](../../../../../.claude/rules/guard-must-be-able-to-fail.md)).

## Граница 1. Чужой файл

Клиент присылает имя, `Content-Type` и заявленный размер — верить нельзя ни одному.

```ts
// 1) заявленный размер — на video.create, ДО выдачи ссылок и ДО списания квоты
if (!Number.isInteger(declaredBytes) || declaredBytes <= 0 || declaredBytes > LIMITS.FILE_BYTES_MAX) return invalid();

// 2) фактический размер — HEAD после CompleteMultipartUpload; ВТОРАЯ проверка обязательна:
//    подпись сама размера не ограничивает
const { ContentLength } = await s3.headObject({ Key: objectKey });
if (Number(ContentLength) > LIMITS.FILE_BYTES_MAX) { await failWithRefund('too_large'); return invalid(); }

// 3) тип — по МАГИЧЕСКИМ БАЙТАМ, диапазонным чтением первых байт объекта
const head = await s3.getObjectRange(objectKey, 0, 64);
if (!sniffMediaType(head)) { await failWithRefund('not_media'); return invalid(); }   // MP4/MOV/WebM/M4A/MP3
```

Длительность здесь НЕ измеряется: у `web` нет `ffprobe`, а атом `moov` у MP4 часто лежит в конце
файла — диапазонное чтение вернуло бы «неизвестно» на законном файле, и по fail-closed это стало бы
отказом добросовестному пользователю (DEC-A-011, V2-R11). Измерение живёт в `ProbeSource`, где
оригинал уже скачан:

```ts
const probe = await runWithTimeout('ffprobe', args, PROBE_TIMEOUT_MS);   // ОТДЕЛЬНЫЙ процесс
if (probe.timedOut) { await failWithRefund('probe_timeout'); return; }   // зависший разбор — отказ, а не ожидание
if (!probe.hasAudio) return failWithRefund('no_audio');
if (probe.durationSec < LIMITS.DURATION_SEC_MIN) return failWithRefund('too_short');
if (probe.durationSec > LIMITS.DURATION_SEC_MAX) return failWithRefund('too_long');
```

Все шесть — отказы по СВОЙСТВАМ файла, и каждый возвращает слот `user_uploads` в ТОЙ ЖЕ транзакции,
что пишет `failed`. Отказ по потолку слот не возвращает: там всё сработало как задумано.

**Внедряемый дефект:** доверять расширению или `Content-Type`; вызывать возврат слота для любого
`failed`, включая `refused_*`.

## Граница 2. Деньги — потолок ДО платного вызова

Полная форма — [`coding-standards`](../coding-standards/SKILL.md) §1. Здесь свойство, ради которого
она такая:

- Списание атомарно **двумя операторами в одной транзакции**; пустой результат `UPDATE` — отказ.
- Ключи собираются ПО ПРИЧИНЕ, и у причины `llm` их **два**: `user_llm` и `global_llm`. Один
  глобальный не связывает — аккаунт, нажимающий «повторить», исчерпал бы общие 20 вызовов в
  одиночку и продукт отказал бы всем остальным по причине, в которой они не виноваты (V2-R21).
- Вызов поставщика после `refused` не выполняется НИКОГДА, ни на одной ветке.
- Счёт по ПОПЫТКАМ: повтор чанка после таймаута списывает минуты заново ДО повторного обращения к
  `whisper-1` (V2-R14). Поставщик берёт деньги за попытку, а не за успех.
- Деградации «обработаем моделью подешевле» и очереди на завтра НЕТ: обе переносят трату, а не
  отменяют.
- Каждая попытка пишет строку в `model-spend.jsonl` — и при успехе, и при отказе поставщика.

**Внедряемый дефект:** однооператорная форма `ON CONFLICT DO UPDATE … WHERE`; чтение
`quota_counter.limit` как колонки; списание по успехам вместо попыток.

## Граница 3. Подписанные ссылки на приватный бакет

Бакет приватный, публичных путей к нему не существует. `web` — единственный, кто подписывает.

```ts
// GET /api/clips/{clip_id}/file — авторизованный redirect, а не отдача байтов
const clip = await db.clip.findUnique({ where: { id } });
if (!clip) return notFound();
const allowed =
  (session && clip.video.accountId === session.accountId) ||
  (guestCode && await guestPackGrants(guestCode, clip.id));      // два пути здесь; третий — витрина (ADR-018,
                                                                  // showcase-file.ts, закрытый набор в коде), четвёртого нет
if (!allowed) return notFound();                                  // не 403: он подтвердил бы существование
if (clip.status !== 'done') return notFound();                    // файла ещё нет
if (clip.expiresAt && clip.expiresAt < new Date()) return notFound();  // срок истёк, объект удалён
return redirect(await s3.presignGet(clip.objectKey, { expiresIn: 900 }));   // ≤ 15 мин
```

Ключи объектов серверные; клиент их не назначает. Подписи и заголовки подписи в журналы не
попадают. Префикс зависит от тарифа (`clips/free/` либо `clips/paid/`): lifecycle бакета вешается
ТОЛЬКО на `free`, иначе он снёс бы клипы платного тарифа (V2-R24).

**Внедряемый дефект:** `403` вместо `404` на чужом клипе; срок ссылки больше 900 с; третий путь
доступа «по коду короткой ссылки» — `/c/{code}` ведёт на лендинг, а не на файл.

## Граница 4. Тариф — решение принимает сервер

```ts
export function watermarkRequired(plan: unknown): boolean {
  return plan !== 'paid';     // сравнение НА РАВЕНСТВО с единственным разрешающим значением
}
```

Значение берётся ТОЛЬКО из базы по `account_id` задания. Поле «без метки» в теле запроса не
читается ВООБЩЕ. Гостевые клипы — те же файлы: гость не `paid`, метка на них та же. Смена тарифа не
перерисовывает готовые клипы — метка вшита в пиксели.

Тест этой границы — перечень мусора, а не один случай:

```ts
for (const bad of [null, undefined, '', 'PAID', ' paid', 'premium', 0, 1, true, {}, ['paid']]) {
  expect(watermarkRequired(bad), JSON.stringify(bad)).toBe(true);
}
```

**Внедряемый дефект:** `plan !== 'free'` — даёт обратное поведение на тех же входах и открывает
снятие метки опечаткой.

## Граница 5. Согласие гостя — правовая, а не интерфейсная

Согласие фиксируется ВЕДУЩИМ до создания гостевой страницы (ADR-008). Без него `guest_pack` не
существует.

```ts
if (input.consentConfirmed !== true) {
  throw new TRPCError({ code: 'UNPROCESSABLE_CONTENT', message: 'нужно подтвердить согласие гостя' });
}
// только после этого — создание guest_pack и строк guest_pack_clip, в одной транзакции
```

Страница приватна по коду ≥ 128 бит, отдаётся с `noindex` и `Cache-Control: no-store`, живёт 14
дней **от отправки** (до отправки не открывается — V2-R18) и отзывается ведущим.

**Внедряемый дефект:** сделать поле необязательным; считать срок от создания, а не от отправки.

## Граница 6. Атрибуция партнёра — три источника, явный сильнее

Решение принимается по полю `attribution.source`, а не по факту существования строки.

| Было | Пришло | Ответ |
|---|---|---|
| `cookie` | `explicit` | `200`, `UPDATE` с записью прежнего в `replaced_source` |
| `explicit` | любой | `409` |
| `guest_link` | `cookie` | `409` |
| любое | недействительный код | **`422`, строка НЕ тронута** |

Недействительный код — ошибка ввода, а НЕ откат к cookie. Активация атрибуции — первый доведённый
до конца выпуск привязанного аккаунта (DEC-A-008), идемпотентно по условию `status = 'pending'`:
второе и третье видео ничего не меняют.

Анти-фрод: 50 применений одного кода с одного `ip_prefix` за 10 мин → `blocked`; самореферал →
`rejected`; самопереходы владельца не считаются. Уникальность переходов и открытий за сутки
обеспечивает **база** частичным индексом, а не код; счётчик `clip_link.unique_view_count` и вставка
события пишутся в ОДНОЙ транзакции (V2-R12, V2-R20).

**Внедряемый дефект:** разрешить откат к cookie при `422`; считать уникальность переходов в коде;
обновлять счётчик отдельным запросом вне транзакции.

## Что эти образцы НЕ закрывают

- **Вебхуков в продукте нет** (ADR-005): маршрут `/api/webhooks/yookassa` в боевом профиле не
  зарегистрирован, и это проверяется стражем. В тот момент, когда он появится,
  [`incoming-webhooks.md`](../../../../../.claude/rules/incoming-webhooks.md) вступает в силу целиком:
  подпись по сырым байтам первой, названный ключ повторности, ответ на перестановку.
- **Встраиваемого виджета нет:** `docs/embed-contract.md` отвечает «виджета нет» — законный ответ,
  а не пропуск. Если появится, три класса отказа из
  [`embeddable-widget.md`](../../../../../.claude/rules/embeddable-widget.md) проверяются на ЧУЖОМ
  origin, а не на своей демо-странице.
- **Ни одна из этих границ не проверена прогоном.** Все утверждения о поведении SQL и о поведении
  поставщиков выведены чтением документов (§7.3 отчёта валидации). Фактом их делает тест, который
  СНАЧАЛА показал красное.
