### 1.2 DoD второй очереди (не в первой неделе, не блокирует её приёмку)

Каждый пункт — самостоятельная небольшая фича, добавляемая ПОСЛЕ того, как ядро прошло §1.1;
ничего из ядра ими не блокируется, а метрика недели (§6) не зависит ни от одного из них
(`PRD.md` §«Очереди поставки»):

1. **Сброс пароля — только страница `/admin/users`; правка после validation-report V3-04
   (уточнение координатора OWN-05A-014a).** Прежняя версия этого пункта утверждала, что в первой
   неделе у забывшего пароль автора нет способа восстановить доступ вообще — это само расходилось
   с PRD §«Очереди поставки» и Specification FR-clips-1 п.5/SC-US-001-8, которые уже называли
   `ops reset-link` инструментом первой недели. Точная формулировка: **во 2-ю очередь уходит
   только веб-страница** — кнопка сброса на `/admin/users`. Сам сброс (одноразовая ссылка на
   почту) работает с первой недели командой оператора `docker compose exec worker-ai
   ops reset-link <email>` (canon §7, Pseudocode «Операции» шаг 5, VA2-22): аккаунт ищется по
   канонической почте (нет → код 1, письмо не отправляется); письмо со ссылкой
   `{BASE_URL}/reset?token=` уходит на почту аккаунта, сам токен оператору не показывается
   (`stdout` его не печатает); `GET /reset?token=` → `POST /api/auth/reset` — уже неделя 1, не
   вторая очередь; `audit_log(actor='ops-cli', action='account.reset_link', target=email)`. Тест:
   токен истёк/использован дважды → отказ (SC-US-001-8), все `refresh_token` отозваны при успехе.
2. `GET /admin/partners` — веб-страница вместо `ops partner-add`; тот же контракт данных
   (`partner_code` уникален, коллизия отклоняется), другой интерфейс.
3. `GET /admin/spend` — веб-страница вместо `ops spend-today`; тот же источник данных
   (`spend_ledger`/`quota_counter`), другой интерфейс. `model-cost-contract.md` «Где виден
   расход» меняется на эту страницу в момент, когда она появляется.
4. Экран fake-door (`/plans`, кнопка «Хочу без знака», событие `fakedoor_clicked`, стадия
   атрибуции `fakedoor`) — FR-GROWTH-003 п.7–8, FR-GROWTH-002 (стадия `fakedoor`), FR-clips-14 п.3.
   Метрика недели не использует этот экран: клик fake-door — сигнал интереса, не конверсия
   (canon §9).

Готовность второй очереди проверяется тем же способом, что и первой (юнит/интеграция/E2E,
мутационные стражи там, где они применимы) — но отдельным прогоном, не задним числом
пристёгнутым к DoD ядра.

**Отдельно — 7 дней беты для метрики недели.** Метрика недели считается «на 7-й день с первого

Сами 7 дней беты идут ПОСЛЕ последнего дня сборки и не сокращаются параллельной работой — они
календарные, не трудовые: нужно физическое время, чтобы 8–12 авторов загрузили видео, посмотрели
свои клипы и вернули подтверждённые ссылки, а оператор перепроверил их на `/admin/publications`
(FR-GROWTH-005 п.3). Итого от старта сборки до числа метрики — **21–26 календарных дня** (14–19
сборки + 7 беты), заметно больше «недели» в буквальном смысле — тот же факт, что был признан на
итерации 1 валидации (VA-09) и подтверждён итерацией 2 (VA2-24), теперь применённый к
уменьшенному (ядро-только) объёму, а не к полному 16–20-дневному.

## 2. Чек-лист развёртывания на VPS в Нидерландах

**Порядок обязателен**, не факультативен — каждый следующий шаг предполагает, что предыдущий
прошёл.

### 2.1 До первого `docker compose up`

```bash
node .claude/hooks/check-ports.cjs projects/05a-podcast-clips-opus            # Правило №0: БД/Redis/MinIO не публикованы
bash scripts/check-port-conflicts.sh projects/05a-podcast-clips-opus          # занятость портов на ЭТОЙ машине

```

Все четыре — детерминированные проверки слоя 1 (`cost-of-detection-ladder.md`). Прогонять после
**каждого** изменения `docker-compose.yml`, не только один раз в начале (`deployment-seams.md`).

### 2.2 Хостовые порты — только через переменную

`docker-compose.yml` объявляет `name: clipmkr` (canon §1, compose-hygiene правило №1). Хостовые
порты — исключительно `${VAR:-default}`, никогда голым числом (`port-conflicts-local.md`):

```yaml
caddy:
  ports:
    - "${CADDY_HTTP_PORT:-80}:80"
    - "${CADDY_HTTPS_PORT:-443}:443"
web:                                    # только тестовый профиль публикует наружу
  ports:
    - "127.0.0.1:${WEB_PORT:-3105}:3000"
```

`postgres`, `redis`, `minio` — без `ports:` вовсе в проде; в тестовом профиле — только
`127.0.0.1:`/`[::1]:` с случайным паролем (canon §1, `docker-ports.md` Правило №0). На сервере в
Нидерландах — конфликт с `80`/`443` местного machine list не актуален (это не машина разработки),
но `bash scripts/check-port-conflicts.sh` запускать всё равно: сервер может держать чужой сервис
(например, панель хостинга).

### 2.3 Образы и `restart`

- Все образы с явными тегами: `postgres:16-alpine`, `redis:7-alpine`, `caddy:2.8-alpine`, MinIO —
  `RELEASE.…`, не `latest` (canon §1, compose-hygiene правило №2).
- У всех сервисов, кроме `migrate` (одноразовый), — `restart: unless-stopped` (canon §1,
  compose-hygiene правило №4).
- `migrate` — одноразовый сервис, остальные ждут `condition: service_completed_successfully`
  (canon §1); зависимости с healthcheck — `condition: service_healthy` (compose-hygiene правило
  №3).
- `web` несёт `GET /api/health` — внутренний маршрут (canon §7), `200` только при доступных
  Postgres и Redis, без пользовательских данных; это и есть healthcheck сервиса `web` в
  `docker-compose.yml`, не отдельный ping без проверки зависимостей.

### 2.4 Секреты и переменные — полный список без дефолта

Все переменные из `canon.md` §6, помеченные «без дефолта» — включая все 9 потолков
(`LIMIT_STT_USER_SEC_DAY`, `LIMIT_STT_NEWBIE_SEC_DAY`, `LIMIT_STT_NEWBIE_GLOBAL_SEC_DAY`,
`LIMIT_UPLOADS_USER_DAY`, `LIMIT_LLM_USER_KOP_DAY`, `LIMIT_STT_GLOBAL_SEC_DAY`,
`LIMIT_LLM_GLOBAL_KOP_DAY`, `LIMIT_LLM_ATTEMPTS_JOB`, `LIMIT_LLM_KOP_JOB` — было «7», V3-05) —
выставляются ДО первого старта в проде. Отсутствие/пустота/невалидность любой из них — процесс не
стартует и называет переменную (NFR-clips-3, `honest-configuration.md` CFG-S1/I2). Проверить
перечень:

```bash
docker compose --profile prod config | grep -A2 'environment:'
```

Ключи моделей (`OPENROUTER_API_KEY`, `OPENAI_API_KEY`) — только у `worker-ai`; их **отсутствие** у
`web` и `worker-render` — часть проверки, не опечатка (ADR-004).

### 2.5 Миграции и первый старт

```bash
docker compose --profile prod up -d postgres redis minio    # (minio — только если решили держать тест на этом же хосте; в проде — Cloud.ru)
docker compose --profile prod run --rm migrate
docker compose --profile prod up -d web worker-ai worker-render caddy
```

`migrate` — `prisma migrate deploy` (canon §1); он завершается перед стартом остальных сервисов,
не одновременно с ними — иначе воспроизводится дефект R3-jan-audit («воркер стартовал раньше
миграций, падал на `relation … does not exist» и лежал 9 часов незамеченным»).

### 2.6 После старта — сквозной прогон на РАЗВЁРНУТОМ адресе

```bash
bash scripts/check-cjm.sh https://clipmkr.ru
```

Не «открылась ли страница», а путь целиком: регистрация → подтверждение письма → загрузка →
`running` → `succeeded` → просмотр → «Скачать» → «Скопировать подпись» → переход по
`https://clipmkr.ru/c/{clip_code}` **с телефона, не с localhost** (`deployment-seams.md`,
`Refinement.md` §2.3). Дефект `BASE_URL` виден только на шаге «перейти по выданной ссылке».

## 4. Логирование

- Уровень — `LOG_LEVEL` (дефолт `info` разрешён, canon §6).
- Формат — структурированный JSON (NFR-clips-8 п.1): обязательные поля `job_id` (когда
  применимо), `step`, `duration_ms`, `result`.
- Хранение: журнал живёт в stdout контейнера; ротация — средствами Docker (`json-file` драйвер с
  `max-size`/`max-file`, чтобы не заполнить диск — правило машины «диск VPS почти полон» не
  повторяется на новом сервере без присмотра).
- Персональные данные в журнале: сырой IP не пишется в таблицу `event` (NFR-clips-6 п.2); IP в
  журнале безопасности хранится не дольше 30 дней (NFR-clips-6 п.1).

## 5. Runbook: проба STT дня 1

Выполняется **до** написания кода конвейера (FR-clips-4 п.9, ADR-001 п.4) — блокирует выбор
`STT_MODEL`, не блокирует остальной код (интерфейс `Transcriber` пишется независимо от результата).

1. Подготовить вход: 10-минутный русский фрагмент подкаста с 2 собеседниками; ручная эталонная
   расшифровка 2 мин с разметкой спикеров (ADR-001 п.4).
2. Прогнать через тот же маршрут OpenRouter, что пойдёт в бой (тот же ключ, тот же адрес
   `https://openrouter.ai/api/v1`), с сервера в Нидерландах — не с машины разработки (ADR-003
   «Как проверить»): все 5 кандидатов ADR-001 — `assemblyai/universal-3-5-pro`,
   `deepgram/nova-3`, `microsoft/mai-transcribe-2`, `meta/muse-voice-transcribe-1.0`,
   `x-ai/grok-stt-1.0` (ADR-001, таблица кандидатов).
3. Резать по правилу ADR-002 (~90 с, пауза `silencedetect`, перекрытие 5 с) — тот же код, что
   пойдёт в конвейер, не отдельный скрипт пробы.
4. Оценить каждого кандидата по 7 критериям ADR-001 (таблица в разделе «Проба дня 1»): наличие
   таймкодов (100 %), метки спикеров через OpenRouter, WER ≤15 % на эталоне, верная метка спикера
   ≥90 %, расхождение начала фразы ≤300 мс, каждый 90-секундный кусок отвечает <60 с без обрывов,
   цена ≤62 ₽/час.
5. Из прошедших ВСЕ 7 критериев — выбрать самую дешёвую. Не прошла ни одна → переключить
   `STT_PROVIDER=openai` (прямой `gpt-4o-transcribe-diarize`) и повторить пробу той же моделью
   оценки. Не прошёл и он → стоп, вопрос владельцу — тихое снижение порогов запрещено (ADR-001).
6. Записать результат (модель, цифры по 7 критериям, дата) в `docs/probes/stt-day1.md`.
   Зафиксировать `STT_MODEL`/`STT_PROVIDER` в конфигурации прод-профиля — не в коде.
7. Юнит-тест адаптера параллельно (не зависит от результата пробы): ответ без `start_ms` →
   `no_timestamps`; ответ без `speaker` → сегменты без спикера + `speaker_labels_missing` в
   журнале (ADR-001 «Как проверить»).

## 6. Метрика недели и как её считать

**Формулировка (OWN-05A-002, FR-GROWTH-005 п.4):** ≥5 уникальных клипов со знаком в статусе
`confirmed` на 7-й день от ≥3 разных авторов.

**Как считается — точная процедура, не только определение:**

1. На 7-й день после запуска беты оператор открывает `/admin/publications` и перепроверяет
   **каждую** ссылку в статусе `confirmed`: пост публичный, в нём этот клип, знак виден
   (FR-clips-11, `/admin/publications`). Пост, который перестал существовать или стал приватным →
   статус `removed`, из счёта выбывает (ADR-014).
2. `/admin/metrics?from=<дата запуска беты>` выполняет запрос: `SELECT COUNT(DISTINCT clip_id),
   COUNT(DISTINCT account_id) FROM publication WHERE status = 'confirmed'` (после перепроверки
   шага 1) — счётчик СНЯТ ИЗ НАШЕЙ БД, не из внешнего API (площадки публикации не дают API-доступа
   к статистике поста, FR-clips-11).
3. Несколько ссылок на один клип считаются как 1 клип (уникальность по `clip_id`, FR-GROWTH-005
   п.4). Самоотчёты «я опубликовал(а)» без ссылки и `candidate`-ссылки — отдельные числа,
   **не складываются** с основным счётчиком (FR-clips-12 п.3).
4. Условие «от ≥3 разных авторов» проверяется отдельным полем того же запроса
   (`COUNT(DISTINCT account_id)`), не выводится из первого числа — 6 клипов одного автора не
   считаются достижением метрики (риск «метрику набирает один энтузиаст», PRD §7, AC …
   SC-US-007-3).
5. Источник значения для `Final_Summary.md`/отчёта владельцу — **наша БД**, из закрытого списка
   источников метрик (`sparc-prd-mini/SKILL.md` §«Success Metrics»: `наш журнал` | `наша БД` |
   `внешний API: <метод>` | `ручное измерение: <как>`). Здесь — `наша БД`, потому что счёт строится
   из таблицы `publication`, а не из внешнего API площадки.

**Что НЕ входит в метрику недели, но выводится рядом (FR-clips-12 п.3):** `i` (подтверждённые
внешние клипы на активированного автора) и `conv%` (доля активированных авторов с ≥1
подтверждённой публикацией; «k из n» при n < 30, не процент) — оба на том же `/admin/metrics`,
раздельными строками.

  (`guard-must-be-able-to-fail.md`) — перед мержем любого PR, трогающего платные вызовы или

### QA

- Тестовое окружение — `docker compose --profile test up`, MinIO вместо Cloud.ru S3 (OWN-004).
- Тестовые данные: синтетический 10-минутный русский фрагмент с 2 голосами (тот же, что для пробы

  (EC-3).

  свободным текстом: дефект без ID требования не трассируется назад.

### Operations

- Продакшн-доступ оператора в первую неделю (OWN-05A-014, ядро) — веб-страницы
  `/admin/publications`, `/admin/metrics`, `/admin/users` под ролью `account.role = 'operator'`
  (canon §5, §7); роль проверяется и в middleware, и в каждом серверном обработчике (ADR-012).
  `/admin/partners`, `/admin/spend` и кнопка сброса пароля на `/admin/users` — 2-я очередь
  (§1.2, V3-04/OWN-05A-014a: только эта кнопка, не весь сброс); их заменяют CLI `ops` внутри
  `worker-ai` (`docker compose exec worker-ai ops …`): `ops grant-operator <email>` (выдача роли),
  `ops stt-probe <файл>` (проба дня 1), `ops partner-add <имя> [код]` (партнёры),
  `ops spend-today` (расход), `ops beta-add <email>` (отметка бета-автора до старта беты,
  OWN-05A-016 — снимает квоту новичка), `ops reset-link <email>` (сброс пароля неделей 1,
  одноразовая ссылка на почту) — все шесть доступны и с хоста без стека
  (`node apps/worker/dist/cli/ops.js …`, canon §7). Прямого доступа к БД в проде нет в этом
  раннере.
- Runbook на этот файл (§2 «Развёртывание», §5 «Проба STT дня 1»).
- Эскалация: на неделе — ручная (владелец/оператор смотрят вывод `ops spend-today` раз в день,
  §3); нет автоматической эскалации, потому что она сама была бы внешним вызовом вне скоупа
  недели.
