### 2.3 E2E — на развёрнутом стенде, по ЧУЖОМУ адресу

Правило `deployment-seams.md`: модуль, корректный в изоляции, ничего не гарантирует о системе.
Юнит- и интеграционные тесты выше не поймают ни один из классов ниже — они об одном модуле, а
дефект живёт в стыке.

**Обязательное условие:** прогон обращается к адресу, который РАЗВЁРТЫВАНИЕ выдало
(`https://clipmkr.ru` в проде, или адрес тестового стенда), а не к `localhost`, который прогон и
так знает — иначе дефект `BASE_URL` (см. таблицу проекта 01 в `deployment-seams.md`) повторится
здесь буквально: `BASE_URL` присутствует в canon §6 как переменная без дефолта именно по этому
уроку.

| Сценарий | Путь | Что ловит |
|---|---|---|
| CJM целиком | регистрация → подтверждение email по реальному письму → загрузка 10-минутного файла → `running` → `succeeded` → просмотр → «Скачать» → «Скопировать подпись» → paste-back | обходной путь пропуска подтверждения; ссылка на `/c/{clip_code}` реально ведёт на `BASE_URL`, не на `localhost` |
| Граница reverse-proxy | прямой запрос к порту `web`/`worker-ai` мимо `caddy` | приложение не опубликовано рядом с прокси (NFR-clips-2 п.10); хранилища недоступны кроме петли (NFR-clips-2 п.9) |
| CORS/куки за прокси | `pref` (canon §7; 60 дней, ADR-015 п.3) ставится на реальном домене, `Secure`/`SameSite=Lax` соблюдены браузером | серверная cookie, а не JS-cookie (FR-GROWTH-002 п.1) — JS-cookie Safari ITP режет 7 днями, это видно только в реальном браузере |
| Загрузка части файла — браузером, не `curl` | реальный `PUT` части через `fetch`/`XHR` из браузера на подписанную ссылку S3; `response.headers.get('ETag')` | `ExposeHeaders: ETag` в CORS бакета действительно достаёт заголовок скрипту (VT-05/VA-07); `curl` не видит этот класс отказа — CORS применяет только браузер (`deployment-seams.md`) |
| Знак после сжатия площадки | клип перекодирован в 720×1280 H.264 1.5 Мбит/с, OCR (rus+eng) | FR-GROWTH-003 п.6, ≥9 из 10 тестовых клипов |
| Обрыв соединения клиента | клиент рвёт TCP посреди `POST …/complete` после получения `202`, но до чтения ответа | job_id уже создан в БД — задача продолжает жить (`long-job-contract.md`, класс `разрыв`) |
| Умерший воркер | `docker compose kill worker-ai` посреди задачи | переустановка через 5 мин, `worker_lost` после 3 попыток (EC-14, реальный BullMQ lock, не мок) |

### 2.4 Конкурентные и адверсариальные тесты (обязательны, не факультативны)

`shared-resource-verification.md`: правку проверяют на разделяемом ресурсе, а не только на своём
сценарии. Первые два теста ниже — правка VT-17: прежняя версия направляла конкурентный тест на
`complete`, который потолок не резервирует; резерв происходит на `POST /api/videos` (лимит
загрузок) и отдельно на допуске STT (остаток секунд).

1. **Лимит загрузок — `POST /api/videos`.** 20 одновременных запросов одного аккаунта при
   остатке 1 из дневного лимита 3 (FR-clips-2 п.7) → ровно 1 создаёт `video` и получает ссылки на
   части, 19 отказывают до выдачи ссылок; сумма созданных `video` за сутки не превышает 3
   (AC-clips-23).
2. **Допуск STT — резерв секунд.** N одновременных задач того же аккаунта при остатке потолка на
   1 задачу (например, остаток 45 мин, две задачи по 40 мин каждая) → проходит ровно та, чей
   резерв укладывается в остаток; сумма зарезервированных секунд по всем прошедшим не превышает
   остаток (FR-clips-10 п.3, AC-clips-12 SC-US-002-5).
3. **10 разных аккаунтов за одним NAT** одновременно создают задачи → никто не отказывает
   другому (персональный потолок — на `account_id`, не на IP; глобальный порог не путается с
   персональным).
4. **Аренда воркера рендера.** 3 задачи одновременно просят рендер при `RENDER_CONCURRENCY=1` →
   не больше 1 активного рендера, остальные ждут в очереди BullMQ, а не отказывают.
5. **VA-01 — повтор после отказа по потолку не обходит потолок.** Автор упирается в
   `failed/quota_user` (или сервис — в `quota_global`) на любом куске транскрипции. В те же сутки
   он нажимает «Повторить» (`POST /api/jobs/{job_id}/retry`). Ожидание: допуск STT проверяется
   **заново** перед постановкой оставшихся кусков в очередь (а не «первая попытка каждого куска
   считается оплаченной допуском» без факта допуска) → повтор даёт **0 новых вызовов STT**,
   `spend_ledger` не растёт, ответ — тот же `failed/quota_user`. Страж на этот тест — мутационный:
   удалить проверку допуска перед постановкой кусков → тест должен покраснеть (все 80 кусков ушли
   в OpenRouter мимо потолка).
6. **Перебор паролей (VT-07/VA-12).** 50 параллельных неверных попыток входа на один `email` →
   не больше предела `10` (FR-clips-1 п.4) дошло до `argon2.verify`; счётчик неуспехов —
   атомарный `INCR` **до** сравнения пароля, не «прочитать `GET`, потом инкрементировать при
   неудаче» (последнее пропускает конкурентные попытки мимо счётчика, `curl --parallel` обходит
   лимит целиком).
7. **Выполнимость LLM проверяется до оплаты STT (OWN-05A-012, VA-03/VT-03).** Три прогона:
   - видео 120 мин у автора и сервиса с достаточным остатком LLM-бюджета (≥ 2400 коп.,
     `LIMIT_LLM_KOP_JOB`) → допуск STT проходит, задача идёт в `transcribing` как обычно;
   - **тот же выпуск, но LLM отвечает невалидной схемой на первую попытку и тратит бюджет на 1
     повтор** (`LIMIT_LLM_ATTEMPTS_JOB = 2`, FR-clips-5 п.5) → резерв на допуске оценивается по
     ХУДШЕМУ случаю (обе попытки, не одна), и при остатке ≥ 2400 коп. вторая попытка всё равно
     укладывается в предел задачи, `succeeded` достигается после повтора, а не `selection_failed`
     из-за исчерпанного на первой попытке резерва;
   - видео, чей резерв LLM заведомо не помещается в остаток (например, у автора на сегодня
     осталось 300 из 5000 коп. `LIMIT_LLM_USER_KOP_DAY`, `SC-US-012-...` в Specification §8) →
     задача отказывает `failed/quota_user`/`quota_global` **на допуске, до первого вызова STT**;
     в `spend_ledger` нет ни одной строки `stt` для этой задачи (ADR-006 п.3).
   Страж на это — мутационный: временно убрать проверку допуска LLM из шага «Допуск STT» → третий
   прогон должен покраснеть (двухчасовой выпуск оплачивает STT целиком и падает
   `selection_failed` только на резерве LLM — ровно дефект VA-03, потраченные деньги без клипа).
8. **Знак переживает кадрирование до полезной полосы (OWN-05A-013, VA-05).** Отрендерить клип из
   16:9-исходника (полезная полоса `y = 420…1028`, знак `x = 70, y = 444` по формуле ADR-010 п.2),
   затем обрезать кадр до `crop=1080:608:0:420` (снять чёрные поля, как сделал бы автор в CapCut
   или в редакторе площадки) → знак остаётся в кадре и читается OCR (та же проверка, что
   FR-GROWTH-003 п.6, ≥ 9 из 10). До OWN-05A-013 знак стоял на чёрном поле и терялся при этой же
   операции без потери самого видео — это и был VA-05; тест фиксирует, что решение о переносе
   знака внутрь картинки действительно закрывает риск, а не просто переносит его на другую
   координату черноты.

### 2.5 Мутационная проверка стражей

`guard-must-be-able-to-fail.md`: страж, никогда не показавший красное, не является проверкой.
Каждый страж ниже обязан быть прогнан с внедрённым дефектом ДО того, как он засчитан:

| Страж | Внедрённый дефект для проверки на падение |
|---|---|
| `check-job-contract.cjs` | временно поставить `**Молчание:** выполняется` → ожидать `exit=1` |
| `check-model-cost.cjs` | временно поставить `**Потолок не сконфигурирован:** БЕЗ ОГРАНИЧЕНИЙ` → ожидать `exit=1` |
| Валидатор magic bytes | подать PDF под именем `.mp4` → ожидать `file_invalid`, НЕ `succeeded` |
| Атомарный резерв потолка | временно заменить на «прочитать-потом-записать», прогнать конкурентный тест 2.4.2 (допуск STT) → ожидать провал (сумма резервов превышает остаток) |
| VA-01: допуск STT перед постановкой кусков | временно убрать повторную проверку допуска в шаге «Повтор» → прогнать конкурентный тест 2.4.5 → ожидать провал (повтор после `quota_user` тратит STT без резерва) |
| VA-03/OWN-05A-012: выполнимость LLM до STT | временно убрать проверку допуска LLM из шага «Допуск STT» → прогнать тест 2.4.7 (третий прогон, заведомо непомещающийся выпуск) → ожидать провал (STT оплачен, падение только на `selection_failed`, деньги потрачены без клипа) |
| OWN-05A-013: знак внутри полезной полосы | временно вернуть знак на чёрное поле (координаты вне `y = 420…1028`) → прогнать тест 2.4.8 → ожидать провал (OCR не читает знак после `crop=1080:608:0:420`) |

## 4. Оптимизации производительности (после первого замера, не до)

`NFR-clips-1` — числа `[НЕ ПРОВЕРЕНО]`/`[ПРЕДЛОЖЕНИЕ]` до первого живого прогона (правило —
`silent-fallbacks.md`, «дорогой способ обнаружения — до, не после»). Оптимизировать раньше замера
запрещено постановкой (Specification §0): числа меняются после факта, не подгоняются под желаемое.

- **Кэширование** не применяется к платным вызовам (STT/LLM): каждый вызов — уникальный кусок
  аудио или уникальный транскрипт, повторный вызов на том же входе не предвидится в недельном
  скоупе.
- **Индексация:** уникальные индексы уже в схеме (canon §4) обслуживают И идемпотентность, И
  выборку — отдельного индекса «для скорости» не заводим до замера `EXPLAIN` на реальных данных.
- **Ленивая загрузка:** экран задачи не подгружает список клипов, пока `status != succeeded`
  (FR-clips-3 п.3) — единственная лени, требуемая постановкой.
- **После замера дня 1–2** (ADR-010 п.4): если рендер клипа 90 с превышает бюджет CPU, следующий
  шаг — не код, а конфигурация (`RENDER_CONCURRENCY`, `cpus:` в compose), пересмотр — только с
  владельцем, если это меняет тариф.

## 5. Усиление безопасности

Сверх `NFR-clips-2` (порядок операций) и `model-cost-contract.md` (пределы) — то, что относится
конкретно к вводу и аудиту:

- **Входная валидация:** порядок фиксирован (`security-operation-order.md`): аутентификация →
  лимит частоты (**до** валидации) → валидация (размер, magic bytes, схема) → резерв потолка
  (**после** валидации) → действие (NFR-clips-2 п.1). Смена порядка — регресс, а не рефакторинг.
- **Ограничение частоты:** регистрации ≤5/IP/час, вход ≤10 неуспешных/аккаунт/15 мин (FR-clips-1
  п.4); `/p/` ≤30/IP/час (SC-US-010-3); всё — **до** проверки пароля/кода.
- **Журналы аудита:** каждое изменяющее действие оператора пишет `audit_log` (кто, что, когда,
  причина) — FR-clips-11. Смена `plan` без причины — не принимается формой (FR-clips-11, страница
  `/admin/users`).
- **TLS:** проверка сертификата включена всегда для всех внешних вызовов (STT, LLM), отключение
  запрещено в любом профиле, включая тестовый (NFR-clips-2 п.6) — дефект донора B (R3-jan-audit
  находка 4) не переносится.
- **Секреты:** только из окружения; `JWT_SECRET` ≥ 32 байт; ключи моделей — только у `worker-ai`
  (ADR-004), проверяется списком `environment:` в `docker compose config`.

## 6. Доступность (WCAG, клавиатура)

Из `NFR-clips-7` и `FR-LOOK-012`/`FR-LOOK-013`:

- Ориентиры `nav`/`main`/`footer` на каждой странице.
- У кнопок — доступные имена (`aria-label`, если текст не самодостаточен: «Скачать клип
  “Название”», не просто «Скачать»).
- Таблица планов — семантика `table`/`row`/`rowheader`/`columnheader`, не набор `div`.
- Кнопки «Скачать»/«Поделиться» — не меньше 44×44 px (правило попадания пальцем, NFR-clips-7 п.4).
- Плеер несёт вшитые субтитры как часть видео (ASS burn-in) — отдельного WCAG-трека субтитров не
  требуется, т.к. подпись уже в кадре (FR-clips-7 п.3/4).
- Светлая/тёмная тема — токенами на `:root`, без постраничных переопределений (FR-LOOK-010).
