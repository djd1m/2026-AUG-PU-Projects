## 1. Сможет ли новый исполнитель поднять проект с нуля только по REPRODUCE?

Да, но последовательность требует двух поправок; ещё один известный дефект воспроизводится вместе с проектом.

- **P2 — `docs/REPRODUCE.md:77`: страж прав помещён в раздел «до всякого запуска стенда» → в этот момент нет `.env`, сети `reviewqr_default` и схемы БД → команда требует `.env` и сеть (`REPRODUCE.md:82–85`), а `scripts/check-db-grants.sh:21–45` обращается к уже мигрированной базе. Страж нужно выполнять в §6 после миграций и назначения паролей, перед запуском сервисов.**

- **P2 — `docs/REPRODUCE.md:37`: «Node на хосте не нужен» → обязательная проверка портов запускается через host-команду `node` (`REPRODUCE.md:117`), а рекомендуемый `npm test` также требует host npm → `package.json:11` лишь перенаправляет его в `scripts/test-all.sh`. Нужно либо добавить Node 22 в prerequisites, либо дать контейнерную команду для hook и предписать `bash scripts/test-all.sh`.**

- **P2 — `docs/REPRODUCE.md:105`: предлагается сгенерировать `SESSION_SECRET`, одновременно отмечено, что compose его не передаёт → исполнитель воспроизведёт работающий стенд, но `device_hash` будет подписан пустым секретом → `docker-compose.yml:32–41` не передаёт переменную, `apps/guest/src/journal.ts:49` использует `''`. Это воспроизводит известный G-13, а не требуемую защиту.**

Миграции 001–012, пароли ролей, порядок запуска, внешние зависимости и создание первой прикладной записи через регистрацию описаны; отдельный seed или импорт не требуется.

## 2. Все ли фичи учтены?

Таблица §13 покрывает реализованные `feat/fix`, три каталога `docs/features/*` и сгруппированные исправления `guest-ip-forwarding`; пропущенной реализованной фичи не найдено. `client-account-handover` корректно отмечена как план.

- **P2 — `docs/features/payment/04_refinement.md:13`: P-7 якобы проверяет «self-attribution → rejected + audit» → тест уже вставляет атрибуцию со статусом `rejected` и проверяет только отсутствие комиссии; ни отклонение self-referral, ни audit не реализованы → `apps/web/tests/payment.test.ts:188–201`, `apps/web/src/payment.ts:216–226`. Поэтому завершённость PAY-5 в `docs/features/payment/05_completion.md:3` завышена; `Specification.md:493` точнее говорит, что атрибуцию никто не создаёт.**

## 3. Противоречия документ ↔ код

- **P2 — `docs/Architecture-OPS.md:50–70`: раздел описывает время в сообщении, «никогда не усекает», ссылку в кабинет при усечении и измеряемое событие `private_message_delivered` → код не добавляет время или ссылку, усекает до лимита только с пометкой и записывает лишь `notifications.sent_at` → `services/notifier/src/format.ts:12–24`, `services/notifier/src/worker.ts:68–69`. Актуальный алгоритм в `Pseudocode-OPS.md:96–122` с этим старым разделом расходится.**

- **P3 — `docs/Specification-OWNER.md:58`: все варианты открытия Telegram якобы строятся из одного `botDeepLink` → функция строит только ссылку `t.me` для кнопки и QR, тогда как `tg://` и Telegram Web собираются отдельно → `apps/web/src/pages.ts:459–479`. Заявленный единый источник для всех ссылок отсутствует.**

Других смысловых расхождений в новых разделах по числу миграций, тестов, сервисам, маршрутам, цене, лимитам и порядку операций не обнаружено.

## 4. Вердикт

**Да с поправками. Оценка: B.**

Проект можно восстановить по документу после перестановки стража и устранения противоречия с host Node. Для воспроизведения заявленной защиты, а не текущего известного дефекта, необходимо также передать `SESSION_SECRET` в `guest`. Механические стражи и тесты повторно не запускались согласно brief; ревью было read-only.
