## Круг 1 — полный (ревизия `7eeb9ab4`) · ВЕРДИКТ C

Проверена ревизия `7eeb9ab4`, diff от `70976978`. Найден блокирующий сценарий: доверие к старому IP прокси сохраняется без ограничения времени при ошибках DNS.

1. **Выбор ключа клиентом.** При актуальном адресе прокси — нет: guest проверяет пира, берёт последний XFF и заново формирует `X-Guest-IP` (`apps/guest/src/client-ip.ts:41`, `apps/guest/src/server.ts:110`). Без `trusted_proxies` Caddy игнорирует присланный клиентом XFF — это соответствует [документации Caddy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#headers). Обычный сосед получает ключ своего сокета. **Исключение:** сосед, которому достался прежний доверенный IP прокси, может передавать произвольный XFF — см. п. 3. Intake доверяет любому контейнеру сети проекта, не исключительно guest (`services/intake/src/server.ts:48`).

2. **Очередь корректна для завершающихся операций одного процесса.** `finally` освобождает следующего и удаляет обе Map после последнего участника; исключение не отравляет цепочку (`services/intake/src/limit.ts:49`). Проверено исполнением извлечённого кода в памяти. Предел — **64 участника вместе с выполняющимся**, то есть 63 ожидающих; следующий получает отказ. Ожидающие эту очередь соединение не держат: `pool.connect()` вызывается внутри `consumeOnce` (`:71`). Зависшая операция удержит очередь: собственного дедлайна/отмены нет. **Две реплики:** превышения лимита advisory-lock не допускает, но конкурирующая реплика получает немедленный отказ (`:79`); «ровно 10» и отсутствие ложных 429 уже не гарантируются.

3. **Ошибка не всегда в сторону строгости.** Новый IP прокси до обновления кэша становится общим ключом гостей; обновление инициируется запросом после TTL, а не таймером. При ошибке DNS старое множество сохраняется, и время кэша обновляется (`apps/guest/src/client-ip.ts:64–73`). Это может продолжаться бесконечно. Если старый IP переиспользован чужим контейнером, тот считается прокси и выбирает ключ заголовком. Сохранение доверия спустя час ошибок DNS воспроизведено с подменённым resolver. Нужны ограничение возраста последнего успешного разрешения и снятие просроченного доверия; окно переиспользования IP внутри TTL требует отдельного решения.

4. **Канонизация неполная.** `2001:db8::1` и `2001:0db8:0:0:0:0:0:1` дают разные ключи; `::ffff:192.0.2.1` превращается в IPv4, а эквивалентный `::ffff:c000:201` — нет (`apps/guest/src/client-ip.ts:26`). В intake канонизации тоже нет (`services/intake/src/server.ts:50`). Воспроизведено. Это недостаток функции, но самостоятельный обход внешним клиентом через данный Caddy не доказан: клиент не выбирает написание адреса, сформированного прокси.

5. **Тесты содержательно проверяют заявленные сценарии одной реплики.** C-1 требует ровно 10 успехов и 10 отказов, C-3 — 20 успехов (`services/intake/tests/seam-guest-ip.test.ts:96`, `:103`). Проверяются вращение первого XFF, подмена `X-Guest-IP` и недоверенный сосед (`:112`, `:126`). Не проверяются настоящий Caddy/Docker, смена IP и отказ DNS, две реплики, насыщение очереди, исключения/зависания БД, доступность пула другим запросам, эквивалентные IPv6 и фактический барьер 200. Интеграционные тесты в этом ревью не запускались.

6. **Регрессия задержки `/go` и страницы выбора.** Теперь ответ ожидает DNS ради аналитики (`apps/guest/src/server.ts:134`, `:174`). У `lookup` нет прикладного дедлайна и объединения одновременных запросов: после истечения TTL возможны параллельные резолвы и задержка ответа (`apps/guest/src/client-ip.ts:64`). Сам `Location` не меняется. При переходе на общий ключ прокси `device_hash` склеивает гостей с одинаковым UA; после восстановления меняется обратно (`apps/guest/src/journal.ts:35`). Очередь также может пережить восьмисекундный timeout guest: intake продолжит обработку после показанного пользователю отказа (`apps/guest/src/server.ts:112`).

Проверки: `tsc --noEmit` — успешно; изолированные проверки очереди, DNS-кэша и представлений IP — выполнены. Профиль — read-only ревью, исполнитель Codex/GPT-6 без делегирования. Файлы и телеметрия не создавались; полная длительность и расход не измерены.

ВЕРДИКТ: C — неограниченное сохранение доверия к старому IP допускает подмену ключа соседом после переиспользования адреса.

Недоверенный сосед получает ключ своего пира; клиентский `X-Guest-IP` заменяется (`apps/guest/src/client-ip.ts:52–56`, `apps/guest/src/server.ts:110`). Сохраняются принятые исключения: переиспользование доверенного IP внутри TTL и доступ контейнеров внутренней сети к intake.

3. **«Каждая ошибка делает лимит строже» — слишком сильное утверждение.** Ошибки DNS и некорректный хвост XFF действительно переводят запрос на ключ пира. 4. **Канонизация эквивалентных IPv6 и IPv4-mapped корректна.** `%eth0`, IPv4 с ведущими нулями и пустые значения отвергаются; пустой последний элемент XFF приводит к ключу пира. Небольшой дефект валидации: регулярное выражение принимает непарные скобки — `[192.0.2.1` и `192.0.2.1]` превращаются в валидный адрес (`apps/guest/src/client-ip.ts:34`, `services/intake/src/server.ts:58`). Лучше снимать только парные скобки. Обхода через заданный Caddy это не демонстрирует.

Проверки: `npm run typecheck` — успешно; изолированные проверки обеих копий канонизации, отказа DNS, дедлайна, восстановления и 20 одновременных запросов — успешно. Интеграционные тесты с БД и реальным Caddy не запускались. Профиль — read-only ревью, Codex/GPT-6, без делегирования; телеметрия не создавалась, длительность и расход не измерены.

ВЕРДИКТ: A — блокер закрыт; остаются принятые риски и небольшие замечания к валидации и формулировке строгости.
