# Адрес гостя в лимите приёма · план

Тир **M** (меняется поведение лимитера на разделяемом ресурсе; цифры лимитов не меняются —
только КЛЮЧ). Источник: README, «Что осталось», п. 6; `demo-script.md:283`, `:351`.

## Дефект

Форма гостя уходит из `guest` в `intake` внутренним `fetch` (`apps/guest/src/server.ts`,
`postToIntake`) с заголовками только `content-type` и `origin`. `intake` без `X-Forwarded-For`
брал `req.socket.remoteAddress` — адрес контейнера `guest`. Итог:

| Порог | Обещано | На деле |
|---|---|---|
| `private_ip_place` (10/час) | с адреса гостя на точку | на точку от **всех** гостей |
| грубый барьер (200/час) | с адреса | на **весь продукт** |

Нарушены C-3 и C-3b (`Refinement.md` §3). Тесты были зелёными: били в `intake` напрямую —
дефект жил в стыке, не в модуле (`deployment-seams.md`).

Второй дефект того же места: `guest` брал **первый** элемент `X-Forwarded-For` — значение
клиента (урок N1, `extractClientIP`).

## Граница доверия

```
гость ──TLS──▶ Caddy (ai-hub-tls-proxy, talk-ai-public) ──XFF──▶ guest ──X-Guest-IP──▶ intake
                                                   ▲ ещё ~10 чужих контейнеров в той же сети
```

1. **guest** читает `X-Forwarded-For` ТОЛЬКО если сокет пришёл с адреса прокси
   (`TRUSTED_PROXY_HOST`, резолв DNS сети, TTL 30 с, дедлайн 1 с). Берётся ПОСЛЕДНИЙ элемент
   (подход N1 `extractClientIP` и N6 `server/ip.ts`: доверять тому, что записал наш прокси).
   Сосед по общей сети, не прокси, получает ключ по своему адресу. Сбой DNS — доверие
   снимается, а не сохраняется.
2. **guest → intake**: адрес в `X-Guest-IP`, заголовок собирается заново (клиентский не
   пробрасывается).
3. **intake** берёт ключ только из `X-Guest-IP`; `X-Forwarded-For` не читает. Верить можно,
   потому что `intake` не опубликован и не в сети прокси — до него достают только контейнеры
   compose-проекта. Условие несущее и записано в коде (`services/intake/src/server.ts`).

## Найдено по ходу (не в исходной постановке)

Try-лок `pg_try_advisory_xact_lock` по ключу `private_place|<place>` давал **ложные 429**
одновременным гостям одной точки с разных адресов, а 20 одновременных с одного адреса
проходили «сколько повезёт», а не ровно 10. Пока все гости шли одним ключом, это было
не видно. Решение: очередь по ключу в памяти ДО `pool.connect()` (ожидающий держит сокет,
не соединение; ≤ 64 на ключ); try-лок в БД остаётся для межпроцессной сериализации.

## Критерии приёмки

| AC | Проверка |
|---|---|
| AC-1 · C-3b через стык: 11-е с одного адреса — 429, другой адрес на ту же точку проходит | `seam-guest-ip.test.ts` |
| AC-2 · C-1 через стык: 20 одновременных с одного адреса — ровно 10 × 200 и 10 × 429 | то же |
| AC-3 · C-3 через стык: 20 одновременных с 20 адресов за одним прокси — 20 × 200 | то же |
| AC-4 · клиент вращает первый элемент XFF и шлёт свой `X-Guest-IP` — ключ не меняется | то же |
| AC-5 · сосед по сети (не прокси) с XFF — ключ его адрес | то же |
| AC-6 · один адрес — один ключ (канонизация), копии в guest и intake совпадают | то же |
| AC-7 · сбой DNS снимает доверие к прокси | то же |
| AC-8 · каждый страж падает на своей мутации | M-30…M-34 (`Refinement.md` §2) |
| AC-9 · полный прогон всех наборов зелёный | `scripts/test-all.sh` |
