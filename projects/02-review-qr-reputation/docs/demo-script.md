## Прогон · часть 2 — техника, 10–12 минут

Сквозная мысль, произнести в начале и в конце: **защита ставится не на слой «ревьюер заметит», а
на самый сильный слой, который способен её выразить** — тип, право СУБД, схема, детерминированный
тест. Всё остальное — иллюстрации к этой мысли.

Ядро (не сокращать): пункты 1, 3, 5, 6. Режутся первыми: 2, 4, 7.

### 1. Гейтинг невыразим — три независимых слоя (2 мин)

| Слой | Где | Что видно |
|---|---|---|
| Тип | `apps/guest/src/server.ts:43` | `renderChoicePage(slug: string)` — один аргумент. Ветвить по оценке или cookie физически не по чему |
| Права | `packages/db/migrations/005_roles_grants.sql:42–56` | у роли `app_render` строки `private_feedback` нет ни в каком виде |
| Схема | `scripts/check-db-grants.sh:101` | закрытый список полей, которых **не должно существовать**: `gating_enabled`, `rating_threshold`, `positive_destination`, `show_if`, `sort_order` |

**Живая команда — «permission denied» за две секунды:**

```bash
docker exec reviewqr-postgres-1 psql -U reviewqr -d reviewqr \
  -c "set role app_render; select count(*) from private_feedback;"
# ERROR:  permission denied for table private_feedback
```

**Формулировка.** Обещание «все гости видят одинаковый путь» реализовано не дисциплиной и не
код-ревью, а невозможностью. Чтобы отфильтровать недовольных, коду пришлось бы прочитать
тональность — у роли, обслуживающей публичную страницу, такого права нет, и запрос падает при
первом запуске. Один слой обходится правкой за минуту; три вместе требуют правки типов, миграции
прав и миграции схемы одновременно — а это уже не случайность, а решение, видное в дифе.

### 2. Четыре роли СУБД = четыре контейнера (1 мин)

`docker-compose.yml`: `guest → DATABASE_URL_RENDER`, `intake → DATABASE_URL_INTAKE`,
`notifier → DATABASE_URL_NOTIFY`, `web → DATABASE_URL_OWNER`. Комментарий в `.env.example`, ради
которого это сделано: **«пул можно перепутать в коде, а `DATABASE_URL`, которого в контейнере
НЕТ, — нельзя»**.

```bash
docker ps --format '{{.Names}}\t{{.Ports}}' | grep reviewqr
```

Ни одного `0.0.0.0:` — наружу смотрит только общий reverse-proxy.

### 3. Тест чистоты: двенадцать запросов, один хэш (1,5 мин)

`apps/guest/tests/purity.test.ts:66–96` — двенадцать вариантов запроса, каждый меняет ровно одно
измерение: `?rating=1`, `?rating=5`, `?sentiment=bad`, cookie `mood=angry`, три User-Agent, два
языка, два разных `X-Forwarded-For`. Утверждение: `sha256` сырого тела совпадает у всех
двенадцати, `expect(seen.size).toBe(1)`.

**Самое интересное — строки 85–88:** сброс кэша перед КАЖДЫМ вариантом, с комментарием «проверено
мутацией: со случайной сортировкой страж оставался зелёным». Без сброса первый запрос клал
страницу в кэш, остальные одиннадцать получали её же и совпадали всегда — **тест был зелёным на
сломанном коде**.

Мысль для зала: «зелёный тест» — утверждение о тесте, а не о коде, пока тест не показывали красным.

### 4. Лимитер: конкурентный тест ловит то, чего последовательный не видит (1 мин)

`services/intake/src/limit.ts:8–16` — разбор дефекта дословно: первая редакция считала и вставляла
одним CTE, полагая, что атомарность даёт СУБД. **«Под READ COMMITTED каждый одновременный оператор
видит СВОЙ снимок — 20 параллельных прошли 14 при пороге 10. Один оператор ≠ сериализация.»**

Починка — `pg_try_advisory_xact_lock`, именно TRY, а не ждущий: очередь за локом держала бы
соединения общего пула.

### 5. Оплата: порядок операций — это и есть защита (2 мин)

`apps/web/src/payment.ts`, три шага в шапке файла:

1. адрес источника — список подсетей ЮKassa **зашит в код**, не в переменную окружения;
2. **подлинность перезапросом статуса у провайдера**, вне транзакции; недоступность провайдера —
   `throw`, а не возвращаемое значение;
3. и только теперь заявка идемпотентности, ключ `«<тип события>:<id объекта>»`.

**Почему порядок несущий.** Поменять шаги 2 и 3 местами — значит позволить подделке с угаданным
`id` занять ключ идемпотентности первой, после чего НАСТОЯЩЕЕ уведомление будет отброшено как
дубль. В проекте 01 этот дефект был реальным: деньги списаны, тариф не повышен, повтор упирается в
занятый ключ и коротит в `duplicate` с кодом 200 — **оплата не применяется никогда**, и ни один из
408 тестов проекта этого не покрывал.

Почему ключ составной: голый `id` схлопнул бы `succeeded` и `canceled` одного платежа в один ключ.

### 6. Дефект, найденный сверкой с первоисточником — IPv6 (1,5 мин)

Список подсетей был снят с документации и выглядел полным. Повторная сверка **в день показа**
нашла у ЮKassa подсеть `2a02:5180::/32`, которой в списке не было, а матчер отвергал любой не-IPv4
адрес — **причём в тестах это было закреплено как ожидаемое поведение**. Уведомление по IPv6
получало бы `400` на каждой попытке: ровно тот дефект, ради которого писался ADR-009, зашедший с
другой стороны.

```bash
git show dfb6497 --stat
```

Мысль для зала: покрытие тестами не есть корректность. Тест написан против того же понимания, что
и код, и повторяет его ошибку. Нашла не машина и не ревью — нашла **сверка кода с
первоисточником**.

### 7. Мутация, которая не применилась (1,5 мин)

Правило проекта: страж принимается только вместе с доказательством, что он **падает**. У самого
этого рецепта обнаружился собственный тихий отказ:

```
мутация внедрена, страж слеп   ->  Tests  13 passed     ← дефект стража
мутация НЕ внедрена            ->  Tests  13 passed     ← дефект процедуры
```

Якорь `str.replace` не совпал ни с одним фрагментом файла, `replace` вернул строку без изменений и
молча записал её обратно. После `assert s2 !== s` те же шесть мутаций дали шесть красных — страж
был исправен с самого начала. Разбор стоил трёх итераций.

Отказ направлен в **худшую** сторону: не «плохой страж примут за хороший» (это ловится), а
«хороший объявят негодным и перепишут».

### 8. Кузница: 37 заявок, найденных прогонами (1 мин, финал)

`harness-forge/README.md` — заявки на улучшение инструментария, каждая с воспроизведением. Общая
черта всех: проверка жила на слое «модель вспомнит», где её пропуск не оставляет следов.

Для аудитории, которая собирается работать с AI-ассистентами, это самая переносимая часть: продукт
у них будет другой, а классы отказов инструментария — те же.

## Опорные формулировки

### Открывающая история (60 секунд)

> «Кафе. Открываю карточку на Яндекс.Картах: 4,3 и сорок семь отзывов. Спрашиваю владельца:
> сколько у вас гостей в день? — „Человек сто". Значит за месяц около трёх тысяч гостей и штук
> шесть новых отзывов. Вопрос один: почему остальные две тысячи девятьсот девяносто четыре не
> написали?
>
> И вторая половина той же истории: те, кто всё-таки пишет, чаще недовольны. О проблеме владелец
> узнаёт из карточки на следующий день, когда извиняться уже поздно.»

Это типовая картина из скрипта продаж, а не замер конкретного заведения — так и говорить.

### Главный критерий, дословно

> **«Все посетители видят одинаковый путь к публичному отзыву, без предварительной сортировки по
> ожидаемой тональности.»**

Проверяется не код-ревью, а тестом: N запросов к развёрнутому стенду, различающихся ровно одним
измерением каждый, дают побайтово совпадающий ответ.

### Правовая рамка — говорить точно

| ❌ Нельзя | ✅ Можно |
|---|---|
| «Gating запрещён законом» | «Прямой нормы в праве РФ нет — мы проверяли» |
| «Яндекс запрещает фильтрацию» | «У Яндекса прямой нормы нет, и gating отсутствует в его собственном перечне нечестных методов» |
| «Конкуренты нарушают правила» | «**2ГИС продаёт такой сервис сам** — „Отзывы Про", публичный лендинг с тарифами» |
| «За это блокируют карточку» | «Подтверждены снятие отзыва и блокировка аккаунта **автора**, не карточки» |

Что соблюдается буквально: не подсказывать содержание отзыва и **не давать стимулов вовсе** — ни
за какой отзыв.

### Честные ограничения — назвать самому, первым

1. **Публикацию проверить нечем.** У Яндекс.Карт и 2ГИС нет API отзывов. Продукт фиксирует переход
   на площадку — и на этом его знание кончается. Записано в схему: источник счётчика отзывов —
   перечисление из одного значения `manual`.
2. **Одна точка на тариф.** «Сеть» и «Агентство» — второй релиз.
3. **Виральности нет, и это свойство.** Гость, оставивший отзыв, не приводит новое заведение. Рост
   линеен по числу продавцов.
4. **Конкурент, вероятно, собирает публичных отзывов больше нас** — гейтинг усиливает публичную
   дверь при высокой оценке. Это записано как риск в PRD.

## Возражения

**«Зачем это, если есть Senja / Restolink за 900 ₽?»**
Начинать с признания: «После разведки у продукта не остаётся ни одного свойства, которого нет у
конкурента. Это записано в наших же документах как главный риск. QR — commodity, Яндекс раздаёт его
за 0 ₽. Остаётся одно расхождение — отказ от роутинга по оценке. Неделя пилота нужна ровно затем,
чтобы узнать, покупают ли это.»

**«Почему нельзя фильтровать?»**
«**Можно.** Тридцать строк кода, и это не запрещено: нормы нет, 2ГИС такой сервис продаёт сам. Я
всё равно этого не делаю. Если мы фильтруем — продаём красивую цифру. Если не фильтруем — продаём
то, что цифра означает. Это разные продукты, и я умею делать второй. Если клиенту нужен первый —
берите Restolink, серьёзно.»

**«А если отзывы будут плохие?»**
«Часть пойдёт — и пойдёт вам лично, а не на карты. Сегодня недовольный гость молчит и пишет в
интернете через день. Здесь он пишет вам, пока ещё в зале, и у вас есть смена, чтобы всё
исправить.»

**«Кто будет клеить QR?»**
«Это узкое место, и оно измерено: шаг „напечатали и физически поставили" даёт 70 %. Поэтому
носители по умолчанию **уносимые** — подвал счёта, оборот визитки, наклейка на упаковке, а не
„повесить рамку".»

**«А Яндекс не забанит?»**
«За наш способ сбора — нет, и утверждать обратное я не буду. Подтверждены санкции за накрутку:
снятие отзыва и блокировка аккаунта **автора**, не карточки. Перечень у них открытый и проверка
ретроактивна — но это риск не наш, а той схемы, которая сортирует.»

**«Вот же редирект `/go` — это и есть роутинг!»**
Ответ готов: роута, **принимающего оценку**, не существует. `/go` принимает дверь, которую гость
**уже выбрал**. Редирект оставлен ради измеримости: статический `<a href>` не даёт доли выбравших
публичную дверь никогда.

| Зал массово шлёт форму, на 11-й приходит отказ | средняя при зале >10 | **Лимит 10/час считает всех зрителей как одного** (внутренний вызов не передаёт адрес гостя). Отправлять форму самому со сцены; залу дать сканировать QR — сканы не лимитированы |
| Обещали рост счётчика «сканы», цифра стоит | высокая при репетиции с ноутбука | Счётчик считает уникальные устройства за неделю; десять открытий с одного ноутбука дают +1. Для роста в кадре — 2–3 зрителя со своих телефонов |
| Отправили форму дважды, пришло два сообщения | средняя | Ключа повторности у формы нет намеренно: гость мог дописать. Назвать свойством, а не оправдываться |
| Telegram задержался | низкая | Не ждать молча: открыть страницу точки в кабинете — обращение уже там |
| Кнопка оказалась «Продлить», а не «Подключить» | **высокая** (подписка активна) | Зарегистрировать новый пустой аккаунт прямо на сцене |

**Задержка Telegram: 5–13 секунд**, обычно ближе к 5 (интервал опроса 5 с). Обещать «мгновенно»
не надо, «в течение десяти секунд» — честно.

**Провал доставки зрителю НЕ ВИДЕН:** гость в любом случае увидит «отправлено». Не увидит только
владелец. Обращение при этом не потеряно — оно в базе и в кабинете.

## Запасные ходы, если стенда нет

**Ход 1 — вебхук отвергает чужой адрес** (нужен интернет, не нужен UI):

```bash
curl -i -X POST -H 'content-type: application/json' \
  -d '{"event":"payment.succeeded","object":{"id":"probe"}}' \
  https://reviewqr.aicoding.space/webhooks/yookassa
# → 400
```

Кадр на 15 секунд: «мы не верим уведомлению об оплате просто потому, что оно пришло».

**Ход 2 — зелёные тесты без базы данных** (главный запасной ход):

```bash
npx vitest run apps/web/tests/payment.test.ts -t "P-10"
# → 4 passed | 12 skipped, 0,6 с
```

Ровно те тесты, что закрыли IPv6-дефект. Рядом: `-t "P-8"` (цена только из конфига),
`-t "P-6"` (сброс кэша только после COMMIT).

**Ход 3 — типы сходятся:** `npm run typecheck` → exit 0.

**Ход 4 — страж умеет ОТКАЗЫВАТЬСЯ:**

```bash
bash scripts/check-db-grants.sh; echo "код возврата: $?"
# ❌ DATABASE_URL_SUPER не задан — проверка НЕ выполнена
# код возврата: 2
```

Это и есть демонстрируемый тезис, и он сильнее зелёной галочки: у стража **три** кода возврата.
`0` — чисто, `1` — нарушение доказано, `2` — **проверка не выполнена**. Страж, отвечающий «чисто»
на недоступной базе, хуже отсутствующего: он превращает неизвестность в заверение.

**⛔ Чего в запасе НЕТ:** `npm test` целиком. Наборы требуют отдельной тестовой базы, которой на
этой машине не поднято — прогон даёт красное по причине, не связанной с кодом. **Не запускать при
зрителях.**
