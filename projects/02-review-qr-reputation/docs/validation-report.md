## 2. Имена, обязанные совпадать

`branding_required` · `guest_event_kind` · `private_feedback` · `rate_limit_events` ·
`platform_links` · `device_hash` · `notifications` — расхождений нет.

**Отдельно стоит отметить:** четыре из семи имён в `Specification` **отсутствуют вовсе**, и это
не пробел, а исполнение вывода, добытого дорого: *требование, называющее таблицу, роль или
право, вышло за свой раздел*. Требования говорят свойствами, схема — механизмами.

## 3. Пары, защищающие только в связке

Метод введён после того, как эта фаза чуть не потеряла такую пару. По отдельности каждый
элемент выглядит самостоятельным; связь между ними невидима, и первый упрощающий код снимет
одну половину как лишнюю.

| Пара | Связь названа в тексте |
|---|---|
| Грубый барьер в памяти ↔ `SELECT` на `rate_limit_events` | ✅ Architecture-OPS §7.2, правилом для будущих правок |
| Отсутствие `UNIQUE` ↔ отсутствие `SELECT` (иначе `ON CONFLICT` — канал чтения) | ✅ Architecture-DATA, у всех трёх таблиц |
| TTL ≤ 60 ↔ явная инвалидация | ✅ |
| `place_id` в хэше ↔ отсутствие индекса `(place_id, device_hash)` | ✅ |
| `branding_required` на точке ↔ рендер не читает `accounts` | ✅ |
| Деградация барьера **в пропуск** ↔ пороги второй ступени | ✅ |
| Сужение `T6` до `/r/:slug` ↔ законность звёзд в `/r/:slug/private` | ✅ |

Ни одной пары без записанной связи не обнаружено.

## 4. Полнота трассировки

- **13 требований** — у каждого есть алгоритм в `Pseudocode*`;
- **14 стражей**, объявленных в `Architecture`, — все присутствуют в `Refinement`;
- **`FR-GROWTH-001…004`** — у каждого ровно три сценария: `@happy-path`, `@edge-case`, `@security`;
- **обязательный критерий приёмки** из постановки — на месте, дословно, с указанием теста `T4`.

## 5. Находка о самой проверке

Проверка «критерий приёмки записан дословно» **дала ложное красное**: `grep` искал строку
целиком, а в документе она перенесена на две строки. Критерий на месте.

Это тот же класс, что дважды бил по проекту сегодня — `grep 'TO app_intake'`, не нашедший
грант из-за перечисления через запятую, и комментарий, давший обратное ложное срабатывание.
**Проверка по форме записи вместо смысла — третий случай за день**, и на сей раз в проверке,
написанной уже после того, как класс был опознан и подан в кузницу.

Практический вывод для Phase 3: проверки по тексту документов писать по **фрагменту без
переносов**, а совпадение подтверждать чтением, а не только кодом возврата.

## 6. Почему проход Б, а не полная Phase 2

Полная Phase 2 — балльная оценка требований по INVEST и SMART. Она проверяет документы
**поодиночке и по чек-листу**, и ни один из двенадцати дефектов этой фазы не имел формы
«плохо сформулированное требование»: все возникали из **конъюнкции безупречных по отдельности
утверждений**.

Отдельный риск, ради которого от неё отказались: у нас есть требования, сознательно
записанные как **свойство без числа** («ожидание ресурса конечно и задано явно», числа
вынесены в архитектуру). По критерию SMART «измеримо» это читается как дефект — и регламент
отправил бы верную работу на переделку.
