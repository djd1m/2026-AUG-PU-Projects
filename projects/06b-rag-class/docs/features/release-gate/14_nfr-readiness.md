# F16 — подготовка локального NFR 200k

2026-10-03, после rollback-2. Статус: **NOT_EXECUTED**. Это план ограниченного измерения, не новая система проверок и не подтверждение NFR.

Основание: Specification NFR-n6b-1 требует top-5 HNSW p95 ≤100 мс при ≤200000 фрагментов. Полный NFR дополнительно включает ответ посетителю p95≤6с, генерацию≤5с и отказ ниже порога≤1.5с; локальная синтетическая БД не подтверждает эти live/stand метрики.

Точный путь поиска: `packages/rag/src/search.ts`, экспорт `searchChunks`; служебная роль, фильтр bot_id, `hnsw.iterative_scan=strict_order`, `hnsw.ef_search=64`, limit5. Схема: `vector(1536)`, индекс `chunk_embedding_hnsw`, cosine, m16/ef_construction64 из `packages/db/migrations/001_init.sql`. Не заменять поиском по упрощённой таблице и не форсировать план через отключение сортировки: фактический EXPLAIN должен показать выбранный план; отсутствие HNSW фиксируется отдельно от численного p95.

Минимальный будущий runner: существующий pgvector0.8.6-pg16 и Node22 image, отдельный Compose project/внутренняя сеть/БД без ports, случайные пароли в удаляемом private tmp. Суммарно CPU2, общий heavy flock, без провайдера/публикации/существующих данных. Канонические миграции и source-bound runtimeoverlay по хешам; никаких npm upgrades и новых зависимостей.

Набор: ровно200000 валидных chunk с детерминированными различными конечными1536-мерными векторами, связанные account/bot/document записи. Распределение по10ботам по20000 фиксируется заранее; разные запросы/боты, проверка принадлежности всех5результатов и числа результатов. Это синтетический performance corpus, не оценка качества настоящих эмбеддингов/recall. Сохранять seed, размеры текста, распределение и контрольный хеш генератора.

Измерение: после загрузки/index/ANALYZE сохранить размеры таблицы/индекса/БД и EXPLAIN ANALYZE/BUFFERS естественного production-запроса; отдельно cold-сэмплы.50warmup и500timed sequential production searchChunks calls с monotonic clock, raw durations, p50/p95/p99/max, определениеp95=sorted[ceil(.95*n)-1], errors0 и >=5валидныхрезультатов. Записывать время с транзакцией/двумя SET LOCAL и отдельно серверныйEXPLAIN, не подменять одну метрику другой. CPU/RAM/Postgres/pgvector/источник/образ/соседнюю нагрузку зафиксировать. Другую конкурентность не подразумевать; общий throughput этим проходом не доказан.

Ресурсы: только элементы векторов занимают как минимум200000×1536×4=1228800000байт (~1.14GiB), без heap/TOAST, копии в индексе, текстов, WAL, временных данных и образов. Реальный peak не измерен. При текущих ~5.5GiB свободного диска нельзя считать безопасным загрузить200k и построить HNSW с гарантированным остатком1.5GiB. Для новой попытки нужен явно зафиксированный консервативный ресурсный бюджет (предварительная оценка8GiB свободно, не измеренное требование), актуальный preflight и непрерывный floor1.5GiB; не брать старый снимок за разрешение. Общий bounded pass≤20мин с statement_timeout/hostdeadline, остановкой и owncleanup; timeout не PASS и не повод молча продлевать.

Готового NFR200k runner в текущем checkpoint нет. Следующее разрешённое действие — узкая реализация этого fixture/измерителя отдельным Sol6.1/high и независимое Astra/high ревью после согласования ресурса; нельзя выдавать подготовку или маленький smoke за выполненный200k.
