## 1. Цель и границы

**Цель.** Ни один платный вызов OpenRouter не происходит, пока все ключи попытки не списаны атомарно в одной транзакции;
исчерпание — отказ `429` без единого платного вызова; каждый вызов оставляет в журнале `started` ДО отправки и ровно один
исход после; исполнитель OpenAI закреплён, его отказ — `503` без перехода к другому исполнителю и без скрытых повторов.

Замечания, которые план закрепляет явно:
- **Подаккаунт студии** — отдельный аккаунт со своими `answer:sandbox:<id>` и `embed:account:<id>`; общий потолок
  студии в документах не назван. Студия с 5 подаккаунтами имеет ×6 личных пределов, но упирается в те же глобальные. →
  Q4 (предложение: оставить, глобальные пределы связывают).
- **Один резерв на ответ** покрывает ОБА платных вызова ответа (эмбеддинг вопроса + генерацию): единица — «ответ», не
  «вызов». Если ниже порога сходства генерация не зовётся — резерв всё равно израсходован (попытка была: эмбеддинг
  оплачен). Токены эмбеддинга вопроса в `embed:*` НЕ считаются — они ограничены числом ответов и длиной вопроса ≤ 500.
- **Ключ часа входа несёт дату** (`2026-09-30T14`), а не только час: иначе в 14:00 завтра счётчик сегодняшних 14:00
  продолжится. Колонка `day` строки — московская дата того же часа.
- **Цепочка «персональный ≤ суточного»:** 30 ≤ 300 ≤ 3000; 100 ≤ 2000; 2M ≤ 20M — проверяется при старте (§7).
- **Деньги в худшем случае `[H]`** (цены `Architecture.md` External Dependencies): ответы 5 000/сутки × ≈ $0.0015 ≈ $7.5;
  эмбеддинги 20M × $0.02/1M = $0.40; итого ≈ **$7.9/сутки, ≈ $240/месяц** при непрерывном исчерпании всех глобальных
  пределов. Токен-потолка на генерацию нет: цена ответа ограничена `max_tokens 400` и промптом из ≤ 5 фрагментов по
  ≈ 500 токенов (≈ 3 000 токенов входа × $0.40/1M + 400 × $1.60/1M ≈ $0.0018 — сходится с оценкой ADR-004). → Q5
  (второй предохранитель — лимит кредитов ключа на стороне OpenRouter).

## 3. Атомарность списания до платного вызова

**Инструкция на ключ (одна, без чтения):**

```sql
INSERT INTO quota_counter (scope, day, used) VALUES ($1, $2, $3)
ON CONFLICT (scope, day) DO UPDATE SET used = quota_counter.used + EXCLUDED.used
  WHERE quota_counter.used + EXCLUDED.used <= $4
RETURNING used;
-- плюс для первой вставки: CHECK на стороне кода n ≤ limit (иначе INSERT создал бы строку сверх предела)
```

Пустой `RETURNING` = предел достигнут. Отличие от N4 #14: там `+1` и `used < limit`; здесь `+n` (токены эмбеддингов) и
`used + n <= limit` — форма N5 #19. Первая вставка при `n > limit` отвергается в коде до SQL (иначе `VALUES(n)` обошёл бы
условие `WHERE`, которое срабатывает только на конфликте) — отдельный тест T-3.

**Одна транзакция на все ключи попытки.** `reserveQuota(tx, keys)` принимает УЖЕ открытый клиент (форма N4
`consume-in-transaction.ts` / N5 `SAVEPOINT`), идёт по ключам в **фиксированном порядке** «частный → общий»
(`visitor → bot → global`; `sandbox:<acc> → sandbox:global`; `embed:account → embed:global`) — одинаковый порядок у всех
вызывающих исключает взаимную блокировку, а общий горячий ключ берётся последним и держится короче всего. Отказ любого
ключа — **исключение** `QuotaExhausted(scope)` → откат ВСЕЙ транзакции (не декремент встречными UPDATE; не значение —
`security-operation-order`: штатный возврат закоммитил бы уже списанные ключи).

**Порядок `paidCall()`:**

```
1. BEGIN
2.   reserveQuota(tx, keys)            — отказ → ROLLBACK → QuotaExhausted → вызывающий: 429, провайдер 0 раз
3.   INSERT model_call_log(state=started, kind, account_id, bot_id) RETURNING id
4. COMMIT                               — резерв и START фиксируются ДО сети; соединение пула ОТПУЩЕНО
5. provider.<embed|answer>(…, deadline) — вне транзакции (shared-resource-verification, вопрос 1)
6. UPDATE model_call_log SET state=succeeded|failed, tokens_in, tokens_out WHERE id=… AND state='started'
```

Почему START в той же транзакции, что резерв: попытка без записи в журнале невидима в расходе; резерв без START — тоже.
Обе строки коммитятся вместе и до отправки. Крах процесса между 4 и 6 оставляет `started` навсегда — это и есть «попытка
засчитана, исход неизвестен» (форма N4 #15). Отдельный `unknown` в enum не добавляется: `started` старше дедлайна
+ 60 с на панели показывается как «исход неизвестен» (вывод, не новое состояние; схему не меняем).

**Разделяемый ресурс (4 вопроса `shared-resource-verification`):**
1. *Что удерживается:* соединение пула — на время шагов 1–4 (миллисекунды, без сети, без чтения тела клиента);
   блокировки строк `quota_counter` — до COMMIT. Сетевой вызов и чтение тела запроса — ВНЕ транзакции (тело читается и
   валидируется до `paidCall`, шаг 1 Answer question).
2. *Сколько единиц:* пул `pg` — число берётся из `foundation` (ожидаемо `max: 10`, `connectionTimeoutMillis: 3000` по
   образцу N5); план требует назвать его в `packages/db` и ждать соединение не бесконечно (таймаут → 503, не зависание).
3. *Кто ещё в очереди:* строка `answer:global` — общая для всех ботов всех клиентов; её блокировка сериализует
   резервы ответов. Держится ≤ время одной транзакции из 2–3 UPDATE. Тест T-6 меряет, что занятых соединений ≤ N пула
   и не растёт с числом ожидающих.
4. *Кого наказывает насыщение:* `answer:global` — ВСЕХ владельцев сразу: один посетитель с многих /24 может выжечь 3 000
   ответов за день, и виджеты всех клиентов ответят 429 до полуночи МСК. Это не дефект реализации, а свойство выбранной
   иерархии пределов; названо в рисках (R-1) и в Q2.

**Конкурентные тесты (обязательны, последовательные не доказывают):**
- T-5a: остаток `answer:visitor` = 3, 50 параллельных `paidCall` одного посетителя → ровно 3 вызова `fake`, 47 × `QuotaExhausted`,
  `used` = 30 (ADR-010, Refinement «Concurrent access»).
- T-5b: `answer:sandbox:global` остаток 5, 20 разных аккаунтов с нетронутым личным пределом параллельно → ровно 5 вызовов;
  у 15 отказавших `answer:sandbox:<acc>` НЕ увеличен (откат всей транзакции) — SC-US-016-4.
- T-5c: `embed:global` остаток 1 000 токенов, 10 параллельных батчей по 300 → проходят ровно 3, сумма `used` ≤ предела.
- T-5d: смешанный порядок — 30 параллельных попыток на пересекающихся ключах (`bot` общий, `visitor` разные) без
  `deadlock detected` за 50 прогонов.
- T-5e: добросовестный параллельный сценарий — 25 разных посетителей одного бота одновременно при `answer:bot` = 300 →
  все 25 проходят (механизм не бьёт по честным).

## 4. Поведение при исчерпании

Отказ, не деградация: ни модели «подешевле», ни очереди, ни укороченного ответа (`model-call-cost.md` п. 2).

| Канал | Ключ отказал | HTTP | Текст (`error.code`, `message`) | Пишется |
|---|---|---|---|---|
| виджет, демо | `answer:visitor` | 429 | `limit_visitor` «Лимит вопросов на сегодня исчерпан. Свяжитесь с владельцем сайта: <контакт>» | `question_log.outcome=limited` |
| виджет, демо | `answer:bot` | 429 | `limit_bot` — тот же текст посетителю (владельцу — отдельно в кабинете, Q3) | то же |
| виджет, демо | `answer:global` | 429 | `limit_global` — текст по решению Q2 | то же |
| песочница | `answer:sandbox:<acc>` | 429 | `limit_sandbox_account` «Лимит песочницы на сегодня (100) исчерпан, сброс в 00:00 МСК» | то же |
| песочница | `answer:sandbox:global` | 429 | `limit_sandbox_global` «Песочница сервиса перегружена на сегодня, сброс в 00:00 МСК» | то же |
| индексация | `embed:*` | — (задача) | задача `failed`, `error` = «исчерпан суточный предел индексации, продолжение завтра»; «Повторить» продолжает (V-4) | `index_job.error` |
| вход/регистрация | `auth:addr` | 429 | `limit_auth` «Слишком много попыток, повторите через час» (bcrypt не вызывается) | — |
| любой | провайдер: таймаут, 5xx, `error` в теле 200, отказ OpenAI без фолбэка | 503 | `provider_unavailable` «Сервис ответа временно недоступен» | `model_call_log.failed`, попытка засчитана |

Код различает scope отказа (`QuotaExhausted.scope`), чтобы маршрут выбрал текст; наружу посетителю scope не раскрывается
иначе как текстом из таблицы (без чисел чужих пределов). Контакт — из `bot.contact` (обязателен для публикации). Заголовок
`Retry-After` — секунды до полуночи МСК (для часа входа — до конца часа).

## 5. Учёт по попыткам

- Резерв списывается ДО вызова и **не возвращается** ни при каких исходах: таймаут, 5xx, `error` в теле 200, нарушение
  схемы, обрыв сети, отмена по дедлайну — всё засчитано (SC-US-016-3). Возвратов (`refund`) в фиче нет вовсе.
- Скрытых повторов нет: адаптер делает ровно один `fetch` на вызов; ретрай-библиотек и `retry`-опций нет (страж S-5).
  Единственный законный второй вызов в попытке ответа — генерация после эмбеддинга вопроса, и оба покрыты одним резервом.
- Токены эмбеддингов резервируются по оценке `js-tiktoken` ДО вызова; фактические `usage.prompt_tokens` пишутся в журнал
  (`tokens_in`) для сверки, но счётчик не корректируется (расхождение видно на панели; «доплата после» превратила бы
  предел в намерение).

## 6. Где виден расход

1. **https://openrouter.ai/activity** — фактический счёт провайдера (строка `Где виден расход` контракта).
2. **`/admin/metrics`** (страница — фича 11) через `spendToday()`: по каждому глобальному ключу `used / limit` за сегодня
   МСК; число попыток `model_call_log` по `kind` и `state` за сутки; `started` без исхода старше дедлайна + 60 с как
   «исход неизвестен»; оценка $ по токенам `[H]`. Пустые данные — «нет данных», не `0 %` (`honest-configuration` CFG-I7).
3. Порог тревоги из `Completion.md`: ≥ 80 % любого глобального предела; > 5 % `failed` за час.
4. Журнал процесса: `warn` на каждый отказ квоты (scope без ключа посетителя), `error` на отказ провайдера. Ключ API не
   логируется (страж S-8).

## 7. Конфигурация

**Закрытый список переменных, которые читает эта фича** (подмножество 13 переменных Boot config check):

| Переменная | Проверка | Кто читает (CFG-I5: каждая обязана читаться решением) |
|---|---|---|
| `OPENROUTER_API_KEY` | есть, не `''` | адаптер `live` |
| `VISITOR_SECRET` | есть, не `''` | `visitorKey()`, `addrKey()` |
| `LIMIT_ANSWER_VISITOR_DAY`, `LIMIT_ANSWER_BOT_DAY`, `LIMIT_ANSWER_GLOBAL_DAY` | `^[1-9][0-9]*$`, ≤ 2 147 483 647; visitor ≤ bot ≤ global | `answerKeys()` |
| `LIMIT_SANDBOX_ACCOUNT_DAY`, `LIMIT_SANDBOX_GLOBAL_DAY` | то же; account ≤ global | `sandboxKeys()` |
| `LIMIT_EMBED_TOKENS_ACCOUNT_DAY`, `LIMIT_EMBED_TOKENS_GLOBAL_DAY` | то же; account ≤ global | `embedKeys()` |
| `LIMIT_AUTH_ADDR_HOUR` | то же | `authKeys()` (вызывает `foundation`) |

Отсутствует, `''`, `0`, `-1`, `1.5`, `1e3`, ` 30`, персональный > суточного → `loadLimits()` бросает ошибку с именем
переменной и последствием (форма N5 `loadLimits`), процесс завершается кодом 1 (SC-US-016-2). Дефолтов нет.

**Выбор адаптера `fake`/`live` — НЕ переменной окружения.** В 13 переменных Spec селектора нет, и добавлять его значит
менять Boot config check. Решение исполнителя: боевой код всегда собирает `live`; `fake` внедряется только тестами через
параметр фабрики (`createPaidCall({ provider })`). Страж S-6: `fake.ts` не импортируется ни одним файлом вне `tests/` и
`packages/rag/src/provider/`. Если владелец/координатор захочет `fake` на стенде для E2E без денег — это новый ADR и
14-я переменная (не в этой фиче).

**Стык с `foundation` (параллельно пишется другим агентом).** Roadmap отдаёт `foundation` Boot config check (13
переменных) и предел входа 10/час — значит примитив квоты и `addr_key` могут появиться там раньше. Правило: **один
писатель на файл**. План исходит из двух вариантов, выбор — по факту слияния `foundation`:
- (а) `foundation` уже принесла `quota.ts`/`addr_key` → эта фича их расширяет (`+n`, набор ключей, `QuotaExhausted`),
  не дублируя; `config.ts` `foundation` вызывает `loadLimits()` отсюда.
- (б) не принесла → модули создаются здесь, `foundation` переводится на них одной правкой integration owner.
Дублирование логики квоты (как в N4, где копий оказалось три) запрещено — страж S-10 ищет второй `ON CONFLICT … used`.

## 10. Риски

| # | Риск | Следствие | Что делаем |
|---|---|---|---|
| R-1 | Один посетитель с многих /24 выжигает `answer:global` 3 000 | виджеты ВСЕХ клиентов 429 до полуночи МСК — DoS продукта за ≈ $4.5 | названо; предел на бота 300 защищает бюджет, но не доступность; пересмотр единицы — ADR-010 порог 5 %; Q2 |

| R-3 | Числа песочницы 100/2000 и входа 10/час не подтверждены владельцем | деньги под непринятым решением | Q1 до начала кода |

## 11. Оценка

- Код: 9 модулей (≈ 600–800 строк TS), тесты: ≈ 13 тест-файлов + 7 стражей (≈ 900 строк). Ни одного файла вне
  `packages/db/src`, `packages/rag/src`, `tests/`.
- Время: 1 исполнитель-кодер (opus) ≈ 3–4 ч + конкурентные тесты на Postgres ≈ 1 ч + мутационный прогон 14 мутаций ≈ 1 ч
  + ревью (cross-family) ≈ 1 ч. Итого ≈ **6–7 ч агентной работы**, при условии что `foundation` слита (миграции таблиц).
- Параллелизм: две единицы без общих файлов — (1) `packages/db` квота + лимиты + журнал + `spendToday`; (2)
  `packages/rag` порт + адаптеры; затем `paid-call.ts` и конкурентные тесты — одним исполнителем после слияния обеих.
- Денег на разработку: 0 (только `fake`); живой вызов — в фиче 16.
