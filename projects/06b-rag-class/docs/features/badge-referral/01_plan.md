## AC

- REF-01: GET /r/b/{public_id} на существующего бота атомарно записывает click с серверным visitorKey (существующий HMAC доверенного IP-префикса), bot и Moscow day; конкурентные повторы дают одну строку. 302 ведёт только на наш фиксированный /?ref=public_id&utm_source=badge. Неизвестный/невалидный id ведёт на наш лендинг без ref. Клиент не выбирает account/visitor/day. Без доверенного IP редирект допустим, click не записывается: не создавать общий фиктивный visitor и не хранить raw IP; эта граница явно раскрыта. Закрытая публикация не добавляется как новый gate: canonical алгоритм требует существование бота.
- REF-02: реальная загрузка лендинга с валидным по формату ref устанавливает n6b_ref на 30 дней лишь при отсутствии cookie; следующее касание не переписывает и не продлевает срок. HttpOnly, SameSite=Lax, Path=/, Secure в production. Невалидный ref не устанавливается. Неизвестный валидный id может остаться first-touch, но не атрибутируется без строки bot. Ответ с установкой cookie не кэшируется публично. Cookie-setting выполняется на серверной границе, не в render Server Component.
- REF-03: регистрация берёт ref только из cookie, разрешает bot в существующей атомарной account+session транзакции и записывает referred_by_bot_id. Подделанный/исчезнувший ref не ломает обычную регистрацию и не создаёт FK error/orphan. Login не переписывает атрибуцию, body account/ref ignored. Сохраняются CSRF, rate limit до bcrypt, email uniqueness и атомарность.
- REF-04: общий DB resolver для доверенного actingStudioId исключает source owner равного студии или её прямому ребёнку; другая семья разрешена. Реальные PG проверки studio/child/unrelated и standalone. В F10 ещё нет создания подаккаунтов: HTTP/UI wiring SC-US-011-2 является явной обязательной зависимостью F13, не объявляется наблюдавшимся пользовательским сценарием. Resolver тестируется сейчас и должен быть переиспользован F13. Новая самостоятельная регистрация из того же браузера по canonical границе не распознаётся как самореферал.
- REF-05: в кабинете Free кнопка «Убрать бейдж» показывает «Скоро: ~990 ₽/мес, оставьте заявку». Аутентифицированный same-origin POST пишет badge_removal_intent не чаще одного раза на аккаунт за Moscow day, включая конкурентные запросы; account берётся только из сессии. Бейдж/plan/badge_removal не меняются. Для атомарности lock существующей строки account и EXISTS growth_event внутри одной транзакции; новой таблицы/индекса не требуется. Нет платежей и operator activation UI.
- REF-06: лендинг ясно предлагает «Сделайте такого для своего сайта», с работающими регистрацией/входом, без выдуманных метрик. Actual Docker UI 1440/390 проверяет badge redirect → landing cookie → registration attribution, повторное касание, кабинет intent и неизменность badge. Браузерные cookies и real PG — реальные, не route.fulfill.
- REF-07: meaningful guard mutation (first-touch guard или семейное исключение) с fixed assertion red, exact restore и тот же green. Unit boundaries и real PG конкурентные click/intent, registration atomicity и family resolver. Node22 полный typecheck/all unit/all real PG/build на frozen source, exact immutable image/source hashes. Отдельный свежий Astra review после Sol, только конкретные исправления. Обязательные checks/UI не заменяются авторским отчётом.
