# Контракт входящих вебхуков — N4 «Тарелка»

Дата: 2026-09-12, переписан 2026-09-29 по коду (прежняя редакция — «входящих вебхуков нет» — описывала
неделю до OWN-001; вебхук оплаты появился фичей `subscription-and-commission` 15.09, а контракт не
обновили — это расхождение документа с кодом, исправленное здесь). Правило:
[`incoming-webhooks.md`](../../../.claude/rules/incoming-webhooks.md). Проверка:
`node ../../.claude/hooks/check-webhook-contract.cjs .`

**Входящие вебхуки:** да
**Отправитель:** ЮKassa
**Проверка повторной доставкой:** НЕ ВЫПОЛНЕНА
**Причина:** no-test-harness
**Ключ повторности:** тип события + id объекта уведомления ЮKassa (`<kind>:<objectId>`, функция `repeatKey` в `apps/api/src/routes/payments-webhook.ts`)
**Источник ключа:** событие-отправителя
**Хранилище ключа:** таблица payment_event, колонки provider/provider_event_id
**Механизм исключения:** уникальный-индекс
**Порядок событий:** перестановочен

Маршрут — `POST <APP_ORIGIN>/api/v1/webhooks/payments/yookassa` (стенд:
`https://tarelka.aicoding.space/api/v1/webhooks/payments/yookassa`), события `payment.succeeded` и
`refund.succeeded`. Имя провайдера в пути, не совпадающее с включённым, — `404`.

**Почему «НЕ ВЫПОЛНЕНА».** Повтор, одновременная доставка, возврат и недоступность провайдера проверены
на детерминированном фейке провайдера и настоящем PostgreSQL (`tests/integration/payments-webhook.test.ts`,
`tests/concurrency/payments-webhook-parallel.test.ts`); адаптер ЮKassa и проверка сети источника — юнит-
тестами (`tests/unit/payments-yookassa.test.ts`, `tests/unit/payments-webhook-source-ip-guard.test.ts`).
Один настоящий платёж тестового магазина прошёл 17.09 (`docs/operations/partner-journey.md`), но
ПОВТОРНОЙ доставки настоящим магазином никто не воспроизводил — стенда-повторителя уведомлений нет.

**Подписи у ЮKassa нет**, поэтому поля «что подписано», «когда проверяется подпись», «сравнение
подписи» и «окно свежести» неприменимы и не заполняются — несуществующая подпись за реализованную не
выдаётся. Подлинность — три проверки ВНЕ транзакции и ДО записи ключа: адрес источника (из
`X-Forwarded-For`, который дверь ЗАМЕНЯЕТ адресом клиента) ∈ сетям ЮKassa из списка в коде
(`apps/api/src/payments/origin.ts`); перезапрос объекта по API ЮKassa ключом магазина; сверка
заявленного объекта с перезапрошенным. Недоступность ЮKassa — исключение `PaymentProviderUnavailable`
до транзакции, ответ `503`, ни одной записи; повтор пройдёт полным путём. Вендорная проверка
описывает только подписанные вебхуки, поэтому её код `2` здесь честно означает «повтор настоящим
магазином не проверен», а не зелёный результат.

## Классы отказа

| Класс | Статус | Признак | Лечение | Доказательство |
|---|---|---|---|---|
| подделка | ЗАКРЫТ | «Оплачено» с чужого адреса или по несуществующему платежу | Сеть ЮKassa из кода + перезапрос + сверка до ключа повторности; `400` без записи | tests/unit/payments-webhook-source-ip-guard.test.ts |
| повтор | ЗАКРЫТ | Две комиссии за один платёж | Ключ `<kind>:<objectId>`, `UNIQUE (provider, provider_event_id)` в `payment_event`; частичный уникальный индекс начисления на платёж; одновременные доставки → один платёж | tests/concurrency/payments-webhook-parallel.test.ts |
| перестановка | ЗАКРЫТ | Подписка «откатилась» или укоротилась | Перестановочно: продление только удлиняет (`GREATEST(current_period_end, now()) + период`), возврат только прекращает | tests/integration/payments-webhook.test.ts |

ЗАКРЫТ означает тесты на фейке провайдера и настоящей базе; приёмка повторной доставки настоящим
магазином ЮKassa остаётся непроверенной. Для закрытия: в кабинете тестового магазина повторно
отправить уведомление по уже оплаченному платежу и убедиться, что в `payment` одна строка, в
`commission_entry` одно начисление.
