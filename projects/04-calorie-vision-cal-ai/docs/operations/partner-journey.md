# Путь партнёра-блогера: от предложения до выплаты

Что происходит на каждом шаге, каким кодом это сделано и **чего в продукте ещё нет**.
Состояние на 16.09.2026, стенд `https://tarelka.aicoding.space`.

> **Главное, что нужно знать до чтения.** Шаг 3 — «блогер публикует ссылку, по ней приходят
> люди, и они привязываются к его коду» — **сегодня не работает**: приложение не умеет ловить
> партнёрский код из адреса ссылки. Всё остальное — знакомство, кабинет, начисление, выдержка,
> выплата — сделано и проверено. Разрыв и его починка описаны в §3.

---

## Числа, на которых стоит вся схема

| Величина | Значение | Откуда |
|---|---|---|
| Цена подписки | **1000 ₽** в месяц | `N4_SUBSCRIPTION_PRICE_MINOR=100000` |
| Ставка партнёра | **50 %** | `partner.commission_rate_bp = 5000` |
| **С чего считается комиссия** | **с ЧИСТОЙ суммы**, после удержания провайдера | `payments-webhook.ts`: `net = gross − fee` |
| Комиссия с одной подписки | **≈ 478,65 ₽** (1000 − 42,70 удержание ЮKassa = 957,30; половина) | замер на живом платеже |
| Выдержка | **14 суток** с даты оплаты | `N4_COMMISSION_HOLD_DAYS=14` |
| День выплаты | **5-е число** каждого месяца | `previewNextPayout` |
| Бесплатный лимит | **20 сканов в сутки** | `N4_SCAN_LIMIT_USER=20` |
| Лимит по подписке | 100 сканов в сутки | `N4_SCAN_LIMIT_PRO=100` |
| Формат кода | `4–12 символов A–Z и 0–9` | CHECK в схеме |

При 2000 платящих подписчиках блогер получает **≈ 957 000 ₽ в месяц**, а не 100 000 — ваша
оценка была занижена примерно в десять раз. Порог «100 000 ₽» набирается уже на **210**
подписчиках.

## Шаг 1. Вы предлагаете блогеру попробовать

Ничего заводить заранее не нужно. Даёте обычную ссылку:

**https://tarelka.aicoding.space**

Что он увидит: экран съёмки сразу, без регистрации и без анкеты. Снимает тарелку → получает
состав, калории и БЖУ с указанием источника числа (запись USDA, её идентификатор, порция).

Ограничения бесплатного знакомства:
- **20 сканов в сутки** (не 10), счёт по московским суткам;
- дневник требует согласия на обработку данных о питании — экран
  **https://tarelka.aicoding.space/consent** покажется перед первой записью;
- аккаунт не нужен вовсе, пока он не захочет подписку или кабинет.

Для показа продукта этого достаточно: съёмка, результат, дневник и карточка «поделиться»
работают анонимно.

## Шаг 2. Блогер согласился — вы заводите его партнёром

Здесь два действия, и **первое пока делается руками в базе** — интерфейса создания партнёра
в кабинете НЕТ (см. «Чего ещё нет», пункт 2).

**2.1. Строка партнёра и его код** — SQL на стенде:

```sql
INSERT INTO partner (display_name, contact) VALUES ('Имя блогера', '@его_канал') RETURNING id;
INSERT INTO partner_code (partner_id, code) VALUES ('<id из предыдущей строки>', 'BLOGER1');
```

Код — от 4 до 12 символов, только заглавные латинские буквы и цифры.

**2.2. Приглашение** — вот это уже в интерфейсе. Вы заходите как владелец:

1. **https://tarelka.aicoding.space/settings** → зарегистрироваться почтой, которая внесена в
   список владельцев (`OWNER_EMAILS` в `apps/api/src/routes/admin.ts`);
2. **https://tarelka.aicoding.space/cabinet** → раздел «Кабинет владельца» → «Партнёры» →
   рядом с нужным партнёром кнопка **«пригласить»**;
3. появляется одноразовая ссылка вида `https://tarelka.aicoding.space/invite/<токен>`,
   она живёт **7 суток**.

Ссылку отдаёте блогеру.

**2.3. Блогер принимает приглашение.** Открывает ссылку, видит: «Вас приглашают стать партнёром
как ‹имя›. 50 % с каждой оплаченной подписки по вашему коду — бессрочно; выплаты 5-го числа».
Регистрируется своей почтой → «Принять приглашение» → его аккаунт привязан к строке партнёра.

С этого момента ему доступен **https://tarelka.aicoding.space/cabinet** — кабинет партнёра:
«к выплате 5-го», баланс, начислено и выплачено всего, воронка по коду (день / неделя / всё
время) и лента движений.

Приглашение одноразовое: повторное открытие той же ссылки даёт «просрочено или уже
использовано». Два одновременных принятия дают одну привязку — проверено конкурентным тестом.

## Шаг 3. Блогер публикует ссылку в канале — ЗДЕСЬ РАЗРЫВ

**Как задумано.** Блогер публикует ссылку со своим кодом; человек переходит, пользуется,
оформляет подписку; оплата привязывается к коду блогера.

**Как сегодня.** Такой ссылки нет. В приложении **нет ни одного места, которое читает
партнёрский код из адреса**: ни `?ref=CODE`, ни `/r/CODE`, ни `?code=CODE`. Проверено поиском
по всем экранам `apps/web/app`.

Механика привязки в сервере при этом **сделана целиком**: маршрут `POST /api/v1/codes/apply`
принимает код, создаёт привязку сессии к партнёру, разбирает конфликты (явный код сильнее
cookie, повторный явный код — отказ `409`), режет самореферал и всплески с одного адреса
(50 применений за 10 минут → код блокируется). Не хватает ровно двух вещей:

1. **страницы-входа по ссылке** — например `/r/BLOGER1`, которая применяет код и уводит на
   экран съёмки;
2. **поля «есть промокод»** на экране Pro — для тех, кто пришёл без ссылки.

Пока этого нет, привязку можно создать только запросом к API вручную:

```bash
curl -X POST https://tarelka.aicoding.space/api/v1/codes/apply \
  -H 'Content-Type: application/json' -d '{"code":"BLOGER1"}' -b cookies.txt -c cookies.txt
```

**Объём починки** — одна страница и одна форма, примерно два часа вместе с тестами.

## Шаг 4. Человек пришёл, пользуется, платит

1. Переход по ссылке блогера → привязка `pending` (после починки §3).
2. **Первое успешное распознавание** переводит привязку в `activated`. Это и есть защита от
   накрутки: переход по ссылке сам по себе денег не создаёт, нужен человек, который
   действительно сфотографировал еду (`activateAttributionOnRecognition`, вызывается воркером
   при завершении скана).
3. Упирается в 20 сканов в сутки → экран лимита → **https://tarelka.aicoding.space/pro**.
4. Оплата требует аккаунта: подписка принадлежит аккаунту, а не браузеру. Регистрация почтой в
   **https://tarelka.aicoding.space/settings**, всё сделанное анонимно (дневник, сканы,
   карточки) переезжает на аккаунт.
5. «Оформить за 1000 ₽» → форма ЮKassa → оплата → возврат на
   `https://tarelka.aicoding.space/pro/return?intent=…`.
6. ЮKassa присылает уведомление на `POST /api/v1/webhooks/payments/yookassa`. Сервер
   перезапрашивает платёж у провайдера (подпись у ЮKassa не используется — подлинность даёт
   адрес источника плюс перезапрос), заводит подписку, записывает платёж и **начисляет
   комиссию**.

## Шаг 5. Что вы видите в своём кабинете

**https://tarelka.aicoding.space/cabinet**, раздел «Кабинет владельца»:

- **выручка нетто** — то, что реально пришло после удержания провайдера;
- выручка брутто, число платежей;
- **на ручном разборе** — платежи, где сумма не совпала с ценой или провайдер не назвал
  удержание. Их нельзя не показывать, иначе они тихо копятся;
- подписки по статусам;
- **партнёры** — у каждого баланс и «доступно к выплате».

Разница между «баланс» и «доступно»: начисление созревает через **14 суток** после оплаты.
До этого возврат денег клиенту отменяет и комиссию (`clawback` — отрицательная запись), поэтому
выплачивать раньше нельзя.

## Шаг 6. Выплата блогеру

Ровно то, о чём вы спрашивали: «через 2 недели нет отписки — перевожу 50 %».

1. В кабинете владельца → «Выплата партнёру»: выбираете партнёра, вводите сумму в рублях,
   нажимаете «Записать выплату».
2. Сервер проверяет, что сумма **не превышает доступную** (`422 over_available`, если больше),
   и записывает движение вида `payout` — баланс партнёра уменьшается, в его кабинете появляется
   строка в «Движениях».
3. Повторное нажатие той же формы **не создаёт вторую выплату**: ключ повторности обновляется
   только после успешной записи, повтор возвращает «уже записано».

**Важно и честно: деньги приложение не переводит.** Запись в кабинете — это учёт, а не платёж.
Сам перевод вы делаете вне продукта (перевод на карту, счёт для самозанятого, договор с ИП).
Автоматических выплат нет и в объём недели они не входили.

## Чего ещё нет — список целиком

| # | Чего нет | Следствие | Объём |
|---|---|---|---|
| 1 | **Ссылки с партнёрским кодом** (`/r/CODE`) и поля «есть промокод» | шаг 3 невозможен без ручного запроса к API — **блокирует всю схему** | ~2 часа |
| 2 | Создания партнёра и его кода в интерфейсе | партнёр заводится SQL-запросом в базе | ~1,5 часа |
| 3 | Автоматической выплаты | перевод денег вручную, кабинет только учитывает | отдельная работа, нужен договор |
| 4 | Уведомлений партнёру | о начислении и выплате он узнаёт, только зайдя в кабинет | ~2 часа |
| 5 | Экспорта движений | нет выгрузки для бухгалтерии | ~1 час |

## Что уже проверено на живом стенде

- регистрация по почте, вход, перенос анонимного дневника на аккаунт;
- приглашение → принятие → кабинет партнёра (пройдено в настоящем браузере);
- оплата тестовой картой ЮKassa → вебхук → подписка `active` → `tier: paid` → потолок 100
  сканов и снятый бейдж с карточки;
- кабинет владельца: выручка, платежи, партнёры, форма выплаты.

**Не проверено на живых деньгах:** начисление комиссии по настоящей оплате. В тестовом прогоне
покупатель применил код, но не сделал ни одного скана — привязка осталась `pending`, и
антифрод справедливо не засчитал оплату партнёру. Это верное поведение, но означает, что путь
«переход → скан → оплата → начисление» целиком ещё не пройден ни разу.
