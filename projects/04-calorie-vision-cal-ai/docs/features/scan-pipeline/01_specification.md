## Цель

Дать пользователю ПЕРВЫЙ платный вызов продукта: снять кадр, дождаться распознавания ингредиентов и
порции моделью, честно отказать при исчерпанном потолке, и не потерять ни рубль на дублях, разрывах
соединения или гонке воркеров. Фича встраивается ПОВЕРХ каркаса `foundation`, а не строит его заново:
атомарный модуль потолков (`apps/api/src/quota/check-and-consume.ts`), аренда задания с fencing
(`apps/recognizer/src/lease.ts`) и интерфейс `ModelProvider` с фейком уже существуют и здесь только
ВЫЗЫВАЮТСЯ, а не переписываются.

Фича НЕ показывает пользователю калорийность и БЖУ и не вычисляет их: это ЯВНО объявленный стык со
следующей фичей `source-and-correct`, см. раздел «Стык с `source-and-correct`» ниже.

## Объём

Входит:

1. `POST /api/v1/scans` — приём фото (multipart, ≤ 12 МБ, JPEG/PNG/WebP/HEIC, ≥ 320×320 px),
   валидация по СОДЕРЖИМОМУ байтов, decompression-bomb защита, EXIF-strip, заявка
   `Idempotency-Key` (обязателен, UUID), квота `reason = primary` (переиспользование
   `CheckAndConsumeQuota` из `foundation`), сохранение оригинала в приватный бакет с
   `expires_on = +30 дней`, ответ `202` с `scan_id`.
2. `GET /api/v1/scans/{id}` — чтение статуса; чужой и несуществующий `id` дают ОДИН `404`.
3. `apps/recognizer`: нормализация фото ДО вызова модели (HEIC→JPEG, длинная сторона ≤ 1568 px,
   ≤ 5 МБ), вызов `ModelProvider.recognize` (Haiku 4.5) со строгой JSON-схемой, проверка диапазонов
   ответа В КОДЕ после разбора, эскалация к Sonnet 5 при `confidence < 0,6` через
   `CheckAndConsumeQuota(reason = escalation)` — четвёртый ключ, `LiveModelProvider` (Anthropic
   Messages API, vision + structured outputs) как вторая реализация интерфейса `ModelProvider`
   рядом с фейком `foundation`.
4. Двухуровневый лимит частоты канона §7 (30/мин мутирующие, 120/мин читающие) поверх общего хука
   `foundation` (FR-foundation-8), применённый к маршрутам 1 и 2.
5. `PurgeExpiredPhotos` — батч-уборка фото старше 30 дней (NFR-SEC-001, ADR-010).
6. Журнал `model_call {reason, model, ok, ms}` на КАЖДУЮ попытку — источник NFR-OPS-001; расход
   виден по счётчикам `scan_quota_counter`, а не только по журналу.
7. Тесты: unit (диапазоны, граница эскалации 0,59/0,60, валидация формата), integration (маршруты,
   нормализация, провайдер), конкурентные (идемпотентность, квота под нагрузкой ЭТОЙ фичи —
   эскалационный ключ, аренда с реальным вызовом провайдера), стражи по исходнику (ADR-001: схема
   без `calories/kcal/protein/fat/carbs`; единственное чтение `model_estimate_kcal`).

Вне объёма (делают другие фичи роадмапа): расчёт ккал/БЖУ из базы USDA, нечёткий поиск, курация
`food_synonym`, импорт FDC, `Snapshot`, `discrepancy_ratio`, экран расхождения — всё это FR-SOURCE-001
(остальная часть)/002/003, FR-CORRECT-003, реализует `source-and-correct` (см. ниже); карточка 9:16,
дневник, коды партнёра, вход через Telegram, экран лимита как UI — реализуют более поздние фичи.
Каркас квоты, аренды и адаптера — `foundation`, здесь не переписывается.

## Стык с `source-and-correct` — явное решение, требует подтверждения координатора

Бриф фичи предлагал: «результат `done` содержит `items` с `food_item_id: null` до появления RAG».
Это противоречит ADR-001 Confirmation (2): «`recognition` без единой ссылки на `food_item` не может
получить статус `done`» — инвариант, гарантированный тестом на внедрённом дефекте. Нарушать принятый
и защищённый ADR ради удобства стыка неверно, поэтому решение здесь ДРУГОЕ и явно расходится с
формулировкой брифа — расхождение зафиксировано, а не скрыто:

- В эту фичу вводится порт `MatchIngredientPort` (`match(item): Promise<{food_item_id, snapshot} |
  null>`) — точка расширения для сопоставления с базой. Реализация ЭТОЙ фичи —
  `NullMatchIngredientPort`, которая ВСЕГДА возвращает `null` (в `food_item` ещё нет ни одной строки:
  импорт делает `source-and-correct`).
- Следствие, СОГЛАСОВАННОЕ с ADR-001: пока используется `NullMatchIngredientPort`, ни один `recognition`
  не может сопоставить ни одной позиции → шаг «ни одна позиция не сопоставлена» истинен ВСЕГДА →
  терминальный статус для любого кадра с распознанной едой — `failed(no_food_matched)`, а НЕ `done`.
  `done` в этой фиче НЕДОСТИЖИМ, и это ожидаемое, объявленное ограничение, а не дефект.
- Логика эскалации, диапазонов, `low_confidence` и `failure_reason = quota_exhausted_escalation`
  проверяется UNIT-тестом с ПОДМЕНЁННЫМ портом (тестовый `MatchIngredientPort`, возвращающий
  совпадение) — это доказывает, что код правильный и готов принять реальный порт, не дожидаясь
  `source-and-correct`. Интеграционный прогон на РЕАЛЬНОМ `NullMatchIngredientPort` отдельно
  доказывает сегодняшнее поведение (`failed(no_food_matched)`).
- `source-and-correct` заменяет `NullMatchIngredientPort` на реализацию с триграммным поиском —
  контракт интерфейса не меняется, меняется только реализация за портом.

Координатор (владелец канона) подтверждает эту трактовку на чекпойнте Phase 1 ЛИБО явно требует
буквального прочтения брифа (что означало бы отмену ADR-001 Confirmation (2) — решение вне
компетенции исполнителя плеча).

## Функциональные требования

### FR-scan-pipeline-1 — приём фото: валидация по содержимому, не по имени
`POST /api/v1/scans` принимает `multipart/form-data` с полем файла. Тип файла определяется по БАЙТАМ
(`file-type` либо аналог, не `Content-Type` заголовка и не расширение). Полиглот (пригоден как
изображение И как HTML/архив) отвергается. Объявленные размеры изображения, дающие распаковку свыше
100 Мпикс, отвергаются ДО декодирования. EXIF, включая GPS, снимается при нормализации (шаг
recognizer, FR-scan-pipeline-5), а не на приёме — приём сохраняет оригинал НЕТРОНУТЫМ (ADR-010:
удаление по запросу удаляет обе копии). Непригодный формат/размер/содержимое даёт `422`/`413` с
названной причиной ДО обращения к квоте и ДО создания `photo`; попытка НЕ списывается
(FR-CAPTURE-002, `EnqueueScan` шаг 2).

### FR-scan-pipeline-2 — заявка ключа повторности форматом, ДО загрузки и ДО транзакции
Заголовок `Idempotency-Key` обязателен и обязан быть UUID; отсутствие или непригодная форма — `422`
ДО загрузки объекта, ДО транзакции БД и ДО обращения к квоте. Это ТОЛЬКО проверка ФОРМЫ; фактическая
атомарная ЗАЯВКА ключа (вставка строки) объединена с сохранением фото и списанием квоты в ОДНУ
короткую транзакцию — см. FR-scan-pipeline-14 (Попытка 3, PC-02). Прежняя формулировка (Попытка 1)
заявляла ключ РАНЬШЕ квоты и `photo_id` отдельным шагом — это оставляло воркеру шанс захватить
незавершённую строку; заменено целиком.

### FR-scan-pipeline-3 — квота ДО вызова модели, атомарно, переиспользованием `foundation`
Каждая ВНЕШНЯЯ попытка распознавания (маршрут `POST /scans`, и — начиная с Попытки 3 — повторный
захват воркером после истечения аренды, FR-scan-pipeline-15) списывает СВОЁ разрешение через
`CheckAndConsumeQuota(session, ip_prefix, day, reason = 'primary')` из `apps/api/src/quota/
check-and-consume.ts` (`foundation`, не переписывается) ДО вызова модели, атомарно, тремя ключами.
`day` вычисляется В МОМЕНТ КАЖДОЙ конкретной попытки, а не наследуется от более раннего вызова
(FR-scan-pipeline-18, PC-06). `IF refused THEN` отказ называет `scope`; НИКАКОГО вызова модели не
делается (ADR-007, FR-LIMIT-001/002).

### FR-scan-pipeline-4 — немедленный `202` после атомарной публикации
Ответ `202` с `{ scan_id, status: 'queued' }` возвращается ТОЛЬКО после успешного `COMMIT`
транзакции FR-scan-pipeline-14 (оригинал сохранён, `recognition` и `photo` вставлены, квота
списана, ВСЁ вместе). При ПЕРВОМ скане сессии пишется `growth_event(type = install, …)` (вне
транзакции — потеря этого события не создаёт денежной или структурной гонки). Идентификатор выдаётся
ДО начала долгой работы, не дожидаясь распознавания (`long-job-contract.md`).

### FR-scan-pipeline-5 — нормализация фото на сервере ДО вызова модели: ориентация, кадр, бюджет
`recognizer` преобразует HEIC/HEIF → JPEG (декодируя ПОДТВЕРЖДЁННЫЙ по байтам на приёме
`photo.mime`, а не заново «заявленный»), берёт РОВНО первый кадр/страницу многокадрового контейнера
(`{ pages: 1 }` — HEIC-последовательности, анимированный WebP), ПРИМЕНЯЕТ ориентацию EXIF (`rotate()`)
ДО удаления метаданных, ЗАТЕМ снимает ВСЕ метаданные целиком, приводит длинную сторону к ≤ 1568 px,
сжимает до ≤ 5 МБ с ограниченным числом итераций, в рамках ОБЩЕГО бюджета декодирования ≤ 50 Мпикс и
≤ 12 МБ на вход — того же бюджета, что и на приёме (FR-scan-pipeline-17), не второго произвольного
числа (PC-05). Оригинал не изменяется. Соединение с базой на время загрузки и нормализации НЕ
удерживается. `IF` любая трансформация не удалась ИЛИ исчерпан предел итераций сжатия `THEN
failed(schema_violation)` с названным шагом, вызова модели НЕ делать — это РЕДКИЙ путь: основная
масса недекодируемых файлов уже отсеяна FR-scan-pipeline-17 на приёме.

### FR-scan-pipeline-6 — вызов модели по строгой схеме с явно переданной моделью, диапазоны — наш код
`recognizer` вызывает `ModelProvider.recognize(image, schema, { model, deadlineMs: 25_000 })` —
МОДЕЛЬ (`N4_MODEL_PRIMARY` либо, при эскалации, `N4_MODEL_ESCALATION`) передаётся ВЫЗЫВАЮЩИМ кодом
явным параметром, а не выбирается интерфейсом (расширение `ModelProvider` из `foundation`, см.
`02_pseudocode.md` «Data Structures», PC-09). Дедлайн запроса — 25 с; скрытые повторы SDK-клиента
отключены явно (`maxRetries: 0`) — единственный законный источник второго вызова на одну попытку
`lease_fence` — эскалация (FR-scan-pipeline-7), не библиотека. Схема ответа: `items[]` (`label_ru`,
`mass_g`, `candidates[]` ≤ 3), `confidence`, `model_estimate_kcal`; полей `calories`, `kcal`,
`protein`, `fat`, `carbs` в схеме НЕТ (ADR-001). После разбора код проверяет: `confidence` в 0…1;
`mass_g` каждой позиции в 1…5000; позиций ≤ 12; кандидатов на позицию ≤ 3; `model_estimate_kcal ≥ 0`.
`IF` любое условие нарушено `THEN failed(schema_violation)` с названным полем — значение вне
диапазона трактуется как отсутствующее, а НЕ подрезается до границы. `IF` провайдер недоступен или
истёк дедлайн `THEN failed(provider_unavailable | provider_timeout)` — попытка уже списана и не
возвращается. `IF` модель не нашла еды `THEN refused(no_food_detected)`, запись дневника не
создаётся (FR-RECOGNIZE-001, SC-US-001-2).

### FR-scan-pipeline-7 — эскалация к Sonnet 5, четвёртый ключ ДО вызова
`IF confidence < 0,6 AND escalated = false THEN` вызвать `CheckAndConsumeQuota(reason =
'escalation')` — ДО обращения к Sonnet 5. `IF granted THEN` повторить вызов модели `Sonnet 5` ровно
ОДИН раз, `escalated = true`, `attempt_no = 2`. `ELSE` второго вызова НЕ делать: результат первичной
модели сохраняется, попытка эскалации отклонена по `scope = escalation`, событие расхода несёт
`quota_exhausted_escalation`. Логика проверяется unit-тестом с подменённым `MatchIngredientPort`
(см. «Стык»), поскольку в реальном окружении этой фичи `done` недостижим (ADR-004, ADR-007,
`model-cost-contract.md`).

### FR-scan-pipeline-8 — итог сопоставления через порт (пакетный вызов), терминальный статус без базы
`MatchIngredientPort.match(items[])` вызывается ОДИН раз на ВЕСЬ список позиций и возвращает МАССИВ
той же длины и порядка — не один `food_item_id`/`Snapshot` на позицию поодиночке (Попытка 1), а
запись `{ food_item_id, portion_g, source_snapshot, parts? }`, где КАЖДЫЙ элемент `parts[]` несёт
СВОЙ `source_snapshot` (идентификатор записи базы, порция в граммах, дата записи базы) — контракт
композиции СИММЕТРИЧЕН верхнему уровню, а не урезан (правка Попытки 4, PC-08). `parts?` допускает составное
блюдо (`food_synonym.recipe_parts`) — контракт, готовый принять реализацию `source-and-correct` без
переделки вызывающего кода (PC-08). Реализация этой фичи (`NullMatchIngredientPort`) возвращает
МАССИВ, где КАЖДЫЙ элемент несёт `food_item_id: null` → каждая позиция помечается `unmatched = true`.
`IF` НИ ОДНА позиция не сопоставлена `THEN recognition = failed(no_food_matched)` — по решению
координатора DEC-A-014, попытка ОПЛАЧЕНА и ОБРАБОТАНА моделью, это не отказ ДО вызова.

**Согласование с ADR-001 Confirmation (2), названное явно (PC-08).** Root `ADR.md` требует
`refused(no_food_matched)` для генуинного «искали и не нашли» — мира, где матчинг реально СПРАШИВАЕТ
базу. В этой фиче матчинг НЕ спрашивает вовсе (`NullMatchIngredientPort` — заглушка, а не поиск с
нулевым результатом), и `failed(no_food_matched)` — статус ДРУГОГО по природе события. Когда
`source-and-correct` подставит реальный порт, генуинный ноль совпадений вернётся к
`refused(no_food_matched)` root-уровня, и `failed(no_food_matched)` этой фичи исчезнет вместе с
заглушкой. Расхождение между документами до тех пор — ОСОЗНАННОЕ и названное, не тихо перекрытое;
координатор подтверждает трактовку явно, она не выводится автоматически ни из одного документа.

Результат записывается УСЛОВНО по своему `lease_fence` И статусу `queued` (см. FR-scan-pipeline-16):
`UPDATE`, затронувший ноль строк, отбрасывается либо как `stale_lease_result` (проиграл гонку
другому воркеру), либо как `swept_as_timeout` (проиграл гонку `SweepStuckScans`) — различаются
перечитыванием строки (ADR-003, DEC-A-008).

### FR-scan-pipeline-9 — `GET /api/v1/scans/{id}`: владение и честные поля
Чужой и несуществующий `id` дают ОДИН `404` (владение — по `owner_key` на сервере). Тело ответа несёт
`status`, `items[]` (`label_ru`, `mass_g`, `unmatched`, `food_item_id: null` — до `source-and-correct`),
`confidence`, `low_confidence`, `escalated`, `model_estimate_kcal`, `failure_reason?`. Поля
`kcal_total`, `macros`, `sources[]`, `conflict_flag`, `share_card_id` из полного контракта проекта
(`Pseudocode.md`, маршрут 2) в ЭТОЙ фиче отсутствуют либо равны `null`/`[]` — они появляются с
`source-and-correct`, и это названо здесь явно, а не подразумевается.

### FR-scan-pipeline-10 — двухуровневый лимит частоты
Хук частоты `foundation` (FR-foundation-8) расширяется порогами канона §7: 30 запросов/мин на
`ip_prefix` для МУТИРУЮЩИХ маршрутов (`POST /scans`), 120/мин для ЧТЕНИЯ (`GET /scans/{id}`); `429`
без тела запроса в журнале (DEC-A-013). Применяется ДО разбора тела (`security-operation-order.md`).

### FR-scan-pipeline-11 — `PurgeExpiredPhotos`
Раз в сутки батч `photo` с `expires_on < today AND file_state = 'present'`, ограниченным размером;
удаление объекта из бакета (отсутствие объекта — тоже успех); `file_state → purged`, строка `photo`
СОХРАНЯЕТСЯ. Идемпотентна: повторный прогон в тот же день не делает ничего (NFR-SEC-001, ADR-010).

### FR-scan-pipeline-12 — наблюдаемость расхода: событие на попытку, переживающее падение процесса
Каждый вызов `ModelProvider.recognize` пишет ДВЕ строки структурированного журнала: `START`
НЕМЕДЛЕННО перед вызовом — `{ request_id, scan_id, fence, reason: 'primary'|'escalation', model,
mode: 'fake'|'live', day }`; `OUTCOME` сразу после ответа — `{ request_id (тот же), outcome:
'ok'|'failed'|'timeout', ms, input_tokens?, output_tokens? }` (PC-07). `START` пишется В
СТРУКТУРИРОВАННЫЙ ВЫВОД (не буферизуется в памяти) — падение процесса МЕЖДУ `START` и `OUTCOME`
оставляет `START` в журнале; плановый агрегатор `scripts/telemetry/model-calls.sh` (план, эта фича
его НЕ реализует) сопоставляет `request_id` и метит непарные `START` старше грейс-периода как
`outcome: 'unknown'` — счётчики попыток это НЕ меняет, квота уже списана ДО вызова независимо от
исхода журнала. Служебная страница расхода (агрегация по дню, стоимости, доле эскалаций) — ПЛАН,
явно ВНЕ недели MVP; NFR-OPS-001 в части «сырое структурированное событие на попытку» закрывается
этой фичей, в части «служебная страница» — нет.

### FR-scan-pipeline-13 — `LiveModelProvider` как вторая реализация порта, включается ключом
`apps/recognizer/src/provider/anthropic.ts` реализует расширенный интерфейс `ModelProvider(image,
schema, { model, deadlineMs })` из `foundation` (см. FR-scan-pipeline-6, PC-09) поверх Anthropic
Messages API (vision + structured outputs), пробрасывая `model` и `deadlineMs` в реальный запрос.
Фейк `foundation` также возвращает `model` в ответе, чтобы транспортный контрактный тест мог
проверить, что вызов эскалации ушёл именно с `N4_MODEL_ESCALATION`, а не повторно с `N4_MODEL_PRIMARY`
(AC-scan-pipeline-29) — без этого поля фейк способен молча скрыть дефект выбора модели. Выбирается
`SelectModelProvider` (`foundation`) при `N4_MODEL_PROVIDER=live` и непустом `ANTHROPIC_API_KEY`; по
умолчанию и во всех тестах — фейк (DEC-A-009). Живой режим не является предметом тестов этой фичи и
отдельно помечается «живое распознавание не выполнено: нет ключа».

### FR-scan-pipeline-14 — атомарная публикация задания: объект ДО транзакции, одна короткая транзакция
Объект загружается в приватный бакет ДО любой транзакции БД, по ДЕТЕРМИНИРОВАННОМУ ключу
`sha256(содержимое) + device_session_id` — повтор того же файла той же сессией перезаписывает ТОТ ЖЕ
объект, орфан физически не создаётся (PC-02). Затем ОДНА короткая транзакция: вставка `photo`,
вставка `recognition` (`status='queued'`, `photo_id` уже установлен ЭТИМ ЖЕ INSERT'ом — не вторым
шагом), списание квоты `primary` (FR-scan-pipeline-3). `IF` квота отказала `THEN` вся транзакция
откатывается ЦЕЛИКОМ — ни `recognition`, ни `photo` не сохраняются вовсе (не переводятся в `refused`:
строки не существует), объект удаляется best-effort и в любом случае ограничен по времени политикой
жизненного цикла бакета (ADR-010, второй, независимый от таблицы `photo` рубеж). `IF` квота разрешила
`THEN COMMIT` — строка `recognition` появляется воркеру ЦЕЛИКОМ и атомарно, промежуточного состояния
«есть строка без `photo_id`» не существует ни для одного наблюдателя. Предикат выборки воркера
(`foundation`) дополнительно требует `photo_id IS NOT NULL` как ВТОРОЙ, defense-in-depth рубеж —
правка ЧУЖОГО файла, не вносится этой квитанцией, а маршрутизируется координатором в план
`foundation` (см. `03_architecture.md`).

### FR-scan-pipeline-15 — повторная попытка после истечения аренды списывает СВОЮ квоту
Каждый ЗАХВАТ задания воркером с `lease_fence ≥ 2` (то есть НЕ первый захват — предыдущий воркер не
уложился в 60 с аренды) списывает ЕЩЁ ОДНУ попытку `primary` (`CheckAndConsumeQuota(reason=primary)`,
три ключа) ДО загрузки фото и ДО вызова модели (PC-01, DEC-A-008: обе попытки оплачены и учтены).
`IF refused THEN recognition = refused(quota_exhausted_${scope})`, модель НЕ вызывается — это отказ
ДО вызова. Первый захват (`lease_fence = 1`) НЕ списывает повторно: попытка №1 уже оплачена
`POST`'ом (FR-scan-pipeline-3). Скрытых повторов внутри одной попытки НЕТ: SDK-клиент создаётся с
`maxRetries: 0` (FR-scan-pipeline-6).

### FR-scan-pipeline-16 — дедлайны задачи и сметание застрявших заданий
`lease_fence ≤ 3` — четвёртый захват НЕВОЗМОЖЕН по построению предиката выборки `foundation`
(зависимость, см. `03_architecture.md`); задание с исчерпанным пределом захватов и истёкшей арендой
становится незахватываемым и было бы вечно `queued` без стороннего вмешательства. `SweepStuckScans`
(отдельный шаг цикла опроса `recognizer`, не отдельный сервис) переводит в `failed(timeout)`: (а)
`queued` без единого захвата дольше 5 минут; (б) `queued` с `lease_fence = 3` и истёкшей арендой; (в)
`queued`, захваченный хотя бы раз, для которого `now() - created_at > 30 с` — но ТОЛЬКО когда аренда
ТОЖЕ истекла (`leased_until IS NULL OR leased_until < now()`, правка Попытки 4/DEC-A-017): задание в
пределах ЖИВОЙ аренды sweeper НИКОГДА не трогает — живой воркер отслеживает свой бюджет сам
(`AbortController`, FR-scan-pipeline-20) и либо сам пишет терминал, либо честно исчерпывает аренду.
Без этого уточнения sweeper мог прервать результат ЕЩЁ обрабатывающего воркера (PC2-02). (г) Предикат
выборки `foundation` желательно исключает захват уже просроченных заданий (`created_at` старше 30 с) —
это оптимизация; ОБЯЗАТЕЛЬНЫЙ рубеж — сам воркер (FR-scan-pipeline-20 шаг 1а), не зависящий от того,
обновлён ли предикат.

### FR-scan-pipeline-17 — ограниченная проверка декодируемости ДО квоты и ДО сохранения
`POST /api/v1/scans` выполняет ДЕШЁВУЮ, но настоящую проверку декодируемости (`sharp(buffer, {
limitInputPixels: 50_000_000 }).metadata()` плюс декодирование одной страницы/кадра целиком) ПОСЛЕ
проверки сигнатуры/размера/decompression-bomb, но ДО загрузки объекта, ДО заявки идемпотентности и
ДО квоты. `IF` файл с правдоподобной сигнатурой не декодируется `THEN RETURN 422 (invalid_image)` —
БЕЗ занятия любого из трёх ресурсов (PC-04). Это ОТДЕЛЬНАЯ, более дешёвая проверка от полной
нормализации (FR-scan-pipeline-5): она не конвертирует и не сжимает, только доказывает
декодируемость. Общий бюджет распаковки (≤ 50 Мпикс, ≤ 12 МБ) — ОДИН и тот же на приёме и при полной
нормализации, не два разных числа.

### FR-scan-pipeline-18 — сутки квоты вычисляются в момент КАЖДОЙ попытки
`day` для `CheckAndConsumeQuota` — календарная дата `Europe/Moscow` В МОМЕНТ КОНКРЕТНОГО вызова:
`POST` считает СВОЙ `day`, повторный захват воркера (FR-scan-pipeline-15) и решение об эскалации
(FR-scan-pipeline-7) считают СВОЙ, независимо от того, каким был `day` у более раннего вызова того
же скана. `reset_at` в ответе `429` — следующая полночь `Europe/Moscow` ОТ МОМЕНТА этого конкретного
отказа. Резервирование квоты между сутками не производится и не нужно: ключ счётчика включает `day`,
поэтому смена суток естественно означает НОВУЮ строку `scan_quota_counter`, начинающую с нуля.
**Правка Попытки 4 (DEC-A-017, закрывает найденную дыру PC-06):** ПЕРВЫЙ захват воркером ТОЖЕ обязан
пересчитать `day` и списать `primary` ЗАНОВО, если `day(now) ≠ day(created_at)` — не только при
`lease_fence ≥ 2`. Скан, принятый в 23:59:30 (день D) и впервые захваченный воркером в 00:00:30 (день
D+1, при перегруженном пуле воркеров без единой истёкшей аренды), иначе тратил бы потолок дня D для
работы, выполняемой в день D+1. Пере-списание на этой границе — СОЗНАТЕЛЬНЫЙ перерасход в сторону
строгости, а не дефект (`RecognizeScanWithinScanPipeline` шаг 2).

### FR-scan-pipeline-19 — владение объектом: свой ключ на загрузку, без дедупликации
`object_key = device_session_id + '/' + recognition_id + '.' + ext`, где `recognition_id` генерируется
ДО загрузки и совпадает с будущим `id` строки `recognition` (PC2-01). Ключ по хешу СОДЕРЖИМОГО
(Попытка 3) ОТМЕНЁН: два разных запроса одной сессии с одинаковым фото и разными `Idempotency-Key`
делили бы один объект, и удаление второго (например, при отказе его квоты) стирало бы фото ПЕРВОГО,
уже принятого скана. Удаление объекта (best-effort при откате транзакции, шаг 9.1/9.3
`EnqueueScanForFeature`) адресовано ИСКЛЮЧИТЕЛЬНО `object_key` СВОЕЙ, отклонённой попытки — структурно
не может задеть чужой объект. Дедупликация одинаковых фото НЕ выполняется: экономия места — не цель
этой недели, целостность чужого скана — да.

### FR-scan-pipeline-20 — общий бюджет задачи 30 с, платная работа не продолжается после истечения
Бюджет задачи = `created_at + 30 с`, ОДИН на все попытки захвата, а не 25 с на каждый вызов заново
(PC-03, PC2-02). Воркер при КАЖДОМ захвате вычисляет `remaining = 30с − (now − created_at)`; `IF
remaining ≤ 0 THEN failed(timeout)` НЕМЕДЛЕННО, без вызова модели и без нового списания — задание
слишком долго ждало в очереди. Иначе дедлайн вызова = `min(25с, remaining)`, и нормализация, и вызов
модели выполняются ПОД ОДНИМ `AbortController`: по истечении бюджета HTTP-вызов обрывается
НЕМЕДЛЕННО — платная работа не продолжается ни секунды сверх бюджета. Ответ, пришедший ПОЗЖЕ бюджета
(гонка между ответом провайдера и истечением), оплачен и учтён (`model_call outcome: 'late'`), но НЕ
применяется — записывается `failed(timeout)`. `SweepStuckScans` — ТОЛЬКО backstop для заданий с
ИСТЁКШЕЙ арендой (воркер, вероятно, упал без штатной отработки `AbortController`); задание в пределах
СВОЕЙ ЖИВОЙ аренды sweeper'ом никогда не трогается (закрывает PC2-02: sweeper больше не может
перевести в `failed` задание, которое в этот момент честно обрабатывает живой воркер).

### FR-scan-pipeline-21 — агрегатор журнала попыток — часть этой фичи
`scripts/telemetry/model-calls.sh` (либо `.cjs`) реализуется В ЭТОЙ фиче (не только планируется, PC-07):
читает JSON-журнал `api`/`recognizer` за сутки, коррелирует `START`/`OUTCOME` по `attempt_id =
recognition_id:fence:reason`, метит непарные `START` старше грейс-периода `unknown`, печатает счётчики
попыток по `(reason, outcome, model)` и суммарное/среднее `ms`. Служебная СТРАНИЦА (веб, владелец,
обновление ≤ 5 минут, расчёт стоимости в валюте) остаётся ПЛАНОМ, явно ВНЕ недели MVP — агрегатор
даёт числа по требованию, не постоянно работающий сервис.

## Нефункциональные требования

### NFR-scan-pipeline-1 — результат ≤ 6 с p95, включая эскалацию (NFR-PERF-001)
Соединение с базой не удерживается во время вызова модели (аренда закрывается ДО обращения к
провайдеру, `foundation` `LeaseRecognitionJob`); подписанная ссылка на объект живёт ≤ 15 минут.
Измеряется на РАЗВЁРНУТОМ стенде по журналу, не на этой машине — в этой фиче НЕ ИЗМЕРЕНО (стенда нет).

### NFR-scan-pipeline-2 — фото приватны, 30 дней, presigned (NFR-SEC-001)
Публичной ссылки на фото не существует ни на одном шаге. Объект отдаётся только подписанным URL
владельцу сессии, срок ≤ 15 минут. `expires_on = created_at + 30 дней`; удаление — `PurgeExpiredPhotos`
плюс политика жизненного цикла бакета как второй рубеж (ADR-010).

### NFR-scan-pipeline-3 — 3000 сканов/сутки без деградации времени ответа (NFR-SCALE-001)
Очередь распознавания не удерживает соединение с базой во время вызова внешней модели (см.
NFR-scan-pipeline-1); горизонтальное масштабирование `recognizer` копиями без изменения кода — цену
несёт единственное настоящее узкое место, внешний вызов модели (латентность 2–5 с).

## Критерии приёмки

### AC-scan-pipeline-1 — вход проверяется по содержимому, не по имени
Given файл `plate.jpg`, чьи первые байты НЕ являются сигнатурой JPEG/PNG/WebP/HEIC
When выполняется `POST /api/v1/scans` с этим файлом и валидным `Idempotency-Key`
Then ответ `422` с названной причиной; строка `recognition` не создана, `scan_quota_counter` не
изменён.

### AC-scan-pipeline-2 — decompression bomb отвергается до декодирования
Given изображение, чьи заявленные размеры дают распаковку свыше 100 Мпикс при валидных байтах формата
When выполняется `POST /api/v1/scans`
Then ответ `422`/`413` до попытки декодирования; сервис не падает и не зависает.

### AC-scan-pipeline-3 — превышение размера и формата не списывает квоту
Given фото 13 МБ (сверх 12 МБ) и фото 250×250 px (меньше 320×320)
When выполняется `POST /api/v1/scans` для каждого
Then оба получают отказ с названной причиной; `scan_quota_counter.used` не изменился ни для одного
ключа.

### AC-scan-pipeline-4 — `Idempotency-Key` обязателен
Given запрос `POST /api/v1/scans` без заголовка `Idempotency-Key` либо со значением `not-a-uuid`
When запрос обрабатывается
Then ответ `422`; квота не проверяется и не списывается.

### AC-scan-pipeline-5 — повтор с тем же ключом не создаёт второй оплаченный скан
Given успешный `POST /api/v1/scans` с ключом `K` вернул `scan_id = S`
When тот же запрос повторяется с тем же `Idempotency-Key = K` и той же сессией
Then ответ `202` с ТЕМ ЖЕ `scan_id = S`; `scan_quota_counter.used` не увеличился повторно; вызов
модели не сделан дважды.

### AC-scan-pipeline-6 — конкурентная идемпотентность
Given два одновременных `POST /api/v1/scans` с одним `Idempotency-Key` и одной сессией
When оба запроса стартуют без ожидания друг друга
Then оба получают ОДИН и тот же `scan_id`; в базе ровно одна строка `recognition` с этим ключом;
ровно ОДИН оплаченный вызов модели.

### AC-scan-pipeline-7 — отказ квоты не создаёт задание и называет `scope`
Given `scan_quota_counter` пользователя уже на пределе (`used = limit`)
When выполняется валидный `POST /api/v1/scans`
Then ответ `429` с телом `{ limit, reset_at, scope: 'user' }`; фото НЕ сохранено в бакет; строка
`recognition` переведена в `refused(quota_exhausted_user)`; вызов модели не выполнен.

### AC-scan-pipeline-8 — конкурентный потолок пользователя (20 при пределе 10)
Given предел `N4_SCAN_LIMIT_USER = 10`, одно устройство, ноль попыток за сегодня
When 20 `POST /api/v1/scans` стартуют одновременно с одним общим барьером
Then ровно 10 получают `202`, ровно 10 получают `429(scope=user)`; `scan_quota_counter.used` для
ключа пользователя равен ровно 10; ни одна попытка не потеряна и не посчитана дважды.

### AC-scan-pipeline-9 — нормализация HEIC до вызова модели
Given фото формата HEIC размером 11 МБ, длинной стороной 4032 px
When `recognizer` обрабатывает задание
Then перед вызовом модели создаётся `photo.normalized_object_key` формата JPEG с длинной стороной
≤ 1568 px и размером ≤ 5 МБ; вызов модели выполняется НАД нормализованной копией, оригинал не
изменён.

### AC-scan-pipeline-10 — неудачная нормализация не вызывает модель
Given повреждённый файл, прошедший приёмную валидацию по сигнатуре, но не декодируемый нормализатором
When `recognizer` обрабатывает задание
Then результат `failed(schema_violation)` с названной причиной; ни одного вызова `ModelProvider` не
зафиксировано счётчиком обращений.

### AC-scan-pipeline-11 — диапазоны проверяет код, а не подрезает
Given ответ модели с `confidence = 1,5`, ЛИБО с позицией `mass_g = 6000`, ЛИБО с 13 позициями
(три отдельных прогона)
When `recognizer` разбирает ответ
Then каждый прогон даёт `failed(schema_violation)` с названным полем; значение НЕ подрезается до
границы (`confidence` не становится `1`, `mass_g` не становится `5000`).

### AC-scan-pipeline-12 — граница эскалации 0,59/0,60
Given ответ первичной модели с `confidence = 0,59`, ЗАТЕМ отдельно `confidence = 0,60`
When `recognizer` принимает решение об эскалации
Then при `0,59` выполняется второй вызов модели (эскалация); при `0,60` второй вызов НЕ выполняется;
оба исхода проверяются счётчиком обращений к адаптеру провайдера.

### AC-scan-pipeline-13 — конкурентная эскалация: 20 при остатке 1
Given предел `N4_ESCALATION_LIMIT_DAY` исчерпан до остатка 1, 20 распознаваний одновременно
возвращают `confidence < 0,6`
When все 20 одновременно вызывают `CheckAndConsumeQuota(reason = escalation)`
Then РОВНО один вызов `Sonnet 5` зафиксирован счётчиком обращений к адаптеру провайдера (не текстом
журнала); остальные 19 получают `refused(escalation)` и НЕ вызывают Sonnet 5.

### AC-scan-pipeline-14 — 601-я эскалация не выбрасывает первичный результат (unit, подменённый порт)
Given `MatchIngredientPort`, подменённый тестовым двойником, возвращающим совпадение для каждой
позиции; счётчик эскалации уже на пределе (601-я попытка)
When `recognizer` обрабатывает задание с `confidence < 0,6`
Then второй вызов модели НЕ выполняется; итоговый статус — `done` с `low_confidence = true` и
`failure_reason = quota_exhausted_escalation`, а НЕ `failed` и НЕ `refused`. Тест явно помечен как
доказательство ГОТОВНОСТИ кода к реальному порту, а не сегодняшнего интеграционного поведения
(см. «Стык с `source-and-correct`»).

### AC-scan-pipeline-15 — реальное окружение этой фичи: `done` недостижим, а инвариант ADR-001 держится
Given реальный `NullMatchIngredientPort` (эта фича, `food_item` пуст), модель нашла еду с ЛЮБЫМ
`confidence`
When `recognizer` завершает обработку
Then итоговый статус — `failed(no_food_matched)`; статус `done` НИ РАЗУ не зафиксирован ни на одном
прогоне интеграционного набора этой фичи; страж по исходнику (ADR-001, Confirmation 2) остаётся
зелёным без единого исключения.

### AC-scan-pipeline-16 — провайдер недоступен или таймаут — попытка засчитана, ошибка не проглочена
Given фейковый провайдер настроен на исход `provider_unavailable` (отдельно — `provider_timeout`)
When `recognizer` вызывает `ModelProvider.recognize`
Then результат `failed(provider_unavailable)` / `failed(provider_timeout)`; квота НЕ откатывается —
попытка уже списана на шаге приёма; исключение из вызова не проглатывается функцией-колбэком
транзакции (`security-operation-order.md`).

### AC-scan-pipeline-17 — устаревшая аренда с реальным вызовом провайдера
Given воркер A взял задание, аренда искусственно истекла ПОКА A ожидает ответ фейкового провайдера с
управляемой задержкой; воркер B захватывает то же задание и завершает его первым
When A получает ответ провайдера и пытается записать результат своим (устаревшим) `lease_fence`
Then `UPDATE` от A затрагивает НОЛЬ строк; результат B остаётся нетронутым; в аудите есть запись
`stale_lease_result` с `scan_id`, `fence` A и текущим `fence`. Обе попытки списаны в квоту — это
названная цена fencing (DEC-A-008), а не дефект.

### AC-scan-pipeline-18 — чужой скан недостижим
Given `recognition` принадлежит сессии X
When сессия Y выполняет `GET /api/v1/scans/{id}` этой записи, а также `GET` НЕСУЩЕСТВУЮЩЕГО `id`
Then оба запроса получают ОДИН И ТОТ ЖЕ `404`; тело ответа не позволяет отличить «чужой» от
«не существует».

### AC-scan-pipeline-19 — атомарная публикация: крах между загрузкой и транзакцией не создаёт видимой строки
Given процесс `api` аварийно завершается СРАЗУ ПОСЛЕ успешного `PUT` оригинала в MinIO, но ДО открытия
транзакции БД
When воркер опрашивает очередь `queued`
Then он НЕ находит ни одной строки, ссылающейся на этот объект (строка `recognition` не существует —
транзакция не открывалась); повтор запроса с ТЕМ ЖЕ `Idempotency-Key` перезаписывает ТОТ ЖЕ
детерминированный ключ объекта и завершается штатно.

### AC-scan-pipeline-20 — отказ квоты откатывает публикацию целиком
Given квота `primary` уже исчерпана
When выполняется валидный `POST /api/v1/scans` с новым `Idempotency-Key`
Then `429` со `scope`; НИ строка `recognition`, НИ строка `photo` не сохраняются (транзакция
откачена целиком, а не переведена в `refused`); объект в бакете удалён best-effort либо остаётся
бесхозным не дольше срока политики жизненного цикла бакета.

### AC-scan-pipeline-21 — повторный захват после истечения аренды списывает вторую попытку
Given задание с `lease_fence = 1`, чья аренда истекла без завершения
When воркер B захватывает то же задание (`lease_fence` становится `2`)
Then ДО вызова модели списывается ВТОРАЯ попытка `primary` (три ключа); при остатке квоты `1` второй
захват получает `refused(scope)` БЕЗ вызова модели; конкурентный вариант — 2 захвата одного задания
подряд при пределе `1` дают ровно одно `granted` и одно `refused`.

### AC-scan-pipeline-22 — предел захватов исчерпан, задание сметено
Given задание с `lease_fence = 3`, чья аренда истекла
When ни один воркер не может его захватить (предикат `foundation` исключает `lease_fence >= 3` из
выборки)
Then `SweepStuckScans` переводит его в `failed(timeout)` в течение одного цикла опроса; условный
`UPDATE` результата от «опоздавшего» воркера (если такой всё же существует) после этого затрагивает
НОЛЬ строк и пишет `swept_as_timeout`, а не перезаписывает статус.

### AC-scan-pipeline-23 — никогда не захваченное задание сметено через 5 минут
Given строка `recognition` в статусе `queued`, `leased_until IS NULL`, `created_at` старше 5 минут
When выполняется прогон `SweepStuckScans`
Then статус становится `failed(timeout)`; повторный прогон в ту же секунду не находит эту строку
снова (условие `status = 'queued'` в `WHERE`).

### AC-scan-pipeline-24 — недекодируемый файл с валидной сигнатурой отвергается до квоты и хранения
Given HEIC-файл с корректной сигнатурой контейнера, но повреждённым/усечённым битстримом
When выполняется `POST /api/v1/scans`
Then `422 (invalid_image)` ДО загрузки объекта в бакет, ДО заявки `Idempotency-Key` и ДО обращения к
квоте; ни одна из трёх защит не тронута.

### AC-scan-pipeline-25 — EXIF-ориентация применяется до удаления метаданных; берётся первый кадр
Given фото с EXIF `Orientation = 6` (повёрнуто на 90°), И отдельно — многокадровый HEIC-контейнер
(две фикстуры, два прогона)
When `recognizer` нормализует фото
Then итоговое изображение визуально ПРАВИЛЬНО ориентировано (поворот применён до strip), метаданные
в результате отсутствуют целиком; для многокадрового входа сохранён РОВНО первый кадр, декодирование
не превышает бюджет 50 Мпикс/12 МБ.

### AC-scan-pipeline-26 — попытка после полуночи списывается в новые сутки
Given `POST /scans` принят в 23:59:30 Europe/Moscow (день D), задание захвачено воркером в 00:00:30
дня D+1 после истечения первой аренды (`lease_fence = 2`)
When воркер списывает вторую попытку `primary`
Then списание происходит по ключу дня D+1, а не дня D; счётчик дня D остаётся равным значению после
`POST`; `reset_at` любого отказа в день D+1 указывает на полночь D+1→D+2.

### AC-scan-pipeline-27 — событие попытки переживает крах процесса между вызовом и ответом
Given процесс `recognizer` аварийно завершается СРАЗУ ПОСЛЕ записи события `model_call START` и ДО
получения ответа провайдера
When читается структурированный журнал по `request_id` этой попытки
Then строка `START` присутствует (записана синхронно, не буферизована); отсутствие парной `OUTCOME`
однозначно определяется по `request_id`; квота этой попытки при этом НЕ откатывается — она была
списана ДО вызова, независимо от исхода журналирования.

### AC-scan-pipeline-28 — порт сопоставления: контрактный тест отделён от поведенческого
Given контрактный тест `MatchIngredientPort` (длина/порядок ответа, положительность `portion_g`,
сумма `parts[].share = 1`) И отдельно — поведенческий тest `NullMatchIngredientPort`
When оба выполняются
Then контрактный тест НЕ проверяет конкретное значение `food_item_id` (готов для любой реализации);
поведенческий тест `NullMatchIngredientPort` проверяет ИМЕННО `food_item_id: null` на каждом элементе
и отсутствие сетевых обращений — падение одного не окрашивает другой.

### AC-scan-pipeline-29 — эскалация вызывает именно `N4_MODEL_ESCALATION`, а не повторно `N4_MODEL_PRIMARY`
Given фейковый провайдер, возвращающий переданный `model` в своём ответе
When происходит эскалация (`confidence < 0,6`, квота разрешила)
Then второй вызов `ModelProvider.recognize` зафиксирован с `model = N4_MODEL_ESCALATION`; тест падает,
если реализация молча повторяет `N4_MODEL_PRIMARY` — фейк формы ответа один этого не доказывает без
поля `model` в ответе.

### AC-scan-pipeline-30 — удаление объекта откатанной попытки не трогает чужой скан
Given два запроса ОДНОЙ сессии с ОДИНАКОВЫМ фото, но РАЗНЫМИ `Idempotency-Key`: A публикуется успешно,
B получает отказ квоты
When транзакция B откатывается и её объект удаляется best-effort
Then фото скана A остаётся доступным (СВОЙ `object_key`, адресованный `recognition_id` B, не пересекается
с объектом A); `GET /scans/{A}` после этого по-прежнему в состоянии обработать задание.

### AC-scan-pipeline-31 — орфан-объект после краха между PUT и commit убирается по возрасту
Given объект в бакете без ЛЮБОЙ строки `photo`, ссылающейся на его `recognition_id`, старше 1 часа
When выполняется суточный прогон уборки орфанов
Then объект удаляется; объект младше 1 часа НЕ удаляется (не мешает ещё идущей транзакции).

### AC-scan-pipeline-32 — первый захват после полуночи списывает квоту нового дня
Given `POST` принят в 23:59:30 дня D; воркеры перегружены, первый захват происходит в 00:00:30 дня D+1
БЕЗ единой истёкшей аренды (`lease_fence = 1`)
When воркер обрабатывает задание
Then квота списывается ПОВТОРНО по дню D+1 (не только по D); `scan_quota_counter` дня D остаётся
равным значению после `POST`.

### AC-scan-pipeline-33 — числовые пределы нормализации — литералы, не примерные величины
Given фото 12 582 912 байт (ровно 12 МБ) на границе входного предела
When выполняется приём и нормализация
Then вход принят (`≤ 12 582 912` байт — включительно); декодирование ограничено `50 000 000`
пикселей; берётся РОВНО 1 кадр/страница; выход — JPEG качеством `85`, длинная сторона `≤ 1568` px,
размер `≤ 5 242 880` байт (5 МБ); время нормализации `≤ 3000` мс — превышение даёт `failed(normalize)`
с учтённой попыткой (координатор, DEC-A-017: расширяет `failure_reason` за пределы исходных 8
значений канона, как и `timeout` в Попытке 3 — оба требуют ратификации координатором в root-документах).

### AC-scan-pipeline-34 — агрегатор считает попытки по reason/outcome/model
Given журнал за сутки с 10 попытками `primary` (7 `ok`, 2 `failed`, 1 `timeout`) и 2 попытками
`escalation` (оба `ok`)
When выполняется `scripts/telemetry/model-calls.sh <дата>`
Then вывод несёт счётчики `primary: {ok:7, failed:2, timeout:1}`, `escalation: {ok:2}`, суммарное и
среднее `ms` по каждой группе; непарный `START` старше грейс-периода учтён как `unknown`.

### AC-scan-pipeline-35 — составное блюдо: у каждой части свой снимок базы
Given ответ порта с `parts: [{food_item_id: X, share: 0.6, source_snapshot: {...}}, {food_item_id: Y,
share: 0.4, source_snapshot: {...}}]`
When разбирается результат сопоставления
Then у КАЖДОЙ части читается СВОЙ `source_snapshot` (не общий на всё блюдо); `NullMatchIngredientPort`
никогда не возвращает `parts`.

### AC-scan-pipeline-36 — sweeper не трогает задание с живой арендой
Given задание захвачено воркером `lease_fence = 1`, `created_at` старше 30 с, но `leased_until` ЕЩЁ в
будущем (воркер продолжает вызов модели под своим `AbortController`)
When выполняется прогон `SweepStuckScans`
Then НИ ОДНА строка не изменена (правило В не совпадает — аренда не истекла); воркер сам решает судьбу
задания по своему бюджету, не sweeper.

## Наследуемые сценарии приёмки проекта

Фича продолжает то, что `foundation` закрыла частично, и закрывает СВОИ сценарии полностью либо
частично там, где полное закрытие требует `source-and-correct`.

| Сценарий проекта | Что закрывает `scan-pipeline` | Что остаётся другой фиче |
|---|---|---|
| SC-US-001-1 — первый результат без анкеты и регистрации | приём кадра, квота, нормализация, вызов модели, `202`/`GET` статуса | время ≤ 6 с измеряется на стенде (не в этой фиче); показ калорий/БЖУ — `source-and-correct` |
| SC-US-001-2 — кадр без еды | `refused(no_food_detected)`, запись дневника не создаётся | — (закрыт полностью) |
| SC-US-002-1 — виден источник числа | НЕ закрыт: числа не считаются в этой фиче | `source-and-correct` целиком |
| SC-US-002-2 — «нет в базе» без нуля | частично: `unmatched = true` на КАЖДОЙ позиции через `NullMatchIngredientPort`, но `failed` вместо `done` с частичным покрытием | `source-and-correct`: `done` с частью позиций `unmatched` |
| SC-US-009-1 — отказ по потолку с временем обнуления | `429` со `scope` и `reset_at` | экран лимита как UI — фича `pro-interest-and-limits-ui` |
