# Фича `subscription-and-commission` — алгоритмы

Порядок шагов здесь — не стиль изложения, а сама защита
(`.claude/rules/security-operation-order.md`). Перестановка любой пары, помеченной ⚠, превращает
набор верных проверок в их отсутствие.

## 1. CreateCheckout — `POST /api/v1/subscription/checkout`

```
1. Ограничение частоты (общий хук onRequest, ДО разбора тела).
2. Сессия обязана быть связана с account. Нет — 401 unauthenticated.
   ⚠ Проверка входа ДО создания намерения: намерение без владельца никому не принадлежит.
3. Если у account уже есть подписка в статусе active — 409 already_subscribed.
4. Идемпотентность: (account_id, idempotency_key) уникальны. Повтор с тем же ключом
   возвращает ТО ЖЕ намерение, а не создаёт второе.
5. Записать payment_intent(status='created', price_minor из окружения, currency='RUB').
   ⚠ Идентификатор выдаётся ДО ухода к провайдеру (long-running-job: ручка, приходящая
   вместе с результатом, умирает вместе с оборванным ответом).
6. Запросить у провайдера форму оплаты. Сетевой вызов — ВНЕ транзакции.
7. Ответ: { intent_id, redirect_url }.
```

Три состояния намерения, различимые на экране: `created` (ждём оплату), `succeeded`, `failed(причина)`.
Молчание провайдера — `created`, никогда не «наверное, оплачено».

## 2. HandlePaymentWebhook — `POST /api/v1/webhooks/payments/{provider}`

Самый опасный алгоритм фичи: здесь деньги превращаются в обязательства перед партнёром.

```
1. Прочитать СЫРЫЕ байты тела. Не разбирать.
2. ⚠ Проверить подпись по сырым байтам, сравнением постоянного времени.
   Не сошлась — 401, ничего не писать, в аудит.
3. ⚠ Проверить свежесть метки времени (ПОСЛЕ подписи: иначе время ответа
   различает «протухло» и «не сошлось").
4. Разобрать тело. Неизвестный тип события — 200 и запись в аудит (провайдер не должен
   ретраить то, что мы сознательно игнорируем), но НИЧЕГО не менять.
5. Открыть транзакцию.
6. ⚠ Заявить ключ повторности АТОМАРНО:
      INSERT INTO payment_event (provider, provider_event_id, payload_sha256)
      ON CONFLICT (provider, provider_event_id) DO NOTHING RETURNING id
   Пустой результат И ЕСТЬ «уже обработано» → COMMIT, 200, выйти.
   Не «прочитать, потом записать»: две попытки приезжают ОДНОВРЕМЕННО.
7. ⚠ Подтвердить подлинность ПЕРЕЗАПРОСОМ статуса у провайдера по provider_payment_id.
   Недоступен → BROSIT ИСКЛЮЧЕНИЕ (ProviderUnavailable). Штатный возврат здесь
   закоммитил бы занятый ключ повторности, и настоящий повтор был бы отброшен как дубль —
   ровно потерянный платёж проекта 01.
8. Сверить сумму с ценой подписки. Расходится → платёж записать, начисление НЕ делать,
   пометить needs_review. Расхождение суммы — либо смена цены, либо подделка.
9. ⚠ Проверить порядок: если occurred_at события СТАРШЕ уже применённого к этой подписке,
   применить только то, что монотонно (например факт платежа), и НЕ откатывать статус.
10. По типу события:
      payment.succeeded  → записать payment(gross, fee, net) + продлить период подписки
                           + AccrueCommission (шаг 3)
      payment.refunded   → ApplyRefund (шаг 4)
      payment.chargeback → ApplyRefund (шаг 4, kind='chargeback')
      payment.failed     → счётчик неудач продления, при третьей → expired
11. COMMIT. Платёж и начисление ложатся ОДНОЙ транзакцией: частично применённое событие
    показало бы выручку без обязательства или наоборот.
12. 200.
```

## 3. AccrueCommission — вызывается ВНУТРИ транзакции шага 2

```
1. Найти attribution аккаунта со статусом activated. Нет — выйти, комиссии не существует.
2. Если partner.account_id == плательщик → выйти (самореферал; уже отбивается при атрибуции,
   здесь ПОВТОРНО, потому что деньги делают попытку осмысленной).
3. Определить партнёра-получателя:
      если у подписки уже есть commission_partner_id — взять ЕГО (ADR-012, фиксация при первой
      оплате: иначе поздняя смена атрибуции крадёт доход у первого партнёра);
      иначе проставить commission_partner_id = partner.id ОДИН раз.
4. rate := partner.commission_rate_bp (базисные пункты, по умолчанию 5000 = 50 %).
   Ставка живёт НА ПАРТНЁРЕ, не константой: обязательство бессрочно, а менять его для новых
   партнёров право должно остаться.
5. amount_minor := net_minor * rate / 10000, округление вниз (в пользу продукта, чтобы сумма
   начислений никогда не превысила полученное).
6. net_minor <= 0 → выйти. Положительного начисления с неположительных денег не бывает.
7. INSERT commission_entry(kind='accrual', partner_id, payment_id, amount_minor = +amount,
   available_at = paid_at + окно возврата).
```

## 4. ApplyRefund

```
1. Найти payment по provider_payment_id. Нет — в аудит, выйти (возврат по неизвестному платежу
   не выдумываем).
2. Пометить payment.status = refunded | chargeback.
3. Найти начисление по этому платежу. Есть → INSERT commission_entry(kind='clawback',
   amount_minor = −(сумма начисления)).
   ⚠ Компенсирующая ЗАПИСЬ, а не UPDATE и не DELETE: леджер append-only (ADR-013),
   иначе история «было начислено и отозвано» исчезает вместе с доказательством.
4. Если баланс партнёра стал отрицательным — это законное состояние: долг гасится из будущих
   начислений. Выплата при отрицательном балансе невозможна.
5. Прекратить подписку немедленно при chargeback; при обычном возврате — по правилу провайдера.
```

## 5. RenewSubscriptions — воркер продлений

Продление — это долгая задача с внешним вызовом, значит применяется тот же каркас, что у
распознавания: аренда строки, а не очередь в памяти.

```
каждые N минут:
  1. Взять в аренду до K подписок, у которых current_period_end <= now и status in (active, past_due):
        UPDATE subscription SET leased_until = now() + interval, lease_fence = lease_fence + 1
        WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING ...
  2. ⚠ Закрыть транзакцию аренды ДО обращения к провайдеру: соединение пула не удерживается
     во время чужого ответа.
  3. Для каждой: инициировать автоплатёж с идемпотентным ключом
     (subscription_id + номер периода) — повтор воркера не создаёт второй платёж.
  4. Результат приходит ВЕБХУКОМ (шаг 2), а не ответом на этот вызов: ответ может оборваться,
     вебхук — нет.
  5. Запись результата проверяет lease_fence: устаревшая аренда обязана затронуть НОЛЬ строк.
```

## 6. Выплата — `POST /api/v1/admin/payouts`

```
1. Вызывающий обязан быть в закрытом списке владельцев В КОДЕ. Не в списке — 404 (не 403:
   403 подтвердил бы существование кабинета).
2. available := SUM(commission_entry.amount_minor) WHERE partner_id = X
                AND available_at <= now()  — начисления и обратные списания вместе.
3. Запрошенная сумма > available → 422 с названным available. Никогда не «выплатим, потом сверим».
4. INSERT commission_entry(kind='payout', amount_minor = −сумма, note = способ и дата).
   Выплата — такая же запись леджера, как начисление: баланс остаётся суммой записей.
5. Идемпотентность: (partner_id, payout_key) уникальны — двойной клик не выплачивает дважды.
```

## 7. ResolveScanLimit — связь подписки с потолком

```
limit := есть ли у account подписка со status='active' И current_period_end > now()
           ? N4_SCAN_LIMIT_PRO
           : N4_SCAN_LIMIT_USER
```

Подписка проверяется в ТОЙ ЖЕ транзакции, что и списание квоты (иначе между проверкой и
списанием подписка успевает истечь). Отсутствие любой из переменных — отказ старта, не дефолт.
