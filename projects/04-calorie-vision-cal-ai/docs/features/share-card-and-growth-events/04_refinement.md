## Testing Strategy

Слой выбирается по природе признака (`.claude/rules/testing.md`), не по удобству написания.

| Природа признака | Слой | Что именно |
|---|---|---|
| закрытые перечисления, границы длины, экранирование | unit | `sanitizeForCardText`, `buildCardPayload` (без БД, без сети) |
| согласованность транзакции создания, ответы маршрутов | integration | `POST /api/v1/share-cards`, `GET /c/{card_id}`, запись `growth_event` |
| разделяемый ресурс: уникальность и блокировка строки согласия | **конкурентный прогон** | AC-12, AC-17 — последовательный тест НЕ отличает атомарный оператор от «прочитать-потом-записать» |
| свойство исходника | страж по коду | `GuardShareCardFieldSet` (тип), деструктуризация вместо спреда (рантайм) |
| путь человека на развёрнутом стенде | E2E (после MVP) | открытие `/c/{card_id}` из чужого браузера без единой cookie |

Тесты НЕ ходят в интернет: `sharp` работает локально над буфером, MinIO — тестовый контейнер профиля
`test` (тот же, что уже использует `scan-pipeline` для фото), поставщик модели в этой фиче не
вызывается вовсе (`NFR-share-card-and-growth-events-3`).

## Обязательные конкурентные тесты — не опция

Последовательный тест на разделяемом ресурсе зеленеет и при верном, и при неверном коде
(`shared-resource-verification.md`). Здесь ДВА разделяемых ресурса, а не один:

1. **Уникальность `(recognition_id)`.** 20 одновременных `POST /api/v1/share-cards` на ОДИН
   `recognition_id` → ровно одна строка `share_card`, все 20 ответов возвращают ОДИН `card_id`, ни
   один запрос не завершается неучтённой ошибкой сервера (конфликт `ON CONFLICT DO NOTHING`
   обрабатывается кодом, не утекает клиенту как `500`). Число одновременно занятых соединений пула не
   растёт с числом ожидающих.
2. **Строка согласия владельца.** Симметричный сценарий отзыва и создания (E7/E8, AC-12) — ДВА
   прогона с управляемой задержкой на каждой стороне (искусственная пауза между `SELECT … FOR UPDATE`
   и `INSERT`/`UPDATE` через тестовый хук, а не `sleep` наугад): в обоих прогонах нет момента, когда
   `share_card.revoked_at IS NULL` ПОСЛЕ того, как отзыв уже зафиксирован — проверяется чтением
   `revoked_at` СРАЗУ после коммита обеих транзакций, синхронизированных барьером (`Promise.all` +
   ожидание обоих commit-событий), а не опросом с интервалом, который мог бы случайно не попасть в
   узкое окно гонки.

## Стражи по исходнику и их испытание

Страж, ни разу не показавший красное, стражем не является.

| Страж | Что проверяет | Внедряемый дефект | Ожидаемый красный |
|---|---|---|---|
| `GuardShareCardFieldSet` | множество полей `ShareCardRenderInput` РОВНО из восьми имён | добавить `dailyTotalKcal` в тип | тест красный: обнаружено лишнее поле |
| `GuardShareCardFieldSet` (обратное направление) | — | убрать `sourceLabel` из типа | тест красный: обнаружено недостающее поле |
| Деструктуризация в `buildCardPayload` | явные восемь имён, не `{...input}` | заменить на `{ ...input }` | `streakDays` из входа попадает в результат — тест красный |
| Единственное чтение `model_estimate_kcal` (наследуется от ADR-001, проверяется и здесь, т.к. `BuildCardPayload` — новое место чтения Snapshot) | поле не читается в `BuildCardPayload` вовсе | добавить чтение `model_estimate_kcal` для «более точного» числа на карточке | страж по исходнику (общий с `source-and-correct`) красный |
| Порядок операций «блокировка ↔ решение» | `SELECT … FOR UPDATE` — ПЕРВЫЙ оператор транзакции `CreateShareCard` | переставить `INSERT` перед `SELECT … FOR UPDATE` | конкурентный тест AC-12 краснеет: обнаруживается окно открытой карточки после отзыва |
| `no-store` на обеих ветках `/c/{card_id}` | заголовок ставится ОДНИМ местом кода для `200` и `404` | продублировать установку заголовка в двух местах и убрать из одной ветки | HTTP-тест на `404`-ветке краснеет: заголовок отсутствует |
| Экранирование SVG | `<`/`>`/`&`/`"`/`'` экранированы перед вставкой в `<text>` | убрать экранирование в `RenderCardImage` | тест с полезной нагрузкой `<image>` в названии — рендер содержит второй графический элемент, тест красный |
