# Фича `diary-and-streak` — спецификация

Проект: N4 «Тарелка». Фаза: Phase 1 PLAN, режим скорости (DEC-A-032: один раунд ревью, без второго
раунда валидации). Дата: 2026-09-13.
Источники имён и чисел: [`docs/canon.md`](../../canon.md) (заморожен 2026-09-12; сущности
`diary_entry`, `day_total` как производная, `streak`, маршруты 4 и 11, `Europe/Moscow`),
[`docs/Specification.md`](../../Specification.md) (FR-DIARY-001, FR-DIARY-002, US-005, US-006,
критерии безопасности при US-005), [`docs/Pseudocode.md`](../../Pseudocode.md)
(`CommitDiaryEntryAndDayTotals`, `ComputeSoftStreak`, API Contracts маршруты 4 и 11),
[`docs/ADR.md`](../../ADR.md) (ADR-009 — согласие до первой записи), `docs/decisions-autonomous.md`
(DEC-A-019 — согласие без исключения для анонимной сессии, DEC-A-032 — режим скорости),
`.claude/rules/{security,testing,coding-style}.md`, `docs/features/foundation/01_specification.md` и
`05_completion.md` как образец формата, `docs/features/consent-and-telegram-auth/{01,02,03}.md` (граница
`EnforceConsentBeforeDiaryWrite`, которую эта фича обязана ИМПОРТИРОВАТЬ, а не повторять). Код,
на который план опирается: `apps/api/src/**` (foundation: `bootstrap.ts`, `session/*`, `quota/*`,
`server.ts`), `packages/db/migrations/001_init.sql` (таблица `diary_entry` уже создана foundation) и
`002_failure_reason_timeout.sql`.

## Цель

Дать владельцу дневника два действия поверх уже существующего распознавания: превратить
подтверждённый скан в запись дневника и увидеть день целиком — список, четыре числа итога, разбивку
по приёмам и мягкий стрик. Фича не вызывает модель, не трогает базу продуктов и не создаёт новых
маршрутов сверх двух, уже объявленных каноном §5.

## Объём

Входит: `GET /api/v1/diary?date=` (маршрут 4) — только по `owner_key` вызывающего, без параметра
«чей дневник»; `PATCH /api/v1/diary/{entry_id}` (маршрут 11) с операциями `confirm` / `set_portion` /
`delete`; мягкое удаление с пересчётом итога дня В ТОЙ ЖЕ транзакции; мягкий стрик
(`ComputeSoftStreak`); проверка согласия ДО первой записи через границу, которую держит
`consent-and-telegram-auth` (эта фича её ИМПОРТИРУЕТ, не переопределяет).

Вне объёма: экран согласия и его текст (`consent-and-telegram-auth`); распознавание, нормализация
фото и расхождение модель/база (`scan-pipeline`, `source-and-correct`); карточка 9:16 и её данные
(`share-card-and-growth-events`); перенос анонимного дневника при входе (`consent-and-telegram-auth`,
`TelegramLogin` шаг 7) — эта фича читает `owner_key` как данность, а не переносит его.

## Осознанное разрешение унаследованной неоднозначности маршрута 11

`docs/Pseudocode.md` (API Contracts, маршрут 11) называет путь `{entry_id}` для ТРЁХ операций, но
`confirm` создаёт запись, которой до вызова не существует — а `entry_id` не может ссылаться на
несуществующую строку. План разрешает это ЯВНО, а не переносит двусмысленность в код:

| Операция | Что означает `{entry_id}` в пути | Почему |
|---|---|---|
| `confirm` | `recognition_id` (тот же `scan_id`, что и в маршрутах 1–3) | `FR-DIARY-001` и `CommitDiaryEntryAndDayTotals` (root `Pseudocode.md`) берут INPUT `recognition_id`; строки `diary_entry` до подтверждения не существует |
| `set_portion`, `delete` | `diary_entry.id`, полученный из ответа `confirm` либо из `entries[]` маршрута 4 | правка и удаление действуют на уже существующую запись |

Владение проверяется ОДИНАКОВО в обоих пространствах идентификаторов: по `owner_key`, вычисленному из
сессии вызывающего, а не по идентификатору, присланному в теле. Чужая и несуществующая запись в ОБОИХ
пространствах дают один и тот же `404` (`.claude/rules/security.md`, «Ответ на чужой ресурс»).

Отдельно зафиксировано осознанное расхождение с `consent-and-telegram-auth/03_architecture.md`
(строка 15, 41): та фича писала «вызывается ИЗ `scan-pipeline` (владелец маршрута дневника)» — на
момент её плана дневник ещё не был выделен отдельной фичей. Владелец маршрутов 4 и 11 — эта фича, и
именно она ИМПОРТИРУЕТ `EnforceConsentBeforeDiaryWrite` из `apps/api/src/consent/enforce-before-diary-write.ts`
(созданного `consent-and-telegram-auth`). Копия логики согласия здесь ЗАПРЕЩЕНА — единственность
границы проверяется `git grep`, а не декларацией (тот же принцип, каким `consent-and-telegram-auth`
проверяет саму себя).

## Функциональные требования

### FR-diary-and-streak-1 — подтверждение создаёт запись атомарно и идемпотентно
`PATCH /api/v1/diary/{recognition_id}` с `{ op: 'confirm' }` вызывает
`EnforceConsentBeforeDiaryWrite(owner_key)` ПЕРВЫМ действием (`security-operation-order`: согласие до
записи). При отказе — `403 consent_required`, строка не создаётся, съёмка и результат остаются
доступны (ADR-009). При согласии: `recognition` читается по `id` И `owner_key` вызывающего — чужая и
несуществующая запись дают `404`. `recognition.status ≠ 'done'` даёт `409` (по аналогии с маршрутом 3:
скан не в статусе, где число подтверждено). Создание — ОДИН атомарный оператор
`INSERT INTO diary_entry (…, recognition_id, …) VALUES (…) ON CONFLICT (recognition_id) DO NOTHING
RETURNING *`; пустой результат означает, что строка уже создана РАНЕЕ (двойной тап, повтор сети) —
тогда читается существующая строка по `recognition_id` и возвращается тот же `entry_id`, а НЕ ошибка
и НЕ вторая строка. «Прочитать, потом вставить» здесь запрещён по той же причине, что и в
`CheckAndConsumeQuota` (`shared-resource-verification`): обе реализации проходят последовательный
тест.

### FR-diary-and-streak-2 — числа копируются из снимка, не из живой базы
Состав, четыре числа и `source_snapshot` копируются из `recognition` в момент подтверждения
(`.claude/rules/coding-style.md`: число из **снимка**, а не из живой строки `food_item`). Запись
дневника после этого не читает `food_item` НИКОГДА, включая пересчёт итога дня: переимпорт базы не
имеет права задним числом изменить уже показанное число. `eaten_on` — календарная дата по
`Europe/Moscow`, а не момент времени; `meal_slot` определяется по времени суток и правится ОДНИМ
тапом (это не отдельная операция маршрута 11 — правка слота внутри `confirm` не входит в объём этой
фичи и остаётся текстовым замечанием на будущее, поскольку канон не резервирует под неё операцию).

### FR-diary-and-streak-3 — правка порции пересчитывает четыре числа за один вызов
`PATCH /api/v1/diary/{entry_id}` с `{ op: 'set_portion', index, mass_g }` находит запись по `id` И
`owner_key`; чужая и несуществующая запись дают `404`. Порция вне 5–2000 г, дробное, отрицательное
значение, строка вместо числа и `null` дают `422 portion_out_of_range` с СОХРАНЕНИЕМ прежней порции —
ввод не принят, а не принят частично (FR-CORRECT-001 применён к уже сохранённой записи). Индекс вне
списка позиций `items` даёт `422`, а не запись мимо массива. Успешная правка пересчитывает
`kcal_total`, `protein_total`, `fat_total`, `carb_total` по той же формуле `(масса_г/100)×значение_на_100г`
из ХРАНИМОГО `source_snapshot` и отвечает не позже 100 мс (p95) — тот же порог, что и у экрана
результата (SC-US-003-1), потому что операция та же по природе: локальный пересчёт без вызова модели.

### FR-diary-and-streak-4 — удаление и пересчёт итога дня в одной транзакции
`PATCH /api/v1/diary/{entry_id}` с `{ op: 'delete' }` — мягкое удаление: условный
`UPDATE diary_entry SET deleted_at = now() WHERE id = :id AND owner_key = :owner_key AND deleted_at
IS NULL RETURNING id`. Ноль затронутых строк означает ОДИН из двух случаев: строка чужая или не
существует (`404`), либо строка УЖЕ удалена (`409`) — различаются повторным чтением по `id` БЕЗ
условия владения (существует ли строка вообще под любым владельцем — не раскрывая чужому вызывающему
её содержимое, только факт «была»). Итог дня пересчитывается В ТОЙ ЖЕ транзакции, что и удаление:
удалённая запись обязана исчезнуть из итога одновременно с исчезновением из списка (root
`Pseudocode.md` шаг 8; `.claude/rules/deployment-seams.md` — стык, а не отдельная гарантия). Ответ
несёт пересчитанные итоги, не позже 100 мс (p95).

### FR-diary-and-streak-5 — чтение дня только по своему `owner_key`
`GET /api/v1/diary?date=YYYY-MM-DD` возвращает `{ entries[], totals, by_meal, streak }` ТОЛЬКО по
`owner_key` вызывающего; параметра «чей дневник» в маршруте нет вовсе — то, чего нельзя попросить,
нельзя и получить (US-005, критерий безопасности). Неразбираемая, будущая за пределом текущих суток
и диапазонная дата дают `422`; подстановка «сегодня» вместо непонятной даты ЗАПРЕЩЕНА
(`.claude/rules/fail-closed-defaults.md`: пустое не значит «любое»). Мягко удалённая запись не
возвращается НИКОГДА — ни в `entries[]`, ни в `totals`, ни по прямому `entry_id` в других операциях
этого маршрута.

### FR-diary-and-streak-6 — итог дня и разбивка по приёмам
`totals` — сумма ПЕРСИСТИРОВАННЫХ `kcal_total`/`protein_total`/`fat_total`/`carb_total` всех
неудалённых записей даты; `by_meal` группирует те же записи по `meal_slot` (четыре значения канона).
Итог НИКОГДА не пересчитывается из `food_item`: агрегирование читает только колонки `diary_entry`
(страж по исходнику, `04_refinement.md`).

### FR-diary-and-streak-7 — мягкий стрик
`ComputeSoftStreak(owner_key, сегодня по Europe/Moscow)`: собрать множество дат с ≥1 неудалённой
записью за последние 60 суток; идти назад от сегодня; один пропущенный день НЕ обнуляет счёт и
помечается «заморожен»; два пропущенных подряд обнуляют счёт до 1 при следующей записи (root
`Pseudocode.md`, `ComputeSoftStreak`). Формулировка на экране — нейтральная: без обратного отсчёта и
без предупреждения о потере (FR-DIARY-002). Стрик возвращается ВМЕСТЕ с `GET /diary`, отдельного
маршрута для него канон не резервирует.

## Нефункциональные требования

### NFR-diary-and-streak-1 — локальный пересчёт быстрее вызова модели
`set_portion` и `delete` отвечают не позже 100 мс (p95) без нового вызова модели и без списания
квоты — они читают и пишут только `diary_entry`, никогда `recognition` или адаптер поставщика.

## Критерии приёмки

### AC-diary-and-streak-1 — подтверждение при данном согласии создаёт запись
Given `recognition.status = 'done'`, согласие дано, запись дневника для этого `recognition_id` ещё
не существует
When `PATCH /api/v1/diary/{recognition_id} { op: 'confirm' }`
Then `201`/`200` (единый конверт `{ data: { entry, totals } }`), в `diary_entry` ровно одна новая
строка с `recognition_id`, равным входному, `eaten_on` по `Europe/Moscow`, числа равны снимку
`recognition`.

### AC-diary-and-streak-2 — подтверждение без согласия отказывает и не создаёт строку
Given `EnforceConsentBeforeDiaryWrite` возвращает отказ (аккаунт без `consent_at` ЛИБО анонимная
`device_session` без согласия — исключения нет, DEC-A-019)
When выполняется `confirm`
Then `403 consent_required`, в `diary_entry` НОЛЬ новых строк, повторный вызов после выдачи согласия
успешен.

### AC-diary-and-streak-3 — подтверждение скана не в статусе done отказывает
Given `recognition.status ∈ {queued, failed, refused}`
When выполняется `confirm`
Then `409`, строка не создаётся; для `refused` тело называет причину, отличную от «согласие».

### AC-diary-and-streak-4 — чужой и несуществующий recognition_id при confirm неразличимы
Given `recognition_id` принадлежит другой сессии, и второй `recognition_id`, которого нет в базе
When выполняется `confirm` для каждого
Then ОБА ответа `404` с одинаковой формой тела; ни один не создаёт строку `diary_entry`.

### AC-diary-and-streak-5 — двойной параллельный confirm не создаёт вторую запись
Given один `recognition_id` в статусе `done`, согласие дано
When 20 параллельных `confirm` для ОДНОГО `recognition_id` стартуют одновременно
Then в `diary_entry` РОВНО одна строка с этим `recognition_id`; каждый из 20 ответов несёт ОДИН и тот
же `entry_id`; ни один ответ не является ошибкой уникальности, поднятой наверх.

### AC-diary-and-streak-6 — правка порции пересчитывает четыре числа
Given подтверждённая запись с порцией 250 г
When `set_portion` меняет порцию на 180 г
Then ответ приходит не позже 100 мс (p95), все четыре числа пересчитаны по хранимому
`source_snapshot`, новый вызов модели не выполнен, `user_corrected = true`.

### AC-diary-and-streak-7 — граница порции отклоняет ввод целиком
Given подтверждённая запись с порцией 180 г
When `set_portion` вызывается с `mass_g` равным `5000`, `0`, `-10`, `"abc"`, `null` (пять прогонов)
Then каждый прогон отвечает `422 portion_out_of_range`, а порция записи остаётся `180` во всех пяти
случаях — ввод не принят частично.

### AC-diary-and-streak-8 — индекс позиции вне списка отклоняется
Given запись с двумя позициями (`index` 0 и 1)
When `set_portion` вызывается с `index = 2`
Then `422`, ни одна позиция не изменена.

### AC-diary-and-streak-9 — удаление и пересчёт итога в одной транзакции
Given день с тремя записями и известным итогом
When одна запись удаляется через `delete`
Then ответ (не позже 100 мс p95) несёт итог БЕЗ удалённой записи; последующий `GET /diary?date=` в
ТОМ ЖЕ прогоне показывает ровно две записи и тот же пересчитанный итог — расхождения между ответом
`delete` и последующим `GET` нет.

### AC-diary-and-streak-10 — повторное удаление уже удалённой записи
Given запись, удалённая шагом AC-diary-and-streak-9
When `delete` вызывается для того же `entry_id` второй раз
Then `409`, итог дня не изменяется повторно (не «минус ещё раз»).

### AC-diary-and-streak-11 — чужая и несуществующая запись для set_portion/delete неразличимы, 403 невозможен
Given `entry_id` другого владельца и второй `entry_id`, которого нет в базе
When `set_portion` и `delete` вызываются для каждого (четыре прогона)
Then все четыре ответа `404` одинаковой формы; НИ ОДИН ответ этого маршрута не равен `403` ни при
каком из четырёх входов.

### AC-diary-and-streak-12 — чтение дня не принимает «чей дневник»
Given два владельца с записями за одну дату
When владелец A выполняет `GET /api/v1/diary?date=` со своей сессией
Then `entries[]` содержит ТОЛЬКО записи владельца A; передача идентификатора другого владельца ЛЮБЫМ
способом, для которого в маршруте нет параметра (query, заголовок), не меняет результат.

### AC-diary-and-streak-13 — непригодная дата отклоняется без подстановки
Given значения `date` равные `2026-13-40`, пустой строке, дате на 400 дней вперёд (три прогона)
When выполняется `GET /diary`
Then каждый прогон отвечает `422`; ни один не возвращает данные за «сегодня» по умолчанию.

### AC-diary-and-streak-14 — граница суток по Europe/Moscow
Given сервер работает в UTC, и подтверждение происходит в 23:50 по `Europe/Moscow`, что соответствует
следующему календарному дню в UTC
When запись создаётся и затем запрашивается `GET /diary?date=` за московскую дату подтверждения
Then запись присутствует в ЭТОЙ дате, а не в дате, вычисленной по UTC.

### AC-diary-and-streak-15 — мягкий стрик переживает один пропуск
Given записи есть за дни `T-6…T-2` (стрик 5) и НЕТ записи за `T-1`
When владелец делает запись сегодня (`T`)
Then `streak.days = 6`, `streak.frozen_days` содержит `T-1`.

### AC-diary-and-streak-16 — два пропуска подряд обнуляют стрик без предупреждения
Given записей нет за `T-2` и `T-1`
When владелец делает запись сегодня (`T`)
Then `streak.days = 1`; ответ не содержит ни обратного отсчёта, ни текста о потере.

### AC-diary-and-streak-17 — конкурентные set_portion и delete на одной записи не теряют и не воскрешают данные
Given одна подтверждённая запись
When `set_portion` и `delete` для ОДНОГО `entry_id` выполняются одновременно (порядок фиксации в базе
не задан заранее)
Then РОВНО ОДИН из двух исходов воспроизводим и проверяем: (а) `delete` зафиксировался первым —
`set_portion` получает `404` или `409` (запись уже удалена) и НЕ изменяет удалённую строку; (б)
`set_portion` зафиксировался первым — запись обновлена, а последующий `delete` удаляет ОБНОВЛЁННУЮ
запись и пересчитывает итог по НОВОЙ порции. Ни при каком порядке фиксации удалённая запись не
получает `deleted_at = NULL` обратно, и ни один из двух вызовов не завершается `500`.

### AC-diary-and-streak-18 — страж: итог дня не читает живую базу продуктов
Given исходник модуля пересчёта итога дня
When выполняется страж по исходнику
Then он подтверждает отсутствие обращений к таблице `food_item` в пути агрегирования итога;
внедрённый дефект (замена суммы персистированных колонок на пересчёт через `JOIN food_item` по
`items->>'food_item_id'`) даёт КРАСНЫЙ результат стража, восстановление — зелёный
(`guard-must-be-able-to-fail`).
