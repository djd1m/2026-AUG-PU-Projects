# Фича `diary-and-streak` — уточнение: краевые случаи, проверки, страж

Слой каждой проверки — по природе признака, а не по удобству
([`cost-of-detection-ladder`](../../../../.claude/rules/cost-of-detection-ladder.md)). Оба
конкурентных сценария (подтверждение и гонка правка/удаление) закрываются ТОЛЬКО параллельным
прогоном — последовательный тест зеленеет при обеих реализациях
(`shared-resource-verification`).

## Edge Cases Matrix

| Случай | Вход | Ожидаемое | Как обеспечивается |
|---|---|---|---|
| согласие не дано, аккаунт | `account.consent_at IS NULL` | `403 consent_required`, строка не создана | `EnforceConsentBeforeDiaryWrite`, импорт |
| согласие не дано, анонимная сессия | `device_session` без согласия | `403` ТАК ЖЕ, исключения нет | DEC-A-019: та же граница, без различия по типу владельца |
| согласие отозвано | `withdraw_consent` обнулил `consent_at` | `403` на НОВУЮ запись; существующие не тронуты | `consent-and-telegram-auth` FR-8: `consent_at IS NULL` не различает «никогда» и «отозвано» |
| скан не готов | `recognition.status` ∈ {queued, failed, refused} | `409`, не создаётся строка | `confirm` требует `status = 'done'` |
| двойной тап confirm | 2+ параллельных `confirm` одного `recognition_id` | РОВНО одна строка, оба ответа с одним `entry_id` | `UNIQUE (recognition_id)` + `ON CONFLICT DO NOTHING` + чтение при конфликте |
| порция вне диапазона | `5000`, `0`, `-10`, `"abc"`, `null` | `422`, прежняя порция сохранена | валидация ДО пересчёта; частичное принятие запрещено |
| индекс вне списка | `index = 2` при двух позициях | `422`, ничего не изменено | проверка длины `items` до записи |
| правка удалённой записи | `set_portion` после конкурентного `delete` | `404` (если удаление увидено на первом чтении) либо `409` (если гонка на самой записи) | условный `UPDATE … WHERE deleted_at IS NULL`; повторное чтение при нуле строк |
| повторное удаление | второй `delete` того же `entry_id` | `409` | условный `UPDATE`, ноль строк, `deleted_at` уже установлен |
| чужая запись любой операции | `owner_key` не совпадает | `404`, НИКОГДА `403` | владение проверяется в `WHERE`, не постфактум |
| дата не разбирается | `2026-13-40`, пустая строка | `422`, без подстановки «сегодня» | `fail-closed-defaults`: пустое не значит «любое» |
| дата в будущем | дата больше сегодняшней по Europe/Moscow | `422` | тот же валидатор |
| граница суток | подтверждение в 23:50 Europe/Moscow = следующий день в UTC | запись попадает в МОСКОВСКУЮ дату | `eaten_on` вычисляется явно по таймзоне, не берётся из `now()` сервера в UTC |
| один пропуск в стрике | нет записи за `T-1`, есть за `T-2` и раньше | стрик продолжается, `T-1` = «заморожен» | `ComputeSoftStreak` шаг 3: один пропуск не обнуляет |
| два пропуска подряд | нет записей за `T-1` и `T-2` | стрик = 1 при записи сегодня, без предупреждения | шаг 3–4: два пропуска обрывают счёт |
| день без единой записи | `GET /diary?date=` на пустой день | `entries: []`, `totals` = нули | ноль записей — это ЧЕСТНЫЙ ноль, не «не измерено» (в отличие от `discrepancy_ratio` при делении на ноль) |
| итог дня после переимпорта базы | `food_item` изменена после подтверждения записи | итог НЕ меняется | `RecomputeDayTotals` читает только `diary_entry`, никогда `food_item` |

## Конкурентные сценарии — обязательны, не опция

1. **Confirm × confirm.** 20 параллельных `PATCH …/confirm` для ОДНОГО `recognition_id`: ровно одна
   строка `diary_entry`, все 20 ответов несут один и тот же `entry_id`, ни один не завершается
   ошибкой уникальности, поднятой наверх приложением (`ON CONFLICT` гасит её на уровне БД).
2. **Set_portion × delete.** Один `entry_id`, одновременно `set_portion` и `delete`: детерминированный
   результат по порядку фиксации в БД, без потери и без воскрешения (AC-diary-and-streak-17). Тест
   запускает оба вызова с общим барьером старта и проверяет ОБА возможных порядка отдельными
   прогонами (принудительная задержка одной из веток), а не полагается на случайное планирование.

## Страж по исходнику: итог дня не читает живую базу продуктов

`day-totals.ts` — единственный файл, агрегирующий калории и БЖУ дня. Страж читает исходник модуля и
подтверждает:
- нет импорта и нет обращения к таблице `food_item` (ни прямого SQL, ни через ORM-подобный вызов);
- источник суммы — ТОЛЬКО колонки `kcal_total`, `protein_total`, `fat_total`, `carb_total` таблицы
  `diary_entry`.

**Испытание стража (`guard-must-be-able-to-fail`):** внедрённый дефект — замена суммы
персистированных колонок на пересчёт по актуальным значениям `food_item` через
`items->>'food_item_id'` (то есть переимпорт базы задним числом менял бы уже показанный итог). Страж
обязан дать КРАСНЫЙ результат на этом дефекте и ЗЕЛЁНЫЙ — после восстановления. Обе строки
(«дефект возвращён → красный», «код восстановлен → зелёный») входят в квитанцию Phase 3, без этого
страж не засчитывается (`guard-must-be-able-to-fail`: проверка, ни разу не показавшая красное, не
является проверкой).

## Testing Strategy

Раннер — `vitest` 3, интеграционные и конкурентные прогоны — на настоящем PostgreSQL профиля `test`
(мок не воспроизводит `UNIQUE (recognition_id)` и блокировки, ради которых тест написан).

| Слой | Что проверяет | Почему этот слой |
|---|---|---|
| unit | границы порции и индекса, арифметика пересчёта, окно стрика и правило заморозки, вычисление календарной даты по таймзоне | арифметика и закрытые перечисления наблюдаются без базы |
| integration | подтверждение (согласие/статус/владение), правка, удаление с пересчётом в транзакции, чтение дня по датам | согласованность операции и ответа маршрута |
| конкурентный | двойной `confirm`, гонка `set_portion`×`delete` | разделяемый ресурс (строка `diary_entry`, уникальность `recognition_id`) |
| страж по исходнику | `day-totals.ts` не читает `food_item` | свойство исходника, а не одного прогона |

## Тесты, которые Phase 3 обязан создать

`tests/unit/day-totals.test.ts`
- `сумма по дню считается только из персистированных колонок diary_entry`
- `день без записей даёт нулевой итог, а не ошибку`

`tests/unit/compute-soft-streak.test.ts`
- `один пропущенный день не обнуляет стрик и помечается замороженным`
- `два пропущенных дня подряд обнуляют стрик до единицы`
- `стрик не заходит дальше окна в 60 суток`

`tests/unit/portion-bounds.test.ts`
- `порция вне диапазона 5-2000 отклоняется с сохранением прежнего значения`
- `индекс позиции вне списка отклоняется без изменения записи`

`tests/integration/confirm-diary-entry.test.ts`
- `подтверждение без согласия отклоняется 403 и не создаёт запись`
- `подтверждение скана не в статусе done отклоняется 409`
- `подтверждение чужого и несуществующего recognition_id дают одинаковый 404`
- `подтверждение при данном согласии создаёт запись из снимка распознавания`

`tests/integration/set-diary-entry-portion.test.ts`
- `правка порции пересчитывает четыре числа и не вызывает модель`
- `правка чужой и несуществующей записи дают одинаковый 404, не 403`

`tests/integration/delete-diary-entry.test.ts`
- `удаление и пересчёт итога дня видны атомарно в одной транзакции`
- `повторное удаление уже удалённой записи отвечает 409`

`tests/integration/get-diary-day.test.ts`
- `чтение дня возвращает только записи вызывающего владельца`
- `непригодная дата отклоняется без подстановки сегодняшнего дня`
- `запись в 23:50 по Europe/Moscow попадает в московскую календарную дату`

`tests/concurrency/confirm-diary-entry-parallel.test.ts`
- `двадцать параллельных подтверждений одного recognition_id создают ровно одну запись`

`tests/concurrency/portion-vs-delete-race.test.ts`
- `конкурентные правка и удаление одной записи не теряют и не воскрешают данные при любом порядке фиксации`

`tests/integration/day-totals-guard.test.ts`
- `страж отклоняет пересчёт итога через живую таблицу food_item`
