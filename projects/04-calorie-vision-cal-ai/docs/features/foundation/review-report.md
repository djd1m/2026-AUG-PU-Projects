## Findings

### RV-foundation-01 — medium — `apps/recognizer/src/worker.ts:97`

Ветка таймаута получает результат `recordResult`, пишет `model_call_deadline_exceeded` и немедленно возвращается. Обработка `stale_lease` и `swept` ниже выполняется только при успешном ответе адаптера.

Воспроизведено без БД, с подставленным ответом исполнителя SQL: условная запись затрагивает ноль строк, перечитанная строка терминальная с прежним fence. Журнал содержит только:
`{"event":"model_call_deadline_exceeded","write":"swept",…}`.

Данные не воскресают, но обязательное событие `swept_as_timeout` отсутствует; аналогично теряется `stale_lease_result` при перезахвате. Поле `write` не заменяет контракт имени события.

Исправление: вынести обработку исхода записи в общий путь для успеха и таймаута. Добавить два сценария с отказом адаптера после уборки и после перезахвата. Этот локальный прогон доказывает дефект ветвления, не конкурентность PostgreSQL.

### RV-foundation-02 — medium — `tests/unit/config.test.ts:159`

FR-foundation-2 прямо требует отдельно проверять отсутствие **и пустую строку** каждой из четырёх переменных S3 у обоих сервисов. Для recognizer цикл проверяет только удаление переменной. Четырёх утверждений с `''` нет.

Зелёные 30 unit-тестов не подтверждают заявленную полноту. Дефект обработки пустого значения, специфичный для recognizer, останется незамеченным.

Исправление: для каждой S3-переменной добавить вызов с `[name]: ''` и проверку названного отказа; сохранить отдельные проверки отсутствия.

### RV-foundation-03 — medium — `docs/features/foundation/validation-report.md:4`

Отчёт READY привязан к `sha256:02cfa7f6…7e3670`, тогда как фактическая спецификация имеет `sha256:431b004e…0e5059`. Это другая редакция требований.

Расхождение содержательное: текущая спецификация требует обе проверки S3 у обоих сервисов, а обязательный случай отсутствует. Следовательно, READY нельзя переносить на текущую спецификацию автоматически.

Исправление: переоценить изменённые требования и покрытие, исправить найденный пробел, затем обновить хеш и вывод валидации. Простая замена контрольной суммы недостаточна.

## Что проверено без замечаний

- Квота реализована условным UPSERT; все три или четыре ключа находятся в одной транзакции, отказ вызывает полный rollback.
- Конкурентные тесты действительно запускают операции параллельно. Последовательные циклы истечения аренды используются для другого свойства — предела повторных захватов.
- Аренда содержит `photo_id IS NOT NULL`, проверку срока и предел fence; транзакция освобождает соединение до адаптера.
- В bootstrap обоих сервисов конфигурация проверяется до создания пула; API открывает сокет после проверки.
- Текущий обработчик ошибок не журналирует query или сегменты пути; неизвестному маршруту соответствует постоянная метка `unmatched`.
- Страж ADR-001 существует и прошёл unit-прогон; историческое испытание с добавлением `calories` описано в completion. Полный расчёт из food_item ещё вне объёма фичи.
- В compose у db/storage нет публикации портов; api/web доступны через proxy. Среди проверенных отслеживаемых файлов `.env` и файлов ключей не обнаружено.
- Фейк не содержит сетевого клиента. Живой адаптер явно не реализован, платных вызовов в проверенной реализации нет.
- Связка «квота до платного вызова», доступ к чужому ресурсу и согласие перед записью дневника относятся к последующим фичам; foundation их выполнение не доказывает.
