# Фича `partner-codes-and-cabinet` — уточнение

## Edge cases

| Случай | Обработка |
|---|---|
| Код с пробелами по краям (`" liza10 "`) | нормализуется до `LIZA10` (FR-1, шаг 1) |
| Код с дефисом/юникодом (`LIZA-10`, `ЛИЗА10`) | не проходит `[A-Z0-9]{4,12}` → `invalid` |
| Код длиной ровно 4 и ровно 12 символов | оба ВАЛИДНЫ (граница включительно, как в `CHECK` схемы) |
| Код длиной 3 или 13 символов | `invalid` (граница исключительно) |
| Повторная отправка ТОГО ЖЕ явного кода поверх уже `explicit` | `conflict`, не отдельная ветка — шаг 11 `ApplyPartnerCode` не различает «тот же» и «другой» код при `explicit`+любой |
| `device_session.account_id` есть, но НЕ равен владельцу кода | не самореферал, проверки anti-fraud и three-outcome идут как обычно |
| Анонимная сессия (`account_id = NULL`) применяет свой же будущий код | самореферал невозможен по построению — `NULL` не равен никакому `account_id`; проверяется заново в `ActivateAttributionOnRecognition`, когда аккаунт появится (AC-14) |
| Два РАЗНЫХ кода одного партнёра (если у партнёра их несколько — канон не запрещает) применяются с одного IP | anti-fraud считается ПО КОДУ (`partner_code_id`), не по партнёру — раздельные окна, раздельные пороги |
| `partner_code.partner_id` ссылается на `partner` с `status ≠ active` (партнёр деактивирован, но код не блокирован) | вне охвата этой фичи: `partner.status` не читается ни одним алгоритмом ЗДЕСЬ — деактивация партнёра как отдельный сценарий не входит в неделю (не в FR-PARTNER-*) |
| Окно `week`/`all` пересекает смену тарифного/учётного дня | окно кабинета — скользящее по `created_at`, НЕ привязано к календарным суткам Europe/Moscow (в отличие от квоты); полночь не создаёт разрыва |
| `ActivateAttributionOnRecognition` вызывается для сессии без `pending`-атрибуции (обычный пользователь без кода) | `no_attribution`, no-op — самый частый случай, не ошибка |
| Гонка `ApplyPartnerCode` (сессия X, шаг 8) и `ActivateAttributionOnRecognition` (та же сессия X) одновременно | оба берут sessionLock ИЛИ `FOR UPDATE` на ту же строку через ОДИН ключ (`device_session_id`); кто первый — тот и выполняется, второй ждёт снятия лока и видит уже актуальное состояние строки |
| `AntiFraudOnCode` считает по `ip_prefix`, а не по полному адресу | два устройства за одним NAT/офисным IP делят один счётчик — это ИЗВЕСТНОЕ и принятое ограничение порога (пороги «пересчитываются после первой недели трафика», FR-PARTNER-003) |

## Стратегия тестирования (слой по природе признака)

| Природа признака | Слой | Тесты фичи |
|---|---|---|
| нормализация, форма кода, границы 4/12 | unit | `NormalizeAndFindCode` |
| три исхода по `source`, self-referral, code_blocked-гейт | integration (настоящий PostgreSQL) | `ApplyPartnerCode` последовательно |
| anti-fraud порог 50/10 минут, счёт по `code_applied` | integration | `AntiFraudOnCode` последовательно (49→allow, 51→block) |
| **разделяемый ресурс: attribution одной сессии** | **конкурентный** | AC-6 — два кода одновременно |
| **разделяемый ресурс: anti-fraud счётчик одного кода** | **конкурентный** | AC-9(б) — 20 одновременных при близком к порогу состоянии |
| активация, идемпотентность, пере-оценка на момент распознавания | integration | AC-12/13/14 |
| кабинет: агрегация, окна, `403`, честные нули, `n<30` | integration | AC-15/16/18/19 |
| свойство исходника: разблокировка только вручную | страж по исходнику + внедрённый дефект | AC-11 |
| свойство исходника: код кабинета только с сервера | страж по исходнику + внедрённый дефект | AC-17 |

Тесты фичи НЕ ходят в сеть и не вызывают модель — фича вообще не касается `recognizer`.
Мок вместо PostgreSQL не годится ни для одного из двух конкурентных тестов
(`shared-resource-verification.md`): advisory-локи — поведение СЕРВЕРА PostgreSQL, а не библиотеки.

## Испытание стражей (обязательно, `guard-must-be-able-to-fail.md`)

| Страж | Внедряемый дефект | Ожидаемое красное |
|---|---|---|
| AC-11, разблокировка только вручную | добавить фоновую задачу `UPDATE partner_code SET status='active' WHERE blocked_at < now() - interval '1 hour'` | страж находит путь, меняющий `blocked → active` вне `ManualUnblockPartnerCode`, и падает, называя файл |
| AC-17, код кабинета с сервера | заменить `partner.id` вызывающего на `request.query.code ?? partner.id` в `dashboard-query.ts` | страж находит чтение кода из тела/query в обработчике маршрута 9 и падает |
| AC-10, окно не пересчитывается на заблокированном коде | переставить шаг 4 (`AntiFraudOnCode`) впереди шага 2 (blocked-проверка) в `apply-partner-code.ts` | конкурентный/последовательный тест AC-10 краснеет: счётчик обращений к `AntiFraudOnCode` для уже заблокированного кода перестаёт быть нулевым |

Каждый страж принимается ТОЛЬКО с обеими строками квитанции — дефект внесён → красный, дефект снят
→ зелёный — в `05_completion.md` при реализации.

## Порядок операций (проверяется тестом на перестановку, `security-operation-order.md`)

| Пара | Обязательный порядок | Что ломает обратный |
|---|---|---|
| codeLock ↔ чтение `partner_code.status` | лок ДО чтения | чтение до лока делает лок бутафорией: код мог заблокироваться между чтением и захватом |
| `blocked`-проверка ↔ `AntiFraudOnCode` | `blocked` ДО anti-fraud | без этого порядка окно пересчитывается на уже заблокированном коде (AC-10) — счётчик растёт бессмысленно, а порог превращается в шум |
| codeLock ↔ sessionLock | codeLock ВСЕГДА первым | обратный порядок в любом из двух алгоритмов создаёт возможность deadlock между `ApplyPartnerCode` и `ActivateAttributionOnRecognition` |
| три проверки (blocked/self-referral/anti-fraud) ↔ запись `attribution` | все три ДО записи | отклонённый код успел бы заменить действующую атрибуцию (буквально ADR-008 и корневой Pseudocode, шаг 4) |
| `growth_event(code_applied)` ↔ исход `applied` | событие ПОСЛЕ решения, той же транзакцией | запись события для `conflict`/`invalid`/`rejected` завела бы второй источник истины о том, что значит «применение» |
