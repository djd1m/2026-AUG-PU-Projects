## Findings

**RV-pro-interest-and-limits-ui-01 — medium — `apps/api/src/routes/interest.ts:65`; `apps/api/src/interest/record-pro-interest.ts:88`**

День блокировки и проверки вычисляется часами приложения **до получения соединения**, а `created_at` вставки получает независимый `DEFAULT now()` из PostgreSQL (`packages/db/migrations/001_init.sql:253`).

Статический сценарий: два запроса вычислили вчерашний день перед московской полуночью, дождались соединений уже после неё. Первый проверяет вчера, вставляет строку с сегодняшним `created_at`. Второй после освобождения той же блокировки снова проверяет вчера, не видит первую строку и тоже вставляет сегодняшнюю. Блокировка сериализует операции, но не исправляет неверный день поиска. Расхождение часов приложения и БД даёт тот же эффект.

Исправить: получать единый момент времени внутри транзакции и использовать его для дня блокировки, проверки и `created_at`. Добавить проверку перехода полуночи с задержкой получения соединения. На PostgreSQL этот сценарий в настоящем ревью не воспроизводился.

**RV-pro-interest-and-limits-ui-02 — medium — `packages/shared/src/domain/classify-contact.ts:22`; `tests/unit/classify-contact.test.ts:40`**

FR-6 разрешает числовой Telegram ID как положительное целое. Реализация вводит незаявленный минимум пять цифр: `"1"` и `"1234"` возвращают `unrecognized`. Это воспроизведено прямым запуском функции. Тест специально закрепляет это расхождение.

Псевдокод также содержит более узкий шаблон, но он не отменяет функциональное требование спецификации. Исправить классификатор и тест коротких положительных ID либо явно согласовать изменение FR-6; не выдавать совпадение реализации с псевдокодом за соответствие спецификации.

**RV-pro-interest-and-limits-ui-03 — medium — `tests/concurrency/interest-cadence.test.ts:40`; `tests/integration/interest.test.ts:77`**

Приёмочные сценарии проверены не полностью. Конкурентность настоящая — обещания создаются до `Promise.all`, — однако маршрут, определение владельца и HTTP-статусы обходятся прямым вызовом функции. Для AC-5 отсутствует полная таблица запросов к API, включая числовой контакт и отклонение произвольного текста без записи.

Испытание стража cadence предъявлено как историческое утверждение: `docs/telemetry/p-replicator/20260913T070000Z-pro-interest-B-pr01/receipts/impl-pro.md:50` ссылается на комментарий теста и несохранённую редакцию. Проверяемой привязки красного прогона к конкретной мутации в рассмотренных материалах нет.

Исправить: добавить десять параллельных `app.inject` с проверкой одного `201`, девяти бизнесовых `429` и одной строки; добавить HTTP-таблицу AC-5. Приложить воспроизводимое доказательство «мутация → красный; восстановление → зелёный».

**RV-pro-interest-and-limits-ui-04 — low — `docs/features/pro-interest-and-limits-ui/05_completion.md:53`**

`Criterion coverage` осталась плановой: все десять путей указывают на `apps/*/tests`, тогда как фактические тесты находятся в корневом `tests/`. Заголовки не обновлены до фактических. Запрошенный `validation-report.md` отсутствует.

Исправить таблицу по существующим файлам и дословным заголовкам, разделить выполненные и непроверенные сценарии. Отсутствие validation-отчёта объяснить явной ссылкой на принятое решение о пропуске стадии; не создавать задним числом фиктивный результат проверки.

## Что проверено без замечаний

- Ограничитель частоты зарегистрирован на `onRequest` до разбора тела. В новом обработчике `source` и контакт проверяются до транзакционной записи.
- Владелец определяется сервером по cookie и связи с аккаунтом; `owner_key` из тела не принимается. SQL параметризован.
- При согласованном дне advisory-lock охватывает проверку и вставку; повтор откатывает транзакцию. Атрибуция `rejected` исключается, отсутствие записывается как `NULL`.
- В просмотренном контуре сканирования квота списывается атомарным SQL до вызова модели; эскалация имеет отдельную проверку. Фича этот код не меняет.
- Стражи ADR-001 читают исходники. Проверки производственной схемы и условия `done` включают мутации в памяти и прошли в `npm test`.
- Тесты отсутствующих потолков конфигурации прошли. Унаследованные конкурентные тесты квоты и захвата аренды используют `Promise.all`; ожидаемые пределы заданы тестовыми литералами.
- Чужой скан возвращает `404` по проверенному коду. Фича не добавляет записей дневника; существующие проверки согласия прошли, но сквозной порядок записи на БД здесь не подтверждался.
- В изменённом коде секретов не обнаружено; `.env` не отслеживается Git. Это проверка текущего дерева и дифа, не аудит всей истории.
- В прочитанном `docker-compose.yml` у PostgreSQL и MinIO нет публикации портов; опубликован только loopback-порт прокси. Живые bindings Docker не проверялись.
- Выполненные тесты используют локальные данные и фейки; обращений к внешней модели не потребовалось.
- Сквозное подключение отказа сканирования к `LimitScreen` заранее исключено из доказательств фичи; успешный рендер компонента не объявляется E2E.
