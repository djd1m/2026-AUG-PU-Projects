# Фича `pro-interest-and-limits-ui` — уточнение и стратегия проверок

## Edge cases

| Случай | Ожидаемое поведение | Источник |
|---|---|---|
| `scope` отсутствует в теле отказа вовсе | трактуется как `global` (самое общее), аномалия в клиентском журнале | FR-2, `fail-closed-defaults` |
| `reset_at` в прошлом (часы клиента разошлись с сервером) | значение всё равно форматируется как есть — экран не занимается синхронизацией часов, это не его ответственность | FR-3 |
| `contact` с ведущими/хвостовыми пробелами | обрезаются до классификации (`ClassifyContact` шаг 1) | 02_pseudocode.md |
| `contact` — валидный email, но домен без реального MX | ПРИНИМАЕТСЯ: продукт не проверяет доставляемость почты, только форму (проверка MX — отдельная, более дорогая защита, которой в неделе нет) | FR-6 |
| два разных `owner_key` (два разных пользователя) отправляют интерес в один момент | оба успешны — cadence считается ПО КАЖДОМУ `owner_key` отдельно, не глобально | FR-7 |
| повторный `POST /api/v1/interest` на СЛЕДУЮЩИЕ сутки по Москве | успешен — cadence привязана к календарным суткам, а не к «24 часам от прошлой записи» | FR-7, `coding-style.md` (сутки — Europe/Moscow) |
| пользователь обновляет страницу экрана лимита | форма снова отображается (клиент не помнит состояние между загрузками); повторная отправка отбивается сервером `429`, деньги/данные не теряются | 02_pseudocode.md `RenderLimitScreen` шаг 4 |

## Стратегия проверок (слой по природе признака)

| Природа признака | Слой | Что именно |
|---|---|---|
| классификация контакта (email/telegram/неопознано), закрытые границы длины | unit | `ClassifyContact` — таблица примеров, включая границы 254/255 символов, 5/4/32/33 символа Telegram-логина |
| текст экрана по `scope`, форматирование `reset_at` | unit (React/DOM) | `LimitScreen` рендерит два разных текста, обрабатывает отсутствующий/битый `reset_at` |
| маршрут `POST /api/v1/interest`, ответы `201`/`422`/`429` | integration | реальный `apps/api` + тестовая БД |
| cadence «раз в сутки», разделяемый ресурс | **конкурентный прогон** | AC-8: 10 одновременных запросов одного `owner_key` → ровно 1 успех |
| отсутствие платёжных элементов на экране | integration (снимок разметки) | поиск запрещённых строк/селекторов в отрендеренном HTML |

## Обязательный конкурентный тест

Cadence проверяется ТЕМ ЖЕ классом теста, что и квота в `foundation`
(`shared-resource-verification.md`): последовательный тест на «одна запись в сутки» зеленеет и при
правильной блокировке, и при «прочитать, потом записать» — различает их только параллельный прогон
N одновременных запросов одного `owner_key` (AC-pro-interest-and-limits-ui-8, N = 10). Добросовестный
параллельный запрос ВТОРОГО `owner_key` не должен быть заблокирован конкуренцией за строку первого
(проверяется тем же прогоном на соседнем `owner_key`, аналогично `AC-foundation-9`).

## Испытание стража (guard-must-be-able-to-fail)

Cadence-проверка (`02_pseudocode.md`, шаг 3 `RecordProInterest`) обязана быть предъявлена ВМЕСТЕ с
прогоном на внедрённом дефекте: заменить транзакционную проверку-и-вставку на «прочитать, потом
записать» (`SELECT`, затем безусловный `INSERT` вне той же блокировки) → конкурентный тест AC-8
обязан покраснеть (более одной строки за сутки); восстановить атомарность → тест снова зелёный. Обе
строки — в квитанции Phase 3.

## Зависимость от `scan-pipeline` — как проверять ДО его реализации

`scan-pipeline` в роадмапе — вторая фича по порядку и на момент PLAN этой фичи ещё не реализована.
Интеграционные тесты `LimitScreen`, требующие реальный `{ scope, reset_at }` из живого
`POST /api/v1/scans`, НЕ могут быть E2E на момент реализации этой фичи и используют
СКОНСТРУИРОВАННОЕ тело отказа (фейковый ответ формы `{ limit, reset_at, scope }`) как вход для
`LimitScreen` напрямую — это ЧЕСТНАЯ граница, а не пропуск: квитанция Phase 3 обязана назвать её
явно («сквозной сценарий от реального отказа квоты до этого экрана не проверен — `scan-pipeline` ещё
не реализован»), а не выдавать модульный прогон за сквозной.

## Что НЕ измеряется этой фичей

- Реальная доставляемость email или существование Telegram-аккаунта — только форма значения.
- Сквозной путь «упёрся в лимит на реальном скане → увидел этот экран» — зависит от `scan-pipeline`.
- Конверсия «показ экрана → отправленный контакт» — это продуктовая метрика, не критерий приёмки
  этой фичи.
