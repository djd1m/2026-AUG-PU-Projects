# Фича `pro-interest-and-limits-ui` — архитектура

Расширений `docs/Architecture.md` НЕТ: ни новой таблицы, ни новой колонки, ни нового сервиса, ни
нового внешнего вызова. Фича добавляет один компонент фронта и один обработчик уже объявленного
маршрута.

## Компоненты

| Компонент | Где | Что делает |
|---|---|---|
| `LimitScreen` (React, `apps/web`) | клиентский компонент, рендерится при получении отказа по квоте от любого вызова, требующего скана | реализует `RenderLimitScreen` (`02_pseudocode.md`); секретов и вызовов модели не делает |
| `InterestForm` (React, `apps/web`, часть `LimitScreen`) | поле контакта + кнопка | клиентская проверка-подсказка; отправка на `POST /api/v1/interest` |
| Обработчик `POST /api/v1/interest` (`apps/api`) | новый файл в `apps/api/src/routes/` (по аналогии с `routes/auth-device.ts`) | `ClassifyContact` + `RecordProInterest`, обращение к `packages/db` |

## Данные

Таблица `pro_interest` уже создана фичей `foundation` (миграция `001_init.sql`, `Architecture.md`
строка `pro_interest`). Эта фича ДОБАВЛЯЕТ ей ровно один запрос — cadence-проверку по
`(owner_key, created_at::date AT TIME ZONE 'Europe/Moscow')` — и не требует индекса сверх уже
названного в `Architecture.md` (`(created_at)`); для эффективной cadence-проверки по владельцу
целесообразен составной индекс `(owner_key, created_at)`, но он НЕ блокирует корректность (проверка
верна и без него, просто медленнее при большой таблице) — решение о добавлении индекса остаётся за
реализацией и не меняет наблюдаемое поведение фичи.

## Взаимодействие с cоседними фичами (потребитель, не производитель контракта)

`{ limit, reset_at, scope }` — ответ `POST /api/v1/scans` (маршрут 1), которым владеет
`scan-pipeline`. Эта фича его ТОЛЬКО читает и форматирует; она не может быть полностью
интеграционно проверена до реализации `scan-pipeline` (см. `04_refinement.md`, раздел о
фейковом источнике отказа для тестов).

## Безопасность

- Ограничение частоты `api` (FR-foundation-8, уже реализовано) покрывает `POST /api/v1/interest` как
  любой мутирующий маршрут (30/мин на IP) — это ОБЩАЯ защита от перебора; cadence «раз в сутки на
  владельца» (FR-pro-interest-and-limits-ui-7) — ОТДЕЛЬНАЯ, бизнесовая, по другому ключу
  (`owner_key`, не `ip_prefix`) и с другим окном. Одна не заменяет другую (`security-operation-order`
  этого проекта: у каждой защиты свой ключ и своя причина).
- `owner_key` берётся из `Cookie: session` на сервере, не из тела запроса — тот же принцип, что у
  `GET /api/v1/diary` (владение по серверному ключу, не по присланному идентификатору).
- Контакт не рендерится нигде на публичной поверхности продукта (нет партнёрского дашборда,
  показывающего чужие `pro_interest`); экранирование строк вывода в этой фиче не требуется, потому
  что значение никогда не возвращается пользователю иначе, чем эхом собственного успешного ввода.
