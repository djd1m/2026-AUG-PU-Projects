## Дефект 1 — на карточке не видно надписей

### Диагноз (подтверждён, не переоткрывался)

- `apps/api/src/share/render-card-image.ts` строит SVG-текст поверх фото через `sharp`.
  `font-family` в тексте не указывался вовсе.
- Образ `api` (до правки) собран на `node:22.22.0-bookworm-slim`: ни `fontconfig`, ни
  шрифтов в нём не было. Подтверждено ДО правки: `docker exec n4-tarelka-api-1 fc-list`
  падал (`fc-list: command not found`), т.е. `fc-list | wc -l` → фактически «команды нет»,
  что для librsvg равнозначно нулю доступных шрифтов — рисовать текст было нечем.
- Эмпирически проверено (изолированный `fontconfig` через `FONTCONFIG_FILE`, три сценария
  локальным `sharp`): при ПОЛНОСТЬЮ пустом каталоге шрифтов рендер даёт ~180 «ярких»
  пикселей на 300×100 (артефакты/tofu-глифы, не текст); с любым системным шрифтом —
  ~937-1000. Важная находка, отличающая мой вывод от буквальной формулировки задачи:
  **сам по себе отсутствующий `font-family` НЕ даёт пустой рендер**, если в системе есть
  ХОТЬ ОДИН зарегистрированный шрифт (librsvg/pango подставляют первый попавшийся). Пустой
  рендер даёт именно ОТСУТСТВИЕ шрифтов в окружении — это и есть подтверждённая на стенде
  причина, а `font-family` — вторая, самостоятельно правильная (детерминированность,
  соответствие дизайн-системе), но не единственно достаточная правка.

### Правка

1. **`Dockerfile`, stage `api`**: `apt-get install -y fontconfig`, `COPY` двух файлов
   `apps/web/public/fonts/{Onest,Unbounded}-wght.ttf` + их `OFL-*.txt` в
   `/usr/share/fonts/truetype/n4/`, `fc-cache -f`. Те же файлы, что уже использует `web`
   (`apps/web/app/globals.css`) — второй набор не заводился. Лицензии OFL едут в образ
   вместе со шрифтами.
2. **`render-card-image.ts`**: каждому `<text>` — явный `font-family`, зеркалируя деление
   `--font-display`/`--font-text` из `globals.css` (дублирование СТРОК, не логики: SVG не
   умеет CSS custom properties, а этот файл рендерится сервером, вне DOM браузера).
   Название блюда и числа — `'Unbounded', 'Onest', sans-serif`; подписи, источник, бейдж —
   `'Onest', sans-serif`.

### Проверка — на ПИКСЕЛЯХ, не на разметке

Новый файл `tests/unit/render-card-image-pixels.test.ts` + вспомогательный процесс
`tests/unit/fixtures/render-card-harness.ts` (fontconfig инициализирует состояние один раз
за процесс — переключение `FONTCONFIG_FILE` внутри теста ничего не меняет, поэтому каждый
сценарий — отдельный `tsx`-процесс).

- Тест 1: рендер с ИЗОЛИРОВАННЫМ набором шрифтов, содержащим РОВНО те два файла, что кладёт
  `Dockerfile`. Доля «ярких» пикселей (текст белый на тёмном фоне) в зоне названия блюда и
  в первой плитке числа — ВЫШЕ порога (0.03 / 0.005).
- Тест 2 (ИСПЫТАНИЕ, guard-must-be-able-to-fail): ТОТ ЖЕ код (с `font-family`), но
  зарегистрированных шрифтов НЕТ ВООБЩЕ — воспроизводит РЕАЛЬНОЕ найденное на стенде
  состояние (не гипотетическую мутацию `font-family`, которая, как показано выше, не
  воспроизводит дефект). Те же пороги — НЕ проходят. Это и доказывает, что страж различает
  «есть текст» от «текста нет», а не подогнан под любой исход.
- Пороги измерены заранее (не «на глаз»): с шрифтами ≈0.11/0.024, без шрифтов ≈0.01/0.0007.

Оба теста ЗЕЛЁНЫЕ на исправленном коде (см. прогон ниже).

## Дефект 2 — из дневника нельзя вернуться к блюду и поделиться

### Правка

`apps/web/app/diary/page.tsx`: каждая запись дня (`entry_id`) теперь — обёрнута в `<a
href="/result/{entry.recognition_id}">`, ведущую на уже реализованный экран результата
(там есть кнопка «поделиться»). `recognition_id` уже приходил в ответе `GET /api/v1/diary`
(`apps/api/src/routes/diary.ts::entryPayload`) — правка только на клиенте. Добавлена
подпись «открыть и поделиться →» и `aria-label`. `globals.css`: `.diary__entry-link` —
сброс стилей ссылки поверх существующей карточки `.item` (форма карточки не менялась),
`.diary__entry-open` — подпись-индикатор.

### Живая проверка

1. `PATCH /api/v1/diary/{recognitionId}` `{"op":"confirm"}` → запись создана
   (`entry_id=6864af06-…`, `recognition_id=45f01f96-…`).
2. `GET /api/v1/diary?date=2026-09-13` → запись присутствует с тем же `recognition_id`.
3. Собранный бандл `web` (после пересборки) содержит ожидаемую разметку: `grep` по
   `.next/static/chunks/app/diary/page-*.js` нашёл
   `` "result/".concat(e.recognition_id),className:"item diary__entry-link" `` — то есть
   ссылка реально попала в отданный браузеру код, а не осталась только в исходнике.
4. `GET /result/45f01f96-…` → `200`, `GET /api/v1/scans/45f01f96-…` за тем же id → тот же
   скан (`status: done`, тот же `scan_id`) — переход по ссылке открывает именно тот скан.

Автоматического компонентного теста на саму ссылку НЕ добавлено (нет прецедента в
проекте — `diary/page.tsx` делает собственный `fetch` внутри `useEffect`, не принимает
данные пропом, как `result-screen.tsx`; заводить его ради одной ссылки в рамках бюджета не
стал). Покрыто: typecheck + lint + build (JSX/типы) + живая проверка выше.
