## Дефекты стыка, найденные слиянием

**Ни один из пяти не был помечен маркером конфликта, и ни одна ветка не могла увидеть их
по отдельности** — ровно тот класс, ради которого слияние делается человеком, а не `-X ours`.

### 1. Два независимых клиента удаления объекта из бакета

`scan-pipeline` внёс `createMinioRemover` (динамический импорт `minio`) для
`PurgeExpiredPhotos`; `consent` внёс `createMinioPhotoStore` для эразуры. Делают РОВНО одно —
удаляют ключ из бакета — и обе трактуют «объекта уже нет» успехом. Оставлена ОДНА реализация
(`createMinioPhotoStore`), `PurgeExpiredPhotos` получает её через адаптер имени метода. Иначе
в одном процессе жили бы ТРИ соединения с хранилищем и ДВА места, где записано одно решение.

### 2. 🔴 Эразура оставляла НОРМАЛИЗОВАННУЮ копию фотографии в бакете

Самая дорогая находка. `RunErasureJob` удалял только `photo.object_key`. Колонка
`normalized_object_key` существовала в `001_init.sql` с самого начала, но ЗАПОЛНЯТЬ её начал
`scan-pipeline` — в дереве ветки нормализации не было, и тестов на второй объект быть не
могло. После слияния каждое распознавание создаёт вторую копию снимка, и аккаунт объявлялся
`erased`, строка `photo` — `purged`, а **изображение тарелки физически оставалось в
хранилище**. Это ровно тот отказ, против которого написан RV-consent-and-telegram-auth-02
(там — заглушка вместо настоящего бакета), вернувшийся через стык; предмет — особая
категория персональных данных (ADR-009).

Починено по существу: выбираются ОБА ключа, отметка `purged` ставится ТОЛЬКО после обоих —
иначе сбой на второй копии навсегда вывел бы строку из выборки следующего прогона.

Два теста на настоящем MinIO, **страж испытан внедрённым дефектом**:

```
строка удаления копии убрана  ->  Tests  2 failed | 10 passed
код восстановлен              ->  Tests  12 passed
```

### 3. 🔴 Каждое событие входа, согласия и эразуры печаталось как `[redacted]`

`SERVICE_LOG_FIELDS` — закрытый список полей журнала — появился в `foundation` ПОСЛЕ того,
как ветка ответвилась (лечение RV-foundation-01). Ни одно поле её событий в списке не
значилось, поэтому в бою `erasure_job_account_failed` выглядел как
`{"account_id":"[redacted]","message":"[redacted]"}`: незавершённое удаление невозможно
разобрать. Секретов при этом не утекало — отказ чисто диагностический и потому молчаливый.

Список отстал и от СВОЕЙ фичи: `attempt_id`, `current_fence`, `failure_reason`, `field`,
`task_budget_expired` (`scan-pipeline`) в нём тоже отсутствовали.

Внесены поля обеих фич (ни одно не несёт секрета: внутренние идентификаторы наравне с
`scan_id`, закрытые перечисления нашего кода, счётчики). Чтобы список и код больше не
расходились молча, добавлен **детерминированный страж слоя 1** — `tests/unit/source-guards.test.ts`,
«каждое поле, передаваемое в журнал, объявлено в `SERVICE_LOG_FIELDS`»: разбор аргументов
вызовов `logger.*` с учётом вложенности (наивный поиск `слово:` принимает `null` из тернарного
оператора за имя поля). Отказ стража означает «внеси поле осознанно», а не «не логируй».

**Страж испытан:** `'account_id'` убран из списка → `1 failed`, указано имя поля и файл;
возвращён → `11 passed`.

### 4. Обязательное поле конфигурации против фикстуры соседней фичи

`telegramBotToken` стал обязательным полем `ApiConfig`; `tests/helpers/scan-config.ts`
появился в `scan-pipeline` и о нём не знал. Поймано `typecheck` (TS2741) — единственный
дефект этого слияния, пойманный машиной без чтения. Токен взят ТОТ ЖЕ, которым
`tests/helpers/telegram.ts` подписывает `initData`: иначе тест проверял бы несовпадение
фикстур, а не входную границу.

### 5. `AC-consent-and-telegram-auth-6`: объявленное имя теста не совпадало с фактическим

Ворота `--completion` дали GAP: в `05_completion.md` заголовок нёс суффикс
«(попытка 3: оба устройства несут записи ДО входа B)», которого в самом тесте нет. Тест
существует и свойство проверяет (RV-08 третьего обзора). Приведено в соответствие ЗАЯВЛЕНИЕ,
а не тест: факт — то, что исполняется.

## Найдено, но НЕ починено — и почему

### 🟠 CSP отвергает загрузку SDK Telegram (и, судя по сборке, ВСЕ скрипты страницы)

`apps/web/middleware.ts` (`foundation`, лежит в БАЗЕ обеих сторон) ставит
`script-src 'self' 'nonce-…' 'strict-dynamic'`. `strict-dynamic` ОТМЕНЯЕТ разрешения по
хосту, поэтому `<Script src="https://telegram.org/js/telegram-web-app.js">`, внесённый веткой,
может исполниться только по nonce. Измерено по собранному артефакту:

```
grep -c 'nonce=' apps/web/.next/server/app/index.html   ->  0
```

Страницы префендерены статически (`○ (Static)` в выводе `next build`), а nonce рождается на
КАЖДЫЙ запрос — совпасть им негде. Вместе с bootstrap-скриптом `next/script`
(`<script>(self.__next_s=…).push(["https://telegram.org/…"])</script>` — инлайновый, без
nonce) это означает, что `window.Telegram.WebApp` не появится, а с ним не заработает ни вход
из Mini App, ни автологин.

**Почему не чинится здесь.** (1) Дефект НЕ создан слиянием: middleware лежит в базе, ветка
имела его при разработке — это пробел `foundation`/ветки, а не стыка. (2) Лечение — выбор
между «разрешить `telegram.org` явно», «отказаться от `strict-dynamic`» и «сделать страницы
динамическими»; это архитектурное решение о политике безопасности, и молча ослаблять CSP в
коммите слияния недопустимо. (3) Слой честно: моё доказательство — слой 1 (собранный HTML,
цитата выше), а окончательный вердикт выносит только настоящий браузер на развёрнутом стенде
(`embeddable-widget.md`, класс `политика-безопасности`), а образы приложений не собирались
(на диске меньше 2 ГБ). Передаю владельцу как отдельную находку.

### 🟡 Удаление аккаунта не закрывает создание новых сканов

`RunErasureJob` откладывает аккаунт, пока у него есть `recognition` в статусе `queued`
(аренда статус НЕ меняет — проверено по `lease.ts`, так что незавершённый вызов модели
учтён верно). Но `POST /scans` работает по `device_session`, а сессия остаётся связанной с
аккаунтом `erasing` до самого конца эразуры: пользователь, продолжающий снимать после запроса
на удаление, откладывает эразуру неограниченно — при объявленном сроке 72 часа. До слияния
это было недостижимо: в дереве ветки маршрута `POST /scans` не существовало. Изменение
поведения здесь — продуктовое решение (отказывать в съёмке? отвязывать сессию сразу?), а не
объединение смыслов, поэтому оставлено владельцу.
