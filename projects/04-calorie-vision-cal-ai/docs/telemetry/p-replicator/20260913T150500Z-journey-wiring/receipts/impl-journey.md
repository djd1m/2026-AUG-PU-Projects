# Квитанция: замкнуть путь пользователя (N4, CJM «Гибрид E»)

Исполнитель: impl-journey. Дефект, найденный владельцем на живом стенде: «после того как
произошло распознавание и показаны калории — никаких переходов с этого экрана нет». Проверено
перед началом: `result-screen.tsx` нёс только правки состава, кнопок «в дневник»/«поделиться» не
было вовсе, экрана дневника в `apps/web/app` не существовало.

## Путь целиком (что теперь замкнуто)

```
камера → результат ──▶ «в дневник» ──▶ [нет согласия?] → согласие → (авто-повтор) → день (стрик, лимит виден отдельным экраном)
                   └──▶ «поделиться» → [нет согласия?] → согласие → (авто-повтор) → адрес карточки /c/<id> + share/копирование
день ──▶ к камере · результат (и отказ) ──▶ к камере
```

## Что добавлено, по экранам

### Экран результата (`apps/web/app/result/result-screen.tsx`)
- Две главные кнопки — «в дневник» (`btn--primary`) и «поделиться» (`btn--accent`), РАЗЛИЧИМЫ
  формой (заливка/контур), не только цветом. Рендерятся ТОЛЬКО когда переданы соответствующие
  действия — страница передаёт их только при `status === 'done'` (компонент вообще не
  инстанцируется на других статусах, см. ниже), так что условие «только при done» выполняется
  на уровне вызывающей стороны, а не проверкой статуса внутри презентационного компонента.
- `journeyNotice` — необязательная строка под кнопками для отказов, которые НЕ уводят со
  страницы (404/409/сеть); консент уводит целиком и заметки не оставляет.
- Ссылка «к камере» — ВСЕГДА в разметке, обычный `<a href="/">`, без JS и без роутера (пункт 5
  задачи; тот же приём навигации, что и остальная фича).

### Маршрут результата (`apps/web/app/result/[id]/page.tsx`)
- `confirmToDiary()` — `PATCH /api/v1/diary/{scanId}` (`{ op: 'confirm' }`). `200` → полный
  переход на `/diary`. `403 consent_required` → `goToConsent('diary')`. `404`/`409`/сеть/прочее →
  `journeyNotice` понятным текстом, страница не уходит.
- `shareItem()` — `POST /api/v1/share-cards` (`{ recognition_id: scanId }`). Сервер ТРЕБУЕТ
  согласие и на этот маршрут тоже (`create-share-card.ts`, `preCheck`/`createShareCardGuarded`
  оба дают `403 consent_required` — карточка несёт состав блюда, те же данные о питании) — задача
  явно называла это только для «в дневник», но контракт сервера одинаков для обеих кнопок,
  трогать его запрещено, поэтому «поделиться» обработан симметрично. При успехе: абсолютный адрес
  карточки (`origin + url`), затем `navigator.share`, если браузер умеет, иначе автокопирование в
  буфer с видимым подтверждением («скопировано») и всегда видимой ссылкой ниже кнопок (панель
  `.share-panel`) — на случай, если ни то, ни другое недоступно (приватный режим без буфера).
- `failed`/`refused` (единственная ветка `status !== 'done' && status !== 'queued'`): причина
  текстом + кнопка «снять ещё раз» на камеру.
- `queued`/сетевые ошибки загрузки — поведение НЕ менялось (задача просила это только для
  failed/refused).

### Согласие: путь «увели — вернули — повторили»
- `PATCH`/`POST` при `403` вызывают `goToConsent(intent)` →
  `window.location.assign('/consent?return=' + encode('/result/<id>?intent=diary|share'))`.
  Полная навигация (`window.location.assign`), не роутер — тот же приём, что и камера.
- `apps/web/app/consent/return-path.ts` (новый, чистый модуль): `isSafeReturnPath` принимает
  ТОЛЬКО путь вида `/...`, отвергает `//чужой-хост` и абсолютные адреса (открытый query-параметр
  — потенциальная дверь редиректа, `honest-configuration` CFG-I3). `resolveDecisionTarget('grant',
  returnTo)` дописывает `consent=granted` (сигнал «повторить»); `'decline'` возвращает БЕЗ
  сигнала — отказ не повторяет действие автоматически.
- `apps/web/app/consent/page.tsx` — правлен МИНИМАЛЬНО: `return` читается из
  `window.location.search` (НЕ `useSearchParams` — избежан риск Next-требования Suspense-границы
  при статической генерации; в этом приложении оно и так не сработало бы, т.к. `headers()` в
  корневом `layout.tsx` уже переводит всё дерево в динамический рендер, но решение принято не
  полагаться на это неявно). Небезопасный/отсутствующий `return` → старое поведение
  `router.back()` (совместимость с прямым переходом на `/consent`, включая существующий тест
  `consent-text-hash-sync.test.ts`, который его не трогает).
- `apps/web/app/result/[id]/page.tsx` — эффект по возврату: если в адресе `consent=granted`,
  параметры `consent`/`intent` вычищаются из URL СРАЗУ (`history.replaceState`), затем РОВНО ОДНО
  действие повторяется автоматически (`confirmToDiary` либо `shareItem`, по `intent`) — обновление
  страницы (F5) не повторит его второй раз.

### Экран дня (`apps/web/app/diary/page.tsx`, НОВЫЙ)
- `GET /api/v1/diary?date=YYYY-MM-DD`, дата по умолчанию — «сегодня» по Москве, вычисляется
  ТОЛЬКО в эффекте после монтирования (не при первом рендере — иначе серверный и клиентский
  первый рендер разошлись бы вокруг полуночи, гидратационное расхождение).
- `401` (прямой заход без предшествующего скана — сессии может не быть) → создать сессию через
  `POST /api/v1/auth/device`, повторить РОВНО один раз — тот же приём, что `capture-upload.ts`.
- Итоги дня (4 плитки, переиспользован `.result__tiles`/`.tile` — ккал, белки, жиры, углеводы),
  стрик (`дней`, список заморозок), список записей (приём пищи, ккал, состав), переключение даты
  на день назад/вперёд; «вперёд» ЗАБЛОКИРОВАНА, когда текущая дата — сегодня (`canGoForward`).
- «Если согласия нет — показывать явно, а не пустой список» (пункт 4 задачи): у `GET /diary`
  (маршрут 4 канона) НЕТ проверки согласия вовсе — пустой список неотличим от «согласия никогда
  не было». Отдельного серверного маршрута статуса согласия в каноне тоже нет, а вводить новый
  запрещено задачей явно («не менять серверные маршруты»). Решение, названное явно, а не
  скрытое: `apps/web/app/consent/local-status.ts` — НЕАВТОРИТЕТНАЯ локальная (`localStorage`,
  только этот браузер) подсказка, записываемая при решении на `/consent`. Экран дня показывает
  баннер «согласия нет — дневник не ведётся» только когда подсказка явно `declined`; `unknown`
  (другое устройство, прямой заход, старые данные) ведёт себя как раньше — список без баннера.
  Названный предел: подсказка может быть неверна (другое устройство того же владельца, очищенный
  `localStorage`) — она ничего не открывает и не запрещает, только выбирает текст, реальная
  защита записи дневника — на сервере (`enforce-before-diary-write.ts`), не тронута.
- Возврат к камере — та же ссылка `<a href="/">`.

## Непроверенное и почему (не скрыто)

- **Реальный клик по кнопкам через браузер** (403 → редирект → согласие → авто-повтор → диван
  `/diary` живьём). DOM/jsdom в этом проекте НЕ настроен (`.claude/rules/testing.md`,
  `capture-upload.test.ts`) — тот же предел, что у степпера порции и остальных интерактивных
  частей `result-screen.tsx` до этой задачи («замер 100 мс степпера — E2E после MVP»). Проверено
  раздельно: (а) чистая сетевая логика — юнит-тестами выше; (б) факт существования и первого
  серверного рендера маршрутов — HTTP-тестами на собранном приложении. Интеграция «клик → фетч →
  переход» подтверждена ЧТЕНИЕМ кода (одна цепочка `useCallback`), не прогоном в браузере.
- `tryNativeShare`/`tryCopyToClipboard` (в `[id]/page.tsx`, не вынесены в чистый модуль —
  тонкие обёртки над `navigator.share`/`navigator.clipboard`, побочный эффект сам по себе) —
  без прямого юнит-теста; риск низким считаю (пять строк, try/catch, оба пути покрыты видимой
  ссылкой-запасным вариантом в разметке), но прогоном не подтверждён.
- **`npx vitest run --config vitest.integration.config.ts` целиком** (включая
  `confirm-diary-entry.test.ts`, `share-cards-route.test.ts`, конкурентные прогоны) — требует
  поднятого PostgreSQL профиля `test`; в бюджет задачи (90 минут, только соединение экранов) не
  поднимал отдельно. Эти серверные маршруты и их тесты НЕ менялись этой задачей — риск считаю
  низким (контракты прочитаны из исходника, не из документации, см. «Что НЕ делать» ниже), но не
  подтверждённым свежим прогоном именно сегодня.
- NFR-PERF (≤1с/≤6с) на живом стенде не снимал — не в объёме задачи.
- Полный CJM с настоящим фото (снять → дождаться распознавания → подтвердить → увидеть в
  дневнике) вручную на живом стенде НЕ пройден — потребовал бы реального вызова модели или
  фейка через отдельную сессию и вышел бы за бюджет.
