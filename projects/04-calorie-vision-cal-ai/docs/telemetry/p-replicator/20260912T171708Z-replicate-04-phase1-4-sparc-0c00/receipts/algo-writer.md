## Отклонения и причины

1. **`REALISES:` у двух алгоритмов не называет ни одного `SC-US-nnn-k`.** `AntiFraudOnCode`
   (`FR-PARTNER-003`) и `PurgeExpiredPhotos` (`NFR-SEC-001`) не имеют пользовательских сценариев
   приёмки: первый покрыт Gherkin-сценарием `@FR-GROWTH-002 @security`, второй проверяется сроком
   хранения. Вместо выдуманной ссылки там стоит прочерк с названной причиной. Это сознательный
   выбор: дописать им чужой `SC` означало бы получить зелёное покрытие ценой ложного утверждения,
   а обратная таблица ловит ровно это. Оба случая названы в тексте раздела `## Scenario Coverage`.
2. **`Solution_Strategy.md` — 115 строк вместо 70–110.** Заданное содержание — семь разделов, из
   них три таблицы (корневые причины, рассмотренные решения, эффекты второго порядка) — в 110 строк
   уложилось только после двух проходов сжатия; третий проход пришлось бы делать за счёт фактов, а
   не формы. Сжималась именно форма: числа, ссылки, оговорки и пометки доверия сохранены полностью.
3. **`FR-GROWTH-005` (поимённый seeding-план) не заявлен ни одним алгоритмом.** Это план недели —
   документ и действие оператора, а не процедура в коде: алгоритма, который его исполняет, не
   существует. Заявка была бы ложной. На покрытие сценариев это не влияет: у требования нет
   `SC-US-nnn-k`, его сценарии живут в §3 спецификации как Gherkin.
4. **`NFR-PERF-002` (видоискатель ≤ 1 с) не заявлен.** Требование к первому экрану клиента,
   реализуется версткой и загрузкой, алгоритма не имеет. Причина та же, что в пункте 3.
5. **Публичный маршрут карточки записан как `GET /c/{card_id}` без префикса `/api/v1`.** Канон §5
   перечисляет его среди десяти, но это страница, которую открывает посторонний человек по ссылке
   из мессенджера, и префикс API там был бы неверен. Расхождение названо прямо в шапке раздела
   `## API Contracts`; маршрутов по-прежнему ровно десять.
6. **В `Research_Findings.md` сохранены 15 строк `НЕ НАЙДЕНО` и два прямых противоречия**
   (80% против 90% в заявлениях источника о собственной точности; Sterling et al. против Biolayne).
   Задание требовало сохранять `НЕ НАЙДЕНО`; противоречия оставлены неразрешёнными с указанием, что
   рассудить их нечем без доступа к методологии. Отдельно помечено, что несущая гипотеза продукта —
   «фото удерживает лучше ручного ввода» — прямого подтверждения в литературе НЕ ИМЕЕТ.

### Что изменено

1. **`ApplyPartnerCode` переписан на решение ПО ПОЛЮ `attribution.source`, а не по факту
   существования строки.** Было 9 шагов с неявной развилкой, стало 10 шагов с четырьмя
   взаимоисключающими исходами: `applied` · `conflict` · `invalid` · `rejected`. Ветки:
   атрибуции нет → создать `pending`, `replaced_source = NULL`; есть со слабым источником
   (`cookie`/`deeplink`) и вызов явный → заменить код, записать `replaced_source` и аудит
   `replaced_weaker_source`, `source = explicit`; есть с `source = explicit` → `conflict` без
   изменений; есть со слабым источником и вызов тоже слабый → `conflict` без изменений (добавлено
   сверх задания: без этой ветки последняя открытая ссылка молча отбирала бы когорту у первой).
   Недействительный код → `invalid`, НИЧЕГО не изменено: существующая атрибуция переживает
   неверный ввод, иначе опечатка отменяла бы уже применённый код.
2. **Три проверки отказа (`code_blocked`, `self_referral`, `antifraud_ip_burst`) сведены в один
   шаг 4 и явно поставлены ДО чтения существующей атрибуции.** Порядок назван в тексте: отклонённый
   код не должен успеть заменить действующую атрибуцию.
3. **Маршрут 7 `POST /api/v1/codes/apply` приведён к той же логике.** `200` отдаёт
   `{ attribution_id, status, code, source, replaced_source: null | 'cookie' | 'deeplink' }`;
   `409 already_attributed` остался ТОЛЬКО для случая, когда существующая атрибуция уже имеет
   `source = explicit` — это записано в ячейке прямым текстом, вместе с утверждением, что замена
   слабого источника есть `200` с непустым `replaced_source`, а не конфликт. `422 invalid_code`
   дополнен словами «НИЧЕГО не изменено».
4. **`attribution` в `## Data Structures`:** `source` объявлен ЗАКРЫТЫМ набором из трёх значений с
   порядком силы `explicit > deeplink > cookie`; добавлено поле `replaced_source: …?`; в строку
   вписана уникальность по `device_session_id`. Прежняя формулировка «уникальность делает код
   сильнее cookie неотменяемым» УДАЛЕНА из шагов алгоритма: она приписывала ограничению свойство,
   которого у него нет — уникальность гарантирует единственность строки, а не её неизменность.
   Это то же исправление, которое `arch-writer` внёс в `Architecture.md`.
5. **`recognition.leased_until` и выборка очереди.** В сущности поле снабжено семантикой «аренда
   воркера, 60 с; `NULL` — задание свободно». В `RecognizeScan` шаг 1 предикат стал
   `WHERE status = 'queued' AND (leased_until IS NULL OR leased_until < now())`, аренда ставится на
   60 с, продление не выполняется. В тексте названо, ЧТО именно закрывает каждая половина:
   `SKIP LOCKED` — одновременный захват двумя ЖИВЫМИ воркерами, предикат по `leased_until` — воркер,
   который взял задание и умер, не удержав блокировку. Названа и цена: редкий повторный вызов
   модели, уже учтённый потолками, потому что счёт идёт по попыткам.
