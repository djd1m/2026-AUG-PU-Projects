### Deployment Sequence

1. **Pull/build.** Integration owner фиксирует commit/SHA, собирает образы `web`, `api`,
   `recognizer` с явными тегами (`compose-hygiene.md`, правило 2); контекст сборки — корень
   монорепо (правило 5, npm workspaces). Секреты (ключ Anthropic, токен Telegram-бота, пароли БД)
   создаются заново для этого окружения, вне git.
2. **Migrate + import.** Применяются миграции `db` (12 таблиц канона); выполняется разовый импорт
   `npm run import:fdc` (не сервис compose — задача до запуска, Architecture.md); курируется
   `food_synonym`. Все сервисы объявляют `healthcheck`, зависимые ждут `condition: service_healthy`,
   а не `service_started` (`compose-hygiene.md`, правило 3); каждый сервис — `restart:
   unless-stopped` (правило 4).
3. **Up за Caddy.** Стек поднимается за `proxy` (Caddy) как единственной дверью; `db` и `storage`
   не публикуют порты, хостовые порты `web`/`api` объявлены только как `${VAR:-default}`. После
   старта сквозной сценарий CJM E проходится на развёрнутом стенде дважды — из браузера (PWA) и из
   Telegram Mini App — по внешнему адресу, который выдало развёртывание, а не по `localhost`
   (ADR-002 Confirmation, `deployment-seams.md`).

### Rollback Procedure

Остановить приём новых сканов (потолок в 0 или флаг обслуживания на `proxy`), не трогая очередь:
`recognition` — это одна строка БД, а не отдельный брокер, поэтому незавершённые задания не теряются
при откате образа (ADR-003). Вернуть предыдущий образ `web`/`api`/`recognizer`; миграции с данными и
`food_item`/`food_synonym` не удалять. Не запускать автоматический повтор эскалации для заданий,
оставшихся в `failed`, — повтор без явного решения человека списывает вторую попытку с того же
суточного потолка (FR-LIMIT-001, FR-LIMIT-002). Presigned-URL, выданные до отката, истекают сами
через 15 минут — отдельной инвалидации не требуется (NFR-SEC-001).

## CI/CD

Стадии `test → build → deploy`.

- **test:** `npm test` (Unit + Integration из `Refinement.md`, включая конкурентный тест атомарности
  квоты и страж «число только из базы», оба испытанные на внедрённом дефекте).
- **build:** `npm run lint`, затем `npm run build` для каждого workspace монорепо (`web`, `api`,
  `recognizer`) — `COPY` в образ выполняется из пути workspace, а не из `/app` (`compose-hygiene.md`,
  правило 5).
- **deploy:** `deploy.sh` выполняет Deployment Sequence выше; шаг блокируется, если Pre-Deployment
  checklist не закрыт целиком.

Команды приведены как план CI: `package.json` монорепо ещё не заведён — он появится на шаге `/start`,
и тогда же имена скриптов будут подтверждены исходником, а не постановкой.

## Monitoring

Канал оповещения ОДИН и он есть в инвентаре зависимостей: запись в журнал плюс сообщение владельцу
в Telegram через Bot API `sendMessage` (`Architecture.md`, External Dependencies, строка «отправляет
сообщение владельцу»). PagerDuty, Slack и почтовая рассылка НЕ используются: их нет в инвентаре, о
них нет договорённости и ни одна из них не проверялась — чек-лист, опирающийся на них, описывал бы
контур эксплуатации, которого не существует (DEC-A-007).

| Метрика | Порог | Источник | Реакция |
|---|---|---|---|
| Response time p99 | > 500ms | наш журнал | журнал + Telegram владельцу (Bot API `sendMessage`) |
| Error rate | > 1% | наш журнал | журнал + Telegram владельцу (Bot API `sendMessage`) |
| CPU usage | > 80% | ручное измерение: метрики контейнера | журнал + Telegram владельцу (Bot API `sendMessage`) |
| Расход на вызовы модели за сутки | > 1560 ₽/сутки (Success Metrics, Specification.md) | наш журнал `/var/log/tarelka/model-spend.jsonl` (`model-cost-contract.md`) | журнал + Telegram владельцу (Bot API `sendMessage`) + служебная страница расхода (NFR-OPS-001) |
| Доля попыток, отклонённых по потолку, с разбивкой по `scope` | > 5% суммарно (Success Metrics, Specification.md) | наш журнал | журнал + Telegram владельцу (Bot API `sendMessage`) |
| Возраст старейшего задания `queued` | > 60 с (окно посредника, `long-job-contract.md`) | наша БД | журнал + Telegram владельцу (Bot API `sendMessage`) |
| Результаты, отброшенные по устаревшей аренде (`stale_lease_result`) | > 0 за сутки | аудит (ADR-003 Confirmation) | журнал + Telegram владельцу (Bot API `sendMessage`) |

Пороги — проектные предложения, не измеренный SLA: ни один процесс ещё не работал под нагрузкой.
Счёт расхода и доли отказов ведётся по попыткам, а не по успехам (FR-LIMIT-001, NFR-OPS-001) —
таймаут и отказ провайдера учитываются наравне с успешным вызовом.

## Logging

Уровни `info`/`warn`/`error`/`fatal` с correlation id (`scan_id`, усечённый `device_session_id`).
Хранение операционных логов — 30 суток, совпадает с TTL фото (NFR-SEC-001); отдельного финансового
лога нет — платежей в неделе нет (PD-PRICE-001). Агрегация на MVP — локальный файл/journald на
хосте, внешнего log-vendor нет. **Не логировать:** байты и содержимое фото, полное значение
`initData`, полный (не усечённый) IP-адрес, содержимое дневника целиком — оно живёт в БД, а не в
логе; секреты (ключ модели, токен бота) — никогда, ни в каком уровне.
