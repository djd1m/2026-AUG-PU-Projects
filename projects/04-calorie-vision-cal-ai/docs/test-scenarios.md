## Область CAPTURE

```gherkin
Feature: Съёмка и загрузка фото

@FR-CAPTURE-001 @happy-path
Scenario: Видоискатель открывается без анкеты и без регистрации
  Given анонимный пользователь впервые открывает продукт
  When приложение загружается
  Then видоискатель камеры показан не позже 1 с, анкеты и полей регистрации нет
  And создана анонимная сессия устройства

@FR-CAPTURE-001 @error-handling
Scenario: Камера недоступна без разрешения устройства
  Given пользователь не выдал приложению разрешение на камеру
  When открывается первый экран
  Then показано системное сообщение о недостающем разрешении с инструкцией
  And видоискатель не отображается, анонимная сессия всё равно создаётся

@FR-CAPTURE-001 @edge-case
Scenario: Ровно одна строка режимов под видоискателем
  Given экран камеры открыт
  When пользователь смотрит под видоискателем
  Then видны ровно два режима «съёмка» и «галерея»
  And штрихкода, ручного ввода и голоса нет

@FR-CAPTURE-002 @happy-path
Scenario: Допустимый формат и размер принимаются
  Given пользователь снимает кадр HEIC размером 2000×2000 px и 8 МБ
  When кадр отправляется
  Then клиент уменьшает длинную сторону до 1536 px
  And кадр принят на распознавание

@FR-CAPTURE-002 @error-handling
Scenario: Непригодный формат отклоняется без списания квоты
  Given пользователь выбирает файл BMP размером 20 МБ
  When он пытается отправить кадр
  Then показан отказ с названной причиной и кнопкой повторной съёмки
  And попытка не списана с квоты FR-LIMIT-001, потому что вызова модели не было

@FR-CAPTURE-002 @edge-case
Scenario: Изображение меньше минимального размера
  Given выбрано изображение 200×200 px
  When оно отправляется
  Then показан отказ по минимальному размеру 320×320 px
  And квота не списана
```

## Область RECOGNIZE

```gherkin
Feature: Распознавание блюда

@FR-RECOGNIZE-001 @happy-path
Scenario: Модель возвращает состав и массу, калории не приходят от модели
  Given фото тарелки принято на распознавание
  When модель отвечает
  Then ответ содержит список ингредиентов, массу каждого в граммах и до трёх кандидатов записей базы
  And ответ модели не содержит полей калорийности или БЖУ (ADR-001, FR-SOURCE-001)

@FR-RECOGNIZE-001 @error-handling
Scenario: Кадр без еды завершается статусом refused
  Given на кадре нет распознаваемой еды
  When распознавание завершается
  Then `recognition.status = refused`
  And показана подсказка «еда не распознана, снимите тарелку целиком»
  And запись дневника не создаётся

@FR-RECOGNIZE-001 @edge-case
Scenario: Меньше трёх кандидатов на ингредиент
  Given для ингредиента «гречка варёная» в базе есть только одна подходящая запись
  When собирается результат распознавания
  Then показан ровно один кандидат, а не заполнение до трёх пустыми значениями

@FR-RECOGNIZE-002 @happy-path
Scenario: Уверенность выше порога — эскалации нет
  Given модель вернула уверенность 0,82
  When собирается результат
  Then вторая попытка распознавания не выполняется
  And в потолок FR-LIMIT-001 засчитана одна попытка

@FR-RECOGNIZE-002 @error-handling
Scenario: Низкая уверенность после эскалации — ручной поиск
  Given первая попытка вернула уверенность 0,4
  When выполняется ровно одна эскалация к Claude Sonnet 5
  And уверенность после эскалации всё ещё ниже 0,6
  Then показан экран «уточните блюдо» с ручным поиском по базе
  And тихого усреднения или выбора первого кандидата не происходит

@FR-RECOGNIZE-002 @edge-case
Scenario: Эскалация списывает вторую попытку с того же потолка
  Given у пользователя было 9 попыток за сутки
  When 10-я попытка получает уверенность 0,3 и эскалируется
  Then обе попытки (базовая и эскалированная) засчитаны в потолок FR-LIMIT-001
  And 11-я попытка (любая, включая новую эскалацию) получает отказ по лимиту

@FR-RECOGNIZE-002 @error-handling
Scenario: Суточная квота эскалаций исчерпана
  Given суточный потолок эскалаций к Sonnet 5 исчерпан (model-cost-contract.md)
  When очередное распознавание получает уверенность ниже 0,6
  Then повторная попытка сильной моделью не выполняется
  And сразу показывается экран «уточните блюдо» с ручным поиском, а не тихая деградация к первому кандидату
```

## Область SOURCE

```gherkin
Feature: Источник числа

@FR-SOURCE-001 @happy-path
Scenario: Число вычисляется из базы по массе
  Given ингредиент сопоставлен записи food_item со значением 130 ккал на 100 г
  And масса ингредиента оценена в 150 г
  When собирается итог
  Then показано 195 ккал = (150 / 100) × 130

@FR-SOURCE-001 @error-handling
Scenario: Нет подходящей записи базы — не подставляется ноль
  Given для ингредиента нет ни одной подходящей записи food_item
  When собирается итог
  Then позиция помечена «нет в базе» и исключена из суммы
  And ноль вместо неизвестного числа не подставляется

@FR-SOURCE-001 @security
Scenario: Страж — оценка модели никогда не попадает в дневник
  Given модель вернула собственную оценку калорийности блюда во внутреннем ответе (для сверки)
  When запись сохраняется в дневник
  Then значение калорийности в дневнике равно сумме по базе, а не оценке модели
  And попытка записать оценку модели напрямую в поле дневника отклоняется на уровне схемы (ADR-001)

@FR-SOURCE-002 @happy-path
Scenario: Источник виден под каждым числом
  Given результат распознавания собран
  When пользователь смотрит на число калорий
  Then рядом видны имя базы «USDA FoodData Central», идентификатор записи, её название, порция в граммах и дата импорта снимка

@FR-SOURCE-002 @edge-case
Scenario: Источник виден на всех трёх поверхностях
  Given одна и та же запись дневника
  When она показывается на экране результата, на экране дня и на карточке 9:16
  Then строка источника присутствует на всех трёх поверхностях без исключения

@FR-SOURCE-003 @happy-path
Scenario: Русское блюдо находится через таблицу синонимов
  Given пользователь произносит/выбирает «борщ»
  When выполняется нечёткий поиск по триграммам
  Then блюдо сопоставлено рецептурной комбинации компонентов USDA с долями
  And состав и источник каждого компонента показаны отдельно

@FR-SOURCE-003 @error-handling
Scenario: Русское блюдо не находится ни через синонимы, ни через USDA
  Given название блюда не входит в таблицу синонимов и не находится нечётким поиском
  When выполняется сопоставление
  Then ингредиент помечен «нет в базе», Open Food Facts не подключается (PD-DATA-002)

@FR-SOURCE-003 @edge-case
Scenario: Падежная форма распознаётся через нормализацию
  Given пользователь вводит «гречкой» (творительный падеж)
  When выполняется поиск
  Then запись «гречка варёная» найдена через нормализованную форму
```

## Область CORRECT

```gherkin
Feature: Корректировка порции и состава

@FR-CORRECT-001 @happy-path
Scenario: Степпер уменьшает порцию с шагом 10 г
  Given результат показывает порцию 250 г
  When пользователь трижды нажимает «минус»
  Then порция равна 220 г
  And все четыре числа пересчитаны локально без нового вызова модели и без списания квоты

@FR-CORRECT-001 @error-handling
Scenario: Ручной ввод вне диапазона отклонён
  Given поле ручного ввода порции открыто
  When пользователь вводит 5000 г
  Then значение не принимается, показан допустимый диапазон 5–2000 г
  And прежняя порция сохранена

@FR-CORRECT-001 @edge-case
Scenario: Длинное нажатие даёт шаг 50 г
  Given степпер порции активен
  When пользователь удерживает «плюс» дольше 500 мс
  Then шаг увеличивается до 50 г за нажатие вместо 10 г

@FR-CORRECT-002 @happy-path
Scenario: Замена ингредиента пересчитывает без вызова модели
  Given модель определила «рис белый», а на тарелке гречка
  When пользователь выбирает «гречка варёная» в поиске по базе
  Then числа пересчитаны по FR-SOURCE-001, источник обновлён
  And новый вызов модели не выполнен, квота не списана

@FR-CORRECT-002 @error-handling
Scenario: Поиск замены не находит ни одной записи
  Given пользователь ищет ингредиент «манго сушёное со специями»
  When поиск по синонимам и USDA не находит совпадений
  Then показано «ничего не найдено», текущий ингредиент остаётся без изменений

@FR-CORRECT-002 @edge-case
Scenario: Удаление ингредиента пересчитывает итог немедленно
  Given блюдо содержит ингредиент «соус»
  When пользователь удаляет «соус»
  Then итог блюда пересчитан без этого ингредиента
  And поправка сохранена в истории и питает курацию синонимов (FR-SOURCE-003)

@FR-CORRECT-003 @happy-path
Scenario: Расхождение больше 15% показывает экран выбора
  Given оценка модели 780 ккал, сумма по базе 640 ккал (расхождение 22%)
  When открывается экран результата
  Then показан экран расхождения с двумя числами и их источниками
  And по умолчанию выбрано число базы, тихое усреднение не выполняется

@FR-CORRECT-003 @error-handling
Scenario: Пользователь выбирает «уточнить состав» вместо числа базы
  Given показан экран расхождения
  When пользователь нажимает «уточнить состав»
  Then открывается редактор состава блюда, а не подтверждение числа базы
  And выбор сохраняется вместе с обоими числами для последующего пересчёта

@FR-CORRECT-003 @edge-case
Scenario: Расхождение ровно на границе 15% не показывает экран
  Given оценка модели отличается от суммы по базе ровно на 15,0%
  When открывается экран результата
  Then экран расхождения не показывается (порог — строго «более 15%», не «от 15%»)
  And в дневник идёт число базы
```

## Область DIARY

```gherkin
Feature: Дневник дня

@FR-DIARY-001 @happy-path
Scenario: Подтверждённый результат создаёт запись дневника
  Given результат распознавания подтверждён в 13:40 по Europe/Moscow
  When запись сохраняется
  Then создана запись с меткой приёма пищи «обед», датой по Europe/Moscow
  And итог дня по ккал и трём макронутриентам пересчитан

@FR-DIARY-001 @error-handling
Scenario: Попытка отредактировать уже удалённую запись
  Given запись дневника удалена в другой вкладке
  When пользователь пытается отредактировать эту же запись
  Then показана ошибка «запись не найдена», список дня перезагружается актуальным

@FR-DIARY-001 @edge-case
Scenario: Метка приёма пищи правится одним тапом
  Given запись автоматически помечена «перекус» по времени 16:10
  When пользователь меняет метку на «ужин» одним тапом
  Then метка сохранена, итог по приёмам пищи пересчитан, публичной ссылки на день по-прежнему нет

@FR-DIARY-002 @happy-path
Scenario: Один пропущенный день замораживает стрик, не обнуляет
  Given стрик равен 5 дням, вчерашний день пропущен
  When пользователь делает запись сегодня
  Then стрик равен 6 дням
  And вчерашний день помечен как «заморожен»

@FR-DIARY-002 @edge-case
Scenario: Два пропущенных дня подряд обнуляют стрик
  Given пропущены два дня подряд
  When пользователь делает запись сегодня
  Then стрик равен 1
  And предупреждений о потере и обратного отсчёта не показывается (нейтральная формулировка)
```

## Область PARTNER

```gherkin
Feature: Код блогера и кабинет партнёра

@FR-PARTNER-001 @happy-path
Scenario: Действительный код применяется по deeplink
  Given партнёру выдан код LIZA10 (4-12 символов A-Z0-9)
  When зритель переходит по deeplink с этим кодом
  Then код применён регистронезависимо, атрибуция создана со статусом pending

@FR-PARTNER-001 @error-handling
Scenario: Недействительный код — ошибка ввода
  Given пользователь вводит код ZZZZ, которого не существует
  When код проверяется
  Then показана ошибка ввода
  And cookie-источник не подставляется вместо него

@FR-PARTNER-001 @edge-case
Scenario: Явный код сильнее cookie
  Given в браузере сохранён cookie-источник с кодом OLD
  When пользователь вводит действительный код NEW руками после результата
  Then атрибуция создана с кодом NEW, а не OLD

@FR-PARTNER-002 @happy-path
Scenario: Кабинет показывает четыре счётчика в трёх окнах
  Given по коду партнёра есть переходы, установки, активации и шеринги
  When партнёр открывает кабинет
  Then показаны все четыре счётчика в окнах «день», «неделя», «всё время»

@FR-PARTNER-002 @edge-case
Scenario: Партнёр без активности видит «данных нет», а не пустой экран
  Given по коду партнёра не было ни одного перехода
  When партнёр открывает кабинет
  Then показаны нули с пометкой «данных нет», а не пустой экран и не прочерки

@FR-PARTNER-002 @security
Scenario: Чужой код не появляется в ответе даже при прямом запросе
  Given партнёр А аутентифицирован
  When он запрашивает данные по коду партнёра Б напрямую через API
  Then возвращается отказ 403, чужие счётчики не раскрываются

@FR-PARTNER-003 @happy-path
Scenario: До 50 применений с одного IP за 10 минут — код работает штатно
  Given за последние 10 минут с одного IP-адреса зафиксировано 49 применений кода
  When приходит 50-е применение
  Then код применяется штатно, атрибуция создаётся

@FR-PARTNER-003 @error-handling
Scenario: 51-е применение с одного IP за 10 минут блокирует код
  Given за последние 10 минут с одного IP зафиксировано 50 применений кода
  When приходит 51-е применение
  Then код блокируется, дальнейшие применения получают статус rejected
  And событие пишется в аудит с кодом, усечённым префиксом адреса и временем

@FR-PARTNER-003 @edge-case
Scenario: Партнёр не может применить собственный код
  Given партнёр вошёл в свой аккаунт
  When он применяет собственный код
  Then атрибуция получает статус rejected и попадает в аудит
```

## Область LIMIT

```gherkin
Feature: Потолки вызовов модели

@FR-LIMIT-001 @happy-path
Scenario: Десятая попытка за сутки укладывается в потолок
  Given за сутки по Europe/Moscow сделано 9 попыток распознавания
  When пользователь делает 10-ю попытку
  Then попытка выполняется штатно, вызов модели происходит

@FR-LIMIT-001 @error-handling
Scenario: Одиннадцатая попытка получает отказ без вызова модели
  Given за сутки сделано 10 попыток распознавания
  When пользователь снимает одиннадцатую тарелку
  Then показан экран лимита с временем обнуления счётчика по московскому времени
  And вызов модели не выполнен

@FR-LIMIT-001 @edge-case
Scenario: Смена одного из двух ключей аноним не обнуляет защиту
  Given анонимный пользователь исчерпал потолок по ключу device_session
  When он подключается с новым IP-адресом, но с тем же device_session
  Then потолок остаётся исчерпанным (оба ключа проверяются одновременно, а не по отдельности)

@FR-LIMIT-002 @happy-path
Scenario: Система в пределах суточного потолка обрабатывает сканы штатно
  Given за сутки система обработала 2999 попыток распознавания
  When приходит очередная попытка любого пользователя
  Then попытка обрабатывается штатно, счётчик увеличивается до 3000

@FR-LIMIT-002 @error-handling
Scenario: 3001-я попытка за сутки отклоняется системным потолком
  Given за сутки система обработала 3000 попыток распознавания
  When приходит 3001-я попытка
  Then новый скан получает отказ «на сегодня лимит исчерпан»
  And уже начатые распознавания доводятся до конца

@FR-LIMIT-002 @edge-case

@FR-LIMIT-003 @happy-path
Scenario: Экран лимита предлагает лист ожидания без цены
  Given показан экран лимита пользователю
  When пользователь оставляет почту для «Pro скоро»
  Then запись интереса сохранена с датой, источником (лимит пользователя или суточный) и кодом партнёра, если применён
  And цена, тариф и платёжная форма на экране отсутствуют

@FR-LIMIT-003 @error-handling
Scenario: Повторный показ экрана лимита в тот же день подавляется
  Given экран лимита уже был показан пользователю сегодня
  When пользователь снова упирается в лимит в тот же день
  Then экран лимита не показывается повторно (не чаще одного раза в сутки на пользователя)

  Given пользователь достиг суточного системного потолка (FR-LIMIT-002), а не личного (FR-LIMIT-001)

  Then источник записи интереса зафиксирован как «суточный», а не «пользовательский»
```

## Growth — дополнительные security-сценарии (не дублируют Specification.md §3)

```gherkin
Feature: Рост — обязательные security-сценарии сверх трёх, уже зафиксированных в Specification.md

@FR-GROWTH-001 @security
Scenario: Перебор card_id не даёт доступа к чужим карточкам
  Given card_id — непредсказуемый идентификатор
  When выполняется последовательный перебор случайных card_id
  Then подавляющее большинство запросов получает 404
  And перебор не даёт статистически значимого доступа к существующим карточкам за разумное время

@FR-GROWTH-002 @security
Scenario: Инъекция в поле кода партнёра отклоняется как невалидный код
  Given поле кода в `POST /codes/apply` получает значение `'; DROP TABLE partner_code; --`
  When запрос обрабатывается
  Then значение отклонено как недействительный код без выполнения как SQL
  And код проверяется параметризованным запросом, а не конкатенацией строки

@FR-GROWTH-003 @security
Scenario: Неаутентифицированный запрос не раскрывает тариф другого пользователя
  Given запрос к конфигурации бейджа не содержит валидной сессии
  When запрос обрабатывается
  Then сервер не возвращает тариф какого-либо конкретного пользователя
  And бейдж на публичной карточке по-прежнему определяется по правилу fail-closed сервера, не клиента

@FR-GROWTH-004 @security
Scenario: Перебор чужих кодов в дашборде партнёра ограничен по частоте
  Given неавторизованный клиент перебирает параметр кода в `GET /partner/dashboard`
  When частота запросов превышает разумный порог с одного адреса
  Then дальнейшие запросы получают отказ по превышению частоты, а не 403 по одному на попытку без предела

@FR-GROWTH-005 @security
Scenario: Код одной группы посева не может быть переприписан другой группе
  Given группе «микро-блогеры» выдан код BLOG5, группе «марафон» — код RUN10
  When активация приходит с кодом BLOG5 из канала, закреплённого за группой «марафон»
  Then атрибуция всё равно засчитывается коду BLOG5 (коду, а не каналу-претенденту)
  And когорта «марафон» не получает чужую активацию задним числом

@FR-GROWTH-006 @security
Scenario: Кэшированная ссылка на отозванную карточку не отдаёт содержимое
  Given пользователь отозвал согласие, публичные карточки должны быть закрыты
  When ранее сохранённая ссылка на карточку открывается повторно (в том числе из кэша браузера)
  Then сервер возвращает отказ без содержимого карточки не позже 60 с после отзыва (FR-GROWTH-006 в Specification)

@FR-GROWTH-007 @security
Scenario: Накрутка переходов по карточке не завышает счётчик конверсии
  Given один и тот же клиент открывает публичную карточку 200 раз за минуту с одного адреса
  When считаются переходы для метрики conv%
  Then повторные открытия сверх разумного порога с одного адреса за короткое окно не увеличивают счётчик линейно
  And автор карточки не получает доступ к идентификатору или дневнику зрителя (см. также Specification.md §3)
```
