# N4 code reviewer

Ревью read-only по `docs/Specification.md`, `docs/Pseudocode.md`, `docs/Architecture.md`,
`docs/Refinement.md` (Edge Cases и критические пути), `docs/ADR.md` (поле Confirmation) и локальным
`.claude/rules/`. Назвать точную ревизию исходника и список прочитанных файлов. Находки — по
серьёзности, каждая с воспроизведением или названным нарушенным инвариантом. **Отсутствие
доказательства не является прохождением.**

## Блокирующие проверки

### Число только из базы (ADR-001)

- JSON-схема вызова модели не содержит `calories`, `kcal`, `protein`, `fat`, `carbs`. Единственное
  поле о калорийности — `model_estimate_kcal`, и страж проверяет именно ЭТО МНОЖЕСТВО, а не
  отсутствие подстроки `kcal`: страж по подстроке запретил бы разрешённое поле.
- `model_estimate_kcal` читается ровно в одном месте — при вычислении `discrepancy_ratio`. Второе
  чтение — блокер.
- Числа считаются из `Snapshot`, а не из живой строки `food_item`: иначе переимпорт задним числом
  меняет уже показанное.
- `recognition` без единой ссылки на `food_item` не может иметь статус `done`. Ноль ссылок —
  `refused(no_food_matched)`, а не `done` с итогом 0 ккал.
- Позиция без записи базы помечена `unmatched` и ИСКЛЮЧЕНА из итога. Ноль вместо неизвестного не
  подставляется. `db_kcal_total = 0` → `discrepancy_ratio = NULL`, не `0%`.

### Атомарность квоты (ADR-007)

- Один оператор `INSERT … ON CONFLICT DO UPDATE SET used = used + 1 WHERE used < :limit RETURNING`.
  Любая форма «прочитать, потом записать» — блокер, даже если последовательный тест зелёный.
- Первичная попытка списывает ТРИ ключа (сессия, IP-префикс, глобальный), эскалация — ЧЕТЫРЕ, все в
  ОДНОЙ транзакции. Отказ любого откатывает транзакцию целиком; встречных декрементов нет.
- Списание выполняется ДО вызова модели. Вызов после `refused` — блокер.
- Счёт по ПОПЫТКАМ: таймаут и отказ провайдера не возвращают списанное.
- Отказ называет `scope`. Отказ по `escalation` даёт `done` + `low_confidence` +
  `failure_reason = quota_exhausted_escalation`, а не `failed`.
- Отсутствие любой из трёх переменных потолка валит старт ненулевым кодом с названным вызовом.
  Дефолт вместо отказа — блокер.

### Аренда задания и fencing (ADR-003, DEC-A-008)

- Предикат выборки содержит И `status = 'queued'`, И `(leased_until IS NULL OR leased_until < now())`
  вместе с `FOR UPDATE SKIP LOCKED`. Без предиката по аренде защиты нет: транзакция закрывается до
  внешнего вызова, и строка снова видна как свободная.
- Захват увеличивает `lease_fence`; запись результата — условный
  `UPDATE … WHERE id = ? AND lease_fence = ?`. Ноль затронутых строк → результат отброшен, в аудите
  `stale_lease_result`. Условный `UPDATE` применяется и к терминальным `failed`/`refused`.
- Соединение с базой не удерживается во время вызова модели.

### Владение и раскрытие

- `GET /scans/{id}`, `POST /scans/{id}/correct`, `PATCH /diary/{entry_id}`, `POST /share-cards` от
  чужой сессии → `404`, тот же ответ, что и для несуществующего, и НИ ОДНО поле не изменено.
  `403` на этих маршрутах — блокер. Единственное исключение — маршрут 8 (кабинет партнёра).
- Владение проверяется по `owner_key` на сервере; идентификатор владельца из тела запроса
  игнорируется. В `GET /diary` параметра «чей дневник» нет вовсе.
- `/c/{card_id}`: удалённая карточка, отозванное согласие и неизвестный `id` дают ОДИН `404` без
  содержимого. Заголовок `Cache-Control: no-store` присутствует.
- Мягко удалённая запись не возвращается ни в списке, ни в итоге, ни по прямому `entry_id`.

### Согласие и особая категория ПДн (ADR-009)

- Запись в дневник без действующего согласия отклоняется на уровне `api`. Съёмка и результат при
  этом остаются доступны.
- Согласие версионировано (текст, хэш, версия, время); неизвестная версия — `422`.
- Отзыв проставляет `revoked_at` всем карточкам немедленно; удаление доводится за 72 ч,
  `account.status = erasing` всё это время, повтор не запускает второе удаление.

### Порядок операций и вход

- Частота ДО разбора тела; валидация ДО заявки `Idempotency-Key`; квота ПОСЛЕ валидации и ДО модели;
  нормализация ДО модели; подпись `initData` по СЫРЫМ байтам ДО разбора, сравнением постоянного
  времени, свежесть `auth_date` ПОСЛЕ подписи.
- Тип файла определяется по байтам, не по заголовку и расширению. EXIF снимается. Полиглот и бомба
  распаковки отвергаются до декодирования.
- Диапазоны проверяются НАШИМ кодом после разбора ответа модели: `confidence` 0…1, `mass_g` 1…5000,
  позиций ≤ 12, кандидатов ≤ 3, `model_estimate_kcal` ≥ 0. Значение вне диапазона → `failed`, а не
  подрезание до границы.
- Недоступность поставщика бросает исключение, а не возвращается значением: штатный возврат из
  колбэка транзакции её коммитит.

### Атрибуция (ADR-008)

Три исхода решаются по полю `source`, а не по существованию строки. Тест, ожидающий, что замену
отобьёт `UNIQUE (device_session_id)`, проверяет ровно ту реализацию, которую решение запрещает:
уникальность гарантирует ЕДИНСТВЕННОСТЬ строки, а не её неизменность. `growth_event(code_applied)`
пишется только при `applied`; `activation` и переход `pending → activated` — одной транзакцией.

## Чем доказывается

Конкурентные прогоны — квота (три ключа), эскалация (четвёртый ключ), аренда, идемпотентность —
обязательны и последовательными тестами не заменяются. Стражи по исходнику принимаются вместе с
прогоном на внедрённом дефекте: две строки, красная и зелёная. Ограничения и блокировки проверяются
на настоящем PostgreSQL; мок их поведения не устанавливает.

Не принимать зелёный результат, полученный на моках, для инварианта базы или конкурентности.
Не объявлять успешными сборку, тесты, хуки и развёртывание по планируемым командам. Живой вызов
модели без ключа не выполнялся — так и записывать (DEC-A-009).
