## Слой выбирается по природе признака, а не по удобству

| Природа признака | Слой | Примеры из проекта |
|---|---|---|
| арифметика, закрытые перечисления, границы | unit | пересчёт `(mass_g/100)×на_100г`, диапазон 5–2000 г, порог 0,59/0,60, мягкий стрик, fail-closed тарифа |
| согласованность двух компонентов, транзакции, ответы маршрутов | integration | `SKIP LOCKED` + fence, три исхода `ApplyPartnerCode`, `initData` по сырым байтам, итог дня в одной транзакции с удалением |
| путь человека на РАЗВЁРНУТОМ стенде | E2E | CJM E дважды: из PWA-браузера и из Telegram Mini App |
| разделяемый ресурс | **конкурентный прогон** | квота (три ключа), эскалация (четвёртый ключ), аренда задания |
| свойство исходника | страж по коду | JSON-схема вызова модели, единственное чтение `model_estimate_kcal` |

## Обязательные конкурентные тесты — не опция

Последовательный тест на разделяемом ресурсе зеленеет при ОБЕИХ реализациях: и при атомарном
операторе, и при «прочитать, потом записать». Различает их только параллельный прогон.

1. **Квота, три ключа.** N параллельных `POST /scans` с одного `device_session_id` при пределе 10 —
   ровно 10 создают `recognition`, ни одна попытка не потеряна и не посчитана дважды. Добросовестный
   параллельный пользователь на соседней сессии не блокируется чужой квотой. Число одновременно
   занятых соединений пула не растёт с числом ожидающих.
2. **Эскалация, четвёртый ключ.** 20 одновременных эскалаций при остатке 1 дают РОВНО один вызов
   Sonnet 5 — проверяется счётчиком обращений к адаптеру провайдера, а не текстом лога. Проверять
   отдельно, а не «заодно»: зелёный тест на трёх ключах ничего не говорит о четвёртом.
3. **Аренда задания.** (а) N воркеров на M заданий — ни одно не захвачено дважды, ни одно не
   потеряно. (б) Устаревшая аренда: A берёт задание, аренда искусственно истекает, B захватывает и
   завершает; затем A пишет результат — его `UPDATE` обязан затронуть НОЛЬ строк, результат B
   не тронут, в аудите есть `stale_lease_result`.
4. **Идемпотентность создания скана.** Два одновременных `POST /scans` с одним `Idempotency-Key` и
   одной сессией дают ОДИН `scan_id` и ОДИН оплаченный вызов модели.

## Стражи по исходнику и их испытание

Страж, ни разу не показавший красное, стражем не является. Каждый принимается ВМЕСТЕ с прогоном на
внедрённом дефекте: дефект возвращён → красный, код восстановлен → зелёный, обе строки в квитанции.

| Страж | Что проверяет | Внедряемый дефект |
|---|---|---|
| ADR-001, схема | в JSON-схеме вызова модели нет `calories`, `kcal`, `protein`, `fat`, `carbs`; единственное поле о калорийности — `model_estimate_kcal`. Проверяется именно это МНОЖЕСТВО, а не «нет слова kcal»: иначе страж запретил бы и разрешённое поле | вернуть `calories` в схему |
| ADR-001, путь показа | `model_estimate_kcal` читается ровно в одном месте — при вычислении `discrepancy_ratio` | добавить второе чтение |
| ADR-001, статус | `recognition` без единой ссылки на `food_item` не может стать `done` → `refused(no_food_matched)` | разрешить `done` при нуле ссылок |
| ADR-005 | строка `openfoodfacts` не встречается ни в коде, ни в окружении | добавить вызов OFF |
| ADR-007 | запуск без ЛЮБОЙ из трёх переменных потолка даёт ненулевой код и называет незакрытый вызов — ТРИ отдельных прогона, потому что проверка одной переменной зеленеет при отсутствующей второй | подставить дефолт вместо отказа |
| порядок операций | перестановка «квота ↔ вызов модели» и «подпись ↔ разбор `initData`» роняет тест | поменять шаги местами |

## Тесты не ходят в интернет

Поставщик модели вызывается ЧЕРЕЗ адаптер; в тестах и на стенде по умолчанию работает
детерминированный фейк (DEC-A-009: ключа `ANTHROPIC_API_KEY` в окружении нет). Фейк отдаёт ответы по
схеме, включая случаи `confidence = 0,59`, `confidence = 0,60`, пустой список ингредиентов, нарушение
схемы, таймаут и 5xx. Живой режим включается ключом в `.env` и помечается в отчёте отдельно: прогон
без ключа не объявляется живым смоуком.

USDA FoodData Central в пользовательском пути не вызывается вовсе — база импортируется заранее,
поэтому тесты распознавания от доступности чужого сервиса не зависят.

У КАЖДОГО из 26 `SC-US-nnn-k` есть именованный сценарий, слой и алгоритм — таблица в
`docs/Refinement.md` §Test Cases. Именованный сценарий для шестой части критериев выглядит как
трассировка целиком, поэтому таблица проверяется на полноту, а не на наличие примеров.
Строки со слоем `конкурентный` последовательным прогоном не закрываются ни при каких условиях.

## Что считается зелёным

- Отсутствующая, пропущенная, недоступная проверка и код возврата 2 — НЕ зелёный результат.
  Код `2` означает «проверка не выполнена» и никогда «всё в порядке».
- Мок вместо PostgreSQL не устанавливает поведение ограничения и блокировки: конкурентность и
  уникальность проверяются на настоящей базе.
- Измерения NFR-PERF-001 (≤ 6 с p95) и NFR-PERF-002 (≤ 1 с) снимаются на РАЗВЁРНУТОМ стенде по
  адресу, который выдало развёртывание, а не на локальной машине и не по `localhost`.
- В квитанции фичи: точная ревизия, фактически выполненные команды, коды возврата и то, что осталось
  непроверенным с причиной. План тестов за результат не выдаётся.
