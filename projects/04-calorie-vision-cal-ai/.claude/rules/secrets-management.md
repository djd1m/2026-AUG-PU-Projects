## Какой секрет какому сервису

Минимальная привилегия здесь проверяема: сервис, которому нечем позвать модель, её не позовёт.

| Секрет | `api` | `recognizer` | `web` | Почему |
|---|---|---|---|---|
| `ANTHROPIC_API_KEY` | нет | **да** | нет | модель зовёт только `recognizer` (`Architecture.md`, Component Breakdown: «`api` не вызывает модель сам») |
| `TELEGRAM_BOT_TOKEN` | **да** | нет | нет | из него производится секрет для HMAC `initData`; проверка выполняется в `api`, не во фронте |
| `N4_DB_APP_PASSWORD` | да | да | нет | `web` не ходит в БД напрямую |
| `S3_ACCESS_KEY` / `S3_SECRET_KEY` | да | да | нет | `api` кладёт оригинал и выдаёт presigned-URL, `recognizer` читает и пишет нормализованную копию |
| `N4_STORAGE_ROOT_PASSWORD` | нет | нет | нет | только у сервиса `storage`; приложение работает под отдельной парой ключей |

`web` не имеет ни одного секрета вызова наружу. Это не стиль, а инвариант: он проверяется списком
`environment:` сервиса `web` в `docker-compose.yml`.

## Только окружение, никаких значений в git

- В репозиторий попадают ТОЛЬКО имена переменных и безопасные примеры — `.env.example`. Значения
  живут в `.env` вне git (`.gitignore`) и создаются заново для каждого окружения.
- Секреты не попадают в образ: `.dockerignore` исключает `.env` и `.env.*`, `COPY . .` без него
  утащил бы их в слой.
- Не логировать никогда: ключ модели, токен бота, полное значение `initData`, сырой токен cookie,
  полный (не усечённый) IP-адрес, байты фото, содержимое дневника целиком.
- Перед приложением доказательства к квитанции вывод команд редактируется. Наличие переменной
  проверяется по ИМЕНИ, без печати значения.

## Отсутствующий секрет — отказ, а не дефолт

Пустая переменная не означает «ограничений нет» и не означает «возьмём разумное значение».

- ТРИ потолка модели — `N4_SCAN_LIMIT_USER`, `N4_SCAN_LIMIT_DAY`, `N4_ESCALATION_LIMIT_DAY` —
  обязательны. Отсутствие ЛЮБОГО валит запуск `api` и `recognizer` ненулевым кодом с сообщением,
  называющим незакрытый вызов (ADR-007). Проверяется ТРЕМЯ отдельными прогонами: проверка одной
  переменной зеленеет при отсутствующей второй.
- `APP_ORIGIN` дефолта не имеет по построению: он определяет КАЖДУЮ выдаваемую наружу ссылку, и
  тихий `http://localhost:3000` сделал бы все выданные адреса нерабочими при зелёных тестах
  (`silent-fallbacks.md`, заслужено проектом 01). В compose объявлен как `${APP_ORIGIN:?…}`.
- В `docker-compose.yml` каждый секрет и каждый потолок объявлен формой `${VAR:?текст}`, а не
  `${VAR:-значение}`: вторая форма превращает «не настроено» в «настроено неверно и молча».
- Исключение ровно одно и оно названо: ХОСТОВЫЕ ПОРТЫ (`N4_EDGE_PORT`, `N4_WEB_PORT`,
  `N4_COMPOSE_PROJECT`) объявлены как `${VAR:-default}` — это требование
  [`port-conflicts-local.md`](../../../../.claude/rules/port-conflicts-local.md), и ошибка в них
  ломает запуск громко, а не отдаёт наружу неверные данные.

## Ключа Anthropic на этой машине нет — и это записано, а не обойдено

DEC-A-009: `ANTHROPIC_API_KEY` в окружении VPS отсутствует. Следствие для кода: поставщик модели
скрыт за адаптером, по умолчанию работает детерминированный фейк, живой режим включается ключом.
Следствие для отчётности: прогон без ключа помечается «живое распознавание не выполнено: нет ключа»
и НЕ объявляется смоуком. Имитация живого прогона хуже его отсутствия — она закрывает вопрос,
не ответив на него.

## Ротация и компрометация

- У каждого секрета своё независимое значение. Один ключ на два назначения означает, что ротация
  одного ломает второе, и потому не выполняется никогда.
- Ротация ключа модели: новый ключ в окружение, перезапуск `recognizer`, отзыв старого в консоли
  поставщика. Незавершённые задания не теряются — `recognition` это строка БД, а не брокер (ADR-003).
- Ротация токена бота инвалидирует все ранее выданные `initData`; пользователи проходят вход заново.
  Аккаунты и дневники при этом не трогаются: связь идёт по `telegram_user_id`.
- Пароли БД и ключи MinIO меняются вместе с перезапуском зависимых сервисов; `db` и `storage` портов
  не публикуют, поэтому окно доступа ограничено сетью compose, а не интернетом.
- При подозрении на утечку: отозвать ключ у поставщика ПЕРВЫМ действием (счёт выставляют чужие
  действия и откатить его нечем), затем сверить расход по журналу
  `/var/log/tarelka/model-spend.jsonl` и по консоли поставщика.
