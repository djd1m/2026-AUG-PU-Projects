# Навигатор фич N4 «Тарелка»

`.claude/feature-roadmap.json` следует канонической схеме из корневой
`../../../../../.claude/commands/next.md` — она единственная, и здесь не переписывается. Работать по
роадмапу вместе с `docs/Specification.md` (какие `FR`/`NFR` закрывает фича) и
`docs/validation-report.md` (что уже проверено и с какими оговорками).

## Выбор следующей фичи

1. Продолжать `in_progress` только если это подтверждает квитанция прогона или указание владельца.
2. Среди `next` сортировать по приоритету `mvp > high > medium > low`, затем по порядку зависимостей.
3. `planned` становится `next`, когда КАЖДАЯ запись `depends_on` имеет статус `done` и не осталось
   блокеров. Завершённость не выводится из наличия плана и не выводится из ожидаемого пути файла.
4. Блокированные показывать вместе с явным блокером.
5. Показывать не больше трёх ограниченных действий и называть связывающие документы и `FR`.

Роадмап MVP линеен по зависимостям: `foundation` → `scan-pipeline` → `source-and-correct` →
`consent-and-telegram-auth` → `diary-and-streak` → `share-card-and-growth-events` →
`partner-codes-and-cabinet` → `pro-interest-and-limits-ui`. Параллелить можно только внутри фичи,
между разными файлами и с одним писателем на файл.

## Смена статуса

- `planned → next`: все зависимости `done`, внешние предпосылки названы и подтверждены.
- `next → in_progress`: реализация действительно началась, известен прогон и исполнитель.
- `in_progress → done`: обязательные проверки фичи прошли на точной ревизии, ревью закрыто.
  Для этого проекта «обязательные» включают конкурентные прогоны, если фича трогает квоту, аренду
  или атрибуцию, и прогон стража на внедрённом дефекте, если фича вводит страж.
- любой → `blocked`: записать блокирующее решение или зависимость, не выдумывая идентификатор фичи.

Отмечая `done`, обновлять зависимые записи только если ВСЕ их зависимости выполнены. Внешние и
владельческие блокеры не снимать. Доказательство писать в описание фичи только когда существует
реальный путь и ревизия.

## Поле `complexity` и локальный роутер сложности — разные вопросы

`complexity` в роадмапе — поле пакетной схемы с закрытым набором `simple | medium | complex`
(соответствует тирам S / M / L). Это АПРИОРНАЯ подсказка по объёму, записанная до того, как появился
дифф.

Тир конкретного изменения решает локальный роутер по фактическому набору файлов:

```bash
bash ../../scripts/complexity-router.sh            # по незакоммиченным изменениям
bash ../../scripts/complexity-router.sh --staged   # перед коммитом
```

`0` — тир T/S/M, идти напрямую · `1` — **L или XL, нужен полный цикл `/feature`** · `2` — проверка
НЕ выполнена, разбираться, а не считать тиром T
([`complexity-router.md`](../../../../../.claude/rules/complexity-router.md)). У тира XL в пакетной
схеме представления нет вовсе: `scan-pipeline` записан как `complex`, но по локальной таблице он XL
— трогает деньги. Расхождение названо здесь намеренно, чтобы «complex» не читалось как «L, значит
без остановки у владельца».

## Кандидаты контролируемых пар EXP-N4-001

Эксперимент [`2026-09-12-n4-profile-ab.md`](../../../../../docs/development/telemetry/experiments/2026-09-12-n4-profile-ab.md)
требует две фичи тира M, реализуемые ДВАЖДЫ от одной спецификации: плечо A (`claude-opus-5`) в
worktree `wt-a-<slug>`, плечо B (`claude-sonnet-5`) в `wt-b-<slug>`, разные RUN_ID, без общих
квитанций. Кандидаты, помеченные `complexity: medium`:

| Фича | Почему подходит парой |
|---|---|
| `diary-and-streak` | ограниченный набор файлов, ни одного платного вызова наружу, приёмка из шести названных `SC-US-005-*`/`SC-US-006-*`, арифметика и закрытые перечисления проверяются unit-слоем — два прогона сравнимы по стоимости и времени |
| `share-card-and-growth-events` | та же форма: сборка на сервере, fail-closed бейджа, пять типов `growth_event`; внешних платных вызовов нет, приёмка из `SC-US-007-*` |

Остальные MVP-фичи распределяются чередованием по порядковому номеру: нечётный → плечо A, чётный →
плечо B; тир записывается ковариатой. §8 эксперимента заполняется из этого роадмапа после Phase 3 и
до первой фичи — иначе распределение перестаёт быть предрегистрацией.

## Чего этот навык не делает

Не устанавливает команды и хуки: `/next`, `/go`, `/run`, `/feature`, `/plan` живут в корневой
`.claude/` и здесь не дублируются. Сам проектный toolkit — метаданные загрузки: он не отмечает
готовой ни одну продуктовую фичу. На момент записи реализация не начиналась, и все восемь фич
находятся в состоянии `next` либо `planned`.
