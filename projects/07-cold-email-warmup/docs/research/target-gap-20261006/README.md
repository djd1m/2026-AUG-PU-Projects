# N7 против цели: unlimited ящики, авто-прогрев, AI-ответ <5 минут

Проверка 2026-10-06. Три агента отдельно проверили исходники N7, официальный
benchmark конкурентов и архитектурный разрыв. Координатор сопоставил результаты.
Код N7 не менялся; этот документ не расширяет автоматически утверждённый scope.

**N7 сейчас — принятый локальный MVP, но указанное продуктовое обещание не выполняет.**
Отчёты о локальной приёмке не подтверждают production, живую почту или AI.

| Требование | Реальное состояние | Что отсутствует |
|---|---|---|
| Неограниченные ящики | Free: 3, TEST Team: 10 на tenant; создание сверх лимита даёт 409 | Отсутствие малого тарифного потолка и измеренная ёмкость подключения/активной работы |
| Автоматический прогрев | Opt-in pool и шаблонный обмен через local sink/fixture | Реальные SMTP/IMAP, постоянно работающий dispatcher, покрытие участников и live-пилот |
| AI-ответ быстрее пяти минут | AI-ответов нет; входящий ответ прекращает цепочку | Intent/context/LLM/draft, approval или отдельное разрешение автопилота, безопасная отправка и end-to-end измерение |

## Важные найденные ограничения

- `src/billing/plans.ts` действительно ограничивает число mailbox rows: 3/10.
  Это отдельное ограничение от ежедневной общей квоты отправки mailbox, максимум 30.
- `src/dispatch/worker.ts` выполняет один pool tick и один claim/submit, затем выходит.
  Compose не содержит постоянного dispatch worker; есть только opt-in local poll loop.
  Этот аудит проверял конфигурацию, а не фактические процессы на сервере.
- `PoolStore.tick` повторно выбирает первую доступную межтенантную пару. При
  сохранённой eligibility и свободной квоте повтор того же pair/day конфликтует,
  но к следующей паре не переходит. Равномерное участие всего пула не обеспечено
  этой ветвью; это вывод по коду, не выполненный нагрузочный тест.
- Poll tick обрабатывает один ящик; интервал 30 секунд не означает проверку каждого
  ящика каждые 30 секунд. UID rescan и ошибки требуют отдельных состояний/восстановления.
- Персонализация N7 — подстановка полей, а reply detector — остановка цепочки.
  Ни то ни другое не является AI-ответом. AI replies явно исключены из принятого PRD.
- Существующие p95 около 85–109 мс относятся к чтению API кабинета и исключают
  provider I/O; к задержке AI-ответа они неприменимы.

## Сопоставление с конкурентами

Официальные страницы подтверждают unlimited connected accounts при отдельных
квотах отправки/контактов и условиях прогрева. Это не неограниченная физическая
мощность и не отмена ограничений почтового провайдера.
Instantly прямо публикует обещание ответа менее пяти минут, но проверенная страница
не определяет измеримый договорный SLA. Источники и условия: [benchmark.md](benchmark.md).
Число $40M+ ARR из запроса не проверялось и не является критерием готовности N7.

## Предлагаемый порядок развития

Это варианты следующего плана, не автоматически активированные фичи:

1. Зафиксировать новый scope: unlimited означает правила подключений, а «ответ» —
   черновик, одобренный ответ либо отправка автопилотом; задать конечную проверяемую нагрузку.
2. Ввести реальные connection/SMTP/IMAP capabilities с сохранением N7 tenant,
   TLS/endpoint pinning, consent, quota, final stop fence и unknown-delivery правил.
3. Добавить постоянный dispatcher и распределение warmup по участникам; проверить
   небольшой разрешённый пул и реальные наблюдения, не обещая inbox placement.
4. Получать bounded body/thread, классифицировать входящие, формировать версионированный
   AI draft и передавать его на одобрение. Старый stop-on-reply остаётся обязательным.
5. Для автопилота добавить отдельное явное полномочие и reply-purpose job; модель
   не отправляет SMTP напрямую и не обходит opt-out/квоты ради скорости.
6. Проверить масштабы и SLO: queue age, fairness, poll freshness, DB lock wait,
   memory и реальные p95/p99 полного пути, включая просроченные/незавершённые события.

Время arrival→observed, observed→draft и approval→SMTP accepted измеряется отдельно.
Для обещания отправленного ответа нужна arrival→SMTP accepted метрика; SMTP accepted
ещё не доказывает доставку. Предлагаемое p95 <300 секунд — новая цель для проверки,
не текущий результат и не обещание для каждого сообщения. Расписание, нагрузка,
denominator и исключения фиксируются до пилота. Ручное ожидание не прячется в SLA draft.

Детальные этапы и SLO: [target-gap.md](target-gap.md). Донорские CSV/UI-фрагменты из
[предыдущего анализа](../instantly-donors-20261006/README.md) могут помочь onboarding,
но не закрывают этот разрыв; готового безопасного AI/mail runtime среди доноров нет.

## Пределы и телеметрия

Статический аудит и чтение официальных страниц; новых runtime/E2E/build/tests,
почты, LLM API, платных действий или развёртывания не было. Старые результаты
локальных проверок не выдаются за новые. Производство роликов остаётся на паузе.
Профиль: bounded read-only swarm, без написания кода. Native model/usage/cost
не раскрыты. Измерены 184 с capability review и 260 с architecture review;
начало всей задачи отдельно не измерено. Квитанция: [run.json](run.json).
