# Specification — Грелка (N7 · Instantly-клон)

Дата: 2026-10-07. Источник требований: [PRD.md](PRD.md), discovery
[product-discovery-brief.md](product-discovery-brief.md), [CJM_Variants.md](discovery/CJM_Variants.md).
Формат ключей: `FR-<SLUG>-<nnn>` — заголовок уровня 3; сценарии — `SC-<US-id>-<n>` в Gherkin.
Приоритеты: Must (неделя) / Should (v1.0) / Could (v2.0).

## 1. Executive Summary

Грелка — веб-сервис холодной email-рассылки с сетевым прогревом: подключение собственных ящиков по
SMTP/IMAP, общий пул переписки участников (вход по явному согласию), доказуемый health-дашборд,
кампании с ротацией и жёстким антиспам-контуром, flat-тарифы в ₽ и $, партнёрская атрибуция.
Семь требований роста из Phase 0 прослежены в §5.

## 2. Роли и границы

- **Владелец (S1, основной)** — соло-продавец: подключает домён/ящики, греет, запускает кампании.
- **Агентство (S2, канал)** — регистрируется по партнёрскому коду, ведёт кампании клиентов.
- **Адресат** — человек в списке: получает письма с отпиской, его жалобы приводят к паузе.
- **Платформа** — очередь, пул, лимиты, хранение секретов, публичная статистика.

Anti-persona: спамер массовых рассылок — против него режим fail-closed (§4.8, §4.4).

## 3. User Stories

### US-001: Аккаунт

US-001: As a владелец, I want to зарегистрироваться и войти, So that мои ящики и кампании
принадлежат мне.

Acceptance Criteria:
[SC-US-001-1]
Given открытая форма регистрации
When вводится валидный email и пароль ≥ 8 символов и подтверждение клика
Then создаётся аккаунт, открывается онбординг, пароль хранится только как Argon2-хэш

[SC-US-001-2]
Given аккаунт существует
When вводится корректная пара email+пароль
Then выдаётся сессия (access ~15 мин, refresh ~30 дней), повторный выход/вход работает

### US-002: Домен

US-002: As a владелец, I want to привязать домен и видеть статус SPF/DKIM/DMARC, So that я знаю,
что авторизация настроена до рассылки.

Acceptance Criteria:
[SC-US-002-1]
Given домен введён
When запускается проверка DNS
Then показываются статусы SPF/DKIM/DMARC из резолвера, каждая запись — с датой камеры проверки

[SC-US-002-2]
Given DKIM-запись отсутствует
When домен сохраняется
Then привязка сохраняется со статусом warning, но запуск кампании блокируется с текстом причины

### US-003: SMTP/IMAP-ящик

US-003: As a владелец, I want to подключить ящик по SMTP/IMAP, So что сервис может отправлять и
читать почту от моего имени.

Acceptance Criteria:
[SC-US-003-1]
Given форма добавления ящика
When вводятся хост/порт/логин/App Password и запускается живая проверка
Then открываются TLS-коннекции (465 implicit или 587 STARTTLS), IMAP LOGIN успешен, ящик
сохраняется со статусом verified

[SC-US-003-2]
Given SMTP или IMAP проверка не прошла
When сохранение подтверждается
Then ящик сохраняется в статусе unverified с диагнозом шага и НЕ участвует ни в пуле, ни в кампаниях

[SC-US-003-3]
Given ящик verified
When секреты сохраняются
Then в БД лежит только AES-256-GCM-конверт секретов, ключ конверта зашифрован мастер-ключом из env,
в логи секрет или его фрагменты не попадают

### US-004: Общий пул прогрева

US-004: As a владелец, I want to включить свои ящики в общий пул прогрева, So что сетевая
переписка наращивает репутацию моего домена.

Acceptance Criteria:
[SC-US-004-1]
Given у аккаунта есть verified ящик и галочка согласия пустая
When я включаю участие в пуле (отдельная явная галочка с текстом «вам будут приходить
прогрев-письма от участников сети»)
Then membership создаётся, факт согласия с текстом и версией сохраняется в аудите

[SC-US-004-2]
Given membership активен
When подходит очередь прогрева дня
Then система строит ramp-план на ящик: день 1 — 2 письма, далее +2 в день, объём рандомизируется,
план не превышает дневной лимит тарифа

[SC-US-004-3]
Given ramp-план дня построен
When разыгрываются пары отправитель→получатель
Then обе стороны — участники пула, отправитель ≠ получатель и не тот же домен, приоритет —
межаккаунтные пары; если активных партнёров меньше двух ящиков, плана нет

[SC-US-004-4]
Given запланирована пара прогрева и слот наступил
When очередь выполняет отправку
Then письмо с человекочитаемым маркером прогрева уходит через SMTP ящика-отправителя с
идемпотентным ключом, при повторе job не дублируется, действие фиксируется в send_log

### US-005: Health-дашборд (момент ценности)

US-005: As a владелец, I want to видеть, как растёт репутация моего домена, So that я понимаю,
что рассылку можно запускать.

Acceptance Criteria:
[SC-US-005-1]
Given у домена есть хотя бы один verified ящик и события отправок
When открывается дашборд
Then видна кривая score по дням (14/30 дней), текущие: доставляемость, спам-рейт по жалобам,
число участников пула

[SC-US-005-2]
Given база сети мала (меньше порога критмассы)
When открывается дашборд пула
Then отображается честная метка «сеть разогревается: N участников», прогресс не приукрашивается

### US-006: Загрузка списка

US-006: As a владелец, I want to загрузить список адресов с экранированием стоп-листа, So что
кампании не пошли в серые адреса.

Acceptance Criteria:
[SC-US-006-1]
Given CSV со строками адресов
When импорт выполняется
Then формат валидируется, роли (abuse@, postmaster@, noc@ и т.п.) отсеиваются на import-этапе с
пометкой причины, дубли склеиваются

[SC-US-006-2]
Given адрес сущствует в глобальном стоп-листе
When импорт подтверждается
Then адрес не попадает в получатели, импорт показывает точное число отсечённых с причиной
stop-list

### US-007: Цепочка кампании

US-007: As a владелец, I want to собрать цепочку писем с переменными, ротацией и лимитами, So
that рассылка похожа на руку продавца, а не на бластер.

Acceptance Criteria:
[SC-US-007-1]
Given кампания создаётся
When последовательность шагов задаётся (шаг 1 день 0, шаг 2 +3 дня, …, стоп при ответе)
Then каждый шаг имеет шаблон с переменными из полей списка, подстановки валидируются на превью

[SC-US-007-2]
Given в кампании несколько ящиков
When шаг отправляется
Then ротация выбирает ящик из пула кампании с учётом израсходованных дневных лимитов

[SC-US-007-3]
Given дневной лимит ящика исчерпан
When очередь подходит к отправке
Then слот переносится на следующий день, адресат не теряет шаг, об отправке не дублируется

### US-008: Запуск и слив кампании

US-008: As a владелец, I want to запустить кампанию явной кнопкой и видеть события, So что
отправки от моего имени происходят только с моего подтверждения.

Acceptance Criteria:
[SC-US-008-1]
Given кампания готова (список, цепочка, ящики verified, DNS ok)
When нажимается «Запустить: это действие от имени моих ящиков»
Then согласие с текстом кампании сохраняется в аудите, pre-flight пройден, кампания переходит в
launched, письма идут по расписанию слотов

[SC-US-008-2]
Given кампания launched
When письмо ушло
Then в журнале: идемпотентный ключ отправки, ящик, слот, статус (queued → sent / bounced), время

[SC-US-008-3]
Given адресат ответил на письмо
When IMAP-входящий обрабатывается
Then сохраняются ТОЛЬКО метаданные ответа (от кого, когда), цепочка для этого адресата
останавливается, дальнейшие шаги не отправляются

### US-009: Тарифная оплата

US-009: As a владелец, I want to перейти на Base/Pro и платить по контуру (₽/ЮKassa, $/Stripe),
So that лимиты растут и платёж был оформлен правильно.

Acceptance Criteria:
[SC-US-009-1]
Given владелец выбрал тариф
When создаётся сеанс оплаты (ЮKassa create payment / Stripe Checkout)
Then возвращается URL платёжного сеанса с идемпотентным ключом, при отмене объект остаётся пустым

[SC-US-009-2]
Given провайдер прислал webhook
When обрабатывается событие и подпись/полномочие проверена
Then подписка/доступ продлевается по статусу события; повторное и неавторизованное событие игнорируется

### US-010: Партнёрская атрибуция

US-010: As a агентство (S2), I want to иметь персональный код, So что привинченный клиент
видится в кабинете, и комиссия копилась от его фактической оплаты.

Acceptance Criteria:
[SC-US-010-1]
Given ссылка с кодом
When открывается лендинг и создаётся аккаунт
Then атрибуция сохраняется ДО оплаты (cookie/параметр, срок 90 дней), поле «кто привёл» отображается

[SC-US-010-2]
Given код в ссылке введён вручную и введён ВЕРНОГО формата, но не существует
When аккаунт создаётся
Then атрибуция НЕ сохраняется и не фолбэкится на cookie

[SC-US-010-3]
Given приведённый оплатил
When webhook подтверждает платеж
Then комисионное событие создаётся у партнёра; повторная оплата того же счёта не создаёт события

[SC-US-010-4]
Given пользователь регистрируется по ссылке со СВОИМ собственным кодом (same email/account/cookie)
When создаётся атрибуция
Then self-referral отсекается: attribution не создаётся (valid=false невозможен)

[SC-US-010-5]
Given страница приглашения по коду партнёра
When открывается лендинг
Then текст приглашения явно раскрывает факт партнёрского вознаграждения (чеклист допустимости №4:
реферальная программа — с раскрытием, не амбассадорская маскировка)

### US-011: Отписка адресата

US-011: As a адресат, I want to отписаться в один клик, So что письма от этой платформы не
приходят больше.

Acceptance Criteria:
[SC-US-011-1]
Given письмо кампании/прогрева у адресата
When адресат жмёт List-Unsubscribe (RFC 8058, HTTPS POST) или ссылку в футере
Then запрос принимается мгновенно и обрабатывается очередью

[SC-US-011-2]
Given запрос отписки принят
When очередь обрабатывает событие (SLA 48 часов)
Then адресат попадает в глобальный стоп-лист, и все ящики платформы учитывают его
при следующей отправке

### US-012: Жалобы

US-012: As a владелец, I want to знать о спам-жалобах и видеть автопаузу, So that моё домен не
сгорел по чужой вине или по моей неточности.

Acceptance Criteria:
[SC-US-012-1]
Given входящий фидбек-loop или признак жалобы обнаружен
When обрабатывается входящий
Then событие complaint записывается с адресатом и кампанией

[SC-US-012-2]
Given уровень жалоб кампании превысил порог
When следующая отправка планировалась
Then кампания автопаузит с уведомлением владельца; возобновление — только по явному действию


## 4. Функциональные требования (ключи)

### FR-AUTH-001
Регистрация и вход по email+пароль (Argon2); обязателен подтверждённый email до любых действий
от имени ящиков. Priority: Must. Traces: US-001 (SC-US-001-1, SC-US-001-2).
Реализация — доноры: `03a-affiliate-rewardful/apps/web/src/lib/auth/` (модуль аутентификации) и
сессионные хелперы `01-testimonials-senja/apps/web/src/lib/login.ts` + `current-session.ts`
(активация под Fastify — см. Architecture §Reuse).

### FR-AUTH-002
Сессии: access ~15 мин + refresh ~30 дней, инвалидация logout на refresh-результате. Priority:
Must. Traces: US-001 (SC-US-001-2).

### FR-DOMAIN-001
Привязка домена с DNS-проверкой SPF/DKIM/DMARC из резолвера, статусы с датой камеры; запуск
кампании требует DKIM ok. Priority: Must. Traces: US-002 (SC-US-002-1, SC-US-002-2).

### FR-MAILBOX-001
Добавление ящика (host/port/login/App Password, 465 implicit TLS либо 587 STARTTLS) с живой
SMTP+IMAP проверкой. Priority: Must. Traces: US-003 (SC-US-003-1, SC-US-003-2).

### FR-MAILBOX-002
Статусы ящика: unverified → verified → paused → disabled; только verified участвует в пуле и
кампаниях. Priority: Must. Traces: US-003, US-008.

### FR-MAILBOX-003
Секреты (App Password) — AES-256-GCM envelope в БД: ключ конверта случайный, шифруется
мастер-ключом из env; секреты никогда не логируются. Priority: Must. Traces: US-003
(SC-US-003-3).

### FR-MAILBOX-004
Любая отправка ОТ ИМЕНИ ящика требует записи явного согласия: у пула — своя галочка (US-004), у
кампании — при запуске (US-008). Прецедент из постановки: действие от имени пользователя без его
ответа отдельным согласием — прямая юридическая проблема. Priority: Must. Traces: US-004, US-008.

### FR-POOL-001
Единый общий пул участников: переписка прогрева возможна ТОЛЬКО между подтверждёнными
memberships; вход/выход — по явному согласию, выход прекращает новые прогрев-письма на этот ящик.
Priority: Must. Traces: US-004 (SC-US-004-1).

### FR-POOL-002
Ramp-план на участника: день 1 — 2 письма, далее +2 в день, объём рандомизируется, потолок —
дневной лимит тарифа; план не выходит за сутки. Priority: Must. Traces: US-004 (SC-US-004-2).

### FR-POOL-003
Разыгрыш пар: обе стороны — участники; отправитель ≠ получатель и разные домены; межаккаунтные

пары приоритет; при малом числе участников плана не вывозится. Priority: Must. Traces: US-004
(SC-US-004-3).

### FR-POOL-004
Публичная агрегированная статистика сети (страница и read-only API): число ящиков в пуле,
суммарный прогресс health; без доменов, ящиков и личных данных. Priority: Must. Traces: FR-GROWTH-005.

### FR-POOL-005
Честная метка «сеть разогревается: N участников» пока база меньше критмассы — отображается и при
малых числах не приукрашивается. Порог критмассы: 25 ящиков (метрика недели, решение владельца
2026-10-07; конфигурация POOL_CRITICAL_MASS). Priority: Must. Traces: US-005 (SC-US-005-2);
FR-GROWTH-001.

### FR-WARMUP-001
Прогрев-письма содержат человекочитаемый маркер прогрева и подписанный текст; чужой адресат не
получает прогрев-переписку без согласия на участие. Priority: Must. Traces: US-004;
FR-GROWTH-006, FR-GROWTH-005. Примечание: маркер [H] — практика индустрии, подтверждение в фазе 1.5.

### FR-WARMUP-002
Отправка через SMTP с идемпотентностью (кнопка очереди — ключ попытки), повторы без дубля письма;
ретраи только по сетевым кодам. Priority: Must. Traces: US-008 (SC-US-008-2).

### FR-WARMUP-003
Прогрев-переписка уважает те же дневные лимиты и очереди, что и кампании; полюс прогресса по
соблюдение декларированных правил видно владельцу в мониторе. Priority: Must. Traces: US-004, US-007.

### FR-CAMP-001
Кампания: CSV-список, шаблон с переменными полей, цепочка шагов со шаговыми слотами и стопом при
ответе. Priority: Must. Traces: US-006, US-007 (SC-US-007-1).

### FR-CAMP-002
Ротация: выбор ящика из пула кампании по квотам и остаткам дня. Priority: Must. Traces: US-007
(SC-US-007-2, SC-US-007-3).

### FR-CAMP-003
Pre-flight перед запуском: статусы DNS, ящиков verified, стоп-листовых отсечений, квот тарифа,
явное согласие. Если список содержит RU-адресатов — обязательное подтверждение владельцем
предупреждения: «рекламные письма по РФ — только с согласия адресата (ст. 18 38-ФЗ)»; для
международных кампаний — проверка per campaign (CAN-SPAM/GDPR, открытый вопрос Q-004).
Priority: Must. Traces: US-008 (SC-US-008-1).

### FR-CAMP-004
Запуск — явная кнопка с формулировкой действия от имени владельца (постановка: согласие на
действие от имени — отдельное, явное). Priority: Must. Traces: US-008 (SC-US-008-1).

### FR-CAMP-005
Отправка jobs хранит идемпотентный ключ и полный статус-журнал; письма адресату не дублируются
на неавторизованных повторах job. Priority: Must. Traces: US-008 (SC-US-008-2).

### FR-CAMP-006
Статистика кампании: sent, bounced, complained, reply (METADATA only), сохраняемая по событиям.
Priority: Must. Traces: US-008, US-005.

### FR-SEC-001
Глобальный стоп-лист: ручные онлайн-отписки, RFC 8058 события, роли при импорте (abuse@,
postmaster@, noc@, security@ и т.п.), ответные «стоп»; все отправки кампаний и прогрева
проверяются на него до выхода. Priority: Must. Traces: US-006, US-011 (SC-US-011-2).

### FR-SEC-002
Отписка обрабатывается очередью с SLA ≤ 48 часов (мгновенный приём ответа); источник события
(версия согласия, момент, канал) фиксируется. Priority: Must. Traces: US-011
(SC-US-011-1, SC-US-011-2).

### FR-SEC-003
Жалобы (complaint-события) → автопауза кампании с уведомлением и запретом повторного запуска без
 editing списка владельцем. Priority: Must. Traces: US-012 (SC-US-012-1, SC-US-012-2).

### FR-SEC-004
Fail-closed потолки: на ящик/день (Free 20, Base 100, Pro 300), на аккаунт/день, почасовой burst;
значения конфигурируются, имеющиеся потолки видны владельцу. Priority: Must. Traces: FR-GROWTH-006,
US-007.

### FR-HEALTH-001
Дашборд: кривая score (14/30 дней), текущие доставляемость, спам-рейт (цель < 0,3 %), участники
пула, доменные предупреждения. Priority: Must. Traces: US-005 (SC-US-005-1).

### FR-HEALTH-002
Score из наблюдаемых событий (авторизация домена, доставленность SMTP, bounce/complaint классы);
никакого «магического» score из прогрева: формула и вклады отображаются. Priority: Must. Traces:
US-005 (SC-US-005-1, SC-US-005-2).

### FR-HEALTH-003
Инбокс-тест (проверочное письмо в свои seed-ящики и фиксация папки по IMAP) — Should (v1.0,
после MVP). Priority: Should. Traces: —.

### FR-BILL-001
Тарифы Free (1 ящик, 1 кампания, 20/день) / Base (5 ящиков, 3 кампании, 100/день, 1 490 ₽ или

потолки отображены прямо (нет слов «unlimited» без числа). Priority: Must (контур подтверждён
владельцем; точные цены — Q-002). Traces: FR-GROWTH-002, FR-GROWTH-004.

### FR-BILL-002
Платёж ₽: ЮKassa API (create payment с идемпотентным ключом, вебхуки на статусы). Priority: Must.
Traces: US-009 (SC-US-009-1, SC-US-009-2).
Реализация — донор: `01-testimonials-senja/apps/web/src/lib/payment.ts` — вебхук-аутентичность
решена там правильно: проверка адреса источника по опубликованным сетям + перезапрос статуса
объекта у самой ЮKassa (ЮKassa подписи webhook не шлёт — см. комментарий донора, ADR-006 N1)

### FR-BILL-003
Платёж $: Stripe Billing (Subscription + webhook события с верификацией подписи). Priority: Must.
Traces: US-009 (SC-US-009-1, SC-US-009-2).
Донора в проектах 01–06 нет (grep по `stripe` пуст) — новая реализация по докам провайдера,
цитаты с датами — Architecture External Dependencies.

### FR-BILL-004
При неоплате/даунгрейде — fail-closed: новые слоты отправки кампании ставятся на паузу, прогрев
остаётся; данные кампаний при блокировке не теряются. Priority: Should. Traces: US-009, FR-GROWTH-002.

### FR-PARTNER-001
Персональные трекируемые коды партнёров и атрибуция ДО платной конверсии (cookie/параметр, 90

Реализация — донор: `03a-affiliate-rewardful/apps/web/src/lib/` (коды/атрибуция Rewardful-клона)

### FR-PARTNER-002
Невалидный явно указанный код не фолбэкится на cookie; self-referral (та же учётка/cookie)

### FR-PARTNER-003
Кабинет партнёра: события комиссий от фактических оплат; вывод средств — вне MVP (вторая неделя,

### FR-PARTNER-004
Страница приглашения по коду прямо раскрывает факт партнёрского вознаграждения (чеклист

## 5. Growth Trace (из Phase 0 — обязательство, не рассказ)

Строки ниже переносят Growth Requirements Seed из
[product-discovery-brief.md](product-discovery-brief.md); каждая реализована или отклонена ЯВНО.
Семенные ключи FR-GROWTH-* — обязательства трассы (не H3-ключи §4/§6); реализуются через
перечисленные FR-ключи раздела 4.

- FR-GROWTH-001 (момент ценности — дашборд health, CTA ровно в момент роста) → реализовано:
  FR-HEALTH-001/002, FR-POOL-005; US-005.
- FR-GROWTH-002 (партнёрская атрибуция до платной конверсии; невалидный код не фолбэкится;
  self-referral отсечена) → реализовано: FR-PARTNER-001/002.
- FR-GROWTH-003 (бейдж на бесплатном тарифе) → реализовано по форме: бейдж «Powered by» ТОЛЬКО на
  публичных поверхностях — публичная страница /pool, публичный снапшот, страница отписки →
  FR-POOL-004; на free обязателен, снятие — платная опция Pro-семейства.
- Частный случай FR-GROWTH-003: бейдж ВНУТРИ писем — отклонено, причина: правила Gmail/Microsoft
  («коммерческий материал в служебных письмах» и жалобы) — бейдж в письме напрямую повышает спам-
  р  риск и ставить его означало бы подтвердить претензию; это противоречит генеральной идее
  «комплаенс by design» (брифе M5, чеклист №7).
- FR-GROWTH-004 (персональные коды партнёров; дашборд: подключение → кампании → оплаты) →
  реализовано: FR-PARTNER-001/003; полный вывод-кабинет — Should (v1.0).
- FR-GROWTH-005 (общий пул прогрева с публичной агрегированной статистикой; вход по явному
  согласию; seed) → реализовано: FR-POOL-001/004, FR-WARMUP-001; seed-план — в PRD §9 R-001.
- FR-GROWTH-006 (антиспам-контур: отписка RFC 8058 ≤48ч, лимиты на ящик/день, глобальный стоп-лист
  с ролями, автопауза жалоб, явное согласие на действие от имени) → реализовано: FR-SEC-001/002/
  003/004, FR-MAILBOX-004, FR-AUDIT-001.
- FR-GROWTH-007 (метрики: прирост пула, conv% раздельно с первого релиза; i в сетевой петле
  отсутствует — вместо него прирост пула и коды партнёров) → реализовано как метрики раздела
  PRD §2.4 («наша БД») и FR-POOL-004; K-фактор в плане не накладывает.

## 6. Нефункциональные требования

### NFR-PERF-001
Ответы API: p99 ≤ 500 мс при 50 одновременных пользователях. Измерение: журнал p99 в
мониторинге (Completion.md).

### NFR-PERF-002
Кампейная отправка: 95 % слотов ухода в заявленные окна ± 5 мин. Измерение: наша БД (слоты vs факт).

### NFR-SEC-001
Секреты: AES-256-GCM envelope; мастер-ключ — env (KEK); доступ к расшифровке — только worker-контур.

### NFR-SEC-002
Исходящие SMTP: только TLS (implicit 465 или STARTTLS 587); plain-канал отклоняется fail-closed.

### NFR-SEC-003
Rate limit API по IP+аккаунту (100 req/min с burst-бюджетом).

### NFR-SCALE-001
Горизонталь: API и workers stateless; состояние — Postgres/Redis, распределённые блокировки в Redis.

### NFR-RELI-001
At-most-once отправка: каждое письмо несёт идемпотентный ключ; повторный job не создаёт
второй копии письма. Измерение: наша БД (send_log, уникальные ключи).

### NFR-PRIV-001
Содержимое входящих писем не хранится: только метаданные (адресат/время/тип); удаление по erasure —
в течение 30 дней.

### NFR-LOC-001
UI и сообщения об ошибках — русский; в тарифных строках — оба контура (₽ и $).
