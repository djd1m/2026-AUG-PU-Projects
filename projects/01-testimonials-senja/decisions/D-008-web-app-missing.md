# D-008: `apps/web` существует только как Dockerfile — исходников нет

**Дата:** 2026-08-26 · **Статус:** ✅ РЕШЕНО (решение принято автономно) · **Приоритет:** блокер запуска

## Развилка

Phase 3 `/start` (интеграция) впервые собирала образы. Выяснилось, что `apps/web` —
это папка из **одного файла**, `Dockerfile`. Ни `package.json`, ни `src/`, ни одной
строки кода. Подтверждение не по впечатлению, а по факту: `apps/web` **отсутствует
в `package-lock.json`** — npm workspaces (`apps/*`) его не видит, потому что видеть
нечего.

Последствие: `docker compose up -d` (то есть `npm run up`, документированный способ
запуска) падает на сборке `web`. Вместе с ним не поднимается `caddy` — у него
`depends_on: web`. Из шести сервисов compose работоспособны четыре.

Отдельно ломается документированный путь миграций. `DEVELOPMENT_GUIDE.md:23` предлагает
`docker compose run --rm web npm run db:migrate` — команда через контейнер, которого
не существует. Миграции применяются, но только в обход этой инструкции.

## Варианты

| Вариант | Плюс | Минус |
|---|---|---|
| A. Сгенерировать Next.js-приложение прямо сейчас | `docker compose up` станет зелёным целиком | Это 13 фич роадмапа (FR-001…008 + growth), а не интеграционная фаза. Phase 3 по `.claude/commands/start.md` — проверка сборки, не разработка продукта |
| B. Сгенерировать пустой скелет с одним `/health` | compose поднимется | Зелёный `up` при отсутствующем продукте — ровно тот класс лжи, против которого написано правило про «сценарий добавлен ≠ требование закрыто» (`p-replicator-known-gaps.md` §3) |
| C. Зафиксировать пробел, довести до зелёного работающую часть, поставить детерминированную проверку | Честное состояние; дефект пойман на самом сильном слое | `npm run up` до реализации `web` остаётся красным |

## Решение: вариант C

Phase 3 существует, чтобы узнать, превратились ли документы в работающее. Ответ по
проекту 01: **инфраструктурный слой — да, продуктовый слой `web` — ещё не написан**.
Скелет ради зелёной галочки этот ответ бы затёр.

`apps/web` пишется в `/run mvp` — там он и стоит в `.claude/feature-roadmap.json`.

## Что сделано вместо генерации

1. Доведены до реально работающего состояния три из четырёх собираемых компонентов
   (см. коммит `532f494`). До Phase 3 **ни один образ не собирался** — дефекты были
   не в `web`, а во всех Dockerfile сразу.
2. Проверка на этот класс дефекта поставлена на **слой 1** (детерминированный скрипт),
   а не на суждение ревьюера — `scripts/check-compose-buildable.sh` **внутри проекта**:
   у каждого сервиса с `build:` в compose должны быть исходники, а не только Dockerfile,
   и ни один Dockerfile не должен запускать `dist/`, которого не собирает.
3. `DEVELOPMENT_GUIDE.md` — команда миграций исправлена на работающую.
4. Заявки в кузницу харнесса (`harness-forge/` в корне репозитория) по этим двум дефектам
   **отложены**: на этой фазе работаем только в папке проекта. Материал для них — раздел
   «Что именно чинилось в Dockerfile» ниже и D-007.

## Что именно чинилось в Dockerfile (все три сервиса)

| Дефект | Почему падало |
|---|---|
| `build: ./services/<имя>` | В монорепо на npm workspaces `package-lock.json` **один, в корне**. `npm ci` без lockfile падает всегда |
| Нет шага сборки, но `CMD ["node","dist/…"]` | `dist/` в `.gitignore` и внутри образа не создаётся → MODULE_NOT_FOUND при старте |
| `npm ci --workspace X` без манифестов остальных | npm сверяет **весь** lock-tree → «Exit handler never called!» |
| Нет `.dockerignore` при `COPY . .` | В образ едут `node_modules`, `tests` и потенциально `.env` |
| `image: minio/minio` | Без тега = `:latest`; через месяц на VPS приедет другой образ |
| `condition: service_started` у transcribe | У сервиса не было HEALTHCHECK — зависимые стартовали до готовности |

## Проверено вживую (не «должно работать»)

- 8 миграций применены на контейнерном Postgres 16; повторный прогон — no-op;
- изоляция арендаторов подтверждена данными: A видит только своё, B — только своё,
  **без контекста аккаунта не видно ничего** (fail-closed); попытка A записать
  audit-событие в проект B → нарушение RLS-политики; UPDATE чужого отзыва → 0 строк;
- граница ролей: `app_authenticated` получает `permission denied` на `commissions`,
  `partner_codes`, `referral_attributions`, `webhook_events`;
- 18/18 тестов `packages/db` и 12/12 `services/worker` на живой БД, включая
  SKIP LOCKED на конкурентных воркерах;
- контейнер `worker` подключается к Postgres и выполняет cleanup-job;
- контейнер `transcribe` — `healthy`, ffmpeg 8.1.2, `GET /health` → 200;
- **граница ADR-005 подтверждена на работающем сервисе**: `POST /transcribe`
  с телом `{text: "перепиши этот отзыв покрасивее"}` → `400 Unrecognized key: "text"`.
  Это FTC-инвариант, проверенный на живом HTTP, а не только юнит-тестом.

## Ограничение проверки в этой песочнице

Полная сборка `docker compose build` здесь не проходит по причине, **не связанной с
проектом**: исходящий HTTPS идёт через прокси с подменой TLS, и внутри build-контейнера
его CA не доверен — `npm ci` падает с `SELF_SIGNED_CERT_IN_CHAIN`, `apk add ffmpeg` —
с `server certificate not trusted`. Это документированное ограничение окружения
(`/root/.ccr/README.md`, раздел «docker build / docker run»).

Чтобы проверка не оказалась пустой, образы собраны из **сгенерированного варианта тех же
Dockerfile** с добавленным CA (сам файл Dockerfile в репозитории не менялся под песочницу
— проверялась его настоящая логика). На VPS, где TLS не подменяется, нужен обычный
`docker compose build`. Временные файлы удалены, CA в контекст сборки не закоммичен.

## Остаточный риск

Логика `apps/web/Dockerfile` (сборка Next.js, `npm run build:widget`) **не проверена
сборкой** — проверять нечего. Её первый настоящий прогон случится, когда появятся
исходники. Контекст сборки у неё уже переведён на корень монорепо заодно с остальными,
но это правка вслепую.
