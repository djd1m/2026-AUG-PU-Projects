> SPARC Phase: **Completion**. Источники: `PRD.md`, `Specification.md`,

## 1. Definition of Done для MVP недели

MVP считается done, когда выполнены оба условия одновременно:

1. Все Must-возможности из PRD §4.1 (FR-001…FR-007) реализованы и проходят acceptance criteria
   из Specification.md.
2. **Метрика недели считается** — число установленных виджетов на внешних доменах не является
   ручным подсчётом, а вычисляется из события `widget_installed` (PRD §6.1: «Критерий
   готовности — метрика недели считается»).

Готовность по фиче — по чек-листу Definition of Done внутри каждого FR в Specification.md
(флажки `[ ]` при каждом FR-GROWTH-00N). Ни один growth-FR не считается done, если его
Definition of Done не закрыт полностью — частичное закрытие (например, тесты есть, а метрика не
инструментирована) не засчитывается.

## 3. Growth Readiness (обязательный раздел)

Контрольный список инструментирования аналитики из Specification.md §4. Правило-предпосылка:
**постфактум эти события не восстанавливаются** — если событие не пишется с первого релиза,
данные за неделю потеряны безвозвратно, и это нельзя исправить ретроактивным патчем.

| Событие | Инструментировано? | Что проверяет |
|---|---|---|
| `invite_shown` | [ ] | Share-CTA показан ровно в момент первого рендера виджета на внешнем домене (FR-GROWTH-001), НЕ на онбординге |
| `invite_sent` | [ ] | Владелец подтвердил шеринг явным действием |
| `badge_impression` | [ ] | Показ badge на внешнем домене, ровно 1 раз за загрузку страницы |
| `badge_click` | [ ] | Клик по badge с UTM-метками источника |
| `signup_from_badge` | [ ] | Регистрация, пришедшая по клику на badge |
| `widget_installed` | [ ] | Домен + первый успешный рендер — это метрика недели, не подменять другим событием |
| `referral_attributed` | [ ] | Атрибуция партнёра — источник (`cookie` / `promo_code`) записан явно |

**Считается ли метрика недели?** Да только если `widget_installed` пишется атомарно на первом
успешном рендере на конкретном домене, и по нему можно посчитать **уникальные домены**, а не
количество рендеров. Подсчёт рендеров вместо доменов даёт завышенное и бессмысленное число.

**Раздельность `i` и `conv%`:**
- `i` (invites per user) = число `invite_sent` / число владельцев с ≥ 1 виджетом.
- `conv%` = регистрации из badge / клики по badge = `signup_from_badge` / `badge_click`.
- Оба должны считаться из **разных** событий и **не** сворачиваться в одно составное число до
  того, как оба посчитаны раздельно — иначе K-factor (`i × conv%`) теряет диагностическую
  ценность: нельзя понять, какое из двух чисел упало.

**Anti-fraud покрытие (обязательно для каждого growth-FR):**
- [ ] Шеринг не публикует ничего от имени владельца без явного подтверждения (FR-GROWTH-001 `@security`)
- [ ] Self-referral и повторная доставка вебхука не создают дублирующих начислений (FR-GROWTH-002 `@security`)
- [ ] Badge нельзя отключить клиентски или через параметр API на free (FR-GROWTH-003 `@security`)
- [ ] Накрутка регистраций по партнёрскому коду детектируется и помечается `suspected_fraud` (FR-GROWTH-004 `@security`)
- [ ] Массовое создание пустых проектов не создаёт индексируемых страниц (FR-GROWTH-005 `@security`)

Если хотя бы одна строка этого раздела не закрыта на момент релиза — Completion не подписывается,
даже если функциональные FR-001…FR-007 готовы. Growth-инструментирование — часть Definition of
Done, а не последующий тюнинг.

## 4. Что НЕ считается за неделю и почему

| Метрика | Почему не считаем |
|---|---|
| Retention D7 / D30 | Требует недель наблюдения — за 7 дней некорректно определить, кто вернулся |
| CAC payback | Требует когорт и полного цикла оплаты, недоступных за неделю |
| Любой процент при n < 30 | Ложная точность — статистический самообман, а не сигнал (PRD §2.4, GROWTH-MECHANICS §4) |
| K-factor как готовое число (не как прокси) | GROWTH-MECHANICS §4 маркирует ориентиры K-factor уровнем доверия MEDIUM — единого индустриального стандарта нет; допустимо использовать `i` и `conv%` как компоненты, но не подавать итоговый K как измеренный факт на выборке недели |

Явно НЕ измеряется как побочный эффект урезанного скоупа: активация через импорт (импорт вне
scope, PRD §1.2) — вместо неё измеряется time-to-first-widget как честная замена (PRD §7, R2).

## 5. Критерии приёмки от заказчика

1. Владелец продукта может за один проход (без обращения к разработчику) создать проект,
   получить ссылку формы, собрать хотя бы один отзыв, одобрить его и увидеть живую Wall of Love
   на собственном тестовом домене через встроенный виджет.
2. Число установленных виджетов на внешних доменах доступно как единое число в дашборде/отчёте,
   без ручного подсчёта.
3. `i` и `conv%` доступны как два отдельных числа, каждое — с явно указанной формулой расчёта.
4. Badge присутствует и работает согласно FR-GROWTH-003 на free-тарифе; попытка отключения
   клиентскими средствами задокументированно не проходит.
5. Прогон Gherkin-сценариев `@happy-path`, `@edge-case`, `@security` для каждого FR-GROWTH-00N
   зелёный.
6. Ни один текст отзыва не проходит через AI-переписывание — подтверждено сценарием
   FR-NFR-SEC-002 (FTC-граница, non-negotiable, PRD §4.4).
7. Открытые вопросы PRD §8 (цена платного тарифа, лимит free-тарифа, домен для публичных стен)
   закрыты явным решением владельца продукта до подписания, либо зафиксированы как принятый
   риск с датой пересмотра.
