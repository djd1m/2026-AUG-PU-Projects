# Specification — Proofwall

> SPARC Phase: **Specification**. Источник: [`PRD.md`](PRD.md), pre-filled context из `discovery/`. Growth-механики заданы здесь как FR, а не описаны прозой в PRD — см. §2.

## 1. Функциональные требования MVP

### FR-001: Регистрация и проект

**User Story:** Как владелец продукта, я хочу создать проект со слагом, чтобы получить адрес
формы сбора и публичной стены.

**Priority:** Must

**Acceptance Criteria:**
- Слаг уникален, `^[a-z0-9-]{3,40}$`, проверка занятости до сабмита
- При создании проекта выдаются: URL формы `/f/<slug>`, URL стены `/w/<slug>`, сниппет виджета
- Все три доступны сразу, до первого отзыва (пустое состояние не 404)

### FR-002: Форма сбора — текстовый отзыв

**User Story:** Как клиент владельца, я хочу оставить текстовый отзыв по ссылке, чтобы не
регистрироваться.

**Priority:** Must

**Acceptance Criteria:**
- Без регистрации. Поля: имя, роль/компания (опц.), текст, фото (опц.)
- Брендирование владельцем: логотип, акцентный цвет, заголовок
- Валидация: текст 10–2000 символов, имя 2–80
- Rate limit: не более 5 отправок с одного IP в час на проект

**Правило по XSS (FR-002/003/005/006):** экранирование — на стороне рендера (FR-005, FR-006), не на приёме (FR-002, FR-003); приём сохраняет ввод как есть — это условие побайтового совпадения из FR-NFR-SEC-002.

```gherkin
Feature: Intake preserves raw content — no sanitization on accept

  @FR-002 @security
  Scenario: Вредоносная разметка в тексте или имени отзыва сохраняется как данные
    Given злоумышленник отправляет текст отзыва, содержащий "<script>alert(1)</script>"
    When форма принимает и сохраняет отзыв
    Then текст сохраняется побайтово как отправлено, без изменения и без отклонения по этой причине
    And сохранение не приводит к выполнению кода на сервере обработки формы
    And экранирование на этом шаге не выполняется — оно выполняется при рендере (FR-005, FR-006)
```

### FR-003: Форма сбора — видео-отзыв

**User Story:** Как клиент владельца, я хочу записать видео-отзыв прямо в браузере или загрузить
готовый файл, чтобы передать эмоцию, которую текст не передаёт, и не тратить время на набор текста.

**Priority:** Must

**Acceptance Criteria:**
- Запись с камеры в браузере либо загрузка файла
- Лимиты: ≤ 120 сек, ≤ 100 MB, форматы webm/mp4
- Транскрипция через внешний STT-провайдер (OpenAI, D-007/ADR-005) — **только расшифровка речи**, без переписывания (см. FR-NFR-SEC-002)
- При отказе в доступе к камере — понятное сообщение и fallback на загрузку файла

```gherkin
Feature: Intake preserves raw content — video form fields

  @FR-003 @security
  Scenario: Вредоносная разметка в имени/роли видео-отзыва сохраняется как данные
    Given злоумышленник указывает имя "<img src=x onerror=alert(1)>" при отправке видео-отзыва
    When форма принимает видео и сопутствующие текстовые поля
    Then поля сохраняются как есть, без исполнения на сервере обработки
    And транскрипт, полученный от внешнего STT-провайдера, сохраняется отдельным полем без интерпретации HTML
    And экранирование этих полей выполняется только при рендере (FR-005, FR-006), не на приёме
```

### FR-004: Модерация

**User Story:** Как владелец продукта, я хочу одобрять или отклонять присланные отзывы перед
публикацией, чтобы на стене и в виджете не оказался спам или чужой отзыв по ошибке.

**Priority:** Must

**Acceptance Criteria:**
- Состояния отзыва: `pending` → `approved` | `rejected` | `hidden`
- Только `approved` попадает на стену и в виджет
- Действие обратимо; переход состояния пишется в audit log с автором и временем
- Отзыв всегда принадлежит проекту; доступ из другого проекта невозможен (проверяемо — см. FR-NFR-SEC-001)

### FR-005: Публичная страница Wall of Love

**User Story:** Как владелец продукта, я хочу иметь публичную страницу со всеми одобренными
отзывами, чтобы отправлять на неё потенциальных клиентов как готовое социальное доказательство.

**Priority:** Must

**Acceptance Criteria:**
- Адрес `/w/<slug>`, серверный рендер, отдаётся без JS
- Показывает только `approved`
- Разметка `schema.org/Review` на каждом отзыве
- Пустое состояние: осмысленная страница, не ошибка
- Требования к индексируемости и содержательности — см. **FR-GROWTH-005**

```gherkin
Feature: Escaped rendering on Wall of Love

  @FR-005 @security
  Scenario: Вредоносная разметка в отзыве не исполняется на публичной стене
    Given одобренный отзыв содержит "<script>alert(1)</script>" в тексте или в имени автора
    When страница /w/<slug> рендерится
    Then содержимое выводится как экранированный текст, видимый как строка, а не как код
    And ни один тег <script> из пользовательского контента не выполняется в браузере
    And разметка schema.org/Review не содержит неэкранированного пользовательского HTML
```

### FR-006: Встраиваемый виджет

**User Story:** Как владелец, я хочу вставить один тег `<script>` на свой сайт, чтобы стена
появилась там без правки вёрстки.

**Priority:** Must

**Acceptance Criteria:**
- Установка: один `<script src="..." data-slug="..." async>`
- Изоляция от стилей хоста (Shadow DOM либо строго префиксованные классы)
- Бандл ≤ 30 KB gzip, не блокирует рендер, p95 отрисовки ≤ 300 мс
- Домен установки фиксируется при первом рендере — это источник метрики недели
  (`widget_installed` — на каждую пару проект+домен, см. §2.4.1 PRD и §4 ниже)
- Badge — см. **FR-GROWTH-003**

```gherkin
Feature: Escaped rendering in embedded widget on a foreign domain

  @FR-006 @security
  Scenario: Вредоносная разметка не исполняется во встроенном виджете на чужом домене
    Given одобренный отзыв содержит вредоносную HTML/JS-разметку в тексте или имени
    When виджет рендерит этот отзыв на домене владельца
    Then разметка выводится как экранированный текст внутри изолированного дерева виджета
    And контент виджета не получает доступа к DOM или cookie хост-страницы
    And ни один скрипт из пользовательского контента не выполняется ни в виджете, ни в хост-странице
```

### FR-007: Тарифы

**User Story:** Как владелец продукта, я хочу оплатить платный тариф, чтобы убрать обязательный
badge и представить стену как часть своего бренда без стороннего лого.

**Priority:** Must

**Acceptance Criteria:**
- Два тарифа: `free` и `paid`
- Различие, релевантное MVP: обязательность badge (FR-GROWTH-003)
- Тариф — атрибут проекта, проверяется на стороне сервера при рендере виджета
- Переход `free` → `paid` выполняется через приём оплаты — см. **FR-008**

### FR-008: Приём оплаты

**User Story:** Как владелец продукта, я хочу оплатить переход на платный тариф через checkout,
чтобы получить платный функционал (снятие badge) сразу после оплаты без ручного вмешательства.

**Priority:** Must

**Acceptance Criteria:**
- Checkout-страница инициирует оплату платного тарифа для конкретного проекта через **ЮKassa**
  (`decisions/D-009`)
- Провайдер присылает вебхук о статусе платежа. ЮKassa уведомления **не подписывает**, поэтому
  подлинность подтверждается двумя независимыми проверками: адрес источника принадлежит
  опубликованному списку сетей ЮKassa **и** статус платежа перезапрашивается через API провайдера.
  Не прошедший любую из них запрос отклоняется без изменения тарифа (см. **FR-GROWTH-002** `@security`)
- Успешный вебхук переводит проект на тариф `paid`; тариф читается на сервере (см. ADR-002)
- Вебхук идемпотентен по `event_id` — повтор не меняет состояние повторно
- Отклонённый, просроченный или неудачный платёж не меняет тариф проекта

## 2. Growth-требования (обязательный блок)

**Основной growth loop: BADGE LOOP.** Виджет живёт на сайте клиента, каждый его посетитель видит
наш бренд. Единственный канал, работающий без нашего трафика.

**Вторичная тактика:** шеринг отзыва автором в соцсеть сразу после отправки — без нового бэкенда.

Каждое требование ниже несёт три Gherkin-сценария: `@happy-path` с числовым порогом,
`@edge-case`, `@security` с anti-fraud.

---

### FR-GROWTH-001: One-click share в момент получения ценности

**User Story:** Как владелец, я хочу поделиться своей стеной одним кликом **в тот момент, когда
увидел её живой на новом домене**, чтобы каждый новый сайт с виджетом становился самостоятельным
поводом поделиться, а не только первый.

**Priority:** Must (MVP)
**Growth Mechanic Type:** Viral Loop

**Момент ценности:** первый успешный рендер виджета на **новом** внешнем домене владельца.
Share-CTA показывается **ровно там**, **не на онбординге**, и при **каждой** новой установке
на новый домен (а не только при первой) — каждый новый сайт самостоятельный повод поделиться.

**Согласование с PRD §2.4.1** («считаем сайты, а не людей»): `invite_shown` и `widget_installed`
имеют одинаковую гранулярность — на пару (проект, домен); повторный рендер на уже известном
домене не порождает ни одного из событий; `i` = `invite_sent` на владельца, несколько сайтов
дают несколько шерингов закономерно, не аномалия.

**Примечание о пороге:** **60 секунд** — эвристическое значение по умолчанию, не выведено из
измеренного SLA доставки события «рендер виджета → дашборд»; вынесено в конфигурацию
(`SHARE_CTA_DELAY_SLA_MS`) и подлежит калибровке по реальным данным после первого релиза.

```gherkin
Feature: Share on every new domain

  @FR-GROWTH-001 @growth @happy-path
  Scenario: Share-CTA появляется при рендере виджета на НОВОМ домене
    Given владелец создал проект и одобрил минимум 1 отзыв
    And виджет проекта ни разу не рендерился на этом конкретном домене
    When виджет впервые успешно отрендерился на этом домене владельца
    Then владелец видит share-CTA в дашборде в течение 60 секунд
    And CTA содержит ссылку на публичную стену /w/<slug>
    And события "invite_shown" и "widget_installed" записаны ровно по 1 разу для пары (проект, домен)

  @FR-GROWTH-001 @growth @edge-case
  Scenario: Повторный рендер на уже известном домене не порождает новых событий
    Given виджет уже успешно рендерился на домене "a.example.com" этого проекта
    When виджет рендерится повторно на том же домене "a.example.com"
    Then новое событие "invite_shown" не записывается
    And новое событие "widget_installed" не записывается
    And share-CTA по этому рендеру не показывается

  @FR-GROWTH-001 @growth @edge-case
  Scenario: CTA не показывается на онбординге и при пустой стене
    Given владелец только что зарегистрировался
    And у проекта 0 одобренных отзывов
    When владелец проходит онбординг
    Then share-CTA не отображается ни на одном экране
    And событие "invite_shown" не записано

  @FR-GROWTH-001 @growth @security
  Scenario: Шеринг не выполняет действий от имени пользователя без согласия
    Given владелец видит share-CTA
    When владелец нажимает "поделиться"
    Then система открывает диалог публикации и ждёт явного подтверждения
    And система не публикует ничего от имени владельца автоматически
    And без подтверждения не отправляется ни одного запроса к внешней сети
```

**Success Metric:** `i` (invites per user) = число `invite_sent` / число владельцев с ≥ 1 виджетом.
Инструментируется с первого релиза, отдельно от `conv%`.

**Definition of Done:**
- [ ] AC покрыты автотестами
- [ ] События `invite_shown` / `invite_sent` пишутся в аналитику
- [ ] Anti-fraud сценарий задокументирован и имеет митигацию
- [ ] Метрика инструментирована до подписания Completion.md

### FR-GROWTH-002: Партнёрская атрибуция до платной конверсии

**User Story:** Как владелец партнёрской программы, я хочу засчитывать партнёру конверсию
**в момент оплаты, а не в момент регистрации**, чтобы платить за деньги, а не за пустые сайнапы.

**Priority:** Must (MVP)
**Growth Mechanic Type:** Referral/Affiliate

**Механика:** cookie **и** промокод — два независимых канала атрибуции; Safari ITP гасит JS-cookie за 7 дней, поэтому промокод — обязательный fallback, а не «приятное дополнение».

**Правило разрешения конфликта:** при расхождении приоритет у **промокода** как явного намерения пользователя — правило фиксируется здесь, а не в коде.

```gherkin
Feature: Affiliate attribution through paid conversion

  @FR-GROWTH-002 @growth @happy-path
  Scenario: Комиссия начисляется при оплате, а не при регистрации
    Given партнёр "P1" имеет реферальную ссылку с кодом "p1"
    And посетитель перешёл по ссылке и получил cookie атрибуции
    When посетитель регистрируется
    Then комиссия партнёру "P1" не начислена
    And атрибуция сохранена в статусе "pending"
    When посетитель оплачивает платный тариф в течение 30 дней
    Then комиссия партнёру "P1" начислена ровно 1 раз
    And начисление ссылается на идентификатор платежа

  @FR-GROWTH-002 @growth @edge-case
  Scenario: Cookie недоступна, атрибуция держится на промокоде
    Given посетитель пришёл по ссылке партнёра "P1"
    And cookie атрибуции удалена или заблокирована браузером
    When посетитель вводит промокод "p1" при оплате
    Then комиссия партнёру "P1" начислена
    And источником атрибуции записан "promo_code"

  @FR-GROWTH-002 @growth @security
  Scenario: Self-referral и дублирование не проходят
    Given партнёр "P1" зарегистрирован с email "p1@example.com"
    When партнёр оплачивает собственный тариф по собственному коду "p1"
    Then комиссия не начислена
    And попытка записана в audit log с причиной "self_referral"
    When тот же вебхук оплаты приходит повторно с тем же event id
    Then повторное начисление не происходит

  @FR-GROWTH-002 @growth @security
  Scenario: Вебхук с неверной подписью отклоняется
    Given платёжный провайдер подписывает вебхуки HMAC-подписью
    When приходит вебхук оплаты с отсутствующей или неверной подписью
    Then запрос отклоняется до обработки бизнес-логики платежа
    And комиссия партнёру не начисляется, тариф проекта не меняется
    And попытка записывается в audit log с причиной "invalid_signature"
```

**Success Metric:** доля платных конверсий с непустой атрибуцией; число `referral_attributed`.

**Definition of Done:**
- [ ] AC покрыты автотестами, включая повторную доставку вебхука
- [ ] Правило приоритета промокода над cookie реализовано и покрыто тестом
- [ ] Self-referral блокируется, событие пишется в audit log
- [ ] Атрибуция и начисление имеют владельца и audit log

### FR-GROWTH-003: Attribution badge на бесплатном тарифе

**User Story:** Как продукт, я хочу, чтобы на бесплатном тарифе badge «Powered by Proofwall»
показывался всегда и не отключался, чтобы каждый посетитель сайта клиента становился показом
нашего бренда — это основной канал роста.

**Priority:** Must (MVP)
**Growth Mechanic Type:** Attribution Badge

**Бизнес-правило (фиксируется здесь, а не хардкодится в коде):**

| Тариф | Badge в виджете | Badge на публичной стене | Снятие |
|---|---|---|---|
| `free` | Обязателен | Обязателен | Невозможно |
| `paid` | Скрыт | Скрыт | Входит в тариф |

Решение принято на этапе Specification как часть тарифной архитектуры.

**Достижимая граница (ADR-002):** восстанавливается видимость **самого элемента badge** при
точечном изменении атрибутов style/hidden. Сокрытие **родительского контейнера целиком**
программно не детектируется (виджет не видит узел выше по дереву) — закрывается условиями
оферты, а не кодом.

```gherkin
Feature: Mandatory attribution badge on free tier

  @FR-GROWTH-003 @growth @happy-path
  Scenario: Badge присутствует и кликабелен на бесплатном тарифе
    Given проект на тарифе "free"
    When виджет рендерится на внешнем домене
    Then badge "Powered by Proofwall" присутствует в DOM виджета
    And badge является ссылкой с UTM-метками источника
    And событие "badge_impression" записано ровно 1 раз за загрузку страницы

  @FR-GROWTH-003 @growth @edge-case
  Scenario: Апгрейд тарифа убирает badge без переустановки виджета
    Given проект на тарифе "free" с установленным виджетом
    When владелец переходит на тариф "paid"
    Then при следующем рендере badge отсутствует
    And владельцу не требуется менять код на своём сайте

  @FR-GROWTH-003 @growth @security
  Scenario: Скрытие самого элемента badge клиентскими средствами не проходит
    Given проект на тарифе "free"
    When на странице хоста применён CSS "display:none" непосредственно к элементу badge
    Then виджет обнаруживает изменение атрибутов style/hidden на элементе badge и восстанавливает
      его видимость
    When запрос конфигурации виджета приходит с параметром, требующим отключить badge
    Then сервер игнорирует параметр и отдаёт конфигурацию с обязательным badge
    And тариф проверяется на сервере, а не по значению из клиента

  @FR-GROWTH-003 @growth @security
  Scenario: Сокрытие родительского контейнера целиком — известное ограничение, не техническое
    Given проект на тарифе "free"
    When хост скрывает весь контейнер виджета целиком (например, "display:none" на родительском
      элементе, а не на самом badge)
    Then это технически неотличимо от отсутствия виджета на странице и не детектируется программно
    And ограничение закрыто условиями оферты: полное сокрытие виджета нарушает условия бесплатного
      тарифа и может быть выявлено выборочной ручной проверкой, а не автоматически
```

**Success Metric:** `badge_impression` на внешних доменах; `conv%` = регистрации из badge / клики по badge.

**Definition of Done:**
- [ ] AC покрыты автотестами, включая серверную проверку тарифа

### FR-GROWTH-005: Индексируемость Wall of Love с самостоятельной ценностью

**User Story:** Как продукт, я хочу, чтобы публичная стена была индексируемой страницей,
несущей самостоятельную ценность для читателя, чтобы получать органический трафик и **не
попасть под политику Google scaled content abuse**.

**Priority:** Must (MVP)
**Growth Mechanic Type:** Content/SEO

**Критерий Google — не «сгенерировано пользователями», а «масштаб + намерение манипулировать ранжированием».** Требование сформулировано как порог содержательности, а не запрет на генерацию.

```gherkin
Feature: Indexable Wall of Love with standalone value

  @FR-GROWTH-005 @growth @happy-path
  Scenario: Содержательная стена индексируема
    Given у проекта не менее 3 одобренных отзывов
    And суммарный объём текста отзывов не менее 400 символов
    When поисковый робот запрашивает /w/<slug>
    Then страница отдаётся со статусом 200 и серверным рендером
    And в разметке присутствует schema.org/Review на каждый отзыв
    And страница не содержит noindex

  @FR-GROWTH-005 @growth @edge-case
  Scenario: Тонкая страница закрыта от индексации
    Given у проекта менее 3 одобренных отзывов
    When поисковый робот запрашивает /w/<slug>
    Then страница содержит noindex
    And страница остаётся доступной для людей по прямой ссылке

  @FR-GROWTH-005 @growth @security
  Scenario: Массовое создание пустых проектов не порождает индексируемых страниц
    Given один аккаунт создал более 20 проектов за час
    Then новые проекты создаются с принудительным noindex
    And снятие noindex возможно только при выполнении порога содержательности
    And событие записано в audit log
```

**Примечание о порогах:** **≥3 отзыва и ≥400 символов**, а также **>20 проектов/час** — эвристики
авторов документа, а не порог политики Google (у неё нет официальной цифры). Значения по
умолчанию, вынесены в конфигурацию (`SEO_MIN_REVIEWS`, `SEO_MIN_CHARS`,
`ABUSE_PROJECT_CREATE_RATE`), подлежат калибровке на реальных данных индексации.

**Success Metric:** число страниц `/w/<slug>`, прошедших порог содержательности.

**Definition of Done:**
- [ ] Порог содержательности реализован и покрыт тестом в обе стороны
- [ ] `schema.org/Review` валидируется автотестом
- [ ] Массовое создание проектов не создаёт индексируемых пустышек

## 3. Нефункциональные требования

### FR-NFR-PERF-001: Производительность виджета
Бандл ≤ 30 KB gzip; загрузка `async`, не блокирует рендер хоста; p95 отрисовки ≤ 300 мс.

### FR-NFR-SEC-001: Мульти-арендная изоляция
Каждый отзыв принадлежит ровно одному проекту. Любой запрос данных проверяет принадлежность на
сервере. Межпроектный доступ невозможен ни через API, ни через параметры виджета.

Анонимные пути (форма, виджет, стена) ходят под ролью `app_service` с `BYPASSRLS` — защита держится **исключительно на коде обработчика**, не на политике БД, поэтому обязательна проверка тестом.

```gherkin
Feature: Multi-tenant isolation

  @FR-NFR-SEC-001 @security
  Scenario: Публичная страница Wall of Love одного проекта не выдаёт данные другого проекта
    Given существуют независимые проекты "A" (с одобренным отзывом) и "B" (с одобренным отзывом)
    And запрос идёт анонимно, под сервисной ролью app_service с BYPASSRLS
    When посетитель запрашивает GET /w/a и дополнительно передаёт параметр или заголовок,
      указывающий на проект "B" (например, query project_id=<id проекта B>)
    Then сервер разрешает выдачу строго по slug "a" из пути запроса, посторонний параметр игнорируется
    And ни один отзыв проекта "B" не появляется в ответе для запроса, инициированного как "/w/a"
    And обработчик резолвит project исключительно из slug в пути запроса, project_id от клиента
      не принимается ни в каком виде

  @FR-NFR-SEC-001 @security
  Scenario: Подмена параметра виджета не расширяет выдачу за пределы своего проекта
    Given виджет легитимно инициализирован с "data-slug=a" (проект "A")
    When запрос конфигурации виджета дополнительно содержит параметр, указывающий на проект "B"
      (например, подменённый project_id или slug в теле/query запроса)
    Then сервер разрешает выдачу строго по данным, привязанным к "data-slug=a"
    And посторонний/противоречащий параметр игнорируется либо запрос отклоняется
    And ни один отзыв проекта "B" не попадает в ответ для запроса, инициированного как "data-slug=a"
```

### FR-NFR-SEC-002: Граница применения AI-транскрипции (non-negotiable)

FTC Rule 16 CFR Part 465 (в силе с 21.10.2024) запрещает AI-сгенерированные отзывы.
Максимальный штраф — **$53,088** за нарушение.

**D-007/ADR-005:** транскрипция реализована через внешний STT-провайдер (OpenAI,
`gpt-4o-mini-transcribe`), не через Claude API — Claude API не принимает аудио, невыполнимо
технически. Граница ниже осталась той же и стала конструктивной: STT физически делает
speech-to-text (расшифровку сказанного), а не генерацию текста.

| ✅ Разрешено | ❌ Запрещено |
|---|---|
| Транскрипция видео (речь → текст) | Генерация текста отзыва |
| Теги, поиск, сортировка | «Улучшение» формулировок автора |
| Сводка по набору **с явной пометкой** | Переписывание отзыва от лица клиента |

```gherkin
Feature: FTC compliance boundary for AI

  @FR-NFR-SEC-002 @security @compliance
  Scenario: Текст отзыва не изменяется системой
    Given клиент отправил текстовый отзыв
    When отзыв сохраняется и публикуется
    Then опубликованный текст побайтово совпадает с отправленным
    And обработка текстового отзыва не выполняет ни одного вызова внешнего STT-провайдера

  @FR-NFR-SEC-002 @security @compliance
  Scenario: Контракт транскрипции структурно не даёт пути для переписывания текста
    Given сервис транскрипции видео (services/transcribe) определяет свой набор доступных путей
    When клиент запрашивает список путей сервиса
    Then единственный путь, принимающий вход, — "POST /transcribe" со входом "video_url" (аудио/видео) и выходом "текст"
    And в контракте отсутствует путь, принимающий текст отзыва в качестве входного параметра

  @FR-NFR-SEC-002 @security @compliance
  Scenario: Транскрипция помечена как машинная расшифровка
    Given клиент отправил видео-отзыв
    When система создаёт транскрипт через внешний STT-провайдер
    Then транскрипт сохраняется отдельным полем, не подменяя видео
    And на публичной странице транскрипт помечен как машинная расшифровка

  @FR-NFR-SEC-002 @security @compliance
  Scenario: Сводка по набору отзывов помечена как сгенерированная ИИ
    Given на дашборде владельца доступна сводка по набору отзывов, созданная через AI-модель
    When сводка отображается владельцу
    Then рядом со сводкой присутствует явная, видимая без доп. действий пометка вида
      "сгенерировано ИИ"
    And пометка не скрыта в тултипе или дополнительных настройках
```

## 4. Метрики, инструментируемые с первого релиза

| Событие | Назначение |
|---|---|
| `invite_shown` (на каждую пару проект+домен — момент ценности), `invite_sent` | `i` — invites per user |
| `badge_impression`, `badge_click` | верх воронки badge loop |
| `signup_from_badge` | `conv%` — вторая половина K-factor |
| `widget_installed` (на каждую пару проект+домен) | **метрика недели** |
| `referral_attributed` | атрибуция партнёра |

`i` и `conv%` — **раздельные** метрики, не восстанавливаемые постфактум, поэтому трекинг входит
в MVP. Семантика — PRD §2.4.1 («считаем сайты, а не людей»): `invite_shown` и `widget_installed`
имеют одинаковую гранулярность (пара проект+домен); повтор на известном домене не даёт новых
событий; несколько сайтов у владельца закономерно дают несколько `invite_sent`.

**Не считаем на неделе:** retention D7/D30, CAC payback, любой процент при n < 30.
