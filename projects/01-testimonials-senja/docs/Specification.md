# Specification — Proofwall

> SPARC Phase: **Specification**. Источник: [`PRD.md`](PRD.md), pre-filled context из `discovery/`.
> Growth-механики заданы здесь как FR, а не описаны прозой в PRD — см. §2.

## 1. Функциональные требования MVP

### FR-001: Регистрация и проект

**User Story:** Как владелец продукта, я хочу создать проект со слагом, чтобы получить адрес
формы сбора и публичной стены.

**Priority:** Must

**Acceptance Criteria:**
- Слаг уникален, `^[a-z0-9-]{3,40}$`, проверка занятости до сабмита
- При создании проекта выдаются: URL формы `/f/<slug>`, URL стены `/w/<slug>`, сниппет виджета
- Все три доступны сразу, до первого отзыва (пустое состояние не 404)

### FR-002: Форма сбора — текстовый отзыв

**User Story:** Как клиент владельца, я хочу оставить текстовый отзыв по ссылке, чтобы не
регистрироваться.

**Priority:** Must

**Acceptance Criteria:**
- Без регистрации. Поля: имя, роль/компания (опц.), текст, фото (опц.)
- Брендирование владельцем: логотип, акцентный цвет, заголовок
- Валидация: текст 10–2000 символов, имя 2–80
- Rate limit: не более 5 отправок с одного IP в час на проект

### FR-003: Форма сбора — видео-отзыв

**Priority:** Must

**Acceptance Criteria:**
- Запись с камеры в браузере либо загрузка файла
- Лимиты: ≤ 120 сек, ≤ 100 MB, форматы webm/mp4
- Транскрипция через Claude API — **только расшифровка речи**, без переписывания (см. FR-NFR-SEC-002)
- При отказе в доступе к камере — понятное сообщение и fallback на загрузку файла

### FR-004: Модерация

**Priority:** Must

**Acceptance Criteria:**
- Состояния отзыва: `pending` → `approved` | `rejected` | `hidden`
- Только `approved` попадает на стену и в виджет
- Действие обратимо; переход состояния пишется в audit log с автором и временем
- Отзыв всегда принадлежит проекту; доступ из другого проекта невозможен

### FR-005: Публичная страница Wall of Love

**Priority:** Must

**Acceptance Criteria:**
- Адрес `/w/<slug>`, серверный рендер, отдаётся без JS
- Показывает только `approved`
- Разметка `schema.org/Review` на каждом отзыве
- Пустое состояние: осмысленная страница, не ошибка
- Требования к индексируемости и содержательности — см. **FR-GROWTH-005**

### FR-006: Встраиваемый виджет

**User Story:** Как владелец, я хочу вставить один тег `<script>` на свой сайт, чтобы стена
появилась там без правки вёрстки.

**Priority:** Must

**Acceptance Criteria:**
- Установка: один `<script src="..." data-slug="..." async>`
- Изоляция от стилей хоста (Shadow DOM либо строго префиксованные классы)
- Бандл ≤ 30 KB gzip, не блокирует рендер, p95 отрисовки ≤ 300 мс
- Домен установки фиксируется при первом рендере — это источник метрики недели
- Badge — см. **FR-GROWTH-003**

### FR-007: Тарифы

**Priority:** Must

**Acceptance Criteria:**
- Два тарифа: `free` и `paid`
- Различие, релевантное MVP: обязательность badge (FR-GROWTH-003)
- Тариф — атрибут проекта, проверяется на стороне сервера при рендере виджета

## 2. Growth-требования (обязательный блок)

**Основной growth loop: BADGE LOOP.** Виджет живёт на сайте клиента, каждый его посетитель видит
наш бренд. Единственный канал, работающий без нашего трафика.

**Вторичная тактика:** шеринг отзыва автором в соцсеть сразу после отправки — без нового бэкенда.

Каждое требование ниже несёт три Gherkin-сценария: `@happy-path` с числовым порогом,
`@edge-case`, `@security` с anti-fraud.

---

### FR-GROWTH-001: One-click share в момент получения ценности

**User Story:** Как владелец, я хочу поделиться своей стеной одним кликом **в тот момент, когда
впервые увидел её живой на своём домене**, чтобы мой шеринг попал в момент максимальной гордости
за результат, а не в момент, когда мне ещё нечего показать.

**Priority:** Must (MVP)
**Growth Mechanic Type:** Viral Loop

**Момент ценности:** первый успешный рендер виджета на внешнем домене владельца.
Share-CTA показывается **ровно там** и **не показывается на онбординге**.

```gherkin
Feature: Share at the aha moment

  @FR-GROWTH-001 @growth @happy-path
  Scenario: Share-CTA появляется при первом рендере виджета на внешнем домене
    Given владелец создал проект и одобрил минимум 1 отзыв
    And виджет проекта ни разу не рендерился на внешнем домене
    When виджет впервые успешно отрендерился на домене владельца
    Then владелец видит share-CTA в дашборде в течение 60 секунд
    And CTA содержит ссылку на публичную стену /w/<slug>
    And событие "invite_shown" записано ровно 1 раз

  @FR-GROWTH-001 @growth @edge-case
  Scenario: CTA не показывается на онбординге и при пустой стене
    Given владелец только что зарегистрировался
    And у проекта 0 одобренных отзывов
    When владелец проходит онбординг
    Then share-CTA не отображается ни на одном экране
    And событие "invite_shown" не записано

  @FR-GROWTH-001 @growth @security
  Scenario: Шеринг не выполняет действий от имени пользователя без согласия
    Given владелец видит share-CTA
    When владелец нажимает "поделиться"
    Then система открывает диалог публикации и ждёт явного подтверждения
    And система не публикует ничего от имени владельца автоматически
    And без подтверждения не отправляется ни одного запроса к внешней сети
```

**Success Metric:** `i` (invites per user) = число `invite_sent` / число владельцев с ≥ 1 виджетом.
Инструментируется с первого релиза, отдельно от `conv%`.

**Definition of Done:**
- [ ] AC покрыты автотестами
- [ ] События `invite_shown` / `invite_sent` пишутся в аналитику
- [ ] Anti-fraud сценарий задокументирован и имеет митигацию
- [ ] Метрика инструментирована до подписания Completion.md

### FR-GROWTH-002: Партнёрская атрибуция до платной конверсии

**User Story:** Как владелец партнёрской программы, я хочу засчитывать партнёру конверсию
**в момент оплаты, а не в момент регистрации**, чтобы платить за деньги, а не за пустые сайнапы.

**Priority:** Must (MVP)
**Growth Mechanic Type:** Referral/Affiliate

**Механика:** cookie **и** промокод — два независимых канала атрибуции. Safari ITP гасит
JS-cookie за 7 дней, поэтому промокод не «приятное дополнение», а обязательный fallback.

**Правило разрешения конфликта:** при расхождении cookie и промокода приоритет у **промокода**
как у явного намерения пользователя. Правило фиксируется здесь, а не в коде.

```gherkin
Feature: Affiliate attribution through paid conversion

  @FR-GROWTH-002 @growth @happy-path
  Scenario: Комиссия начисляется при оплате, а не при регистрации
    Given партнёр "P1" имеет реферальную ссылку с кодом "p1"
    And посетитель перешёл по ссылке и получил cookie атрибуции
    When посетитель регистрируется
    Then комиссия партнёру "P1" не начислена
    And атрибуция сохранена в статусе "pending"
    When посетитель оплачивает платный тариф в течение 30 дней
    Then комиссия партнёру "P1" начислена ровно 1 раз
    And начисление ссылается на идентификатор платежа

  @FR-GROWTH-002 @growth @edge-case
  Scenario: Cookie недоступна, атрибуция держится на промокоде
    Given посетитель пришёл по ссылке партнёра "P1"
    And cookie атрибуции удалена или заблокирована браузером
    When посетитель вводит промокод "p1" при оплате
    Then комиссия партнёру "P1" начислена
    And источником атрибуции записан "promo_code"

  @FR-GROWTH-002 @growth @security
  Scenario: Self-referral и дублирование не проходят
    Given партнёр "P1" зарегистрирован с email "p1@example.com"
    When партнёр оплачивает собственный тариф по собственному коду "p1"
    Then комиссия не начислена
    And попытка записана в audit log с причиной "self_referral"
    When тот же вебхук оплаты приходит повторно с тем же event id
    Then повторное начисление не происходит
```

**Success Metric:** доля платных конверсий с непустой атрибуцией; число `referral_attributed`.

**Definition of Done:**
- [ ] AC покрыты автотестами, включая повторную доставку вебхука
- [ ] Правило приоритета промокода над cookie реализовано и покрыто тестом
- [ ] Self-referral блокируется, событие пишется в audit log
- [ ] Атрибуция и начисление имеют владельца и audit log

### FR-GROWTH-003: Attribution badge на бесплатном тарифе

**User Story:** Как продукт, я хочу, чтобы на бесплатном тарифе badge «Powered by Proofwall»
показывался всегда и не отключался, чтобы каждый посетитель сайта клиента становился показом
нашего бренда — это основной канал роста.

**Priority:** Must (MVP)
**Growth Mechanic Type:** Attribution Badge

**Бизнес-правило (фиксируется здесь, а не хардкодится в коде):**

| Тариф | Badge в виджете | Badge на публичной стене | Снятие |
|---|---|---|---|
| `free` | Обязателен | Обязателен | Невозможно |
| `paid` | Скрыт | Скрыт | Входит в тариф |

Решение принято на этапе Specification как часть тарифной архитектуры.

```gherkin
Feature: Mandatory attribution badge on free tier

  @FR-GROWTH-003 @growth @happy-path
  Scenario: Badge присутствует и кликабелен на бесплатном тарифе
    Given проект на тарифе "free"
    When виджет рендерится на внешнем домене
    Then badge "Powered by Proofwall" присутствует в DOM виджета
    And badge является ссылкой с UTM-метками источника
    And событие "badge_impression" записано ровно 1 раз за загрузку страницы

  @FR-GROWTH-003 @growth @edge-case
  Scenario: Апгрейд тарифа убирает badge без переустановки виджета
    Given проект на тарифе "free" с установленным виджетом
    When владелец переходит на тариф "paid"
    Then при следующем рендере badge отсутствует
    And владельцу не требуется менять код на своём сайте

  @FR-GROWTH-003 @growth @security
  Scenario: Badge нельзя скрыть на бесплатном тарифе клиентскими средствами
    Given проект на тарифе "free"
    When на странице хоста применён CSS "display:none" к элементу badge
    Then виджет обнаруживает сокрытие и восстанавливает видимость badge
    When запрос данных приходит с параметром, требующим отключить badge
    Then сервер игнорирует параметр и отдаёт конфигурацию с обязательным badge
    And тариф проверяется на сервере, а не по значению из клиента
```

**Success Metric:** `badge_impression` на внешних доменах; `conv%` = регистрации из badge / клики по badge.

**Definition of Done:**
- [ ] AC покрыты автотестами, включая серверную проверку тарифа
- [ ] `badge_impression` и `badge_click` инструментированы раздельно
- [ ] Попытка отключить badge на free не проходит ни клиентски, ни через API

### FR-GROWTH-004: Персональные коды партнёрам с аудиторией

**User Story:** Как growth-менеджер, я хочу выдавать авторам рассылок и Telegram-каналов про
SaaS и инди-хакинг **персональные трекируемые коды**, чтобы считать CAC по когорте каждого
партнёра отдельно и отличать рабочего партнёра от мёртвого.

**Priority:** Must (MVP)
**Growth Mechanic Type:** Influencer/Partnership

```gherkin
Feature: Trackable partner codes

  @FR-GROWTH-004 @growth @happy-path
  Scenario: Регистрации и оплаты атрибуцируются конкретному партнёру
    Given партнёру "newsletter-A" выдан персональный код
    When по коду "newsletter-A" пришли 10 регистраций и 2 оплаты
    Then дашборд показывает по партнёру "newsletter-A": 10 регистраций и 2 оплаты
    And когорта партнёра отделена от когорт других партнёров

  @FR-GROWTH-004 @growth @edge-case
  Scenario: Отозванный код перестаёт атрибуцировать, история сохраняется
    Given код "newsletter-A" отозван
    When новый посетитель приходит по этому коду
    Then новая атрибуция не создаётся
    And ранее начисленные комиссии по коду остаются без изменений

  @FR-GROWTH-004 @growth @security
  Scenario: Накрутка регистраций по коду детектируется
    Given по коду "newsletter-A" за 10 минут пришло более 50 регистраций с одного IP
    Then регистрации помечаются флагом "suspected_fraud"
    And комиссия по помеченным регистрациям не начисляется до ручной проверки
    And событие записано в audit log
```

**Success Metric:** число активных партнёрских кодов с ≥ 1 платной конверсией.

**Definition of Done:**
- [ ] AC покрыты автотестами
- [ ] Когорта на партнёра выделяется в аналитике
- [ ] Детектор накрутки задокументирован и имеет митигацию

### FR-GROWTH-005: Индексируемость Wall of Love с самостоятельной ценностью

**User Story:** Как продукт, я хочу, чтобы публичная стена была индексируемой страницей,
несущей самостоятельную ценность для читателя, чтобы получать органический трафик и **не
попасть под политику Google scaled content abuse**.

**Priority:** Must (MVP)
**Growth Mechanic Type:** Content/SEO

**Критерий Google — не «сгенерировано пользователями», а «масштаб + намерение манипулировать
ранжированием».** Поэтому требование сформулировано как порог содержательности, а не как запрет
на генерацию.

```gherkin
Feature: Indexable Wall of Love with standalone value

  @FR-GROWTH-005 @growth @happy-path
  Scenario: Содержательная стена индексируема
    Given у проекта не менее 3 одобренных отзывов
    And суммарный объём текста отзывов не менее 400 символов
    When поисковый робот запрашивает /w/<slug>
    Then страница отдаётся со статусом 200 и серверным рендером
    And в разметке присутствует schema.org/Review на каждый отзыв
    And страница не содержит noindex

  @FR-GROWTH-005 @growth @edge-case
  Scenario: Тонкая страница закрыта от индексации
    Given у проекта менее 3 одобренных отзывов
    When поисковый робот запрашивает /w/<slug>
    Then страница содержит noindex
    And страница остаётся доступной для людей по прямой ссылке

  @FR-GROWTH-005 @growth @security
  Scenario: Массовое создание пустых проектов не порождает индексируемых страниц
    Given один аккаунт создал более 20 проектов за час
    Then новые проекты создаются с принудительным noindex
    And снятие noindex возможно только при выполнении порога содержательности
    And событие записано в audit log
```

**Success Metric:** число страниц `/w/<slug>`, прошедших порог содержательности.

**Definition of Done:**
- [ ] Порог содержательности реализован и покрыт тестом в обе стороны
- [ ] `schema.org/Review` валидируется автотестом
- [ ] Массовое создание проектов не создаёт индексируемых пустышек

## 3. Нефункциональные требования

### FR-NFR-PERF-001: Производительность виджета
Бандл ≤ 30 KB gzip; загрузка `async`, не блокирует рендер хоста; p95 отрисовки ≤ 300 мс.

### FR-NFR-SEC-001: Мульти-арендная изоляция
Каждый отзыв принадлежит ровно одному проекту. Любой запрос данных проверяет принадлежность на
сервере. Межпроектный доступ невозможен ни через API, ни через параметры виджета.

### FR-NFR-SEC-002: Граница применения Claude API (non-negotiable)

FTC Rule 16 CFR Part 465 (в силе с 21.10.2024) запрещает AI-сгенерированные отзывы.
Максимальный штраф — **$53,088** за нарушение.

| ✅ Разрешено | ❌ Запрещено |
|---|---|
| Транскрипция видео (речь → текст) | Генерация текста отзыва |
| Теги, поиск, сортировка | «Улучшение» формулировок автора |
| Сводка по набору **с явной пометкой** | Переписывание отзыва от лица клиента |

```gherkin
Feature: FTC compliance boundary for AI

  @FR-NFR-SEC-002 @security @compliance
  Scenario: Текст отзыва не изменяется системой
    Given клиент отправил текстовый отзыв
    When отзыв сохраняется и публикуется
    Then опубликованный текст побайтово совпадает с отправленным
    And ни один вызов Claude API не принимает текст отзыва на переписывание

  @FR-NFR-SEC-002 @security @compliance
  Scenario: Транскрипция помечена как машинная расшифровка
    Given клиент отправил видео-отзыв
    When система создаёт транскрипт через Claude API
    Then транскрипт сохраняется отдельным полем, не подменяя видео
    And на публичной странице транскрипт помечен как машинная расшифровка
```

### FR-NFR-SEC-003: Rate limiting и защита формы
Не более 5 отправок с одного IP в час на проект. Превышение — 429 без раскрытия деталей.

### FR-NFR-A11Y-001: Доступность публичной страницы
Контраст не ниже AA, alt у изображений, семантическая разметка, навигация с клавиатуры.

## 4. Метрики, инструментируемые с первого релиза

| Событие | Назначение |
|---|---|
| `invite_shown`, `invite_sent` | `i` — invites per user |
| `badge_impression`, `badge_click` | верх воронки badge loop |
| `signup_from_badge` | `conv%` — вторая половина K-factor |
| `widget_installed` (домен + первый рендер) | **метрика недели** |
| `referral_attributed` | атрибуция партнёра |

`i` и `conv%` — **раздельные** метрики. Постфактум эти события не восстанавливаются, поэтому
трекинг входит в MVP, а не в «потом».

**Не считаем на неделе:** retention D7/D30, CAC payback, любой процент при n < 30.
