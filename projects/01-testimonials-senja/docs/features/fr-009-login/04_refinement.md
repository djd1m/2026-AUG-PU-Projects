# FR-009 · Уточнения и краевые случаи

| Случай | Ожидание | Почему |
|---|---|---|
| Email в другом регистре | Вход проходит | Регистрация нормализует — вход обязан так же, иначе учётка недостижима |
| Email с пробелами по краям | Вход проходит | Тот же довод |
| Пароль пустая строка | `401`, тот же ответ | Не `400`: отдельный код отличал бы «пустой» от «неверный» |
| Тело не JSON | `400` | Это ошибка формата, не аутентификации — различимость здесь безопасна |
| `password` не строка (число, массив, объект) | `401`, без исключения | Мусорный ввод не должен ронять маршрут |
| Аккаунта нет | `401` + argon2 всё равно посчитан | NFR-009.2 |
| Хеш в БД битый/чужого формата | `401` | `verifyPassword` уже возвращает `false`, а не бросает |
| Повторный вход | Новая сессия, старая продолжает жить | Завершение чужих сессий — FR-010, не здесь |
| Лимит по email исчерпан | `429` без цифр | NFR-009.3 |
| Лимит по IP исчерпан (30/час по разным email) | `429` без цифр | NFR-009.3 — защита машины, а не учётки |
| 5 неудач по email A, затем попытка по email B с того же IP | Проходит к проверке пароля | Лимиты независимы; иначе одна учётка запирает все |
| Успешный вход | Счётчики НЕ увеличиваются | Записывается только неудача — иначе активный владелец сам себя запирает |
| `?next=//evil.example` | Игнорируется, переход на кабинет | Протокол-относительный URL начинается со слеша — «начинается со слеша» дырявая проверка (уже ловилось в виджете) |
| `?next=/dashboard/acme` | Переход туда | Относительный путь допустим |
| У аккаунта два проекта | `projects` содержит оба, переход на страницу выбора | FR-009.4, FR-009.5 |

## Тест-стратегия

**Слой 1 — поведение:**
- три отказных сценария дают побайтово одинаковое тело и один код;
- тело успешного ответа не содержит токена (проверка по отсутствию значения cookie в JSON);
- сессия от входа открывает кабинет; TTL совпадает с TTL от регистрации.

**Слой 1 — тайминг (NFR-009.2):** сравнить медиану времени `login` для несуществующего
email и для существующего с неверным паролем. Порог задать с запасом (различие не более
чем в 2 раза) — тест не должен мигать на нагруженной машине, но обязан падать, если
ранний возврат вернут.

**Слой 1 — стражи по исходнику** (тайминг-тест вероятностен; эти — нет):
- `lib/login.ts` не содержит `return` до вызова `verifyPassword` — дефект вернётся при
  первом же «оптимизирующем» рефакторинге;
- `insert into sessions` встречается **ровно в одном файле** проекта (NFR-009.6);
- ни один файл, кроме `lib/login.ts`, не сравнивает с константами scope входа.

**[v2] Слой 1 — запись в счётчик (NFR-009.4):** до и после неудачной попытки посчитать
строки `rate_limit_events` по обоим ключам; ожидание — рост ровно на 1 у каждого.
Без этого теста критерий «превышение даёт 429» проходит на реализации, где запись
не происходит вовсе.

**Испытание стражей на способность падать** (`.claude/rules/guard-must-be-able-to-fail.md`):
внедрить ранний возврат, убедиться в красном, восстановить.
