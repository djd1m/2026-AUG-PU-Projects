# FR-009 · Архитектура

## Размещение

| Компонент | Путь | Роль БД |
|---|---|---|
| Маршрут | `apps/web/src/app/api/auth/login/route.ts` | — |
| Логика | `apps/web/src/lib/login.ts` | `withService` |
| Страница | `apps/web/src/app/login/page.tsx` | — |

## Почему `withService`, а не `withAccount`

На момент входа контекста аккаунта ещё нет — его как раз и устанавливают. Значит роль
`app_service` (`BYPASSRLS`), и по правилу `.claude/rules` изоляция целиком на коде:
выборка идёт по `email`, единственному входному значению, и возвращает ровно одну
строку. Никаких «взять по id из тела» здесь быть не может.

## Граница ответственности

`lib/login.ts` не знает про HTTP: принимает `client`, `email`, `password`, возвращает
результат-объединение. Маршрут превращает его в ответ и ставит cookie. Это позволяет
тестировать инвариант «одинаковый ответ» без поднятия сервера.

```ts
// [v2] Успех несёт projects — FR-009.4. Отказ не несёт НИЧЕГО.
export type LoginResult =
  | { ok: true; accountId: string; token: string; projects: ProjectSummary[] }
  | { ok: false };          // без причины НАМЕРЕННО: причина — это и есть утечка

export interface ProjectSummary { slug: string; urls: ProjectUrls }
```

Отсутствие поля `reason` у отказа — не упрощение, а реализация NFR-009.1 **формой типа**:
вызывающий код физически не может отдать наружу разные ответы, потому что различить
их нечем. Приём из [`source-parsing-invariant-guard`](../../../.claude/patterns/source-parsing-invariant-guard.md):
инвариант выражен формой, а не дисциплиной.

## Схема БД

Изменений нет. `accounts(email unique, password_hash)`, `sessions` и `rate_limit_events`
(с колонкой `scope`) уже есть — вход добавляет два новых значения `scope`, не таблицу.

## [v2] Что фича меняет в существующем коде

| Файл | Изменение | Почему обязательно |
|---|---|---|
| `lib/session.ts` | **добавляется** `createSession(client, accountId)` | Единственная точка выдачи сессии (NFR-009.6) |
| `lib/register.ts` | переводится на `createSession` | Иначе точек станет две и инвариант рухнет в момент введения |
| `lib/project.ts` | **добавляется** `listProjectsForAccount(client, accountId)` | FR-009.4; сейчас есть только поиск по слагу |
| `app/dashboard/[slug]/page.tsx` | переход на `/login` при отсутствии сессии | FR-009.3 |

Правка `register.ts` — часть этой фичи, а не «заодно»: вынести общую функцию и не
перевести на неё единственного существующего потребителя значит создать ровно ту
вторую точку, которую фича запрещает.

## Влияние на существующее

`/dashboard/[slug]` сейчас при отсутствии сессии полагается на редирект или ошибку —
проверить и привести к переходу на `/login`.
