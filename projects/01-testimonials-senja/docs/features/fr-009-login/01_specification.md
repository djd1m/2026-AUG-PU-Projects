# FR-009 · Спецификация: вход в систему

> Ревизия 2 (после 🔴 валидации: 4 блокера). Изменения помечены **[v2]**.

## Проблема

Входа не существует. `/api/auth/login` и страницы входа нет, `verifyPassword` написана,
покрыта тестами и **не вызывается ниоткуда**. Доступ даёт только cookie сессии на 30 дней
без продления — по истечении владелец теряет кабинет безвозвратно.

**[v2] Как это классифицировать.** Ранее здесь было написано «вход не входил в объём MVP».
Это неверно. `PRD` и `Specification` действительно не содержат слова «вход» — но
`Architecture.md:455` прямо опирается на него («тот же контракт „владелец залогинен →
есть `account_id`“»), а `Refinement.md:188` строит на нём интеграционный тест
(«войти владельцем A»).

Значит вход **потерян между документами**: архитектура его предполагала, требование не
описало, псевдокод не реализовал. Это класс дефекта PR-003 («сценарий есть, реализации
нет»), а не сознательное сокращение объёма.

## Функциональные требования

| # | Требование |
|---|---|
| FR-009.1 | `POST /api/auth/login` принимает `email` + `password`, при совпадении выдаёт сессию |
| FR-009.2 | Токен уходит ТОЛЬКО в `httpOnly`-cookie, никогда в тело ответа |
| FR-009.3 | Страница `/login` с формой; `/dashboard/<slug>` без валидной сессии ведёт на неё |
| FR-009.4 **[v2]** | Успешный вход возвращает **список** проектов аккаунта: `projects: [{ slug, urls }]`. Список, а не один проект: схема (`003_core.sql:32`) допускает несколько проектов на аккаунт, и допущение «ровно один» сломается при первой же фиче создания второго |
| FR-009.5 **[v2]** | Куда попадает браузер после входа: один проект → его кабинет; несколько → страница выбора. Параметр возврата `?next=` принимается **только** как относительный путь `^/[A-Za-z0-9/_-]*$`; всё прочее игнорируется молча |

## Нефункциональные требования `@security`

| # | Требование | Почему несущее |
|---|---|---|
| NFR-009.1 | Неверный пароль и несуществующий email дают **побайтово одинаковый** ответ и один код | Различимые ответы — оракул перечисления учёток |
| NFR-009.2 | Они дают **сопоставимое время ответа** | Пропуск argon2 при ненайденном email — таймингов оракул, который текстом не закрывается |
| NFR-009.3 **[v2]** | Два независимых лимита, оба обязаны пропустить: **по email — 5 попыток в час**, **по IP — 30 в час** | Один лимит по IP не годится: у входа ключ без `project_id`, и при пороге 5, как у формы отзыва, пять опечаток запирают весь офис за NAT. Восстановления пароля нет (FR-010 вне объёма), поэтому цена ложного срабатывания — потерянный кабинет до конца окна. Тугой лимит защищает **учётку**, свободный — ограничивает **машину**, и это разные задачи |
| NFR-009.4 **[v2]** | Каждая неудачная попытка **записывается** в оба счётчика | Без этого требования критерий «превышение даёт 429» зеленеет на реализации, где запись не происходит вовсе: тест засеет таблицу напрямую и не заметит, что пароль перебирается без ограничений |
| NFR-009.5 | Ответ при отказе не содержит счётчиков и времени сброса | Различимость ответов — утечка |
| NFR-009.6 **[v2]** | Сессия выдаётся **единственной функцией**, общей с регистрацией | «Тот же TTL и тот же способ хранения» зеленеет на втором независимом `INSERT` с теми же константами — и именно так два класса сессий разъезжаются молча |
| NFR-009.7 | Сравнение паролей константное по времени | Обеспечивает `argon2.verify` в `verifyPassword` |

## Критерии приёмки

- [ ] Вход выдаёт рабочую сессию; кабинет открывается по ней
- [ ] **[v2]** `JSON.stringify(тело ответа)` **не содержит значения** cookie сессии (не «нет поля `token`»: слабая форма проходит, если токен уехал в поле `session`, `sid` или во вложенный объект)
- [ ] Ответ и код **побайтово совпадают** для: неверный пароль / нет такого email / пустой пароль / `password` не строка
- [ ] Медиана времени ответа для несуществующего email отличается от медианы для неверного пароля не более чем в 2 раза
- [ ] **[v2]** Страж по исходнику: в `lib/login.ts` нет `return` до вызова `verifyPassword` (тайминг-тест вероятностен и на нагруженной машине может смолчать — этот не может)
- [ ] **[v2]** После неудачной попытки число строк в `rate_limit_events` для обоих ключей выросло ровно на 1
- [ ] **[v2]** 6-я подряд неудачная попытка по одному email даёт `429`; она же с ДРУГОГО email и того же IP — не даёт (проверяет, что лимиты независимы)
- [ ] **[v2]** 31-я попытка с одного IP по разным email даёт `429`
- [ ] Тело `429` не содержит цифр
- [ ] **[v2]** Страж по исходнику: `insert into sessions` встречается **ровно в одном файле** проекта
- [ ] **[v2]** `projects` в ответе содержит все проекты аккаунта; проверяется на аккаунте с двумя проектами
- [ ] **[v2]** `?next=//evil.example`, `?next=https://evil.example`, `?next=javascript:…` игнорируются
- [ ] **[v2]** Страница `/login` существует, отдаёт форму с полями email и пароль
- [ ] `/dashboard/<slug>` без валидной сессии ведёт на `/login`, а не отдаёт 500

## Вне объёма — и чем это грозит

Смена и восстановление пароля — FR-010. Партнёрский вход — FR-011.

**[v2] Принимаемый осознанно риск (R-1 валидации).** Анти-перечисление учёток как
**системное** свойство этой фичей не достигается: `/api/auth/register` на существующий
email отвечает `409 { error: 'аккаунт с таким email уже существует' }`
(`lib/register.ts:74`). Вход закрывает одну дверь из двух. Закрытие второй меняет
поведение регистрации и относится к отдельной фиче; до тех пор NFR-009.1 даёт свойство
**только для входа**, и утверждать большее нельзя.
