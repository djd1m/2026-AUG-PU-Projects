# Потолок расхода · Алгоритмы

## Где ставится счётчик — и почему не там, где кажется

Соблазн — считать в момент **приёма видео** (`POST /api/testimonials/video`). Неверно: между
приёмом и вызовом модели стоит очередь, и одна принятая запись порождает **до трёх** вызовов при
повторах. Счётчик на приёме считал бы заявки, а платим мы за вызовы.

Счётчик ставится в **воркере, непосредственно перед вызовом провайдера**, и увеличивается
**до** вызова, а не после ответа. Ответ может не прийти вовсе — деньги при этом уже потрачены.

```
claimAndProcessOneTestimonial:
    ...скачали видео, извлекли звук...

    # ── потолок проверяется ЗДЕСЬ, между извлечением звука и вызовом модели
    если НЕ spendAllow(day_key, user_key):
        пометить transcript_status = 'failed', причина 'spend_ceiling'
        НЕ повторять: повтор упрётся в тот же потолок и потратит ещё одну попытку впустую
        выйти

    spendRecord(day_key, user_key)          # ДО вызова: платим за попытку, не за успех
    text = вызвать модель                    # может бросить — счётчик уже увеличен, и это верно
```

## spendAllow / spendRecord — на существующем механизме, без новой таблицы

Правило проекта: «не заводить отдельный стор под новое requirement того же класса — расширять
`scope`». Класс тот же: «не более N событий за интервал T по ключу».

```
scope = 'model_call'
ключ суточный      = 'day'                      окно 24 ч   порог DAILY_MODEL_CALLS
ключ пользователя  = ip + ':' + project_id       окно 24 ч   порог USER_MODEL_CALLS

spendAllow  = НЕ превышен(day) И НЕ превышен(user)
spendRecord = записать ОБЕ строки одной транзакцией
```

Обе записи в одной транзакции: иначе при отказе между ними суточный счётчик разойдётся с
пользовательским, и один из них начнёт врать в приятную сторону.

## Конфигурация — незаданный потолок ВАЛИТ ЗАПУСК

```
на старте воркера:
    DAILY = целое из env DAILY_MODEL_CALLS        # нет значения → БРОСИТЬ
    USER  = целое из env USER_MODEL_CALLS         # нет значения → БРОСИТЬ
    если USER > DAILY: БРОСИТЬ                    # иначе персональный не сработает никогда
    если DAILY <= 0 или USER <= 0: БРОСИТЬ        # ноль это не «без ограничений»
```

Текст исключения называет **последствие**, а не факт: «потолок расхода не задан; без него один
посетитель может выставить вам счёт, отменить который нельзя».

Разница с `VIDEO_INTAKE_ENABLED`, которая уже выкачена: тот выключатель fail-closed **молча
закрывает** платный путь, и это верно для выключателя. Потолок молча закрывать нельзя — иначе
«потолок не настроен» станет неотличимо от «видео выключено», и владелец будет чинить не то.

## Видимость расхода (SPEND-5)

```
GET /dashboard/<slug>  → блок «Расход на расшифровку сегодня»
    вызовов сегодня: N из DAILY
    ваш проект: M из USER
```

Считается тем же запросом к `rate_limit_events`, никаких обращений к провайдеру: биллинг
провайдера отстаёт и на вопрос «сколько уже потрачено прямо сейчас» не отвечает.
