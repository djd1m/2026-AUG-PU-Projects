# Agent payments: настройка и границы проверки

Статус внедрения и проверки — в [05_completion.md](05_completion.md).
Этот документ описывает настройку кандидата; наличие инструкции не означает,
что новая версия уже развёрнута на основном публичном Proofwall.

Отдельный [публичный TEST-пилот и инструкция демонстрации](public-pilot.md) уже
развёрнуты. Он использует существующий TEST-магазин с неизменённым webhook и
сверкой известных платежей через API; общие шаги про отдельный магазин ниже
не означают, что для этого пилота требуется менять текущий webhook.

## Состав

- `packages/agent-payments`: переносимое ядро, собственная схема PostgreSQL,
  provider/host ports, лимиты, поручения, заказы и журнал событий.
- `apps/web/src/lib/agent-payments`: адаптер Proofwall, привязка существующего аккаунта,
  email, тарифа, человеческого согласия и атрибуции N3.
- `services/agent-api`: отдельный контейнер MCP/A2A без доступа к БД и PSP credentials.
- `services/worker/src/agent-payments-poll.ts`: периодическая сверка уже отправленных
  платежей через backend; не создаёт новые платежи.

Для другого продукта переносится пакет, реализуются его `HostPort` и транспортные
обработчики идентификации. Не нужно копировать Proofwall UI, N3 или таблицы его тарифов.
Контракт и пример отдельного потребителя — в README и extraction test пакета.

## Подготовка без изменения обычного CJM

1. Собрать и проверить исходную ревизию. Выполнить `npm ci`, собрать ядро,
   затем backend и worker. Web prebuild собирает ядро автоматически.
2. Выполнить обычные миграции `npm run db:migrate`, затем отдельную
   `node scripts/migrate-agent-payments.mjs` с `DATABASE_URL` backend.
   Вторая команда создаёт схему ядра; первая сама её не создаёт.
3. Оставить `AGENT_PAYMENTS_ENABLED=false`. Проверить существующие регистрацию,
   вход, восстановление, обычную покупку и партнёрское начисление.
4. Создать случайный `AGENT_GATEWAY_SECRET` длиной не меньше 32 символов в приватном
   env-файле. Не помещать его в Git, браузер или конфигурацию покупателя.
5. Указать отдельные `AGENT_YOOKASSA_TEST_SHOP_ID` и
   `AGENT_YOOKASSA_TEST_SECRET_KEY` с префиксом `test_`. Существующие
   `YOOKASSA_SHOP_ID/YOOKASSA_SECRET_KEY` обслуживают обычный checkout.
6. Для агентного TEST-магазина указать webhook
   `https://<Proofwall-host>/api/agent-payments/webhook` для уведомлений об оплате
   и возврате. Backend сверяет объект через API провайдера. Возврат в браузер,
   ответ агента и неподтверждённое тело webhook не считаются доказательством оплаты.
7. Добавить overlay `compose.agent-payments.yml`. Перед запуском проверить свободный
   `AGENT_GATEWAY_PORT` (по умолчанию 13041) и итоговую конфигурацию сетей.
   Gateway состоит только в `agent_gateway`; PostgreSQL только во внутренней сети
   backend. У БД нет опубликованных портов. Сети P1 и N3 не объединяются.
8. Задать `AGENT_PUBLIC_ORIGIN`, организовать HTTPS ingress и включить compose profile
   `agent-payments`. Сам профиль не включает выдачу финансовых полномочий.
9. Для восстановления задать worker
   `AGENT_RECONCILE_URL=http://web:3000/api/agent-payments/reconcile` и тот же service key.
   Его единственная операция — проверка сохранённых попыток, каждые 30 секунд,
   без пересекающихся запросов. Ошибка этой интеграции не останавливает другие задачи.
10. Включать `AGENT_PAYMENTS_ENABLED=true` только после проверок кандидата. Отключение
    новых агентных действий не является отменой уже отправленного платежа: сохранять
    credentials и обработку webhook/reconciliation для незавершённых попыток.

Нельзя запускать overlay со старым backend image из `compose.bridge-release.yml`:
в нём нет новых обработчиков. Новые имена образов должны ссылаться на проверенный commit.

## Кто участвует в платеже

| Этап | Агент | Человек / провайдер |
|---|---|---|
| Подключение | Запрашивает ссылку подключения | Вход, email, проект, выдача ограниченного ключа |
| Предложение и заказ | Получает серверную цену, сохраняет requestKey и orderId | Действие не означает списание |
| Первая покупка | Возвращает ссылку подтверждения | Явное согласие; hosted checkout и требуемая PSP аутентификация |
| Сохранение метода | Не получает реквизиты или токен метода | Отдельное согласие на сохранение у PSP |
| Поручение на продление | Не может выдать его себе | Отдельное согласие с фиксированными условиями |
| Допустимое продление | Запрашивает исполнение | Backend проверяет лимит, срок, тариф и метод; PSP может потребовать участие |
| Результат | Читает состояние заказа | Backend сверяет PSP и применяет тариф/комиссию |
| Неизвестный результат | Читает тот же заказ | Сверка по сохранённому ID; иногда требуется разбор оператором |

Текущая политика Proofwall: 990 ₽ за 30 дней, продление в последние 3 дня тарифа,
поручение не дольше 90 дней, общий предел автоматических покупок 990 ₽ за календарный
месяц по Москве. Ручные дополнительные покупки допустимы, но учитываются в доступном
автоматическом бюджете. Возврат не восстанавливает лимит автоматического расхода.

Ключ подключения агента действует 24 часа. После его истечения в этой версии нужно
снова подключить агента через человеческий аккаунт, даже если поручение на 90 дней
ещё действует. Поэтому это интерфейс покупки по запросу агента, а не готовое
автоматическое списание каждый месяц без участия человека. Самостоятельного расписания
списаний и обновления buyer credentials здесь нет; worker только сверяет уже начатые платежи.

## Честная оценка готовности

Проверки SDK, PostgreSQL, провайдерских fixtures и браузера с тестовым HTTP-провайдером
дают разные доказательства. Ни одна из них не подтверждает фактическое включение
автоплатежей у настоящего магазина ЮKassa. Отдельная приёмка требует реального TEST-магазина,
первого hosted-платежа с согласием на сохранение и подтверждения пригодности сохранённого
метода. Live-списания этим этапом не разрешены.

CloudPayments/AP2/ACP/UCP не объявлены подключёнными адаптерами. Исследование совместимости:
[agentic-payments-build-vs-buy.md](../../research/agentic-payments-build-vs-buy.md).

## Как воспроизвести демонстрацию

Изолированный [браузерный сценарий и команда запуска](../../../tests/agent-payments-e2e/README.md)
проверяет настоящее приложение, MCP SDK и A2A с локальными ответами PSP и Resend.
Это воспроизводимая техническая демонстрация; публичный агентный URI ещё не развёрнут.

1. Агент запрашивает подключение и передаёт человеку approval URL.
2. Человек регистрируется или входит обычным способом, затем повторно открывает
   исходную ссылку подключения: текущий login не сохраняет `pairingId` в `next`.
3. Человек подтверждает email и выдаёт ключ агенту. Polling ключ не возвращает.
4. Агент получает предложение и создаёт заказ. Попытка оплатить одним ключом
   возвращает необходимость человеческого подтверждения без списания.
5. Человек подтверждает первую покупку и отдельно сохранение метода у провайдера.
   После подтверждённого PSP-события появляется оплаченный тариф.
6. Человек выдаёт отдельное ограниченное поручение на продление. В тесте календарная
   история синтетического аккаунта переводится в следующий расчётный период,
   тариф — в последние два дня. Это подготовка теста, не реальное ожидание месяца.
7. Агент выполняет допустимое продление. Повтор команды не создаёт второй платёж.
8. Человек отзывает ключ; следующий запрос агента отклоняется.

Зафиксированный прогон: 11/11 проверок, ровно два создания платежа у локального
провайдера. Отдельная человеческая матрица A–D сохранила покупку, комиссию и возврат
без ключей агента или поручений; результаты приведены в [Completion](05_completion.md).
