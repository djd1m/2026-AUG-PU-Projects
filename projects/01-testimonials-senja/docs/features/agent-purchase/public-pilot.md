# Публичный TEST-стенд агентных покупок

Статус на 2026-09-10: развёрнут; браузерная приёмка агентной покупки,
продления и отзыва доступа с настоящим TEST-магазином прошла.

## Адреса

- Приложение: https://proofwall-agent.212.192.0.33.sslip.io/
- Вход: https://proofwall-agent.212.192.0.33.sslip.io/login
- Подтверждения и полномочия: https://proofwall-agent.212.192.0.33.sslip.io/agent-payments
- MCP Streamable HTTP: https://proofwall-mcp.212.192.0.33.sslip.io/mcp
- A2A JSON-RPC: https://proofwall-mcp.212.192.0.33.sslip.io/a2a

Это отдельная БД: существующий аккаунт основного Proofwall сюда не переносился.
Создайте тестовый проект на главной странице и войдите созданным аккаунтом.
Используется действующий TEST-магазин ЮKassa проекта 1, не локальная имитация PSP.
Обычный сайт https://proofwall.aicoding.space/ остаётся на прежнем образе.

## Как провести демонстрацию

1. Откройте главную страницу, создайте проект и войдите. Откройте страницу
   `/agent-payments`, отправьте письмо подтверждения и откройте ссылку в том же
   браузере. Нажмите «Подтвердить почту».
2. Агент вызывает `buyer_link_start`. Для демонстрации без настройки MCP-клиента
   можно использовать A2A из терминала:

   ```sh
   curl -fsS https://proofwall-mcp.212.192.0.33.sslip.io/a2a \
     -H 'Content-Type: application/json' \
     --data '{"jsonrpc":"2.0","id":"demo-link","method":"message/send","params":{"message":{"kind":"message","role":"user","messageId":"demo-link","parts":[{"kind":"data","data":{"command":"buyer_link_start","input":{"displayName":"Демо-агент","audience":"proofwall-agent-api"}}}]}}}'
   ```

3. Откройте `result.parts[0].data.approvalUrl` из ответа. Ссылка подключения живёт
   10 минут. Выберите свой проект, прочитайте условия и подтвердите подключение.
   Если потребовался login, после входа снова откройте исходную ссылку подключения.
4. Передайте показанный один раз ключ своему агенту как `Authorization: Bearer`.
   Не отправляйте ключ в общий чат, GitHub или демонстрационную запись экрана.
5. Агент выполняет `offer_get` с `productId: proofwall-paid-30-days`, затем
   `order_create` с полученным `quoteId` и новым стабильным `requestKey`, затем
   `payment_execute` с полученным `orderId`. Формат A2A тот же, меняются `command`
   и `input`; для этих команд требуется buyer Bearer. Одного ключа недостаточно
   для автоматического списания: результат потребует подтверждения человеком.
6. Откройте возвращённую ссылку. Человек явно подтверждает покупку и отдельно
   выбирает сохранение метода оплаты. На hosted-странице ЮKassa используйте
   **только тестовую карту из официальной инструкции**, не настоящую карту.
7. После оплаты агент читает тот же заказ через `order_get`. Сам возврат в браузер
   ещё не подтверждает оплату: backend проверяет ЮKassa; worker повторяет сверку
   примерно каждые 30 секунд. В дашборде появляется платный тариф.
8. Отдельно выдайте поручение на продление. Сразу после покупки продление
   закономерно запрещено: тариф ещё не в последних трёх днях и бюджет месяца
   уже использован. В техническом E2E время моделируется только для созданного
   тестового аккаунта; обычному пользователю условия не обходятся.
9. Отзовите ключ на странице полномочий и проверьте отказ следующего запроса агента.

Тестовые карты и поведение подтверждений:
[официальная инструкция ЮKassa](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing).
Сохранение метода считается подтверждённым только после проверки `payment_method.saved`
через API, а не по отметке checkbox.

## Границы этого стенда

- N3 здесь пока выключен. Действующая программа N3 привязана к основному Proofwall;
  её адрес и connector не изменялись ради пилота. Полная агентная цепочка до комиссии
  требует отдельной конфигурации и не считается проверенной этой демонстрацией.
- Webhook существующего TEST-магазина не перенастраивался. Пилот сверяет известные
  payment ID через API. Возврат и потерянный ответ создания требуют отдельной
  операторской сверки; это не готовая автоматическая обработка всех уведомлений.
- В пилоте проверяйте оплату через описанную агентную цепочку. Обычный checkout
  из дашборда пока не имеет автоматической доставки своего webhook в отдельную
  БД пилота; успешная оплата там не гарантирует автоматического включения тарифа.
  Обычную человеческую покупку продолжайте проверять на основном Proofwall.
- Ключ агента действует 24 часа; поручение до 90 дней не продлевает ключ.
- Yandex ID и видео в этом изолированном платёжном стенде не подключены.
- БД/MinIO не публикуют портов. Gateway не подключён к БД и не получает ключ ЮKassa.

## Развёртывание и восстановление

`compose.agent-pilot.yml` создаёт отдельный проект `proofwall-agent-pilot`.
Секреты в игнорируемой `.secrets/agent-pilot/`, пароль БД, session и gateway secrets
сгенерированы отдельно. Миграции применены только к новой БД.

Существующий Caddy подключён только к `proofwall-agent-pilot_ingress`. При его
пересоздании эту связь нужно восстановить и применить актуальный host Caddyfile.
Файловый bind mount текущего прокси указывает на старый inode, поэтому reload
по `/etc/caddy/Caddyfile` прочитает устаревший файл. Применять проверенное содержимое
host-файла через stdin с `--adapter caddyfile`; не перезаписывать чужие маршруты.
Это явный шаг восстановления, а не автоматически установленный deployment controller.

Для остановки пилота: `docker compose -f compose.agent-pilot.yml stop`.
Удаление volumes не требуется. Остановить только этот compose-проект; основной
Proofwall, N3 и общий proxy не останавливать.

[Телеметрия, образы и независимый обзор](../../telemetry/p-replicator/20260910-agent-payments-public-pilot/run.json).

## Результат фактической проверки

- Настоящие публичные HTTPS, Firefox, MCP SDK, A2A, Resend и API ЮKassa.
- Первая покупка: 990 ₽ TEST, подтверждение человеком, `saved=true`, тариф активен.
- Продление: 990 ₽ TEST по сохранённому методу и отдельному поручению;
  без повторного ввода карты. Для одного E2E-аккаунта смоделированы дата
  продления и предыдущий расчётный месяц; политика приложения не менялась.
- Повтор команд: в БД ровно два заказа, две попытки, две записи резервирования.
- Отзыв поручения и ключа через браузер: следующий запрос A2A отклонён (401).
- Основные публичные P1/P2/N3 A–D: 8/8 страниц прошли браузерную проверку.

Во время первоначальной настройки Caddy возник краткий сбой маршрутизации N3:
reload прочитал старый bind-mounted файл. Актуальный файл применён через stdin,
после исправления восстановление проверено браузером. Этот прогон не подтверждает
отсутствие перерыва доступности. Образы основных приложений не заменялись.
