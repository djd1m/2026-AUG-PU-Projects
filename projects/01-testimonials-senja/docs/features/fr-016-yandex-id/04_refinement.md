| Случай | Ожидание | Критерий |
|---|---|---|
| Новый человек | учётка без пароля, вход выполнен | AC-016.1 |
| Повторный вход тем же Яндексом | та же учётка | AC-016.2 |

| Повторный коллбэк с тем же кодом | отказ, второй учётки нет | AC-016.9 |
| Два одновременных коллбэка с одним кодом | успешен ровно один | AC-016.10 |
| Провайдер ответил `5xx` или молчит | понятный отказ, учётки нет, сессии нет | AC-016.14 |
| Секретов нет в проде | отказ при старте потока | AC-016.15 |

## Конкурентная проверка (S5)

Два одновременных коллбэка с одним кодом — не выдумка: браузер повторяет запрос при
разрыве, а пользователь жмёт «назад». Последовательный тест этого не различает:

```
два одновременных callback с одним externalId -> ровно одна учётка, ровно одна привязка
```

При проверке-перед-вставкой оба увидят «идентификатора нет» и создадут **две** учётки на
один яндексовый аккаунт — и человек будет попадать то в одну, то в другую.

## Как проверяется без сети

Сетевой слой (`lib/sso.ts`) отделён от политики (`lib/sso-account.ts`). Политика тестируется
на живой БД без единого сетевого вызова — ей на вход подаются `externalId` и `email`.
Сетевой слой тестируется подменённым `fetch`: коды ответов, таймаут, форма ответа Яндекса.

Это и даёт возможность проверить `AC-016.4` — главный критерий фичи — без учётной записи
разработчика у провайдера.
