# FR-016 · Спецификация: вход через Yandex ID

## Зачем

П. 10 ст. 8 149-ФЗ предписывает **закрытый перечень** способов авторизации пользователей,
находящихся в РФ. Собственная пара «email + пароль» прямо в нём не названа; единственная
зацепка — подпункт 4 («иная информационная система… владелец которой российское лицо»), у
которого два прочтения и **нет официальных разъяснений**. Штрафы по ст. 13.55 КоАП действуют
с 07.07.2026 — до 700 тыс. руб. на юрлицо.

Российский SSO переводит вопрос из спорной трактовки в прямо разрешённое текстом.

**Честная граница.** Прямых заявлений «Яндекс ID соответствует п. 10 ст. 8 149-ФЗ» в
официальной документации Яндекса **не найдено** — это консенсус юридических обзоров, а не
гарантия провайдера. Фича снимает риск узкого прочтения, но не заменяет правовую оценку.

## Несущее решение: автосвязывания по email НЕТ

Проверено по документации: `login.yandex.ru/info` **не отдаёт признака подтверждённости**
адреса — полей вида `email_verified` в ответе нет вовсе, и приложение программно не может
отличить подтверждённый адрес от вписанного. Провайдер Yandex в Auth.js берёт `default_email`
без проверки, а сама Auth.js называет связывание по email **`allowDangerousEmailAccountLinking`** —
опасность вынесена в имя настройки.

Отсюда два следствия, и оба несущие.

**Ключ учётной записи — идентификатор Яндекса, а не email.** Email хранится как атрибут и
служит подсказкой в сообщениях, но связь «человек ↔ учётка» держится на `id`.

**Связывание происходит только из аутентифицированной сессии.** Тогда человек доказывает
владение обеими сторонами разом: паролем Proofwall и прохождением OAuth Яндекса.

| Вход через Yandex ID | Что делаем |
|---|---|
| Идентификатор известен | Впускаем — это привязанная учётка |
| Идентификатор неизвестен, адреса нет в базе | Создаём учётку, `password_hash` пуст |
| Идентификатор неизвестен, адрес есть, у учётки **нет пароля** | Впускаем и привязываем: других способов входа у неё нет, подмены не возникает |
| Идентификатор неизвестен, адрес есть, у учётки **есть пароль** | **Не впускаем.** «Аккаунт с этим адресом уже есть — войдите паролем и привяжите Яндекс ID в настройках» |

Последняя строка — вся защита. Без неё атака работает в обе стороны:
- атакующий ставит адрес жертвы в свой яндексовый профиль и входит в её кабинет;
- атакующий заранее регистрирует в Proofwall учётку на адрес жертвы со своим паролем, и жертва,
  войдя через Яндекс, попадает **в чужую** учётку, к которой у атакующего есть пароль.

Второе направление не лечится подтверждением адреса на нашей стороне — только отказом от
автосвязывания.

## Дельта разделяемых ресурсов — заполнена ДО кода

| Ресурс | Было | Стало | Кто ещё в очереди | Кого наказывает насыщение |
|---|---|---|---|---|
| **внешние вызовы** | ЮKassa (2, в `apps/web`), почта FR-015, транскрибация | **+2**: обмен кода на токен, чтение профиля | весь пул, если вызвать внутри транзакции | всех — оба вызова вне транзакции и с таймаутом |
| соединение пула | — | одна короткая транзакция после того, как оба вызова завершились | вход, дашборд, витрина, виджет, приём отзывов, кабинет партнёра, импорт, восстановление | всех — потому транзакция и открывается последней |
| поток событий (синхронная работа) | — | разбор JSON профиля, единицы килобайт | всё приложение | не задет при таком размере |
| CPU | — | не задет: argon2 на пути SSO не считается вовсе | argon2 входа и смены пароля | не задет |
| память: вход | — | ответ провайдера, единицы килобайт | — | не задет |
| память: выход | — | не задет | — | не задет |
| блокировки строк | — | строка `accounts` при связывании | вход (`insert into sessions` берёт `FOR KEY SHARE`) | **никого — блокировки не берём**, связывание ограничением БД |
| счётчики и квоты | — | свой scope на коллбэк | общая `rate_limit_events` | адрес — ключ по IP, учётки на этом пути ещё нет |
| **состояние между запросами** | **нового класса нет** | `state` и `code_verifier` между стартом и коллбэком | — | **новое: cookie-состояние, живущее между двумя запросами** |

Последняя строка нового класса: до `FR-016` в проекте не было состояния, которое надо
пронести между двумя HTTP-запросами и проверить на возврате. Отсюда NFR-016.4.

## Нефункциональные требования `@security`

| # | Требование | Почему несущее |
|---|---|---|
| NFR-016.1 | Ключ учётной записи — идентификатор Яндекса, никогда email | Признака подтверждённости адреса провайдер не отдаёт |
| NFR-016.2 | Учётка **с паролем** не привязывается автоматически ни при каком совпадении адреса | Иначе захват в обе стороны, см. выше |
| NFR-016.3 | Оба вызова к провайдеру — **вне транзакции** и **с таймаутом** | Четвёртый и пятый внешние вызовы проекта. Первая же попытка сформулировать это в FR-015 опиралась на ложную посылку «внешних вызовов не было», и у существующих их не оказалось |
| NFR-016.4 | `state` обязателен и одноразов; PKCE обязателен | Без `state` — CSRF на коллбэке: атакующий подсовывает свой код и привязывает свою учётку к чужой сессии |
| NFR-016.5 | Код авторизации погашается атомарно; повтор отвергается | Тот же класс, что токен восстановления: проверка-перед-записью оставляет окно |
| NFR-016.6 | Сессия выдаётся **только** через `createSession` | Единственная точка выдачи, закреплена стражем |
| NFR-016.7 | `password_hash` становится nullable; `NULL` означает «пароля нет» и не открывает вход | `login.ts:127` уже коалесцирует в заглушечный хеш — свойство есть, теста нет |
| NFR-016.8 | Секреты провайдера — без права на дефолт в проде | Тот же класс, что `RESEND_API_KEY` |

## Критерии приёмки

| # | Критерий | Падает при |
|---|---|---|
| AC-016.1 | Новый пользователь через Яндекс: учётка создана, `password_hash` пуст, вход выполнен | — |
| AC-016.2 | Повторный вход тем же Яндексом ведёт в **ту же** учётку | ключ по email вместо идентификатора |
| AC-016.3 | Смена email в яндексовом профиле **не создаёт** новую учётку | то же |
| AC-016.4 | **Учётка с паролем и совпадающим адресом не привязывается**: отказ с объяснением | автосвязывание по email |
| AC-016.5 | Учётка без пароля и совпадающим адресом привязывается и впускает | — |
| AC-016.6 | Учётка с `password_hash = NULL` **не входит никаким паролем**, включая пустой, и неотличима по времени от несуществующей | заменить `?? dummyHash()` на ранний возврат |
| AC-016.7 | Смена пароля на учётке без пароля даёт отказ, а не `500` | `verifyPassword(null, …)` бросит |
| AC-016.8 | Коллбэк без `state` / с чужим `state` / с истёкшим `state` → отказ | не проверять `state` |
| AC-016.9 | Повторный коллбэк с тем же кодом → отказ, второй учётки не создаётся | проверка-перед-записью вместо атомарной |
| AC-016.10 | Два одновременных коллбэка с одним кодом: успешен ровно один | то же |
| AC-016.11 | **Страж:** оба вызова к провайдеру вне `withService`/`withAccount` | занести в транзакцию |
| AC-016.12 | **Страж:** у каждого вызова задан таймаут (проверяется по всем внешним вызовам `apps/web`) | убрать `signal` |
| AC-016.13 | **Страж:** `insert into sessions` по-прежнему ровно в одном файле | вписать выдачу сессии в SSO-модуль |
| AC-016.14 | Провайдер ответил ошибкой или таймаутом → понятный отказ, учётка не создана, сессия не выдана | глотать ошибку |
| AC-016.15 | Секреты провайдера отсутствуют в проде → отказ при старте потока, а не тихий пропуск | дефолт `''` |
| AC-016.16 | Порог попыток коллбэка достигается настоящими вызовами; превышение → `429` | убрать лимитер |
| AC-016.17 | Ни `code`, ни `access_token`, ни `state` не попадают в журнал | залогировать при отладке |
| AC-016.18 | Маршруты в списке стража предела тела; формы в `PAGES` | — |
