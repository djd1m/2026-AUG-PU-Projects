## Ответы на шесть заданных вопросов

### 1) Растёт ли перевыполнение порога линейно с N? — НЕТ, но обещанное число ложно

Залп с одного адреса, порог 30, неверный токен, `Promise.allSettled` поверх пула из 30:

```
N= 40   дошло до сверки = 40   429 = 0     ошибок = 0   105 мс
N=100   дошло до сверки = 54   429 = 46    ошибок = 0    61 мс
N=500   дошло до сверки = 49   429 = 451   ошибок = 0   193 мс
```

Читается так: **потолок ≈ порог + размер пула ≈ 50-60**, дальше не растёт — соединений
больше нет, ожидающие входят уже после того, как записи легли, и получают `429`. Никаких
`POOL_TIMEOUT`, соседний путь не пострадал (`select 1` во время залпа: p95 = 15 мс).
Ревизия 4 по существу верна.

Ложно ровно одно: **число 37**. Оно измерено для ревизии 2 (`try`-лок по паре), где стояло с
пометкой «← дефект» (`validation-report.md:23,465`), и перенесено в отгруженный
NFR-011.4 как «принятая цена» ревизии 4. Для ревизии 4 его никто не мерил. Настоящее
значение при N=40 — **40 из 40**, то есть на этом залпе счётчик не отклоняет НИ ОДНОЙ
попытки, и отгруженный код в этой точке строго хуже конструкции, которую отвергли блокером.

### 2) Ограничен ли показ кабинета? — ДА, и это сделано правильно

`dashboard/page.tsx:39-43` зовёт ту же `resolvePartner`, неудача записывается в тот же
`scope`, при исчерпании страница уходит в `redirect('/partner')` — неотличимо от «токен не
подошёл», оракула нет. Прежняя схема с двумя транзакциями и обходом счётчика в коде
отсутствует. Единственная оговорка — H-3 ниже: ключ счётчика у двух дверей выводится разным
кодом.

### 3) Может ли владелец ВЕРНОГО неотозванного токена грузить систему бесплатно? — ДА, безлимитно

Это H-1, разобран ниже. 200 последовательных успешных сверок с одного адреса → **0 записей в
счётчик**. 100 одновременных полных показов кабинета одним токеном → **100 обслужено, 0
отказано**.

### 4) Стоит ли лишний round-trip в `getPartnerCohortDashboardById` того? — НЕТ, цель достижима дешевле

Измерено: **6 запросов на один показ** (без `BEGIN`/`SET ROLE`/`COMMIT`), из них **три — по
`partner_codes` за одной и той же строкой**: сверка по хешу, затем `id → code`, затем
`code → id, partner_name, status`. Цель — «`code` не едет дальше по стеку, ошибка „взяли
партнёра из адреса“ невозможна по сигнатуре» — сформулирована верно и достойна цены. Но она
достигается и без лишнего запроса: параметризовать основную выборку по `id`, а функцию по
`code` оставить тонкой обёрткой (`select id from partner_codes where code = $1` → вызов
по id). Сигнатура кабинета не меняется, запросов на показ становится 5 вместо 6. Оставить
как есть — тоже допустимо; это L-1, не блокер.

### 5) Инъекция в конкатенации `columns`/`values`? — НЕТ

`partner.ts:54-56`: обе строки собираются из литералов по булеву `withRate`, снаружи в них
не приходит ничего — ни имя колонки, ни фрагмент SQL. Значения все параметризованы
(`$1..$5`), включая `partnerName` и `commissionRate`. Инъекции нет. Замечание по форме — L-6.

### 6) Миграция 012: NULL сосуществуют, дубликат отвергается? — ДА, проверено на БД

```
два кода без токена сосуществуют: true
дубликат хеша: duplicate key value violates unique constraint "partner_codes_dashboard_token_hash_idx"
```

Уникальный индекс по nullable-колонке ведёт себя ровно как обещает комментарий миграции.

## HIGH

### H-1. Путь УСПЕХА не ограничен ничем — и это тот самый снятый аргумент из FR-010 H-1

**Пятое повторение класса.** Ревизия 4 убрала лок — правильно. Вместе с ним из фичи ушёл
последний механизм, ограничивавший стоимость успешного обращения, и это обосновано
`partner-auth.ts:24-26`:

> ЗАПИСЫВАЕТСЯ ТОЛЬКО НЕУДАЧА — как NFR-009.4 входа: «запись при успехе заперла бы активного
> владельца им самим».

Ссылка на FR-009 корректна, но неполна: **предыдущая фича этот аргумент уже опровергла.**
`password-change.ts:130-131`, находка ревью H-1 (коммит `ee2cee7`):

> Успешные смены тоже стоят двух argon2 каждая (H-1). Прежний комментарий утверждал, что путь
> успеха «самоограничивается…» — неверно.

И там же решение, которое снимает возражение «запер бы владельца им самим»: **отдельный
scope по ЛИЧНОСТИ, а не по адресу** — `PWCHANGE_SUCCESS_SCOPE`, ключ `hashKey(scope,
accountId)`, порог 10/час. Партнёр за NAT не мешает соседу, потому что ключ не адрес.

**Сценарий отказа.** Партнёр, с которым расстались, но код которого не отозвали (отзыв —
ручное действие, административного маршрута нет, см. M-5); или утёкшая cookie; или просто
партнёр с агрессивным авто-обновлением вкладки. Каждый показ: 1 соединение общего пула из 30
и 6 запросов, из них 4 — по `partner_codes`. Ограничения нет ни по адресу, ни по токену, ни
по партнёру.

**Замерено.**

```
200 последовательных успешных сверок с одного адреса -> успешных 200/200, записано в счётчик 0
100 одновременных полных показов ОДНИМ токеном       -> показано 100, отказано 0, ошибок 0, 190 мс
   соседний путь во время залпа (select 1)           -> p50 27 мс, p95 151 мс (базовый p95 = 15 мс)
```

Последняя строка — **слабое** свидетельство: пробник успел сделать всего 3 замера за 190 мс
залпа. Порядок величины (десятикратный рост латентности соседа) указывает в правильную
сторону, но числом я его не называю.

**Вопрос 3 из `.claude/rules/shared-resource-verification.md` («кто ещё стоит в очереди за
тем же ресурсом?») для пути успеха не задан.** В очереди стоят витрина, виджет, форма приёма
отзывов и дашборд владельца — тот же пул на 30.

**Починка (одна на семь строк, форма уже написана в соседней фиче):**
`PARTNER_SUCCESS_SCOPE = 'partner_dashboard_success'`, ключ `hashKey(scope, partnerCodeId)`,
порог щедрый (60-120/час — партнёр смотрит кабинет, а не долбит его), проверка ПОСЛЕ
успешной сверки, запись там же. Партнёр не запирает ни себя (порог по личности, а не 30 по
адресу), ни соседа за NAT.

### H-2. Принятая цена — число из отвергнутой ревизии; отгруженный код показывает 40 из 40

`partner-auth.ts:21-22`, `01_specification.md:68` (NFR-011.4), `02_pseudocode.md:140`:

> Принятая цена приблизительного счётчика названа числом: при залпе N=40 с одного адреса
> проходит ~37 попыток вместо 30.

Происхождение числа — `validation-report.md:23`:

```
рев.2  try-лок по паре (ip, хеш токена)  ->  ДОШЛО_ДО_СВЕРКИ 37   записей 37   ← дефект
```

и `validation-report.md:465`: «рев.1 / рев.2 / рев.3 → **2 / 37 / 30**». 37 — это ревизия 2,
и она была признана блокером B-1. Ревизия 4 взяла это число себе в качестве принятой цены,
не измерив собственное.

**Измерено для отгруженного кода: 40 из 40 при N=40.** Это не «на семь запросов больше», это
«счётчик на этом залпе не отклонил ни одного». Класс — тот же, что `.claude/rules/
fail-closed-defaults.md` называет для метрик: число, которое никто не проверял на том, что
оно описывает, хуже отсутствия числа, потому что читается как измерение.

**Сценарий отказа не в безопасности** (2^256 перебором не берут ни с локом, ни без), а в
том, что калибровка порога будет опираться на ложную базу: увидев «30 при пороге 30», автор
следующей ревизии решит, что запас есть.

**Починка:** заменить число на измеренное и, главное, на ПРАВИЛЬНУЮ величину — потолок
≈ `порог + PGPOOL_MAX`, потому что перевыполнение ограничивает пул, а не счётчик. Плюс тест,
стерегущий именно потолок (при N=500 дошло ≤ 60), а не единичное значение при N=40.

### H-3. Две двери — два разных вывода ключа счётчика; в 4 случаях из 6 ключ расходится

`dashboard/page.tsx:17-27` — вторая, независимая реализация разбора `X-Forwarded-For`, с
комментарием:

> Тот же разбор, что у маршрутов: последний элемент X-Forwarded-For от прокси.

Разбор **не тот же**: в нём нет `looksLikeIp` и нет снятия скобок IPv6, которые есть в
`client-ip.ts:23-46`. Измерено сравнением ключей `hashKey(PARTNER_IP_SCOPE, ip)`:

```
СОВПАЛ     IPv4 за прокси            маршрут="1.2.3.4"        кабинет="1.2.3.4"
РАЗОШЁЛСЯ  IPv6 в скобках            маршрут="2001:db8::1"    кабинет="[2001:db8::1]"
РАЗОШЁЛСЯ  последний элемент — мусор маршрут="unknown"        кабинет="not-an-address"
РАЗОШЁЛСЯ  последний — не IP         маршрут="unknown"        кабинет="999.999.999.999"
РАЗОШЁЛСЯ  x-real-ip мусорный        маршрут="unknown"        кабинет="garbage-x-real-ip"
СОВПАЛ     XFF пустой                маршрут="unknown"        кабинет="unknown"
```

**Что это значит.** Заявленное «одна охрана на две двери» держится ТОЛЬКО на том, что Caddy
дописывает валидный IPv4 последним элементом. Как только последний элемент управляется
клиентом — прямой доступ мимо прокси, второй прокси в сети `talk-ai-public`, смена Caddy на
конфигурацию с `X-Real-IP` — дверь кабинета выдаёт **свежее ведро счётчика на каждый
запрос**, а дверь POST схлопывает то же значение в `unknown`. Порог 30 на кабинете
обнуляется сменой заголовка, ровно как это было воспроизведено в FR-009 (`client-ip.ts:13-21`).

Сегодня это НЕ эксплуатируется: `docker-compose.yml` объявляет `web` без `ports:`, только
`expose`. То есть перед нами не дыра, а **вторая копия несущего рассуждения**, живущая по
собственным правилам — ровно то, что запрещает шапка `request-body.ts:3-6`: «копия в каждом
роуте была бы не дублированием, а миной: предел разъехался бы, и закрытой осталась бы одна
дверь из двух».

**Починка:** расширить `extractClientIP` перегрузкой по `Headers` (или вынести
`extractClientIPFromHeaders(h: Headers)`, а `extractClientIP(request)` сделать обёрткой) и
звать её из страницы. Минус 11 строк, копия исчезает. Плюс страж по исходнику: в
`app/partner/**` не должно встречаться `x-forwarded-for`.

### M-1. Ротация токена не пишет в `audit_log`, хотя выдача и отзыв пишут

`partner.ts:97-104`. `issuePartnerCode` пишет `partner_code_issued`, `revokePartnerCode` —

жалуется «кабинет перестал открываться» — в журнале нет ни события, ни момента, ни актора.
Актора функция даже не принимает: у неё нет параметра `actorId`, в отличие от обеих соседок.
Тест AC-011.21 запрещает `audit_log` в `partner-auth.ts` и в маршруте — `partner.ts` не
запрещён, починка ничего не ломает.

### M-2. `rotateDashboardToken` не смотрит на `status` — ротирует отозванный код и возвращает мёртвый токен

`partner.ts:100`: `update partner_codes set dashboard_token_hash = $1 where code = $2` — без
`and status = 'active'`. Владелец ротирует код, который сам же отозвал, получает
правдоподобный токен, передаёт его партнёру, и `resolvePartner` его не примет никогда
(`partner-auth.ts:94` требует `status = 'active'`). Возврат `null` означает «такого кода
нет», а «код есть, но мёртв» отдаётся тем же значением, что успех. Тихий отказ на
административном пути. Починка — добавить условие в `where` и вернуть `null`.

### M-3. `secure: true` жёстко, в обход единственной точки настроек cookie

`route.ts:63-69` собирает опции cookie на месте, тогда как для сессии владельца существует
`sessionCookieOptions()` (`session.ts:48-63`) с прямо противоположным решением и записанной
причиной:

> Secure выключается только вне production: на localhost по http браузер иначе выбросит
> cookie и разработка встанет.

Два следствия. Первое: на стенде по plain HTTP (не localhost) вход в кабинет даёт петлю —
`login-form.tsx:27` уводит на `/partner/dashboard`, cookie браузером не сохранена,
`page.tsx:32` уводит обратно на `/partner`, и наружу это выглядит как «форма не работает».
Второе, важнее: это ВТОРАЯ копия опций cookie, и она уже разошлась с первой в первый же
день — тот же класс, что H-3. Починка: `partnerCookieOptions()` рядом с
`sessionCookieOptions()`, отличается только `path` и `maxAge`.

### M-4. Чек-лист готовности не заполнен: колонка «Тест» пуста во всех 27 строках

`05_completion.md` — таблица «Критерий → тест → испытание», колонка «Тест» содержит `—` в

Второе: колонка «Испытан внедрением» ссылается на мутации N1–N28, но следа их прогона в

### M-5. Принятый риск ссылается на скрипт выдачи, которого нет

`05_completion.md`, риск 6: «Выдача и ротация выполняются владельцем вручную скриптом на

grep'ом по `apps`, `services`, `packages`). Сам факт отсутствия административного маршрута

сегодня ни один партнёр не может получить токен без того, чтобы кто-то написал разовый код
на сервере. Это не дефект кода; это пункт, который нельзя отмечать как закрытый.
Минимальная починка — `scripts/partner-issue.mjs` на десять строк, либо честная замена
формулировки на «маршрута и скрипта нет, выдача — разовый код».

## Что сделано хорошо и не должно потеряться

- **Отказ без причины выражен ТИПОМ** (`partner-auth.ts:55-61`): вызывающий физически не может
  различить «нет токена» / «код отозван» / «мусор». Это сильнее, чем дисциплина в маршруте.
- **Ротация в ТОЙ ЖЕ строке**, а не перевыпуск кода — и тест это стережёт сравнением `id`
  до и после (`partner-dashboard.test.ts:167-169`). Разрез когорты надвое был бы тихим.
- **Починка `commissionRate`** (`partner.ts:54`): явный `NULL` отменял `default 0.3000`, и
  кабинет показывал бы ноль каждому партнёру навсегда, объясняя это «честным отображением».
  Дефект чужой, предъявлял бы его пользователю этот кабинет — взят в объём правильно.
- **Стражи по исходнику** (AC-011.20, AC-011.21, AC-011.23) стерегут СВОЙСТВО кода, а не
  поведение одного прогона: «запросы к партнёрским таблицам только в трёх модулях» переживёт
  рефакторинг, которого не переживёт поведенческий тест.
- **Тест изоляции написан на двух партнёрах с РАЗНЫМИ ненулевыми числами** — на одном
  партнёре мутация «убрать `where partner_code_id`» прошла бы незаметно. Проверено: она
  красит три теста.

## НЕ ПРОВЕРЕНО

Честный перечень того, на что этот отчёт не даёт ответа.

1. **Живой стенд не поднимался.** Всё измерено на уровне библиотеки и тестовой Postgres.
   Страница `/partner/dashboard` как React-компонент **не рендерилась ни разу** — ни в
   Next.js, ни в браузере. Маршрут прогонялся как функция `POST(Request)`, а не по HTTP.
   `.claude/rules/deployment-seams.md` прямо говорит, что дефект этого класса живёт именно
   там, куда я не дошёл.
2. **Поведение cookie в браузере.** M-3 (петля входа при `secure: true` по plain HTTP)
   выведено из кода и из комментария `session.ts:57-59`, а не воспроизведено. На localhost
   современные браузеры Secure-cookie по http принимают — там петли не будет.
3. **Форма входа не открывалась.** Отображение ошибки, состояние `busy`, поведение при 429
   (`TOO_MANY` вместо «ключ не подошёл») глазами не проверено.
4. **Настоящая конкуренция под Next.js.** Залпы делались `Promise.allSettled` поверх пула в
   одном процессе. Сколько одновременных рендеров даёт инстанс Next и как это меняет потолок
   перевыполнения (H-2) — не измерено.
5. **Миграция на боевой БД.** Тестовая база свежая; поведение `add column if not exists` +
   `create unique index` на таблице с реальным объёмом и существующими кодами (блокировка на
   время построения индекса) не проверялось.
6. **Сквозной путь** регистрация → атрибуция → оплата → комиссия → кабинет не прогонялся.
   Проверено только, что все 575 тестов проекта зелёные, включая 18 тестов `partner.test.ts`.
7. **`p95 = 151 мс` соседнего пути** (H-1) — 3 замера. Это указание, не измерение.
8. **Утечка токена через журналы Next.js** (не через наши `console.*`, которые стережёт
   AC-011.21, а через access-log самого фреймворка и Caddy при 500) не проверялась.
