# FR-011 · Краевые случаи и испытание критериев

> **Ревизия 2.** Добавлены N15–N20 — мутации, которых не поймал бы ни один критерий первой
> редакции. N15 и N16 особенно: они воспроизводят дефект, проходивший ВСЕ пятнадцать её AC.

| Случай | Ожидание | Критерий |
|---|---|---|
| Верный токен | кабинет с числами ЭТОГО партнёра | AC-011.1 |
| Токен партнёра A, в адресе код партнёра B | показаны числа A | AC-011.3 |
| Неизвестный токен | `401`, cookie не ставится | AC-011.5 |
| Мусорная строка, пустая строка, не-строка | тот же `401`, тем же телом | AC-011.5 |
| Токен отозванного кода | тот же `401` — неотличимо от неизвестного | AC-011.5 |
| Код отозван ПОСЛЕ выдачи cookie | кабинет закрыт при следующем показе | AC-011.6 |
| Партнёр без регистраций | `conversion_rate = null`, не `0` | AC-011.14 |
| 30 неверных предъявлений с одного IP | `429` | AC-011.11 |
| Тело больше предела | `413` | AC-011.13 |
| Код без токена (выдан до фичи) | `401` — токена нет, сверять нечего | AC-011.5 |

## Тест-стратегия

**Слой 1, поведение** — все строки выше на живой БД, с ДВУМЯ партнёрами, у каждого свои
ненулевые и **различающиеся** числа. Один партнёр не годится: изоляция на нём зеленеет
всегда.

**Слой 1, стражи по исходнику** — AC-011.4, .7, .9, .15.

**Слой 3** — таблица мутаций ниже, прогоном.

именно ради них критерии написаны так, а не иначе.

## Как проверяется межпартнёрская изоляция (AC-011.2)

Недостаточно «в кабинете A нет данных B». Нужно, чтобы у B данные **были и отличались**,
иначе тест зеленеет на пустой базе:

```
партнёр A: 3 регистрации, 1 конверсия, начислено 100
партнёр B: 7 регистраций, 5 конверсий, начислено 900
кабинет A обязан показать ровно 3 / 1 / 100 — и ни одного числа из строки B
```

Мутация N5 при таком наборе даёт A десять регистраций вместо трёх — тест краснеет. При
одном партнёре или при нулевых данных та же мутация прошла бы незаметно.
