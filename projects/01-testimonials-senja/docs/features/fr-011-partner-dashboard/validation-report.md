## 2. Блокеры

### 🔴 B-1. Несущее требование FR-011.1 не имеет критерия, который падает

**Требование:** «у партнёрского кода есть отдельный секрет, **не совпадающий с самим кодом**».
Это ядро фичи: вся она существует потому, что код публичен.

**Ни один из пятнадцати AC не краснеет, если это нарушить.** Реализация, проходящая
AC-011.1, .2, .3, .4, .7, .9, .10 целиком и при этом отдающая кабинет любому, кто видел
реферальную ссылку:

```
// вариант «а»: секретом объявлен сам код
issuePartnerCode: dashboard_token = code;  store sha256(code)
// вариант «б»: в cookie кладётся не токен, а идентификатор партнёра
POST /api/partner/session: сверить токен по хешу ✅ → setCookie(PARTNER_COOKIE, row.code)
```

Разбор по критериям (вариант «б»):

| AC | Проходит? | Почему |
|---|---|---|
| AC-011.1 «токен A открывает кабинет и показывает числа A» | ✅ | токен сверяется по хешу честно |
| AC-011.2 «в кабинете A нет чисел B» | ✅ | с cookie A показаны только числа A |
| AC-011.3 «подстановка чужого `code` в адрес/поле/заголовок не меняет показанное» | ✅ | страница читает **только cookie** — адрес игнорируется буквально |
| AC-011.4 «страж: идентификатор не читается ниоткуда, кроме cookie» | ✅ | он и читается из cookie. Формулировка не требует, чтобы в cookie лежал **секрет** |
| AC-011.7 «в БД не пишется исходный токен» | ✅ | пишется `sha256` |
| AC-011.9 «токена нет в адресе и в теле» | ✅ | нет |
| AC-011.10 «cookie httpOnly, path=/partner» | ✅ | да |

**Атака:** `curl -b 'pw_partner=NEWSLETTERA-K7QM' https://.../partner/dashboard` — код взят из
реферальной ссылки, которую партнёр публикует сам. Ровно та утечка, ради предотвращения которой
написана вся фича.

Это тот же класс, что закрыт в FR-010 (NFR-010.7) и процитирован в самом документе: **проверка
изоляции смотрит, не задет ли чужой при работе со своим, и молчит, когда «своим» объявлен чужой.**
Документ называет класс и повторяет его вариацию.

**Чем доказано:** таблица выше — разбор пятнадцати AC из `01_specification.md:71-88` и
четырнадцати мутаций из `04_refinement.md:35-52`; ни одна мутация N1–N14 не описывает подмену
содержимого cookie.

**Что добавить перед Phase 3:**
- `AC-011.16`: подделанная cookie, содержащая **публичный код или id партнёра**, доступа не даёт;
  единственное значение, открывающее кабинет, — то, чей `sha256` совпал с `dashboard_token_hash`.
  Падает при: класть в cookie `code`/`id` вместо токена.
- `AC-011.17`: выданный `dashboard_token` не равен `code` и не выводится из него.
  Падает при: `token = code`.
- Мутации `N15` (cookie = код) и `N16` (`dashboard_token = code`) в таблицу.

### 🔴 B-2. Лок по IP: внесён дефект того класса, который FR-009 уже чинил

**Псевдокод** (`02_pseudocode.md:60`):
```
if not try_advisory_xact_lock(PARTNER_LOCK_NAMESPACE, hashtext(keyIp)): return TooMany
```
Ключ лока — **IP**. Вход по FR-009 делает наоборот: `login.ts:102-106` берёт лок по **паре**
`hashKey(PAIR_SCOPE, email, ip)`, и это не случайность — `login.ts:16-18` объясняет:

> «Лок по IP наказывал бы всех за одним NAT, а не атакующего.»

Правило проекта фиксирует тот же случай отдельной строкой: `.claude/rules/shared-resource-verification.md`,
ревизия 3 → 3.1 — «try-блокировка по IP: очереди нет, но все за одним NAT получают ложные `429`».

**Последствие:** два добросовестных партнёра одной компании (или один партнёр с двух вкладок)
одновременно отправляют форму → второй получает `429` немедленно, не дойдя ни до счётчика, ни
до сверки. Порог 30 здесь ни при чём: лок отвергает **на второй одновременной попытке**.

Пары, как у входа, здесь действительно нет — но это довод против **счётчика** по паре, а не
против выбора ключа лока. Не рассмотрены оба дешёвых выхода: лок по паре `hashKey(SCOPE, ip,
sha256(token))` (счётчик при этом остаётся по IP — бюджет атакующему не обновляется, потому что
считает **счётчик**, а не лок) либо отказ от лока в пользу единого SQL-выражения.

Отдельно: цена ложного `429` здесь выше, чем цена обхода лимита. Пространство токена — 2^256;
лимит не является защитой от перебора, он защищает от нагрузки. Запирать ради этого живых
партнёров — плохой размен, и он нигде не назван.

**Чего нет в критериях.** `shared-resource-verification.md` требует третьим пунктом
обязательный тест: «добросовестный параллельный сценарий проходит: N разных пользователей за
одним NAT/доменом не мешают друг другу». Такого AC нет. AC-011.11 и AC-011.12 —
последовательные, а последовательный тест на этом дефекте зеленеет всегда.

**Чем доказано:** `02_pseudocode.md:60` против `apps/web/src/lib/login.ts:16-18,102-106`;
`.claude/rules/shared-resource-verification.md`, таблица ревизий.

**Что добавить:** `AC-011.18` — два одновременных предъявления **разных верных** токенов с
одного IP: оба получают `200`. Мутация `N17` — вернуть лок по `keyIp`, тест обязан покраснеть.

### 🟠 H-1. «Тип — это и есть реализация NFR-011.1» — утверждение неверно

`03_architecture.md:44-46` утверждает: «Идентификатор партнёра НЕ является входным параметром ни
одной функции этого модуля… Ошибка "взяли партнёра из адреса" **невозможна по сигнатуре**, а не
по внимательности.»

Граница модуля кончается на один вызов раньше, чем нужно. Последний вызов страницы —
`getPartnerCohortDashboard(c, partner.code)` (`02_pseudocode.md:106`), а её сигнатура:

```ts
export async function getPartnerCohortDashboard(client: PoolClient, code: string)   // partner.ts:132-135
```

`code: string` — это и есть «идентификатор партнёра входным параметром». `const data = await
getPartnerCohortDashboard(c, searchParams.code)` компилируется без единой ошибки типов.
Защита остаётся ровно та, которую документ объявил недостаточной: страж по исходнику AC-011.4.

**Чем доказано:** `apps/web/src/lib/partner.ts:132-139` против `03_architecture.md:41-46`.

**Что сделать:** либо `partner-auth.ts` экспортирует `getDashboardForAuth(client, auth: PartnerAuth)`
и AC-011.4 стережёт, что страница не зовёт `getPartnerCohortDashboard` напрямую; либо параметр
получает branded-тип, конструируемый только сверкой токена. И снять утверждение о невозможности
по сигнатуре, пока оно неверно.

### 🟠 H-2. AC-011.15: «константное по времени сравнение на стороне БД по уникальному индексу»

Три отдельные проблемы в одной формулировке:

1. **Неточность по существу.** Поиск по btree-индексу не является константным по времени:
   сравнение текста прекращается на первом различающемся байте, а число посещённых страниц
   зависит от данных. Свойство, которое здесь на самом деле защищает, другое: **сравниваются
   хеши, а не секреты** — утечка тайминга не даёт восстановить токен, потому что нужен прообраз
   sha256.
2. **Критерий не проверяет то, что называет.** В `05_completion.md:31` AC-011.15 испытывается
   мутацией `N4` («хранить токен открытым») — это проверка **хеширования**, а не времени сравнения.
   Про тайминг не падает ничего.
3. **Риск стража, красного на верном коде.** Буквальная реализация («в коде обязан быть
   `timingSafeEqual`») покраснеет на правильной SQL-сверке, где сравнения в коде нет вовсе.
   Этот класс в проекте уже встречался (`.claude/rules/guard-must-be-able-to-fail.md`).

**Чем доказано:** `apps/web/src/lib/current-session.ts:27-28` — существующий код делает ровно ту
же сверку и **не заявляет** константного времени: «равенство по 64 hex-символам, восстановить
токен из хеша нельзя». `session.ts:40-41` держит `timingSafeEqual` отдельно и с оговоркой «на
случай сравнения **вне SQL**».

**Переформулировать:** «Сверка идёт по `dashboard_token_hash` в SQL; открытый токен не
сравнивается в коде ни с чем. Утечка тайминга безвредна, так как сравниваются хеши.»

### 🟠 H-3. NFR-011.2 назван, страж описан в архитектуре — но AC для него нет

`03_architecture.md:60-62` обещает: «NFR-011.2 закрывается стражем "ни один запрос к этим
таблицам не появился вне `partner.ts`"». В списке AC-011.1…15 такого критерия **нет**.
AC-011.2 покрывает поведенческую половину — и только для трёх уже написанных запросов

`partner-auth.ts` или прямо в страницу, не покраснит ничего.

Цена ошибки здесь выше обычной и в документе названа верно: RLS на `partner_codes`,

Единственный фильтр — тот, что написан в запросе.

**Что добавить:** `AC-011.20` — страж по исходнику: `from referral_attributions` и `from
commissions` встречаются ровно в `lib/partner.ts` (форма стража — как в `tests/login.test.ts:300-306`

### 🟠 H-4. Как токен попадает партнёру — не описано и не покрыто критерием

FR-011.2: «исходное значение показывается **один раз при выдаче**». Кому показывается и каким
каналом уезжает партнёру — не сказано нигде.

`issuePartnerCode` **не вызывается из продакшн-кода**: `grep -rn "issuePartnerCode" apps services
packages` → только `lib/partner.ts:31` (объявление) и `tests/partner.test.ts`. Админского
маршрута или команды нет.

Отсюда пункт `05_completion.md:5` — «Выкачено, вход партнёра проверен вживую» — невыполним без
ручного `insert` в psql с самостоятельным подсчётом `sha256`. Это ровно тот разрыв, который
описывает `.claude/rules/deployment-seams.md`: сквозной сценарий обрывается на шаге «получить
ссылку/секрет».

**Что сделать:** либо внести в объём CLI/скрипт выдачи (`scripts/issue-partner-code.mjs`),
печатающий токен один раз, либо явно записать в «Вне объёма», что выдача идёт вручную через
psql, и привести точную команду в `05_completion.md`.

### 🟠 H-5. «Потерял токен → перевыпустить код» тихо разрезает когорту партнёра надвое

Принимаемые риски 2 и 3 (`05_completion.md:41-49`) оба разрешаются одинаково: «владелец
перевыпускает код». Но перевыпуск — это **новая строка** в `partner_codes` с новым `code`
(`partner.ts:41-48`), а все начисления привязаны к `partner_code_id` старой строки
(`referral_attributions.partner_code_id`, `partner.ts:146,153`).

Следствие: партнёр входит в новый кабинет и видит **нули** вместо своей истории, а старые
реферальные ссылки перестают быть его ссылками. Про это не сказано ни в рисках, ни в
требованиях. Особенно едко для риска 3: **все** коды, выданные до фичи, попадают именно в этот
сценарий.

**Что сделать:** добавить `issueDashboardToken(client, code)` — проставляет
`dashboard_token_hash` **существующей** строке и возвращает токен один раз. Это же закрывает и
ротацию при компрометации. AC: «выдача токена существующему коду не создаёт новый код и не
меняет `partner_code_id`».
