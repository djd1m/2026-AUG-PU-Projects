# ЧАСТЬ 2. Седьмая итерация — найдена

## 🔴 B-1 (новый). Вложенный `withService`: 31 одновременный запрос кладёт пул всего продукта

### Что написано

Ревизия 3 разделила одну транзакцию на две — правильное решение, снявшее блокер второго
прохода. Но обёртка от однотранзакционной редакции осталась на месте, и `02` теперь
противоречит **сам себе** на контракте одной функции:

```
02:99    result = withService(client -> authenticatePartner(client, token, ip))
                  ^^^^^^^^^^^^^^^^^^^^ маршрут открывает транзакцию и передаёт client

02:155   function authenticatePartner(token, ip):
                                      ^^^^^^^^^ client НЕ принимается
02:156       if not checkAndRecordAttempt(ip):  return TooMany     # внутри: withService (02:129)
02:157       return withService(c -> resolvePartnerByToken(c, token))
```

Реализованное буквально по `02:99` — а это первый и самый конкретный фрагмент маршрута в файле —
даёт **три соединения на один вход**: внешнее удерживается всё время, пока внутренние две
транзакции пытаются взять свои. `withService` в этом проекте нереентрантен: `tenant.ts:30` —
безусловный `pool.connect()`.

### Проверено прогоном — обрыв, а не наклон

Пул 30, `connectionTimeoutMillis = 5000` (`packages/db/src/index.ts:44,48` — боевые значения).
Параллельно с залпом работает «продуктовый» пробник (витрина/виджет: одна короткая транзакция
каждые 5 мс).

```
вложенный (02:99)  N= 10 |    81 мс | продукт p95=27 мс   | OK 10
вложенный (02:99)  N= 29 |    85 мс | продукт p95=34 мс   | OK 29
вложенный (02:99)  N= 31 |  5033 мс | продукт p95=5005 мс | POOL_TIMEOUT 19, OK 12, ОТКАЗ продукта 1
вложенный (02:99)  N= 60 |  5020 мс | продукт p95=5003 мс | POOL_TIMEOUT 57, OK 3
плоский            N= 31 |    61 мс | продукт p95=6 мс    | OK 31
плоский            N= 60 |   133 мс | продукт p95=64 мс   | OK 60
```

Порог — ровно размер пула. При `N ≤ 29` внешние обёртки оставляют свободное соединение и всё
работает; при `N = 31` все 30 соединений заняты внешними обёртками, внутренние транзакции ждать
могут только друг друга, и **никто не может продвинуться**. Это классическая самоблокировка на
пуле: держать один экземпляр ресурса, ожидая второй из того же исчерпанного пула.

Отказывает при этом **не только вход партнёра**. Продуктовый пробник — это дашборд владельца,
витрина, виджет и приём отзывов: p95 = 5005 мс и один прямой отказ. Тридцать один параллельный
`curl` по неаутентифицированному маршруту кладёт продукт целиком.

### Почему это блокер по объявленному порогу

Конкретный дефект, воспроизведённый числом и проходящий мимо **всех 25** критериев:

| Критерий | Почему не ловит |
|---|---|
| AC-011.23 «не более 30 доходит до сверки» | вложенность не влияет на **число** прошедших — влияет на время удержания. При N=31 до сверки доходит 12, что «не более 30» |
| AC-011.18 «два одновременных верных → оба 200» | N=2, вложенность на двух запросах невидима |
| AC-011.11, .12 | последовательные |
| N21 (ключ лока ≠ ключ счётчика) | мутация про ключ, не про транзакции |
| AC-011.13 «предел тела» | разбор тела **снаружи** транзакции соблюдён (`02:94-97`) — и это правильно; страж проекта стережёт именно его |

Ни один критерий и ни одна из 25 мутаций не говорят о вложенности транзакций и о занятости пула.
Проект при этом **имеет страж ровно этой формы** — `tests/login.test.ts:308-316`, «разбор тела НЕ
внутри транзакции — иначе исчерпание пула». Идиома существует и не применена к соседнему маршруту.

## 🟠 H-1 (новый). «Очередь в микросекундах» — измерено 1371 мс. Ждущий лок отменил дешёвый сброс нагрузки

NFR-011.4 ревизии 3 обещает свойством: партнёр «не получает отказ, а получает **очередь,
измеряемую микросекундами**». `02:118-120` защищает выбор ждущего лока тем, что в FR-009
ожидание длилось argon2 (~50 мс), а здесь — «один COUNT плюс один INSERT».

Секция действительно короткая. Но обещание касается не длины секции, а длины **очереди**, и
очередь растёт линейно с числом одновременных попыток. Измерено (пул 30, тот же продуктовый
пробник, залп с одного адреса, ждущий лок против try-лока):

```
                залп       продукт p95   POOL_TIMEOUT   отказы продукта
N=1000  ждущий  1289 мс      1235 мс           0              0
N=1000  try      201 мс       187 мс           0              0
N=3000  ждущий  3457 мс      3412 мс           0              0
N=3000  try      426 мс       406 мс           0              0
N=6000  ждущий  5078 мс      5023 мс        1350              1
N=6000  try      771 мс       737 мс           0              0
```

Число **одновременно занятых** соединений не растёт с N — оно упирается в размер пула (30) во
всех трёх режимах, включая try. Растёт **длительность полного насыщения**: линейно по N для
ждущего лока и почти плоско для try. Отвечая на вопрос прямо: заданный критерий «растёт ли число
занятых соединений» не выполняется ни в одном режиме и потому дефекта не различает; различает его
время удержания, и вот оно растёт — 1.3 с при 1000, 5.1 с при 6000, с отказами продукта.

Механика: ждущий лок опускает пропускную способность маршрута с ~7800 попыток/с (дешёвый сброс:
`try` не удался → 429 немедленно, соединение отпущено) до ~1180 попыток/с (сериализация на локе).
Всё, что не помещается, копится **в очереди пула**, а пул общий у входа, дашборда, витрины,
виджета и приёма отзывов.

`set local lock_timeout` поясом здесь **не работает** — проверено: при пуле 30 очередь за локом
не длиннее 30 позиций (≈9 мс), таймаут в 250 мс не срабатывает никогда, а настоящая очередь
стоит уровнем выше, в пуле. Число не меняется: 5059 мс против 5078 мс при N=6000.

### Починка есть, она в три строки, и она измерена

Дешёвый отсев **до** взятия лока: read-only `exceeded()` — если порог уже выбран, `429` сразу,
лок не берётся вовсе. Авторитетная проверка остаётся под локом, поэтому атомарность цела, а
глубина очереди за локом ограничена **порогом**, а не числом атакующих.

```
                        залп     продукт p95   POOL_TIMEOUT   дошло до сверки   добросовестные 5 за NAT
N=6000  ждущий          5064 мс    4983 мс         895              30                  5 из 5
N=6000  с отсевом        797 мс     776 мс           0              30                  5 из 5
N=6000  try по адресу    727 мс     709 мс           0              30                  1 из 5
```

Отсев даёт обе половины сразу: цифры try-лока по нагрузке (797 мс против 5064 мс, ноль
POOL_TIMEOUT против 895) и цифры ждущего лока по добросовестности (5 из 5 против 1 из 5).

**Что сделать:** внести отсев в `02` как первый шаг `checkAndRecordAttempt`, до
`advisory_xact_lock`. Переписать NFR-011.4: «очередь в микросекундах» — утверждение
измеримое и **опровергнутое**, требование не должно обещать того, чего механизм не даёт.
Добавить **AC-011.27**: *при N = 1000 одновременных попыток с одного адреса задержка
постороннего запроса к БД не превышает X мс* — с числом, иначе это не критерий. И **N27**:
убрать отсев — измерение обязано покраснеть.
