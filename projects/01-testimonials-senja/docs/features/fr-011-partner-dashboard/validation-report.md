# ЧАСТЬ 2. Шестое повторение — найдено

## 🔴 B-1 (новый). Пара в ключе лока сняла атомарность счётчика: лимит обходится залпом

### Что было и зачем

Первая редакция брала лок по IP. Первый проход назвал это дефектом (ложные `429` за одним NAT) —
и был прав. Ревизия 2 ключ исправила:

```
# 02_pseudocode.md:104
keyLock = hashKey(PARTNER_IP_SCOPE, ip, sha256(token))
if not try_advisory_xact_lock(PARTNER_LOCK_NAMESPACE, hashtext(keyLock)): return TooMany
if rateLimit.exceeded(PARTNER_IP_SCOPE, keyIp, PARTNER_WINDOW, PARTNER_IP_THRESHOLD, client): ...
```

**Ключ лока — пара, ключ счётчика — только адрес.** Лок стал строго тоньше того, что он охраняет.

Зачем лок вообще существует, записано в коде, который ревизия 2 цитирует как образец
(`apps/web/src/lib/login.ts:88-91`):

> «`exceeded` (COUNT) и `record` (INSERT) — две операции без блокировки: под READ COMMITTED
> сто параллельных запросов все видят count = 0, все проходят. Лимит обходился бы `curl --parallel`.»

Атакующий перебирает **разные** токены. Каждый его запрос берёт **свой** лок. Ни один не ждёт
другого. Ровно тот обход, ради предотвращения которого лок и вводился, вернулся.

### Проверено прогоном — числа, а не рассуждение

Тестовая БД `proofwall_test`, PostgreSQL 16.13. 40 одновременных транзакций с одного «адреса»,
порог 30. Логика каждой — как в псевдокоде: `try_advisory_xact_lock` → `count(*) >= 30` → запись.

```
== режим лока: пара (адрес, хеш токена) — РЕВИЗИЯ 2 ==
     40 PASSED_TO_SVERKA
записей в счётчике: 40

== режим лока: один адрес — РЕВИЗИЯ 1 ==
      1 PASSED_TO_SVERKA
     39 TOO_MANY_LOCK
записей в счётчике: 1
```

Промежуточный прогон на двух сессиях показывает механику по шагам:

```
-- лок по паре:  A lock_taken=t, A counter_seen=0
--               B lock_taken=t, B counter_seen=0   ← INSERT сессии A не виден, обе прошли
-- лок по адресу: A lock_taken=t, B lock_taken=f    ← B отвергнут ДО счётчика
```

**Уборка проверена:** `drop table fr011_probe` выполнен, `select count(*) from pg_tables where
tablename='fr011_probe'` → `0`. Все вставки в `partner_codes` шли в транзакции и откачены
(`select count(*) … like 'PROBE-%'` → `0`).

### Почему это блокер по объявленному порогу

Конкретный дефект, проходящий мимо **всех 22** критериев:

| Критерий | Почему не ловит |
|---|---|
| AC-011.11 «порог достигается настоящими предъявлениями → 429» | **последовательный**. На залпе зеленеет всегда — счётчик после залпа действительно ≥ 30 |
| AC-011.12 «одно неверное предъявление +1 к счётчику» | одиночное, про запись, не про чтение |
| **AC-011.18** «два одновременных **верных** токена → оба 200» | ⚠️ этот критерий **требует** отсутствия сериализации. Он зеленеет именно потому, что дефект есть |
| N7, N9 (мутации лимита) | обе про ключ и наличие `exceeded`, обе последовательные |

Критерия «N одновременных **неверных** токенов с одного адреса — лимит держится» нет ни одного.
`shared-resource-verification.md` требует его третьим пунктом дословно; первый проход это же
требование предъявил к ревизии 1, и ревизия 2 добавила из него **только половину** — ту, что
проверяет добросовестный сценарий, и не добавила ту, что проверяет атакующий.

### Чего это стоит на практике — честно

Пространство токена 2^256; перебором фичу не берут, и документ прав, когда пишет, что лимит здесь
защищает от нагрузки. Но:

- `PGPOOL_MAX = 30`, `connectionTimeoutMillis = 5000` (`packages/db/src/index.ts:44,48`). Залп в
  несколько сотен параллельных POST на **неаутентифицированный** маршрут держит все 30 соединений;
  дашборд, витрина, виджет и приём отзывов в это время получают таймаут пула. Лимит — единственное,
  что должно было это ограничивать, и он не ограничивает.
- Прежний ключ эту работу выполнял: 39 из 40 отвергались одним быстрым запросом и отпускали
  соединение немедленно. Ревизия 2 сняла ограничение, не назвав, что снимает его.

### Форма повторения

| Ревизия | Что чинили | Что внесли | Разделяемый ресурс |
|---|---|---|---|
| FR-009 1→2 | лимит без чисел | разбор тела внутри транзакции | пул |
| FR-009 2→3 | исчерпание пула | ждущая блокировка | пул + локи |
| FR-009 3→3.1 | очередь за локом | лок по IP → ложные 429 за NAT | лок, общий для многих |
| FR-009 3.1→4 | лок по IP | argon2 внутри транзакции | пул |
| FR-010 | (по своему отчёту) | страж, красный на верном коде | — |
| **FR-011 1→2** | **лок по IP → ложные 429 за NAT** | **лок тоньше счётчика → счётчик неатомарен** | **счётчик, пул** |

Строка 3.1→4 и строка FR-011 1→2 — **одна и та же жалоба и одна и та же правка**, и оба раза
починка потеряла второе назначение лока. Знание о дефекте не помогло, потому что проверялась
**правка**, а не **ресурс**.

### Что требуется — и чего делать НЕ надо

**Не возвращать лок по IP.** Это воспроизведёт B-2 первого прохода. Требуемое свойство
формулируется без выбора реализации:

> Проверка и запись счётчика **атомарны** относительно параллельных попыток с того же адреса,
> и добросовестный партнёр при этом **не получает отказ** — он получает очередь, измеряемую
> микросекундами.

Два способа, оба дешёвы:

1. **Счётчик строкой вместо потока событий.** `insert … on conflict (scope, key, bucket) do update
   set n = n + 1 returning n` — блокировка строки сериализует ровно писателей по этому адресу и
   держится на время одного `UPDATE`, а не на время сверки. Порог проверяется по возвращённому `n`.
   Отличие от ждущего лока, который проект отверг в FR-009, — принципиальное: там ожидание длилось
   argon2 (≈50 мс) и держало соединение; здесь оно длится один `UPDATE`.
2. **Оставить пару локом и добавить второй, широкий лок — только вокруг пары «счёт + запись»**,
   не вокруг сверки. Дороже в реализации, тот же результат.

**Критерий, без которого правку принимать нельзя** (AC-011.23): *N одновременных предъявлений
**разных неверных** токенов с одного адреса при пороге 30: до сверки доходит не более 30.*
Мутация **N21**: вернуть ключ лока, не совпадающий с ключом счётчика, — тест обязан покраснеть.
Порядок именно такой: сначала показать красное, потом чинить (`guard-must-be-able-to-fail.md`).

Заодно ответить на четыре вопроса `shared-resource-verification.md` прямо в `02`: что удерживается,
сколько единиц всего (30), кто ещё в очереди (весь продукт), кого наказывает насыщение.

## 🟠 H-1 (новый). Сырой токен уезжает в SQL — против собственного AC-011.15 и против NFR-011.5

```
# 02_pseudocode.md:116        и то же самое в 02:64 (ротация)
row = SELECT id FROM partner_codes
       WHERE dashboard_token_hash = sha256($token) AND status = 'active'
```

`$token` — это **параметр запроса**, то есть открытый секрет уезжает в БД. AC-011.15 ревизии 2
запрещает это дословно: «в SQL уходит `sha256(токен)`, **сам токен в условие запроса не попадает**».

Документ и его собственный критерий противоречат друг другу на несущем пункте — и противоречие
именно того рода, который ревизия 2 взялась чинить.

Цена — та самая **третья утечка**, ради которой токен не кладут в адрес (`01:43-44`): при
`log_statement = 'all'`, при `log_min_duration_statement`, в `pg_stat_statements` и в дампе
`pg_stat_activity` параметр запроса виден. AC-011.21 сюда не достаёт: он стережёт `console.*` и
`audit_log`, а не журнал БД.

Дополнительно — **как написано, не скомпилируется**: в PostgreSQL 16 `sha256()` принимает и
возвращает `bytea`, а `dashboard_token_hash` объявлен `text` (`03:23`). Нужен либо
`encode(sha256($1::bytea), 'hex')`, либо — правильно — хеш считается в Node, и параметром едет
только hex.

**Что сделать:** в `02` (обе точки) заменить на `WHERE dashboard_token_hash = $1`, где `$1 =
sha256hex(token)`, посчитанный в `partner-auth.ts`. Расширить AC-011.21 до «переменная токена не
уходит и параметром SQL-запроса» и добавить мутацию **N22** (передать сырой токен параметром).

| Ротация записывается в `audit_log` | **нет** | выдача кода пишет `partner_code_issued` (`partner.ts:50-54`); смена ключа доступа не пишет ничего |
| Ротация отозванного кода | **нет** | `WHERE code = $1` без `status = 'active'` — токен выдаётся коду, который никого не пустит |

Первая строка — единственная с ценой безопасности, и она попадает мимо всех критериев. Формально
FR-011.6 говорит только про **утраченный** токен; но H-5 первого прохода вводил ротацию словами
«это же закрывает и ротацию при компрометации», а ревизия 2 этот случай из формулировки потеряла.
Утраченный токен — это по умолчанию токен, который кто-то мог найти.

**Что добавить:**
- `AC-011.23`… (нумерация после B-1) — **прежний токен после ротации даёт `401`**, включая
  предъявление уже выданной cookie. Мутация: хранить оба хеша.
- `AC` — ротация возвращает токен **только** если `rowCount = 1`; иначе исключение
  (`fail-closed-defaults.md`, пункт 5: недоступность/несовпадение — отказ, а не значение).
- `AC` — ротация пишет `audit_log` с действием `partner_dashboard_token_rotated`.

## 🟠 H-6 (новый, найден прогоном). Кабинет покажет **ноль** каждому партнёру: `NULL` поверх дефолта

Ценность фичи заявлена как «партнёр видит свои начисления». Проверено, что он увидит.

Миграция `010_commission_default.sql:23` ставит `alter column commission_rate set default 0.3000`.
Но `issuePartnerCode` передаёт значение **явно**:

```ts
// apps/web/src/lib/partner.ts:43-48
insert into partner_codes (code, partner_name, status, commission_rate, owner_account_id)
values ($1, $2, 'active', $3, $4)
…
[code, partnerName, options.commissionRate ?? null, options.ownerAccountId ?? null]
```

Явный `NULL` **отменяет** дефолт колонки. Прогон на тестовой БД (всё в транзакции, откачено):

```
  code   | commission_rate
---------+-----------------
 PROBE-A |                    ← insert … values (…, null, …)   — как делает issuePartnerCode
 PROBE-B |          0.3000    ← insert без колонки              — как сработал бы дефолт
```

Дальше `convertAttributionOnPayment` (`referral.ts:140-142`) при `commission_rate === null`
**не создаёт строку `commissions` вовсе** — возвращает `rateMissing: true`. Значит
`getPartnerCohortDashboard` просуммирует пустоту: `total_commission = 0` навсегда, для каждого
кода, выданного после миграции 010.

Риск 4 в `05:214-216` описывает следствие верно («суммы будут нулевыми»), но объясняет его
**устаревшей** причиной — `[GAP]` в `004_growth.sql:50`, который миграция 010 закрыла. Ссылка
в «Вне объёма» (`01:113`) на тот же `004_growth.sql:50` тоже устарела (и номер строки неверен:
колонка на 55).

Это **не дефект FR-011** — но FR-011 является ровно той фичей, которая предъявляет его партнёру,
и единственной, в чьих документах он записан как «честное отображение состояния». Починка — одна
строка: `options.commissionRate` не подставлять `?? null`, а опускать колонку из INSERT, либо
`coalesce($3, 0.3000)`.

**Что сделать:** переписать риск 4 по факту, либо внести правку в объём фичи и закрыть критерием
«код, выданный `issuePartnerCode` без явной ставки, получает 0.3000».

## 🟠 H-7 (новый). DIFF, введённый чтобы ничего не потерять, теряет шестое свойство

`02:34-53` показывает выдачу токена как diff — правильное решение, снявшее B-3. Но строка,
поданная как **неизменённый контекст**, существующему коду не соответствует:

| В diff (контекст, то есть «как есть сейчас») | В `partner.ts:38-61` на самом деле |
|---|---|
| `for (let attempt = 0; attempt < 10; attempt += 1) {` | `let attempt = 0; while (true) { … attempt += 1; if (attempt > 10) throw new Error('не удалось подобрать уникальный код партнёра за 10 попыток'); }` |

Реализованный буквально, diff превращает явный отказ в **тихий**: после десяти коллизий цикл
`for` просто заканчивается, функция доходит до конца и возвращает `undefined`. Вызывающий
получит `undefined.id`. Это `fail-closed-defaults.md` наизнанку — исчерпание попыток перестаёт
быть отказом.

**Шестое свойство `issuePartnerCode`, которого нет в списке AC-011.19:** *исчерпание попыток
подбора кода бросает исключение, а не возвращает пустое значение.* Пять названных свойств
(сигнатура, `id`, `audit_log`, `commission_rate`/`owner_account_id`, цикл) проверены по коду —
список верен, но неполон ровно на одно.

Мелочью рядом: обе стороны diff опускают колонку `status` из INSERT. Безвредно — у колонки есть
`default 'active'` (`004_growth.sql:49`, проверено) — но diff, который показывают как точный,
неточен в трёх местах из трёх.

**Что сделать:** привести контекстные строки diff к настоящему коду; дописать в AC-011.19 шестое
свойство.
