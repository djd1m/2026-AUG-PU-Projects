## Миграция

```sql
alter table partner_codes add column if not exists dashboard_token_hash text;
create unique index if not exists partner_codes_dashboard_token_hash_idx
  on partner_codes (dashboard_token_hash);
```

Колонка **nullable**: коды, выданные до этой фичи, токена не имеют и кабинет им недоступен,
пока владелец не перевыпустит. Это осознанно — альтернатива требовала бы придумать токен за
партнёра и передать его каналом, которого нет.

Уникальный индекс несёт двойную нагрузку: он и ускоряет сверку, и делает коллизию токенов
ошибкой БД, а не тихим совпадением. `null` в уникальном индексе Postgres не конфликтует сам
с собой — несколько кодов без токена сосуществуют штатно.

## Граница ответственности

`lib/partner-auth.ts` не знает про HTTP: принимает `client`, токен и IP, возвращает
`{ partnerCodeId, code } | null | TooMany`. Маршрут превращает это в ответ и ставить cookie;
страница читает cookie и вызывает ту же функцию.

**Тип закрывает бо́льшую часть NFR-011.1, но не всё — и первая редакция это переоценила.**
Идентификатор партнёра не является входом ни одной функции `partner-auth.ts`. Однако
последним вызовом страницы была `getPartnerCohortDashboard(c, partner.code)`, а её параметр —
`code`, то есть ПУБЛИЧНОЕ значение: граница кончалась на один вызов раньше, чем нужно.
Поэтому вводится `getPartnerCohortDashboardById(client, partnerCodeId)`, и по этому пути
публичный код не едет вовсе. Утверждение «невозможно по сигнатуре» верно только после
этой правки, и то лишь для двух модулей — остальное закрывает страж AC-011.20.

```ts
export type PartnerAuth =
  | { ok: true; partnerCodeId: string; code: string }
  | { ok: false; tooMany: boolean };   // причины НЕТ — см. NFR-011.3
```

Отсутствие причины в отказе — та же форма, что у `LoginResult` (`login.ts:53`), и по той же
причине: вызывающий физически не может отдать наружу разные ответы, потому что различить их
нечем.

## Роль БД и почему здесь опаснее, чем в FR-010

Путь идёт под `withService`, роль `app_service`.

На `partner_codes`, `referral_attributions`, `commissions`:
- **RLS не включена** (`007_rls.sql:85-89` их не перечисляет);
- **грантов роли `app_authenticated` нет вовсе** (`:70-72` — только `app_service`).

То есть здесь нет даже той половинной подстраховки, что была в FR-010, где RLS хотя бы
существовала для соседних таблиц. Единственный фильтр — тот, что написан в запросе.

Смягчает ровно одно: все три запроса уже написаны и уже фильтруют
(`partner.ts:141,148,155`), а фича их не переписывает. Поэтому NFR-011.2 закрывается
стражем «ни один запрос к этим таблицам не появился вне `partner.ts`», а не переписыванием.

## Хеш токена — отдельная функция, а не `hashSessionToken`

`hashSessionToken` подмешивает `SESSION_SECRET`. Переиспользовать её значило бы связать два
пространства секретов: ротация `SESSION_SECRET` обнулила бы все партнёрские токены заодно с
сессиями, и причина была бы неочевидна. Токен партнёра — 32 случайных байта, их энтропии
достаточно и без соли, поэтому хеш простой `sha256`, как у `token_hash` сессий по замыслу
схемы.
