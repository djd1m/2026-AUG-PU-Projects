# FR-011 · Спецификация: партнёрский кабинет

## Проблема

`getPartnerCohortDashboard` написана (`lib/partner.ts:132`), покрыта тестами и **не вызывается
ниоткуда**. Роадмап прямо фиксирует причину: функция «предполагается вызываемой из админки
владельца продукта, способ аутентификации партнёра не описан». Партнёр не видит ни своей
когорты, ни своих начислений — он узнаёт о них, только спросив владельца.

## Отступление от роадмапа: адрес `/partner/[code]` использовать НЕЛЬЗЯ

Роадмап предлагает файл `apps/web/src/app/partner/[code]/page.tsx`, то есть адрес,
параметризованный партнёрским кодом. **Это раскрыло бы заработок партнёра любому, кто видел
его реферальную ссылку.**

Партнёрский код — значение **публичное по назначению**, и это не предположение, а два
работающих пути в коде:

| Путь | Где | Кто видит код |
|---|---|---|
| Промокод, который вводит пользователь при регистрации | `referral.ts:33-38` | каждый приглашённый |
| Метка в реферальной ссылке, кладущаяся в cookie | `referral.ts:42-44` | каждый перешедший по ссылке |

Партнёр распространяет код по своей аудитории — в этом весь смысл. Сделать его же ключом к
странице с суммами начислений означает опубликовать эти суммы вместе с ссылкой.

Поэтому вводится **отдельный секрет**, не совпадающий с кодом: `dashboard_token`.

## Почему секрет не в адресе, а в cookie

Простейшая форма — `/partner/d/<token>` — плоха тремя утечками, каждая из которых
наблюдалась в реальных продуктах:

1. **`Referer`.** Любой внешний ресурс на странице (шрифт, картинка, счётчик) получает
   полный адрес в заголовке `Referer`.
2. **История и синхронизация браузера.** Адрес попадает в историю, а с ней — в облачную
   синхронизацию и в автодополнение на чужом устройстве.
3. **Журналы прокси.** Caddy пишет путь запроса; секрет оседает в логах, к которым доступ
   шире, чем к самим начислениям.

Ни одна из трёх не касается тела POST-запроса. Поэтому: партнёр открывает `/partner`, вводит
токен в форму, ответ ставит **httpOnly-cookie**, дашборд читает её. Та же дисциплина, что у
сессий владельца, и по той же причине.

## Функциональные требования

| # | Требование |
|---|---|
| FR-011.1 | У партнёрского кода есть отдельный секрет `dashboard_token`, не совпадающий с самим кодом |
| FR-011.2 | Токен хранится **хешем**, как и токены сессий; исходное значение показывается один раз при выдаче |
| FR-011.3 | `POST /api/partner/session` принимает токен и ставит httpOnly-cookie, ограниченную путём `/partner` |
| FR-011.4 | `/partner/dashboard` показывает когорту и начисления **того** партнёра, чей токен предъявлен |
| FR-011.5 | Отозванный партнёрский код (`status = 'revoked'`) доступа к кабинету не даёт |

## Нефункциональные требования `@security`

| # | Требование | Почему несущее |
|---|---|---|
| NFR-011.1 | Партнёр, к которому относится страница, определяется **только** предъявленным токеном — никогда параметром адреса, поля формы или заголовка | Тот же класс, что закрыт в FR-010 (NFR-010.7): проверки изоляции смотрят, не задет ли чужой партнёр при работе со своим, и молчат, когда «своим» объявлен чужой |
| NFR-011.2 | Все запросы к `partner_codes`, `referral_attributions`, `commissions` фильтруют по `partner_code_id` **явно** | RLS на этих таблицах **нет вовсе**, и грантов роли `app_authenticated` тоже нет (`007_rls.sql:66-72`) — путь идёт под `app_service`, то есть без единой подстраховки. Забытый фильтр показывает чужие деньги |
| NFR-011.3 | Ответ на неизвестный, отозванный и синтаксически негодный токен **неразличим** | Различимость превращает форму в оракул: «такой партнёр есть, но код отозван» — уже утечка |
| NFR-011.4 | Попытки предъявления токена ограничены по IP | Токен — предъявительский секрет. Ключ **только по IP**, без пары: аккаунта, который можно было бы запереть, здесь нет, а ключ по токену защищал бы атакующего от собственного лимита |
| NFR-011.5 | Токен не попадает ни в адрес, ни в тело ответа, ни в журнал | См. три утечки выше |
| NFR-011.6 | Предел размера тела — общий с остальными маршрутами, одной реализацией | Маршрут неаутентифицирован по определению: он и есть вход |

## Критерии приёмки

| # | Критерий | Падает при |
|---|---|---|
| AC-011.1 | Токен партнёра A открывает кабинет и показывает **числа A** | не сверять токен с БД вовсе |
| AC-011.2 | **Межпартнёрская изоляция:** в кабинете A нет ни одного числа партнёра B — ни регистраций, ни конверсий, ни сумм. Проверяется на данных, где у B они заведомо ДРУГИЕ и ненулевые | убрать `where partner_code_id = $1` из любого из трёх запросов |
| AC-011.3 | Подстановка чужого `code` в адрес, поле формы или заголовок не меняет показанное | взять партнёра из параметра адреса |
| AC-011.4 | Страж по исходнику: страница и маршрут не читают идентификатор партнёра ниоткуда, кроме cookie-токена | то же |
| AC-011.5 | Неизвестный токен, отозванный код и мусорная строка дают **один и тот же** ответ: код, тело, и отсутствие cookie | вернуть «код отозван» отдельным текстом |
| AC-011.6 | Отозванный код: кабинет закрывается, даже если cookie была выдана ДО отзыва | проверять статус только при входе, а не при каждом показе |
| AC-011.7 | Страж по исходнику: в `partner_codes` не пишется исходный токен — только `dashboard_token_hash` | сохранить токен как есть |
| AC-011.8 | Выданный токен возвращается вызывающему **ровно один раз**, при создании; повторно его получить нельзя | добавить чтение токена |
| AC-011.9 | Токена нет ни в адресе, ни в теле ответа дашборда | передать токен в query-параметре |
| AC-011.10 | Cookie httpOnly, ограничена путём `/partner` | снять httpOnly |
| AC-011.11 | Порог попыток достигается **настоящими** предъявлениями; превышение → `429` тем же литералом, что у входа | убрать `rateLimit.exceeded` |
| AC-011.12 | Одно неверное предъявление увеличивает счётчик по IP ровно на 1 | убрать `rateLimit.record` |
| AC-011.13 | Тело больше предела → `413`; маршрут в списке стража предела тела | убрать `readBodyAtMost` |
| AC-011.14 | `conversion_rate` при нуле регистраций — `null`, а не `0`: «нет данных» и «0 %» разные ответы | вернуть `0` |
| AC-011.15 | Сравнение токена — по **хешу**, константным по времени сравнением на стороне БД по уникальному индексу | сравнивать открытые строки в коде |

## Вне объёма

Самостоятельная регистрация партнёров, вывод средств, история начислений по датам,
уведомления. Ставка комиссии остаётся `[GAP]` — она уже помечена в схеме (`004_growth.sql:50`)
и решается владельцем, а не этой фичей.
