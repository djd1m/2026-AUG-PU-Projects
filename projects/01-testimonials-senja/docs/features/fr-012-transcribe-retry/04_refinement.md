## Тест-стратегия

**Слой 1, поведение.** Все девять строк выше — на живой БД, с фиксированными числами,
прибитыми в тесте отдельно от кода.

**Слой 1, страж по исходнику** (AC-012.9): условие выборки содержит проверку
`transcript_next_attempt_at`. Поведенческий тест проверяет один прогон; страж — что
проверка вообще есть в запросе, а не выполнена после выборки.

**Испытание на способность падать.** Для каждого стража — внедрить дефект, убедиться
в красном, восстановить. Конкретно:

| Внедрить | Обязан упасть |
|---|---|
| Убрать условие срока из `SELECT` | NFR-012.2 (AC-012.4) |
| `attempts >= MAX` → `>` | AC-012.2 |
| `clock_timestamp()` → `now()` в `UPDATE` | **AC-012.11 и AC-012.13** — проверено прогоном. Критерий переписывался дважды: сравнение с моментом после возврата не ловило (ревизия 2), сравнение с `T_begin + BASE` тоже не ловило, потому что транзакция открывается ПОЗЖЕ `T_begin`. Ловит третья редакция: различает формулы длительность самого вызова |
| Убрать ВНЕШНИЙ `catch` целиком | **AC-012.14, обе проверки** — измерено: 2 красных |
| `release(poisoned)` → `release()` | **только страж по исходнику**, и это честная граница — см. ниже |

**Почему `release(poisoned)` не покрыт поведенческим тестом.** `ROLLBACK` на аварийной
транзакции **успешен** и очищает её — значит на всех воспроизводимых путях `poisoned`
оказывается пустым, и подмена ничего не меняет. Ветка с уничтожением клиента нужна
единственно тогда, когда не прошёл сам откат, то есть соединение мертво физически;
детерминированно вызвать это в процессе нечем.

Утверждать, что мутация ловится, было бы неправдой. Держит её страж по исходнику, и он
ловит только буквальное переименование — это записанная граница, а не пробел, о котором
не знают.
| Убрать учёт попытки в ветке не-`SttApiError` | AC-012.8, AC-012.12 |

Последняя строка — суть находки B-2: критерий, зеленеющий при двух взаимоисключающих
поведениях, не является критерием.
