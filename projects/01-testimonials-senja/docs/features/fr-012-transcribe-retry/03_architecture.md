## Где живут числа

`MAX_ATTEMPTS` и `RETRY_BASE_MS` — экспортируемые константы `transcribe-job.ts`.

Не в окружении: это **поведение продукта**, а не настройка машины, и переменная окружения
здесь дала бы третье место, где число может разойтись с документом. Тест прибивает
значения независимо (порог обязан не следовать за кодом — урок FR-009, где подмена
`MAX_LOGIN_BODY` прошла зелёной, потому что тест брал константу из продакшена).

## Форма результата

```ts
export type ClaimResult =
  | { status: "empty" }
  | { status: "completed"; testimonialId: string }
  | { status: "failed"; testimonialId: string }
  // [FR-012] Новый исход. Отличается от failed НАМЕРЕННО: вызывающий код и логи
  // должны различать «больше не пытаемся» и «попробуем позже» — иначе разбор
  // инцидента упрётся в одинаковую запись для двух разных состояний.
  | { status: "retry_scheduled"; testimonialId: string; attempts: number };
```

## Что НЕ меняется и почему

`transcript_status` остаётся тремя значениями. Соблазн добавить `retrying` есть, но он
завёл бы четвёртое состояние, которое пришлось бы учитывать в каждом месте, читающем
статус, — включая витрину и модерацию. Ожидание повтора выражается парой
«`pending` + срок в будущем», и этого достаточно.
