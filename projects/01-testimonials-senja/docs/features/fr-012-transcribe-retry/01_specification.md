# FR-012 · Спецификация: повтор транскрипции при сбое STT

## Проблема

`transcribe-job.ts:112-119`: любой `SttApiError` переводит отзыв в `transcript_status =
'failed'` немедленно и навсегда. Разовый сетевой сбой, таймаут или временная недоступность
сервиса распознавания **безвозвратно** лишает отзыв расшифровки — при том что схема
(`003_core.sql:63`) допускает возврат строки в очередь: `pending` остаётся валидным статусом.

Владелец при этом не видит ничего: отзыв модерируем, просто без текста. Причину узнать
неоткуда, повторить — нечем.

## Функциональные требования

| # | Требование |
|---|---|
| FR-012.1 | Сбой STT не переводит отзыв в `failed` сразу: попытка засчитывается, строка остаётся в очереди |
| FR-012.2 | Число попыток ограничено. Исчерпание → `failed`, отзыв остаётся валидным и модерируемым |
| FR-012.3 | Между попытками выдерживается **возрастающая** задержка |
| FR-012.4 | Число попыток и время следующей хранятся в схеме, а не в памяти процесса |

## Нефункциональные требования

| # | Требование | Почему несущее |
|---|---|---|
| NFR-012.1 | Повтор **не создаёт вторую расшифровку** у одного отзыва | Успех записывает `transcript` одним `UPDATE` той же строки. Вторая запись означала бы потерю или дублирование текста автора |
| NFR-012.2 | Строка, ожидающая повтора, **не выбирается** очередью до срока | Иначе задержка не задержка: воркер крутил бы одну строку в цикле, сжигая квоту STT |
| NFR-012.3 | Ожидающая повтора строка не блокирует остальные | Очередь берёт по одной с `SKIP LOCKED`; исключение по сроку обязано быть в **условии выборки**, а не в коде после |
| NFR-012.4 **[v2]** | Не-`SttApiError` **тоже** получает задержку, но НЕ помечается `failed` до исчерпания попыток | Ревизия 1 предписывала «`failed` сразу», и это была смена существующего поведения без обоснования. Причина отказа не в провайдере — помечать отзыв `failed` рано. Но и оставлять как есть нельзя: строка остаётся `pending`, `ORDER BY created_at` выбирает **её же** каждый тик, и одна «ядовитая» запись блокирует всю очередь навсегда, повторяясь каждые 5 секунд (`index.ts` → `pollIntervalMs = 5000`, `transcribe-job.ts:151-156` — исключение обрывает внутренний цикл) |
| NFR-012.6 **[v2]** | Срок вычисляется по **стенным часам**, а не по времени начала транзакции | В Postgres `now()` = `transaction_timestamp()`. Транзакция открывается ДО сетевого вызова к STT, а вызов может занимать минуты. При вызове дольше задержки записанный срок оказывается в прошлом уже на момент `COMMIT` — задержки нет вовсе, и ровно в том режиме, ради которого фича написана |
| NFR-012.8 **[v3]** | Если `ROLLBACK` сам упал, соединение возвращается в пул **с ошибкой** (`release(err)`), а не молча | По исходникам `pg` `release()` без аргумента не делает отката и не уничтожает клиента. Соединение в состоянии abort вернулось бы в пул и роняло бы **любой** следующий запрос, включая `BEGIN`. Пул деградировал бы по одному соединению за случай, молча, а в лог уходил бы `25P02` вместо настоящей причины |
| NFR-012.7 **[v2]** | Учёт попытки при не-`SttApiError` идёт отдельной транзакцией **на том же соединении** после `ROLLBACK` | Предписывать `UPDATE` + `COMMIT` в транзакции, откатываемой из-за обрыва соединения с БД, значит предписать невыполнимое ровно тогда, когда оно предписано. **Тем же соединением**, а не новым из пула: второе соединение на каждый сбой вдвое режет ёмкость пула именно в момент, когда сбои идут потоком |
| NFR-012.5 | Счётчик попыток не сбрасывается при успехе задним числом | След нужен для разбора: «расшифровалось с третьей попытки» — полезный факт |

## Критерии приёмки

| # | Критерий |
|---|---|
| AC-012.1 | Первый `SttApiError` оставляет `transcript_status = 'pending'` и увеличивает счётчик до 1 |
| AC-012.2 | Исчерпание попыток даёт `failed`; отзыв остаётся видимым и модерируемым |
| AC-012.3 | Задержка растёт от попытки к попытке (проверяется по значениям, а не по факту наличия) |
| AC-012.4 | Строка со сроком в будущем **не выбирается** очередью: воркер возвращает `empty` |
| AC-012.5 | Наступивший срок делает строку снова доступной |
| AC-012.6 | Ожидающая повтора строка не мешает выбрать ДРУГУЮ готовую |
| AC-012.7 | Успех после неудач: ровно один `transcript`, статус `completed`, счётчик **сохранён** |
| AC-012.8 **[v2]** | Не-`SttApiError`: счётчик растёт, срок планируется, статус остаётся `pending`, исключение **пробрасывается** выше |
| AC-012.10 **[v2]** | Не-`SttApiError` при исчерпании попыток → `failed`. Различается от AC-012.8 по счётчику: два поведения не должны проходить один критерий |
| AC-012.11 **[v3]** | Медленный клиент держит паузу, затем бросает `SttApiError`. Тест фиксирует `T_begin` **до** вызова и требует: записанный срок **строго больше `T_begin + RETRY_BASE_MS`**. На `clock_timestamp()` истинно при любой паузе; на `now()` ложно при любой паузе больше нуля — критерий разборчив И быстр. **Прежняя формулировка** («больше `clock_timestamp()` после возврата») была ложна: на сломанной формуле она проходит при любой паузе меньше задержки, то есть практически всегда |
| AC-012.14 **[v3]** | После не-`SttApiError` соединение возвращается в пул **пригодным**: следующий запрос на нём выполняется. Проверяется прогоном задания дважды подряд на одном пуле |
| AC-012.12 **[v2]** | Ядовитая строка (всегда не-`SttApiError`) не мешает выбрать следующую после планирования срока |
| AC-012.9 | Страж по исходнику: условие выборки содержит проверку срока — иначе NFR-012.2 держится на удаче |
| AC-012.13 **[v2]** | Страж по исходнику: в тексте `UPDATE`, планирующего срок, **нет** `now()` — только `clock_timestamp()` или параметр |

## Вне объёма

Ручной повтор из кабинета, уведомление владельца о неудаче, выбор другого провайдера STT.
