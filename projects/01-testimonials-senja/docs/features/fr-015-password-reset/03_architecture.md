## Миграция

```sql
create table if not exists password_reset_tokens (
  id uuid primary key default gen_random_uuid(),
  account_id uuid not null references accounts(id) on delete cascade,
  token_hash text not null unique,
  expires_at timestamptz not null,
  used_at timestamptz,
  created_at timestamptz not null default now()
);

create index if not exists password_reset_tokens_account_idx
  on password_reset_tokens (account_id) where used_at is null;

grant select, insert, update on password_reset_tokens to app_service;
```

**`token_hash`, а не токен** — та же дисциплина, что у `sessions.token_hash`, и по той же причине.
У донора значение лежит в Redis открытым (`password-reset.ts:40-58`); эту форму переносить нельзя.

**`unique` на `token_hash`** делает совпадение двух токенов ошибкой БД, а не тихим совпадением.

**`on delete cascade`** — удаление аккаунта уносит его токены.

**Частичный индекс `where used_at is null`** — гасить предыдущие приходится на каждом выпуске,
и это единственный частый запрос по `account_id`.

**Гранты только `app_service`.** RLS на этой таблице не включается **намеренно**: контекст
арендатора на пути восстановления ещё не установлен — человек не аутентифицирован, `account_id`
появляется только после погашения токена. Изоляцию обеспечивает то, что `account_id` берётся
**из самой строки токена**, а не из входных данных, — то есть подделать его нечем. Это
записано здесь, потому что «RLS нет» без объяснения читается как упущение.

## Граница ответственности

`lib/password-reset.ts` не знает ни про HTTP, ни про почту: принимает `client`, email или токен,
возвращает результат-объединение. Маршрут превращает в ответ. `lib/email.ts` не знает про БД.

**Отправка письма физически не может оказаться внутри транзакции**, потому что функция сброса не
принимает отправителя, а маршрут вызывает его после того, как `withService` вернулся. Это
свойство сигнатур, а не порядка строк — флаг «не отправлять внутри» однажды передали бы неверно.

```ts
export type IssueResult =
  | { ok: true; token: string }        // токен нужен маршруту, чтобы собрать ссылку
  | { ok: false; tooMany: boolean };   // null-случай (адреса нет) НЕ различается снаружи
```

Отсутствия аккаунта в типе нет намеренно: маршрут не должен иметь возможности ответить иначе.
Функция возвращает `{ ok: true, token }` только когда письмо действительно надо отправить, и
`{ ok: false, tooMany: false }` во всех остальных случаях — включая «адреса нет». Различить их
вызывающий не может, и NFR-015.3 закрыт формой типа, а не дисциплиной.

## Первый внешний вызов в проекте

До FR-015 ни один путь кода не ходил в сторонний сервис. Это меняет две вещи:

1. **Новая строка в дельте ресурсов** — «внешние вызовы», и она сразу самая опасная: время
   ответа провайдера нам не принадлежит.
2. **Новый класс отказа** — «сервис недоступен». Правило `fail-closed-defaults.md` требует, чтобы
   недоступность источника истины была отказом. Здесь **наоборот**: провайдер письма источником
   истины не является, и его отказ не должен ни откатывать токен, ни менять ответ. Это исключение
   из правила, и оно названо явно, чтобы не читаться как его нарушение.

## Роль БД

Обе транзакции идут под `withService`: человек не аутентифицирован ни в одной из них. Фильтр по
владельцу везде явный, а `account_id` берётся из строки токена — единственного места, где он
может появиться.
