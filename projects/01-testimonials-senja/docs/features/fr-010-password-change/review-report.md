## BLOCKER

### B-1. Гонка на строке `accounts`: «последний записавший побеждает», обе стороны получают «успех»

**Где.** `apps/web/src/lib/password-change.ts:104-107` (чтение хеша без `for update`),
`:130` (hash нового), `:132` (UPDATE), `:76` и `:85-90` (ключ лока — ПАРА, а не аккаунт).

**Что сломано.** Между `select password_hash` и `update accounts` проходит
`verifyPassword` + `hashPassword` — на замеренной машине ~42 мс, по П-17 отчёта валидации
под нагрузкой до 134 мс. В это окно любая другая транзакция может закоммитить свою смену
пароля того же аккаунта. `SELECT` без `FOR UPDATE` блокировку строки не берёт, а
advisory-лок сериализовать это не может **по построению**: его ключ — пара
(`accountId`, `ip`), и два разных адреса дают два разных лока. То есть механизм, который
`03_architecture.md` и AC-010.19 называют сериализацией конкурентных смен, сериализует
только совпадающие адреса — то есть две вкладки одного браузера, а не два устройства и
не «владелец против вора».

**Сценарий отказа (полный, не гипотетический).**
Вор сидит в кабинете по украденной cookie. Владелец замечает и меняет пароль `A → B` —
ровно то действие, ради которого фича написана. Вор в тот же момент (скрипт, реагирующий
на 401 своей сессии) шлёт свою смену `A → C`. Обе транзакции прочитали хеш `A`, обе
успешно его проверили, обе прошли лимитер по своим ключам.

Наблюдалось в прогоне, дословный вывод раундов 0, 2, 4, 5:

```
round 0: A={"ok":true} B={"ok":true} | вход A=false вход B=true | сессия A: ОТОЗВАНА
```

Владелец получил `200`, форма показала «Пароль изменён. Все остальные устройства вышли из
аккаунта», браузер получил cookie — и **эта cookie уже отозвана** вторым UPDATE, а пароль
в базе тот, который выбрал вор. Владелец выброшен, пароля не знает, восстановления в
системе нет, аккаунт у вора. Из шести раундов в четырёх «победила» вторая транзакция, в
двух — первая; исход определяется планировщиком.

**Почему это ЧЕТВЁРТОЕ повторение класса, а не новый дефект.** Ревизия 3 вернула
`hashPassword(next)` внутрь транзакции ради пункта AC-010.25 (не платить argon2 на пути
429). Побочно она поместила ~20-38 мс между чтением хеша и его перезаписью, то есть
**расширила это окно на длину одного argon2**. Правку проверяли на её сценарии (число
вызовов argon2), а разделяемый ресурс «строка `accounts`» не проверил никто —
`.claude/rules/shared-resource-verification.md`, вопрос 3 списка: «кто ещё стоит в очереди
за тем же ресурсом».

Отчёт валидации ревизии 3 (§2.1) прямо утверждает обратное: «Разделяемые ресурсы проверены
поимённо (пул, CPU, advisory-лок, **блокировка строки `accounts`**) — ни один не
деградировал». Проверка была рассуждением, и рассуждение ошиблось: деградировал именно
последний из перечисленных.

**Как чинить.** Любой из двух, оба по одной строке:

```sql
select password_hash from accounts where id = $1 for update
```

— и тогда обязательно отобразить `55P03` в `busy`/409 (см. H-2), иначе проигравший получит
500 вместо честного «повторите». Либо взять ВТОРОЙ `pg_try_advisory_xact_lock` в своём
пространстве имён по одному `accountId` — ровно та сериализация, которую документы уже
описывают как существующую. Ключ лимита при этом остаётся парой: запирания владельца
второй лок не создаёт, потому что живёт десятки миллисекунд, а не час.

**Критерий, без которого починка не считается.** Конкурентный тест, а не
последовательный: N одновременных `changePassword` одного аккаунта с РАЗНЫХ адресов, из
которых ровно один возвращает `ok`, остальные — `busy`; и вход старым паролем после этого
не работает ни разу. Сегодня AC-010.19 держит лок снаружи по ТОМУ ЖЕ ключу пары — то есть
проверяет случай, который в проде почти не встречается, и молчит о том, который
встречается.

### B-2. B-10 отчёта валидации не закрыт: грубый лимит 30/час не стережёт ни один критерий

**Где.** `password-change.ts:93` (`exceeded(PWCHANGE_IP_SCOPE, …)`), критерии —
`05_completion.md`, таблица из 25 строк; AC-010.26 в ней отсутствует.

**Что сломано.** Дефекта в коде нет — оба `exceeded` на месте. Сломан набор критериев:
удаление **только** проверки по IP отключает грубый лимит целиком, и все 37 тестов
остаются зелёными. AC-010.15 продолжает видеть запись в `PWCHANGE_IP_SCOPE` (её никто не
трогал), AC-010.10 продолжает срабатывать на паре, AC-010.16 продолжает проходить с
другого адреса. Мутация M9 убирает **оба** `exceeded` и половину не ловит.

Это ровно та форма, которую ревизия 3 закрыла для `record` (M8b/M8c) и не заметила у
соседнего оператора. Счётчик, который пишут и никогда не читают, — зеркало того самого
дефекта, который эта фича чинит в `sessions.revoked_at`.

**Почему блокер, а не среднее.** Отчёт валидации ревизии 3 назвал это ЕДИНСТВЕННЫМ
блокером и дал готовый текст критерия (AC-010.26) и двух мутаций (M9b/M9c) — цена закрытия
один тест. Реализация прошла мимо. `.claude/rules/guard-must-be-able-to-fail.md`: проверка,
которая не может показать красное, проверкой не является.

**Как чинить.** Дословно текст из `validation-report.md` §1: 8 аккаунтов × 4 неверные
попытки с одного адреса, 31-я и 32-я получают 429; пороги в тесте числами.

## HIGH

### H-1. Успешная смена не ограничена ничем — неограниченный расход argon2 из одной учётки

**Где.** `password-change.ts:120-121` (`record` только в ветке `!verifyPassword`),
`:127-129` — комментарий, обосновывающий это.

**Что сломано.** Прогон: **20 успешных смен подряд одной парой (аккаунт, IP) за 1131 мс,
ни одна не отклонена.** Каждая стоит `verify` + `hash` = два argon2, каждый 19 МиБ памяти,
42 мс CPU на ненагруженной машине. Порог 5 не участвует: он считает только неудачи.

Комментарий `:128-129` утверждает: «самоограничивается (после успеха сессия сменилась)».
Это неверно дважды: ответ выдаёт рабочую cookie в том же HTTP-ответе (`route.ts:84`), и
новый пароль вызывающему известен — он его сам и выбрал. Цикл `B→C→B→C` не требует ничего,
кроме одной валидной учётки.

**Сценарий отказа.** Регистрация в проекте лимитера не имеет вовсе (`/api/auth/register`,
отмечено в отчёте валидации). Атакующий заводит 20 аккаунтов и с 20 адресов крутит цикл
смены пароля. Advisory-лок по паре ограничивает КАЖДУЮ пару одним запросом в полёте, но
не число пар. 20 пар × 2 argon2 × 19 МиБ — это 8 ядер под нагрузкой и деградация входа,
который считает argon2 на том же процессоре. Шапка самого файла (`:16-18`) называет этот
эффект как повод для порядка операций — и не закрывает его на пути, который вдвое дороже.

**Как чинить.** Отдельный scope `pwchange_success` со своим порогом (10/час на пару —
с большим запасом над любым живым сценарием) и запись в него ПОСЛЕ успеха, до COMMIT.
Одна строка в шаге 4 плюс критерий. Это H-8 отчёта валидации, дословно.

### H-2. `lock_timeout` даёт 500, а не 409 — и именно на том сценарии, ради которого введён 409

**Где.** `password-change.ts:80` (`set local lock_timeout = '250ms'`), `route.ts:71-79`
(нет обработки исключения).

**Что сломано.** `SET LOCAL lock_timeout` действует на ВСЕ последующие операторы
транзакции, а не только на захват advisory-лока (который к тому же `try` и ждать не
умеет). Реально таймаут срабатывает на `update accounts` (`:132`) и `update sessions`
(`:135`). При срабатывании Postgres бросает `55P03`, `withAccount` откатывает и
пробрасывает, маршрут не ловит.

Прогон на уровне маршрута, дословно:

```
ROUTE: МАРШРУТ БРОСИЛ НАРУЖУ: canceling statement due to lock timeout
```

То есть в Next это 500. Форма (`change-password.tsx:35-38`) на 500 не получит JSON, покажет
запасное «не удалось сменить пароль» — человек не поймёт, что делать, и повторит, а
повтор в этой ситуации как раз уместен, но интерфейс об этом не говорит.

**Сценарий отказа.** Это тот же сценарий, что B-1: два устройства владельца, или владелец
против вора. Если транзакции разъедутся во времени — B-1 (обе «успешны»); если совпадут на
UPDATE — H-2 (500 у одной). Оба исхода неверны, и оба маскируют друг друга: 409, который
описывают документы, не получает никто.

**Как чинить.** В маршруте: `catch (e) { if (e?.code === '55P03' || e?.code === '40P01')
return 409 BUSY; throw e; }`. И привести `03_architecture.md` в соответствие — сегодня он
описывает сериализацию, которой в коде нет. Это H-5 отчёта валидации, дословно.

### H-3. Тест AC-010.12 роняет ЧУЖИЕ тестовые файлы — набор врёт красным примерно раз в десять прогонов

**Где.** `apps/web/tests/password-change.test.ts:273-284`, комментарий `:263-266`.

**Что сломано.** Тест вешает на таблицу `sessions` ограничение
`check (revoked_at is null) not valid`. Ограничение **глобальное для базы**, а vitest по
умолчанию гоняет файлы параллельно (`vitest.config.ts` ничего не отключает). Пока
ограничение висит (~300 мс), любой параллельный тест, выполняющий смену пароля, падает.

Комментарий в тесте утверждает обратное: «FR-010 — единственный писатель этой колонки во
всём проекте, поэтому параллельные тесты оно не заденет». Единственный писатель — да; но
писателем его вызывают ТРИ файла фичи, и они запускаются одновременно.

Воспроизведено дважды, независимо:

*Наблюдение в живом прогоне* — первый из десяти полных прогонов `npx vitest run`:

```
 ❯ runInTransaction ../../packages/db/src/tenant.ts:33:20
 ❯ POST src/app/api/auth/password/route.ts:71:18
 ❯ tests/password-change-route.test.ts:95:17
   update sessions set revoked_at = now() where account_id = $1 …
 Test Files  1 failed | 25 passed | 1 skipped (27)
```

Упал AC-010.18 (чужой `account_id` в теле) — критерий безопасности, к ограничению
отношения не имеющий.

*Детерминированное доказательство механизма* — то же ограничение, поставленное вручную,
и смена пароля рядом:

```
ПАРАЛЛЕЛЬНЫЙ ТЕСТ ВИДИТ: new row for relation "sessions" violates check constraint / code=23514
```

**Почему высокий, а не средний.** Красный набор раз в десять прогонов — это машина,
обучающая людей перезапускать проверку вместо того, чтобы её читать. Первый настоящий
регресс, пойманный этим набором, будет списан на «оно иногда так». Ровно то, ради чего
написан `.claude/rules/guard-must-be-able-to-fail.md`, только с обратным знаком.

Отчёт валидации (H-7, п. 5 списка «что сделать до Phase 3») требовал трёх вещей: чистить
`sessions` перед `ALTER`, задать `ALTER` собственный `lock_timeout`, снимать ограничение в
`finally`. Сделано одно — `finally`. Плюс `NOT VALID`, который решает другую задачу
(не падать на прошлых строках) и от параллельных файлов не защищает.

**Как чинить.** Либо изолировать: `describe.sequential` не помогает (изоляция нужна между
ФАЙЛАМИ) — нужен отдельный vitest-проект/`fileParallelism: false` для этого файла, либо
`poolOptions.threads.singleThread` для набора. Либо сменить механизм индукции на такой,
который не трогает схему: подменить `createSession`/клиент так, чтобы падал именно второй
UPDATE в этой транзакции.

## MEDIUM

### M-1. Нет подтверждения нового пароля, а восстановления в системе не существует

**Где.** `change-password.tsx:64-75` — одно поле `new_password`.

Опечатка в единственном поле меняет пароль на неизвестный владельцу. Смягчение есть и оно
реальное: в этом браузере остаётся свежая cookie, и можно сменить ещё раз. Но:
восстановления пароля в MVP нет (`05_completion.md`, риск 1), маршрута выхода в проекте
нет вовсе (`grep revoked_at` даёт ровно двух потребителей — `password-change.ts` и
`current-session.ts`), TTL сессии 30 дней. То есть окно на исправление — до первой чистки
cookie, после чего аккаунт потерян безвозвратно.

Поле `new_password_confirm` на клиенте стоит пяти строк и не требует изменений сервера.

### M-3. Неаутентифицированный POST стоит транзакции и не ограничен ничем

Свойство разделяется с дашборд-путями и потому не ново, но это POST-маршрут — то есть
приглашение к автоматизации, — и он добавлен этой фичей.

### M-5. Значение окна лимита не закреплено ничем

**Где.** `password-change.ts:47` (`PWCHANGE_WINDOW = { seconds: 3600 }`).

Пороги 5 и 30 закреплены литералами в AC-010.24 (`password-change.test.ts:400-401`).
Окно — нет: `PWCHANGE_WINDOW` в тестах только импортируется и передаётся в `count`, но его
значение не утверждается ни разу (проверено grep'ом по всем 27 файлам тестов). Правка
`{ seconds: 1 }` превращает часовой лимит в секундный; AC-010.10 делает свои пять попыток
за ~200 мс и в секунду укладывается. M-9 отчёта валидации, закрыт наполовину.

## LOW

### L-1. `extractClientIP` возвращает `'unknown'` — общий ключ грубого лимита

`client-ip.ts:46`. Без заголовков прокси все запросы получают один ключ, и порог 30/час
становится общим для всех. За Caddy не воспроизводится, но это единственное, что отделяет
конфигурацию от общего запирания смены пароля. Свойство унаследовано от входа, не ново.

### L-2. Истёкшая сессия показывает «неверный текущий пароль»

`route.ts:23,51`. Совпадение тел — осознанная мера (NFR-010.4) и она правильная. Но
дашборд и так редиректит неаутентифицированного (`page.tsx:32`), значит увидеть это
сообщение можно ровно одним способом: сессия истекла при открытой вкладке. Человек будет
перенабирать верный пароль. Клиент может обрабатывать 401 перезагрузкой страницы — оракула
это не создаёт, потому что браузер и так знает состояние своей cookie.

### L-3. Чек-лист готовности не заполнен и ссылается на устаревший перечень мутаций

`05_completion.md:20-25` — все пункты `- [ ]`, включая «Все AC-010.x закрыты тестами» и
«Выкачено на стенд, смена пароля проверена вживую», при том что ниже документ утверждает

прогнать ровно те, ради которых делалась ревизия 3. M-11 отчёта валидации.

### L-4. Транзакция смены пароля без `statement_timeout`

`password-change.ts:80` задаёт только `lock_timeout`. Долгий argon2 под насыщенным CPU

границы. Не дефект сегодня, но единственная граница удержания — время argon2, а оно растёт
с конкуренцией нелинейно.

## Ответы на три заданных вопроса

**1. Пул соединений на пути успеха.** `PGPOOL_MAX` = 30, `PGPOOL_CONNECTION_TIMEOUT_MS` =
5000 (`packages/db/src/index.ts:44,48`). Удержание на успехе — замерено 56 мс на смену
(20 смен за 1131 мс последовательно). Пул делят ВСЕ маршруты: один модульный синглтон.
Арифметика: 30 / 0,056 ≈ 535 одновременных успешных смен в секунду до исчерпания.
**Пул здесь не узкое место — CPU упирается раньше**: 2 argon2 по 19 МиБ на смену, 8 ядер
дают ~90 смен/с потолка по процессору. Но удержание НЕ аддитивно: при 30 одновременных
argon2 каждое держит соединение ~0,8 с (П-18), то есть под насыщением CPU пул исчерпывается
следом. Практический вывод: ограничивать надо не пул, а число одновременных argon2 —
и сегодня единственное, что это делает, — advisory-лок по паре, то есть **только по одной
паре, а не глобально**. См. H-1.

**2. Кто ещё ждёт advisory-лок.** Никто. Пространство имён 90_010 своё, лок `try` (не
ждущий), ключ включает IP. Вход берёт 90_009 — столкновения нет, проверено по коду.
Обратная сторона ровно в этом: **лок не сериализует то, что документы считают
сериализованным** (B-1).

**3. `lock_timeout = 250ms` на последующих операторах.** Да, применяется ко всем, включая
оба UPDATE и вставку сессии. Ложный отказ достижим — воспроизведён удержанием строки
`accounts`. Владелец видит **500**, не 409 и не понятную ошибку. См. H-2.
