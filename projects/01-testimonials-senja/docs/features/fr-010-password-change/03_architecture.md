## Граница ответственности

`lib/password-change.ts` не знает про HTTP: принимает `client`, `accountId`, `ip`, текущий
пароль и **готовый хеш** нового, возвращает результат-объединение. Маршрут превращает его
в ответ и ставит cookie.

Так проверяются инварианты без поднятия сервера — тот же приём, что в `lib/login.ts`.

```ts
export type ChangeResult =
  | { ok: true; token: string }
  | { ok: false; reason: 'unauthorized' | 'too_many' | 'busy' | 'invalid_new' };
```

`busy` отделён от `too_many` намеренно (H-3, AC-010.19). Проверка сессии идёт в **своей**
транзакции (`current-session.ts:26`), смена — в следующей; две одновременные смены пароля
сериализуются TRY-локом, и вторая при общем `too_many` получила бы «слишком много попыток» —
ответ, не соответствующий происходящему. `409` говорит правду.

Причина отказа здесь **есть**, в отличие от входа: перечислять нечего — аккаунт уже известен
из проверенной сессии, а «новый пароль не годится» человеку надо показать. Но `unauthorized`
один на «нет аккаунта» и «пароль не тот» (NFR-010.4).

**Тип — это и есть реализация NFR-010.7.** `accountId` приходит параметром, а не полем
разобранного тела: у функции физически нет доступа к запросу. Страж AC-010.17 закрепляет
это, запрещая файлу упоминать `Request`, `cookies` и `json(`.

## Роль БД и почему это самое опасное место проекта

Путь дашбордный → `withAccount`, роль `app_authenticated`.

**RLS на `accounts` и `sessions` НЕ действует** (`007_rls.sql:31`: «вне правила Architecture
§3.1»), при этом `update` этой роли выдан (`:36`). Привычное рассуждение «RLS отфильтрует
сама» здесь **ложно**. Проверено прогоном (`validation-report.md` §0): из-под контекста
аккаунта A правится пароль аккаунта B, а `UPDATE` без `WHERE` правит все аккаунты сразу;
контрольный `select from projects` из того же контекста отдаёт 0 строк — то есть RLS
работает везде, кроме этих двух таблиц.

Поэтому NFR-010.2 закрыт с трёх сторон:

1. поведенчески — AC-010.5, AC-010.6 (чужой аккаунт не задет при работе со своим);
2. по источнику — AC-010.17, AC-010.18 (своим не может быть объявлен чужой);
3. стражем по исходнику — AC-010.13, **по фактическим именам ключей**: `accounts` → `id`,
   `sessions` → `account_id`. Формулировка ревизии 1 требовала `account_id` от обеих таблиц
   и падала бы на верном коде; будучи ослаблена до «`id` ИЛИ `account_id`», она перестала бы
   ловить что-либо. Страж покрывает **оба** новых файла: запрос, написанный в маршруте,
   ревизией 1 не просматривался вовсе.

Ни одна из трёх сторон не заменяет другие: (1) молчит при подмене источника, (2) молчит при
забытом `WHERE`, (3) молчит при верном по форме, но неверном по смыслу запросе.
