## Граница ответственности

`lib/password-change.ts` не знает про HTTP: принимает `client`, `accountId`, два пароля,
возвращает результат-объединение. Маршрут превращает его в ответ и ставит cookie.

Так проверяются инварианты без поднятия сервера — тот же приём, что в `lib/login.ts`.

```ts
export type ChangeResult =
  | { ok: true; token: string }
  | { ok: false; reason: 'unauthorized' | 'too_many' | 'invalid_new' };
```

Здесь причина в отказе **есть**, в отличие от входа: перечислять нечего — аккаунт уже
известен из проверенной сессии, а «новый пароль не годится» человеку надо показать.
Но `unauthorized` один на «нет аккаунта» и «пароль не тот» (NFR-010.4).

## Роль БД и почему это опасное место

Путь дашбордный → `withAccount`, роль `app_authenticated`.

**RLS на `accounts` и `sessions` НЕ действует** (`007_rls.sql:31`: «вне правила
Architecture §3.1»), при этом `update` этой роли выдан (`:36`). То есть привычное
рассуждение «RLS отфильтрует сама» здесь **ложно**, и цена ошибки максимальна: забытый
`account_id` в `WHERE` меняет пароль чужому аккаунту или гасит чужие сессии.

Поэтому NFR-010.2 закрыт не только тестами на изоляцию (AC-010.5, AC-010.6), но и стражем
по исходнику (AC-010.13): любой запрос к этим двум таблицам обязан нести `account_id`.
