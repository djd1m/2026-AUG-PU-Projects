# FR-010 · Краевые случаи

| Случай | Ожидание | Почему |
|---|---|---|
| Нет сессии | `401`, ничего не изменено | FR-010.1 |
| Неверный текущий пароль | `401`, пароль прежний, сессии живы, счётчик +1 | AC-010.7 |
| Новый пароль короче 8 / длиннее 200 | `400` до обращения к БД | AC-010.8 |
| Новый пароль равен текущему | `400` | AC-010.9 |
| Нестроковые поля | `400`, маршрут не падает | — |
| Тело больше предела | `413` | AC-010.11 |
| Успех | все сессии отозваны, новая выдана, старая cookie мертва | AC-010.2–010.4 |
| Второй аккаунт | его пароль и сессии не тронуты | AC-010.5, AC-010.6 |
| Лимит исчерпан | `429` без цифр | AC-010.10 |
| Отказ на любом шаге | ни пароль, ни сессии не изменены | AC-010.12 |

## Тест-стратегия

**Слой 1, поведение** — все строки выше на живой БД. Пороги прибиты в тесте независимо
от кода: порог, следующий за константой продакшена, не является порогом.

**Слой 1, стражи по исходнику:**
- запросы к `accounts`/`sessions` несут `account_id` (AC-010.13);
- `insert into sessions` по-прежнему ровно в одном файле — новая фича не должна завести
  вторую точку выдачи.

**Испытание на способность падать** — таблица мутаций:

| Внедрить | Обязан упасть |
|---|---|
| Убрать `AND account_id` из отзыва сессий | AC-010.5 |
| Убрать `WHERE id = accountId` из смены пароля | AC-010.6 |
| Отзывать только «прочие» (`token_hash <> текущий`) | AC-010.3 — вор остаётся внутри |
| Убрать выдачу новой сессии | AC-010.4 — владелец заперт |
| Разнести пароль и отзыв по разным транзакциям | AC-010.12 |
| Убрать запись в счётчик попыток | AC-010.10 |

Каждая строка — проверяется прогоном, а не рассуждением. За две предыдущие фичи три
критерия оказались неразборчивыми при убедительном обосновании.
