# FR-010 · Краевые случаи и испытание критериев

> **Ревизия 3.** Добавлены M8b, M8c, M13b и M18: половинные мутации счётчика и
> перенос argon2 — ровно те, что ревизия 2 не проверяла ничем.
>
> **Ревизия 2.** Таблица мутаций ревизии 1 утверждала покрытие, которого не было: из шести
> строк подтверждалась прогоном одна. Здесь у каждой строки назван **механизм** внедрения,
> а не только ожидание.

## Тест-стратегия

**Слой 1, поведение** — все строки выше на живой БД. Пороги прибиты в тесте числами
(`PAIR_THRESHOLD = 5`, `IP_THRESHOLD = 30`, окно 3600 с): порог, импортированный из
продакшен-кода, не является порогом — он подтвердит любое значение, включая изменённое.

**Слой 1, стражи по исходнику** — AC-010.13, .17, .21, .22, .23, .24.

**Слой 3** — обязательная сверка таблицы ниже прогоном перед закрытием фичи.

## Таблица мутаций — с механизмом внедрения

Правило, выведенное из трёх предыдущих фич: строка засчитывается, только когда мутация
**внесена в код, тест прогнан и покраснел**. Согласованное рассуждение о покрытии за
доказательство не принимается — за две фичи три критерия оказались неразборчивыми именно
при убедительном обосновании.

| # | Что внедрить | Как именно | Обязан упасть |
|---|---|---|---|
| M1 | Отзыв не фильтрует владельца | убрать `AND account_id = $1` | AC-010.5 |
| M2 | Смена не фильтрует владельца | убрать `WHERE id = $1` | AC-010.6 |
| M3 | Отзывать только «прочие» | дописать `AND token_hash <> $current` | **AC-010.3** |
| M4 | Отзывать только текущую | заменить на `AND token_hash = $current` | **AC-010.14** |
| M5 | Не выдавать новую сессию | убрать `createSession` | AC-010.4 |
| M6 | Обратный порядок | выдача перед отзывом | AC-010.4 |
| M7 | Две транзакции | заменить один `withAccount` на два последовательных | AC-010.12 |
| M8 | Счётчик не пишется вовсе | убрать **оба** `rateLimit.record` | **AC-010.15** (и только он — AC-010.10 при засеве остаётся зелёным, ради чего .15 и добавлен) |
| M8b **[v3]** | Грубый лимит по IP не пишется | убрать **только** `record(PWCHANGE_IP_SCOPE, …)` | **AC-010.15** — он и добавлен ради этой строки. Ревизия 2 считала строки суммарно и была на этой мутации зелёной, то есть грубый лимит удалялся незаметно всему набору |
| M8c **[v3]** | Тугой лимит по паре не пишется | убрать **только** `record(PWCHANGE_PAIR_SCOPE, …)` | **AC-010.15**, и следом AC-010.10 (порог пары не набирается) |

| M13 **[v3]** | argon2 нового пароля считается на пути отказа | перенести `hashPassword` из ШАГА 3 в начало `changePassword`, до `verifyPassword` | **AC-010.22** — на неверном пароле число вызовов `hashPassword` станет 1 вместо 0 |

## Как индуцируется отказ для M7 (механизм ЗАМЕНЁН после ревью)

На корректной реализации между `UPDATE accounts` и `UPDATE sessions` ничего не падает само,
поэтому «разнести по двум транзакциям» без сбоя даёт тот же наблюдаемый результат. Отказ надо
**создать** — но не любой ценой.

**Первая версия вешала на таблицу `sessions` ограничение `CHECK (revoked_at is null) NOT VALID`
и была неверна.** Ограничение глобально для базы, а vitest гоняет файлы параллельно: пока оно
висело (~300 мс), параллельные файлы ЭТОЙ ЖЕ фичи падали на своих законных сменах пароля.
Набор врал красным примерно раз в десять прогонов — машина, обучающая людей перезапускать
проверку вместо того, чтобы её читать. Комментарий там утверждал «FR-010 единственный писатель
`revoked_at`, поэтому не заденет»: писатель действительно единственный, но **вызывают его три
файла, и запускаются они одновременно**.

**Действующий механизм — подменённый клиент.** Транзакция получает `Proxy`, роняющий ровно тот
`UPDATE sessions`, который в ней выполняется:

```ts
const failOnRevoke = (client: PoolClient): PoolClient =>
  new Proxy(client, {
    get(target, prop, recv) {
      if (prop !== 'query') return Reflect.get(target, prop, recv);
      return (text: unknown, params?: unknown) => {
        const sql = typeof text === 'string' ? text : (text as { text?: string })?.text ?? '';
        if (/update\s+sessions/i.test(sql)) return Promise.reject(new Error('индуцированный сбой'));
        return (target.query as (t: unknown, p?: unknown) => unknown)(text, params);
      };
    },
  }) as PoolClient;
```

Схему он не трогает вовсе, поэтому соседним файлам невидим **по построению**, а не по
рассуждению. Проверено: 8 полных прогонов подряд чистые.

**Утверждение, которое здесь стояло прежде, опровергнуто и удалено.** «Побочный эффект на
соседей отсутствует, и это проверено, а не предположено» — оно было предположением, и
предположение оказалось ложным.

## Область AC-010.12 — и почему счётчик из неё выведен

Ревизия 1 требовала «ни пароль, ни сессии, ни счётчик». Это противоречило AC-010.7
(«счётчик +1» при неверном пароле): выполнить оба одновременно нельзя. Область сужена до
пары «пароль + сессии». Счётчик живёт по своим правилам: на пути «неверный пароль» функция
возвращается штатно, транзакция коммитится, запись остаётся — так и задумано.
