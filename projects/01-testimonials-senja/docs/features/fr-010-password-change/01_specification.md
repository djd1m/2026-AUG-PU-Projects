# FR-010 · Спецификация: смена пароля и завершение сессий

## Проблема

Пароль задаётся один раз при регистрации и не может быть изменён никогда. Скомпрометированный
пароль нечем отозвать; украденную cookie — тоже: колонка `sessions.revoked_at` существует
(`003_core.sql:21`) и не используется ни одним путём кода.

## Отступление от формулировки роадмапа — и почему

Роадмап говорит: «смена пароля завершает **все прочие** сессии, текущую оставляет».

Так делать **нельзя**. Кража cookie не создаёт новую строку в `sessions` — вор пользуется
**той же** сессией, что и владелец. «Прочие» её не покрывают, и после смены пароля вор
остаётся внутри. Мера, ради которой фича существует, не срабатывает в главном сценарии.

Поэтому: смена пароля отзывает **ВСЕ** сессии аккаунта, включая текущую, и тут же выдаёт
владельцу новую. Снаружи это выглядит так же — человек остаётся в кабинете, — но вор
выброшен.

## Функциональные требования

| # | Требование |
|---|---|
| FR-010.1 | `POST /api/auth/password` принимает текущий и новый пароль; требует валидной сессии |
| FR-010.2 | Неверный текущий пароль → `401`, ничего не меняется |
| FR-010.3 | Успех отзывает **все** сессии аккаунта и выдаёт новую текущему браузеру |
| FR-010.4 | Форма смены пароля в кабинете |
| FR-010.5 | Новый пароль проходит те же границы, что при регистрации (не короче 8, не длиннее 200) и обязан отличаться от текущего |

## Нефункциональные требования `@security`

| # | Требование | Почему несущее |
|---|---|---|
| NFR-010.1 | Смена пароля и отзыв сессий — в **одной** транзакции | Иначе возможны два наблюдаемых состояния: пароль сменён, а старые сессии живы (вор внутри), либо сессии отозваны при старом пароле (владелец заперт) |
| NFR-010.2 | Все запросы к `accounts` и `sessions` фильтруют по `account_id` **явно** | RLS к этим таблицам **не применяется** (`007_rls.sql:31`), хотя `app_authenticated` имеет на них `update`. Забытый фильтр здесь означает смену чужого пароля или отзыв чужих сессий — и RLS не подстрахует |
| NFR-010.3 | Попытки подбора текущего пароля ограничены по аккаунту | Вор с украденной cookie перебирает текущий пароль изнутри. Без лимита он подберёт его и сменит, заперев владельца |
| NFR-010.4 | Ответ при неверном текущем пароле не отличается от ответа при любом другом отказе аутентификации | Разные ответы дали бы вору сигнал «сессия жива, пароль не тот» |
| NFR-010.5 | Предел размера тела — общий с входом и регистрацией | Маршрут аутентифицирован, но сессия могла быть украдена |
| NFR-010.6 | Новая cookie ставится в том же ответе, что и отзыв | Иначе между отзывом и следующим запросом владелец без сессии |

## Критерии приёмки

| # | Критерий |
|---|---|
| AC-010.1 | Верный текущий пароль → `200`, вход новым паролем работает |
| AC-010.2 | Вход **старым** паролем после смены → `401` |
| AC-010.3 | Cookie, выданная ДО смены, доступа не даёт |
| AC-010.4 | Cookie из ответа на смену — даёт |
| AC-010.5 | Сессии **другого** аккаунта не тронуты. Падает при забытом `account_id` |
| AC-010.6 | Пароль другого аккаунта не изменён. То же |
| AC-010.7 | Неверный текущий пароль: `401`, пароль в БД прежний, сессии живы |
| AC-010.8 | Новый пароль короче 8 или длиннее 200 → отказ, ничего не изменено |
| AC-010.9 | Новый пароль равен текущему → отказ |
| AC-010.10 | Превышение лимита попыток → `429` без цифр в теле |
| AC-010.11 | Тело больше предела → `413` |
| AC-010.12 | Отказ на любом шаге не оставляет частичного состояния: либо и пароль, и сессии, либо ничего |
| AC-010.13 | Страж по исходнику: в `lib/password-change.ts` нет запроса к `accounts`/`sessions` без `account_id` в `WHERE` |

## Вне объёма

Восстановление забытого пароля (нужна почта, которой в MVP нет), список активных сессий,
выборочный отзыв одной сессии.
