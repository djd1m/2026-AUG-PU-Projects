## 2. Ответы по семи заданным вопросам

### 2.1 AC-010.13 — страж по фактическим именам ключей (п. 1 задания, «главное»)

**Опасение не подтвердилось: страж зелёный на верной реализации и красный на M1 и M2.**
Проверено по реальной схеме и по собственному псевдокоду фичи, а не по формулировке.

Операторы верной реализации в области стража (`lib/password-change.ts`):

| Оператор | `accounts` → `where id = $` | `sessions` → `where account_id = $` |
|---|---|---|
| `select password_hash from accounts where id = $1` | ✅ есть | — |
| `update accounts set password_hash = $1 where id = $2` | ✅ есть | — |
| `update sessions set revoked_at = now() where account_id = $1 and revoked_at is null` | — | ✅ есть |
| `set local lock_timeout = '250ms'` | не упоминает ни ту, ни другую | |

**Гипотеза задания про `createSession` — не срабатывает, и это не случайность, а сцепка двух
стражей.** `insert into sessions` без `where` действительно существует, но живёт в
`lib/session.ts:80` — вне области AC-010.13 (она названа поимённо: два новых файла). Держит его
там существующий страж `tests/login.test.ts:299-306`: `insert into sessions` обязан встречаться
**ровно в одном файле**, и это `lib/session.ts`. То есть попытка вписать вставку в
`password-change.ts` (чтобы обойти AC-010.13) немедленно ломает страж выдачи сессий. Два стража
запирают друг друга, и ни один не бракует верный код. Это хорошо, и это стоит записать в
`03_architecture.md` явно — сейчас сцепка не названа, а держится на ней разборчивость обоих.

Ложных срабатываний по «соседним» словам тоже нет: `currentAccountId`, `withAccount`,
`sessionCookieOptions`, `SESSION_COOKIE`, `'./session'` подстрок `accounts` / `sessions` не
содержат ни в каком регистре.

**Два условия реализации, без которых страж всё-таки испортится** (не блокер, но выполнить обязательно):

1. **Сравнивать по оператору, а не по файлу.** Файловая форма («в файле есть `accounts` ⇒ в
   файле есть `where id = $`») **зелёная на M2**: после вырезания `WHERE` из `UPDATE` в файле
   остаётся `SELECT … where id = $1`, и условие выполняется. Разница между рабочим и нерабочим
   стражем — ровно здесь. M12 в `04_refinement.md` это ловит, но требование «по оператору» надо
   держать в тексте критерия, а не только в мутации.
2. **Читать исходник с вырезанными комментариями** — как это уже делает `read()`/`strip()` в
   `tests/login.test.ts:32-34`. Иначе комментарий «отзываем все sessions» станет «оператором,
   упоминающим sessions без `where account_id`». Дом уже так делает; надо не забыть.

### 2.2 AC-010.12 и индукция отказа через CHECK (п. 2 задания)

Проверено прогоном по всем четырём подпунктам. **Три из четырёх утверждений документа верны,
четвёртое неверно.**

| Утверждение `04_refinement.md` | Прогон | Итог |
|---|---|---|
| (а) ограничение добавляется на непустую `sessions` | П-1 | ✅ верно |
| (б) `UPDATE … revoked_at = now()` его нарушает | П-2 | ✅ верно |
| (в) вставку новых сессий не ломает | П-3 | ✅ верно |
| (г) «побочный эффект на соседей отсутствует, **и это проверено, а не предположено**» | П-4, П-5, П-6 | ❌ **неверно** (см. H-7) |

Механизм как таковой рабочий и критерий разборчив: на верной (однотранзакционной) реализации
исключение откатывает обе записи → зелёный; на M7 (две транзакции) первая уже закоммичена →
пароль сменён → красный. **B-4 закрыт.**

Неверно именно (г), и неверно двумя независимыми способами:

- **`ADD CONSTRAINT` проверяет ВСЮ таблицу, а не строки этого теста** (П-4). Любая уже отозванная
  строка роняет ALTER с `is violated by some row`. А отозванные строки в этой таблице оставит
  **сам файл теста FR-010**: AC-010.3, AC-010.5, AC-010.14 отзывают сессии. Порядок тестов
  становится несущим, чего документ не говорит.
- **`ADD CONSTRAINT` берёт ACCESS EXCLUSIVE** (П-5, П-6). Достаточно, чтобы соседний тест держал
  открытую транзакцию с обычным `select` по `sessions` — и ALTER встаёт в очередь; у `adminPool`
  `lock_timeout` не задан, то есть ждёт **бесконечно**. Хуже того, пришедший позже обычный
  читатель встаёт **за** ожидающим ALTER (П-6: 2 с простоя на пустой таблице). Утверждение
  «параллельно идущие тесты других файлов ограничение не заденут» опирается на семантику
  ограничения и не учитывает блокировку, которой оно берётся.

Посылка, на которой всё это строилось, при этом **верна** — см. §2.7.

### 2.3 B-5 / ключ лимита, и не открылась ли новая дыра (п. 3 задания)

**AC-010.16 разборчив: на M10 он падает.** С ключом по одному `accountId` владелец с другого
адреса попадает в тот же исчерпанный ключ и получает `429` — критерий красный. С парой — новый
ключ, `count = 0`, проходит. Мутация уронит критерий.

**Подделка IP владельца через `X-Forwarded-For` — невозможна, пока держится ровно одно условие,
и это условие сегодня выполнено и проверяемо.** `extractClientIP` берёт **последний** элемент
XFF (`lib/client-ip.ts:30-39`); последний дописывает Caddy, и это адрес непосредственного пира.
Вор, знающий адрес владельца, может прислать его первым элементом — он будет отброшен. Условие:
`web` не опубликован в обход прокси. Проверено: `docker-compose.yml:76` — `expose: ["3000"]`,
наружу смотрит только Caddy (`:133`). Правило и разбор того же класса —
`.claude/rules/docker-ports.md`, «За reverse-proxy приложение тоже не публикуется».
Дополнительно `accountId` берётся из проверенной сессии (NFR-010.7, AC-010.17/18), поэтому вторая
половина ключа тоже неподделываема. **Новой дыры парный ключ не открыл.**

Остаточный риск, который стоит назвать явно и который в документе не назван: **сосед по NAT**.
За CGNAT мобильного оператора вор и владелец могут иметь один адрес — тогда пара совпадает, и
запирание владельца снова возможно; а грубый счётчик 30/час, будучи ключом по IP, за большим NAT
общий на всех. Это не отменяет решения (ключ по одному аккаунту хуже во всех сценариях), но это
принимаемый риск, а сейчас он не записан — см. M-7.

### 2.4 H-1 / NFR-010.8 — верен ли размен (п. 4 задания)

**Размен «CPU дешевле соединения пула» верен. Утверждение, что расход CPU ограничен счётчиком, —
неверно.** Это и есть B-7; отвечаю по числам, как просили.

Что действительно улучшилось: argon2 нового пароля больше не удерживает соединение пула
(~38 мс на запрос, измерено П-9) и не удерживает advisory-лок. Против ревизии 1 это выигрыш, и
возвращать `hashPassword` внутрь транзакции **не нужно**.

Что сломалось: счётчик стоит **после** хеша, поэтому «5/час» не ограничивает число хешей.

| Сценарий | argon2/час | Чем ограничено |
|---|---|---|
| Как обещает документ (лимит до хеша) | 5 × 2 = **10** на пару «аккаунт+IP» | парный счётчик |
| Как получается по псевдокоду | **не ограничено** | ничем; каждый запрос = 1 хеш, даже если ответ `429`/`409` |
| Потолок машины (замер) | **168 хеш/с** (8 ядер), пик RSS 126 МиБ на 200 в полёте | железо |

Вор с украденной cookie — не худший случай; худший — любой, кто один раз зарегистрировался:
сессия у него своя, легальная, и бессрочная. 168 хеш/с — это 100 % CPU восьмиядерной машины на
запросах, каждый из которых для атакующего стоит одного HTTP-запроса. На VPS в 2–4 ядра порог
вчетверо ниже. argon2 входа и регистрации делит тот же процесс, то есть насыщение бьёт по входу.

Починка дешёвая и не трогает NFR-010.1 и AC-010.22: **быстрая непринудительная проверка обоих
счётчиков ДО `hashPassword`** — отдельная короткая транзакция только на `count` (индексированный
`rate_limit_events`, ~1 мс, соединение отпускается сразу). Авторитетная проверка, лок и запись
остаются внутри `withAccount` там, где они сейчас, — атомарность не страдает, двойная проверка
безвредна. И параллельно исправить утверждение в `02_pseudocode.md`: сейчас оно называет
границу, которой нет.

### 2.5 AC-010.19 — достижим ли 409 и различим ли он (п. 5 задания)

**Достижим — но только когда обе смены идут с одного IP; и это не тот случай, о котором говорит
критерий.** Проверено прогоном.

- Один IP → один ключ → `pg_try_advisory_xact_lock` возвращает `f` → `busy` → **409** (П-8). ✅
- Разные IP → **разные** ключи (`hashKey(PAIR_SCOPE, accountId, ip)`) → лок берут **обе**; вторая
  упирается в блокировку строки `accounts` и умирает по `set local lock_timeout = '250ms'` с
  `55P03` (П-7). Это исключение, а не `busy`, — маршрут отдаст **500**, а не 409.

То есть обоснование `03_architecture.md` — «две одновременные смены пароля сериализуются
TRY-локом» — **неверно**: лок сериализует пару «аккаунт+IP», а не аккаунт. Сценарий «владелец
меняет пароль на двух устройствах» (разные адреса) — это как раз общий случай. См. H-5.

**Полезен ли 409 атакующему.** Практически нет: он возникает только при конкуренции внутри одной
пары «аккаунт+IP», то есть вор видит собственные параллельные запросы. Узнать через него о
действиях владельца можно, лишь уже находясь за тем же адресом. Утечкой это не считаю.

Побочно: `busy` возвращается **до** обоих `exceeded`, поэтому при параллельном переборе с одного

такой запрос не делает, — но каждый такой 409 всё равно стоит одного argon2 (B-7).
