# Доверие к email из Yandex ID для связывания аккаунтов

Вопрос: гарантирует ли Яндекс, что `default_email` / `emails` из
https://login.yandex.ru/info ПРИНАДЛЕЖАТ вошедшему пользователю (подтверждены),
или туда может попасть непроверенный адрес?

Короткий ответ: документация НЕ содержит гарантии подтверждённости и НЕ отдаёт
признака verified. Значит связывание по email обязано быть fail-closed.

---

## 1. Что ИМЕННО возвращают `default_email` и `emails` (дословно)

Источник: Яндекс, «Получение информации о пользователе»
(https://yandex.ru/dev/id/doc/ru/user-information, англ. https://yandex.com/dev/id/doc/en/user-information).

- `default_email` — «E-mail по умолчанию, предназначенный для связи с пользователем».
- `emails` — «Массив электронных адресов пользователя. В настоящее время включает
  единственный e-mail — e-mail по умолчанию».

Ключевое: формулировка «для связи с пользователем» — это НЕ «подтверждённый адрес,
которым пользователь владеет». Документация нигде не утверждает, что этот адрес
проверен на владение. (Догадка: скорее всего в типичном случае это основной ящик
`login@yandex.ru`, которым пользователь владеет по факту существования аккаунта, — но
документация этого НЕ гарантирует и не запрещает иную конфигурацию. Помечено как догадка.)

## 2. Может ли пользователь назначить основным/добавить адрес на ЧУЖОМ домене, и требует ли Яндекс подтверждения — ЯДРО ВОПРОСА

Установлено ЧАСТИЧНО.

Источник: справка Яндекс ID, «Дополнительные адреса почты»
(https://yandex.ru/support/id/ru/authorization/email).

- Добавление ЗАПАСНОЙ (дополнительной) почты ТРЕБУЕТ подтверждения: «Яндекс отправит
  на введённый адрес письмо с кодом подтверждения», код действует 3 часа, подтверждение
  по ссылке или вводом кода. Это относится к адресам восстановления доступа.
- Назначение дополнительных адресов по справке — ВОССТАНОВЛЕНИЕ доступа и оповещения о
  подозрительной активности. Про то, что дополнительный адрес становится `default_email`
  в ответе API, справка НЕ говорит.
- Ограничения по домену (можно ли @gmail.com) справка НЕ уточняет — сказано просто «почту».
- Остаётся ли НЕподтверждённый адрес в профиле после истечения кода — НЕ установлено.

Вывод по пункту: подтверждение для ЗАПАСНОЙ почты есть. Но НЕ установлено, что адрес,
попадающий в `default_email`/`emails` ответа API, — это всегда именно подтверждённый или
именно принадлежащий Яндексу ящик. Связь «поле API ⇄ статус подтверждения» в документации
ОТСУТСТВУЕТ. Строить безопасность на «наверное это подтверждённый ящик» нельзя.

## 3. Признак подтверждённости (verified/confirmed) в ответе API

НЕ УСТАНОВЛЕНО наличия — фактически отсутствует. В описании полей ответа
(https://yandex.ru/dev/id/doc/ru/user-information) НЕТ поля вида `email_verified`,
`is_email_confirmed` и т.п. Приложение не может программно отличить подтверждённый адрес
от неподтверждённого. Это решающий факт: без флага verified доверять email нельзя.

## 4. Что делают известные реализации

- Auth.js (провайдер Yandex, https://authjs.dev/reference/core/providers/yandex, код
  packages/core/src/providers/yandex.ts):
  ```ts
  profile(profile) {
    return {
      id: profile.id,
      name: profile.display_name ?? profile.real_name ?? profile.first_name,
      email: profile.default_email ?? profile.emails?.[0] ?? null,
      ...
    }
  }
  ```
  email берётся из `default_email`/`emails[0]` БЕЗ какой-либо проверки подтверждённости.

- Политика Auth.js `allowDangerousEmailAccountLinking`
  (https://authjs.dev/reference/core/providers, обсуждения nextauth #2808/#9228):
  автоматическое связывание аккаунтов по email ВЫКЛЮЧЕНО по умолчанию и названо
  «dangerous» именно потому, что «часто приводит к захвату аккаунтов у третьих сторон,
  которые используют email как идентификатор». Включать его безопасно только для
  провайдеров, про которых ИЗВЕСТНО, что они надёжно верифицируют email (Google, GitHub,
  Microsoft), либо при наличии claim `email_verified`. Яндекс такого claim НЕ отдаёт (п.3).
  Само название «dangerous» — сильный косвенный ответ: экосистема считает связывание по
  email небезопасным по умолчанию.

- Общий класс уязвимости подтверждён Snyk Labs
  (https://labs.snyk.io/resources/OAuth-mistake-takeover-part-one/) и GitLab
  (https://gitlab.com/gitlab-org/gitlab/-/issues/228629): «обход верификации email при
  OAuth ведёт к захвату аккаунтов на третьих сторонах». Это ровно сценарий из постановки.

## 5. Рекомендуемый ключ учётной записи и стабильность

Источник: https://yandex.ru/dev/id/doc/ru/user-information.

- `id` — «Уникальный идентификатор пользователя Яндекса» (глобальный для пользователя).
- `psuid` — «Идентификатор авторизованного пользователя … формируется на стороне Яндекса
  на основе пары `client_id` и `user_id`» (привязан к вашему приложению).

Догадка (помечена): ключом учётной записи логично брать `id` (или `psuid` для privacy —
он не раскрывает пользователя между приложениями), а НЕ email. Явной фразы «используйте id
как ключ» в документации я не нашёл — это архитектурный вывод, а не цитата.

---

## Вывод

Связывать вход через Yandex ID с существующим паролевым аккаунтом ПО EMAIL без
дополнительной проверки НЕЛЬЗЯ:

1. API не отдаёт признака подтверждённости email (п.3) — приложение не может отличить
   принадлежащий пользователю адрес от вписанного.
2. Документация НЕ гарантирует, что `default_email`/`emails` — подтверждённый и
   принадлежащий пользователю адрес (п.1, п.2).
3. Экосистема (Auth.js) считает такое связывание «dangerous» и требует для него флага
   `email_verified`, которого у Яндекса нет (п.4).

Правильная схема (fail-closed): существующий аккаунт с паролем НЕ привязывается
автоматически по совпадению email. Человек сначала входит паролем и привязывает Yandex ID
из настроек; либо после входа через Yandex ID требуется подтверждение владения адресом
(письмо со ссылкой) до объединения. Ключ учётной записи Yandex — `id`/`psuid`, не email.

## НЕ УСТАНОВЛЕНО

- Может ли `default_email` в ответе API быть адресом на чужом домене (@gmail.com и т.п.),
  и остаётся ли он там неподтверждённым. Справка ограничений по домену не даёт, связи
  «поле API ⇄ статус подтверждения» нет.
- Остаётся ли неподтверждённый добавленный адрес в профиле после истечения кода (3 часа).
- Явной рекомендации Яндекса «использовать id как ключ учётной записи» в документации не
  найдено — это вывод по свойствам полей, а не цитата.

Поскольку ядро вопроса (может ли непроверенный адрес попасть в поля API) документацией
прямо НЕ закрыто, вывод обязан быть консервативным — см. «Вывод».
