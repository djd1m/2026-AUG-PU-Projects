# Оценка по коду: SSO (Yandex ID / Sber ID) рядом с email+пароль в проекте 01

**ВЕРДИКТ:** одна крупная фича уровня «FR-009 + половина FR-010»: ~600–900 строк продуктового кода + ~600–900 строк тестов (~40–50 тестов), одна миграция; архитектура проекта СОВМЕСТИМА без переломов — createSession переиспользуется как есть, login.ts не меняется вовсе, главный риск не в коде, а во ВТОРОМ внешнем вызове проекта и в политике связывания учёток по email.

---

## 1. СХЕМА

**Отдельная таблица связей, не колонки в accounts.** Колонки (`sso_provider`, `sso_id`) запирают
аккаунт на одного провайдера; человек, вошедший сначала Яндексом, потом Сбером, — та же учётка.

**«Паролем, потом SSO с тем же email» — ОДНА учётка.** `accounts.email` уже `not null unique`
(003_core.sql:10), вторая учётка на тот же email невозможна физически — вопрос только в политике
связывания (см. риск в п. 8).

Миграция `packages/db/migrations/014_sso.sql` (~45 строк SQL):

```sql
-- 014_sso.sql — внешние идентичности (FR-0xx SSO).
create table if not exists account_identities (
  id uuid primary key default gen_random_uuid(),
  account_id uuid not null references accounts(id) on delete cascade,
  provider text not null check (provider in ('yandex', 'sber')),  -- allowlist В СХЕМЕ, не в env (fail-closed-defaults §3)
  provider_user_id text not null,
  email_at_link text not null,          -- email, который провайдер утверждал в момент привязки (аудит-след)
  created_at timestamptz not null default now(),
  unique (provider, provider_user_id)   -- идемпотентность повторного коллбэка = ON CONFLICT, без advisory-лока
);
create index if not exists account_identities_account_id_idx on account_identities (account_id);

-- Пароль перестаёт быть обязательным: SSO-аккаунт его не имеет.
alter table accounts alter column password_hash drop not null;

-- Grants по образцу accounts/sessions (007_rls.sql:31-36): вход/коллбэк идут под app_service
-- ДО существования контекста аккаунта; RLS не применяется — таблица без project_id, тот же
-- класс, что accounts/sessions. delete не выдаётся никому (отвязка вне MVP).
grant select, insert on account_identities to app_service;
grant select on account_identities to app_authenticated;   -- показать «привязан Яндекс» в кабинете
```

State/PKCE-verifier таблицы НЕ требуют: живут 10 минут в HMAC-подписанной httpOnly-cookie
(секрет — существующий SESSION_SECRET, session.ts:104). Ноль строк схемы, ноль чистки протухших.

Правка типов: `packages/db/src/types.ts:23` — `password_hash: string` → `string | null` (~1 строка,
плюс каскад по местам чтения — см. п. 2).

## 2. ЧТО ЛОМАЕТСЯ В ИНВАРИАНТАХ: password_hash NOT NULL (003_core.sql:11)

Разрешение: **drop not null + трактовка NULL как «пароля нет» с заглушкой argon2**. Дыры «вошёл
с пустым паролем» не возникает, и вот почему по строкам:

- **login.ts НЕ МЕНЯЕТСЯ ВООБЩЕ.** Строка apps/web/src/lib/login.ts:127 уже написана как
  `const storedHash = account?.password_hash ?? (await dummyHash());` — NULL из БД коалесцируется
  в заглушечный хеш от 32 случайных байт, verifyPassword честно не сходится, счётчики пишутся,
  тайминг неотличим от «аккаунта нет» (NFR-009.2 сохраняется по построению). Нужен только ТЕСТ,
  закрепляющий это свойство (~15 строк): «аккаунт с password_hash NULL не входит НИКАКИМ паролем,
  включая пустой, и не отличим по времени».
- **password-change.ts — единственное место, где NULL взорвётся.** Строка 168:
  `verifyPassword(account.password_hash, candidate)` — @node-rs/argon2 на NULL-хеше бросит
  исключение → 500. Правка ~3 строки: `if (account.password_hash === null) { record оба счётчика;
  return unauthorized }` — SSO-аккаунт текущего пароля не имеет, отказ корректен. Оракула нет:
  маршрут аутентифицирован, перечислять нечего. (Флоу «задать пароль SSO-аккаунту впервые» —
  отдельная фича, в этот объём не входит, честно объявить out of scope.)
- register.ts:107 (`insert into accounts (email, password_hash)`) не меняется — парольная
  регистрация всегда передаёт хеш.

Альтернатива «оставить NOT NULL и писать заглушечный хеш» отвергнута: это данные-ложь, и она
молча ломает compare-and-swap смены пароля (password-change.ts:189 сравнивает хеш с хешем).

## 3. СЕССИИ

**Ничего менять не нужно — в этом и сила текущей конструкции.** createSession
(apps/web/src/lib/session.ts:160) принимает `(client, accountId)` и не знает, откуда пришла
аутентификация. Коллбэк SSO внутри своей withService-транзакции вызывает
`createSession(client, accountId)` импортом — страж «insert into sessions встречается РОВНО в
одном файле» (tests/login.test.ts:299) остаётся зелёным, потому что проверяет он именно текст
`insert into sessions` по исходникам, а не число вызовов. Cookie ставится тем же
`sessionCookieOptions()`; заметьте — `sameSite: 'lax'` (session.ts:143) уже выбран с оглядкой на
возврат с внешнего провайдера (комментарий про платёжку), редирект-коллбэк SSO он тоже переживёт.
Стоимость: 0 строк в session.ts, ~5 строк вызова в коллбэке.

пользователя, строго говоря, нечего, кроме слага.

  (`/{slug}` — витрина), local-part утёк бы в URL.

  трогаются.

Вариант Б (экран «назовите проект» после входа) дороже по всем осям: +1 страница (+1 строка в

## 5. МАРШРУТЫ И ПОРЯДОК ОПЕРАЦИЙ

Два маршрута на провайдера, через динамический сегмент — итого два файла:

**`app/api/auth/sso/[provider]/start/route.ts` (GET, ~60 строк).**
provider не из allowlist (литерал в коде: `['yandex','sber']`) → 404. Сгенерировать
state (32 байта) + PKCE verifier → HMAC-подписанная httpOnly cookie (TTL 10 мин) → 302 на
authorize-URL провайдера. **БД не трогается вовсе** — транзакций нет, лимитер не обязателен
(маршрут ничего не стоит: ни CPU, ни соединения; редирект-спам режется IP-лимитом коллбэка).

**`app/api/auth/sso/[provider]/callback/route.ts` (GET, ~120 строк). Порядок — это защита:**
1. Сверить state из query со state из cookie (timingSafeEqual уже есть в session.ts), проверить
   срок. Мимо → 302 на /login?error=sso. Cookie state погасить в любом исходе (одноразовость).
2. **ВНЕШНИЕ ВЫЗОВЫ — СТРОГО ДО withService**: POST token-exchange (code+verifier), GET userinfo.
   Это второй внешний вызов проекта после ЮKassa (payment.ts:97) — и у payment.ts fetch БЕЗ
   таймаута; НЕ копировать этот пробел: `AbortSignal.timeout(5000)` обязателен, иначе время,
   которым управляет ЧУЖОЙ сервер, становится временем удержания... нет, соединение не удерживается
   (мы ещё вне транзакции) — становится временем висящего запроса и сокета. Отказ/таймаут
   провайдера = исключение → redirect с ошибкой, никакой транзакции ещё не открыто, откатывать
   нечего (security-operation-order: сетевой вызов ВНЕ транзакции — здесь выполняется по
   построению маршрута, и это надо закрепить стражем, см. п. 6).
3. `withService`-транзакция (короткая, без argon2, без сети): лимит по IP (свой scope, ~30/час) →
   `select … from account_identities where provider=$1 and provider_user_id=$2` → ветки:
   найдено → createSession; не найдено, но email (нормализованный ЕДИНСТВЕННЫМ normalizeEmail)
   совпал с accounts → insert identity (ON CONFLICT DO NOTHING + re-select — гонка двойного
   коллбэка) + createSession + audit_log 'identity_linked'; никого →
   createAccountWithProject(passwordHash: null) + insert identity + createSession + audit_log.
4. 302 на /dashboard/{slug}, cookie сессии в ответе.

Лимитер именно в шаге 3, ДО записей: невалидный state до лимитера не доходит и не сжигает бюджет
честных (порядок «лимит до валидации» здесь инвертирован осознанно — state-проверка бесплатна и
отсекает мусор без БД; в счётчик же должен попадать только запрос, дошедший до данных).

## 8. ЧТО ПОЙДЁТ НЕ ТАК — таблица дельты разделяемых ресурсов ЗАРАНЕЕ

| Ресурс | Дельта и где дефект будет жить |
|---|---|
| Пул соединений | ГЛАВНЫЙ риск фичи. Соблазн «уже открыл транзакцию — заодно схожу за токеном» кладёт внешнюю задержку (сотни мс — секунды, управляет ЧУЖОЙ сервер) внутрь удержания соединения; 10 медленных ответов провайдера = пул исчерпан = лежат дашборд, витрина, виджет, приём отзывов. Ровно класс NFR-009.9, только вместо клиента-дописывателя — провайдер. Лекарство: порядок п. 5 + страж «fetch не внутри withService» + конкурентный тест |
| Внешние вызовы | Было 1 место (ЮKassa, payment.ts:97 — БЕЗ таймаута), станет 3 (token, userinfo). Таймаут обязателен; недоступность = исключение, не значение (security-operation-order). Квота провайдера на token-запросы — общая на приложение: флуд коллбэками с мусорными code сжигает её всем; IP-лимит коллбэка это и ограничивает |
| CPU / event loop | В ПЛЮС: SSO-вход не считает argon2 вообще — дешевле парольного. Новых тяжёлых операций нет. HMAC state — микросекунды. Не задет |
| Память вход/выход | `res.json()` от провайдера без предела — теоретически чужой сервер (или MITM без строгого TLS) может прислать гигабайт. Ограничить чтение ответа (тот же принцип, что readBodyAtMost). Иначе — не задет |
| Блокировки строк | Двойной коллбэк (double-click, повтор редиректа) → два insert одной identity: unique(provider,provider_user_id) + ON CONFLICT DO NOTHING, второй перечитывает. Без ON CONFLICT второй получает 500 при живом первом. insert into sessions берёт FOR KEY SHARE на строке accounts (урок password-change.ts:150) — SSO-транзакция коротка, конфликтов не добавляет |
| Счётчики rate_limit | Свои scope-константы (sso_ip), таблица общая rate_limit_events — рост объёма пренебрежим. НЕ переиспользовать литералы login_* (страж login.test.ts:389 упадёт — и правильно) |
| Advisory-локи | Не задет: новый путь локов не берёт. Пространства 90_009/90_010 не трогаются |
| Файловые дескрипторы/сокеты | +2 исходящих соединения на вход через SSO; с таймаутом — не задет |
| **Небезопасный по построению участок (не ресурс, но главный кандидат в дефекты)** | Связывание по email = захват аккаунта, если провайдер отдаёт НЕПОДТВЕРЖДЁННЫЙ email: атакующий заводит у провайдера учётку с чужим email и входит в чужой аккаунт проекта. Yandex ID отдаёт свой же подтверждённый ящик — ок; для Sber ID проверить признак верификации ДО включения авто-связывания, иначе fail-closed: не связывать, просить парольный вход (правило «неопознанное → самое строгое») |

## НЕ ПРОВЕРЕНО

- Тесты не запускались; все «страж останется зелёным» — по чтению кода стражей, не по прогону.
- Конкретика API Yandex ID / Sber ID (эндпоинты, поля userinfo, признак верификации email,
  требования Sber к клиенту/сертификации) — не смотрел, это зона sso-providers; оценка блока (б)
  предполагает стандартный OAuth 2.0 + PKCE без mTLS.
- Поведение @node-rs/argon2 verify на NULL-хеше (утверждение «бросит» — по типам, не по прогону).
- `sameSite: 'lax'` и цепочка 302-редиректов провайдера — рассуждение, не проверка в браузере;
  как раз класс дефектов «curl не видит» из deployment-seams.
- Caddy/compose не смотрел: redirect_uri — внешний адрес, завязан на BASE_URL; история проекта
  с BASE_URL требует включить redirect_uri в check-cjm-прогон на развёрнутом стенде.
- Полные тексты register.test.ts / password-change-route.test.ts читал выборочно (grep), не целиком.
