# Исследование: Sber ID и Yandex ID как способ входа (по первоисточникам)

**ВЕРДИКТ ОДНОЙ СТРОКОЙ: Yandex ID существенно проще — самостоятельная регистрация приложения без договора и модерации, стандартный OAuth 2.0 + PKCE, готовый провайдер в Auth.js/NextAuth; Sber ID требует договор-оферту через ЭДО на портале для бизнеса, сертификат, обязательные аналитические события в проде и access token со сроком жизни 60 секунд.**

Дата исследования: 2026-08-30. Все утверждения ниже помечены источником; что не удалось
подтвердить первоисточником — вынесено в раздел «НЕ УСТАНОВЛЕНО».

---

## YANDEX ID

### 1. Кто может подключиться

- Регистрация приложения — самостоятельная, на https://oauth.yandex.ru/ из любого аккаунта
  Яндекса. Официальная документация (https://yandex.ru/dev/id/doc/ru/register-client)
  **не содержит** требований юрлица, договора, модерации или проверки домена.
- Требование по существу одно: «предоставьте полную информацию о приложении, чтобы
  пользователи знали, кому дают доступ к данным». Документация рекомендует (не требует)
  подтвердить аккаунт разработчика на Госуслугах.
- Два типа приложений (выбирается при создании, потом НЕ меняется): «авторизация
  пользователей» (до 3 групп прав) и «доступ к API» (без права `login`). Нам нужен первый.
- Сроки: подключение мгновенное (self-service). Модерации по официальным документам нет.

### 2. Деньги

- В документации OAuth/Яндекс ID цена не упоминается вообще — ни тарифов, ни лимитов.
  Прямого слова «бесплатно» в документации не найдено (см. «НЕ УСТАНОВЛЕНО»), но
  процесс не содержит ни одного платёжного шага.

### 3. Протокол

- **OAuth 2.0** (документация прямо это называет; OIDC/ id_token НЕ упоминается —
  данные пользователя берутся отдельным запросом, не из id_token).
- Эндпоинты (https://yandex.ru/dev/id/doc/ru/codes/code-url):
  - authorize: `https://oauth.yandex.ru/authorize` (`response_type=code`, `client_id`,
    `redirect_uri`, `scope`, `state` до 1024 симв., `force_confirm`, `login_hint`)
  - token: `POST https://oauth.yandex.ru/token` (`grant_type=authorization_code`;
    client_secret в теле или Basic-auth)
  - **PKCE поддерживается**: `code_challenge` + `code_challenge_method=S256` (рекомендован).
  - Код живёт 10 минут. Ответ: `access_token`, `expires_in`, `refresh_token`, `scope`.
- user-info: `GET https://login.yandex.ru/info`, заголовок `Authorization: OAuth <token>`
  (https://yandex.ru/dev/id/doc/ru/user-information).
- **Стабильный идентификатор — два кандидата, оба в каждом ответе:**
  - `id` — глобальный уникальный ID пользователя в Яндексе;
  - `psuid` — pairwise-идентификатор, формируется Яндексом из пары `client_id` + `user_id`
    (стабилен для нашего приложения, не переносим между приложениями).
  Как ключ учётной записи годится любой; `id` переживёт смену client_id, `psuid` — нет.
  Рекомендация: хранить оба, ключ — `id`.

### 4. Готовая библиотека

- **Auth.js (NextAuth) имеет встроенный провайдер Yandex** —
  https://authjs.dev/reference/core/providers/yandex. Конфигурация: clientId + clientSecret,
  callback `https://<домен>/api/auth/callback/yandex`. Профиль маппится из login.yandex.ru/info
  (id, psuid, default_email, first_name/last_name и т.д.).
- Поскольку в проекте СВОЯ auth (argon2id, без NextAuth), реалистичный путь — ручной
  OAuth-клиент: это 3 HTTP-вызова (redirect на authorize, POST token, GET info) +
  state/PKCE. Оценка: **~150–250 строк** включая обработку ошибок и тесты формата ответа.
  Тянуть NextAuth ради одного провайдера не обязательно.

### 5. Что отдаёт про пользователя

- Всегда: `login`, `id`, `client_id`, `psuid`.
- По scope: `login:email` → `default_email` + массив `emails`; `login:info` → ФИО, пол,
  дата рождения; `login:avatar` → аватар; телефон → объект `default_phone` (id, number).
- Согласие: пользователь видит экран согласия с перечнем запрошенных прав; email приходит
  только при выданном scope. **Телефон НЕ обязателен** — отдельный scope, можно не просить.
- Для нашей задачи достаточно `login:email` (+ `login:info` для имени в профиле).

### 6. Юридическое закрытие (пп. 4 п. 10 ст. 8 149-ФЗ)

- Фактура: Яндекс ID — информационная система ООО «Яндекс» (российское юрлицо),
  обеспечивающая авторизацию. Формально подпадает под текст подпункта 4.
- **Прямых заявлений «Яндекс ID соответствует п. 10 ст. 8 149-ФЗ» в официальной
  документации разработчика НЕ найдено.** Соответствие называют сторонние юридические
  обзоры (Гарант.ру, it-lex.ru, workspace.ru — Яндекс ID в списках допустимых способов
  наряду с Госуслугами, VK ID, Сбер ID). Это консенсус рынка, не официальная гарантия.
- Важно из тех же обзоров: с 07.07.2026 действуют штрафы (до 700 тыс. руб.) за
  авторизацию через иностранные сервисы — мотивация закрыть вопрос выросла.

### 7. Подводные камни

- Тип приложения нельзя сменить после регистрации — сразу выбирать «авторизация пользователей».
- redirect_uri должен точно совпадать с зарегистрированным.
- «Мгновенная авторизация» (виджет/кнопка) — это JS-скрипт Яндекса на странице; для нас
  необязательна, обычный redirect-flow документирован и работает без их JS.
- У кнопки есть конструктор и фирменный стиль; жёсткость требований к брендбуку в
  документации не сформулирована как обязательство (в отличие от Сбера).
- Отзыв согласия пользователем: поведение (умирает ли токен) в прочитанных разделах не
  описано — см. «НЕ УСТАНОВЛЕНО». Logout-эндпоинт не обязателен, flow его не требует.

## SBER ID

### 1. Кто может подключиться

- Порядок (https://developers.sber.ru/docs/ru/sberid/service/overview): регистрация на
  портале для бизнеса https://id.sber.ru/profile/b2b → **подписание оферты через ЭДО** →
  получение Client ID, Client Secret **и сертификата** → интеграция.
- Про юрлицо/ИП: сторонние и полуофициальные источники (sberbusiness.live, страница
  sberbank.ru/ru/legal/services/sber-id — недоступна извне, см. камень про сертификаты)
  говорят «юрлица и ИП». **В открытой документации разработчика явного перечня
  допустимых форм НЕТ** — вынесено в «НЕ УСТАНОВЛЕНО». Физлицо без статуса — признаков
  возможности не найдено (портал b2b + оферта через ЭДО фактически предполагают бизнес-субъект).
- Сроки подключения официально не публикуются.

### 2. Деньги

- Официальной публичной цены в документации нет. Сторонние источники (webasyst,
  пересказ маркетинга Сбера) утверждают «бесплатно, Сбер несёт расходы за авторизации».
  **Первоисточником не подтверждено** — в «НЕ УСТАНОВЛЕНО».

### 3. Протокол

- **OIDC** (authorization code + PKCE, id_token присутствует).
- Эндпоинты:
  - authorize (web): `https://online.sberbank.ru/CSAFront/oidc/authorize.do`; для
    «Cloud»-схемы и сертификатов Минцифры — `https://id.sber.ru/CSAFront/oidc/authorize.do`
    (https://developers.sber.ru/docs/ru/sberid/service/reqdescription/authcodereq/web/overview).
    Параметры: response_type=code, client_type=PRIVATE, client_id, scope, state, nonce,
    redirect_uri, code_challenge(+method) — PKCE поддержан и рекомендован.
  - token: прод `https://oauth.sber.ru/ru/prod/tokens/v2/oidc`, тест
    `https://oauth-ift.sber.ru/ru/prod/tokens/v2/oidc`
    (https://developers.sber.ru/docs/ru/sberid/service/reqdescription/accessidtokens/overview).
    Обязателен заголовок `RqUID` (32 hex-символа) в каждом запросе. Таймаут ответа 10 с.
    **Требуется сертификат, полученный при регистрации приложения** (в док-е не
    расшифровано, mTLS ли это — см. «НЕ УСТАНОВЛЕНО»).
  - userinfo: прод `https://oauth.sber.ru/ru/prod/sberbankid/v2.1/userinfo`, тест
    `https://oauth-ift.sber.ru/ru/prod/sberbankid/v2.1/userinfo`; заголовки
    `Authorization: Bearer <token>` + `x-introspect-rquid` (32 симв.).
- Времена жизни: **access_token — 60 секунд** (использовать немедленно), refresh_token —
  30 дней (только при scope `offline_access`).
- **Стабильный идентификатор: `sub` в id_token — «основной неизменяемый идентификатор
  пользователя», до 96 символов.** Плюс `sub_alt` — альтернативный идентификатор для
  обработки слияний/дедупликации аккаунтов. Хранить оба, ключ — `sub`, `sub_alt` — для
  миграций при склейке аккаунтов Сбера.

### 4. Готовая библиотека

- Официальный **@sberid/js-sdk** (npm, v3.0.x; github.com/SberID/js-sdk) — но это
  **фронтовый** SDK: кнопка по гайдам + получение AuthCode. Обмен кода на токены и
  userinfo — писать самим на сервере.
- Провайдера в NextAuth/Auth.js **нет**. Community-модуль kmorpex/sberbank-id для Node
  существует, неофициальный и старый — в проде полагаться нельзя.
- Оценка ручной серверной части: **~250–400 строк** (RqUID, сертификат, обработка
  60-секундного токена, обязательные аналитические события — см. п. 7).

### 5. Что отдаёт про пользователя

- Пакеты scope (userinfo): «Лайт» — `sub`, email, phone_number; «Стандартный» — + ФИО,
  дата рождения, пол; «Профессиональный» — + паспорт, ИНН, СНИЛС, адреса, работа
  (нам не нужен и его ещё надо согласовать).
- Телефон в Сбер ID — базовый идентификатор пользователя (вход по номеру), в «Лайт»
  присутствует. Email — «если пользователь его указывал», т.е. **email НЕ гарантирован**.
  Это важно: наша модель учёток строится на email — потребуется fallback (просить email
  при первом входе, ключ — `sub`, не email).
- Согласие: пользователь управляет передачей данных через услугу «Удобный доступ» в
  СберБанк Онлайн и может её отключить (= отозвать согласие). Запрос неразрешённого
  партнёру scope → ошибка `invalid_scope` (scope согласуются при подключении).

### 6. Юридическое закрытие (пп. 4 п. 10 ст. 8 149-ФЗ)

- Фактура: Сбер ID — система ПАО «Сбербанк» (российское юрлицо). Формально подпадает
  под текст подпункта 4.
- **Прямых заявлений о 149-ФЗ в документации разработчика НЕ найдено** (проверены
  overview, service/overview, help-раздел). Как и с Яндексом, соответствие утверждают
  сторонние юридические обзоры, где Сбер ID стоит в списке допустимых способов.

### 7. Подводные камни

- **Договор-оферта через ЭДО** — нужен работающий ЭДО у ИП/юрлица; сама заявка и
  модерация — процесс с людьми, не self-service.
- **Сертификаты Минцифры**: серверы Сбера переходят на TLS-сертификаты НУЦ Минцифры
  (https://developers.sber.ru/docs/ru/sberid/faq/a3-how-use-cert-mintsifry). Два следствия:
  (а) браузер пользователя без российского корневого сертификата может не открыть
  страницу авторизации (SDK 3.1.1+ отрабатывает это автоматически); (б) НАШ сервер при
  запросах к oauth.sber.ru должен доверять НУЦ Минцифры — стандартный Node/Debian trust
  store его НЕ содержит (мы сами при исследовании получили «self signed certificate in
  certificate chain» на sberbank.ru — это оно и есть).
- **access_token живёт 60 секунд** — архитектурно: обменял код → сразу userinfo, ничего
  не откладывать.
- **Обязательные аналитические события в prod** (Шаг 4 интеграции) — Сбер требует слать
  события в свой центр аналитики; это дополнительный код и зависимость.
- **iFrame запрещён**; кнопка — строго по гайдбуку («Требования к дизайну» — отдельный
  обязательный раздел документации).
- `RqUID`/`x-introspect-rquid` в каждом запросе; redirect_uri — посимвольное совпадение.
- Отзыв согласия пользователем («Удобный доступ» выкл.) — вход перестаёт работать;
  поведение для уже выданных токенов в прочитанных разделах не описано.

## СРАВНЕНИЕ: что дешевле подключить

| Критерий | Yandex ID | Sber ID |
|---|---|---|
| Оргбарьер | Нет: self-service из любого аккаунта | Портал b2b + оферта через ЭДО, выпуск сертификата |
| Кто может | Ограничений в доках нет (физлицо ок) | Юрлицо/ИП (по вторичным источникам; официально не опубликовано) |
| Цена | Платёжных шагов нет (прямого «бесплатно» в доках нет) | «Бесплатно» только по вторичным источникам |
| Протокол | OAuth 2.0 + PKCE, 3 простых эндпоинта | OIDC + PKCE, RqUID, сертификат, access token 60 с |
| Библиотека | Встроенный провайдер Auth.js; руками ~150–250 строк | Только фронтовый JS SDK; сервер руками ~250–400 строк |
| Ключ учётки | `id` (глобальный) / `psuid` (pairwise) | `sub` (+ `sub_alt` для склеек) |
| Email | Гарантирован при scope login:email | НЕ гарантирован («если указывал») |
| Доп. обязательства | Минимальные | Аналитические события в prod, гайдбук кнопки, запрет iframe |
| Серверная инфраструктура | Ничего особенного | Trust store с НУЦ Минцифры на нашем сервере |
| Время до работающего входа | Часы (регистрация мгновенная) | Недели (договор + модерация; официальных сроков нет) |
| Юр. закрытие 149-ФЗ | Российская ИС; прямых заявлений в доках нет | Российская ИС; прямых заявлений в доках нет |

**Рекомендация:** начать с Yandex ID (закрывает юридический вопрос тем же способом, что
и Sber ID, при на порядок меньшей стоимости подключения). Sber ID — вторым провайдером,
если появится бизнес-причина (аудитория СберБанк Онлайн), и только после заключения оферты.

## НЕ УСТАНОВЛЕНО (честный список пробелов)

1. **Sber: официальный перечень допустимых форм партнёра** (юрлицо/ИП/самозанятый) —
   в открытой документации не найден; «юрлица и ИП» — вторичные источники. Страница
   sberbank.ru/ru/legal/services/sber-id не открылась из-за цепочки сертификатов Минцифры.
2. **Sber: официальное «бесплатно» и сроки подключения** — не опубликованы; «бесплатно,
   Сбер платит за авторизации» — только пересказы (webasyst, sbersova).
3. **Sber: природа «сертификата», выдаваемого при регистрации** — mTLS-клиентский или
   иное; документация говорит «обязателен», но не расшифровывает механизм.
4. **Yandex: прямое слово «бесплатно»** в документации — не найдено (платных шагов тоже нет).
5. **Оба: прямые заявления провайдера о соответствии п. 10 ст. 8 149-ФЗ** — в
   документации обоих НЕ найдены; соответствие утверждают только сторонние юробзоры
   (Гарант.ру и др.). Вывод «годится по подпункту 4» остаётся правовой оценкой, а не
   гарантией провайдера.
6. **Оба: поведение выданных токенов при отзыве согласия пользователем** — не описано
   в прочитанных разделах.
7. **Yandex: наличие/обязательность ревью приложения при запросе scope телефона** — не
   проверялось (телефон нам не нужен).
