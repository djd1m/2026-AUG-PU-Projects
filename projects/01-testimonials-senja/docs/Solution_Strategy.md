# Solution Strategy — Proofwall

> SPARC Phase: **Specification** (стратегическая надстройка над PRD/Specification).
> Источники: `PRD.md`, `discovery/CJM_Variants.md`, `discovery/Product_Discovery_Brief.md`.

## 1. Зачем именно этот MVP-скоуп

Неделя — константа, не переменная. Скоуп выбирался не «что круто», а «что доводит до метрики
недели» — числа установленных виджетов на внешних доменах (PRD §2.4).

Цепочка обязательности: чтобы посчитать виджеты на внешних доменах, нужен (1) виджет →
(2) чтобы виджет было чем наполнить, нужна модерация одобренных отзывов → (3) чтобы отзывы
появились, нужна форма сбора → (4) чтобы форма и виджет были адресуемы, нужен проект со слагом.
Это и есть FR-001…FR-006 из PRD §4.1 — минимальный путь до измеримой метрики, ни одним пунктом
короче.

Всё, что не лежит на этой цепочке, исключено явно (PRD §1.2 «Явно НЕ входит»): импорт с 30+
платформ, AI-редактирование, команды/роли/seats, Zapier и публичный API. Это не «не успели» —
это «не на критическом пути метрики недели».

## 2. Почему основной growth loop — именно Badge Loop

`research/GROWTH-MECHANICS-REQUIREMENTS.md` §2 требует ровно один основной loop на проект и
прямо называет для Senja-клона **Badge loop** (строка 60 таблицы): «Wall of Love на сайте
клиента → "Powered by" видят все его посетители». Это единственный из рассмотренных в §2
loop'ов, помеченный как рабочий без оговорок для нашего продукта — в отличие, например, от
проекта №02 (не viral loop вовсе) или №07 (network effect, но требует критической массы).

Badge loop подходит по трём независимым причинам:

1. **Не требует нашего трафика.** Каждый установленный виджет — это чужой сайт, который
   бесплатно показывает наш бренд своим посетителям (PRD §2.1).
2. **Совпадает с метрикой недели по конструкции.** Одна установка виджета = одновременно
   единица роста базы (badge impression) и единица метрики недели (widget_installed). Не нужно
   доказывать связь между активностью и метрикой — она встроена.
2. **Не требует нового бэкенда.** Badge — это статичный элемент в уже необходимом виджете
   (FR-006), а не отдельная фича.

Вторичная тактика без нового кода — шеринг отзыва автором в соцсеть сразу после отправки
(PRD §4.2). Правило «один loop за неделю, иначе ни один не доведён» (PRD §4.2,
GROWTH-MECHANICS §2) соблюдено: Badge — единственный, за который отвечаем метрикой.

## 3. Разбор трёх вариантов CJM и обоснование решения

`discovery/CJM_Variants.md` предлагает три варианта, различающихся по Aha Moment, Entry Hook и
времени монетизации.

| | A · Speed-to-Proof | B · Proof-of-Human | C · Proof Engine для AI |
|---|---|---|---|
| Aha Moment | «Нашли 47 ваших отзывов по всему интернету» | Verified-бейдж + FTC audit trail | AI-visibility дашборд цитирований |
| Ключевая зависимость | Авто-скан 30+ платформ | C2PA / Content Credentials | Измеримость AI-цитирований (шаткая) |
| Главный риск (по CJM_Variants) | Ценовая война, паритет фич | Долгий education cycle | Атрибуция AI-цитирований технически шаткая |

**Почему не B.** Aha Moment варианта B требует C2PA-инфраструктуры и compliance-отчётности —
рынок для этого, по собственной оценке CJM_Variants, «ещё не осознал боль», а цикл продажи
длинный и дорогой. Для недельного MVP это несовместимо с constraint времени.

**Почему не C.** Aha Moment варианта C зависит от измеримости AI-цитирований, которую сам
CJM_Variants называет «технически шаткой». Строить недельный MVP на метрике с непроверенной
измеримостью — противоречит принципу «метрика недели определена и считается» (PRD §2.4).

**Почему A — ближайший, но не буквально.** Вариант A ближе всего к MVP-скоупу по Entry Hook
(functional job S1 — «отзывы разбросаны по 8 местам», PRD §3.1) и по Invite/Referral
(«"Powered by" в виджете → классический вирусный контур» — это буквально Badge loop). Но его
Aha Moment — «мы нашли 47 ваших отзывов по всему интернету» — целиком построен на авто-скане
30+ платформ, который PRD §1.2 явно исключает из scope недели.

### Что было потеряно и что приобретено (без приукрашивания)

Слепое взятие варианта A означало бы обещать продукт, который не может выполнить собственный
Aha Moment — форма без наполнения не «находит» ничего сама. PRD §2.3 разрешает это переопределением
момента ценности на **«владелец увидел ПЕРВУЮ живую стену отзывов на своём домене»**.

| | Вариант A из discovery | Принятое решение |
|---|---|---|
| Что даёт ценность | Импорт (магия обнаружения чужими руками) | Скорость от нуля до публичного proof |
| Зависимость | 30+ интеграций | Ноль интеграций |
| Кто добывает первый отзыв | Продукт (сам находит) | Владелец (сам просит) |

**Потеряно:** активация слабее оригинала — первый отзыв владелец обязан добыть сам, магии
«уже готово» нет. PRD §7 (R2) фиксирует это как принятый риск, а не как случайный пробел, и
назначает митигацию — измерение time-to-first-widget как прокси активации.

**Приобретено:** growth loop не зависит от способа наполнения стены. Метрика недели —
установленные виджеты — считается для любой стены, наполненной хоть вручную, хоть импортом.
Это делает Badge loop устойчивым к последующему добавлению импорта (см. §5) без переделки.

**Обоснование выбора (PRD §2.3):** основной growth loop запускается установкой виджета, а не
способом наполнения стены. Импорт улучшает активацию, но не растит базу доменов с виджетом —
для метрики недели он не на критическом пути.

## 4. Позиционирование в red ocean

`discovery/Product_Discovery_Brief.md` честно называет категорию «собери и покажи отзыв»
**red ocean** с дном цены **$9/мес** (Famewall). Прямая ценовая конкуренция с клоном-в-лоб
проигрышна по построению: у нас нет экономии на масштабе первой недели.

Решение — не конкурировать ценой, а конкурировать **скоростью до первого виджета**:

- Позиционирование недели: «от регистрации до живой стены на своём домене — за один вечер»
  (PRD §3.1, персона: «Стена отзывов на лендинге за вечер»).
- Метрика активации — time-to-first-widget (PRD §2.4) — прямое измерение этого обещания,
  а не абстрактный UX.
- Единственный источник ценового давления, который мы контролируем на неделе — обязательность
  badge на free-тарифе (FR-GROWTH-003): бесплатно, но с нашим брендом на каждом показе. Это
  превращает бесплатных пользователей в канал приобретения, а не только в затраты на
  инфраструктуру.

Долгосрочная дифференциация (Blue Ocean гипотеза из discovery — верифицируемость через C2PA,
машиночитаемый слой для AI-поиска) сознательно не входит в неделю — она требует варианта B/C
CJM, которые сами по себе исключены по §3. Задел на неё сохраняется — badge и schema.org/Review
(FR-GROWTH-005) уже создают базовый машиночитаемый слой, на который можно нарастить AI-visibility
слой позже, не переделывая архитектуру.

## 5. Что отложено и в каком порядке

PRD §6.2 фиксирует три направления следующей итерации. Порядок обоснован зависимостью от того,
что уже наработано на неделе, а не произвольным списком «хотелок»:

1. **Мини-импорт из одного источника (CSV).** Первым — потому что напрямую возвращает часть
   потерянного в §3 Aha Moment варианта A, при этом не требует 30+ интеграций сразу. Наименьший
   шаг с наибольшим возвратом активации.
2. **C2PA verified capture (вариант B CJM).** Вторым — открывает сегмент S2/S3 (B2B с юристами,
   health/fintech), но требует зрелости рынка, которой по оценке `CJM_Variants.md` пока нет.
   Есть смысл держать в очереди, но не форсировать.
3. **AI-visibility трекер (вариант C CJM).** Третьим — потому что его метрика (атрибуция
   AI-цитирований) сама по себе технически шаткая (см. §3 выше). Прежде чем строить на ней
   продукт, нужно сначала доказать, что метрика вообще измерима — это отдельная исследовательская
   задача, не инженерная.

Отдельно: полноценные команды/роли/seats и Zapier/API (PRD §1.2) отложены не по значимости, а
потому что не влияют на growth loop недели — они возвращаются в очередь только после того, как
Badge loop подтверждён метрикой.
