## 1. Стратегия тестирования по уровням

| Уровень | Что покрывает | Инструмент (класс) |
|---|---|---|
| Unit | Чистая логика: `resolveAttribution`, `recomputeContentThreshold`, переходы состояний в `ALLOWED_TRANSITIONS`, валидация полей формы, расчёт комиссии | Юнит-фреймворк JS/TS с моками БД |
| Integration | Обработчики API с реальной тестовой БД: `submitTestimonial`, `moderateTestimonial`, `apiWidgetConfig`, `onPaymentWebhook` (включая идемпотентность и self-referral), rate limit на реальном сторе | Тестовая Postgres-схема (Supabase local/test project) |
| E2E | Полный путь пользователя: форма → модерация → публичная стена → виджет на внешней странице; путь регистрация → атрибуция → оплата → комиссия | Браузерный E2E-раннер |

**Принцип распределения:** всё, что выражается как чистая функция от входа к выходу (переходы
состояний, приоритет промокода, пороги), тестируется юнитом — это самый дешёвый и надёжный
слой (ladder-правило проекта: детерминированное — на самый сильный доступный слой). Всё, что
зависит от реальной БД/вебхука/сети — интеграционно. E2E — только для пользовательских путей,
которые нельзя валидировать иначе (SSR-рендер, поведение виджета в чужом DOM).

### 1.1 Тестирование виджета на чужой странице (нетривиально)

Проблема: виджет исполняется в DOM, которым не управляет тестовый раннер, и должен переживать
конфликтующие стили/скрипты хоста.

**Подход:**
1. Собрать тестовую "хост-страницу" — HTML-фикстура с намеренно агрессивными глобальными
   стилями (`* { all: unset !important }`, конфликтующие классы `.badge`, `.container`) и
   сторонним `<script>`, схожим по паттерну с популярными сайт-билдерами.
2. Встроить реальный собранный бандл виджета через `<script src=".../widget.js" data-slug=...>`
   в эту фикстуру, поднятую на отдельном тестовом origin (не origin приложения) — это
   обязательное условие: без второго origin `currentDomain() == OUR_APP_DOMAIN` и тест не
   проверит §4/§5 по-настоящему.
3. Через браузерный раннер проверить:
   - виджет рендерится и содержимое видимо, несмотря на `* { all: unset }` хоста (изоляция
     Shadow DOM/scoped CSS сработала);
   - глобальные стили хоста не "утекли" внутрь виджета и стили виджета не "утекли" наружу;
   - размер шрифта/цвет элементов хоста не изменился после загрузки виджета (нет побочных
     эффектов на страницу-контейнер);
   - тег `<script>` хоста продолжает работать (виджет не перехватывает глобальные обработчики).
4. Для badge-integrity (§5.2 Pseudocode) — на этой же фикстуре программно применить
   `display:none` к найденному узлу badge и проверить восстановление видимости в течение
   заданного числа `setInterval`-тиков (см. §4 ниже — отдельный раздел про growth-тестируемость).

**Почему не просто unit-тест рендер-функции:** конфликт стилей — эмерджентное свойство
взаимодействия двух независимо написанных DOM-деревьев; юнит-тест функции `renderTestimonials`
в изоляции не может обнаружить, что классы виджета совпали по имени с классами хоста.

## 2. Граничные случаи по FR

| FR | Граничный случай | Ожидаемое поведение |
|---|---|---|
| FR-002 | Текст ровно 10 / ровно 2000 символов | Принимается (границы включительно) |
| FR-002 | Текст 9 или 2001 символ | 400 с указанием поля |
| FR-002 | 6-я отправка с того же IP в течение часа | 429 без деталей о текущем счётчике |
| FR-002 | Проект деактивирован/не существует | 404, без различия для внешнего наблюдателя |
| FR-003 | Видео ровно 120 сек / ровно 100 MB | Принимается (границы включительно) |
| FR-003 | Видео 121 сек или формат `avi` | Явная ошибка валидации с указанием причины |
| FR-003 | Camera permission denied | Fallback на загрузку файла, понятное сообщение |
| FR-003 | Claude API недоступен во время транскрипции | `transcript_status: failed`, отзыв остаётся модерируемым, транскрипт не блокирует публикацию |
| FR-003 | Транскрипция и текст расходятся по содержанию | Текст остаётся исходным; транскрипт — отдельное поле, помечено как машинное |
| FR-004 | Попытка перехода `pending → hidden` напрямую | 400 — переход не в `ALLOWED_TRANSITIONS[pending]` |
| FR-004 | Модератор чужого проекта пытается изменить отзыв | 403 + запись в audit log с причиной `cross_project` |
| FR-004 | Повторный переход в тот же статус | Не определено в Specification — [GAP: считать ли идемпотентным no-op или 400 "нет изменений"] |
| FR-005 | 0 одобренных отзывов | Осмысленная пустая страница, не 404 |
| FR-006 | `data-slug` отсутствует в теге `<script>` | Тихий no-op с предупреждением в консоль, страница хоста не ломается |
| FR-006 | Виджет вызван дважды на одной странице (двойной тег) | [GAP: не определено — нужна защита от двойной инициализации/двойного invite_shown] |
| FR-GROWTH-001 | Два посетителя грузят внешнюю страницу одновременно, домен новый | Ровно одна запись `widget_installed`, ровно один `invite_shown` (гонка разрешена на уровне БД) |
| FR-GROWTH-002 | Cookie и промокод указывают на разных партнёров | Побеждает промокод |
| FR-GROWTH-002 | Тот же `event.id` вебхука приходит дважды | Комиссия начислена один раз |
| FR-GROWTH-002 | Оплата спустя 31 день после регистрации | Атрибуция `expired`, комиссия не начисляется |
| FR-GROWTH-003 | Апгрейд на `paid` посреди активной сессии виджета | При следующем рендере (не текущем) badge исчезает — переустановка не требуется |
| FR-GROWTH-004 | Код отозван, затем приходит регистрация по нему | Атрибуция не создаётся; старые комиссии не пересчитываются |
| FR-GROWTH-005 | Ровно 3 отзыва и ровно 400 символов суммарно | Индексируется (пороги включительно) |
| FR-GROWTH-005 | 3 одобренных отзыва, но 4-й отзыв снят с публикации до 400 символов | noindex накладывается повторно |

## 3. Тестируемость growth-механик (отдельный раздел)

Эти четыре свойства невозможно правдоподобно проверить чтением кода — каждое требует теста,
который воспроизводит условие гонки, атаки или двустороннего перехода.

### 3.1 Badge нельзя снять с клиента

**Как проверить:** в браузерном тесте на фикстуре из §1.1 —
1. Дождаться первого рендера виджета с `badge_required: true` (мокнуть `apiWidgetConfig` или
   использовать тестовый проект на `free`).
2. Программно установить `badgeNode.style.display = 'none'` через `page.evaluate(...)`.
3. Дождаться следующего тика `MutationObserver`/`setInterval` (см. Pseudocode §5.2) и
   проверить, что `computedStyle(badgeNode).display != 'none'`.
4. Отдельным тестом — вызвать `apiWidgetConfig` напрямую с поддельным телом запроса, содержащим
   `hide_badge: true` / `tariff: 'paid'` в query, и убедиться, что ответ **игнорирует** эти поля
   и всё равно возвращает `badge_required: true` для проекта, реально находящегося на `free` в
   БД — это интеграционный тест, а не юнит, так как проверяет именно то, что сервер не доверяет
   клиентскому вводу.

### 3.2 `invite_shown` пишется ровно один раз

**Как проверить:** интеграционный тест с реальной (тестовой) БД —
1. Создать проект с ≥1 approved отзывом, без записи в `widget_install_events`.
2. Запустить `recordFirstRenderIfNeeded(slug, "external-domain.test")` **параллельно** из N
   конкурентных вызовов (например, `Promise.all` с N=10 одновременными вызовами обработчика).
3. Проверить: в таблице `widget_install_events` ровно одна строка для проекта; событие
   `invite_shown` эмитировано ровно один раз (мок аналитик-синка считает вызовы).
4. Отдельно — регресс-тест на edge-case: вызов из онбординга (`domain == OUR_APP_DOMAIN`) не
   создаёт запись и не эмитирует событие.

### 3.3 Приоритет промокода над cookie

**Как проверить:** юнит-тест `resolveAttribution` (чистая функция, без БД) —
- Таблица случаев: `{cookie: A, promo: B} → source=promo_code, partner=B`;
  `{cookie: A, promo: none} → source=cookie, partner=A`;
  `{cookie: none, promo: B} → source=promo_code, partner=B`;
  `{cookie: none, promo: none} → source=null`;
  `{cookie: A, promo: invalid_code} → source=null` (невалидный код не откатывается на cookie —
  явное намерение пользователя ввести код превалирует, даже если код не сработал).
- Дополнительно интеграционный тест: полный путь `onSignup` → `onPaymentWebhook`, где cookie и
  промокод расходятся, подтверждает, что комиссия начислена партнёру из промокода.

### 3.4 Noindex в обе стороны

**Как проверить:** интеграционный тест `recomputeContentThreshold` —
1. Стартовое состояние: 2 approved отзыва, `noindex=true`. Одобрить 3-й отзыв, суммарно ≥400
   символов → проверить `noindex=false` и запись `noindex_removed` в audit log.
2. Обратный переход: из состояния `noindex=false` при 3 отзывах — скрыть (`hidden`) один из
   approved так, чтобы осталось 2 → проверить `noindex=true` и запись `noindex_applied`.
3. Граница: ровно 400 символов (не 399) → индексируется; 399 → не индексируется.
4. E2E: реальный HTTP-запрос к `/w/<slug>` проверяет наличие/отсутствие
   `<meta name="robots" content="noindex">` в отданном HTML, а не только состояние в БД —
   тест должен ловить и баг "в БД `noindex=false`, но шаблон всё равно вставил тег".

## 4. Производительность виджета

| Метрика | Порог | Как измерять |
|---|---|---|
| Размер бандла | ≤ 30 KB gzip | Шаг CI: собрать `widget.js`, прогнать через `gzip -9`, сравнить размер с порогом; провал сборки при превышении (детерминированная проверка — размещается в CI, не в ревью человека) |
| Блокировка рендера хоста | Не блокирует | Тег вставляется с `async`; в E2E-тесте фикстуры (§1.1) замерить, что `DOMContentLoaded` хост-страницы не ждёт загрузки `widget.js` |
| p95 времени отрисовки | ≤ 300 мс | В браузерном тесте — время от `widgetBootstrap()` начала выполнения до `renderTestimonials` завершения, повторить N прогонов (N ≥ 30 — правило "не мерить на выборке < 30" из PRD применимо и к перфометрике), взять 95-й перцентиль |
| Сетевой запрос конфигурации | Таймаут 300 мс (Pseudocode §3) | Тест с искусственной задержкой ответа `apiWidgetConfig` проверяет, что виджет переходит в `renderEmptyPlaceholder` не позже таймаута, а не подвисает |

**Важно:** порог бандла — это CI-гейт (`wc`-подобная проверка размера файла), а не пункт в
чек-листе ревьюера — по ladder-правилу проекта детерминированная числовая проверка обязана
жить на самом дешёвом и надёжном слое.

## 5. Риски реализации и осознанный технический долг недели

| # | Риск / долг | Осознанное решение на неделю |
|---|---|---|
| T1 | `startBadgeIntegrityWatch` использует `setInterval` каждые 2 сек как подстраховку к `MutationObserver` — постоянный таймер на странице хоста | Принято ради надёжности anti-tamper за неделю; оптимизация (снятие интервала после N чистых проверок) — в следующей итерации |
| T2 | Транскрипция без retry при ошибке Claude API (Pseudocode §1.1) | Отзыв остаётся валидным без транскрипта; ручной ретрай через повторную постановку задачи — вне scope недели |
| T3 | Идемпотентность вебхука хранится в отдельной таблице `webhookEventStore` без TTL/очистки | За неделю рост таблицы некритичен; политика ретеншена — технический долг |
| T4 | Anti-fraud пороги (>50 регистраций/IP/10мин, >20 проектов/аккаунт/час) — фиксированные константы, не адаптивные | Соответствует Specification буквально; калибровка по реальному трафику — после недели |
| T5 | `apiWidgetConfig` не кеширует ответ (каждый рендер — сетевой запрос) | В рамках p95 ≤ 300 мс укладывается без кеша при MVP-нагрузке; кеширование (CDN/edge) — следующая итерация |
| T6 | Изоляция стилей виджета через Shadow DOM **либо** префиксованные классы — выбор не зафиксирован окончательно | [GAP: нужно архитектурное решение Shadow DOM vs scoped classes — влияет на тестовую стратегию §1.1 и на поддержку старых браузеров] |
| T7 | Домен для публичных стен — наш поддомен или CNAME клиента (PRD Q3, открытый вопрос) | Блокирует финальную реализацию `renderWallOfLovePage`; до ответа предполагается поддомен `*.proofwall.app` |
| R1 | Red ocean, дно цены $9/мес (PRD R1) | Вне контроля Refinement — продуктовый риск, не инженерный |
| R2 | Виджет может конфликтовать с CSS-in-JS хостами, не покрытыми фикстурой §1.1 | Фикстура покрывает типовые кейсы (глобальный `unset`, конфликт имён классов); экзотические CSS-in-JS раннеры — риск, принятый за неделю |
