# Подключение ЮKassa к Proofwall — что делает владелец, что уже сделано

Записано 2026-09-02. Поводом стало то, что ключи от магазина ReviewQR **не годятся**: адрес
уведомлений у магазина ЮKassa **один**, и он уже занят проектом 02. Платежи создавались бы, а
уведомления уходили в чужой продукт — деньги списаны, тариф не повышен, повторить нечем. Ровно тот
дефект, который этот проект однажды уже пережил (коммит `0501766`).

## Шаг 1 — завести отдельный магазин (делает владелец, ~10 минут)

В кабинете ЮKassa: **Настройки → Магазины → Добавить магазин**. Отдельный магазин, а не второй
ключ того же — потому что у магазина один адрес уведомлений и один набор чеков.

Для пилота достаточно **тестового магазина**: он выдаёт ключ с префиксом `test_`, реальные деньги
не списываются, тестовая карта `5555 5555 5555 4444`, любой будущий срок, CVC `123`.

## Шаг 2 — адрес уведомлений

**Настройки → HTTP-уведомления** нового магазина:

```
https://proofwall.aicoding.space/api/webhooks/payment
```

События — **только два**, больше код не обрабатывает и не ждёт:

| Событие | Что делает продукт |
|---|---|
| `payment.succeeded` | перезапрашивает статус у ЮKassa, затем применяет тариф |
| `payment.canceled` | помечает незавершённую сессию оплаты, тариф **не трогает** |

## Шаг 3 — ключи в `.env` (значения не коммитятся, файл в `.gitignore`)

```
YOOKASSA_SHOP_ID=<идентификатор нового магазина>
YOOKASSA_SECRET_KEY=<секретный ключ нового магазина>
PAYMENTS_STUB=false
```

`PAYMENTS_STUB=false` — **последний** шаг, после адреса уведомлений. Пока заглушка включена,
маршрут оплаты честно отвечает `stub: true`, и это лучше, чем создавать платежи, о результате
которых никто не узнает.

`YOOKASSA_API_URL` менять не нужно — значение по умолчанию верное.

Перезапуск: `docker compose -f docker-compose.yml -f compose.demo.yml up -d web`
(**обычный `docker compose up` поднимет свой Caddy и упрётся в занятые 80/443 чужого прокси**).

## Что уже проверено и менять не нужно

| | Состояние |
|---|---|
| Порядок операций в вебхуке | подлинность **перезапросом статуса** у провайдера ДО заявки идемпотентности; недоступность провайдера — исключение, откатывающее транзакцию. Починено коммитом `0501766`, закреплено пятью тестами и стражами по исходнику |
| Подпись | ЮKassa уведомления **не подписывает** — HMAC был бы видимостью защиты. Подлинность собирается из адреса источника и перезапроса статуса |
| Список подсетей провайдера | зашит в код, **включая IPv6** `2a02:5180::/32`; матчер понимает IPv6 и форму `::ffff:a.b.c.d` — проверено 2026-09-02 прогоном |
| Идемпотентность | уникальное ограничение в БД по `(provider, event_id)`, не проверка перед вставкой |
| Маршрут вебхука снаружи | отвечает; запрос с чужого адреса отвергается до разбора тела |

## Чего НЕ делать

- **Не переиспользовать магазин ReviewQR.** Один магазин — один адрес уведомлений; включив его
  здесь, вы сломаете оплату в ReviewQR, где контур уже проверен живым платежом.
- **Не выключать заглушку до настройки уведомлений.** Платёж создастся, тариф не применится.
- **Не публиковать ключи в репозитории.** `.env` в `.gitignore`, значения только там.

## Открытое решение владельца

Цена платного тарифа не назначена: в дорожной карте `DEC-001` со статусом `blocked`. В коде есть
дефолт `PAID_TIER_PRICE_RUB=990`, но это конфигурация, а не продуктовое решение. **До назначения
цены боевой магазин подключать незачем** — тестового достаточно, чтобы проверить тракт.
