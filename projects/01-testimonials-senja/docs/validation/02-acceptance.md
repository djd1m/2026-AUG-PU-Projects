## 2. Разбор проблемных AC growth-блока

### FR-GROWTH-001 — необоснованный порог
> «Then владелец видит share-CTA в дашборде в течение **60 секунд**»

Число есть (SMART: Measurable ✓, Time-bound ✓), но нигде не объяснено, откуда 60 — не привязано к
Success Metric, не выведено из инфраструктурного ограничения (доставка события рендер-виджета →
дашборд). Это классический «SLA с потолка»: тест напишется («поднять событие через API, поллить
дашборд, assert <60s»), но порог не проверяет ничего реального — можно было написать 10 или 300
секунд с тем же обоснованием (никаким). Не блокер, но снижает Achievable/Relevant.

`@security`-сценарий этого FR — не anti-fraud:
> «система не публикует ничего от имени владельца автоматически… без подтверждения не отправляется
> ни одного запроса к внешней сети»

Это анти-паттерн «тёмных паттернов»/consent-check, а не атака. Нет модели угрозы (кто атакующий?
что он пытается получить?). Формально тестируемо, но не закрывает раздел Security Acceptance
Criteria методики — ни input validation, ни authz, ни anti-abuse здесь не проверяются.

### FR-GROWTH-002 — хороший пример
`@security`-сценарий реально моделирует две атаки: self-referral (владелец начисляет себе комиссию)
и replay вебхука (тот же `event id` дважды) — обе с явной митигацией («комиссия не начислена»,
«повторное начисление не происходит», запись в audit log). Это качественный anti-fraud сценарий —
эталон для остальных FR. Но: сценарий проверяет ТОЛЬКО идемпотентность и self-referral, не проверяет
**подлинность** вебхука (HMAC/подпись) — см. §4.

### FR-GROWTH-003 — нереализуемое как описано
> «виджет обнаруживает сокрытие и восстанавливает видимость badge»

Два вопроса:
1. **Противоречие с FR-006.** FR-006 предлагает изоляцию «Shadow DOM **либо** строго
   префиксованные классы». Если выбран Shadow DOM, CSS хост-страницы физически не может
   таргетировать внутренний элемент badge (граница shadow-дерева блокирует внешние селекторы, кроме
   `::part()`), поэтому вся security-сценарий FR-GROWTH-003 применим только к варианту
   «префиксованные классы» — но выбор варианта не зафиксирован, значит для одной из двух
   архитектур этот AC невыполним по построению. Нужно либо зафиксировать реализацию как
   Shadow DOM + `::part()`, либо переписать сценарий под класс-изоляцию.
2. **Нет тайминга.** «Восстанавливает видимость» — без «в течение N мс». Обнаружение через
   MutationObserver не сработает на изменение внешнего CSS-правила (`display:none` из
   `<style>`/stylesheet хоста не создаёт мутацию атрибута на самом элементе) — нужен polling
   `getComputedStyle`, и тогда автотест не может быть детерминированным без порога ожидания.
   Without Time-bound → тест либо флаки, либо тестирует не то, что написано в AC.

### FR-GROWTH-004 — сильный, но с тем же дефектом порога
> «более 50 регистраций с одного IP за 10 минут» → `suspected_fraud`

Хороший, реалистичный anti-fraud сценарий с митигацией (holding до ручной проверки, audit log). Но
порог «50/10 минут» так же не обоснован, как и в FR-GROWTH-005, и покрывает только атаку с одного IP
— распределённая накрутка (пул прокси/ботнет) этим порогом не ловится вообще, хотя именно она
экономически интереснее атакующему при партнёрских выплатах.

### FR-GROWTH-005 — пороги в PRD, а не в политике Google
> «не менее **3** одобренных отзывов… не менее **400** символов»

Числа тестируемы (легко writable как `>=3` / `>=400`), но сам текст требования корректно объясняет
критерий Google («масштаб + намерение манипулировать ранжированием», не «сгенерировано
пользователями») — а затем подменяет его фиксированными цифрами без источника. У Google нет
официального порога «3 отзыва / 400 символов»; эти числа — эвристика авторов документа, не
доказанное соответствие политике. Риск: страница с 3 отзывами по 134 символа пройдёт AC и попадёт в
индекс, оставаясь тонким контентом по факту, тогда как страница с 2 длинными содержательными
отзывами (300 знаков каждый = 600 суммарно) не пройдёт формальный порог по числу штук. AC проверяет
цифры, а не то качество, которое требование заявляет как цель.

`@security`-сценарий (>20 проектов/час → принудительный noindex) — качественный и по существу
адресует «scaled content abuse» (массовое создание тонких страниц), это лучший из пяти
`@security`-сценариев по соответствию названию требования.

## 3. FR-NFR-SEC-002 — достаточен ли сценарий «побайтово совпадает»?

Нет, недостаточен для гарантии соответствия FTC Rule 16 CFR Part 465 в заявленном объёме:

1. **Таблица требования шире, чем покрытие.** Таблица допустимого/запрещённого использования Claude
   API называет ТРИ разрешённых применения: транскрипция, теги/поиск/сортировка, **и «сводка по
   набору с явной пометкой»**. Gherkin-сценариев два, и ни один не проверяет, что при наличии
   AI-сводки на публичной странице стоит «явная пометка». Если эта функция появится в реализации, у
   неё не будет автотеста на дисклеймер — при штрафе $53 088 за нарушение это дыра, а не мелочь.
2. **Второй Then первого сценария — не наблюдаемое следствие When.**
   > «ни один вызов Claude API не принимает текст отзыва на переписывание»

   Это глобальный негативный инвариант («никогда»), а не результат конкретного `When`. Как BDD-шаг
   он тестируем только если явно ограничен рамками сценария («в рамках этого запроса ни один вызов…
   не содержит текста отзыва с намерением rewrite») — иначе это архитектурный инвариант, который
   нужно проверять статическим анализом/code review, а не рантайм-тестом с одним запуском.
3. Плюс сам факт, что документ называет это «non-negotiable» и указывает штраф, а тестовое покрытие
   собственной таблицы неполное — по методике security-relevant требование без полного покрытия
   получает -10 и попадает в BLOCKED (см. таблицу выше).

## 4. Security Acceptance Criteria — покрытие по таблице методики

| Критерий методики | Применим? | Покрыт? | Комментарий |
|---|---|---|---|
| Input Validation | Да (FR-002/003 — публичные формы) | Частично | Длина/формат/размер есть; **XSS/HTML-инъекция в тексте отзыва, имени, роли — не упомянута нигде**, хотя эти поля рендерятся на стене и в виджете на чужих доменах (FR-005/FR-006). Это классический stored-XSS вектор с расширенным blast radius (одна отравленная запись = JS на каждом сайте с виджетом). Ни одного security-сценария на инъекцию нет ни у одного FR — а SKILL.md прямо требует "Input injection scenario (SQL, XSS, command)" для каждого security-relevant требования. |
| Authentication | Частично применим | Не проверено в этом документе | Механизм входа владельца не описан в Specification (вероятно, в Architecture.md — вне области этой проверки, см. §5). |
| Authorization | Да (модерация, доступ к проекту) | Нет | FR-004 заявляет «доступ из другого проекта невозможен» прозой, без AC/Gherkin. |
| Data Protection | Да (фото, видео, имя — PII реальных людей) | Нет | Ни слова о шифровании хранения видео/фото, сроках хранения, согласии на публикацию лица/голоса. |
| Multi-Tenant Isolation | Да, ключевой риск SaaS | **Нет — 0 сценариев** | FR-NFR-SEC-001 — единственное требование, целиком посвящённое этому, и единственное без единого Gherkin-сценария. Прямое нарушение правила методики: security-relevant требование без критериев = -10, BLOCKED. |
| Secret Management | Не в Specification | Не проверено | Вероятно домен Architecture.md/ADR.md — вне области. |
| Webhook Security | Да (FR-GROWTH-002 — оплата) | Частично | Есть идемпотентность (dedup по event id), **нет проверки подписи/HMAC входящего вебхука**. Без неё атакующий может отправить поддельный «оплата прошла» и разблокировать paid-функциональность/начислить комиссию партнёру — это ровно тот риск, который таблица методики называет красным флагом («Accept POST, no HMAC»). |

**Итог по разделу:** 2 из 7 применимых критериев полноценно покрыты (Input Validation — частично,
Webhook Security — частично), 2 не покрыты вовсе при высокой применимости (Multi-Tenant Isolation,
Data Protection), 1 полностью отсутствует, несмотря на явную критичность (XSS/injection).

## 5. BLOCKED (score < 50 или явный блокер)

1. **FR-NFR-SEC-001** (25) — ключевое требование мульти-тенантности не имеет ни одного
   Gherkin-сценария; при этом это единственный NFR, прямо утверждающий «невозможен ни через API, ни
   через параметры виджета» — заявление, которое сейчас никак не подтверждается тестом.
2. **FR-NFR-SEC-002** (48) — non-negotiable compliance-требование с прямо названным штрафом,
   покрытие которого не соответствует собственной таблице требования (см. §3).
3. **FR-002** (48) — публичная форма без auth, принимающая контент, который затем публично
   рендерится на сторонних доменах, без единого AC/сценария на инъекцию/санитизацию.
4. **FR-003** (45) — приём видео/файлов от анонимных пользователей (до 100 MB) без AC на проверку
   реального формата (content-sniffing vs расширение), антивирус/malware-скан не упомянут.

## 6. Что я НЕ проверял и почему

- **INVEST / качество user-story** — вне области этой проверки (см. системную инструкцию); этим
  занимается отдельный агент по историям (`validator-stories`).
- **Architecture.md, ADR.md, PRD.md** — читал точечно только там, где Specification прямо ссылается
  на архитектурное решение (FR-006 Shadow DOM vs FR-GROWTH-003). Не проверял, закрывают ли эти
  документы найденные здесь дыры (Secret Management, Authentication) — возможно, они описаны там;
  формально это не отменяет отсутствия AC/Gherkin в самом Specification.md.
- **Реальную тестируемость на живом коде** — проекта на этапе Specification, кода нет; все выводы о
  «тестируемо / нет» — по написанному тексту сценария, не по факту прогона теста.
- **Юридическую точность формулировки FTC-раздела** — не проверял, действительно ли 16 CFR Part 465
  и сумма $53 088 процитированы корректно; это фактическая проверка домена права, не AC-валидация.
- **Производительность и доступность как отдельные дисциплины** — FR-NFR-PERF-001 и FR-NFR-A11Y-001
  оценены только на предмет отсутствия Gherkin/числовых порогов, не на техническую достижимость
  заявленных цифр (30 KB gzip, 300 мс p95, AA-контраст).
