## Разбор по пунктам

### B-1. Stored-XSS — ЗАКРЫТ

Intake и render — действительно разные Feature-блоки с разными assertion'ами:
- Intake (Specification.md:34-44, :59-69): проверяет **сохранение без изменений**, не исполнение.
- Render (Specification.md:98-108 FR-005, :125-135 FR-006): проверяет именно **неисполнение**
  — «ни один тег `<script>` из пользовательского контента не выполняется в браузере» и «контент
  виджета не получает доступа к DOM или cookie хост-страницы».

Правило «экранирование на рендере» согласовано с побайтовым совпадением текста явно, одной
фразой (Specification.md:32): «приём сохраняет ввод как есть — это условие побайтового совпадения
из FR-NFR-SEC-002». Конфликта нет — обе нормы ссылаются друг на друга, а не молчат друг о друге.

Виджет на чужом домене (Shadow DOM) покрыт отдельно: Refinement.md §1.1 и §3.5 требуют реального
второго origin (не origin приложения) именно потому, что иначе `currentDomain() == OUR_APP_DOMAIN`
и тест ничего не проверит — методологически это сильнее многих реальных проектов.

**Слабое место (не блокер):** intake-сценарии проверяют «сохранение не приводит к выполнению кода
на сервере обработки формы» (Specification.md:42, :66) — это почти неопровержимое утверждение при
параметризованной вставке в Postgres, реальной защитной силы не несёт. Не считаю это пустышкой:
сценарий существует как регресс-барьер против будущей санитизации на приёме, которая сломала бы
побайтовое совпадение (FR-NFR-SEC-002), а не как замена render-проверке.

### B-2. Мульти-арендная изоляция — ЗАКРЫТ ЧАСТИЧНО

Сценарий 2 (Specification.md:501-509, подмена параметра виджета) и код `apiWidgetConfig`
(Pseudocode.md:234-245, «resolves slug → project, только slug принимается») — согласованы и
конкретны. Refinement §3.6 добавляет 3 реально исполнимых теста: виджет, аутентифицированная
модерация (403 + audit log, Pseudocode.md:140-143), подмена параметра.

**Находка:** Сценарий 1 (Specification.md:494-499) описывает «API проекта B запрашивает отзыв,
принадлежащий проекту A, **по его идентификатору**» под ролью `app_service`/`BYPASSRLS`. Ни в
Architecture.md, ни в Pseudocode.md **нет ни одного анонимного эндпоинта, принимающего ID
отзыва** — `apiWidgetConfig` работает только по `slug` и отдаёт список, `moderateTestimonial`
(единственное место с проверкой `testimonial.project_id != actor.project_id`, Pseudocode.md:140)
требует аутентифицированного `actor`, то есть роль `app_authenticated`, а не `app_service` из
Given этого сценария. Как написано, Сценарий 1 не соответствует ни одной описанной точке входа —
это тест без цели, пока такой эндпоинт не появится. Не фатально (реальная анонимная поверхность
— `apiWidgetConfig` — закрыта Сценарием 2), но именно этот сценарий нельзя автоматизировать
буквально сегодня.

### B-3. FTC-compliance — ЗАКРЫТ

Все три требования отчёта выполнены:
1. Сценарий на пометку сводки добавлен (Specification.md:546-553) — конкретный, проверяемый DOM/UI-assertion.
2. Инвариант переформулирован в проверяемое условие с явным `When` (Specification.md:526-530):
   «отзыв сохраняется и публикуется» → «обработка ... не выполняет ни одного вызова Claude API».
3. Сценарий MCP-контракта (Specification.md:532-537) — реально автоматизируем: запросить список
   tool'ов у MCP-сервиса и проверить, что он состоит из одного `transcribe_video`.

**Усиление, которое стоит зафиксировать явно (не было в отчёте):** в docker-compose
(Architecture.md:320-360) `ANTHROPIC_API_KEY` объявлен **только** в контейнере `mcp-claude`;
у `web` и `worker` этой переменной нет вообще. Это значит, что даже гипотетический прямой вызов
Claude API из бизнес-кода физически не сможет пройти аутентификацию — граница держится не только
на контракте tool'ов, но и на разделении секретов между контейнерами. Архитектурно это сильнее,
чем просило исправление.

### B-4. Подпись платёжного вебхука — ЗАКРЫТ ЧАСТИЧНО (главная находка ре-валидации)

Формально пункт отчёта («добавить `@security`-сценарий на отклонение вебхука с неверной
подписью») выполнен буквально: сценарий есть, Specification.md:293-299, не дублирует
идемпотентность (это отдельный сценарий, отдельная секция Given/When/Then, отдельная причина
audit log — `invalid_signature` vs `self_referral`).

**Но:** алгоритм `onPaymentWebhook` в Pseudocode.md:355-374 — тот самый код, по которому это будет
реализовано — **не содержит ни единой строки проверки подписи**:

```
function onPaymentWebhook(event):
  if webhookEventStore.exists(event.id):           # идемпотентность по event id (@security)
    return HTTP 200
  webhookEventStore.record(event.id)
  if event.type != "payment_succeeded":
    return HTTP 200
  ...
```

Нет ни `verifySignature(event, secret)`, ни отдельного `HTTP 401`/`403` при неверной подписи, ни
секрета в переменных окружения `web` (Architecture.md:320-337 — только `DATABASE_URL`,
`SESSION_SECRET`, `S3_*`, `MCP_CLAUDE_URL`; нет `PAYMENT_WEBHOOK_SECRET` и аналогов). ADR-006
(идемпотентность вебхуков, ADR.md:225-267) тоже ни разу не упоминает подпись — весь ADR посвящён
исключительно дедупликации `event_id`.

Это ровно та ситуация, о которой предупреждает задание: сценарий **выглядит** как проверка, но
поддерживающий его слой (алгоритм, который инженер реально закодирует) её не реализует. Если
кодировать буквально по текущему Pseudocode.md, сценарий Specification.md:294-299 **упадёт** —
подписи никто не проверяет, запрос с любой или отсутствующей подписью пройдёт до бизнес-логики.
FR-008 (Specification.md:160-161) тоже формулирует это требование прозой («подпись вебхука
проверяется»), но и туда не спускается ни в Architecture, ни в Pseudocode (см. ниже).

**Вердикт по B-4:** документ Specification.md прошёл бы поверхностную проверку «сценарий
добавлен», но по существу требование не закрыто — закрыт только один из двух слоёв (спецификация
поведения), второй слой (алгоритм реализации) пропущен.

### C-1. Схема момента ценности — ЗАКРЫТ

Проверено во всех шести документах:
- PRD.md §2.4.1 (актуальная редакция, «версия отменена» зафиксирована явно) — источник истины.
- Architecture.md §3.3, §4.2, §10 — одна таблица `widget_installs`, `unique(project_id, domain)`,
  атомарный `INSERT ... ON CONFLICT (project_id, domain) DO NOTHING RETURNING id`.
- Pseudocode.md §4 — та же логика, с явным комментарием "версия «invite_shown раз на проект»
  ОТМЕНЕНА" (Pseudocode.md:190) и разбором гонки словами, не только кодом (строки 224).
- Specification.md §FR-GROWTH-001, §4 (метрики) — та же гранулярность и текст.

Остатков старого решения («один раз на проект», `widget_install_events`,
`ON CONFLICT (project_id)`) **в шести проверяемых документах не найдено** — grep по всему `docs/`
их не нашёл нигде, кроме самого `validation-report.md` (историческая цитата блокера, что и
ожидаемо). Гонка разобрана через атомарность `INSERT ... RETURNING`, а не `exists()`-затем-`insert()`
— именно так, как требовал отчёт, и с явным комментарием в коде, почему `exists-then-insert` не
годится (Pseudocode.md:199-202).

### C-2. Badge vs Shadow DOM — ЗАКРЫТ

Все три документа согласованы дословно:
- Specification.md:330-333, :353-371 — два отдельных сценария вместо одного безусловного:
  восстановление самого узла (детектируется и чинится) и сокрытие родителя (честно объявлено
  недетектируемым, закрыто офертой).
- ADR-002 (ADR.md:82-87) — тот же текст остаточного риска, тот же вывод про ToS.
- Pseudocode.md §5.2 (строки 259-279) — код `checkAndRestore` буквально реализует эту границу с
  комментарием, почему `forceVisibleStyles` не может починить скрытие предка (каскад CSS, не
  пробел в коде).

Безусловной формулировки «система обнаруживает сокрытие и восстанавливает видимость» в текущих
документах не осталось — она есть только в `validation-report.md` как цитата исходного блокера.

## Сценарии-пустышки

1. **FR-NFR-SEC-001, Сценарий 1** (Specification.md:494-499) — тестирует эндпоинт, которого не
   существует в Architecture/Pseudocode (см. B-2 выше). Не пустышка в смысле «имитирует и ничего
   не даёт», но пустышка в смысле «нечего запускать» — пока не появится конкретный анонимный
   `GET .../:id`, сценарий нельзя превратить в автотест буквально.
2. **FR-GROWTH-002, Сценарий «Вебхук с неверной подписью отклоняется»** (Specification.md:293-299)
   — это главная находка отчёта: сценарий текстуально безупречен, но не имеет опоры в алгоритме
   (см. B-4). Формально не пустышка (написан для реального намерения), но станет пустышкой в
   момент, когда QE Phase 3 отчитается «сценарий покрыт», проверяя не более чем идемпотентность.
3. **FR-GROWTH-003, Сценарий «Сокрытие родительского контейнера...»** (Specification.md:363-371)
   — не пустышка, но нетипичная форма: тестирует «система корректно ничего не делает». Годится
   только как регресс-барьер против будущей избыточной попытки «дотянуться» до DOM хоста; в
   тест-плане Phase 3 стоит явно пометить как negative/contract-тест, а не забыть при подсчёте
   покрытия.

## Новые проблемы, появившиеся вследствие правок

- Сама попытка закрыть B-4 текстом сценария, не тронув Pseudocode, создала **иллюзию закрытости**:
  таблица в `validation-report.md` при поверхностном ре-чтении покажет «сценарий добавлен» как
  факт исправления, хотя проверяемое поведение не описано на уровне, с которого его будут кодировать.
  Это ровно тот паттерн, о котором предупреждало задание.
- FR-008 — новое требование текущей итерации — ввело зависимость (`payment_webhook_secret`,
  checkout-эндпоинт), которая теперь нигде не спроектирована; раньше (до FR-008) этой дыры не было,
  потому что не было и самого требования оплаты.

## Итоговый вердикт

**Идти в Phase 3 в текущем виде не рекомендую без ещё одной короткой правки.** Из шести пунктов
отчёта закрыто по существу пять (B-1, B-3, C-1, C-2 полностью; B-2 частично, с второстепенной
оговоркой). Один — B-4 — закрыт лишь на уровне формулировки требования, а не на уровне алгоритма,
и это ровно тот класс требования (платёжная безопасность, начисление комиссий), где расхождение
между «сценарий написан» и «код это делает» стоит реальных денег партнёрской программы.

**Рекомендация:** прежде чем переходить к toolkit generation (Phase 3), точечно донести в
`Pseudocode.md` §7.2 шаг проверки подписи (`verifySignature(rawBody, signatureHeader, secret)` до
`webhookEventStore.exists`) и добавить секрет в `docker-compose`/Architecture §7. Остальное (rate-limit
дублирование, FR-008 архитектура, устаревшие имена в Refinement/C4) — не блокеры уровня B-4, но
должны попасть в бэклог итерации 2, иначе W-1-класса находки (уже отмеченные ранее как
«существенные», не блокирующие) повторятся в новой форме.
