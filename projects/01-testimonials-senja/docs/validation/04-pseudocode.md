## 2. Разбор четырёх ключевых алгоритмов

### 2.1 FR-GROWTH-001 — момент ценности

Сам примитив идемпотентности (`INSERT ... ON CONFLICT DO NOTHING RETURNING id` в одной
транзакции) — технически верное решение против гонки: неважно, сколько параллельных вызовов,
`inserted=true` получит ровно один. Это работает.

Но: **пседокод и Architecture.md расходятся в схеме ровно там, где это критично.**
- Pseudocode §4: `ON CONFLICT (project_id) DO NOTHING` → уникальный индекс подразумевается
  **только по `project_id`** (таблица названа `widget_install_events`).
- Architecture.md §4.2/таблицы: таблица `widget_installs`, `unique(project_id, domain)` —
  то есть уникальность **по паре**, а значит новый домен того же проекта снова пройдёт `INSERT`.

Это не стилистическая мелочь: если реализация пойдёт по схеме Architecture (что вероятнее — там
описана вся ER-модель), `recordFirstRenderIfNeeded` из Pseudocode будет эмитировать
`invite_shown` **при каждом новом домене**, а не один раз за всю жизнь проекта, как читается
формулировка "момент ценности" и DoD `invite_shown` в Specification. Какая семантика верна —
не решено ни в одном документе.
- "Внешний домен" определён только отрицанием (`!= OUR_APP_DOMAIN`), это признанный GAP в самом
  Pseudocode — но он же снимает вопрос про allowlist поддоменов клиента (www vs apex — два разных
  домена по этой логике → потенциально два разных "первых рендера").
- Гонка при параллельных рендерах учтена корректно (БД-транзакция).

**Вывод:** ядро идемпотентности верно, но модель данных для "ровно 1 раз" не зафиксирована
однозначно между двумя документами — это заблокирует Phase 3, если не решить сейчас.

### 2.2 FR-GROWTH-002 — атрибуция

Порядок разрешения (`promo_code` → `cookie`) реализует правило приоритета текстуально верно,
таблица случаев в Refinement §3.3 полная и корректная, включая кейс "невалидный код не
откатывается на cookie".

Идемпотентность вебхука: `webhookEventStore.exists(event.id)` проверяется **до** записи и
**до** проверки типа события — корректный порядок, TOCTOU не рассматривается (единственный
воркер обрабатывает вебхуки последовательно — не описано явно, но неявно предполагается；
при нескольких инстансах API возможна гонка `exists` → `record`, т.к. это два отдельных
вызова, не одна атомарная операция, в отличие от §4, где применён `ON CONFLICT`).
**Это несогласованность внутри самого документа:** для `widget_install_events` реализовали
атомарный upsert против гонки, а для `webhook_events`, куда бьёт внешний, потенциально
дублирующий трафик от платёжного провайдера, — обычный `exists` + `record` без транзакционной
гарантии.

Self-referral: сравнение `partner.email == account.email` — не нормализует регистр/plus-адреса
(`p1+test@example.com` пройдёт как "другой" email). Достаточно для MVP, но не задокументировано
как осознанный компромисс (в отличие от других решений в Refinement §5).

Что если cookie от партнёра А, а промокод от партнёра Б — обработано явно и корректно
(§7.1, побеждает Б).

### 2.3 FR-GROWTH-005 — порог индексируемости

Пересчёт вызывается из `moderateTestimonial` при **любом** переходе в/из `approved`
(`if target_state == "approved" or previous_state == "approved"`) — значит удаление отзыва
(approved → hidden/rejected) корректно вызывает пересчёт **в обе стороны**, включая обратный
переход ниже порога. Это прямо отвечает на вопрос задания: **да, работает и вверх, и вниз**,
и в Refinement §3.4 есть тест именно на обратный переход. Идемпотентность пересчёта тоже
учтена (ветка "ничего не пишем").

Единственный недостающий кусок — anti-abuse по массовому созданию проектов (§6 "Anti-abuse")
пишет `forced_noindex_bulk_creation`, но не показано явно, что `recomputeContentThreshold`
уважает или игнорирует "forced" флаг — комментарий говорит "снимается только через обычный
recompute", но в коде `recomputeContentThreshold` нет проверки forced-состояния вообще, поэтому
неясно, чем строка forced в БД отличается от обычной `noindex=true` на уровне схемы (одно и то
же поле или отдельный флаг — не специфицировано).

### 2.4 FR-GROWTH-003 — восстановление скрытого badge

`checkAndRestore` проверяет только `computedStyle(badgeNode)` — т.е. состояние **самого узла
badge**. Прямой вопрос задания подтверждается: **если хост скрывает не сам badge, а
родительский/оборачивающий элемент** (`display:none` на контейнере, в котором сидит shadow-host),
то `computedStyle(badgeNode)` **не обязательно вернёт `display:none`** (у элемента внутри
скрытого предка `offsetWidth/offsetHeight` будут 0, что MutationObserver+checkAndRestore
формально ловит через `offsetWidth == 0 and offsetHeight == 0` — но `forceVisibleStyles(badgeNode)`
чинит стиль самого badge, а не предка, поэтому визуально бейдж всё равно останется невидим).
**Механизм не работает для этого кейса**, и это не домысел — сама Architecture.md честно
признаёт это как "остаточный риск в ADR-002" ("не может обойти CSS хоста, который скрывает сам
host-элемент"). Но: **Specification FR-GROWTH-003 `@security` формулирует AC безусловно**
("виджет обнаруживает сокрытие и восстанавливает видимость" — без оговорки), а Pseudocode §5.2
не содержит этой оговорки вообще. Расхождение видно только если читать Architecture отдельно —
уязвимое место находок для Phase 3, если инженер прочитает только Pseudocode.

## 3. Алгоритмы без обработки ошибок / только happy path

1. **§1 `submitTestimonial` → §1.1 `handleVideoTestimonial`:** `handleVideoTestimonial`
   объявляет `raise ValidationError(...)` при плохом видео, но `submitTestimonial` **не
   оборачивает вызов в try/catch** и не транслирует исключение в HTTP 400 — путь невалидного
   видео не имеет определённого ответа (по факту это будет необработанное исключение / 500).
   Дополнительно: `rateLimitStore.increment` выполняется **до** видео-валидации, то есть
   невалидное видео уже съедает один из 5 слотов лимита в час — не обязательно баг, но не
   зафиксировано как осознанное решение.
2. **`uploadIfPresent(request.photo)` (§1), `uploadToStorage` (§1.1):** нет catch на сбой
   стораджа (MinIO недоступен/квота) — ни статус-кода, ни отката созданной записи.
3. **`transcribeVideoJob`:** `catch ClaudeApiError` ловит только один класс ошибок; сбой
   `extractAudioTrack` (повреждённое видео, отсутствие аудиодорожки) — необработанное
   исключение, job упадёт без записи `transcript_status: failed`.
4. **`notifyOwnerDashboard`** (§4): не специфицирован механизм доставки (WebSocket/poll), при
   этом Specification требует показ CTA "в течение 60 секунд" — нет ни retry, ни fallback, если
   уведомление не долетело (SLA не на чём проверить).
5. **`onPaymentWebhook`:** нет обработки `partner is null` / `account is null` до обращения к их
   полям (`partner.email`, `account.email`) — если `getPartner`/`getAccount` вернут null
   (например, партнёр удалён между созданием pending-атрибуции и оплатой), код упадёт на
   разыменовании null, а не вернёт осмысленный ответ.
6. **FR-001 целиком** — раз алгоритма нет, обработка ошибок (занят слаг, некорректный формат)
   тоже не описана.

## 5. Тестируемость growth-механик (Refinement)

Раздел 1.1 честно и не тривиально описывает тестирование виджета на чужой странице (второй
origin, агрессивные стили хоста, проверка отсутствия побочных эффектов на страницу-контейнер) —
это реалистичный план, не отписка.

Разделы 3.1–3.4 покрывают badge-integrity, `invite_shown` "ровно 1 раз", приоритет
промокода и noindex в обе стороны — все четыре ключевых свойства из задания протестированы
на своём уровне (браузерный/интеграционный/юнит соответственно).

**Пробел:** нет отдельного раздела тестируемости для FR-GROWTH-004 (когортный дашборд,
детект накрутки >50/10мин) и для FR-005 (`schema.org/Review` валидация упомянута как DoD-пункт,
но не как тестовый сценарий в Refinement §1–3). Таблица трассируемости Specification §5 тоже не
включает FR-005/FR-007/FR-001 — только growth-FR и один NFR.

## 6. Балл и вердикт

**Балл: 54 / 100 — 🟡 УСЛОВНО ГОТОВО (CAVEATS), не 🔴, но Phase 3 нельзя начинать без правок.**

Обоснование: ядро самых рискованных механик (идемпотентность invite_shown на уровне БД,
двусторонний noindex, приоритет промокода) спроектировано грамотно и это не косметика. Но:
(а) три FR без алгоритма вообще (FR-001, часть FR-GROWTH-004, FR-NFR-A11Y-001),
(б) прямое противоречие схемы данных между Pseudocode и Architecture для самого важного growth-
события недели (C1) — это блокер, а не мелочь,
(в) заявленная в Specification как безусловная защита badge на деле не работает для документированного
Architecture-ом кейса (C2),
(г) несколько путей без обработки ошибок, один из них (невалидное видео) — реальный дефект
поведения API, а не пропуск описания.

**Рекомендация:** до Phase 3 — зафиксировать единую схему `widget_install*` (project_id-only
vs project_id+domain) и явно решить семантику "invite_shown один раз за жизнь проекта или один
раз на домен"; дописать алгоритм FR-001; либо снять безусловность из AC FR-GROWTH-003, либо
доработать `checkAndRestore` для случая скрытого предка.
