## 3. Новая находка, не пойманная предыдущими проверками

### 🔴 FR-NFR-SEC-002, сценарий 4 («Сводка по набору отзывов помечена как сгенерированная ИИ») — сценарий для нереализуемой в MVP функции

Specification.md:549-556 описывает Gherkin-сценарий для функции «сводка по набору отзывов,
созданная через Claude API». Эта функция:
- не упомянута ни в одном FR раздела 1-2 (FR-001…FR-008, FR-GROWTH-001…005);
- отсутствует в Architecture.md (нет компонента, нет API-роута, нет поля в схеме данных);
- отсутствует в Pseudocode.md (нет функции генерации сводки);
- прямо названа ADR-005 (ADR.md:203-205) как **вне scope MVP-недели**: «Будущая функция «сводка
  по набору отзывов»... вне scope MVP-недели, но если будет реализована, обязана переиспользовать
  тот же принцип явной пометки».

Это тот же класс дефекта, из-за которого исходно был выставлен B-4: сценарий выглядит как
проверка, но не имеет опоры ни в архитектуре, ни в алгоритме — только сейчас опора отсутствует не
потому, что её забыли спроектировать, а потому что сама функция официально отложена. QE Phase 3,
получив этот Gherkin-сценарий, либо потратит время на попытку найти несуществующий код, либо
формально "покроет" его моком без реальной цели — то самое "иллюзия покрытия", о которой
предупреждает 06-revalidation.md.

**Не блокер** (сценарий описывает поведение будущей, официально не-MVP функции — Phase 3 не
должна и не будет её строить в рамках этой недели), но **требует одного из двух действий до
генерации `test-scenarios.md`:** либо пометить сценарий как `@future`/`@out-of-scope-mvp` и
исключить из подсчёта покрытия Phase 3, либо убрать его из Specification.md до момента, когда
функция реально появится в Architecture/Pseudocode.

### Второстепенное: неявные (не алгоритмизированные) `@security`-проверки

Пункты FR-005/FR-006/FR-NFR-SEC-002-сц.3/FR-GROWTH-001 из матрицы §2 полагаются на типовое, но не
прописанное явно поведение (авто-экранирование фреймворка, безопасный DOM API, текстовая пометка,
UI-диалог). Ни один не является дефектом сам по себе — это нормальная степень детализации
псевдокода для этой недели, — но именно эти четыре места стоит держать в фокусе на code review в
Phase 3, поскольку это ровно та точка, где "сценарий написан, а реализация может незаметно
разойтись" (паттерн B-4).

Прочих новых рассинхронов после итерации 2 не найдено: `rate_limit_events`, FR-008,
`PAYMENT_WEBHOOK_SECRET`, канонические имена — везде согласованы (см. §1, W-1/W-7/W-10).

## 7. ИТОГОВЫЙ ВЕРДИКТ: 🟢 READY

**Обоснование.** Все 4 официальных блокера (B-1…B-4) закрыты по существу, включая B-4 — главную
находку предыдущей ре-валидации: проверка подписи вебхука теперь в алгоритме `onPaymentWebhook`,
до записи идемпотентности, с секретом в окружении `web`, где физически исполняется роут. Оба
критических противоречия (C-1, C-2) закрыты и согласованы дословно между всеми документами. Все
10 существенных замечаний (W-1…W-10) закрыты, включая полную унификацию `rate_limit_events` по
всем трём местам использования — то, что итерация 1 не довела до конца. Пересчитанный средний
балл (≈89) далеко за порогом READY.

Единственная находка этого гейта — сценарий FR-NFR-SEC-002 №4 для нереализуемой в MVP функции
(«сводка по набору отзывов») — не блокер: описывает поведение официально отложенной за пределы
недели функции (ADR-005), не имеет отношения к тому, что Phase 3 будет строить. Требуется
разметить его `@future`/исключить из подсчёта покрытия — разумная гигиена перед генерацией
`test-scenarios.md`, а не причина для возврата на Phase 1.

**Идти в Phase 3 можно без дополнительной итерации.** Рекомендация (не блокирующая): пометить
сценарий из §3 как out-of-scope и держать в фокусе 4 неявных `@security`-соответствия из §2 при
код-ревью реализации FR-005/FR-006/транскрипт-пометки/share-диалога.
