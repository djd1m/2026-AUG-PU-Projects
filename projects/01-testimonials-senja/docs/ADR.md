## ADR-001: Изоляция виджета от стилей хоста — Shadow DOM

**Статус:** Принято

**Контекст**

FR-006 и FR-NFR-PERF-001 требуют, чтобы виджет не конфликтовал со стилями и скриптами
произвольного хост-сайта (R6 в PRD: «Виджет ломает вёрстку хоста»). Виджет должен работать на
сайте, о CSS которого мы ничего не знаем заранее.

**Решение**

Виджет рендерится в **Shadow DOM** (`attachShadow({mode: 'open'})`). Все стили инжектируются
внутрь shadow-root. Наружу торчит только один host-элемент с минимальной разметкой.

**Альтернативы**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Shadow DOM** (выбрано) | Полная двусторонняя изоляция CSS: стили хоста не проникают внутрь, стили виджета не «текут» наружу. Нативный браузерный API, без рантайм-библиотек | См. честные минусы ниже |
| Строго префиксованные классы (`.pw-card`, `.pw-badge`) | Проще для очень старых браузеров, легче дебажить в devtools без открытия shadow-root | Не защищает от глобальных CSS-сбросов хоста (`* { margin: 0 !important }` всё равно применяется), не защищает от совпадения имён классов на масштабе тысяч сайтов, требует дисциплины навсегда |
| iframe | Максимальная изоляция (включая JS) | Отдельный HTTP-запрос на документ, сложнее асинхронно подогнать высоту под контент, хуже для SEO-контекста страницы хоста, тяжелее уложиться в p95 ≤ 300 мс |

**Последствия — честный разбор минусов выбранного варианта**

- **Стилизация под бренд хоста усложняется.** Если в будущем понадобится «повторить шрифт сайта
  хоста внутри виджета» (не в scope недели), это требует явного проброса `font-family` через
  CSS custom properties снаружи внутрь shadow-root — Shadow DOM не даёт этого «бесплатно».
- **`display:none` на host-элементе снаружи всё ещё возможен.** Shadow DOM изолирует *содержимое*
  от стилей хоста, но не защищает сам host-элемент от того, что хост-скрипт спрячет его целиком.
  Это прямо связано с ADR-002 (остаточный риск сокрытия badge).
- **Старые браузеры (pre-2018, доля тестовой аудитории S1-сегмента пренебрежимо мала) требуют
  полифилл** — не считаем блокером для MVP недели, но фиксируем как известное ограничение.
- **Сложнее автоматизированное E2E-тестирование** обычными DOM-селекторами — тесты обязаны explicit
  проходить через `shadowRoot`, иначе селекторы молча ничего не найдут (частая ошибка).

## ADR-002: Серверная проверка тарифа для badge

**Статус:** Принято

**Контекст**

Это ADR о безопасности growth-механики, а не о UI. FR-GROWTH-003 требует, чтобы badge
«Powered by Proofwall» был обязателен на бесплатном тарифе и не мог быть снят клиентскими
средствами. Badge loop — **единственный** growth-канал продукта (PRD §4.2): если badge можно снять
без оплаты, основной канал роста ломается в первую же неделю после первого технически подкованного
пользователя, который откроет devtools.

**Решение**

Тариф проекта (`project.tier`) читается **исключительно на сервере** при каждом запросе
`/api/widget/config`. Ответ клиенту содержит уже вычисленное `badge_required: boolean`, само поле
`tier` клиенту не передаётся вообще. Виджет не содержит логики «если free — показать badge»: он
безусловно рендерит badge, если сервер прислал `badge_required = true`, и безусловно не рендерит,
если `false`. Виджет физически не может решить иначе, потому что решение принимается не в нём.

Дополнительно: `MutationObserver` на host-элементе восстанавливает атрибуты `style`/`hidden`, если
скрипт хоста пытается их изменить точечно (см. Architecture.md §4.3).

**Альтернативы**

| Вариант | Почему отклонён |
|---|---|
| Передавать `tier` в конфиге, решение о badge — в JS виджета | Тривиально обходится редактированием переменной в devtools/через прокси-ответ; badge исчезает навсегда для конкретного домена |
| Подписывать badge-флаг JWT с коротким TTL | Излишняя сложность для MVP недели; тот же результат (нельзя подделать), что и просто не отдавать `tier`, но с доп. инфраструктурой (ключи, ротация) |
| Встраивать badge как часть server-side отрендеренного HTML (SSR-фрагмент), а не JS-конструкцию | Рассмотрено серьёзно: сильнее устраняет клиентскую подделку. Отклонено для MVP из-за сложности встраивания SSR-фрагмента в третий домен без CORS/iframe-накладных расходов за неделю; кандидат на пересмотр, если badge-снятие станет наблюдаемой проблемой в проде |

**Последствия**

- Каждый рендер виджета — минимум один сетевой запрос к нашему серверу; нельзя закэшировать
  ответ конфигурации надолго на CDN без риска отдать устаревший `badge_required` сразу после
  апгрейда тарифа (FR-GROWTH-003 @edge-case требует, чтобы апгрейд убирал badge «при следующем
  рендере» без переустановки — короткий TTL кэша, не «без кэша вообще»).
- Остаточный риск (честно, не скрываем): хост может скрыть **весь host-элемент** через
  `display:none` в CSS, что сервер не видит и не может обнаружить программно. Мы не решаем эту
  проблему технически на MVP — она смещается в плоскость условий использования (ToS): скрытие
  виджета целиком нарушает условия бесплатного тарифа, обнаруживается вручную/выборочно, не
  инструментируется в §6 Architecture.md на этой неделе. `[GAP: нужен продуктовый ToS-текст про
  запрет скрытия виджета — вне scope архитектуры]`.
- Тест-контракт: `badge_required` покрывается автотестом в обе стороны (free → true, paid → false)
  и тестом на попытку передать параметр отключения badge через query/API (должен игнорироваться).

## ADR-003: Приоритет промокода над cookie при конфликте атрибуции

**Статус:** Принято

**Контекст**

FR-GROWTH-002 определяет два независимых канала партнёрской атрибуции: cookie (автоматический,
ставится при переходе по реферальной ссылке) и промокод (вводится вручную при оплате). Safari ITP
(Intelligent Tracking Prevention) гасит JS-устанавливаемый cookie за 7 дней — типичный B2B/SaaS
цикл принятия решения (PRD ссылается на dark-funnel тренд MT-6: ~211 дней исследования до контакта)
легко превышает этот срок. Правило поведения при **расхождении** двух источников не было очевидным
и должно быть зафиксировано явно, а не решаться в коде реализующего инженера.

**Решение**

При оплате, если у пользователя одновременно присутствует валидная cookie-атрибуция на партнёра A
**и** введён промокод партнёра B — засчитывается **промокод (B)**. Промокод — явное, осознанное
действие пользователя в момент оплаты; cookie — фоновый артефакт браузера, который мог устареть,
относиться к давно забытому переходу или быть техническим шумом (несколько переходов по разным
ссылкам подряд). Если промокод не введён — используется cookie-атрибуция как единственная.

**Альтернативы**

| Вариант | Почему отклонён |
|---|---|
| Приоритет у cookie (first-touch) | Стандартная модель атрибуции, но именно её гасит Safari ITP через 7 дней — сделало бы правило бесполезным для главного риска, ради которого FR-GROWTH-002 вообще существует |
| Last-touch между cookie и промокодом по времени установки | Требует хранить временные метки обоих и сравнивать — сложнее реализовать за неделю, тот же практический результат в подавляющем большинстве случаев, потому что промокод почти всегда вводится позже cookie |
| Запрещать одновременное наличие обоих (выбор одного канала на визит) | Технически проще, но лишает пользователя возможности осознанно исправить устаревшую атрибуцию промокодом — противоречит духу FR-GROWTH-002 |

**Последствия**

- Правило реализуется в одном месте — обработчике оплаты (см. Architecture.md §6,
  `referral_attributed`), а не размазывается по нескольким точкам входа.
- `source` пишется в `referral_attributions` (`cookie` | `promo_code`) — это делает правило
  наблюдаемым в аналитике, а не только задокументированным.
- Self-referral (партнёр платит по своему же коду) блокируется независимо от источника —
  см. Specification.md `@FR-GROWTH-002 @security`.

## ADR-004: Порог содержательности и `noindex` для тонких страниц `/w/<slug>`

**Статус:** Принято

**Контекст**

FR-GROWTH-005 требует, чтобы Wall of Love была индексируемой и несла самостоятельную ценность.
Google Scaled Content Abuse policy наказывает не «страницы с пользовательским контентом» как
класс, а **масштаб + намерение манипулировать ранжированием** (зафиксировано в Specification.md
как явная формулировка критерия). Пустая или почти пустая `/w/<slug>` — типичный паттерн такой
злоупотребляющей страницы, если таких страниц создаются тысячи автоматически.

**Решение**

Страница `/w/<slug>` получает `noindex`, если проект не набрал **минимум 3 одобренных отзыва И
суммарно ≥ 400 символов текста**. Оба числа берутся напрямую из
`@FR-GROWTH-005 @happy-path`/`@edge-case` в Specification.md — это не архитектурное изобретение,
а перенос уже заданного порога в код. Снятие `noindex` — автоматическое, при первом же запросе
страницы после пересечения порога (не требует ручного действия владельца).

Дополнительно: аккаунт, создавший >20 проектов за час, получает принудительный `noindex` на все
новые проекты этого аккаунта независимо от порога контента, до ручной проверки (anti-abuse,
`@security`-сценарий в Specification.md).

**Альтернативы**

| Вариант | Почему отклонён |
|---|---|
| Индексировать всё, полагаться на постмодерацию Google | Прямое нарушение принятого продуктового решения; риск R4 в PRD реализуется быстрее, чем Google успеет заметить и наказать вручную — можно попасть под алгоритмическую пессимизацию всего домена |
| Полностью закрыть `/w/<slug>` от индексации на MVP (безопаснее) | Убивает единственный SEO-канал FR-GROWTH-005 целиком; страница явно задумана как источник органического трафика, а не только как виджет-контейнер |
| Более высокий порог (например, 10 отзывов) | Не подтверждён исходными документами — превысил бы заданный Specification.md порог без основания; отклонено как выдумывание сверх постановки |

**Последствия**

- Порог — единственная константа, определяющая индексируемость; изменение порога — правка одного
  места (не разбросано по коду рендера страницы).
- Тест-контракт (Specification.md DoD): порог покрыт тестом «в обе стороны» — и на попадание в
  индекс, и на закрытие от индекса.
- Страница остаётся **доступной людям по прямой ссылке** независимо от `noindex` — `noindex`
  влияет только на директиву для поисковых роботов, не на доступность.

## ADR-005: Граница применения Claude API под FTC Rule

**Статус:** Принято (non-negotiable, зафиксировано в PRD §4.4 / Specification.md FR-NFR-SEC-002)

**Контекст**

FTC Rule 16 CFR Part 465 (действует с 21.10.2024) прямо запрещает AI-сгенерированные отзывы и
testimonials; штраф — до $53,088 за нарушение (актуальная сумма; discovery-документ ссылался на
устаревшую цифру 2024 года $51,744 — индексируется ежегодно, PRD это явно фиксирует). Стек проекта
включает Claude API, что создаёт прямой регуляторный риск, если границу применения не закрепить
архитектурно, а не только процессно.

**Решение**

Claude API используется **только** для транскрипции речи видео-отзыва в текст, через единственный
MCP-инструмент `transcribe_video` (см. Architecture.md §2, §5). Архитектурная граница — это набор
доступных инструментов на MCP-сервере: **инструмента «переписать/улучшить/сгенерировать текст
отзыва» не существует в кодовой базе вообще**, а не «существует, но не вызывается в проде».

Правила, вытекающие из решения:

- Текст отзыва, отправленный пользователем, никогда не проходит через Claude API ни в каком виде.
- Транскрипт сохраняется в **отдельное поле** (`testimonials.transcript`, см. Architecture.md §10
  «Канонические имена»), не подменяя и не соседствуя с оригинальным видео как «более авторитетная
  версия».
- Транскрипт помечается на публичной странице как **машинная расшифровка** — явно, не мелким
  шрифтом.
- Будущая функция «сводка по набору отзывов» (упомянута в PRD как разрешённая при явной пометке)
  — вне scope MVP-недели, но если будет реализована, обязана переиспользовать тот же принцип
  явной пометки и не подменять оригинальные тексты.

**Альтернативы**

| Вариант | Почему отклонён |
|---|---|
| Использовать Claude для «лёгкой» грамматической правки транскрипта | Прямо запрещено FR-NFR-SEC-002 («улучшение формулировок автора» — под запретом даже для транскрипта, не только для текстовых отзывов) |
| Не давать MCP-серверу разделение инструментов, полагаться на промпт-инструкцию «только транскрибируй» | Промпт — не архитектурная гарантия: инструкцию можно случайно изменить при рефакторинге, обойти через другой промпт из другого места кода. Отдельный tool с одной обязанностью — гарантия на уровне интерфейса, а не текста |

**Последствия**

- Complience-тест (`@FR-NFR-SEC-002` в Specification.md): опубликованный текст отзыва побайтово
  совпадает с отправленным; ни один вызов Claude API не принимает текст отзыва как вход для
  переписывания. Второй тест реализуем как статическую проверку: единственный экспортируемый
  инструмент `mcp-claude` — `transcribe_video`, вход — `video_url`, а не `testimonial_text`.
- Юридическая граница становится техническим фактом: аудит регулятора может быть отвечен ссылкой
  на код MCP-сервера, а не только на политику компании.

## ADR-006: Идемпотентность обработки платёжных вебхуков

**Статус:** Принято

**Контекст**

FR-GROWTH-002 требует начислять партнёрскую комиссию **ровно один раз** при оплате
(`@FR-GROWTH-002 @security`: «тот же вебхук оплаты приходит повторно с тем же event id → повторное
начисление не происходит»). Повторная доставка вебхука — стандартное поведение платёжных
провайдеров (retry при таймауте/5xx на нашей стороне, at-least-once delivery), а не редкий edge
case. Двойное начисление — прямые финансовые потери и подрыв доверия партнёрской программы FR-GROWTH-004.

**Решение**

Таблица `webhook_events (provider, event_id UNIQUE, payload, processed_at)`. Обработчик вебхука:

1. Пытается `INSERT` строку с `event_id` из тела вебхука.
2. Если `INSERT` конфликтует по уникальному `event_id` (событие уже обработано) — возвращает 200
   немедленно, **не выполняя бизнес-логику повторно**.
3. Если `INSERT` прошёл — выполняет начисление комиссии внутри той же транзакции, что и запись в
   `commissions` (уникальный `payment_event_id` на `commissions` — вторая, независимая гарантия
   на случай гонки внутри самой обработки).

**Альтернативы**

| Вариант | Почему отклонён |
|---|---|
| Проверять «уже начислено?» через `SELECT` перед `INSERT` в `commissions` | Гонка (race condition) между двумя параллельными доставками одного и того же вебхука — `SELECT` может не увидеть ещё не закоммиченную запись от параллельного обработчика. Нужен либо `UNIQUE` constraint (что и выбрано), либо явная блокировка |
| Полагаться на идемпотентность на стороне провайдера (Idempotency-Key при выставлении счёта) | Решает другую проблему (дубликат *запроса на списание*), не защищает от повторной *доставки уведомления* о уже состоявшемся платеже — это разные механизмы у большинства провайдеров |
| Дедупликация по времени (например, «не начислять, если было начисление за последнюю минуту») | Ненадёжно: легитимные быстрые повторные оплаты того же партнёра/клиента дали бы ложный отказ; не даёт строгой гарантии «ровно один раз» |

**Последствия**

- Гарантия «ровно один раз» обеспечивается на уровне схемы БД (`UNIQUE` constraint), а не только
  логикой приложения — соответствует правилу проекта «детерминированная проверка → тест/constraint,
  а не код-ревью-бдительность».
- Провайдер-агностично: решение не привязано к конкретному провайдеру (выбор провайдера — открытый
  вопрос, см. `[GAP]` в Architecture.md §9), контракт `event_id` универсален для Stripe/Paddle/
  аналогов.
- Тест-контракт: интеграционный тест отправляет один и тот же payload дважды подряд, ожидает ровно
  одну строку в `commissions`.

## ADR-007: TLS-терминация и раздача виджета — Caddy

**Статус:** Принято

**Контекст**

Найдено при валидации Architecture (W-3): ADR.md не содержал ни одной записи про TLS, хотя это
решение того же калибра критичности, что ADR-002. Причина, по которой это не «просто нужен
HTTPS», а архитектурная развилка ранга badge-проверки:

Виджет (`<script src="https://cdn.proofwall.app/widget.js">`) загружается на **чужие** сайты
клиентов-владельцев, и подавляющее большинство таких сайтов сами на HTTPS. Если наш домен
(`cdn.proofwall.app` / API `/api/widget/config`) отдаёт `http://`, браузер хоста молча блокирует
запрос как **mixed content** — ни ошибки на экране посетителя, ни исключения в коде виджета, просто
тишина в консоли разработчика. Badge (FR-GROWTH-003, ADR-002) физически не отрендерится ни на одном
внешнем сайте. Badge loop — **единственный** growth-канал продукта (PRD §4.2) — не запустится
вообще, а не деградирует частично. Значит валидный TLS-сертификат на своём домене — не
инфраструктурная деталь, а предпосылка единственного канала роста.

**Решение**

TLS терминируется контейнером **Caddy** перед `web` (docker-compose, §7 Architecture.md). Caddy
получает и обновляет сертификат Let's Encrypt автоматически по одному указанию домена в
`Caddyfile`, без отдельного ACME-клиента и без cron-задачи на обновление. Сертификат хранится в
именованном томе `caddy_data` — переживает пересоздание контейнера при деплое, поэтому обычные
редеплои **не** переиздают сертификат и не расходуют лимиты Let's Encrypt (5 дублирующих
сертификатов на домен в неделю, 50 сертификатов на зарегистрированный домен в неделю).

**Альтернативы**

| Вариант | Почему отклонён |
|---|---|
| **Caddy** (выбрано) | Автоматический HTTPS «из коробки» одной директивой в `Caddyfile`, встроенный ACME-клиент и обновление без отдельного процесса — минимальная поверхность отказа для недели |
| nginx + certbot | Самый документированный вариант, но два независимых процесса (nginx + cron `certbot renew`) вместо одного — классический отказ «сертификат обновился, nginx не перечитал конфиг» требует явного `--deploy-hook`, которого проще не забыть в Caddy, потому что там нет отдельного шага |
| Traefik | Тоже автоматический HTTPS и Docker-native, но ориентирован на динамическую multi-service маршрутизацию (label-based discovery на десятках сервисов) — больше конфигурационной поверхности, чем нужно для одного `web` + виджета за неделю |
| Cloudflare Tunnel | TLS терминируется на границе Cloudflare, портов наружу вообще нет — но это выносит терминацию единственного публичного входа в чужое управляемое облако. Тот же класс конфликта, что уже был решён против Supabase (§9 Architecture.md): Architecture Constraints требуют, чтобы наш стек жил в Docker Compose на своём VPS, а не зависел от внешней managed-платформы на критичном пути |
| Без reverse-proxy (TLS в самом Next.js/Node) | Дублирует функцию Caddy худшим кодом собственного написания: ACME-протокол, хранение/ротацию сертификата и HTTP→HTTPS редирект пришлось бы реализовывать вручную внутри `apps/web` — не оправдано для недели |

**Последствия — включая честный разбор отказа выпуска сертификата**

- **Если Let's Encrypt не может выпустить сертификат** (DNS ещё не указывает на VPS, ACME
  rate-limit исчерпан, временная недоступность Let's Encrypt): Caddy не падает и не блокирует
  остальной стек — он логирует ошибку и **повторяет попытку с экспоненциальным backoff**. До
  первого успешного выпуска порт 443 либо не отвечает, либо отдаёт TLS-handshake ошибку —
  посетитель хост-сайта увидит недоступный `/api/widget/config`, виджет не отрендерится вовсе (тот
  же эффект, что и mixed content, но чуть более заметный в devtools — явная TLS-ошибка). Это
  затрагивает **все** новые проекты сразу, а не деградирует по одному — сигнал для мониторинга,
  а не тихий сбой.
- Поэтому: домен должен резолвиться на VPS **до** первого деплоя (не после) — иначе первая попытка
  ACME-challenge гарантированно провалится и уйдёт в backoff до следующей успешной проверки DNS.
- `caddy_data` не бэкапится (см. §7 Architecture.md) — при потере тома Caddy просто выпускает
  сертификат заново при следующем старте; риск — упереться в еженедельный лимит Let's Encrypt при
  частой потере тома (не ожидается на масштабе недели, один VPS, один редеплой в день максимум).
- Тест-контракт: smoke-проверка после деплоя — `curl -I https://<домен>/api/widget/config` отдаёт
  `200` с валидной TLS-цепочкой, а не ошибку сертификата; проверка гоняется как часть CI-пайплайна
  §8 Architecture.md после `up -d`, до объявления деплоя успешным.
