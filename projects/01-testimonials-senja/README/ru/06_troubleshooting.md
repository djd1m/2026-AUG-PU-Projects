# Устранение неполадок

Все случаи ниже — настоящие, из разработки этого проекта. Общее у них одно: система
выглядит работающей.

## Все выданные ссылки ведут на `localhost:3000`

**Признак.** Регистрация проходит, страницы открываются, тесты зелёные — но ссылка на
форму, витрину или сниппет виджета указывает на машину посетителя.

**Причина.** `BASE_URL` не передан сервису `web` в `docker-compose.yml`. У кода есть
тихий дефолт, поэтому приложение стартует и ни на что не жалуется.

**Проверка и починка.**

```bash
bash scripts/check-env-wiring.sh          # покажет переменные, не доехавшие до сервиса
# добавить BASE_URL в environment сервиса web, затем:
docker compose up -d --build
bash scripts/check-cjm.sh "$BASE_URL"
```

**Почему не поймали раньше.** Проверка UI шла по страницам по отдельности и передавала
переменные через `docker run -e`, минуя compose — то есть ровно тот слой, где был дефект.

## Виджет не грузится ни на одном стороннем сайте

**Признак.** В консоли браузера — ошибка CORS. `curl` при этом отдаёт `200`.

**Причина.** Заголовок `Access-Control-Allow-Origin` ставят **и** Caddy, **и** приложение.
Два одинаковых заголовка браузер отвергает.

**Починка.** Оставить ровно одно место. `curl` для проверки не годится — он не применяет
политику браузера; проверять headless-браузером или вкладкой «Сеть».

## Ограничение частоты обходится

**Признак.** С одного адреса проходит больше 5 отправок в час, если менять
`X-Forwarded-For`.

**Причина.** Сервис `web` опубликован через `ports:`, поэтому Caddy можно обойти, и
«последний элемент `X-Forwarded-For`» становится значением атакующего.

**Починка.** В `docker-compose.yml` у `web` — `expose:`, не `ports:`. Проверка:

```bash
bash ../../scripts/check-port-conflicts.sh .
```

## Тесты падают с `ECONNREFUSED`

**Признак.** Ещё вчера зелёные тесты массово падают на подключении к базе.

**Причина.** `compose.test.yml` и `docker-compose.yml` лежат в одном каталоге, и без
явного `name:` Compose даёт обоим стекам одно имя проекта. Поднятый демо-стенд молча
вытесняет тестовые контейнеры.

**Починка.** В `compose.test.yml` — `name: proofwall-test`. Проверить:
`docker compose -f compose.test.yml ps`.

## `docker compose up` падает на занятом порту

**Причина.** Машина не пустая: `80`, `443`, `8080` и другие обычно уже заняты.

**Починка.** Задать свободные значения **в `.env`**, а не правкой `docker-compose.yml`:

```bash
bash ../../scripts/check-port-conflicts.sh .    # покажет все конфликты сразу
```

Конфликтует только **хостовая** (левая) часть. Номер внутри контейнера менять нельзя —
на него ссылаются `depends_on`, healthcheck и внутренние адреса.

Полагаться на «увижу при запуске» не стоит: Docker называет по одному порту за прогон,
и к этому моменту часть стека уже поднята.

## Видео-отзывы остаются нерасшифрованными

**Признак.** `transcript_status` не выходит из `pending`.

**Причины по частоте:**

1. **Воркер не работает.** `docker compose ps`. Воркер, стартовавший до применения
   миграций, падает; убедиться, что у сервиса есть `restart: unless-stopped`.
2. **Очередь забирает текстовые отзывы.** Если в выборке нет условия
   `video_object_key IS NOT NULL`, текстовый отзыв попадает в очередь, у него нет видео,
   и задание падает вместо того, чтобы взять следующее видео.
3. **`transcribe` не отвечает или нет `OPENAI_API_KEY`.** `docker compose logs transcribe`.

Неудача расшифровки не ломает отзыв: он остаётся валидным и модерируемым.

## Витрина не попадает в поиск

Это может быть **штатным поведением**: страница, где отзывов слишком мало или они
слишком короткие, закрывается от индексации намеренно. Проверить наличие `noindex` в
разметке и число одобренных отзывов.

## Загрузка фото отвергается

Проверяется **содержимое** файла, а не расширение. Отвергаются: файлы не JPEG/PNG/WebP,
больше 5 МБ, и файлы, чьё содержимое не соответствует заявленному типу. SVG запрещён
всегда — это XML-документ, умеющий выполнять код на вашем домене.

## Через 30 дней владелец теряет доступ к кабинету

**Это известное ограничение MVP, а не поломка.**

В системе **нет входа**: маршрута `/api/auth/login` и страницы входа не существует.
Функция проверки пароля написана и покрыта тестами, но не вызывается ниоткуда — пароль
задаётся при регистрации и больше нигде не проверяется.

Доступ к кабинету даёт только cookie сессии, выданная в момент регистрации. Её срок —
**30 дней абсолютных, без продления при активности**. После истечения владелец не может
войти ни по паролю, ни как-либо ещё.

**Обход на сегодня:** зарегистрировать новый проект под новым слагом. Отзывы старого
проекта при этом остаются в базе, но управлять ими будет нельзя.

**Что нужно, чтобы закрыть:** маршрут входа, который вызывает уже существующую
`verifyPassword`, и страница формы. Заведено как `FR-009` в `.claude/feature-roadmap.json`.

**Как это вышло.** `PRD` и `Specification` слова «вход» не содержат — но
`Architecture.md:455` прямо на него опирается («тот же контракт „владелец залогинен →
есть `account_id`“»), а `Refinement.md:188` строит на нём интеграционный тест
(«войти владельцем A»). То есть вход не был сокращён из объёма сознательно — он
**потерян между документами**: архитектура его предполагала, требование не описало,
псевдокод не реализовал.

## За существующим reverse-proxy: пересоздание контейнера рвёт связь с прокси

**Признак.** После `docker compose up -d --build` стенд отвечает `502`, хотя контейнер
здоров и внутри отдаёт `200`.

**Причина.** Подключение сервиса в сеть чужого прокси (`docker network connect`) — это
состояние *контейнера*, а не compose-файла. Пересоздание контейнера его теряет.

**Починка после каждого пересоздания:**

```bash
docker network connect <сеть-прокси> <имя-контейнера-web>
```

Первые секунды после подключения прокси может отвечать `502` — он держит прежний адрес.
Это проходит само; повторить запрос через несколько секунд.

**Почему это не лечится в compose.** Сеть принадлежит чужому проекту, и объявлять её
`external` в нашем `docker-compose.yml` значит сделать наш стек незапускаемым на машине,
где этого прокси нет. Развёртывание за существующим прокси — это ручной шаг, и его
надо помнить.

## Общее правило

Три худших дефекта проекта имели одинаковую форму: **каждый модуль корректен, а дефект
живёт в стыке кода и конфигурации.** Зелёный юнит-тест — утверждение о функции, а не о
системе. Поэтому перед сдачей запускаются проверки, работающие на **развёрнутом** стенде:

```bash
bash ../../scripts/check-port-conflicts.sh .
bash scripts/check-env-wiring.sh
bash scripts/check-cjm.sh "$BASE_URL"
```
