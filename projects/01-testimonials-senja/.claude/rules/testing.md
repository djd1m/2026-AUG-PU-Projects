# Testing Rules — Proofwall

Источники: `docs/Refinement.md` §1, §3, §4, `docs/test-scenarios.md` (BDD). Ladder-правило
проекта: детерминированная проверка — на самый сильный доступный слой (CI/constraint), а не на
ревьюера или на память агента.

## 1. Уровни и распределение (Refinement.md §1)

| Уровень | Что покрывает | Пример |
|---|---|---|
| Unit | Чистые функции: `resolveAttribution`, `recomputeContentThreshold`, `ALLOWED_TRANSITIONS`, валидация полей, расчёт комиссии | Без БД, без сети |
| Integration | API-обработчики с реальной тестовой Postgres: `submitTestimonial`, `moderateTestimonial`, `apiWidgetConfig`, `onPaymentWebhook` (идемпотентность + self-referral), rate limit | `docker compose -f compose.test.yml` |
| E2E | Полный путь: форма → модерация → публичная стена → виджет на внешней странице; регистрация → атрибуция → оплата → комиссия | Браузерный E2E-раннер |

**Принцип:** всё, что выражается как чистая функция вход→выход (переходы состояний, приоритет
промокода, пороги) — юнитом, самый дешёвый и надёжный слой. Всё, что зависит от реальной
БД/вебхука/сети — интеграционно. E2E — только для путей, не валидируемых иначе (SSR-рендер,
поведение виджета в чужом DOM).

**Порядок по риску (не по номеру FR):** прогонять/писать тесты в этом порядке при ограниченном
времени — 1) мульти-арендная изоляция и XSS (данные одного клиента текут в другой аккаунт или
исполняется чужой JS — наивысший риск), 2) идемпотентность вебхука и self-referral (прямые
финансовые потери), 3) badge/тариф на сервере (единственный growth-канал), 4) момент
ценности/гонка на `widget_installs` (метрика недели), 5) остальные growth-механики,
6) граничные случаи форм и NFR (перф, a11y).

## 2. Тестирование виджета на чужой странице (нетривиально, Refinement.md §1.1)

Виджет исполняется в DOM, которым не управляет тестовый раннер. Подход:

1. Собрать тестовую хост-фикстуру с намеренно агрессивными глобальными стилями
   (`* { all: unset !important }`, конфликтующие классы `.badge`/`.container`) и сторонним
   `<script>`.
2. Встроить реальный собранный `widget.js` через `<script data-slug=...>` в эту фикстуру,
   поднятую на **отдельном тестовом origin** (не origin приложения) — обязательное условие: без
   второго origin `currentDomain() == OUR_APP_DOMAIN` и тест не проверит серверную защиту тарифа
   по-настоящему.
3. Проверить: виджет рендерится несмотря на `* { all: unset }` хоста; стили не «текут» ни в
   одну сторону; шрифт/цвет элементов хоста не изменился; `<script>` хоста продолжает работать.
4. На этой же фикстуре — badge-integrity: программно `display:none` на найденном узле badge,
   проверить восстановление в течение заданного числа `setInterval`-тиков.

**Почему не юнит-тест `renderTestimonials` в изоляции:** конфликт стилей — эмерджентное свойство
взаимодействия двух независимо написанных DOM-деревьев; юнит не обнаружит совпадение имён
классов виджета и хоста.

## 3. Гонка на `widget_installs` (момент ценности + метрика недели, Refinement.md §3.2)

Обновлено по решению PRD §2.4.1: обе метрики — одна уникальность `(project_id, domain)`.

1. Проект с ≥1 approved отзывом, без записи в `widget_installs`.
2. `recordInstallAndInviteIfNeeded(slug, "external-domain.test")` **параллельно** из N≥10
   конкурентных вызовов на **один и тот же** домен.
3. Проверить: ровно одна строка `(project_id, domain)`; `widget_installed` и `invite_shown`
   эмитированы ровно по одному разу — атомарность `INSERT ... ON CONFLICT DO NOTHING`, не
   `exists()`-проверка.
4. **Второй домен того же проекта** — НОВАЯ пара событий ожидается (регресс-барьер против
   отменённой версии решения «invite_shown раз на проект»).
5. Повторный вызов на уже известном домене — ни одного события, только `last_seen_at`.
6. `domain == OUR_APP_DOMAIN` (онбординг/дашборд) — не создаёт запись, не эмитирует события.

## 4. Индексируемость `/w/<slug>` — проверять в обе стороны (Refinement.md §3.4)

1. 2 approved отзыва, `noindex=true` → одобрить 3-й, суммарно ≥400 символов → `noindex=false` +
   `audit_log(noindex_removed)`.
2. Обратный переход: из `noindex=false` при 3 отзывах скрыть один до 2 → `noindex=true` +
   `audit_log(noindex_applied)`.
3. Граница: ровно 400 символов индексируется, 399 — нет.
4. E2E — реальный HTTP-запрос проверяет `<meta name="robots" content="noindex">` в отданном
   HTML, не только состояние в БД (баг «в БД false, но шаблон вставил тег» — реальный класс
   ошибки, не гипотетический).

## 5. Приоритет промокода над cookie — таблица случаев (Refinement.md §3.3)

Юнит-тест `resolveAttribution` (чистая функция, без БД):

```
{cookie: A, promo: B}       → source=promo_code, partner=B
{cookie: A, promo: none}    → source=cookie,     partner=A
{cookie: none, promo: B}    → source=promo_code, partner=B
{cookie: none, promo: none} → source=null
{cookie: A, promo: invalid} → source=null   # невалидный код НЕ откатывается на cookie
```

Плюс интеграционный тест полного пути `onSignup → onPaymentWebhook` с расходящимися cookie и
промокодом — комиссия должна начислиться партнёру из промокода.

## 6. XSS при рендере на чужом домене (Refinement.md §3.5)

1. Одобрить отзыв с `text = "<img src=x onerror=alert(document.domain)>"`,
   `author_name = "<script>window.__xss=true</script>"`.
2. E2E на фикстуре §2 (второй origin): открыть `/w/<slug>` и отдельно загрузить виджет — в обоих
   случаях `window.__xss` не установлен, `alert` не вызван.
3. Проверить не только неисполнение, но и **видимость как текста** — `<img src=x onerror=...>`
   должен отображаться как строка, а не исчезать молча (см. `.claude/rules/security.md` §1).
4. Юнит-тест функции экранирования — дополнительный быстрый слой, НЕ замена пунктам 1-3:
   исполнение JS зависит от контекста рендера (Shadow DOM vs SSR), не только от экранирования строки.

## 7. Межпроектный доступ (Refinement.md §3.6)

Оба пути обязательны, покрытие одного не закрывает инвариант FR-NFR-SEC-001:

1. Виджет: `GET /api/widget/config?slug=<A>&domain=...` — в ответе нет отзывов проекта B.
2. Модерация (аутентифицированный путь): владелец A пытается изменить отзыв B — `403` +
   `audit_log(moderation_denied_cross_project)`.
3. Подмена параметров: анонимный запрос с `project_id` вместо `slug` — API его не принимает.

## 8. Производительность виджета — CI-гейт, не ручная проверка (Refinement.md §4)

| Метрика | Порог | Как измерять |
|---|---|---|
| Размер бандла | ≤30 KB gzip | CI: собрать, `gzip -9`, сравнить с порогом — провал сборки при превышении |
| Блокировка рендера хоста | Не блокирует | E2E: `DOMContentLoaded` хоста не ждёт `widget.js` |
| p95 отрисовки | ≤300 мс | N≥30 прогонов (правило «не мерить на выборке <30» из PRD применимо и здесь), 95-й перцентиль |
| Таймаут конфигурации | 300 мс | Искусственная задержка ответа → `renderEmptyPlaceholder`, не подвисание |

## 9. Definition of Done для growth-FR (Completion.md §3)

Ни один `FR-GROWTH-00N` не считается done при частичном закрытии — тесты есть, а метрика не
инструментирована, не засчитывается. Обязательно для каждого: AC покрыты автотестами, события
аналитики пишутся, `@security`-сценарий имеет тест и митигацию, метрика инструментирована **до**
подписания Completion.md (постфактум события не восстанавливаются).
