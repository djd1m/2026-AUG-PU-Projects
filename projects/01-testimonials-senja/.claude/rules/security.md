# Security Rules — Proofwall

Источники: `docs/Specification.md` §3 (NFR), `docs/ADR.md` (ADR-002, ADR-005, ADR-006),
`docs/Architecture.md` §3.1/§3.4. Non-negotiable пункты помечены явно — не открываются заново
на код-ревью, только проверяются на соответствие.

## 1. XSS: экранирование на рендере, не на приёме (FR-002/003/005/006)

**Правило (Specification.md, буквально):** приём (`submitTestimonial`) сохраняет `text`,
`author_name`, `author_role` **побайтово как отправлено**, без санитизации и без отклонения по
этой причине. Экранирование выполняется **только** при рендере — на публичной странице
`/w/<slug>` (SSR) и внутри виджета на произвольном чужом домене.

- Это условие побайтового совпадения из FR-NFR-SEC-002 — санитизация на приёме исказила бы
  опубликованный текст относительно отправленного, что нарушило бы FTC-инвариант «текст не
  изменяется системой». Не «забыли санитизировать», а осознанное разделение ответственности.
- На рендере — два независимых места, оба обязаны экранировать: SSR-шаблонизатор
  `serverRenderTemplate` (FR-005) и клиентский рендер внутри shadow-root (FR-006, FR-006 требует
  безопасный DOM-API — `textContent`, не `innerHTML`, для текста отзыва).
- `schema.org/Review` разметка на каждом отзыве не должна содержать неэкранированный
  пользовательский HTML.
- Тест-контракт (Refinement.md §3.5): не только неисполнение JS, но и **корректное отображение**
  как текста — `strip_tags` вместо экранирования прошёл бы тест на неисполнение, но незаметно
  испортил бы легитимные отзывы с символами `<`/`&`.

## 2. Мульти-арендная изоляция — держится на коде для анонимных путей (FR-NFR-SEC-001)

**Два независимых места, оба обязательны (defense in depth, Architecture §3.1):**

1. **Аутентифицированный дашборд-путь** (роль `app_authenticated`): RLS-политика на каждой
   таблице с `project_id` + `SET LOCAL app.current_account_id` в начале транзакции. `SET LOCAL`
   действует только внутри текущей транзакции — следующий запрос из пула не наследует контекст.
2. **Анонимные пути — форма, виджет, Wall of Love** (роль `app_service`, `BYPASSRLS`): RLS
   **осознанно обходится**, изоляция — обязанность кода обработчика. Каждый запрос резолвит
   `slug → project_id` и фильтрует `.where('project_id', projectId).where('status','approved')`.
   **Ни один анонимный роут не принимает `project_id` от клиента, только `slug`.**

Регресс сюда — критичная уязвимость, не стилистическое замечание: `app_service` использует
`BYPASSRLS`, поэтому единственная защита на этом пути — фильтр в коде. Если проверка забыта, RLS
её не подстрахует.

Тест-контракт: интеграционный тест «проект A не может прочитать/изменить данные проекта B»
гоняется **через оба** пути — аутентифицированный (403 + `audit_log(reason='cross_project')`) и
анонимный (подмена `project_id` в query/теле запроса игнорируется).

## 3. Подпись платёжного вебхука — до идемпотентности, секрет в env (ADR-006, FR-GROWTH-002)

Порядок в `onPaymentWebhook` принципиален, не переставлять:

1. Проверка HMAC-подписи от **сырого тела** запроса (`raw_body`, не пере-сериализованный JSON —
   любая пере-сериализация ломает подпись), сравнение — **константным по времени** (не `==`,
   защита от timing-атаки). Невалидная подпись → `HTTP 400`, запрос отклоняется **до** парсинга
   JSON и до любой записи в БД.
2. Только после успешной проверки подписи — проверка идемпотентности по `event_id`
   (`webhook_events(provider, event_id UNIQUE)`).

**Почему порядок принципиален:** если сначала записать `event.id`, а подпись проверить после,
злоумышленник шлёт поддельный вебхук с угаданным id → мы его записываем как обработанный →
настоящий вебхук с тем же id отбрасывается как дубль, комиссия не начисляется никогда.

`PAYMENT_WEBHOOK_SECRET` — переменная окружения `web` (роут физически исполняется в `apps/web`,
Architecture §3.5), а не только `mcp-claude`. Секреты — только имена переменных в
docker-compose, значения — в `.env`/CI secrets, никогда не коммитятся.

Self-referral (партнёр платит по своему коду) блокируется независимо от источника атрибуции —
`audit_log(reason='self_referral')`, комиссия не начисляется.

## 4. Rate limiting — единый механизм на три требования (Architecture §3.4)

Одна таблица `rate_limit_events(scope, key, created_at)`, без Redis (масштаб недели не
оправдывает 4-й контейнер). Не заводить отдельный стор под новое requirement того же класса
«не более N событий за интервал T по ключу» — расширять `scope`:

| Requirement | scope | key | окно | порог |
|---|---|---|---|---|
| FR-NFR-SEC-003 (форма) | `form_submission` | `ip`+`project_id` | 1 час | 5 |
| FR-GROWTH-004 (партнёрский код) | `signup_via_partner_code` | `ip` | 10 мин | 50 |
| FR-GROWTH-005 (создание проектов) | `project_created` | `account_id` | 1 час | 20 |

Все пороги — эвристики авторов документа, явно помечены как подлежащие калибровке на реальных
данных (не выдумывать более «обоснованные» числа при реализации — использовать заданные).

## 5. FTC-граница применения Claude API — non-negotiable (ADR-005, PRD §4.4)

Штраф FTC Rule 16 CFR Part 465 (действует с 21.10.2024) — до **$53,088** за AI-сгенерированный
отзыв/testimonial.

| ✅ Разрешено | ❌ Запрещено |
|---|---|
| Транскрипция речи видео-отзыва в текст | Генерация текста отзыва |
| Теги, поиск, сортировка | «Улучшение» формулировок автора, в т.ч. лёгкая грамматическая правка транскрипта |
| Сводка по набору отзывов **с явной, видимой без доп. действий пометкой** (вне scope MVP-недели — не реализовывать сейчас) | Переписывание отзыва от лица клиента |

**Архитектурная граница, не процессная:** единственный экспортируемый MCP-инструмент
`services/mcp-claude` — `transcribe_video(video_url) → text`. Инструмента, принимающего текст
отзыва как вход для переписывания, не должно существовать в кодовой базе. Не полагаться на
промпт-инструкцию «только транскрибируй» — промпт можно случайно изменить при рефакторинге.

Инвариант, проверяемый тестом: опубликованный текст отзыва побайтово совпадает с отправленным;
ни один вызов Claude API не принимает `testimonial.text` как вход. Транскрипт — отдельное поле
`testimonials.transcript`, помечается на публичной странице как **машинная расшифровка**, явно,
не мелким шрифтом (см. код-ревью чек-лист по FR-NFR-SEC-002 сц.3 в `.claude/agents/code-reviewer.md`).

`ANTHROPIC_API_KEY` — переменная окружения только `services/mcp-claude`, не `apps/web`/`worker`.

## 6. Anti-tamper badge — что детектируется, что нет (ADR-002)

`checkAndRestore` восстанавливает видимость **самого узла badge** при точечном изменении
`style`/`hidden`. Сокрытие **родительского контейнера целиком** (`display:none` снаружи
shadow-host) технически неотличимо от отсутствия виджета — это признанный остаточный риск, не
баг реализации. Не пытаться «дотянуться» до DOM хоста выше собственного shadow-root — это
архитектурная граница (ADR-001), не пробел в этой конкретной функции.
