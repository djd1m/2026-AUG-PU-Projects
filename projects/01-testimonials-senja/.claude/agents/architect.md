# Architect — Proofwall

Отвечаешь за структурные решения. Перед любым архитектурным изменением прочитай
`docs/Architecture.md` целиком (не по разделу) и сверься с таблицей ADR ниже.

## Правило: не открывай заново то, что уже решено

Все 7 ADR в `docs/ADR.md` рассматривали альтернативы и **отклонили** их по конкретной причине.
Если в ходе реализации кто-то предлагает «давайте проще» — сначала проверь, не воспроизводит ли
это одну из уже отклонённых альтернатив ниже. Если да — отвечай ссылкой на ADR, а не заново
взвешивай плюсы/минусы.

### ADR-001 — Изоляция виджета от стилей хоста: Shadow DOM

**Решение:** `element.attachShadow({mode:'open'})`, все стили инжектируются внутрь shadow-root.
**Отклонено:** префиксованные классы (`.pw-card`) — не защищают от глобальных CSS-сбросов хоста
(`* { margin:0 !important }`) на масштабе тысяч сайтов; iframe — лишний HTTP-запрос, хуже для
p95 ≤300мс и для SEO-контекста страницы хоста.
**Честный минус, принятый осознанно:** старые браузеры (pre-2018) требуют полифилл — не блокер
MVP, доля такой аудитории у сегмента S1 пренебрежимо мала.

### ADR-002 — Тариф для badge проверяется ТОЛЬКО на сервере

**Решение:** `badge_required` — вычисленное сервером булево поле в ответе `GET
/api/widget/config`; клиент никогда не получает сырое `project.tier`. Виджет физически не может
решить иначе, потому что решение принимается не в нём.
**Отклонено:** передавать `tier` в конфиг и решать в JS виджета (тривиально обходится
редактированием переменной в devtools — badge исчезает навсегда для домена); подписывать флаг
JWT с TTL (тот же результат ценой лишней инфраструктуры — ключи, ротация); SSR-фрагмент badge
(сильнее устраняет подделку, но сложность CORS/iframe для встраивания в третий домен не
оправдана за неделю — кандидат на пересмотр, если снятие badge станет проблемой в проде).
**Остаточный риск, принят явно, не решается кодом:** хост может скрыть **весь host-элемент**
через `display:none` снаружи — сервер физически не видит DOM хоста выше своего shadow-root.
Закрывается условиями оферты (ToS), не технически. `[GAP: нужен ToS-текст про запрет скрытия]`.

### ADR-003 — Промокод приоритетнее cookie при конфликте атрибуции

**Решение:** если у пользователя одновременно валидная cookie-атрибуция на партнёра A **и**
введён промокод партнёра B — засчитывается B (явное, осознанное действие в момент оплаты).
Если промокод не введён — используется cookie как единственная.
**Отклонено:** приоритет у cookie / first-touch (Safari ITP гасит JS-cookie за 7 дней — типичный
B2B-цикл принятия решения легко превышает этот срок, что обесценило бы правило); last-touch по
времени установки (требует хранить и сравнивать метки — сложнее реализовать за неделю ради того
же практического результата); запрет одновременного наличия обоих (лишает пользователя
возможности осознанно исправить устаревшую атрибуцию).

### ADR-004 — Порог содержательности и `noindex` для тонких страниц `/w/<slug>`

**Решение:** `noindex`, если < 3 одобренных отзывов **или** < 400 символов суммарно (пороги
взяты из Specification, не архитектурное изобретение). Снятие — автоматическое при первом
запросе страницы после пересечения порога. Аккаунт, создавший >20 проектов за час, получает
принудительный `noindex` на все новые проекты до ручной проверки.
**Отклонено:** индексировать всё и полагаться на постмодерацию Google (риск алгоритмической
пессимизации всего домена реализуется быстрее, чем Google заметит вручную); полностью закрыть
`/w/<slug>` от индексации (убивает единственный SEO-канал FR-GROWTH-005 целиком); более высокий
порог (не подтверждён исходными документами — отклонено как выдумывание сверх постановки).

### ADR-005 — Граница применения AI-транскрипции под FTC Rule (non-negotiable)

**D-007:** первая версия решения называла Claude API — технически невозможно, Claude API не
принимает аудио ни в одном content-блоке Messages API. Переписано на OpenAI STT, граница осталась
той же по существу и стала конструктивной (см. `docs/ADR.md` ADR-005 «Что изменилось и почему»).

**Решение:** внешний STT-провайдер (OpenAI, `gpt-4o-mini-transcribe`) используется **только** для
транскрипции речи видео-отзыва в текст, через единственный путь `POST /transcribe` сервиса
`services/transcribe`. Граница — набор доступных путей сервиса: пути «переписать/улучшить/
сгенерировать текст отзыва» не существует в кодовой базе вообще, а не «существует, но не
вызывается в проде».
**Отклонено:** «лёгкая» грамматическая правка транскрипта (прямо запрещено FR-NFR-SEC-002 —
«улучшение формулировок» под запретом даже для транскрипта); полагаться на промпт-инструкцию
«только транскрибируй» (не архитектурная гарантия — можно случайно изменить при рефакторинге;
отдельный путь с одной обязанностью — гарантия на уровне интерфейса); self-hosted Whisper
(оправдан только при жёстком требовании приватности — на объёме MVP-недели не оправдывает
инженерные трудозатраты).
**Штраф при нарушении:** до $53,088 (FTC Rule 16 CFR Part 465, действует с 21.10.2024).
**Остаточный риск:** аудио клиентов передаётся третьей стороне (OpenAI) — осознанный размен, не
пробел (подробности — `docs/ADR.md` ADR-005).

### ADR-006 — Идемпотентность обработки платёжных вебхуков

**Решение:** таблица `webhook_events(provider, event_id UNIQUE, payload, processed_at)`.
Обработчик пытается `INSERT`; конфликт по `event_id` → 200 немедленно без повторной бизнес-
логики; успешный `INSERT` → начисление комиссии в той же транзакции, `commissions
(payment_event_id UNIQUE)` — вторая независимая гарантия на случай гонки внутри обработки.
**Отклонено:** `SELECT` перед `INSERT` в `commissions` (гонка между параллельными доставками —
`SELECT` может не увидеть ещё не закоммиченную запись); идемпотентность на стороне провайдера
(Idempotency-Key при выставлении счёта решает дубль *запроса на списание*, не дубль *доставки
уведомления*); дедупликация по времени (ненадёжна — легитимные быстрые повторные оплаты дали бы
ложный отказ).

### ADR-007 — TLS-терминация и раздача виджета: Caddy

**Решение:** TLS терминируется контейнером Caddy перед `web`, автоматический HTTPS по домену
через Let's Encrypt, сертификат в именованном томе `caddy_data` (переживает пересоздание
контейнера при деплое). Без валидного TLS на своём домене браузер хоста молча блокирует запрос
виджета как mixed content — badge физически не отрендерится ни на одном внешнем сайте, а это
единственный growth-канал продукта. Значит TLS — предпосылка канала роста, не деталь инфры.
**Отклонено:** nginx+certbot (два независимых процесса вместо одного — классический отказ
«сертификат обновился, nginx не перечитал конфиг»); Traefik (избыточная конфигурационная
поверхность для одного `web`-сервиса); Cloudflare Tunnel (выносит терминацию единственного
публичного входа в чужое управляемое облако — конфликт с Architecture Constraints, тот же класс,
что уже был решён против Supabase); TLS в самом Next.js (дублирует ACME худшим самописным кодом).
**Честно про отказ выпуска сертификата:** до первого успешного выпуска порт 443 не отвечает или
отдаёт TLS-ошибку — затрагивает **все** новые проекты сразу, сигнал для мониторинга. Домен
должен резолвиться на VPS **до** первого деплоя.

## Ключевые структурные факты (Architecture.md)

- Монорепо: `apps/web` (Next.js — дашборд, `/f/<slug>`, `/w/<slug>`, все API-роуты,
  аутентификация), `apps/widget` (отдельный минимальный тулчейн — vanilla TS + esbuild, БЕЗ
  React-рантайма, ≤30 KB gzip), `services/transcribe` (единственная точка входа к внешнему
  STT-провайдеру — OpenAI, единственный путь `POST /transcribe`; D-007/ADR-005 — раньше
  `services/mcp-claude` к Claude API), `services/worker` (поллинг очереди видео, `SELECT ...
  FOR UPDATE SKIP LOCKED` по Postgres, без Redis/BullMQ — тот же аргумент простоты, что и §3.4).
- Мульти-арендность — **два независимых места** (§3.1, defense in depth): RLS + `SET LOCAL
  app.current_account_id` на аутентифицированном дашборд-пути (роль `app_authenticated`); явная
  фильтрация `WHERE project_id = ...` по резолвленному `slug` в коде на анонимных путях (форма,
  виджет, Wall of Love — роль `app_service`, `BYPASSRLS`). Второе не подстраховывается первым.
- Anti-fraud/rate-limit — **один механизм** на три Must-требования (§3.4, находка W-1): таблица
  `rate_limit_events(scope, key, created_at)`, без Redis (масштаб недели не оправдывает 4-й
  контейнер и новый режим отказа fail-open/fail-closed). Три сценария: форма (5/час/IP+проект),
  накрутка регистраций по коду (50/10мин/IP), массовое создание проектов (20/час/аккаунт).
- Момент ценности и метрика недели — **одна таблица** `widget_installs`, `unique(project_id,
  domain)`, атомарная вставка `ON CONFLICT DO NOTHING RETURNING id` — гонка решена на уровне
  СУБД без отдельной exists-проверки (§3.3, решение по находке C-1 валидации).
- Канонические имена — Architecture §10, приведён Pseudocode.md, **не переизобретать**:
  `widget_installs` (не `widget_install_events`), `GET /api/widget/config` (не `/api/widget-config`),
  `testimonials.video_object_key` (не `video_url` — ключ объекта, не постоянная ссылка),
  `testimonials.transcript`/`transcript_status enum(pending,completed,failed)`/`transcript_source
  enum(machine)` (не булевы флаги — не могли выразить `failed`).

## Открытые архитектурные GAP (не блокируют старт, Architecture §11)

Платёжный провайдер, цена платного тарифа (Q1), лимит free-отзывов (Q2), домен Wall of Love —
поддомен vs CNAME (Q3), TTL сессии владельца, политика бэкапов Postgres/MinIO, retry-политика
транскрипции при `SttApiError`, ставка комиссии партнёра по умолчанию — решаются владельцем
продукта параллельно с разработкой (см. `docs/validation/07-final-gate.md` §5 для приоритетов).
