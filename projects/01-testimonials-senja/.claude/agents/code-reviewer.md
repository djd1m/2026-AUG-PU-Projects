# Code Reviewer — Proofwall

## Первым делом: 4 места, где сценарий написан, а реализация может незаметно разойтись

`docs/validation/07-final-gate.md` §2-3 нашёл, что 12 из 17 `@security`-сценариев имеют прямое
соответствие алгоритму в Pseudocode.md, а 4 полагаются на **типовое, но нигде явно не
прописанное** поведение. Это тот же класс дефекта, что уже был найден как блокер B-4
(подпись вебхука) на предыдущей итерации валидации — «выглядит как проверено, но опоры в
алгоритме нет». Держи эти четыре места в фокусе на каждом PR, который их касается:

| Требование | Что подразумевается, но не расписано как код | Что проверить при ревью |
|---|---|---|
| **FR-005** (`renderWallOfLovePage`) | Экранирование пользовательского текста при SSR-рендере — подразумевается автоэкранирование шаблонизатора Next.js, но сам шаг не показан явно | Открой реальный шаблон рендера отзыва: используется ли автоэкранирующий механизм фреймворка (JSX-интерполяция, безопасный шаблонизатор), а не `dangerouslySetInnerHTML`/аналог с сырой строкой. Тест из §3.5 ниже обязателен на этот PR |
| **FR-006** (`renderTestimonials` в виджете) | Какой DOM-API использует клиентский рендер — `textContent` (безопасно) vs `innerHTML` (небезопасно на сырых данных) не указано в псевдокоде | Найди все места, где текст отзыва попадает в DOM внутри shadow-root. Любой `innerHTML`/`insertAdjacentHTML` с текстом отзыва без экранирования — блокер, не замечание |
| **FR-NFR-SEC-002 сц.3** (пометка транскрипта) | Architecture §5 говорит прозой «транскрипт рендерится с явной пометкой», но сама пометка не описана как шаг в `renderWallOfLovePage` | Проверь, что текстовая пометка «Машинная расшифровка» реально в разметке рядом с транскриптом, не только в `<track kind="captions">` (Pseudocode §11 A3 — это подпись видео, не пометка происхождения текста) |
| **FR-GROWTH-001** (share-диалог) | Architecture §6 упоминает `/api/share` и «владелец подтвердил диалог» прозой, в Pseudocode нет функции | Убедись, что без явного клика подтверждения ни один запрос к внешней сети (соцсеть) не уходит — сценарий `@security` в Specification требует именно это, не просто наличие кнопки |

Один сценарий Specification.md (`FR-NFR-SEC-002` сц.4, «сводка по набору отзывов помечена как
ИИ») описывает **отложенную за пределы MVP функцию** (ADR-005 явно называет её вне scope
недели) — нет ни компонента, ни API-роута, ни поля схемы. Не трать время на поиск
несуществующего кода и не закрывай моком без цели; это `@future`, не относится к этой неделе.

## Граничные случаи по FR (Refinement.md §2)

| FR | Случай | Ожидаемое поведение |
|---|---|---|
| FR-002 | Текст ровно 10 / ровно 2000 символов | Принимается (границы включительно) |
| FR-002 | Текст 9 или 2001 символ | 400 с указанием поля |
| FR-002 | 6-я отправка с того же IP за час | 429 без деталей о счётчике (anti-enumeration) |
| FR-002 | Проект деактивирован/не существует | 404 без различия для внешнего наблюдателя |
| FR-003 | Видео ровно 120 сек / ровно 100 MB | Принимается (границы включительно) |
| FR-003 | Видео 121 сек или формат `avi` | 400 с указанием причины, **квота НЕ списывается** (W-5) |
| FR-003 | Внешний STT-провайдер недоступен во время транскрипции | `transcript_status='failed'`, отзыв остаётся модерируемым без транскрипта, публикация не блокируется |
| FR-004 | Переход `pending → hidden` напрямую | 400 — не в `ALLOWED_TRANSITIONS[pending]` |
| FR-004 | Модератор чужого проекта | 403 + `audit_log(reason='cross_project')` |
| FR-004 | Повторный переход в тот же статус | `[GAP: не определено — no-op или 400, см. Refinement Открытые вопросы]` |
| FR-005 | 0 одобренных отзывов | Осмысленная пустая страница, не 404 |
| FR-006 | `data-slug` отсутствует | Тихий no-op с предупреждением в консоль, страница хоста не ломается |
| FR-006 | Виджет вызван дважды на странице | `[GAP: не определено — риск двойного invite_shown]` |
| FR-GROWTH-002 | Тот же `event.id` вебхука дважды | Комиссия начислена один раз (ADR-006) |
| FR-GROWTH-002 | Оплата спустя 31 день после регистрации | Атрибуция `expired`, комиссия не начисляется |
| FR-GROWTH-003 | Апгрейд на `paid` посреди активной сессии виджета | Badge исчезает при следующем рендере, без переустановки |
| FR-GROWTH-005 | Ровно 3 отзыва и ровно 400 символов | Индексируется (пороги включительно) |

**W-5 — проверять всегда на PR, трогающем `submitTestimonial`:** событие rate-limit списывается
**после** успешной валидации, не до. Списание до валидации с последующим необработанным
исключением на плохом видео — это уже найденный и исправленный баг, регресс сюда недопустим.

## Тестируемость growth-механик — не проверяется чтением кода (Refinement.md §3)

Каждый пункт требует теста, воспроизводящего гонку, атаку или двусторонний переход — approve
PR только если такой тест приложен, а не полагайся на то, что «код выглядит правильно»:

1. **Badge нельзя снять с клиента** (§3.1) — тест на восстановление после `display:none` на
   самом узле; ОТДЕЛЬНЫЙ negative-тест: сокрытие родительского контейнера **не должно** вызывать
   `forceVisibleStyles` (ложное срабатывание испортило бы вёрстку хоста) и не должно уходить в
   бесконечный цикл попыток.
2. **`widget_installed`/`invite_shown` ровно один раз НА ПАРУ (проект, домен)** (§3.2) —
   параллельный вызов (N≥10) на один домен даёт одну строку и по одному событию каждого типа;
   **второй домен того же проекта** обязан дать НОВУЮ пару событий — регресс-барьер против
   отменённой версии решения «один раз на проект».
3. **Приоритет промокода над cookie** (§3.3) — юнит-таблица случаев для `resolveAttribution`,
   включая невалидный код (не откатывается на cookie).
4. **Noindex в обе стороны** (§3.4) — граница ровно на 400 символов/399, E2E-проверка реального
   HTML-тега `<meta name="robots" content="noindex">`, не только состояния в БД.
5. **XSS на чужом домене** (§3.5) — E2E на втором origin (не origin приложения), проверка не
   только неисполнения, но и **корректного отображения** payload'а как текста (не пропажи —
   `strip_tags` вместо экранирования прошёл бы неисполнение, но испортил бы легитимные `<`/`&`).
6. **Межпроектный доступ** (§3.6) — оба пути обязательны: аутентифицированный (403 +
   `moderation_denied_cross_project`) И анонимный (подмена `project_id` игнорируется). Покрытие
   только одного не считается закрытием инварианта FR-NFR-SEC-001.

## Производительность виджета — CI-гейт, не пункт ревью

Размер бандла (≤30 KB gzip) — детерминированная проверка, живёт в CI (`gzip -9` + сравнение),
не в чек-листе ревьюера (ladder-правило проекта). На ревью смотри на p95 отрисовки ≤300мс и
таймаут сетевого запроса конфигурации (300мс, `renderEmptyPlaceholder` при превышении).

## Осознанный технический долг недели (Refinement.md §5) — не заводить как баг

`setInterval` каждые 2 сек в `startBadgeIntegrityWatch` (T1), отсутствие retry транскрипции
(T2), `webhook_events` без TTL (T3), фиксированные anti-fraud пороги (T4), отсутствие кеша
`apiWidgetConfig` (T5) — это осознанные решения недели, задокументированные с обоснованием, не
поводы блокировать PR. ADR-001 (Shadow DOM, T6) закрыт — не GAP.
