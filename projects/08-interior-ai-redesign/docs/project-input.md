# N8 — действующий вход для p-replicator

Исходник: `start/REPLICATE-PROMPTS-PROJECTS.md`, раздел 08.
Уточнения владельца: 2026-10-13. Этот документ заменяет конфликтующие ограничения
исходного промпта для N8. Прежние исключения подбора товаров, планировщика и 3D-тура
не действуют; GPU/ControlNet не является заранее обязательным способом генерации.

## Продукт и расширенный CJM

Помощник по ремонту: обмеры/план → референсы → варианты дизайна → согласование →
конкретные товары → бюджет → пересмотр при изменении цены, наличия или пожеланий.
Три CJM показывают расширенный продукт. Владелец выбрал самый близкий к gist путь A
и разрешил продолжить SPARC, валидацию, toolkit и реализацию без ожидания второго approval.
Основной CJM и оптимальный ориентир — https://gist.github.com/djd1m/3dd228d9f6b09b5249dfb35bfdc59aeb .
Первичный клиент — человек, делающий ремонт для себя. Все три варианта относятся
к этому сегменту и сохраняют путь из gist. Партнёрские программы с крупными
строительными магазинами — позже; подбор товаров не требует такой партнёрки.

- Обмеры: Scaniverse https://apps.apple.com/us/app/scaniverse-3d-scanner/id1541433223
  или готовый план. Проверить форматы экспорта, масштаб и точность; не предполагать GLB.
- Референсы: Pinterest API при доступе или публичные страницы, включая
  https://ru.pinterest.com/pin/1117807570051119485/ . Проверить доступность и условия;
  предусмотреть загрузку изображений пользователем.
- Доступ к ценам: рассмотреть web scraping как альтернативу API. Проверить публичные
  карточки, structured data, robots/условия, регион/магазин, частоту обновления и
  стабильность парсинга. Не обходить авторизацию, CAPTCHA и блокировки. API, scraper
  и ручное подтверждение — адаптеры одного контракта; сохранять источник и timestamp.
- Товары и бюджет: крупные строительные магазины России. Исследовать текущие
  эквиваленты OBI и Leroy Merlin/Лемана ПРО, каталоги, API, региональные цены,
  наличие, количество, единицы, запас материалов, доставку и дату актуальности.
- LLM для анализа и управления 3D-моделированием: наиболее подходящая подтверждённая
  модель Gemini через OpenRouter. Выбор конкретного ID — после исследования.
  Отдельно обосновать получение геометрии, визуализацию и контроль размеров;
  способность генерировать точную 3D-модель не считать доказанной заранее.
- Сохранение геометрии остаётся обязательным критерием качества. Изменение стен,
  окон, дверей или масштаба без согласования — дефект. Обещание 25 секунд проверить.
- Сохранить сравнение до/после, историю вариантов, монетизацию и growth-механики
  исходного промпта; порядок оплаты и публикацию пользовательских материалов
  проработать в CJM.

## Обязательный поиск и переиспользование перед кодированием

Для КАЖДОЙ фичи, требующей нового кода:

1. Сначала исследовать готовый или похожий код проектов 1–7 на этом VPS.
   Проверить также варианты проектов 03a и 05a. Отсутствующие checkout явно отметить.
2. Затем обязательно выполнить поиск подходящих open-source решений на GitHub,
   даже если локальный кандидат найден; не превращать поиск в бесконечное сравнение.
3. Зафиксировать кандидатов, точные пути/ревизии, лицензии, пригодность, ограничения
   и решение: reuse, adapt или new с конкретным обоснованием.
4. Проверить совместимость контрактов, схем, ролей, секретов, конфигурации и тестов.
   Не копировать окружение, credentials и специфичные для донора бизнес-правила.
5. Максимально переиспользовать пригодные модули аутентификации, личного кабинета,
   оплаты, партнёрки, очередей, хранения файлов и прочих общих возможностей.
   Сначала адаптер/композиция существующего модуля, новый код — для подтверждённого пробела.
6. Делать N8 модульным, с явными интерфейсами. Не менять донорские проекты без
   отдельно согласованного scope; не строить общий фреймворк без конкретной потребности.

## Обязательный anti-drift после каждой реализованной фичи

После реализации и обязательных проверок, до завершения фичи: отдельный ревьюер
проверяет точную ревизию спецификации → код → тесты/сценарии. Проверка двусторонняя:
каждый FR/NFR/AC имеет реализацию и доказательство, каждое добавленное поведение
имеет основание в согласованной спецификации. Сверять также ADR, интерфейсы,
ошибки, роли, лимиты и соответствующий CJM; зелёные тесты сами по себе не доказывают соответствие.
Отчёт содержит ID требования, код/символ, тест или другое доказательство,
результат и конкретные расхождения. Не выдавать неисполненный сценарий за pass.
При расхождении владелец разрешил координатору автономно выбрать исправление кода
или изменение спецификации по смыслу задачи, качеству и доказательствам. Каждое решение
фиксировать: before/after, затронутые ID, причина, альтернатива, ревизии и проверки.
Обновить трассировку и повторить затронутые обязательные проверки. Отклонение без
решения и доказательства блокирует завершение. Нельзя молча подгонять спецификацию
под код или выдать ослабленные проверки за успех. Ожидание апрува CJM отменено последующим прямым разрешением владельца.
После устранения drift — teach/reinforce
подтверждённых уроков и передача результата.

## Обязательный цикл обучения

- До исследования и каждой фичи: `dz recall` по предметным ключевым словам;
  перед ревью — recall по соответствующим рискам.
- Recall и teach привязать к одному canonical brain: корню этого репозитория,
  в том числе при работе из изолированных worktree. Проверить синтаксис установленной CLI.
- Прочитать найденные уроки и применить подходящие в требованиях, ADR и проверках;
  записать ссылки/ID и решение, а не только количество результатов.
- После подтверждённой находки и её проверки: `dz teach` для нового обобщаемого
  урока; `dz teach --reinforce` для уже существующего. Сравнить с recalled patterns,
  исключить дубли. Не обучать на гипотезах или непроверенных успехах.
- Для повторяющихся отказов предпочитать тест или guard, если он оправдан риском;
  запись в памяти не заменяет проверку.
- Проверять завершение и сохранение команд. Недоступность CLI или хранилища
  записывать явно; локальные Markdown insights — fallback, не успешный dz-вызов.
  Не менять глобальные hooks/config и не объявлять автоматический цикл установленным.
- Исходные записи и доказательства N8 хранить в проекте; общую dz-память использовать
  для обобщённых уроков без секретов и персональных данных.

## План и разрешения

План: подготовка → два ограниченных параллельных исследования → синтез продукта →
три самостоятельных интерактивных HTML-CJM → независимое ревью → конкретные
исправления → передача владельцу. Не более двух дочерних агентов одновременно.
Пишущие агенты — в изолированных worktree с явным владением файлами.

Плановые модели: research gpt-5.6-sol medium; consequential product design
gpt-6-astra high; HTML implementation и отдельное review gpt-5.6-sol high.
Координатор остаётся текущим; requested/actual/fallback и пробелы usage фиксируются.

Максимальная автономная длительность после одобрения плана — 10 часов.
План одобрен владельцем 2026-10-13; одобрение покрывает автономную работу до CJM checkpoint.
Владелец разрешил установку dz CLI по github.com/djd1m/dz-harness.
Не устанавливать глобальные hooks и не менять глобальную конфигурацию моделей.
Владелец последующим сообщением отменил ожидание CJM approval: выбрать A, максимально
близкий к gist, и сразу продолжать реализацию. Ранее заданная остановка после HTML отменена.
Три HTML и независимое ревью сохраняются как артефакты; выбран A.
Ориентир владельца — проверенный результат через 8 часов; предел автономии остаётся 10 часов.
Вести модульную разработку и обязательный локальный/GitHub reuse-поиск для каждой фичи.
Публикация на внешнем домене и оплачиваемые inference-эксперименты не входят в разрешение
на подготовку и кодирование. Разрешены локальный/изолированный запуск, разработка адаптеров
и проверки. Платные API-эксперименты отложены до определения бюджета; для прототипов использовать
явно обозначенные demo-данные. Наличие API и работоспособность интеграции не подменять демо.
