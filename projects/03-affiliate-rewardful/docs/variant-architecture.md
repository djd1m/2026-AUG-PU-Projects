# N3: предлагаемая общая архитектура четырёх вариантов

2026-09-08. Статус: **предложение для рассмотрения, не утверждённая архитектура**.
Тир XL: начисления, возвраты, права и выплаты. Этот документ описывает последующую реализацию; production-код сейчас не создаётся.
Основания: `docs/discovery/payout-decisions.md`, `docs/discovery/agent-interface-cjm.md`, `docs/product-discovery-brief.md` проекта N3.
Новое поручение владельца разрешает четыре PRD и план четырёх реализаций; прежняя остановка перед PRD в discovery — историческая запись.

## Структура и владение

Все пути ниже относительно `projects/03-affiliate-rewardful/`.

```text
variants/
  a-merchant/             # PRD, merchant UI: настройка, проверка начислений, реестр
  b-customer/             # PRD, embedded UI: добровольное участие, credits, применение
  c-partner/              # PRD, partner UI: условия, ссылка, cash, статус перевода
  d-agent/                # PRD, agent entry UI: делегация, задача, артефакт, продолжение
shared/
  contracts/              # версионированные команды, запросы, DTO, ошибки
  domain/                 # правила и типы отдельных предметных модулей
  application/            # единые use cases, policy enforcement, транзакции
  infrastructure/         # БД, inbox/outbox, provider adapters
  transports/             # HTTP, MCP и A2A адаптеры к application
  ui/                     # дизайн-токены, компоненты, представления артефактов
  testing/                # fixtures, синтетические события, часы, reset и общие проверки
apps/api/                 # одна композиция backend и фоновых обработчиков
docs/architecture/        # ADR, матрица прав, модель событий и принятия артефакта
```

Один модульный монолит и одна БД на окружение; четыре пакета интерфейсов используют общие контракты. Общие деньги, авторизация и расчёты не копируются в варианты. Физические схемы/таблицы принадлежат предметным модулям; изменения проводит один интеграционный владелец.
Владелец A отвечает за merchant journey; B — за customer journey и embed; C — за partner journey; D — за делегацию и agent journey. Владелец shared отвечает за контракты, инварианты и общий runtime. Общие manifests/lockfiles изменяет только интегратор; параллельная реализация — в изолированных worktree.
Допустимые зависимости: `variants → shared/contracts, shared/ui`; `transports → application → domain`; infrastructure реализует порты application. Browser-пакеты не импортируют серверные модули, credentials или ORM. Между вариантами прямых импортов нет; import-boundary check закрепляет это.

## Предметные границы

| Модуль | Ответственность | Существенная граница |
|---|---|---|
| Identity / tenancy / delegation | Субъект, tenant, роли, scopes, срок и отзыв | Variant и transport не выдают полномочий |
| Programs / attribution | Версия условий, участие, связь рекомендации с оплатой | Изменение правил не переписывает старые начисления |
| Payment events | Приём, проверка, нормализация оплат, renewals, refunds | Это учёт входящей оплаты, не исходящий payout API |
| Cash commissions | Pending/eligible комиссии и корректировки | Только обязательства перед cash-получателями |
| Customer credits | Earn/reserve/redeem/reverse credits | Без конвертации в cash или выплаты по умолчанию |
| Registry / settlement | Период, исключения, версия реестра, ручная отправка | «Подготовлено», «отправлено», «зачислено» — разные факты |
| Artifacts / tasks / audit | Принятый результат, версии, причины, задачи, след действий | UI, MCP и A2A работают с одним сохранённым результатом |

Cash и credits — отдельные append-only журналы с явными типами единиц; одинаковая сумма в рублях не делает их взаимозаменяемыми. Корректировки ссылаются на исходные записи, баланс выводится из проводок. Факты отправки и подтверждения получателя также не редактируют старые записи начислений.
Cash payout использует только cash ledger. Credit redemption резервирует и списывает credit ledger атомарно; конкурентные попытки не могут использовать один баланс дважды. Ошибка billing adapter не превращает резерв в успешное использование.
Решение о начислении cash, credits или сочетания обоих задаётся явной версией правил программы. Один purchase не начисляет оба вознаграждения из-за переключения UI; комбинация требует отдельного продуктового решения.

## Команды, права и результат

Контекст каждого серверного действия: `tenant_id`, `actor_id`, `subject_id`, а для делегации — `delegation_id`, разрешённые действия и expiry. Идентичность берётся из проверенной сессии/токена; значения из тела запроса не заменяют проверку принадлежности.
Предлагаемые use cases: `GetOwnRewards`, `ExplainAccrual`, `PrepareRegistry`, `ApproveArtifactVersion`, `RecordManualTransfer`, `ReserveCredit`, `RedeemCredit`, `RevokeDelegation`. Одни и те же use cases вызываются всеми транспортами. Обёртка MCP/A2A не обходит права и не создаёт отдельной бизнес-логики.
Merchant видит свой tenant; customer — свои credits; partner — свои cash-комиссии; агент действует в пересечении прав субъекта и делегации. Отсутствующая, истёкшая, отозванная или неизвестная делегация запрещает действие. Публичное обнаружение возможностей не содержит персональных данных.
Результат `VersionedArtifact`: `artifact_id`, `tenant_id`, `type`, `schema_version`, `revision`, `content_hash`, `source_snapshot`, `rule_version`, строки, исключения, `created_by`, время и audit references. Артефакт изначально не утверждён; отдельное одобрение ссылается на его точную версию/хеш.
Подтверждение ссылается на `artifact_id + revision + content_hash`; новый расчёт создаёт новую версию без прежнего подтверждения. UI и агент продолжают работу с тем же артефактом по ID. Чужой субъект не получает его даже при известном ID.
Обновление состояния использует ожидаемую версию и атомарную проверку; устаревшее подтверждение возвращает конфликт. Идемпотентная команда привязана к tenant, actor, action, key и hash входа: тот же ключ с другим телом отклоняется.
Для agent task различаются pending/running/waiting/completed/failed/canceled и доступный результат. Отмена/отзыв прекращают будущие действия; уже записанный факт внешнего ручного перевода не исчезает. Внутренние статусы отображаются на конкретную выбранную версию протокола после проверки совместимости.

## Платежи, повторы и поздние возвраты

Для каждой оплаты и renewal определяется устойчивая provider identity. Кандидат ключа нормализованного факта: `(tenant_id, provider_account_id, event_type, provider_object_id, provider_event_version)`; точный состав утверждается после аудита реальных полей провайдера, а не выдумывается из локального request ID.
Общий inbox с уникальным индексом атомарно исключает дубли; применение проводок и отметка обработки находятся в одной транзакции. Подлинность проверяется до необратимого действия способом, реально предоставленным провайдером; не обещать отсутствующий у него HMAC. Проверка провайдера вне удерживаемой транзакции, затем короткая запись с проверкой актуальности.
Перестановка событий не откатывает подтверждённое состояние. Нужны сценарии duplicate, concurrent duplicate, renewal, partial refund, несколько partial refunds, refund-before-payment, timeout и retry после недоступности провайдера. Сумма возвратов ограничена исходной оплатой; сумма reversal рассчитывается накопительно с единым правилом округления.
Возврат после ручной отправки создаёт компенсирующую cash-запись, задолженность/исключение и объяснение. Он не меняет старый approved registry, не «отзывает» банковский перевод и повторной доставкой не создаёт второй долг. Автоматическое удержание из будущего реестра остаётся кандидатом политики владельца; до решения — явное исключение для ручного разбора.
Для потраченных credits поздний refund создаёт отдельный adjustment/exception. Возможность отрицательного остатка, ограничения следующего применения и работа с billing корректировкой требуют отдельного решения; не списывать cash скрыто.
Основной процесс: реестр предыдущего месяца и ручной перевод до 5-го следующего. До запуска с реальными деньгами согласуются timezone, cutoff, hold, поздние события, выходные, минимальная сумма и подтверждение отправки/зачисления. Эти параметры в fixtures помечаются демонстрационными.

## Четыре демо и изоляция эксперимента

Каждый variant имеет собственный запускаемый entry и сценарный набор, при общем backend. Одна команда поднимает launcher с четырьмя ссылками; отдельная команда запускает конкретный вариант. Команды и URL появятся вместе с реализацией, сейчас они не существуют.
Демо работает только на fixtures: оплачено/renewal/held/refunded/после отправки/отказ доступа. Во всех вариантах видимая маркировка «демо», воспроизводимые часы и reset. Сценарное завершение требует изменения состояния, а не только перехода по статическим экранам.
В одной экспериментальной среде данные разделяются серверным `experiment_run_id` и tenant; reset затрагивает только разрешённый run. Для сопоставимого сравнения используются независимые клоны одного seed, поэтому действие в A не подготавливает результат за пользователя D. Отдельный сценарий handoff проверяет переход UI ↔ agent с одним артефактом.
Fixture runtime не имеет секретов, сетевых полномочий платёжного провайдера или маршрута выдачи внешней выплаты. Production окружение использует отдельную БД/учётные данные, не принимает fixture identity; отсутствие integration config показывает unavailable, а не включает симуляцию.
B проверяется на чужом HTTP origin с ограничительным CSP, CORS и враждебным CSS; нужны изоляция стилей и серверная проверка customer identity. Merchant preview на своём origin не закрывает embed acceptance.
A/B/C представляют разные роли и задачи, D — канал для этих ролей. Общую «конверсию четырёх вариантов» ранжировать нельзя. Сравнивать A-UI ↔ D-merchant на подготовке одного реестра; B-UI ↔ D-customer на объяснении одного credit; C-UI ↔ D-partner на проверке одной выплаты.
Метрики: правильность суммы/получателей/прав, принятый артефакт, время до принятия, исправления человеком, успешность отзыва и продолжения, доступный расход на принятую задачу. Порядок UI/agent чередуется; identity, fixture version, task и seed фиксируются. Разница трёх сегментов исследуется отдельно качественно.

## Последующие этапы реализации

1. **PLAN/VALIDATE, XL.** Четыре PRD, общий ADR, матрица прав, решения денежных исключений, AC → сценарий → проверка. Независимо оспорить права, повторные возвраты и версии артефактов. Сохранить конкретный рассмотренный план и применимое решение владельца перед реализацией.
2. **Общий каркас и fixtures.** Workspace packages, shared contracts, isolated demo store, общий use-case API, синтетические cash/credit события и артефакты. Проверки границ импортов, повторов, прав и seed isolation. Реальные credentials не нужны.
3. **Четыре запускаемых варианта.** A: тестовая оплата → реестр → ручная отметка; B: opt-in → referral → credit → применение; C: условия → ссылка → комиссия → статус; D: делегация → задача → тот же артефакт → approval/revoke/handoff. Browser acceptance каждого пути, ошибок и пустых состояний; B дополнительно на чужом origin.
4. **Общая долговечность и протоколы.** Одна БД, миграции, inbox/outbox, журналы, атомарные операции, настоящие локальные MCP/A2A adapters и protocol clients на fixtures. Проверить перезапуск, конкурентность, cancellation, версии, отзыв и transport parity. Имитация agent UI до этого этапа не называется работающим MCP/A2A.
5. **Интеграционный аудит.** Сначала project01 YooKassa/referral source audit и gap matrix для renewal/refund/auth/idempotency; переносить только проверенные части. Затем отдельные adapters по актуальной документации и контрактные тесты. CloudPayments и marketplace split — отдельные кандидаты, не обязательные четыре копии интеграций.
6. **Sandbox/pilot и приёмка.** При доступном подключении выполнить sandbox отдельно от production; сохранить evidence каждой capability. Проверить manual payout workflow, сверку, восстановление и все обязательные регрессии. Production rollout — последующее решение с доказательствами, а не следствие готового демо.

Матрица готовности заполняется отдельно для каждого adapter/capability: `fixture only`, `code per docs`, `contract tests passed`, `sandbox verified`, `production verified`, с датой, revision и evidence. Пропущенная стадия и неизвестный результат остаются неизвестными. Исходящие переводы не заявляются реализованными при наличии только YooKassa payment webhook.
Обязательные ворота реализации: денежные property/invariant tests, concurrent duplicates и credit redemption, tenant/subject/delegation denial tests на всех транспортных путях, stale approval, repeat refund after paid, import boundaries, четыре browser journey и embed contract. Стражи испытываются внесённым дефектом; полный набор регрессий и build привязываются к точной ревизии.


## Приоритет документов и размещение PRD

[Общий PRD](../shared/docs/PRD.md) задаёт обязательные правила; локальные PRD — variants/*/docs/PRD.md. Уточнения фиксируются версией контракта и обновлением всех затронутых потребителей. Этот файл — предлагаемая архитектура, не полный SPARC Architecture/Pseudocode комплект. [Конкретный план реализации](variant-implementation-plan.md).

Исходная технология выбирается с учётом project01: TypeScript/React/Next.js присутствуют в его package.json, PostgreSQL в существующем payment/referral модуле. Точные версии, frontend-host и package manager проверяются при W0; наличие зависимости в соседнем проекте не подтверждает её пригодность/безопасность для новой сборки.
