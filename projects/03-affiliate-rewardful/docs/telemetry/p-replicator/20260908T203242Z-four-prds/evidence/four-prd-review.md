## 1. High — определить переход approval → allocation → пересчёт/возврат

Места: `docs/variant-architecture.md:47`, `:55`, `:56`, `:57`, `:65`; `shared/docs/PRD.md:50`; `variants/d-agent/docs/PRD.md:38`.
Новые allocations правильно исключают двойное включение в выплаты. Однако снятие утверждения старой версии не определяет судьбу закреплённых сумм. После V1→V2 собственный старый settlement может блокировать новое утверждение; безусловное освобождение способно затронуть уже отправленные строки.
Второй аспект того же перехода: refund меняет ledger/source snapshot, но без запуска явного пересчёта старые revision/hash остаются прежними. Проверки только версии артефакта недостаточно, чтобы запретить свежий экспорт устаревшей суммы.
Действие на W0: задать атомарный переход для неотправленных allocations при invalidation/replacement и проверку актуальности экономического snapshot при approval/export. Новая версия требует нового approval; отправленные суммы сохраняются и компенсируются отдельно.
Не смешивать запрет нового использования устаревшего реестра с записью реального факта: если владелец уже перевёл по ранее скачанному CSV, факт надо сохранить как исключение для сверки, а не потерять из-за stale-version отказа.
Проверки: approved V1→refund без пересчёта→export; V1→V2→approve без вечной блокировки старым allocation; 1 из 3 переводов отправлен→refund/пересчёт; конкурентные refund и approval/export.
Классификация: конкретный незаданный инвариант для обязательного W0-контракта, а не блокер выпуска нынешних документов.

## 2. High — устранить несовместимость F1 acceptance с отложенными протоколами

Места: `shared/docs/PRD.md:27`, `:70`, `:78`; `variants/b-customer/docs/PRD.md:51`; `variants/c-partner/docs/PRD.md:49`; `variants/d-agent/docs/PRD.md:65`; `docs/variant-implementation-plan.md:16`, `:20`, `:21`, `:22`.
F1 требует все общие и локальные SC, включая запросы UI/MCP/A2A и общий реальный pilot backend. Одновременно настоящий wire transport появляется только на W4/F2, а W2D использует симуляцию. Поэтому буквальная приёмка F1 невозможна; её молчаливое «выполнение» симуляцией завысит доказательства.
Действие: явно размечать соответствующие SC по уровням доказательств. F1 проверяет use-case/identity parity через HTTP и fixture task transport; W4 повторяет эти SC реальными MCP/A2A clients; требования о реальном пилоте остаются F3. Одинаковые бизнес-инварианты сохраняются на каждом доступном уровне, wire tests не считаются выполненными заранее.
Связанный разрыв сравнения: `docs/variant-implementation-plan.md:48` и `:51` обещают B↔D, но D-customer только опционально на W4, после сравнения W3. Либо добавить fixture D-customer на W2D, либо явно отложить эту пару и не включать её в приёмку W3.
Детерминированный D на W3 даёт сведения об интерфейсе, делегации и handoff; его время и отсутствие model usage не доказывают скорость, стоимость или точность настоящего личного агента. Это ограничение надо закрепить в decision record выбора.
Классификация: противоречие заявленного объёма проверки, исправляемое сейчас таблицей этапов; не повод переносить настоящие интеграции в F1.

## Что проверено и не является новым блокером

- Все четыре PRD и автономные HTML находятся в отдельных variant-папках; общий runtime явно будущий. Общие HTML исходники не выдаются за финансовое ядро.
- Browser/server граница задана явно; перечни «импортирует из shared» в локальных PRD следует читать вместе с запретом серверных импортов в следующем абзаце. Мелкое уточнение на W0: назвать пакет клиентского фасада в allowed dependency graph (`variant-architecture.md:32`).
- Cash и credits разделены; UI не меняет reward policy. Новые SC-US-004-5/6 закрывают competing settlement и повторную отметку другим оператором; SC-US-203-3 задаёт unknown billing и однократный release. Прежние потенциальные замечания по этим местам сняты после повторного чтения.
- Grant ограничен субъектом/сроком/actions; read+draft не даёт approve/pay/send; отзыв проверяется и перед новой выдачей защищённого результата. Owner handoff сохраняет артефакт по независимым правам.
- Срок ручной выплаты до 5-го сохранён; экспорт, отправка и зачисление разделены. Cash refund после отправки не объявлен возвратом банковского перевода.
- Роль A/B/C и канал D различены; общий рейтинг конверсии «четырёх победителей» справедливо запрещён.
- Production rounding/hold/cutoff, правила потраченных credits, документы получателя и доступы провайдеров явно отложены. Для F1 достаточно утверждённой демонстрационной policy на W0; неизвестность production-параметров сама по себе не блокирует этот стенд.
- Аудит существующего YooKassa-кода, отдельные адаптеры по документации, contract/sandbox/production evidence и повторная проверка pipeline resolver явно будущие. Тексты не обещают выполненное подключение.
- Отсутствующий полный SPARC и точный frontend/package manager уже назначены W0. Независимый challenge не заменяет эти ворота и не требует завершить их в текущем scope.
