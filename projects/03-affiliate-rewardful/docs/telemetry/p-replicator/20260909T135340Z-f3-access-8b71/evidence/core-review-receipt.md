## Findings
### P2 — Unverified accounts can accept invitations after enforcement is enabled
Evidence: shared/identity/service.mjs:159–173, particularly session-only authorization at162 followed by membership insertion171, invitation consumption172 and tenant persistence173. apps/api/account.mjs exposes POST /api/account/accept-invite directly. Unlike resolveUser/resolveAgent/referral authorize, acceptInvite never calls assertVerified.

Reproduction: create an invitation with a verified merchant, retain an unverified F2 or SSO account/session, persist access_policy.verification_required=true, and submit that invitation from the unverified session. Current function authenticates the session and mutates memberships/tenant/invitation, without reading the policy. Expected: EMAIL_VERIFICATION_REQUIRED before invitation/tenant locks, zero mutations and reusable invitation. This is a source-proven missing guard, not an executed reproduction by this reviewer. The bypass does not grant subsequent dashboard access (resolveUser still enforces policy), but it violates the specified security-only state and permits business mutation during enforcement. Fix: assertVerified(client,account.id) immediately after session resolution, with the existing transactional policy lock. Add HTTP/service assertion covering unchanged membership, tenant actors and invitation accepted_by.

### P2 — Password change still upgrades a shared account lock and can deadlock concurrent changes
Evidence: shared/identity/service.mjs changePassword final transaction calls session(client,plain), whose account lookup uses FOR SHARE, then UPDATE accounts SET password_hash/version. The new explicit account→session resolver fixes the former joined-row lock inversion, but does not prevent two changePassword transactions both holding SHARE on the same account before attempting UPDATE.

Deterministic reproduction design: two valid sessions of one account start changePassword with valid current password; hold both final transactions immediately after their session checks so both account SHARE locks exist, release the barrier, and both issue UPDATE. Each requests an incompatible account lock while holding the other's conflicting SHARE lock; PostgreSQL must abort one transaction as a deadlock. transaction() masks this as DATABASE_UNAVAILABLE. Expected: serialize on account FOR UPDATE before source-session proof, allowing one successful change and the stale loser to return auth/conflict refusal without database failure. Use the account-first currentSession pattern or equivalent direct FOR UPDATE; avoid a shared-to-exclusive account upgrade. Source-derived concurrent schedule, not an executed test in this work unit. Include queued reset versus password change if the owner adds a wider race test.
