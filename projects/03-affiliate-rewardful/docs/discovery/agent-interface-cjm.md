# Агентный интерфейс N3: уточнение CJM

Решение владельца, 2026-09-08: проектировать продукт с интерфейсами MCP/A2A для агентных действий. Представление о личных агентах у большинства людей — стратегическая гипотеза владельца, а не измеренный прогноз рынка. В текущем scope меняются исследование и HTML CJM; MCP server/A2A endpoint и PRD не создаются.

## Вывод: общий агентный доступ + вариант D

MCP/A2A — каналы доступа к возможностям N3, а не ещё один сегмент покупателей. A–C описывают роли и пользу; D проверяет другой способ прохождения пути: намерение → делегирование → результат → проверка/исключение → продолжение. Поэтому сохранены A/B/C и добавлен D «Через личного агента». Рекомендация для обсуждения: взять роли и операционный процесс A/C, а D использовать как альтернативный вход; B сохраняет собственную гипотезу subscription credits. Это ещё не выбор владельца.

| Исходный CJM | Что меняется при агентном доступе | Что остаётся у человека |
|---|---|---|
| A — владелец | Агент готовит правила, объясняет комиссии, собирает месячный реестр; показывает источник и исключения | Разрешение доступа; утверждение конкретной версии реестра; ручной перевод до5-го |
| B — клиент | Личный агент по запросу читает условия и личный баланс, готовит ссылку/текст рекомендации | Добровольное участие; решение кому и что отправить; использование бонуса по выбранной политике |
| C — партнёр | Агент запрашивает собственные начисления и дату выплаты, объясняет изменение суммы | Выбор программы и предоставление необходимых данных; спор/исправление при расхождениях |
| D — агентный вход | Поручение «Подготовь выплаты за август» вместо обхода кабинетов; один результат с доказательствами и статусом задачи | Ограниченная делегация и контроль существенных действий, а не подтверждение каждого чтения |

## Что подтверждают протоколы

MCP позволяет обнаруживать и вызывать типизированные инструменты продукта; structured outputs пригодны для машиночитаемых результатов. Протокол не требует чат-интерфейса и не задаёт бизнес-политику согласований. В N3 предлагается дать чтение и подготовку черновиков в пределах выданного доступа, отдельно — утверждение конкретного результата. [MCP tools, версия2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

Для HTTP-транспорта MCP описывает авторизацию доступа к защищённому серверу. Токен доступа не заменяет проверку tenant, роли, принадлежности данных и допустимого действия в продукте. Объём, срок и отзыв делегации — продуктовые требования; фактическая совместимость клиентов ещё не проверялась. [MCP authorization, версия2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization).

A2A описывает Agent Card для обнаружения возможностей и взаимодействие через сообщения/задачи/артефакты. Подходит для разговора личного агента с агентом сервиса, когда нужно сопровождение задачи; для одиночного tool call достаточно MCP. A2A не даёт универсального доверия между агентами: авторизация и доступ к задаче проверяются сервером. В HTML названия стадий пользовательские, не обещание wire compatibility. [Официальная спецификация A2A, просмотр2026-09-08](https://a2a-protocol.org/latest/specification/).

## D: шесть экранов

1. **Поручение.** Владелец видит задачу и ожидаемый артефакт, а не список интеграций.
2. **Доступ.** Только Proofwall, чтение начислений + подготовка реестра на текущую задачу. Платежи, изменение ставок и рассылки не разрешены. Отказ/отзыв доступны.
3. **Первый результат.** Агент подготовил реестр:3 партнёра,9600₽, срок до5 сентября; отдельно видно удержанное начисление. Результат явно демонстрационный.
4. **Контроль.** Владелец утверждает конкретную версию, скачивает реестр и переводит деньги вне сервиса. Пересчёт снимает предыдущее утверждение; повторная подготовка не дублирует строки. Есть отзыв/истечение доступа, восстановление в UI.
5. **Цена.** Платит владелец за сервис; чтение партнёром своего статуса не превращается в платёжную воронку. Агентная упаковка и лимиты — гипотезы.
6. **Агент партнёра.** Отдельная роль и делегация: запрос только собственного статуса, ожидание ответа, отмена, демонстрация ответа. Не получает общий merchant registry. Отмена задачи не откатывает уже сделанный внешний перевод.

## Передача на следующую фазу — пока кандидаты

| ID | Обязательство | Обоснование |
|---|---|---|
| PD-AGENT-001 | Машиночитаемые возможности N3 через MCP; A2A для задач с агентом сервиса | Прямое направление владельца |
| PD-AGENT-002 | Одна бизнес-модель прав/статусов для UI, MCP, A2A; tenant/subject checks на каждом серверном действии | Смена канала не расширяет полномочия |
| PD-AGENT-003 | Делегация ограничена целью, субъектом, сроком; отзыв прекращает будущие действия | Контролируемая автономность |
| PD-AGENT-004 | Утверждение привязано к версии/содержимому артефакта; изменение требует нового решения | Реестр нельзя незаметно изменить после просмотра |
| PD-AGENT-005 | Повторы идемпотентны; ожидание, ошибка, отмена и результат различаются | Агенту и человеку нужен достоверный статус |
| PD-AGENT-006 | MCP/A2A не создают автоматических выплат или рассылок сверх делегации | Сохраняется ручной payout process владельца |
| PD-AGENT-007 | Обнаружение сервиса не раскрывает клиентские данные; tool/agent input не считается доверенным | Клиентские агенты и внешние материалы могут ошибаться |
| PD-AGENT-008 | Вознаграждаем реальную рекомендацию/оплату, не вызов tool, регистрацию агента или автоматический spam | Growth-модель не меняется от появления нового канала |

В будущем уточнить: какие клиенты поддерживаем первыми, требуется ли собственный reasoning-agent N3 или достаточно tools, как передавать идентичность пользователя при A2A, версионировать артефакты и подтверждения, обрабатывать сбои/повторы/отзыв, кто оплачивает model usage. Это не скрыто утверждённая архитектура.

## Проверка гипотезы

Сравнивать UI и agent-path на одинаковых заданиях: время до принятого реестра, число исправлений человеком, правильность суммы/получателей, успешность отмены и отзыва, расходы на принятую задачу. Метрика «меньше кликов» недостаточна. Для B/C — время до правильного ответа о собственном бонусе/выплате и конверсия добровольного приглашения в реальную оплату. Полевые результаты и provider usage пока отсутствуют.
