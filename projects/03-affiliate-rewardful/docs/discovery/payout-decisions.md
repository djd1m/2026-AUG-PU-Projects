# Решения владельца о выплатах

Зафиксировано из переписки 2026-09-08. Эти решения уточняют более ранние исследовательские гипотезы.

1. Основной рабочий сценарий — ручные выплаты. Ведём реестр «кому сколько» за предыдущий месяц, отправляем переводы организационно **до 5-го числа следующего месяца**, затем отмечаем отправку. До 100 партнёров — рабочее допущение владельца о достаточности процесса, не измеренная пропускная способность.
2. ЮKassa — исходная интеграционная база. Пользователь сообщает, что код уже готов; в project01 найдены webhook приёма платежей и расчёт referral commission. Это ещё не подтверждение готового API исходящих выплат. Перед повторным использованием нужен аудит конкретных модулей.
3. **Split payments относится к Яндекс Кассе** — уточнение владельца. Историческое имя Яндекс.Касса соответствует текущей ЮKassa. CloudPayments рассматривается отдельно. Marketplace split не считается автоматически подходящим для отложенных партнёрских комиссий.
4. На следующем этапе допускается написать интеграционные адаптеры по документации без проверки реального подключения. Статусы должны различать: код по документации, контрактные тесты, sandbox, production. Не проверенные на реальном подключении выплаты не объявлять готовыми к эксплуатации.
5. Три дня на согласование и необходимость открыть ИП — ожидания владельца в его ситуации. Не превращать их в универсальную гарантию провайдера. Условия подключения уточняются отдельно.
6. Текущий этап заканчивается после HTML CJM. Адаптеры, PRD и production-интеграция сейчас не реализуются.

## Что согласовать после выбора CJM

- Закрытие месячного реестра: какие начисления попадают в период, как переносить поздние и удерживаемые комиссии при сроке до 5-го.
- Разница «подготовлено», «отправлено владельцем» и «зачислено получателю»; доказательство перевода и сверка.
- Возврат после отправки, отрицательное сальдо, минимальная сумма, ошибочные реквизиты, перенос срока при нерабочем дне.
- Кто является плательщиком и получателем, какие документы и данные нужны для выбранной модели.
- Применимость именно marketplace split к этому продукту, отдельно от обычного payout API.
