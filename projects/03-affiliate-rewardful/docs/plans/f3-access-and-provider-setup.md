## 1. Результат этапа

В N3 появляются подробные инструкции по платёжным провайдерам и рабочие сценарии подтверждения почты, восстановления пароля через Resend и входа через Yandex ID. Общее ядро авторизации обслуживает кабинеты A–D. Существующие tenant/membership, финансовые факты и MCP/A2A сохраняются.

Документация платежей охватывает настройку кабинета провайдера и соответствие текущему коду N3. CloudPayments в этом запросе — инструкция и контракт будущего подключения; включение нового платёжного адаптера не входит в предлагаемый объём. Автовыплаты также не включаются. Базовый процесс выплат остаётся ручным, до 5-го числа за предыдущий месяц.

Яндекс.Касса — прежнее название ЮKassa, а не третий независимый провайдер. В документации будет один основной runbook и отдельный раздел по прежнему названию, сплитованию и выплатам. Сплитование между магазинами, партнёрская комиссия и рассрочка покупателя не подменяют друг друга. Основания: [история компании](https://yookassa.ru/about), [сплитование](https://yookassa.ru/developers/solutions-for-platforms/split-payments/payments).

### 3.2. Email и восстановление

1. Добавить `email_verified_at`, состояние незавершённой регистрации, отдельные purpose-bound одноразовые токены и индексы. Действующий токен привязан к аккаунту/адресу/версии/назначению. В таблицах токенов хранится только hash.
2. Для новой регистрации: почта и название → письмо → страница активации с установкой пароля → атомарное создание/активация аккаунта и пустой организации. Привилегии не выдаются паролю, заданному кем-то до доказательства владения ящиком.
3. Для существующих F2 аккаунтов: не ставить verified автоматически. Предусмотреть подтверждение с безопасным переустановлением пароля и отзывом старых сессий/агентов, сохранив ID и членства. План включения не должен оставлять владельца без пути восстановления.
4. Предлагаемые сроки: подтверждение 24 часа, reset 1 час. Повторная отправка ограничена cooldown и атомарными лимитами email/IP; новая ссылка гасит предыдущую. Точные лимиты заморозить в спецификации и проверять буквальными значениями.
5. Ссылка открывает страницу; GET от сканера писем не погашает токен и не меняет пароль. Изменение выполняется явным POST. Ссылка не выдаёт пользовательскую сессию сама по себе; после reset требуется обычный вход.
6. Resend вызывается вне SQL-транзакции. Установить таймауты/лимиты параллелизма и объёма ответа. Повторная отправка — явный ограниченный запрос; отдельный фоновый почтовый сервис не нужен для этого объёма. Ответ recovery не раскрывает, зарегистрирован ли адрес, и не заявляет доказанную доставку. При отсутствии конфигурации — одинаковый явный unavailable для всех адресов.
7. Reset атомарно погашает токен, меняет Argon2id-хеш, увеличивает account.version и отзывает все прежние сессии/агентные credentials. Повтор, гонка, истечение при ожидании блокировки и смена пароля между выдачей/погашением не обходят проверку.
8. Верификация/активация не объединяет чужие организации и роли. API и агентные действия проверяют актуальную политику подтверждения; UI не является единственным ограничителем.
9. Ссылки собираются только из разрешённых origin; токены не попадают в access logs, referrer, localStorage или стороннюю аналитику. Шаблоны экранируют динамические данные.

Порядок включения: сначала совместимая миграция и конфигурация Resend, затем проверка доставки и включение обязательной верификации. Если почта недоступна, новые функции явно не настроены; текущие F2 аккаунты не исчезают. После включения верификации outage почты не ослабляет уже принятую политику доступа.

### 3.3. Yandex ID

1. Адаптировать code flow и PKCE S256 из проекта 01. State — ограниченный по времени, привязан к браузеру/intent/origin, одноразовый; нельзя переиспользовать callback или подменить login на link.
2. Разрешить только четыре точных N3 origin из deployment-контракта. Callback каждого хоста: `/api/account/yandex/callback`; после успеха `/account` на том же хосте. Яндекс требует точное совпадение URI со списком приложения. Host-only cookie сохраняются.
3. Ключ внешней личности — `(provider, external_id)` с уникальным индексом. Email профиля — контакт, не доказательство владения локальным аккаунтом. Автослияние по email запрещено для всех состояний аккаунта.
4. Новый пользователь получает одну пустую организацию; повторный/параллельный вход не плодит аккаунты/членства. Поддержать nullable password_hash для SSO-only аккаунтов, сохранив отказ обычного password login без установленного пароля.
5. Привязка существующего аккаунта — из авторизованного подтверждённого кабинета с недавним доказательством текущего способа входа и независимым OAuth-подтверждением. Чужая уже привязанная identity не переезжает. Отвязка не удаляет последний действующий способ входа.
6. Полученный Yandex email не получает `email_verified_at` автоматически. Recovery SSO-only аккаунта требует ранее подтверждённого контактного email; произвольный email из профиля не становится обходным способом входа.
7. Provider token используется сервером для профиля, не возвращается браузеру; постоянное хранение/refresh не нужны для login-only интеграции. Нет fake login при пустых ключах.
8. Проверить ошибки state/PKCE, code replay, отказ пользователя, missing email, коллизию адреса, недоступность провайдера, login/link race и отзыв сеансов.

### 3.4. UI A–D

Общие модули в `shared/ui/account/`: запрос/повтор письма, страница активации, forgot/reset, состояние подтверждения, кнопка Yandex, привязка/отвязка в безопасности, явная ошибка ненастроенного провайдера. Сохраняются текущие защита от поздних ответов, очистка полей/секретов и доступность с клавиатуры. A–D получают общие изменения без четырёх копий кода. Полный перенос остальных специализированных CJM в real mode не входит в F3.

## 5. Команда и модели

Профиль `compact-quality-first-v2`. Максимум координатор + два одновременно работающих дочерних агента; роли сменяются по волнам. Модель и effort задаются при запуске и подтверждаются метаданными. Ни один новый дочерний агент ещё не запущен.

| Агент / роль | Модель | Навыки / ответственность | Владение |
|---|---|---|---|
| `coordinator` — текущая сессия | `gpt-6-astra`, high, фактически подтверждена | Риск, `sparc-prd-mini`, security design, канон, интеграция, сложные конкурентные E2E, релиз | Существующие identity/schema/service/API, общий manifest/lockfile/compose, итоговые документы и телеметрия |
| `provider-docs` | `gpt-5.6-sol`, high | Синтез локальных доноров и официальных docs, пошаговые инструкции, сверка с реальным кодом | Новые `docs/integrations/*`, будущий docs index, собственный receipt |
| `auth-adapters` | `gpt-6-astra`, high | Resend и Yandex provider modules, ограниченные сетевые границы, PKCE/state primitives, их контрактные тесты | Только новые выделенные `shared/identity/providers/*` и собственные тесты; существующие общие файлы не правит |
| `account-ui` | `gpt-5.6-sol`, high | `frontend-design` в существующей визуальной системе, auth forms/states, UI boundary tests | `shared/ui/account/*` и закреплённые UI tests после фиксации API |
| `independent-review` | `gpt-6-astra`, high | `requirements-validator`, затем отдельный `brutal-honesty-review`, security/concurrency challenge | Только отчёты; не автор проверяемого кода |

Смена модели координатора не изображается и глобальная конфигурация не меняется. Terra/Luna здесь не нужны: механические проверки выполнит скрипт, а recovery/linking имеют высокий риск. Astra-review не означает независимость поставщика моделей; независимы задача и исполнитель.

Волны: (1) координатор проектирует, reviewer оспаривает план; (2) после VALIDATE provider-docs и auth-adapters работают параллельно, координатор реализует общую БД/identity; (3) после освобождения слота и заморозки API запускается account-ui, координатор интегрирует адаптеры и concurrency tests; (4) независимый reviewer проверяет кандидат, координатор выполняет E2E; (5) исправления → обязательные проверки → выкладка.

У каждого писателя отдельный worktree и точный список файлов. Передача: RUN_ID, WORK_UNIT_ID, абсолютный TRACE_PATH, исходные SHA, AC, тесты, ограничения. Receipt — содержательный файл, завершающийся `Status: completed` либо `Status: failed`; проверяется до cherry-pick. Общий браузер и VPS принадлежат только координатору. Параллельные агенты не делят один WebDriver-сеанс.

Основные команды после реализации: `npm run build`, `docker compose -f docker-compose.test.yml run --rm --no-deps backend npm test`, `node scripts/run-public-e2e.mjs`, расширенные account/provider E2E, `node scripts/check-pipeline.mjs`, установленный `check-review-contract.cjs`, актуальный mutation suite, `node scripts/check-deployment.mjs`. Перед Docker up — корневой `scripts/check-port-conflicts.sh` и проверка принадлежности занятых портов. Пакетный compatibility wrapper N3 не ослабляет проверки; при изменении package SHA требует пересмотра.

При работе с публичными webhook действуют provider-specific проверки. Для ЮKassa — authenticated read-back; для CloudPayments документация описывает его HMAC-контракт. Отсутствующая живая проверка остаётся NOTPERFORMED, а не зелёным результатом.

## 7. Внешняя настройка и выкладка

Для живой приёмки нужны выделенные N3 credentials Resend/Yandex и ЮKassa, контролируемый отправляющий домен/DNS, контрольный почтовый адрес и доступ владельца к Yandex consent. В этом плане их наличие не предполагается. Проверка реального ящика и вход в реальный Yandex — отдельные доказательства от контрактных тестов с тестовым провайдером.

Код и локальные полные browser E2E доводятся до готовности независимо от доступа к провайдерам. Test provider живёт только в изолированном тестовом окружении; публичного API для извлечения reset/verify токенов не будет. На публичном VPS выполняются доступные smoke/UI проверки и только настроенные внешние сценарии. Отсутствие секретов явно отражается в UI/документации и итоговом статусе.

Выкладка: совместимая миграция → backend с функциями, управляемыми конфигурацией → A, B, C, D последовательно → доступные end-to-end проверки → включение проверки email после подтверждения mail readiness. Rollback приложения не отменяет уже выполненный отзыв credentials и не удаляет новые данные; совместимость предыдущего image с nullable password/новыми состояниями проверить на стадии PLAN.

## 8. Коммиты, время и телеметрия

Небольшие содержательные commit/push после документов/контрактов, адаптеров, identity integration, UI и проверок. Ни одного крупного общего коммита в конце; конфликты интегрирует координатор.

Предварительная оценка **3–5 часов отозвана 2026-09-09**: она не была обоснована сверкой объёма готовых доноров. Resend sender/reset и Yandex HTTP/PKCE переиспользуются из проекта01; дополнительные работы — адаптация к N3 identity/revocation, новая регистрационная верификация и проверки. Следующая оценка опирается на фактический прогресс переноса; внешние согласования/DNS/credentials учитываются отдельно.

У планирования отдельная запись `docs/telemetry/p-replicator/20260909T104725Z-f3-plan-93d5/`. При одобрении новый implementation RUN_ID и связанный batch; ожидание владельца учитывается отдельно. Фиксируем actual/requested model, effort, fallback, source hashes, stage times, все повторы, uncached/cached/output usage, доступные расходы. Не заявляем экономию без сопоставимого baseline. При доступном недельном счётчике предупреждаем при остатке <=2%.
