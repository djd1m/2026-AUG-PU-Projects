# План: четыре работающих варианта на общем ядре

2026-09-08 · XL · предложение для согласования. Существуют4 PRD и HTML-прототипы; нижеперечисленный runtime ещё не реализован. Цель первого цикла — F1: четыре работающих сценария на изолированных тестовых данных для сравнения, затем выбор/сочетание. Полный продукт и production-платежи — последующие этапы.

## Пакет для решения владельца

[Общий PRD](../shared/docs/PRD.md), [четыре локальных PRD](../variants/README.md), [архитектура](variant-architecture.md). Предлагается один backend с одной БД на окружение, четыре самостоятельных UI entry packages в variants/* и общие server/client модули в shared/*. Менять денежные правила для одной оболочки скрытым flag нельзя.

Разрешение на подготовку PRD/плана получено. Перед финансовой/authorization реализацией нужен ответ на конкретный рассмотренный XL план: это граница `.claude/rules/complexity-router.md`, а не повторный запрос разрешения на документацию. Согласование F1 не выдаёт автоматически доступ к production, провайдерам или денежным операциям.

## Этапы и проверяемые выходы

| Этап | Что получаем | Критерий выхода | Зависимость |
|---|---|---|---|
| W0 — контракт и подготовка | Workspace/команды/lockfile, матрица прав, версии DTO/fixture policy, mapping PRD→Spec→алгоритм→проверка; audit scope project01 | Полный достаточный план финансов/прав, независимый challenge, обязательные gates подключены, решение владельца | PRD review |
| W1 — общее F1 ядро | domain/application/contracts, один backend, изолированное долговечное demo-хранилище, seed/reset без real provider credentials | Общие SC-US-001…006 исполняются на fixture backend; duplicate/parallel/credit reserve/stale approval/reset tests | W0 |
| W2A — merchant | variants/a-merchant/src + tests: настройки/оплата/реестр/CSV/отметка | US-101…104 + общие инварианты,390/1440px | W1 |
| W2B — customer | variants/b-customer/src + tests: opt-in/credit/применение/share | US-201…204, включая concurrent credit, identity и чужой origin | W1 |
| W2C — partner | variants/c-partner/src + tests: terms/enroll/history/own payout | US-301…304, отсутствие чужих данных, точность статусов | W1 |
| W2D — agent UI/task | variants/d-agent/src + tests: intent/grant/task/artifact/revoke/handoff | US-401…404 на fixture task transport, явный статус «симуляция протокола» | W1; UI handoff W2A |
| W3 — сравнимый F1 стенд | Launcher4вариантов, один seed catalog, независимые run-клоны, общий журнал, сбор результатов | Полные journey/negative tests всех4, одинаковый dataset/rules; открытые ограничения доступны пользователю | Все W2 |
| W4 — protocol candidate | Настоящие локальные MCP/A2A endpoints и выбранные protocol clients поверх fixture application | Transport parity, identity, timeout/cancel/late responses, повтор и отзыв после рестарта | W3 + подтверждённый контракт протоколов |
| W5 — provider candidate | Audit/reuse ЮKassa payment code, отдельные contracts/adapters, sandbox по доступности | Evidence capability: docs-only / contract / sandbox / production; отсутствующая конфигурация не включает fake | W3 + решения денег/доступов |
| W6 — выбор и сборка | Выбранный профиль или гибрид, сохранённое shared ядро, ограниченный пилот по готовности | Decision record с метриками/исключениями; реальные деньги отдельным решением | Сравнение W3; при необходимости W4/W5 |

W1 включает перезапуск/долговечность fixture-реестра, а W4 — protocol durability/recovery. Чтобы избежать двух реализаций хранилища, конкретный adapter F1 фиксируется на W0; не строить временное финансовое ядро отдельно для каждого UI.

W2A/B/C можно делать параллельно после заморозки shared contracts. D использует тот же artifact contract; финальная parity/handoff проверка ждёт A. Если B требует новый credit use case, сначала изменяется общий контракт и его тесты, затем потребитель. Изолированные worktree и один интегратор общих файлов обязательны.

## Владение и маршрутизация моделей

- Общая архитектура, XL денежные инварианты, сложная реализация и QE: Astra high; consequential plan challenge — Astra xhigh.
- Согласованные UI-сценарии и обычная реализация: Sol high. Бounded UI/DTO/test fixture module с фиксированным контрактом: Terra medium/high.
- Механическая генерация/проверка: скрипты; модель не нужна. Requested/actual/fallback/usage каждого запуска — в проектной телеметрии.
- У каждого исполнителя конкретный variant/work-unit, PRD/common version, владельцы файлов и AC. Shared module change принимается интегратором с регрессией всех потребителей.

## Как переиспользуем и выбираем

Ни один variant не импортирует соседний. Общими являются contracts, clients, UI primitives, application/domain, provider adapters, fixtures и измерения. Уникальными — вход, тексты, композиция экранов, часть продуктовых политик через типизированные extension points, сценарные tests.

После сравнения собрать профиль приложения из выбранных экранов/политик, например merchant flow A + partner portal C + agent access D. B можно подключить как отдельную credit policy. Выбор UI не мигрирует и не суммирует балансы. Shared изменения версионируются/откатываются для всех вариантов согласованно; экспериментальные UI-флаги не дают новых прав.

## План сравнения

| Пара | Одно и то же задание | Что сравниваем |
|---|---|---|
| A UI ↔ D merchant | Подготовить/исправить/утвердить реестр | Правильность, время, исправления, стоимость принятой задачи |
| B UI ↔ D customer | Объяснить свой credit и условие применения | Понимание, ошибки, успешность действия; D-customer добавляется как parity case |
| C UI ↔ D partner | Узнать сумму/дату/причину удержания | Правильность ответа, обращения за помощью, время |

D-customer — расширение действующего D HTML, в котором пока показаны только merchant и partner; оно включается в W4 parity при необходимости сравнения B↔D. Не называть это уже реализованным сценарием.

Отдельно исследуем спрос на A/B/C по соответствующим аудиториям. Общая «конверсия победителя из4» не имеет корректного смысла при разных ролях. Для UI↔agent заданий меняем порядок предъявления, сохраняем seed version, отделяем обучение от основного замера. Малый пилот даёт направляющие наблюдения, не статистически доказанный uplift.

Источники измерений — общий PRD. Бизнес-targets и сроки пока не назначены. Обязательные критерии качества абсолютны: отсутствие чужих данных/двойного начисления/незаметного изменения утверждённого реестра. При их провале вариант не принимается за счёт скорости.

## Граница текущей работы

Этот пакет —4 продуктовых PRD + shared PRD и XL план, сформированные по имеющемуся discovery. Не объявляется завершением всей Phase1 SPARC: ещё нужны утверждённые решения, спецификация/алгоритмы и обязательная трассировка. Отсутствующий package pipeline-gap resolver и автоматическая source path съёмка из предыдущих прогонов не объявляются исправленными. Их readiness повторно проверяется на W0.
