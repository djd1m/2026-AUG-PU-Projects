# Агентная покупка Proofwall: граница ответственности N3

Дата 2026-09-10. Статус: **план, не реализовано**.
Полный сценарий с точками участия человека и источниками ЮKassa:
[план проекта 01](../../../01-testimonials-senja/docs/features/agent-purchase/plan.md).

N3 остаётся источником истины для рекомендации и комиссии. Авторизация покупателя,
платёжное поручение агенту, сохранённый способ оплаты, лимиты и тариф принадлежат
магазину Proofwall. N3 не получает карточные данные и не выдаёт агенту покупателя
право читать доходы партнёра.

Планируемая цепочка:

1. Агент получает offer Proofwall и источник рекомендации.
2. Пользователь связывает аккаунт, подтверждает почту и полномочия агента.
3. Proofwall передаёт visit token/промокод и подтверждённого клиента через
   существующий серверный connector API N3. Браузерная cookie не обязательна.
4. N3 проверяет источник, срок, self-referral и неизменность привязки.
5. Proofwall создаёт внешний заказ N3, затем платёж у ЮKassa.
6. Первая покупка требует human handoff. Следующее продление может пройти без
   него по ранее подтверждённому поручению и сохранённому способу оплаты.
7. Проверенная оплата проходит существующий outbox → external-events → проверку
   провайдера → журнал комиссии. Повторное списание — новый платёж, а не дубль события.
8. Агент покупателя читает оплату/тариф/статус рекомендации в Proofwall.
   Агент партнёра отдельно читает свою комиссию через уже существующие MCP/A2A N3.

Нужна отдельная проверка корректности повторного начисления: published policy
`recurring` сохраняется в заказе, новый provider payment учитывается один раз,
возврат уменьшает соответствующую комиссию. Смена ключа API не должна менять атрибуцию.

Не объединять внутренние Docker-сети P1/N3. Сохранить публичный HTTPS connector,
раздельные БД и ключи. Новый `agent-api` не становится вторым биллингом.
У N3 уже есть агентные протоколы, поэтому переносить их в новый контейнер только
ради симметрии с Proofwall на этом этапе не требуется.

Текущая человеческая цепочка:
[архитектура интеграции](proofwall-architecture.md).

автоплатёжные поручения и новые credentials в рамках планирования не создавались.
