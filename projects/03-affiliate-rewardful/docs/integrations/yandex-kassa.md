# Яндекс.Касса, ЮKassa, сплитование и выплаты

Дата сверки: **2026-09-09**. Этот документ помогает выбрать продукт и не принять старое название или отдельный денежный процесс за уже подключённую возможность N3.

## Старое название

**Яндекс.Касса — прежнее название ЮKassa.** В 2020 году после выхода из группы компаний Яндекса кошелёк стал ЮMoney, а Яндекс.Касса — ЮKassa. Для обычного приёма платежей не создавайте в N3 третий provider и не ищите отдельный `yandex-kassa` ключ: используйте действующий runbook [ЮKassa](yookassa.md), `.runtime/yookassa.json` и `N3_YOOKASSA_CONFIG_FILE`.

Старые договоры, плагины и логи могут содержать `Яндекс.Касса`, `Yandex.Checkout` или старые API. Название само по себе не доказывает совместимость. Перед миграцией установите версию протокола и сопоставьте каждый статус/идентификатор с современным API ЮKassa; не направляйте старые уведомления прямо в N3.

## Четыре разных процесса

| Задача | Продукт провайдера | Состояние в N3 |
|---|---|---|
| Получить оплату на один магазин | Обычный приём платежей ЮKassa | Реализован для одного shop + tenant на deployment |
| Разделить один платёж между магазинами | «Сплитование платежей» для платформ | Не реализовано |
| Перевести деньги физлицу | «Выплаты по API» с отдельным шлюзом | Не реализовано |
| Выплатить продавцу после выполнения сделки | «Безопасная сделка» | Не реализовано |

Партнёрское вознаграждение N3 также не превращает provider payment в автоматическую выплату. N3 формирует и утверждает реестр/CSV и хранит факты ручной отправки. Действующий бизнес-процесс — ручная выплата за предыдущий месяц до 5-го числа. CSV не отправляет деньги.

## Если нужен только текущий приём платежей

1. Создайте отдельный тестовый/боевой магазин ЮKassa.
2. Настройте `.runtime/yookassa.json` по [основной инструкции](yookassa.md).
3. Включите только `payment.succeeded` и `refund.succeeded` на `https://n3-a.212.192.0.33.sslip.io/api/webhooks/yookassa`.
4. Проверьте authenticated read-back и дедупликацию.
5. Не добавляйте параметры `transfers`, payout credentials или старые Yandex.Checkout SDK: текущий адаптер их не обрабатывает.

Ожидаемый результат — обычный verified payment/refund одного выделенного магазина. Ни распределения денег между shops, ни перевода партнёру этот результат не подтверждает.

## Если рассматривается сплитование платежей

Официальное сплитование предназначено для платформ, где один платёж распределяется между подключёнными магазинами, а платформа может удерживать комиссию. Оно требует отдельного подключения:

1. Обратитесь в ЮKassa и прямо запросите «Сплитование платежей».
2. Подпишите необходимые документы и дождитесь фактического статуса платформы в разделе **Интернет-площадки**. ЮKassa не публикует гарантированный для N3 срок одобрения; обещание «одобрят за три дня» использовать нельзя.
3. Получите credentials платформы.
4. Пригласите продавцов, дождитесь их договоров и появления `shopId` у каждого.
5. Согласуйте комиссию платформы, возвраты, реестры и кассовый сценарий каждого магазина.
6. Проведите тестовые платежи с `transfers` по официальному контракту.

На этом шаге **не записывайте platform credentials в `.runtime/yookassa.json`**. Текущий N3 создаёт обычный single-shop payment и не формирует `transfers`/`platform_fee_amount`; использование platform key не добавит недостающую бизнес-логику.

Перед подключением к N3 нужна отдельная фича с контрактом:

- связь seller ↔ provider shop и её проверенная принадлежность tenant;
- распределение и комиссия как сохранённый до внешнего IO авторитетный snapshot;
- дедупликация и порядок payment/refund для каждого transfer;
- частичные возвраты и их распределение;
- чеки от имени соответствующего магазина;
- сверка provider registries с N3;
- миграция, тестовая приёмка и финансовый rollback.

До такой реализации ожидаемый результат от изучения кабинета — только подтверждение доступности продукта для вашего договора. N3 не должен отправлять split payment.

## Если нужны выплаты по API

Обычные выплаты ЮKassa — отдельный продукт для перевода денег физическим лицам. У него отдельный шлюз и credentials: `agentId` используется как login Basic Auth, секретный ключ относится к шлюзу выплат, а не к магазину приёма платежей.

Порядок подготовки у провайдера:

1. Сообщите менеджеру ЮKassa, что нужны выплаты по API; новый клиент следует актуальной форме/контакту на официальной странице подключения.
2. Согласуйте получателей, способы, лимиты, комиссию, идентификацию и требования к персональным данным.
3. Откройте требуемый расчётный счёт/шлюз и получите `agentId` и секретный ключ.
4. Настройте отдельные payout notifications и тестовый шлюз.
5. Проверьте успешные/неуспешные выплаты, повторы, баланс и ежедневные реестры.

Не помещайте `agentId`/payout secret в `shopId`/`secretKey` N3. У N3 нет payout adapter, config-схемы или webhook endpoint. Такая подмена либо даст ошибку аутентификации, либо создаст опасную путаницу полномочий.

До отдельной реализации N3 продолжает:

- агрегировать только подтверждённые денежные факты;
- готовить/утверждать точную ревизию реестра;
- экспортировать CSV без статуса отправки;
- принимать ручное подтверждение перевода с evidence;
- сохранять corrections/debt после возврата, а не автоматически списывать их с будущего заработка.

## Безопасная сделка не заменяет оба сценария

«Безопасная сделка» удерживает деньги покупателя до выполнения условий и затем позволяет выплатить продавцу или вернуть покупателю. Это отдельный договор и API-сценарий со сроком жизни сделки, ограничениями выплат и реестрами. Нельзя включить его одним полем в обычном N3 payment или считать эквивалентом сплитования.

## Тестовый и боевой переход

Для любого нового денежного продукта ведите доказательства отдельно:

1. **Документация/договор** — менеджер подтвердил доступный продукт и выданы test credentials.
2. **Изолированный контрактный тест** — запросы, подпись/read-back, повторы, перестановка и ошибки проверены без production денег.
3. **Provider sandbox/test** — dashboard и API показывают тестовый объект; деньги не переводятся.
4. **Небольшая боевая операция** — фактические деньги/возврат или payout сверены с кабинетом, банком и N3.
5. **Операционная готовность** — мониторинг, reconciliation, fiscal/legal обязанности, ротация и incident rollback отрепетированы.

Тестовый `test:true` объект не доказывает production. Одобрение договора не доказывает адаптер. Успешный ordinary payment не доказывает split или payout.

## Ошибки и остановка

| Признак | Решение |
|---|---|
| В старом документе указан Яндекс.Касса | определить API/версию; для современного single-shop перейти на runbook ЮKassa |
| Менеджер выдал platform/agent credentials | хранить отдельно; не загружать в текущий N3 |
| Ожидается автоперевод по CSV | остановить: N3 экспортирует данные, но не отправляет банк/provider payout |
| `transfers` отсутствуют в созданном payment | ожидаемо для текущего адаптера; split не реализован |
| Партнёр не получил деньги после payment | payment создаёт reward obligation, ручная выплата — отдельный процесс |
| Неясны сроки подключения | фиксировать ответ провайдера; не обещать срок, которого нет в официальном контракте |

## Ротация и rollback будущих интеграций

Credentials приёма, платформы и выплат должны иметь разные secret-файлы, владельцев и журнал ротации. Сначала разворачивают новый ключ и проверяют минимальную операцию/read-back, затем отзывают старый, если provider поддерживает overlap. При компрометации соответствующий ingress/egress отключают и сверяют все операции с момента риска.

После появления split/payout фактов нельзя откатываться на код, который их не понимает. Остановите новые операции, сохраните provider IDs, уведомления и реестры, затем выпускайте совместимый forward-fix. Никогда не удаляйте денежную историю ради повторного запуска.
