# Эксплуатация связки Proofwall → N3

Контрольная точка 2026-09-09. Публичные origins: `https://proofwall.aicoding.space` и `https://n3-a.212.192.0.33.sslip.io`. Tenant N3: `b439d03a-1156-48a6-b807-49bf77d44103`. Магазин остаётся TEST. Платёж создаёт Proofwall; он же принимает исходное уведомление `/api/webhooks/payment`. N3 получает идентификаторы событий через приватный API и самостоятельно перечитывает факты из ЮKassa.

## Развёрнутые версии

- Proofwall web/worker: `proofwall-web:bridge-229e7ee`, `proofwall-worker:bridge-229e7ee`; исходники main `229e7ee`, исправления автора `d9f5d6a`. Миграция `019_n3_bridge.sql` применена транзакционно.
- N3 API и A–D: `n3-api:bridge-acf124e`, `n3-{a,b,c,d}:bridge-acf124e`. Изолированная релизная ветка `codex/n3-proofwall-release`, commit `acf124efb4db8dd43e304d82c6b4cb3ce8cd8ebc`, основана на принятом `f8055e3`. Незавершённый access onboarding из main не включён.
- Версии фиксируют `compose.bridge-release.yml` внутри P1, P3 и каждой папки варианта. Для повторного запуска добавляйте этот overlay; не пересобирайте N3 из произвольного main до отдельной приёмки access onboarding.

Запуск из папки P3: `docker compose -f docker-compose.yml -f compose.bridge-release.yml up -d --no-build --no-deps api`.
Из папки каждого варианта: такая же команда с `frontend` вместо `api`.
Из папки P1: такая же команда с `web worker` вместо `api`. Не запускайте P1 `caddy`: порты 80/443 принадлежат существующему `ai-hub-tls-proxy`.

Перед каждым запуском проверяйте порты корневым `scripts/check-port-conflicts.sh`. Порты 13030–13034 при обновлении заняты теми же заменяемыми контейнерами; это проверенный перезапуск на месте, а не выделение новых портов. БД P1 и N3 не имеют host bindings. Сеть БД P1 — только её PostgreSQL/web/worker; сеть БД N3 — только её PostgreSQL/API. Проект 2 не изменяется.

## Конфигурация и ключи

P1 `.env`: `N3_BRIDGE_ENABLED=true`, публичный `N3_BASE_URL`, `N3_TENANT_ID`, секретный `N3_CONNECTOR_KEY`. Web и worker получают одинаковый ключ. Нативные `YOOKASSA_*`, `RESEND_API_KEY`, `MAIL_FROM` используются из существующей конфигурации P1.

P3 `.runtime/yookassa.json`: `enabled`, `tenantId`, тот же `shopId`/`secretKey` тестового магазина P1, `testMode:true`, `returnUrl:https://proofwall.aicoding.space/dashboard`. Этот deployment поддерживает один настроенный магазин/tenant. Повторное использование ключа P1 согласовано владельцем именно для независимой проверки оплаты; это не доступ к БД или внутренней сети P1.

Все файлы с секретами имеют режим 0600 и игнорируются Git. Значения не копируются в документацию. API читает конфигурацию при старте; после её изменения пересоздайте соответствующие контейнеры.

Операторский `scripts/provision-proofwall-bridge.mjs` предназначен для выполнения внутри N3 API с JSON stdin `{tenantId,connectorKey}`. Ключ заранее генерируется и надёжно сохраняется в закрытом файле. Скрипт проверяет существующего владельца, текущую версию его аккаунта, опубликованную денежную программу и участие партнёра. Он не создаёт пользовательские сеансы, не меняет подтверждение почты, не меняет правила и отказывается заменять другой существующий ключ. Повтор с тем же действующим ключом допустим. Срок ключа — 90 дней; штатную последующую ротацию выполняет владелец и обновляет P1 web/worker.

## Диагностика и откат

Проверки без секретов: P1 `GET /api/n3/program` → `{enabled:true}`; N3 `/health` → ok; `node scripts/check-deployment.mjs` из P3 проверяет закрытую БД и runtime.

В P1 `n3_bridge_outbox` сохраняет попытки и ошибки доставки. Повторы — от 60 секунд до часа, задания не выбрасываются. Смотрите статус/число ожидающих, не публикуйте payload с почтой. Не отмечайте задания доставленными вручную. Оплата, активация тарифа и постановка события в очередь атомарны; недоступность N3 не должна требовать новой оплаты.

Закрытый каталог на VPS:
`projects/03-affiliate-rewardful/.runtime/bridge-release/`.
В нём сохранены дампы `p1-before.dump`, `n3-before.dump`, прежняя конфигурация и JSON с прежними image IDs. Каталог не публикуется на GitHub.

При откате сначала остановите новые bridge-покупки (`N3_BRIDGE_ENABLED=false`, пересоздать P1 web/worker), сохраните новую очередь и финансовые факты для сверки. Затем верните прежние image IDs и конфигурацию через временный overlay. Миграция 019 добавочная: таблицы/очередь сохраняются. Не восстанавливайте старый дамп поверх новых оплат автоматически — он удалит события после резервной копии. Сетевую изоляцию БД сохраняйте при откате. При ротации ключа обновите P1 прежде, чем считать очередь работоспособной.

## Оплата успешна, но партнёрская комиссия не появилась

Обезличенный разбор типового сбоя. Суммы ниже — пример: покупка 990 ₽, ставка программы 20%, комиссия 198 ₽. Email, идентификаторы пользователей, организаций, заказов и платежей в разбор не включены.

### Признаки и диагностика

Партнёр видит нулевые вознаграждения и «Подтверждённых оплат: 0», хотя покупатель завершил оплату. Нулевой баланс сам по себе не доказывает сбой: тестовые комиссии исключаются из выплат. Проверять нужно весь путь:

1. Убедиться, что открыт кабинет нужного **партнёра**, а регистрация покупателя привязана к его ссылке.
2. Через authenticated GET API ЮKassa проверить существующий платёж: `status=succeeded`, `paid=true`, `test=true`, ожидаемые магазин, валюта RUB и сумма.
3. Сверить intent в Proofwall. Если он остаётся `pending`, тариф не активирован и в outbox нет `payment.succeeded`, проблема находится до передачи события в N3.
4. Проверить доставку HTTP-уведомления и журнал отказов Proofwall. Отсутствие записи об отказе не доказывает, что настройки магазина верны или что уведомление вообще приходило.
5. Если intent уже `completed`, проверить outbox: статус доставки, последнюю ошибку и повтор. Затем проверить платёж и комиссию нужного партнёра в N3.

**Не просить покупателя платить повторно.** Возврат браузера из платёжной формы и слова покупателя не заменяют проверку провайдера.

### Безопасное восстановление

Операторский `projects/01-testimonials-senja/scripts/reconcile-n3-payment.ts` запускается внутри P1 backend для конкретного существующего TEST-платежа. Он вызывает штатный `bridgeNotification`: независимо перечитывает факты ЮKassa, проверяет сохранённую привязку платежа к заказу/проекту, затем атомарно активирует тариф и ставит событие в outbox. Worker передаёт событие в N3, который самостоятельно проверяет платёж у провайдера.

Исходники собираются esbuild для Node с внешним `pg`; bundle исполняется в P1 web с `NODE_PATH=/app/node_modules`. Это административная процедура, а не публичный endpoint или автоматическая фоновая сверка. Нельзя подделывать IP провайдера, вручную начислять комиссию или помечать outbox доставленным.

После восстановления проверить: один платёж, одна комиссия, доставленное событие. Повторная сверка должна сохранить прежний `paid_until` и не создать дубликатов. Такая проверка была выполнена; автоматическая доставка следующего уведомления требует отдельной приёмки.

### Что увидит партнёр

После «Обновить данные» при первой тестовой покупке из примера:

| Показатель | Ожидаемое значение |
|---|---|
| Подтверждённых оплат | 1 |
| Оплат в тестовом магазине | 1 |
| Тестовые комиссии с учётом возвратов | 198.00 ₽ |
| Доступно / Удерживается / Отправлено по реестру | Без увеличения от тестовой покупки |

При отсутствии других операций денежные балансы останутся нулевыми. Если покупки уже были, проверять прирост показателей. Owner видит общую статистику программы; персональная комиссия отображается у партнёра, которому принадлежит реферальная ссылка.

### Настройка уведомлений для следующих покупок

В кабинете **нужного тестового магазина ЮKassa → Интеграция → HTTP-уведомления**:

- URL: `https://<proofwall-domain>/api/webhooks/payment` — подставить публичный домен Proofwall; это адрес P1, а не webhook N3.
- События: `payment.succeeded`, `payment.canceled`, `refund.succeeded`.
- Сохранить настройки и проверить автоматическую обработку следующего тестового платежа без операторской сверки.

При HTTP Basic Auth уведомления настраиваются в кабинете магазина. API управления webhook предназначен для OAuth; отказ этого API с Basic-ключом не означает, что ключ для чтения/создания платежей не работает. [Документация ЮKassa](https://yookassa.ru/developers/using-api/webhooks).

Не объявлять автоматическую цепочку исправной лишь по успешной ручной сверке. Реальные выплаты и боевой магазин этим сценарием не проверяются.
