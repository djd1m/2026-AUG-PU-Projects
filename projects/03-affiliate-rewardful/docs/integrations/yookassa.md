# ЮKassa: подключение магазина к N3

Дата сверки: **2026-09-09**. Эта инструкция описывает уже реализованный адаптер N3. Она не подтверждает договор, активацию магазина или успешный настоящий платёж: для этого нужны отдельные credentials и приёмочные операции владельца магазина.

## Что поддерживает N3

Один deployment N3 работает ровно с одним выделенным магазином ЮKassa и одной реальной организацией N3 (`tenantId`). Нельзя подключить один файл к нескольким магазинам или tenants. Для другого магазина нужен отдельный deployment либо доработка архитектуры.

Адаптер:

- создаёт платежи в RUB через API `https://api.yookassa.ru/v3`;
- использует HTTP Basic Auth: `shopId` как имя и секретный ключ магазина как пароль;
- принимает только `payment.succeeded` и `refund.succeeded` на `POST /api/webhooks/yookassa`;
- не доверяет телу уведомления как финансовому факту: сервер с теми же credentials перечитывает payment/refund из API ЮKassa и сверяет ID, магазин, test/live, валюту, сумму, статус и время;
- дедуплицирует подтверждённые payment/refund по provider business ID в PostgreSQL;
- не отправляет выплаты, не включает сплитование и не передаёт состав чека.

## 1. Подготовьте отдельный магазин

1. Войдите в личный кабинет ЮKassa под аккаунтом, доступ к которому не зависит от одного сотрудника.
2. Для первичной проверки создайте отдельный **тестовый магазин**. Не используйте Shop ID и ключи других проектов.
3. Откройте нужный магазин. Возьмите `shopId` в **Настройки → Магазин**.
4. Откройте **Интеграция → Ключи API**. Получите секретный ключ именно этого магазина. Боевой ключ выпускается и активируется по правилам кабинета; сохраните его сразу в менеджер секретов — кабинет может не показывать значение повторно.
5. В N3 войдите как владелец нужной организации. Возьмите её UUID `tenantId` из ответа `/api/account/me` для выбранного membership. Не переносите UUID из fixture/demo.
6. Выберите HTTPS `returnUrl`, например `https://n3-a.212.192.0.33.sslip.io/account`. Возврат браузера по этому адресу означает только возврат пользователя; он не доказывает оплату.

Тестовый и боевой магазины имеют разные Shop ID/ключи. Значение `testMode` в N3 обязано соответствовать полю `test` объектов выбранного магазина.

## 2. Запишите секрет N3

Канонический файл — ignored `.runtime/yookassa.json`, права `0600`. Безопасный отключённый вариант:

```json
{"enabled":false}
```

Для выбранного магазина файл должен иметь такую форму (значения ниже — placeholders, не credentials):

```json
{
  "enabled": true,
  "tenantId": "UUID_ОРГАНИЗАЦИИ_N3",
  "shopId": "ДЕСЯТИЧНЫЙ_SHOP_ID",
  "secretKey": "СЕКРЕТ_ВЫДЕЛЕННОГО_МАГАЗИНА",
  "testMode": true,
  "returnUrl": "https://n3-a.212.192.0.33.sslip.io/account"
}
```

API получает путь через `N3_YOOKASSA_CONFIG_FILE`; Docker Compose монтирует файл как `/run/secrets/n3_yookassa_config`. Не помещайте ключ в Compose environment, shell history, тикет, скриншот, `docker inspect` или Git.

После атомарной замены файла проверьте его владельца и режим доступа, затем проверьте занятые порты штатным скриптом проекта и пересоздайте только API:

```bash
docker compose up -d --force-recreate --wait api
```

Отсутствующий, пустой или некорректный enabled-конфиг должен останавливать/отключать реальную возможность, а не переводить её на fixture.

## 3. Настройте уведомления

В **Интеграция → HTTP-уведомления** выбранного магазина укажите один адрес:

```text
https://n3-a.212.192.0.33.sslip.io/api/webhooks/yookassa
```

Включите только:

- `payment.succeeded`;
- `refund.succeeded`.

Другие события текущий N3 отвергает и не применяет. URL должен быть доступен по HTTPS извне. Не ставьте промежуточный сервис, который меняет JSON, ID или направляет тестовые события в боевой deployment.

Native notification ЮKassa не несёт разделяемой HMAC-подписи, которую мог бы проверить N3. Документация провайдера рекомендует проверять подлинность по состоянию объекта или IP. N3 использует более узкий для своего контракта authenticated read-back: после уведомления запрашивает конкретный объект у фиксированного API ЮKassa. Успешный HTTP-ответ webhook ещё не заменяет сверку факта в N3.

## 4. Проверьте тестовый магазин

1. Оставьте `testMode:true`, перезапустите API и откройте `/account` выбранного домена.
2. Выберите именно организацию из `tenantId`. В платёжном блоке ожидается «Тестовый магазин ЮKassa … настроен; API проверяется при запросе». Это проверяет чтение конфигурации, но не доступность API.
3. Опубликуйте cash-условия и подготовьте допустимого получателя/заказ штатным UI или connector flow.
4. Создайте один тестовый checkout. Сохраните N3 `orderId`, provider `paymentId` и используйте тот же idempotency key при сетевом повторе. Не создавайте новый заказ, чтобы скрыть неопределённый исход старого.
5. Перейдите по `confirmationUrl` и используйте тестовые данные только из актуальной страницы ЮKassa. Настоящие карты в тестовом магазине использовать нельзя.
6. Дождитесь `payment.succeeded`. Проверьте три разных сигнала:
   - **конфигурация прочитана** — UI показывает test shop;
   - **провайдер ответил** — checkout получил provider ID/confirmation URL;
   - **событие применено** — после authenticated read-back заказ и финансовый факт N3 перешли в подтверждённое состояние.
7. Повторно доставьте то же уведомление или дождитесь provider retry: итог и начисление не должны удвоиться.
8. Создайте возврат в кабинете ЮKassa, дождитесь `refund.succeeded` и проверьте одну неизменяемую коррекцию. Возврат до уведомления об оплате также должен разрешиться после перечитывания исходного платежа.

Тестовый платеж не переводит деньги и не является боевой приёмкой.

## 5. Чеки и переход в боевой режим

До боевого включения владелец вместе с бухгалтером/юристом определяет требования 54-ФЗ, тип кассы, ставки НДС, предмет/способ расчёта и контакты покупателя. ЮKassa требует данные `receipt` в соответствующих сценариях. Текущий N3-адаптер **не передаёт составной чек** при создании платежа/возврата, поэтому включать production для сценария, где чек обязан формироваться через API, нельзя до отдельной реализации и приёмки.

Для production:

1. Завершите договорное подключение настоящего магазина и настройте способы оплаты/кассу в кабинете.
2. Выпустите отдельный боевой ключ и повторите настройку двух уведомлений в настоящем магазине.
3. В окно обслуживания атомарно замените все связанные значения: `shopId`, `secretKey`, `testMode:false`, `tenantId`, `returnUrl`.
4. Пересоздайте API. Старые незавершённые заявки другого shop/test-mode N3 не должен продолжать как новые.
5. Выполните минимальный настоящий платёж на согласованную сумму и полный/частичный возврат; сверьте кабинет ЮKassa, N3 и банковские/кассовые записи.

До выполнения этих шагов корректная формулировка статуса: «контрактные тесты пройдены, внешняя тестовая/боевая приёмка не выполнена».

## Ошибки

| Признак | Что проверить |
|---|---|
| `PAYMENT_UNCONFIGURED` или UI «не подключена» | `enabled`, точный `tenantId`, mount и `N3_YOOKASSA_CONFIG_FILE`; выбран ли тот membership |
| 401/403 от ЮKassa | пара `shopId:secretKey`, магазин и среда; ключ не урезан и не от другого проекта |
| `SHOP_CHANGED` | существующая заявка создана с другим shop/test-mode; остановить повторы и сверить её вручную |
| Checkout создан, подтверждения нет | статус payment в кабинете, URL уведомления и выбранные события; return URL не считать доказательством |
| Webhook принят, факт не применён | read-back payment/refund, совпадение ID, RUB, суммы, `recipient.account_id`, `test`, succeeded/paid |
| Повтор через 23 часа остаётся неопределённым | не обходить новой заявкой: ЮKassa хранит idempotency key 24 часа, нужна ручная сверка |
| Нет чека | это известная граница адаптера; остановить боевой запуск и реализовать согласованный receipt-сценарий |

## Ротация и откат

При штатной ротации сначала выпустите новый ключ по процедуре ЮKassa, замените файл, пересоздайте API и проверьте authenticated GET/новый тестовый заказ; только затем удаляйте старый ключ, если кабинет допускает период перекрытия. При компрометации сразу отключите/удалите старый ключ в кабинете, установите `{"enabled":false}`, пересоздайте API и сверяйте все заявки с момента утечки.

После появления provider-заказа нельзя откатывать backend на версию, которая не понимает его записи, поздние дубли или возвраты. При дефекте остановите payment ingress, сохраните таблицы/события и делайте совместимое исправление вперёд. Отключение конфигурации прекращает новые операции, но не удаляет обязательства и историю.
