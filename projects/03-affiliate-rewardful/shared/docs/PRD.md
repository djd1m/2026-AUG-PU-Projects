# Общий PRD N3 — ядро четырёх вариантов

Версия: draft1, 2026-09-08. Статус: F1 synthetic разрешён владельцем к автономной реализации 2026-09-08; production financial integration — отдельный этап. Это обязательная общая часть PRD вариантов A/B/C/D. Требования интерфейса варианта не переопределяют правила денег и доступа. При конфликте — остановка затронутой реализации и явное изменение общего контракта.

## Задача и границы

Дать владельцу SaaS один достоверный учёт рекомендаций, оплат, вознаграждений и ручных выплат; клиенту/партнёру — объяснимый личный результат; их агентам — те же возможности в рамках делегации. Четыре варианта проверяют разные способы получения пользы на общей модели данных. Источники: [discovery](../../docs/product-discovery-brief.md), [payout decisions](../../docs/discovery/payout-decisions.md), [agent decisions](../../docs/discovery/agent-interface-cjm.md).

**Решения владельца:** отдельная папка каждого варианта, общий код, ЮKassa как база, ручные выплаты за предыдущий месяц до5-го следующего, агентные интерфейсы MCP/A2A. До100 партнёров — допущение о ручной работе. Подписочные бонусы B — эксперимент, отдельный от cash commissions. Marketplace split Яндекс Кассы/ЮKassa и CloudPayments — будущие отдельные адаптеры по документации; production не считается проверенным.

## Режимы готовности

| Режим | Допустимый результат | Недопустимое заявление |
|---|---|---|
| F0: текущий HTML | Локальные демонстрации сценариев | Рабочий backend или протокол |
| F1: функциональный стенд | Четыре приложения/профиля с общими use cases, fixture adapters и сохранением тестовых данных | Реальные деньги/production integration |
| F2: интеграционный кандидат | Код провайдера, подтверждённые contract/sandbox tests по доступности | Успешный production без проверки |
| F3: ограниченный пилот | Известные роли/правила, доступы/договоры, сверка и операционный владелец | Автоматический rollout всем партнёрам |

Следующий предлагаемый результат реализации — F1, чтобы выбрать/смешать варианты на работающих сценариях. Выплаты в F1 исключительно демонстрационные. Переходы F1→F2→F3 отдельные решения после приёмки.

## Приёмка по режимам: бизнес-семантика и реальный протокол

Названия UI/MCP/A2A в SC описывают целевой доступ к одной операции. F1 проверяет её бизнес-семантику через общий application layer и fixture actor/transport harness; UI действительно подключён к backend, MCP/A2A пока имитируются. Требование wire interoperability не объявляется выполненным этим harness.

| Рубеж | Обязательная проверка | Что остаётся непроверенным |
|---|---|---|
| F1 / W1–W3 | Все business SC на fixtures; UI journeys, проверка ролей/делегации; три logical channel contexts через test harness | MCP/A2A handshake, serialization, OAuth/client interoperability, стоимость реального LLM |
| W4 / protocol candidate | Те же SC через выбранные настоящие MCP/A2A clients/endpoints; negotiation/errors/auth/cancel и parity | Реальные денежные операции и доступность платёжного провайдера |
| F2/F3 payment integration | Проверенные provider fields, confirmed events, sandbox/production evidence по capability | Неизмеренные capability остаются unknown |

W3 даёт сравнение композиций сценариев и правильности business-state. Скорость/расход настоящего агентного взаимодействия сравниваются после W4 и подключения реального клиента/модели; результат simulator не выдаётся за agent productivity.

## Общие пользовательские истории

### US-001 — ограничение доступа
Как владелец/партнёр, хочу работать только с разрешёнными данными независимо от интерфейса.

- **SC-US-001-1:** Given пользователь tenantX, When запрашивает resource tenantY через UI/MCP/A2A, Then отказ до чтения/изменения, отсутствие чужих полей в ответе.
- **SC-US-001-2:** Given партнёрX, When запрашивает общий реестр или запись партнёраY, Then отказ; знание ID и выбор варианта не дают доступа.
- **SC-US-001-3:** Given пользователь имеет две роли, When переключает рабочий контекст, Then сервер проверяет членство и роль заново; UI отображает действующего субъекта.

### US-002 — атрибуция и повторные оплаты
Как владелец, хочу начислять вознаграждение только за подтверждённую оплату.

- **SC-US-002-1:** Given подтверждённый платёж, When событие доставлено дважды/параллельно, Then одно эффективное начисление на business payment id и reward policy, а не на delivery attempt.
- **SC-US-002-2:** Given тот же клиент оплатил следующий период, When пришёл новый подтверждённый payment id, Then отдельное начисление, если версия политики предусматривает recurring; converted referral не блокирует renewal.
- **SC-US-002-3:** Given событие не проверено у провайдера или проверка недоступна, When поступило уведомление, Then оно не становится подтверждённым доходом, доступен повтор/сверка.
- **SC-US-002-4:** Given одновременно ссылка и промокод, When атрибуция разрешается, Then применяется одна версия правила. Предложение пилота: явный промокод приоритетен, неверный явный код не даёт скрытого cookie fallback; это требует утверждения до F2.

### US-003 — объяснимое вознаграждение
Как получатель, хочу знать источник суммы, удержание и коррекции.

- **SC-US-003-1:** Given оплата/возврат/пересчёт, When изменяется экономический итог, Then сохраняются исходная запись и коррекция с причиной/ссылкой на событие; история не переписывается под текущую ставку.
- **SC-US-003-2:** Given cash и subscription credit, When строится баланс, Then разные типы обязательств и доступности; credit нельзя выгрузить как денежную выплату или автоматически конвертировать в cash.
- **SC-US-003-3:** Given возврат уже оплаченной комиссии, When он обработан, Then видна корректировка/задолженность и необходимость сверки; физический перевод не объявляется автоматически отменённым.

### US-004 — ручной месячный реестр
Как владелец, хочу подготовить и отправить правильные суммы до5-го.

- **SC-US-004-1:** Given выбранный период и допустимые к выплате начисления, When подготовлен реестр, Then видны период, получатели, сумма, валюта, версия, исключения; не включены уже отправленные позиции и credits.
- **SC-US-004-2:** Given утверждена версияV1, When состав/сумма меняется, Then появляется новая версия и старое утверждение неприменимо; экспорт требует действующего утверждения этой версии.
- **SC-US-004-3:** Given CSV выгружен, When его скачивание завершилось, Then статуса «отправлено» нет. Отдельная отметка владельца содержит дату/оператора/основание, не гарантирует зачисление.
- **SC-US-004-4:** Given повторная подготовка периода, When одинаковый запрос повторён, Then не возникает второй набор подлежащих оплате обязательств; экспорт сам по себе не резервирует новую выплату.

- **SC-US-004-5:** Given одно cash-обязательство доступно двум одновременно подготовленным реестрам, When утверждаются оба, Then оно атомарно закрепляется только за одним действующим settlement; второй получает конфликт и пересчёт. Разные idempotency keys не создают право платить его дважды.
- **SC-US-004-6:** Given обязательство уже помечено отправленным, When другой оператор/агент повторяет отметку с другим ключом, Then второй факт отправки не увеличивает выплаченную сумму; исправление ошибочной отметки — отдельная аудируемая процедура.

- **SC-US-004-7:** Given утверждённый, но не отправленный реестр с allocations, When новый подтверждённый refund меняет source snapshot, Then в одной транзакции старое утверждение/экспорт становятся недействительными, только неотправленные allocations освобождаются либо переносятся в новую явно неутверждённую версию. Отправленные строки не освобождаются.
- **SC-US-004-8:** Given оператор фактически перевёл деньги по ранее скачанному устаревшему CSV, When фиксирует это после refund, Then факт не скрывается и не отбрасывается как будто перевода не было: создаётся reconciliation exception с исходной версией/суммой и отдельной коррекцией; запись не означает разрешение нового перевода.

### US-005 — одинаковые действия UI и агентов
Как владелец, хочу делегировать подготовку и продолжать тот же результат вручную.

- **SC-US-005-1:** Given действующий grant чтения/черновика, When агент выполняет разрешённую задачу, Then нет лишнего подтверждения каждого чтения; approve/pay/send из этого grant не следуют.
- **SC-US-005-2:** Given grant отозван/истёк, When начинается следующий защищённый шаг либо отдаётся новый защищённый результат, Then он отвергается; сохранённый результат доступен владельцу по его собственным правам.
- **SC-US-005-3:** Given агентный артефакт id/version/hash, When владелец продолжает в UI, Then использует тот же артефакт, суммы и правила; переключение канала не создаёт новый расчёт.
- **SC-US-005-4:** Given задача отменена, When приходит поздний ответ, Then он не продвигает отменённую задачу и не записывается как результат новой задачи; cancel не объявляется отменой внешнего перевода.

### US-006 — сравнение без перемешивания данных
Как исследователь продукта, хочу сравнить варианты без повторных начислений и несопоставимых выводов.

- **SC-US-006-1:** Given один тестовый dataset, When запускаются варианты, Then каждому сеансу выделен изолированный sandbox/tenant; не объединяются fake balances разных испытаний.
- **SC-US-006-2:** Given переход UI↔agent внутри одной задачи, When передан artifact reference, Then сохраняются tenant/subject и версия; изоляция экспериментальных сеансов не разрывает этот переход.
- **SC-US-006-3:** Given реальный пилот, When один платёж виден в нескольких интерфейсах, Then он обрабатывается общим backend ровно один раз, а варианты читают один ledger.

## Общие NFR и критерии F1

- Доступ, суммы, повторобезопасность и версии проверяются в общем application/domain слое. Браузерная часть варианта не имеет прямого доступа к БД, provider SDK или вычислениям комиссий.
- Денежные величины — целые minor units с currency; дата платежа, effective time, период и policy version сохраняются. Правила округления/переноса/часового пояса обязательны до F2.
- Интерфейс адаптируется к390/1440px, работает с клавиатуры; скрытие элемента не считается авторизацией.
- Ошибки/ожидание/нет данных/отказ/частичный результат различаются. Нет подтверждения провайдера — нет ложного успеха.
- F1 acceptance: общие сценарии выше + локальные PRD; mutation для отказа доступа и версии; повтор/параллельный payment; рефанд до/после отправки; cross-channel parity. Общие изменения гоняют регрессию всех4 вариантов.
- Performance budget для F1: измерить время до принятого результата и интерфейсные задержки на фиксированном стенде; SLA не утверждено, неизвестные измерения не заменять нулём.
- Секреты провайдеров не включаются в браузер/fixture/HTML; серверное безопасное хранение и ownership уточняются в архитектуре F2. Предложение типового browser-only хранения не подходит unattended webhook и не принимается автоматически.

## Экономика и измерения

Цена1990₽, ставка20%, bonus300₽, window30дней, hold14дней — примерные данные HTML, не утверждённый production контракт. Продуктовые targets формируются по пилоту; сейчас измеряем baseline.

| Метрика | Источник значения | Условие сравнения |
|---|---|---|
| Время до принятого без ошибок реестра | ручное измерение: одинаковое задание, старт/принятие | Та же роль, набор оплат и условия; UI vs D |
| Ошибки суммы/получателей и число исправлений | наш журнал | Сверка с эталонным fixture, одинаковый task id |
| Activation → paid recommendation | наша БД | Отдельные cohorts клиентов B и внешних партнёров C |
| Работа оператора на закрытие месяца | ручное измерение: таймер операций сверки | Размер реестра/исключений одинаков |
| Расход на принятую агентную задачу | наш журнал | Только provider counters; unknown при их отсутствии |

## Решения до реальных денег

Владелец продукта: утвердить attribution/recurring/округление/hold, cutoff и перенос после5-го, возврат после отправки, payer/payee модель, credit применение и лимиты, platform pricing. Технический владелец: доступность провайдеров/секретов, tenant/identity, реальные contract/sandbox evidence. Эти вопросы не блокируют изолированный F1 на явно заданных фикстурах; блокируют обещание готового F2/F3.
