# PRD C — Внешний партнёр контролирует доход

Версия: draft1 · 2026-09-08 · статус: F1 разрешён владельцем к автономной реализации 2026-09-08; production не разрешён.

## Обязательная общая часть

[Общий PRD ядра](../../../shared/docs/PRD.md) входит в этот PRD целиком. Истории US-001…006 обязательны. Этот документ задаёт различия опыта, не переопределяет деньги/права. [Архитектура](../../../docs/variant-architecture.md) · [План](../../../docs/variant-implementation-plan.md).

## Для кого и зачем

**Пользователь:** Автор, агентство или специалист, рекомендующий SaaS своей аудитории.
**Задача:** Понять условия, вступить и самостоятельно увидеть происхождение комиссии и срок ручной выплаты.
**Гипотеза:** Сценарий C полезен, если партнёр без обращения в поддержку находит правильные условия, сумму и статус выплаты.

## Путь и объём F1

1. Открытые условия программы.
2. Добровольное вступление и ссылка.
3. История оплаты и своей комиссии.
4. Личный payout status за месяц.
5. Вид владельца: тариф сервиса.
6. Материалы и текст рекомендации.

[Текущий HTML-прототип](../prototype/index.html) показывает идею, а не выполненные критерии F1. Следующая реализация должна сохранять состояние через общий application layer, иметь реальные программные границы/ошибки и воспроизводимый fixture seed. Ничего не списывает и не отправляет.

## Пользовательские истории и критерии приёмки

### US-301 — Понять условия до вступления
Как партнёр, хочу заранее знать правила комиссии и срок выплат.

- **SC-US-301-1:** Given есть опубликованная версия программы; When открывает public terms; Then видит тип/ставку/окно/удержание/порядок выплат, дату версии и статус участия.
- **SC-US-301-2:** Given условия изменились; When просматривает старое начисление; Then видит применённую историческую версию, не только текущую ставку.

### US-302 — Вступить и получить ссылку
Как партнёр, хочу получить свой инструмент рекомендации.

- **SC-US-302-1:** Given подтвердил участие в программе; When enrollment принят по fixture policy; Then получает personal referral link/share kit, отличный от enrollment URL.
- **SC-US-302-2:** Given тот же запрос повторён; When вступает второй раз; Then не создаются второй партнёр/дублирующая атрибуция; возвращается существующее участие.

### US-303 — Понять свою выплату
Как партнёр, хочу видеть сумму, период и состояние перевода.

- **SC-US-303-1:** Given есть собственный начисленный доход; When открывает history/payout; Then видит только свои записи и причины hold/коррекции, ориентир до5-го следующего месяца.
- **SC-US-303-2:** Given владелец пометил перевод отправленным; When обновляет статус; Then видит отправку с датой; зачисление не утверждается без отдельного подтверждения.

### US-304 — Спросить своего агента
Как партнёр, хочу узнать статус через своего ассистента.

- **SC-US-304-1:** Given личный grant разрешает own payout read; When UI или MCP/A2A запрашивает статус; Then возвращается один и тот же actor-scoped результат с источником/временем.
- **SC-US-304-2:** Given в запросе указан другой partner id; When агент вызывает tool/task; Then доступ отвергается даже при известном ID; общий реестр не раскрывается.

## Владение и переиспользование

**Владеет вариант:** Public terms, partner portal, onboarding и контент share kit.
**Импортирует из shared:** Cash ledger, program policies, own payout projection, enrollment, actor/grant, статусные UI компоненты.

Другие варианты не импортируются. Нужная нескольким вариантам возможность переносится в shared через общий контракт и parity tests. В браузере допускаются только contracts, клиентский фасад и UI; серверные use cases вызываются через транспорт. Прямое чтение БД, provider SDK и вычисление денежных итогов в variant UI запрещены.

## UI и альтернативные пути

Визуальная основа — измеренный публичный Rewardful, адаптация под роли. Поддержка390/1440px и клавиатуры, состояния loading/empty/error/denied, понятное восстановление. Переключатель лаборатории не меняет роль пользователя. В продакт-режиме нет случайного перехода партнёра в оплату владельца; обзор других ролей — отдельная демосреда.

## Зависимости и ограничения

Доступ к чужим клиентским данным/полным реквизитам не нужен. До F2 согласовать состав личного кабинета, документы получателя и спорные выплаты. Авто-поиск/массовые рассылки партнёрам не входят в F1.

F1 использует только изолированные fixtures. Внешние подтверждения и договорные условия берутся из общего PRD/реестра интеграций. Даты/скорость провайдера/экономия не обещаются без измерений.

## Метрики и выбор

- Время до правильного ответа о выплате.
- Обращения по суммам/100 начислений.
- Квалифицированное enrollment → оплаченная рекомендация.

Источники: наш журнал для событий/ошибок; наша БД для paid conversion; ручное измерение: таймер одинакового задания; provider usage сохраняется в наш журнал только при доступности. Численные бизнес-targets не утверждены. A/B/C оцениваются на своих аудиториях; D сравнивается с соответствующим UI на одинаковой задаче.

## Выпуск и открытые решения

F1: пользовательский путь, общий seed/use cases, позитивные и отрицательные сценарии, route/role tests; приемлемость оценивается по SC этого PRD и общего ядра. F2: интеграции и полная спецификация финансов/доступа после решения владельца. F3: ограниченный пилот, сверка и метрики. Сроки не назначены до оценки W0/W1 в общем плане.

Выбор варианта пока не сделан. После эксперимента допустим гибрид; не требуется переносить код между четырьмя репозиториями. Устаревающая оболочка архивируется после переноса нужных сценариев, общие доменные данные сохраняются.
