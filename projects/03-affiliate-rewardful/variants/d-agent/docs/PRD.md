# PRD D — Поручение личному агенту

Версия: draft1 · 2026-09-08 · статус: на согласовании, реализация F1 запланирована.

## Обязательная общая часть

[Общий PRD ядра](../../../shared/docs/PRD.md) входит в этот PRD целиком. Истории US-001…006 обязательны. Этот документ задаёт различия опыта, не переопределяет деньги/права. [Архитектура](../../../docs/variant-architecture.md) · [План](../../../docs/variant-implementation-plan.md).

## Для кого и зачем

**Пользователь:** Владелец либо партнёр, предпочитающий выполнить задачу через личного агента.
**Задача:** Получить проверяемый результат по поручению, ограничить полномочия агента и сохранить возможность продолжить вручную.
**Гипотеза:** Сценарий D выигрывает конкретную задачу, если даёт столь же правильный результат быстрее/дешевле по полному циклу, чем сопоставимый UI.

## Путь и объём F1

1. Поручение и ожидаемый результат.
2. Ограниченная делегация.
3. Артефакт с расчётом и исключениями.
4. Проверка версии, отзыв и ручное продолжение.
5. Тариф владельца/лимиты агентного доступа.
6. Личный agent-to-agent запрос партнёра.

[Текущий HTML-прототип](../prototype/index.html) показывает идею, а не выполненные критерии F1. Следующая реализация должна сохранять состояние через общий application layer, иметь реальные программные границы/ошибки и воспроизводимый fixture seed. Ничего не списывает и не отправляет.

## Пользовательские истории и критерии приёмки

### US-401 — Делегировать задачу
Как владелец, хочу дать агенту ровно нужные возможности.

- **SC-US-401-1:** Given идентифицирован пользователь/tenant и цель; When подтверждает read+draft grant; Then показаны срок, субъект и scope; платёж/approve/send не входят в grant.
- **SC-US-401-2:** Given grant истёк/отозван; When агент начинает новый защищённый шаг; Then операция запрещена; UI владельца остаётся доступен по независимым правам.

### US-402 — Получить один результат
Как владелец, хочу доверять структуре и объяснению результата.

- **SC-US-402-1:** Given есть один logical task и fixture payments; When повторяет запрос подготовки; Then получает тот же logical artifact или явно новую версию, без второго payable registry.
- **SC-US-402-2:** Given появился refund; When запускает пересчёт; Then меняются и строки/сумма, и объяснение; прошлое утверждение недействительно.

### US-403 — Проверить и продолжить вручную
Как владелец, хочу утвердить конкретную версию и передать её в A.

- **SC-US-403-1:** Given видит artifact id/version/hash; When утверждает и выгружает; Then получает только утверждённое содержимое; экспорт не запускает перевод.
- **SC-US-403-2:** Given доступ агента отозван после пересчёта; When владелец открывает ручное продолжение; Then получает тот же исправленный реестр; новое owner approval разрешено без оживления grant агента.

### US-404 — Вести задачу между агентами
Как партнёр, хочу дождаться личного ответа или отменить запрос.

- **SC-US-404-1:** Given есть own-status grant и taskT1; When создаёт запрос, затем повторяет его; Then видит тот же task и статус, без повторного начисления/отправки.
- **SC-US-404-2:** Given T1 отменён, затем создан T2; When приходит поздний ответ с taskT1; Then ответ не завершает T2; отмена не объявляется rollback внешних действий.

## Владение и переиспользование

**Владеет вариант:** Intent/task UI, grant presentation, artifact view, UI handoff и демонстрация remote task.
**Импортирует из shared:** Все финансовые use cases, authorization/delegation/task state, schemas, MCP/A2A adapters в shared; D не содержит свой калькулятор комиссии.

Другие варианты не импортируются. Нужная нескольким вариантам возможность переносится в shared через общий контракт и parity tests. В браузере допускаются только contracts, клиентский фасад и UI; серверные use cases вызываются через транспорт. Прямое чтение БД, provider SDK и вычисление денежных итогов в variant UI запрещены.

## UI и альтернативные пути

Визуальная основа — измеренный публичный Rewardful, адаптация под роли. Поддержка390/1440px и клавиатуры, состояния loading/empty/error/denied, понятное восстановление. Переключатель лаборатории не меняет роль пользователя. В продакт-режиме нет случайного перехода партнёра в оплату владельца; обзор других ролей — отдельная демосреда.

## Зависимости и ограничения

F1: детерминированный task runner и fixture transport, явно помеченные. F2: реальные MCP/A2A adapters с контрактными тестами и выбранным клиентом. Рабочий стандартный endpoint и настоящий LLM не объявлять существующими по наличию чат-экрана.

F1 использует только изолированные fixtures. Внешние подтверждения и договорные условия берутся из общего PRD/реестра интеграций. Даты/скорость провайдера/экономия не обещаются без измерений.

## Метрики и выбор

- UI vs agent: время до принятого результата.
- Исправления человеком и доля неверных ответов.
- Токены/credits и повторы на принятую задачу.

Источники: наш журнал для событий/ошибок; наша БД для paid conversion; ручное измерение: таймер одинакового задания; provider usage сохраняется в наш журнал только при доступности. Численные бизнес-targets не утверждены. A/B/C оцениваются на своих аудиториях; D сравнивается с соответствующим UI на одинаковой задаче.

## Выпуск и открытые решения

F1: пользовательский путь, общий seed/use cases, позитивные и отрицательные сценарии, route/role tests; приемлемость оценивается по SC этого PRD и общего ядра. F2: интеграции и полная спецификация финансов/доступа после решения владельца. F3: ограниченный пилот, сверка и метрики. Сроки не назначены до оценки W0/W1 в общем плане.

Выбор варианта пока не сделан. После эксперимента допустим гибрид; не требуется переносить код между четырьмя репозиториями. Устаревающая оболочка архивируется после переноса нужных сценариев, общие доменные данные сохраняются.
