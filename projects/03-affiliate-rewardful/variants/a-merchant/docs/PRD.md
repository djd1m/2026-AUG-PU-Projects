# PRD A — Владелец запускает программу

Версия: draft1 · 2026-09-08 · статус: на согласовании, реализация F1 запланирована.

## Обязательная общая часть

[Общий PRD ядра](../../../shared/docs/PRD.md) входит в этот PRD целиком. Истории US-001…006 обязательны. Этот документ задаёт различия опыта, не переопределяет деньги/права. [Архитектура](../../../docs/variant-architecture.md) · [План](../../../docs/variant-implementation-plan.md).

## Для кого и зачем

**Пользователь:** Владелец небольшого SaaS с уже работающей оплатой.
**Задача:** Запустить партнёрский канал и закрыть месяц с проверяемым реестром, не собирая цифры в нескольких системах.
**Гипотеза:** Сценарий A победит для владельца, если он быстрее получает правильный первый результат и закрывает месяц с меньшим числом исправлений.

## Путь и объём F1

1. Превью программы и явные условия.
2. Подключение fixture payment source, настройки политики.
3. Первая подтверждённая оплата и объяснение начисления.
4. Реестр/версия/утверждение/CSV.
5. Тариф сервиса для владельца.
6. Приглашение партнёров по enrollment URL.

[Текущий HTML-прототип](../prototype/index.html) показывает идею, а не выполненные критерии F1. Следующая реализация должна сохранять состояние через общий application layer, иметь реальные программные границы/ошибки и воспроизводимый fixture seed. Ничего не списывает и не отправляет.

## Пользовательские истории и критерии приёмки

### US-101 — Настроить программу
Как владелец, хочу задать правила и увидеть их до публикации.

- **SC-US-101-1:** Given есть права владельца и fixture project; When сохраняет валидные ставку/окно/тип вознаграждения; Then создана версия политики, видимая в preview; будущие начисления ссылаются на неё.
- **SC-US-101-2:** Given ставка отсутствует или значение вне разрешённого диапазона; When пытается опубликовать; Then публикация запрещена с исправляемой ошибкой; скрытого default нет.

### US-102 — Проверить начисление
Как владелец, хочу связать реальную оплату с партнёром и объяснить итог.

- **SC-US-102-1:** Given есть confirmed fixture payment и атрибуция; When запускает пример начисления; Then видит событие/правило/сумму/hold; общий SC-US-002 применяется.
- **SC-US-102-2:** Given после оплаты зарегистрирован возврат; When повторно получает старое событие оплаты; Then коррекция остаётся; комиссия не восстанавливается из-за delivery replay.

### US-103 — Закрыть месяц
Как владелец, хочу утвердить реестр и организовать переводы до5-го.

- **SC-US-103-1:** Given есть eligible cash entries за месяц; When готовит/проверяет/утверждает реестр; Then выгружает именно эту версию и видит исключённые строки.
- **SC-US-103-2:** Given уже выгрузил CSV; When ещё не делал перевод; Then интерфейс не показывает отправку; отдельная отметка хранит оператора и дату.

### US-104 — Пригласить и передать работу агенту
Как владелец, хочу делиться условиями и продолжать ту же задачу другим каналом.

- **SC-US-104-1:** Given создана программа; When копирует приглашение; Then получает enrollment link, а не customer referral link; отображается действующая ставка.
- **SC-US-104-2:** Given агент подготовил исправленную версию реестра; When открывает её в A; Then тот же id/version/hash/суммы доступны по правам владельца; не подставляется старый demo dataset.

## Владение и переиспользование

**Владеет вариант:** Композиция мастера и кабинета владельца, merchant copy и route-level tests.
**Импортирует из shared:** Первые начисления, monthly registry, approve/export, policy version, authorization и UI таблицы.

Другие варианты не импортируются. Нужная нескольким вариантам возможность переносится в shared через общий контракт и parity tests. В браузере допускаются только contracts, клиентский фасад и UI; серверные use cases вызываются через транспорт. Прямое чтение БД, provider SDK и вычисление денежных итогов в variant UI запрещены.

## UI и альтернативные пути

Визуальная основа — измеренный публичный Rewardful, адаптация под роли. Поддержка390/1440px и клавиатуры, состояния loading/empty/error/denied, понятное восстановление. Переключатель лаборатории не меняет роль пользователя. В продакт-режиме нет случайного перехода партнёра в оплату владельца; обзор других ролей — отдельная демосреда.

## Зависимости и ограничения

Публичная публикация условий и реальные ключи не входят в F1. До F2 утвердить recurring/attribution/период/hold; повторно использовать код Proofwall только после audit.

F1 использует только изолированные fixtures. Внешние подтверждения и договорные условия берутся из общего PRD/реестра интеграций. Даты/скорость провайдера/экономия не обещаются без измерений.

## Метрики и выбор

- Время до правильного первого начисления.
- Ошибки реестра и время закрытия месяца.
- Доля завершённых приглашений партнёров.

Источники: наш журнал для событий/ошибок; наша БД для paid conversion; ручное измерение: таймер одинакового задания; provider usage сохраняется в наш журнал только при доступности. Численные бизнес-targets не утверждены. A/B/C оцениваются на своих аудиториях; D сравнивается с соответствующим UI на одинаковой задаче.

## Выпуск и открытые решения

F1: пользовательский путь, общий seed/use cases, позитивные и отрицательные сценарии, route/role tests; приемлемость оценивается по SC этого PRD и общего ядра. F2: интеграции и полная спецификация финансов/доступа после решения владельца. F3: ограниченный пилот, сверка и метрики. Сроки не назначены до оценки W0/W1 в общем плане.

Выбор варианта пока не сделан. После эксперимента допустим гибрид; не требуется переносить код между четырьмя репозиториями. Устаревающая оболочка архивируется после переноса нужных сценариев, общие доменные данные сохраняются.
