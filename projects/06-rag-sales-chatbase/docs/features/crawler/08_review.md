# crawler — независимое ревью

**Фича:** 4 `crawler` · **Дата:** 2026-09-25 · **Автор кода:** Opus 5.5 · **Ревьюер:** Sonnet 5 (независимый
агент; код не менялся) · **Исходники:** [`07_code_report.md`](07_code_report.md), [`05_completion.md`](05_completion.md),
A-N6-026 · Не полный cross-family review (только Anthropic, с 25.09.2026) — фиксируется как есть.

## Вердикт: **REJECT**

Проверка адреса (SSRF) выполнена образцово — 34 запрещённые формы, разрешающий список для IPv6, DNS
проверяется целиком, каждый `Location` — заново, соединение строго по проверенному IP, тест-стенд
структурно (а не только утверждением) не даёт соединиться с непроверенным адресом. Ни одного обхода
`CheckAddress` найти не удалось.

Но найдены **два независимых, воспроизводимых способа положить весь воркер** (не одну задачу — весь
однопоточный процесс Node) содержимым, которое приходит с чужого сайта, то есть ровно из того
источника, который этот код по своей же постановке обязан считать враждебным (`security.md`: «чужой
контент... может быть враждебным»). Ни один не покрыт тестом или мутацией, оба — в зоне, которую
задание ревью прямо просило проверить («не зависает ли на патологическом вводе, ReDoS»). Роадмап
отмечает фичу `done`; с этим классом дефекта — рано.

## Находки

### BLOCKER-1 — ReDoS в разборе `robots.txt`: `compile()`

**Файл:** `apps/worker/src/crawl/robots.ts:14-18` (используется в `isAllowed`, `robots.ts:53-55`,
вызывается на КАЖДЫЙ кандидатный URL обхода, `crawl-site.ts:144,168`).

```ts
function compile(path: string): RegExp {
  const anchored = path.endsWith('$');
  const body = (anchored ? path.slice(0, -1) : path).split('*')
    .map((part) => part.replace(/[.+?^${}()|[\]\\]/g, '\\$&')).join('.*');
  return new RegExp(`^${body}${anchored ? '$' : ''}`);
}
```

Каждый `*` в правиле `Disallow`/`Allow` становится `.*` в регэкспе. Несколько `.*`, разделённых
короткими литералами, против строки, которая **не** совпадает целиком, — классический экспоненциальный
паттерн (несколько независимых позиций подгонки без якоря на общий итог). И шаблон (`path`), и
проверяемая строка (`pathWithQuery`, из ссылок на самой странице) полностью во власти сайта, который
краулер читает по прямому приглашению владельца бота — то есть барьер, который должен защищать нас от
чужого сайта, сам становится дырой в сторону чужого сайта.

**Воспроизведено** (без БД, без сети, чистый вызов `compile`/`RegExp.test`, логика скопирована 1:1 из
исходника):

```
паттерн: '/' + 'a*'.repeat(30) + 'END'   (64 символа)
строка:  '/' + 'a'.repeat(40) + 'X'      (42 символа, не заканчивается на END)
re.test(строка) → false, время: 10 444 мс
```

30 `*` — не экзотика: `ROBOTS_MAX_BYTES = 500 * 1024` (`limits.ts:10`) разрешает файл до 500 КиБ,
а само число `*` в одном правиле НИЧЕМ не ограничено. Владелец сайта (случайно, через генератор
robots.txt со своими шаблонами) или недоброжелатель (нарочно) кладёт одну строку вида
`Disallow: /*/*/*/*/*/*/*/*/*/*/*/*...` — и `isAllowed` вызывается на каждый URL обхода
(`crawl-site.ts:144` — для каждой страницы очереди, `crawl-site.ts:168` — повторно для конечного адреса
после перенаправления). Один такой файл вешает `apps/worker` целиком: Node однопоточный, синхронный
regex-бэктрекинг не прерывается ни таймаутом запроса (`CRAWL_PAGE_TIMEOUT_MS`), ни бюджетом времени
обхода (`CRAWL_TIME_BUDGET_MS`) — оба меряют время МЕЖДУ асинхронными операциями, а не внутри
синхронного вызова. Событийный цикл воркера стоит для ВСЕХ задач этого процесса, не только для
атакованной, пока JS-движок не домотает регэксп до конца (со звёздами побольше — практически
никогда).

Тестов на этот случай нет: `tests/robots.test.ts` проверяет только функциональность разбора
(`*`, `$`, группы, регистр), ни одного патологического шаблона.

**Чем чинить:** заменить построение регэкспа из `*` на алгоритм без бэктрекинга — либо ручное
сопоставление сегментов (RFC 9309 §2.2.2 не требует именно regex: посимвольное/посегментное
сравнение с `*` как жадным, но НЕ регэксп-движковым wildcard, за линейное время), либо жёсткий
потолок числа `*` на правило (например, 10) с отказом/игнорированием правила сверх потолка, либо
матчинг через движок без экспоненциального бэктрекинга (RE2-подобный). Обязательно — тест по
guard-must-be-able-to-fail: внедрённый патологический шаблон + ассерт на верхнюю границу времени
(например, `< 100` мс на файл до `ROBOTS_MAX_BYTES`).

### BLOCKER-2 — алгоритмический DoS в `extract-text.ts`: `html.toLowerCase()` на весь документ на каждый тег

**Файл:** `apps/worker/src/crawl/extract-text.ts:71`.

```ts
const end = html.toLowerCase().indexOf(`</${name}`, TOKEN.lastIndex);
```

Вызывается на КАЖДОЕ вхождение `script`, `style`, `noscript`, `template`, `textarea`, `xmp` или
`title` (`extract-text.ts:70`). `html.toLowerCase()` копирует и перекодирует **весь** документ
заново при каждом вызове, а не только хвост от `TOKEN.lastIndex`. Страница с большим числом мелких
сырых тегов даёт `O(длина_документа × число_тегов)`.

**Воспроизведено** (тот же цикл `toLowerCase().indexOf`, скопирован из исходника):

```
документ: '<script></script>'.repeat(30 000)  →  510 000 байт (в 4× меньше потолка 2 МБ)
30 000 повторов indexOf: 7 806 мс, монотонный рост без выхода на плато
```

Документ близкий к потолку `CRAWL_MAX_PAGE_BYTES = 2 МБ` (`limits.ts:7`) с плотной сеткой таких
тегов экстраполируется в десятки–сотни секунд синхронной работы на одной странице одного обхода —
снова блокирует событийный цикл всего `apps/worker`, а не только эту задачу. Ни `tests/crawl.test.ts`,
ни `tests/robots.test.ts` не содержат документа с числом тегов выше единиц.

**Чем чинить:** привести `html` к нижнему регистру ОДИН раз до цикла (или держать индекс без
регистро-нечувствительного copy — искать `</` + `name` вручную посимвольно с `toLowerCase` на
отдельных символах, либо регэкспом `new RegExp('</' + name, 'i')` с `lastIndex`, без копирования
строки). Добавить мутационный тест: документ с N≈10⁴ сырых тегов, ассерт на верхнюю границу времени.

### MEDIUM-1 — редирект может понизить схему https → http без ограничения

**Файл:** `apps/worker/src/crawl/safe-get.ts:104-106`.

```ts
try { url = new URL(once.location, checked.url); } catch { throw new FetchFailed('unreachable'); }
url.hash = '';
continue;
```

Схема следующего прыжка берётся из `Location` без сверки с исходной. Адрес каждого прыжка проверяется
заново (`checkAddress`) — это НЕ обход SSRF, — но сетевой атакующий на пути между воркером и уже
проверенным публичным адресом может через `Location: http://...` заставить один из прыжков идти в
открытом виде и подменить контент по дороге. Смягчающее обстоятельство: содержимое сайта в этом
продукте и так трактуется как недоверенные данные (`security.md`, promt-injection barrier), поэтому
ущерб ограничен целостностью самого обхода (ложные ссылки/контент), а не привилегией. Не покрыто
тестом ни в одну, ни в другую сторону. Стоит либо зафиксировать схему не ниже схемы корня (или
предыдущего прыжка), либо явно принять как раскрытый риск в квитанции.

### MEDIUM-2 — ветка отказа от `Content-Encoding` не покрыта тестом

**Файл:** `apps/worker/src/crawl/safe-get.ts:69-70`. Механизм («никогда не распаковывать» — тело
уничтожается сразу при любом `content-encoding !== identity») сам по себе — лучшее из возможных
решений против gzip-бомбы (распаковки нет вообще, лимит после распаковки в принципе не нужен). Но
ни один тест не проверяет сервер, который присылает `Content-Encoding: gzip` вопреки
`Accept-Encoding: identity` — стоит добавить фикстуру и ассерт `skipped.encoding === 1`, тело не
прочитано.

### LOW-1 — двойной запрос `kind` источника

`apps/worker/src/run-index-job.ts` (`processByKind`) делает `SELECT kind FROM source`, а

## Что подтверждено без замечаний (проверено целенаправленно, обхода не найдено)

- **SSRF-список** (`check-address.ts`): все запрошенные диапазоны IPv4/IPv6 закрыты, включая
  `0.0.0.0/8`, CGNAT, TEST-NET ×3, `192.0.0/24`, `198.18/15`, мультикаст/резерв, IPv4-mapped
  `::ffff:a.b.c.d` (проверено делегированием в IPv4-правило по числовому значению — работает для ЛЮБОЙ
  текстовой формы адреса, не только записи с точками), NAT64 `64:ff9b::/96` и 6to4 `2002::/16`
  (через разрешающий список 2000::/3 минус служебные — надёжнее растущего запрещающего списка), зона
  `%eth0` — отказ.
- **Числовые/восьмеричные/десятичные хосты** (`2130706433`, `0x7f.1`, `017700000001`) — проверено
  эмпирически: `new URL(...)` в Node нормализует их в `127.0.0.1` ДО того, как код увидит `hostname`,
  так что `isBlockedIp` получает уже канонический вид. Это верно, но implicit — стоит явно
  задокументировать зависимость от поведения WHATWG URL-парсера в комментарии `check-address.ts`,
  раз на неё опирается вся защита от числовых литералов.
- **userinfo в URL, порт** — отвергаются до DNS (`checkUrlShape`); только 80/443, как того требует
  Pseudocode `CheckAddress` п.1 — не отклонение, а соответствие постановке.
- **Соединение по проверенному IP, без второго резолва** — `safe-get.ts` передаёт `host` числовым IP
  и `family` явно; Node не резолвит IP-литерал. SNI/`servername` и `Host` — из исходного имени, не из
  IP: корректно для виртуального хостинга (не прогонялось на настоящем TLS — уже честно отмечено
  как открытый пункт в `05_completion.md` №2, не дублирую как новую находку).
- **Каждый редирект — заново, лимит 5** — подтверждено тестом со структурным барьером (тестовый `dial`
  бросает исключение при попытке соединиться с непроверенным адресом, а не просто проверяет постфактум).
- **robots.txt**: группа по токену, иначе `*`; самое длинное правило, при равенстве — Allow; `4xx` —
  всё разрешено, `5xx`/таймаут/сеть — `unreachable` (fail-closed: без знания правил не читаем).
  Разбор синтаксиса корректен для всех протестированных случаев.
- **Лимиты**: обрыв потока по факту байт (не только по заявленному `Content-Length`), таймаут на весь
  запрос целиком (включая тело — от slowloris защищает: таймер один на весь цикл запрос-ответ, не
  сбрасывается на каждый чанк), только `text/html` с параметрами (`text/html; charset=...`), gzip-бомба
  структурно невозможна (тело сжатого ответа не читается вообще).
- **Извлечение ссылок**: `javascript:`, `data:`, `mailto:` и прочие схемы кроме `http(s)` отбрасываются;
  относительные ссылки и `<base href>` разрешаются корректно; учётные данные и нестандартный порт в
  ссылке — вне обхода.
- **Интеграция с задачей**: фенс проверяется в ТОЙ ЖЕ транзакции, что и запись страницы/счётчика
  (`recordProgressTx`), устаревшая попытка не дописывает и не продолжает сеть; прогресс «N из M»
  корректен на всех протестированных сценариях.
- **Журнал**: `site-processor.ts` пишет только счётчики (прочитано/без изменений/пропущено по причинам/
  запросов/остановка) — ни тел, ни текста, ни адресов.
- **carry_over `closeFailedTx`**: условие статуса перенесено внутрь функции, ранний возврат на 0 строк —
  корректно, соответствует описанному тесту и мутации.

### BLOCKER-1 (robots ReDoS) — разбор `matchRule` (`robots.ts:19-43`)

Правило хранится как литеральные сегменты между `*` (`compile`, `robots.ts:19-23`); `matchRule`
ищет каждый сегмент `indexOf` СТРОГО вперёд от текущей позиции, без возврата назад. Это не эвристика —
для шаблонов, где `*` означает «любая последовательность БЕЗ ограничений на алфавит» (ровно семантика
robots.txt), самое левое вхождение очередного сегмента доказуемо не хуже любого другого выбора: оно
максимизирует оставшееся пространство поиска для последующих сегментов. Стандартный результат теории
сопоставления с шаблоном (тот же принцип, что у безвозвратного алгоритма wildcard-matching), здесь
применён корректно. Проверено построчно:
- Позиция после совпадения сегмента строго возрастает (средние сегменты гарантированно непустые —
  `compile` схлопывает подряд идущие `*`), поэтому число итераций внутреннего цикла ограничено
  длиной правила, а не строки.
- Крайний случай «хвост перекрывает начало» (`/ab*ba$` против `/aba`) обработан явно
  (`text.length - tail.length >= position`) и подтверждён тестом — без этой проверки заякоренный
  хвост дал бы ложное совпадение.
- `V4`-подобная деградация исключена: единственный примитив — `String.prototype.indexOf`, который в
  V8 не деградирует до наивного O(n×m) на состязательных данных (проверено отдельно: игла в 2000
  символов против стога в 2 000 000 — 13 мс, не секунды).
- `MAX_LITERAL` (`robots.ts:26,63`) отбрасывает правило, чьи литералы длиннее `CRAWL_MAX_URL_LENGTH` —
  оно не может совпасть ни с одним запрошенным адресом, это не ослабление запрета.

Семантика `*`/`$`/подряд идущих `*` проверена таблицей из 8 утверждений
(`crawl-pathological.test.ts:33-43`) — совпадает с прежним regex-поведением там, где regex был
корректен, и добавляет случай перекрытия головы/хвоста, которого раньше не было.

### BLOCKER-2 (алгоритмический DoS в extract-text.ts) — разбор ручного сканера (`extract-text.ts:60-87`)

`nextToken` продвигает позицию МОНОТОННО в каждой ветке (текст — до следующего `<` или конца; `<!--`,
`<![CDATA[`, `<!`, `<?` — до маркера конца или конца документа; обычный тег — до `>` вне кавычек или,
если `>` не найден, СРАЗУ до конца документа). Ключевое отличие от прежнего регэксп-токенизатора и от
находки, сделанной автором при правке (незакрытый тег пересканировался с каждой позиции): здесь
неудачный поиск `>` завершает разбор ЦЕЛИКОМ (`position = html.length`), а не откатывается на один
символ назад для повторной попытки с соседней позиции. Проверено вручную на конструкции
`"<a<a<a...<a"` (много начал тега, ни одного `>` во всём документе) — с прежним кодом (или с
мутацией `unterminated-tag-rescan`) каждое повторное «<» запускало новый O(n) скан, что в сумме даёт
O(n²); с текущим кодом первый же неудачный скан обрывает весь разбор одним проходом.

Кавычки открываются только сразу после `=` (`previous === '='`), поэтому `class=it's` не принимает
апостроф за открывающую кавычку, а `alt='a>b'` не считает внутренний `>` концом тега — оба случая
подтверждены тестом (`crawl-pathological.test.ts:60-64`) и совпадают с ручной трассировкой.

Поиск закрывающего тега для `script`/`style`/…/`title` — регэксп `</name` с `lastIndex` от текущей
позиции, кэшированный по имени (`CLOSERS`, `extract-text.ts:44-49`): не копирует документ (в отличие
от прежнего `html.toLowerCase().indexOf`), и подтверждено, что больше нигде в файле `.toLowerCase()`
не вызывается на всём `html` — только на именах тегов, отдельных атрибутах и коротких строках
(`grep` по файлу).

### MEDIUM-1 (downgrade) — `nextHop` (`safe-get.ts:94-100`)

Сравнение схемы берётся у `checked.url` ТЕКУЩЕГО прыжка (не у исходного корня), поэтому понижение
пресекается на КАЖДОМ шаге цепочки, а не только против первого запроса — `https→https→http` тоже
поймано, не только `https→http` напрямую. `downgrade` корректно заведён в `SkipReason`
(`crawl-site.ts:21`) и в классификацию отказа корня как сетевого сбоя (`crawl-site.ts:157`), так что
даунгрейд корневого адреса даёт `unreachable` для всей задачи, а не «готово, 0 страниц».

### MEDIUM-2 — покрыт тестом, код был и остаётся корректным.

### Тесты и мутации

`tests/crawl-pathological.test.ts` намеренно использует `vm.runInNewContext(..., {timeout})`
(`crawl-pathological.test.ts:15-17`) — это не косметика: таймаут `vm` ПРЕРЫВАЕТ синхронный
бэктрекинг/цикл изнутри, поэтому регресс даёт быстрый красный тест, а не зависший прогон, который
пришлось бы убивать вручную. Мутации `robots-regex-backtracking`, `extract-tolower-per-tag`,
`unterminated-tag-rescan`, `downgrade-allowed` (`scripts/test-crawler-mutations.mjs:46-54`)
воспроизводят именно те три строки кода, которые были уязвимы, — прочитаны построчно, каждая
действительно возвращает код в состояние из первого ревью. Сами мутации не прогонялись в этой сессии
(требуют `DATABASE_URL`/образ — недоступны здесь), их устройство и данные квитанции (`07_code_report.md`,
9/9) приняты на основании чтения кода мутаций, а не запуска.

### Что не проверялось независимо (без нового значения — уже честно названо)

Живой TLS/SNI, реальный IPv6-прогон, полный `docker compose` цикл, cross-family review — вне
компетенции этой сессии, статус не изменился со времени первого ревью, самих находок это не отменяет.
