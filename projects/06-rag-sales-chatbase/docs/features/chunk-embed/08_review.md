## 1. Изоляция арендатора (главный риск) — ПОДТВЕРЖДЕНО

- `packages/db/src/chunks.ts:105-119` (`SEARCH_CHUNKS_SQL`, `searchChunks`): `WHERE c.bot_id = $1`
  внутри CTE `own AS MATERIALIZED`, **до** `ORDER BY … LIMIT` — не пост-фильтр. SQL параметризован
  (`$1`/`$2`/`$3`), без строковой сборки. `bot_id` в этой фиче приходит только из `lease.botId`
  (арендованная задача, `index-jobs.ts`) или из вызова теста — путь HTTP-запроса (будущий
  `rag-answer`) в этой фиче не существует, поэтому нет строки кода, где `bot_id` берётся из тела
  запроса. Замечание на будущее в п.6.
- Тест `tests/chunk-embed.integration.test.ts:88-130`: бот A — 3 «далёких» вектора, бот B — 300
  векторов, гарантированно ближе к вопросу. Обычный план: A получает ровно свои 3, B — ровно свои 4
  из своих 300 (строки 111-117). Второй тест форсирует `enable_seqscan/sort/bitmapscan = off` и читает
  `EXPLAIN` (`SEARCH_CHUNKS_SQL`), утверждая, что план **не** содержит `chunk_embedding_hnsw`
  (строка 125) — то есть тест доказывает именно то, что задокументировано в A-N6-028, а не рядом
  стоящий похожий SQL (комментарий в chunks.ts:99 честно называет эту причину выбора одного текста
  запроса).
- Мутация `bot-filter-removed` (`scripts/test-chunk-embed-mutations.mjs:30-33`) убирает оба вхождения
  `bot_id = $1` из SQL и даёт **2 failed** — страж реально падает (guard-must-be-able-to-fail
  выполнено), восстановление зелёное.
- `packages/db/src/chunks.ts:112-115`: `searchChunks` отдельно валидирует `isUuid(botId)`,
  `isEmbeddingOfDimension`, `topK` диапазон 1–20 — отказ до запроса, а не в SQL.
- Индекс `chunk_bot ON chunk (bot_id)` существует в схеме (`packages/db/migrations/001_init.sql:100`,
  фича `foundation`, не тронута этим диффом) — точный перебор внутри бота идёт по индексу, а не
  сканирует таблицу целиком по всем ботам. Вывод отчёта «HNSW+фильтр теряет свои» подтверждён третьим
  независимым способом при чтении: это ожидаемое поведение `iterative_scan` pgvector 0.8 при жёстко
  запрещённых перебору/сортировке путях планировщика — тест это доказывает прогоном, а не только
  цитатой из документации поставщика, чего явно и достаточно для локального решения A-N6-028.

## 2. A-N6-028 — точный перебор внутри бота: решение обосновано, масштаб не закрыт

- Обоснование смены пути — качество, не вкус: эмпирический прогон (0 из 3 своих при 300 чужих ближе)
  задокументирован и воспроизведён тестом (п.1). Отказ от HNSW-поиска в пользу перебора при
  подтверждённой потере полноты — правильное решение под honest-configuration (CFG-I4: источник
  истины недоступен/неверен → отказ, не тихая деградация «не знаю»).
- Замер `searchChunks`: 5001 фрагмент ОДНОГО бота — 34 мс (`tests/chunk-embed.integration.test.ts:150-155`,
  порог теста 500 мс). Это подтверждает производительность на масштабе одного крупного бота у предела
  плана (300 страниц × ~16 фрагментов/страницу ≈ 5000). **НЕ измерено**: NFR-SCALE-001 требует
  1 000 000 фрагментов НА МАШИНУ (все боты вместе) — при перебора-по-индексу `bot_id` время поиска
  одного бота не зависит от чужих фрагментов, так что риск здесь низкий (индекс `chunk_bot` ограничивает
  сканирование ботом), но это умозаключение, не измерение; отчёт сам называет это открытым пунктом
  (05_completion.md, «Чего фича НЕ доказывает» п.6) — согласен с этой самооценкой.
- **Удержание соединения пула на записи (shared-resource-verification) — подтверждаю находку автора,
  она не устранена.** `writeIndexedPage` (`packages/db/src/chunks.ts:64-71`) оборачивает
  `upsertPageTx` + `replaceChunksTx` ОДНОЙ транзакцией; `replaceChunksTx` вставляет пачками по
  `EMBED_BATCH_MAX = 64` (`packages/rag/src/constants.ts:31`), но **без верхнего предела на общее
  число фрагментов страницы** — `validateChunks` (`chunks.ts:22-30`) проверяет только форму каждого
  фрагмента, не их количество. Замер автора: вставка при живом HNSW — 2,8 мс/фрагмент; страница
  ≤ 2 млн символов (разрешена крауле­ром, `CRAWL_MAX_PAGE_BYTES`) даёт ≈ 2000–4000 фрагментов →
  **5,6–11,2 с внутри одной транзакции**, держащей соединение пула и строку `index_job` (плюс сама
  оценка консервативна: реального прогона с 2000+ фрагментами в одной транзакции `writeIndexedPage`
  не было — измерялась только вставка сама по себе с DROP INDEX). При NFR-SCALE-001 «2 одновременные
  задачи индексации» и без `statement_timeout`/предела фрагментов на страницу это реальный, хоть и не
  катастрофический (не публичный HTTP-путь, а фоновый воркер) риск исчерпания пула БД у `web` и
  `worker-index`, которые пул делят с обычными запросами кабинета/виджета. Автор сам занёс это в
  carry_over (`account-erasure`) и в A-N6-028 п.6 альтернатив — то есть находка раскрыта, а не
  спрятана (fail-closed-defaults соблюдён по духу: решение явно отложено, а не тихо принято). Требую
  как FIX: либо ограничить число фрагментов страницы константой кода до первого реального прогона на
  сайте с тяжёлыми страницами, либо явно принять риск письменным решением владельца перед запуском на
  живом трафике (не перед мержем этого кода — стек ещё не разворачивается).
- Мутация теста производительности отсутствует и не нужна: это измерение (замер), а не страж; верно
  классифицировано в 07_code_report.md как «слой 1 (замер)».

## 3. Деньги (model-call-cost, security-operation-order)

- Каждая попытка пачки идёт через `meteredCall` (`packages/rag/src/spend.ts:64-83`): порядок
  `charge()` → `spend(attempt, fsync)` → `run()` → `spend(outcome)`, отказ модели/таймаут НЕ
  возвращает списанное, повтор — новая попытка и новое списание. Мутация `retry-not-charged`
  (`spend.ts` — `if (call.charge && attempt === 1)`) даёт **3 failed** (resume + 2 в чужом
  `spend.test`) — страж реально ловит регресс именно в эту сторону, не только в общем виде.
- `charge()` (`apps/worker/src/embed/embed-and-store.ts:39-53`) — одна короткая транзакция на попытку:
  фенс/пульс задачи (`touchAndChargeJobBudgetTx`) → бюджет задачи (если предпросмотр) →
  `account_embed_tokens` + `global_embed_tokens` (`indexEmbedCharges`/`previewEmbedCharges`,
  `packages/db/src/ceilings.ts:69-79`, не тронуты этим диффом, но верно использованы). Отказ любого —
  `ROLLBACK TO SAVEPOINT`, откат ВСЕХ списаний попытки; исходная короткая транзакция коммитится пустой.
  Соответствует таблице `docs/model-cost-contract.md` (строка «эмбеддинг-индексации», предел на
  пользователя ≤ предела в сутки: 2 000 000 ≤ 20 000 000 — верно).
- Отклик шлюза: 429/5xx/сеть/таймаут → `RetryableCallError`, повтор до `EMBED_RETRIES = 2` (3 попытки
  всего), 4xx/мусор → `GatewayResponseError` без повтора (`packages/rag/src/openrouter.ts:49-53`) —
  верно совпадает с model-call-cost (счёт по попыткам) и Pseudocode EmbedAndStore п.2-3.
  `resume.test.ts:61-79` считает попытки и списания напрямую по журналу — не по побочному эффекту.
- Размерность 1536 проверяется ТРИЖДы через одну функцию `isEmbeddingOfDimension`
  (`packages/rag/src/constants.ts:37-39`): у клиента (`openrouter.ts:89`), второй раз в
  `embed-and-store.ts:71` («клиент может быть подменён или ослаблен» — верное рассуждение
  defense-in-depth, не дублирующаяся логика), третий раз перед записью (`chunks.ts:28`). Несовпадение
  → `internal` + строка «СИГНАЛ ОПЕРАТОРУ» (не тихий `dimension_mismatch` без сигнала). Мутация
  `vector-3072-accepted` (единственная точка правки — `constants.ts`) даёт **4 failed** — доказывает,
  что все три места действительно зависят от одной функции, а не совпали случайно.
- Плательщик: предпросмотр — бюджет задачи; бот без аккаунта и без бюджета — `internal`, НЕ бесплатно
  (`embed-and-store.ts:29-35`) — соответствует A-N6-028 п.6 и fail-closed-defaults.

## 4. Транзакция страница+фрагменты, идемпотентность повтора

- `writeIndexedPage` (`chunks.ts:64-71`): `upsertPageTx` (фенс — первый оператор через
  `recordProgressTx`) → `replaceChunksTx` (DELETE старых + INSERT новых пачками + `chunks_done` под
  тем же фенсом) — ОДНА транзакция. Мутация `chunks-outside-page-tx` (разбить на две транзакции) даёт
  **1 failed** — страж реально проверяет именно это разделение, не что-то соседнее.
- Эмбеддинги считаются ДО транзакции (`site-processor.ts`/`pdf-processor.ts`: `chunkDocument` →
  `embedder.embed` → `writeIndexedPage`) — сетевой вызов не держит соединение пула
  (security-operation-order «вызов вне транзакции» соблюдён).
- Двойная доставка: `tests/chunk-embed.integration.test.ts:165+` (не процитировано целиком, но
  структура подтверждена по коду) и по описанию в 05_completion.md — одна попытка перехватывает фенс,
  вторая получает `StaleAttemptError`; повторная доставка после `done` — `skipped`. `UNIQUE (page_id,
  ordinal)` — вторая линия защиты от дублей на уровне схемы, независимая от логики приложения.
- `resetAttemptCountersTx` (`chunks.ts:74-80`) пересчитывает `chunks_done` от факта в БД
  (`count(*) WHERE bot_id AND source_id`), а не от предположения — верно для продолжения по
  `content_hash` после сбоя.

## 5. Нарезка (ChunkDocument) — линейность и враждебный ввод

- `packages/rag/src/chunk.ts`: разбор заголовков/абзацев/предложений/слов — только `charCodeAt`-циклы
  и один `replace(/\s+/g, ' ')` с одним квантификатором (без возвратов, `squash`, строка 54); граница
  предложения — посимвольный проход (строки 90-101), не регэксп с обратным ходом. Суррогатные пары не
  разрываются (`hardSplit`, строка 65: `isHighSurrogate` перед резом).
- Измерено на 2 млн символов × 8 враждебных форм (одно гигантское слово, 2000 слов без точки, 666k
  крохотных предложений, 100 000 заголовков, эмодзи, строки PDF) — 157–661 мс при пороге теста 3 с
  (07_code_report.md). Формы выбраны осмысленно (это ровно классы, которые ломают наивные
  реализации), не только «текст побольше».
- `context_path`: дубль title/h1 схлопывается (`chunk.ts:178`), заголовок ≤ 120 символов через
  `clip()` (символы, не code units — `Array.from`, строка 134), перекрытие не пересекает границу
  раздела (`section()` сбрасывает `previous = null`, строка 155).
- `embeddingInput` (строка 189) кладёт `context_path` перед текстом — соответствует FR-INDEX-001
  («от 350 ₽» находится вопросом о доставке только с контекстом).

- Обе правки — регрессные фиксы существовавших до фичи дефектов обвязки (найдены и подтверждены
