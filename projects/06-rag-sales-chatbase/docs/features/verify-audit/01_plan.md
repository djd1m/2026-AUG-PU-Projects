## Инцидент (стенд 28.09, из постановки координатора)

Отметка «Я проверил ответы бота» у бота `829606b3…` пропала между 13:39 и 13:46 без обхода и без новых фрагментов.
Единственный путь, снимающий отметку без фрагмента, — `POST /api/bots/{id}/verify { verified: false }` владельцем.
Кнопка блока «Ответы на сайте» — переключатель: после первого нажатия та же кнопка на том же месте становится «Снять
отметку», запрос шлёт `!verified`. Второе нажатие (двойной клик, повторный Enter) молча выключило ответы посетителям.
Журнала «кто и когда» нет — восстановить картину по данным нельзя (BACKLOG §3в, третий пункт).

## Критерии приёмки

| AC | Что | Как проверяется |
|---|---|---|
| AC-1 | «Я проверил ответы бота» ставит отметку одним нажатием и шлёт ЯВНО `verified: true` (не `!verified`) | unit (`requestVerify`, страж по исходнику) + браузер |
| AC-2 | Когда отметка стоит — отдельная второстепенная кнопка «Снять отметку»; её нажатие НЕ шлёт запрос, а раскрывает подтверждение: «Посетители сайта перестанут получать ответы и увидят «Бот ещё настраивается». Снять?» и кнопки «Снять» / «Отмена» | браузер (гидратированный `BotScreen`, счётчик запросов тестового сервера) |
| AC-3 | Двойное нажатие «Я проверил ответы бота» оставляет отметку: ни одного запроса `verified: false` | браузер (`dblclick`, Chromium + WebKit) |
| AC-4 | Escape и «Отмена» закрывают подтверждение без запроса; фокус возвращается на «Снять отметку»; при раскрытии фокус — на «Отмена» (безопасное по умолчанию) | браузер |
| AC-5 | Разметка подтверждения доступна: `role="alertdialog"` с именем и описанием, `aria-expanded`/`aria-controls` у кнопки; цели ≥ 44×44; прибор R1/R2/R5/R8, axe AA, обе темы, 320–1440 | браузер |
| AC-6 | Сервер: `verified: false` без `confirm: true` — `400 confirm_required`, отметка не меняется (старая вкладка с прежним переключателем после выкладки не снимет отметку) | unit обработчика + мутация |
| AC-7 | Журнал `bot_verification_event` (миграция 014): `bot_id`, `kind` ∈ `set` · `unset_owner` · `unset_new_material`, `actor` ∈ `owner` · `system`, `created_at`; без ПДн; пишется в ТОЙ ЖЕ транзакции, что изменение отметки — любым путём записи | integration: владелец ставит/снимает, фрагмент снимает; откат транзакции не оставляет события |
| AC-8 | Повторная установка уже стоящей отметки — не событие и не сдвигает дату «стоит с»; повторное снятие снятой — не событие | integration |
| AC-9 | Экран бота: «Отметка стоит с <дата>» / «Снята <дата> владельцем | из-за новых материалов»; последние 5 событий раскрытием (`<details>`) | integration (`readBotCabinet`) + unit строки + браузер |
| AC-10 | Баннер gate-onboarding и пометка `answers_verified_reset_*` согласованы с журналом: снятие фрагментом — дата пометки = дата события `unset_new_material`; соседние наборы gate-onboarding зелёные без правки смысла | integration + полный прогон |
| AC-11 | Установка отметки из баннера не оставляет под курсором кнопку другого блока: баннер после отметки заменяется строкой «Отметка поставлена…», а не исчезает | браузер |
| AC-12 | Мутации: подтверждение убрано → красный; событие не пишется → красный; сервер принимает снятие без `confirm` → красный | `scripts/test-verify-audit-mutations.mjs` |

## Решение: событие пишет БАЗА (триггер), а не код

Путей записи отметки два: `setAnswersVerified` (владелец) и триггер фрагментов 004/011 (система). Варианты:

1. Вставка события в `setAnswersVerified` + вставка в функцию триггера фрагментов — два места; прежнее приложение при
   откате (схема 014, код 011) снимало бы отметку без события — журнал врал бы молчанием.
2. Перенос сброса из триггера в код — все пути вставки фрагментов (краулер, PDF, «Повторить», переиндексация) обязаны
   помнить про отметку; именно это A-N6-036 и запретило.
3. **Выбрано:** `AFTER UPDATE OF answers_verified_at ON bot FOR EACH ROW` — событие на ПЕРЕХОДЕ «стоит ↔ не стоит», в той же
   транзакции (это тот же оператор). Кто снял — по строке: триггер фрагментов ставит `answers_verified_reset_reason =
   'new_material'` в том же UPDATE → `unset_new_material`/`system`; любое другое снятие (сейчас только владелец) →
   `unset_owner`/`owner`. Обойти журнал новым путём записи нельзя; прежнее приложение на схеме 014 пишет события тоже.

Установка без перехода (уже стоит) — не событие; `setAnswersVerified` больше не сдвигает `answers_verified_at`
(`COALESCE`), чтобы «стоит с» было датой установки, а не последнего нажатия.

Пометка `answers_verified_reset_*` (011) остаётся: это ТЕКУЩЕЕ состояние под CHECK-инвариантом, из неё читает баннер и тесты
соседней фичи; журнал — история. Смысл не дублируется: баннер говорит «почему сейчас снято», журнал — «кто/когда вообще».
Даты совпадают по построению (`now()` одной транзакции) — проверяется тестом.

## Что сознательно НЕ делается

- `unset_source_added`: добавление источника само отметку не снимает (снимает только вставка фрагмента) — события без пути
  записи в закрытый набор не добавляется.
- «Снимать отметку только при существенном изменении» (BACKLOG §3в, второй пункт) — решение владельца, не здесь.
- История прошлых снятий до выкладки не восстанавливается: журнал начинается с миграции 014.
