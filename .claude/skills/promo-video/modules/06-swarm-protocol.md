## Process

### §1. Worktree и владение файлами

- Каждый исполнитель — свой worktree (одна ветка, изолированная копия). Два писателя в одном worktree запрещены.
- Владение: исполнитель `<proj>` пишет ТОЛЬКО `promo/capture/<proj>/**`, `promo/remotion/<proj>/**`,
  `/home/dz-projects-2026/.promo-assets/<proj>/**`. Общие файлы — `promo/remotion/shared/**`, `promo/remotion/package*.json`,
  `promo/capture/hidpi-recorder.mjs`, `promo/SERIES.md`, `05_project_inputs.md`, `promo/dist/README.md` — у координатора
  или у одного назначенного агента шаблона. Нужна правка общего — сообщить владельцу файла, не править.
- `node_modules` между worktree не делится: первый `render.sh` в worktree ставит зависимости сам (≈ 12 с, сеть bridge).
- Приоритет в очереди рендера — по готовности; пять исполнителей фазы 2 работали одновременно, рендеры сериализовала
  блокировка (§2).

### §2. Блокировка, имена контейнеров, остановка только своего

- Сборка бандла и каждый рендер — под `flock /home/dz-projects-2026/.promo-assets/render.lock` (делает `render.sh`).
  Ожидание блокировки — не замер; N2 ждал ≈ 38 мин за N1/N4/N5.
- Имена контейнеров: `promo-<proj>-{install,bundle,16x9,9x16,1x1,16x9-repeat,probe,stills,capture}`. Занятое имя —
  `render.sh` отдаёт 2 и чужой контейнер не трогает.
- **Останавливать только своё**: `docker stop promo-<proj>-<шаг>` или PID своего процесса. `pkill -f render.sh` и любые
  шаблоны по имени скрипта запрещены — в пилоте у двух исполнителей был одинаковый `render.sh`, и `pkill -f` соседа убил
  три чужих фоновых прогона (SIGTERM, код 144; журнал N6 ревизии `8a9dc756`, попытка 10).
- Повисшая очередь к блокировке: `fuser /home/dz-projects-2026/.promo-assets/render.lock` → снимать только свой ждущий
  `flock`; живой держатель — не трогать, ждать.
- Длинные фоновые прогоны — через `setsid`, чтобы не зависеть от оболочки агента.

### §3. Хостовый сторож (инвентаризировать ДО протокола замеров)

- На машине работает `crypto-miner-watchdog.sh` (наследие инцидента 26.08): считает контейнер с **мгновенным** CPU
  > 300 % (`docker stats`, раз в ~60 с) майнером и делает `docker restart`. Сторож не трогать; исключение для `promo-*` —
  решение владельца.
- Измерено в пилоте: `--cpus=6` → рендер 360–475 % → 11 перезапусков; `--cpus=2.9` → замер 301,36 % в 06:11 → перезапуск;
  итоговый лимит **`--cpus=2.5`** (запас 15 %), дальше ни одного срабатывания ([`PILOT-N6.md`](../../../../promo/PILOT-N6.md), поправки 1–2).
- `render.sh` проверяет сторож только внутри своей функции `run()` — это `install`, `bundle` и рендер каждого формата.
  **Вне `run()` остаются** `probe` (отдельный `docker run` в `render()`), `stills`, раскадровка, запись, `gate-*.sh` — их
  исполнитель проверяет сам, после КАЖДОЙ такой операции, с окном по времени старта:
  ```bash
  T0=$(date '+%Y-%m-%d %H:%M:%S')      # до операции
  <операция с контейнером promo-<proj>-<шаг>>
  bash .claude/skills/promo-video/scripts/gate-watchdog.sh promo-<proj>-<шаг> "$T0"; echo "rc=$?"
  ```
  Внутри — тот же `awk` по журналу, что в `render.sh` (`substr($0,2,19) >= T0 && index($0, "'имя'")`). Коды: `0` — не
  трогал; `1` — трогал, строки выведены, результат операции недействителен; `2` — журнал не читается/пуст, T0 не вида
  `YYYY-MM-DD HH:MM:SS` или **после T0 в журнале нет ни одной строки** (обход раз в 1–2 мин не доказан — повторить через
  3 мин). Проверено: `promo-n2-16x9` после 09:16 → 0; `promo-capture-n6` после 04:00 → 1 (перезапуск пилота 04:22:49);
  T0 в будущем → 2; нет журнала → 2. Для `probe` внутри `render.sh` имя `promo-<proj>-probe`, T0 — время строки
  операции формата в `receipt.txt`.
- Урок: хостовых сторожей инвентаризировать ДО протокола — лимит CPU в первой постановке был на этой машине невыполним.

### §4. Лимиты контейнеров

| Операция | Лимиты | Сеть |
|---|---|---|
| запись (Playwright) | `--memory=1500m --cpus=2 --shm-size=1g`; перед стартом `free -g` (модуль 03 п. 2) | нужна (стенд) |
| `npm ci` | `--cpus=2.5 --memory=4g` | bridge, вне замера |
| сборка, рендер, `stills` | `--cpus=2.5 --memory=4g` | **`--network none`** |
| раскадровка (`storyboard.sh`) | `--cpus=2.5 --memory=2g` | **`--network none`** |
| `probe` внутри `render.sh` | **фактически `--cpus=1 --network none` без `--memory`** (лимита памяти нет) — так в коде `render()` | none |
| `probe`/ffprobe вручную, `gate-config.sh`, `gate-media.sh` | `--cpus=1 --memory=1g` — `--memory=1g` добавлять ВСЕГДА при ручном вызове | **`--network none`** |

Порты не публикуются ни в одной операции. Машина: 8 vCPU, 11 ГБ, без GPU; при живых стендах доступно ~5 ГБ.

### §5. Файловые квитанции исполнителей

- До запуска координатор выдаёт `RUN_ID`, `WORK_UNIT_ID` (`promo-<proj>-a`, `promo-<proj>-b`) и абсолютный `TRACE_PATH`
  в своём scratchpad; фиксирует, что файла нет.
- Исполнитель пишет содержательный отчёт (что сделано, файлы и коммиты, коды `render.sh`, sha256, платные вызовы, что не
  снято, открытые вопросы) во временный файл рядом, последней строкой `Status: completed` или `Status: failed`, затем
  `mv` в `TRACE_PATH`, и только после этого — одна строка-указатель координатору.
- Координатор перед сводкой проверяет каждый путь: обычный файл, не симлинк, непустой, создан после запуска, последняя
  строка терминальная; сообщает `валидных / требуемых`. Нет файла — единица не сдана, как бы ни выглядел ответ в чате.
  Молчание агента — не «работает».

### §6. Проверка вторым семейством (Codex)

1. **Предполётная проверка**: `node "<codex-plugin>/scripts/codex-companion.mjs" setup --json` → `"ready": true`. Нет —
   записать «проверка другим семейством НЕ выполнена» и не выносить «готово к публикации».
2. **Бриф — в файл** `promo/VERIFY-<что>-BRIEF.md` (эталон — `VERIFY-SERIES-BRIEF.md`: что прочитать, 6 разделов —
   титры, «нельзя показывать», единообразие, замеры, шаблон, вердикт да/да с поправками/нет + оценка A–D; формат
   «файл: утверждение → что не так → довод»). Промпт — одна строка «прочитай бриф и выполни» (потолок длины промпта).
3. **Вызов** — read-only, stdin закрыт, ответ в файл:
   ```bash
   timeout 900 codex exec --skip-git-repo-check -m gpt-6-astra -c model_reasoning_effort="medium" \
     -s read-only -C "$REPO" -o promo/VERIFY-<что>-CODEX.md \
     "Прочитай promo/VERIFY-<что>-BRIEF.md и выполни, что там написано." </dev/null > "$LOG" 2>&1
   grep -m1 '^model:' "$LOG"; grep -m1 'reasoning effort' "$LOG"   # фактическая модель и усилие — в итог
   test -s promo/VERIFY-<что>-CODEX.md || echo "ПУСТОЙ ОТВЕТ — проверки НЕТ"
   ```
   Без `</dev/null` вызов висит до таймаута (580 с, измерено). Серия 29.09: `gpt-6-astra` medium подтверждён строками
   журнала, 103 311 токенов. Пустой ответ или текст без вердикта — не «замечаний нет».
4. **Codex не рендерит и видео не видит**: судит по документам, конфигам и коду. Поэтому раскадровка готовых mp4 с
   путями и sha256 (модуль 07) — то, что делает его вывод о запретах проверяемым.
5. **Решения по вердикту** (эталон DEC-S-01…05): титр, обещающий не снятое, — правится без ожидания владельца;
   стилистика — по слову владельца; противоречие README ↔ конфиг — сверка по журналу записи; правки шаблона — отдельной
   фазой, чтобы не перерендеривать все проекты дважды.
6. **Второй круг — узкий, по диффу**: бриф называет коммиты правок и **заранее заданный критерий выхода** — «закрыты ли
   обязательные правки первого круга; не сломано ли соседнее». Полный круг не повторять.

### §7. Что решает владелец и когда спрашивать

| Вопрос | Когда |
|---|---|
| стиль, адрес финала, музыка, лимит платных вызовов | до модуля 03, один раз на серию |
| сцена, которую нельзя снять честно (за входом, нужна правка продукта) | как только исполнитель записал «не снято, нужна правка» |
| отложить проект (N3: стенд недоступен, `403 ORIGIN_DENIED`, лимит демосеансов исчерпан) | до запуска части A |
| исключение `promo-*` в стороже хоста, сборка образа, место на диске | до протокола замеров |
| удаление фикстур-учёток; лицензия Remotion (бесплатно до 3 человек, иначе от $25/мес) | после серии |
| публикация роликов и ссылок | только владелец; координатор готовит страницу с роликами |

Не спрашивать владельца о том, что решено правилами серии (кодирование, раскладка, 45 с, запреты).

## Output

- Журнал серии в `promo/SERIES.md` (координатор): время UTC, проект, событие, решение.
- `TRACE_PATH` каждого исполнителя с терминальной строкой; сводка `валидных / требуемых`.
- `promo/VERIFY-<что>-{BRIEF,CODEX}.md`; `promo/RESULT-<что>.md` — таблица замеров, вердикт, решения `DEC-…`, открытые вопросы.

## Quality Gate

| Проверка | Как | Слой | Блокирует |
|---|---|---|---|
| один писатель на проект, общие файлы не тронуты исполнителем | `git diff --stat` исполнителя ⊂ его каталогов | 1 | да |
| все квитанции исполнителей валидны | проверка §5 | 1 | да (частичная сводка — с долей) |
| ни одного `HIT` сторожа в квитанциях | `gate-receipt.sh` (модуль 05 п. 9) → 0 | 1 | да (переснять) |
| сторож не трогал операции вне `run()` | `gate-watchdog.sh` после каждой: capture, probe вручную, stills, storyboard, gate-* | 1 | да: 1 → переснять; 2 → повторить через 3 мин |
| вердикт Codex получен, модель подтверждена журналом | непустой файл + строка `model:` | 3 | да для «готово к публикации» |
| обязательные правки первого круга закрыты | второй узкий круг | 3 | да |

## Dependencies

- Codex CLI + companion (OPTIONAL) — fallback: вердикт «одно семейство», без «готово к публикации».
- `brutal-honesty-review` (OPTIONAL) — самопроверка исполнителя перед сдачей; fallback — чек-лист SKILL.md.
- `swarm-file-evidence`, `codex-invocation-local` (правила, REQUIRED).

## Reusability

§1–§5 — общий протокол для любого роя, делящего одну машину с тяжёлыми контейнерами (рендер, сборка образов, E2E):
блокировка по файлу, префикс имён, остановка только своего, инвентаризация сторожей до лимитов. §6 — шаблон
независимой проверки документов и конфигов другим семейством моделей.
