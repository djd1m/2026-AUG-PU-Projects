# Анализатор телеметрии проекта

Результат — проверяемый разбор с конкретными улучшениями и способом проверить их
эффект. Используй один из режимов: **diagnose**, **forecast**, **compare**; по умолчанию
diagnose. Один исполнитель достаточен для небольшого корпуса.

## Входы и запуск

Установи проект/каталог телеметрии, период или RUN_ID и вопрос пользователя.
Для forecast нужны описание новой задачи, критерии приёмки и внешние зависимости.
Для compare — изменение процесса и две сопоставимые группы прогонов.
Если границы не заданы, выбери текущий проект и явно обозначь выбор.

В этом монорепозитории прочитай `projects/TELEMETRY-AGENT.md` и применимые правила;
для другого репозитория используй его протокол. Подробности принятия решений:
[методика анализа](references/analysis.md).

Из корня репозитория запусти, подставив существующую папку:

```sh
python3 .claude/skills/project-telemetry/scripts/analyze.py \
  --root projects/03-affiliate-rewardful/docs/telemetry --format json
```

`--run ID` повторяется для выбранных прогонов; `--format markdown` даёт краткую
таблицу. Для периода отфильтруй паспорта по датам, затем передай явные ID;
прогоны без даты перечисли отдельно. Передавай скрипту только каталог телеметрии.
Он ничего не записывает, не запускает внешние команды и не обращается в сеть.
В переносимой копии путь к скрипту отсчитывай от каталога этого skill.

## Работа с результатом

1. Проверь `issues`, охват и ссылки на исходные поля. Ошибки чтения не означают
   нулевой расход. Exit 0 означает успешное извлечение, а не приёмку продукта;
   exit 2 означает проблемы входных данных или пустую выборку.
2. Скрипт выдаёт **заявленные** статусы и агрегаты. Проверь receipts, качество,
   actual-модели, usage scope и привязку тестов к версии отдельно. Для конкретной
   причины прочитай только нужные события и отчёты, а не весь чат.
3. Длительности попыток — наблюдаемый труд, включая параллельные интервалы.
   Это не критический путь. Частичные ожидания — нижняя граница известных ожиданий.
   Количество попыток одной стадии само по себе не доказывает переделку.
4. Скрипт намеренно не суммирует usage, не оценивает цены и не прогнозирует сроки
   автоматически: в текущих форматах недостаточно подтверждённой семантики.
   Сначала установи происхождение и непересечение данных по протоколу.
5. Применяй методику выбранного режима. Каждому предложению сопоставь наблюдение,
   предполагаемую причину, проверку причины, ожидаемый механизм улучшения,
   метрику успеха, защитные проверки и условия отката.

## Выход

Дай: границы и ревизию анализа; полноту данных; таблицу результатов; подтверждённые
проблемы и отдельно гипотезы; прогноз с основаниями либо объяснение его отсутствия;
приоритетные эксперименты; конкретные недостающие измерения.
Для сравнения добавь качество, все попытки и общие затраты, включая неуспехи.
Выделяй наблюдение / вычисление / гипотезу / оценку. Не объявляй экономию без baseline.

Если запрос включает сохранение отчёта, пиши отдельный файл в
`<project>/docs/telemetry/analysis/<дата>-<тема>.md`; JSON-сводку сохраняй рядом.
Для межпроектного анализа согласованный общий путь — `docs/development/telemetry/analysis/`.
Запиши commit и хеши входов из вывода скрипта; незакоммиченные входы обозначь отдельно.
Исторические паспорта не переписывай. Анализ не разрешает самостоятельно менять
политику моделей, приложение, запускать платежи, стенды или эксперименты с расходом.

`project-telemetry`. Эта поставка не меняет глобальные настройки или список навыков
уже запущенной сессии. Папка самодостаточна для копирования в каталог skills другого
проекта; ссылки на местный протокол адаптируются к его правилам.
