# Известные пробелы p-replicator — обходить вручную

Дефекты пайплайна, найденные на прогоне проекта 01. **Пока не исправлены в самом харнессе** —
компенсируем здесь. Полные заявки: [`/harness-forge/`](../../harness-forge/).

Запускать после каждой фазы: `bash scripts/check-pipeline-gaps.sh <путь-к-проекту>`

## Что пайплайн не проверяет сам

| # | Пробел | Что делать вручную |
|---|---|---|
| PR-001 | growth-анализ не доходит до требований | Подавать growth-блок в постановку явно — [`start/REPLICATE-PROMPTS.md`](../../start/REPLICATE-PROMPTS.md) |
| PR-002 | стек из постановки может противоречить Architecture Constraints | Не дублировать стек в постановке. Managed BaaS (Supabase, Firebase, Neon) запрещены |
| PR-003 | сценарий в Specification может не иметь реализации в Pseudocode | Сверять трассировку после Phase 1 |
| PR-004 | метрика без целевого числа проходит валидацию | Метрика = название + число + срок |
| PR-005 | параллельные агенты расходятся в именах | Фиксировать канон имён ДО фан-аута |
| PR-006 | `has_adr` всегда False для SPARC-проектов | Генератор тулкита не видит `docs/ADR.md` — решения ADR в тулкит не попадут |
| PR-007 | CJM и ADR не имеют обратной трассировки | Проверять вручную: каждый ADR → ссылка из Specification; каждый элемент CJM → требование или явное «НЕ входит» |

## Правила, которые из этого следуют

1. **Phase 2 не пропускать.** Она поймала 4 блокера на проекте 01, включая stored-XSS
   в контенте, который рендерится на чужих сайтах.
2. **Ре-валидация после правок обязательна.** Блокер B-4 был закрыт текстом в Specification,
   но без реализации в Pseudocode — поймала только повторная проверка со скептической установкой.
3. **«Сценарий добавлен» ≠ «требование закрыто».** Проверять, что алгоритм его реализует.
4. **`[GAP]` в документе не останавливает пайплайн.** Собирать их вручную перед Phase 3.
