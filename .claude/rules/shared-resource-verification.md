# Правка проверяется на разделяемом ресурсе, а не только на своём сценарии

## Maturity: 🔴 Alpha · Извлечено: 2026-08-27 · Источник: `projects/01-testimonials-senja`, цикл FR-009 · v1.0

## Утверждение

**Исправление проверяют на том сценарии, ради которого его написали.** Разделяемый
ресурс — пул соединений, блокировки, память, CPU, файловые дескрипторы, квота внешнего
API — при этом не проверяет никто, потому что он не упомянут ни в дефекте, ни в правке.

Следствие наблюдалось четыре ревизии подряд, без единого исключения:

> **Каждая ревизия вносила дефект того же класса, что чинила.**

## Чем заслужено

Цикл `/feature` над одной фичей (вход в систему). Реализация не начиналась — весь ущерб
пойман на планах, но каждая правка была написана человеком, который держал в голове
предыдущий дефект.

| Ревизия | Что чинили | Что внесли | Разделяемый ресурс |
|---|---|---|---|
| 1 → 2 | Лимит без чисел; критерий, зеленеющий без записи в счётчик | Разбор тела переехал **внутрь транзакции** — соединение пула удерживается, пока клиент дописывает запрос | **пул соединений** |
| 2 → 3 | Тот самый DoS пула | Ждущая блокировка: очередь за локом **тоже удерживает соединения** | **пул + блокировки** |
| 3 → 3.1 | Очередь за локом | `try`-блокировка по IP: очереди нет, но все за одним NAT получают ложные `429` | **блокировка, общая для многих клиентов** |
| 3.1 → 4 | Лок по IP снят | argon2 остался **внутри** транзакции: каждая попытка держит соединение ≈50 мс | **пул соединений** |

Обратите внимание на строку 2→3: чинили ровно исчерпание пула — и внесли исчерпание пула
другим механизмом. Знание о дефекте не помогло, потому что проверялась **правка**, а не
ресурс.

## Правило

К каждой правке, добавляющей или переносящей операцию, задаются четыре вопроса. Не «стало
ли лучше в моём сценарии», а:

1. **Что удерживается и как долго?** Соединение, блокировка, память, дескриптор. Если
   удержание стало длиннее — на сколько и под чьим контролем находится это время. Время,
   которым управляет **клиент** (чтение сокета, ожидание внешнего ответа), — всегда красный флаг.
2. **Сколько таких единиц всего?** Пул из 10 — это 10 одновременных удержаний до полной
   остановки. Число надо назвать, а не подразумевать.
3. **Кто ещё стоит в очереди за тем же ресурсом?** Не только тот путь, который правим.
   Пул общий у входа, дашборда, витрины, виджета и приёма отзывов — исчерпание одним
   маршрутом кладёт все.
4. **Кого наказывает механизм при насыщении?** Блокировка, общая для многих клиентов
   (по IP, по домену, по арендатору), при насыщении бьёт по добросовестным, а не по
   атакующем. Гранулярность ключа — часть защиты, а не деталь.

## Как проверять

Слой 1 по лестнице стоимости обнаружения — тест на **конкурентность**, а не на
последовательность:

```text
последовательный тест:   6-я попытка подряд -> 429     ✅ зеленеет, защита работает
конкурентный тест:       20 одновременных   -> ?       ← вот здесь живёт дефект
```

Минимальный набор для правки, трогающей разделяемый ресурс:

- **N одновременных запросов** по одному ключу — сколько дошло до дорогой операции;
- **число одновременно занятых единиц ресурса** не растёт с числом ожидающих
  (иначе ожидающие копятся и ресурс кончится);
- **добросовестный параллельный сценарий** проходит: N разных пользователей за одним
  NAT/доменом/арендатором не мешают друг другу.

Последний пункт ловит то, что первые два пропускают: механизм может корректно ограничивать
атакующего и при этом ломать нормальную работу.

## Анти-паттерны

| Анти-паттерн | Почему плохо |
|---|---|
| Проверять правку только на дефекте, ради которого её писали | Ровно так вносится следующий дефект того же класса |
| Последовательный тест как доказательство работы лимита | Зеленеет там, где защита работает, и молчит там, где она обходится `curl --parallel` |
| Держать соединение/лок во время операции, длительностью которой управляет клиент | Неаутентифицированный маршрут получает право исчерпать общий ресурс |
| Блокировка с грубым ключом «чтобы наверняка» | При насыщении наказывает добросовестных: за одним адресом сидят живые люди |
| «Пул большой, хватит» без называния числа | Требование без числа непроверяемо (тот же класс, что метрика без цели) |
| Ждать ресурс без таймаута | `pg.Pool` без `connectionTimeoutMillis` ждёт **бесконечно** — недоступность обязана быть отказом |
