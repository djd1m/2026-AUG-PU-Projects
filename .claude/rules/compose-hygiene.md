# Гигиена compose и образов — то, что проверяется grep'ом

## Maturity: 🔴 Alpha · Извлечено: 2026-08-27 · Источник: `projects/01-testimonials-senja` · v1.0

Дополняет [`docker-ports.md`](docker-ports.md) (тот — про публикацию портов) вопросами
сборки и жизненного цикла. Все правила ниже — **слой 1**: каждое проверяется командой,
ни одно не требует суждения.

## Правила

### 1. Любой дополнительный compose-файл объявляет `name:`

```yaml
name: myproject-test
```

Без него compose берёт имя **каталога** — то же самое, что у боевого файла, — и стеки
начинают вытеснять друг друга. На прогоне: поднятый демо-стек молча заменил тестовые
контейнеры, 117 тестов легли с `ECONNREFUSED`. Диагноз уводит в сторону — это читается
как «БД не поднялась», а не «её подменил соседний стек».

Особенно едко: дефект жил в файле, созданном ради устранения **другого** дефекта.

```bash
grep -qE '^name:' compose*.y*ml docker-compose*.y*ml
```

### 2. Образы только с явным тегом

`image: minio/minio` — это `:latest`. Через месяц на VPS приедет другой образ, и сборка
перестанет быть воспроизводимой.

```bash
grep -nE '^\s+image:\s+[^:]+$' docker-compose*.y*ml   # пусто = хорошо
```

### 3. `depends_on: condition: service_started` бессмысленно без healthcheck

`service_started` означает «процесс запущен», а не «готов принимать». Зависимые сервисы
стартуют раньше готовности. Нужен `condition: service_healthy` **и** `healthcheck` у
зависимости.

### 4. `restart: unless-stopped` — каждому сервису

Без него однократное падение навсегда. На прогоне воркер стартовал раньше миграций,
падал на `relation … does not exist` и **лежал девять часов незамеченным**: пять
сервисов healthy, приложение работает, транскрипции нет, и об этом не сообщил никто.

`unless-stopped` превращает гонку старта в задержку.

```bash
docker compose config | grep -c 'restart: unless-stopped'   # сверить с числом сервисов
```

### 5. Монорепо npm workspaces в Docker — пять отдельных грабель

До того как это было исправлено, **не собирался ни один образ проекта**:

| Правило | Что происходит при нарушении |
|---|---|
| Контекст сборки = **корень монорепо** | `package-lock.json` только там; из подпапки `npm ci` невозможен |
| `npm ci` нужны манифесты **ВСЕХ** workspace | Иначе `Exit handler never called!` — npm сверяет весь lock-tree, а не одну ветку |
| `COPY` из пути workspace, не из `/app` | Сборка кладёт результат в `/app/apps/web/.next`; `COPY /app/.next` даёт рантайм на пустом месте |
| `CMD` только на скрипт, существующий в **этом** `package.json` | `CMD ["npm","start"]` при скрипте в workspace-манифесте не находит команду |
| `.dockerignore` обязателен при `COPY . .` | Иначе в образ едут `node_modules`, `tests` и потенциально `.env` |

TypeScript-пакет, у которого `exports` указывает на `./src/*`, копируется в рантайм-образ
целиком — сборка его не «запечёт».

### 6. Проверять запуском, а не рассуждением

Записанный остаточный риск — это **предсказание**, к которому обязательно возвращаются.
На прогоне зафиксировали «логика Dockerfile не проверена сборкой — проверять нечего».
Когда появились исходники, **все три предсказанных дефекта оказались реальными**.

```bash
bash scripts/check-compose-buildable.sh   # собрать И СТАРТОВАТЬ каждый build-сервис
```

### 7. Не генерировать пустой скелет ради зелёной сборки

Зелёный `up` при отсутствующем продукте — тот же класс лжи, что «сценарий добавлен ≠
требование закрыто». Честнее зафиксировать пробел и поставить проверку сборки на слой 1.

## Проверка целиком

```bash
bash scripts/check-port-conflicts.sh .     # публикация портов, БД, обход прокси
bash scripts/check-compose-buildable.sh    # собирается и стартует
bash scripts/check-env-wiring.sh           # переменные доезжают
```
