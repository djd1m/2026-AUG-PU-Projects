# Отсутствие данных означает самое строгое, а не самое разрешающее

## Maturity: 🔴 Alpha · Извлечено: 2026-08-27 · Источник: `projects/01-testimonials-senja` · v1.0

## Утверждение

Пустое значение, опечатка, неопознанный вариант и недоступный источник — это **отказ**,
а не «ограничений нет». Класс дефектов, который отсюда растёт, коварен тем, что система
при нём выглядит работающей: она пропускает всё.

## Чем заслужено

Четыре случая в одном проекте, каждый превращал защиту в её отсутствие:

| Случай | Механика | Что означало на деле |
|---|---|---|
| Пустая маска в CIDR | `"1.2.3.4/"` → `Number('') === 0` → префикс `/0` | Одна опечатка в списке сетей провайдера = «принимать вебхуки с любого адреса». Поймано тестом, не ревью |
| Allowlist из переменной окружения | Переменная приехала пустой | Пустой список читался как «ограничений нет». Лечение: список **зашит в код**, а не в env |
| `BASE_URL="/"` | Срезание хвостового слеша оставило пустую строку | Каждый `new URL(path, base)` падал. Лечение: **валидировать** через `new URL` + allowlist протоколов, а не подчищать |
| Неопознанный тариф | `'PAID'`, `' paid'`, `['paid']`, `null` | Любое неузнанное значение обязано означать бесплатный тариф, то есть более строгий |

Смежное наблюдение из того же проекта: **ошибка, показывающая правдоподобное число,
опаснее ошибки, показывающей пустоту.** Статуслайн рисовал `mvp 0/0` полосой как
валидное состояние — «прогресс ноль» вместо «данные не найдены».

## Правило

1. **Неопознанное значение → самый строгий вариант.** Не исключение, не «как было»,
   не значение по умолчанию из середины диапазона.

   ```ts
   export function badgeRequiredFor(tier: unknown): boolean {
     return tier !== 'paid';   // всё, что не ровно 'paid', требует badge
   }
   ```

2. **Пустое отличается от отсутствующего.** `undefined` (поля нет) и `''` (поле есть,
   но пустое) — разные случаи, и второй обычно опечатка:

   ```ts
   if (prefixRaw !== undefined && prefixRaw.trim() === '') return false;  // "1.2.3.4/" — опечатка, не /0
   ```

3. **Список разрешений — в коде, не в конфигурации.** Вынесенная наружу переменная
   однажды приедет пустой или с опечаткой; в коде она проходит ревью и тесты.

4. **Значение из окружения валидируется, а не подчищается.** Непригодное трактуется
   как отсутствующее и уступает следующему кандидату в цепочке.

5. **Недоступность источника истины — отказ.** Не «пропустить, раз проверить не смогли».
   В вебхуке оплаты недоступность провайдера обязана быть исключением, откатывающим
   транзакцию, а не значением, коммитящим её.

6. **Пустота показывается как пустота.** `0/0` — не «ноль процентов», а «данных нет».

## Как проверять

Отдельный тест с перечнем мусорного входа. В проекте-источнике он состоит из 11 видов
и ловит регрессии дешевле любого ревью:

```ts
it('ЛЮБОЕ неопознанное значение трактуется как free (fail-closed)', () => {
  for (const bad of [null, undefined, '', 'PAID', ' paid', 'premium', 0, 1, true, {}, ['paid']]) {
    expect(badgeRequiredFor(bad), JSON.stringify(bad)).toBe(true);
  }
});
```

Такой тест дешевле и надёжнее, чем правило в чек-листе: он проверяет **все** перечисленные
формы при каждом прогоне.

## Анти-паттерны

| Анти-паттерн | Почему плохо |
|---|---|
| `Number(x)` на значении, где `''` осмысленно | `Number('')` равен нулю, а ноль часто и есть «разрешить всё» |
| Пустой allowlist трактуется как «фильтра нет» | Ровно наоборот: пустой список никого не пропускает |
| «Проверить не смогли — пропустим» | Превращает временный сбой в постоянную дыру |
| Прогресс-индикатор рисует `0/0` как валидное состояние | Отсутствие данных выдаётся за измеренный ноль |
