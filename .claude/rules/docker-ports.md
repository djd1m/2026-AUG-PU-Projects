# Порты в Docker: БД никогда наружу, и проверять занятость ДО запуска

Правило для **всех** проектов репозитория. Применяется в двух моментах:
при **генерации** `docker-compose.yml` (Phase 3 `/replicate`, `/start`) и перед
**каждым** `docker compose up`.

## Почему это правило существует

Эта машина держит несколько проектов одновременно. На момент написания правила уже
заняты `80`, `443`, `3002`, `5480`, `8080`, `8081`, `8088`, `11000`, `11001`, `11379`,
`11432` — и список растёт с каждым новым проектом курса.

Найдено на проекте 01: сгенерированный `docker-compose.yml` просил `80:80` и `443:443`
под Caddy, а обе эти двери уже держал контейнер `ai-hub-tls-proxy`. Документы были
согласованы, тесты зелёные, сборка проходила — и `docker compose up` всё равно упал бы
на первой же машине, где его запустят. Дефект не в коде: он в допущении, что машина пустая.

`80` и `443` — самый частый случай: их почти всегда уже слушает чужой reverse-proxy.

## Правило №0 (главное): база данных не публикуется НИКОГДА

Заслужено инцидентом 2026-08-26 на этой машине, подробности ниже.

```yaml
postgres:
  expose: ["5432"]        # ✅ видно только соседям по сети compose
  # ports: ["5432:5432"]  # ❌ НИКОГДА. Это дверь в интернет
```

Запрещено публиковать наружу: **Postgres, MySQL, MongoDB, Redis, Elasticsearch, MinIO,
RabbitMQ** и любое другое хранилище или брокер. Наружу смотрит ТОЛЬКО reverse-proxy и,
при необходимости, приложение. Всё остальное общается по внутренней сети compose
по имени сервиса (`postgres:5432`), где публикация не нужна в принципе.

### То же касается разовых `docker run` в отладке

Инцидент случился **не** из-за compose — сгенерированный `docker-compose.yml` был
правильным, там `expose:`. Нарушением был ad-hoc запуск тестовой БД в обход него:

```bash
docker run -p 55432:5432 -e POSTGRES_PASSWORD=postgres postgres:16-alpine   # ❌
```

`-p 55432:5432` публикует порт на **все** интерфейсы, включая публичный IP. «Необычный»
номер порта не защищает — это безопасность через неочевидность. Пароль `postgres`
подобрали примерно за час, дальше `COPY … TO PROGRAM` дал выполнение команд, и в
контейнер лёг червь-майнер.

Единственная допустимая форма для локальной отладки:

```bash
docker run -p 127.0.0.1:55432:5432 -e POSTGRES_PASSWORD="$(openssl rand -hex 24)" …   # ✅
```

Два обязательных условия: **явный `127.0.0.1`** в публикации и **случайный пароль**.
Дефолтные учётные данные (`postgres/postgres`, `minioadmin/minioadmin`, `root/root`,
Redis без пароля) — не «временно для тестов», а готовая точка входа.

### Почему это архитектурное правило, а не совет по гигиене

Прямое подключение к БД снаружи не нужно ни одному сценарию системы: приложение ходит
в базу по внутренней сети, миграции запускаются из контейнера или по внутренней сети,
отладка — через `docker exec … psql`. Публикация порта БД не решает ни одной задачи
архитектуры и создаёт поверхность, которой в схеме нет. Поэтому это запрет, а не
рекомендация с исключениями.

## Правило №0.1: за reverse-proxy приложение тоже не публикуется

Если в compose есть Caddy/nginx/traefik — он и есть единственная дверь. Опубликованное
рядом приложение позволяет обойти прокси, а вместе с ним и всё, что прокси гарантирует.

```yaml
web:
  expose: ["3000"]        # ✅ снаружи доступен только через caddy
  # ports: ["3000:3000"]  # ❌ прокси обходится прямым обращением
caddy:
  ports: ["${HTTP_PORT:-80}:80", "${HTTPS_PORT:-443}:443"]   # ✅ единственная дверь
```

**Конкретный случай, ради которого это правило появилось.** `extractClientIP` доверяет
ПОСЛЕДНЕМУ элементу `X-Forwarded-For`, потому что его дописывает Caddy — на этом держится
rate limit 5 отправок в час на IP. Пока web не опубликован, рассуждение верное. Стоит его
опубликовать — и атакующий шлёт запрос напрямую со СВОИМ единственным `X-Forwarded-For`,
«последний элемент» становится его значением, и лимит обнуляется сменой заголовка.

Воспроизведено на живом контейнере: с ротацией заголовка прошли 7 запросов подряд при
пороге 5; с одним адресом — 5 и затем 429. Найдено вторым мнением (Codex), а не тестами:
каждый модуль по отдельности был корректен, дефект жил В СТЫКЕ кода и compose.

Отсюда общий вывод: **гарантия, которую даёт прокси, действует ровно до тех пор, пока его
нельзя обойти.** Любой код, доверяющий заголовку от прокси, обязан быть закрыт от прямого
доступа — и это должно проверяться, а не подразумеваться.

## Правило генерации

Генератор `docker-compose.yml` **обязан**:

1. **Не зашивать хостовый порт числом.** Только через переменную с умолчанием:

   ```yaml
   ports: ["${WEB_PORT:-3000}:3000"]
   ```

   Конфликтует **только левая (хостовая) часть**. Номер внутри контейнера менять не нужно
   и не следует — на него ссылаются `depends_on`, healthcheck'и и адреса вида
   `http://transcribe:7331`.

2. **Объявить эти переменные в `.env.example`** с комментарием, что правятся они под машину,
   а не в общем compose.

3. **Не публиковать наружу то, что нужно только внутри.** `expose:` вместо `ports:` —
   у Postgres, MinIO, внутренних сервисов. Опубликованный порт — это не «удобно
   подключиться», а занятая дверь и открытая поверхность.

4. **Проверить занятость до того, как отдать результат:**

   ```bash
   bash scripts/check-port-conflicts.sh <путь-к-проекту>
   ```

## Правило запуска

Перед **любым** `docker compose up` — и перед `docker run` тоже:

```bash
bash scripts/check-port-conflicts.sh .    # 0 — чисто, 1 — конфликт
```

Скрипт берёт занятые порты из `docker ps` и из слушающих сокетов хоста (`ss`), а желаемые —
из `docker compose config` (он разворачивает `${VAR:-default}` и `.env` сам). Проверка
детерминированная — **слой 1** по лестнице стоимости обнаружения (корневой `CLAUDE.md`).

Полагаться на «увижу при запуске» нельзя по двум причинам: docker называет **один** порт
за прогон, так что конфликты вскрываются по одному, и часть стека к этому моменту уже
поднята — состояние грязное.

### Разовые контейнеры для тестов

То же самое касается `docker run -p` в отладке. Занимать порт «на минутку» на машине с
десятком чужих контейнеров — это отложенный конфликт. Проверить: `ss -tlnH | grep :ПОРТ`.

## Как чинить конфликт

| Ситуация | Решение |
|---|---|
| Порт занят другим проектом | Задать свободное значение в `.env` этой машины. Compose не трогать |
| `80`/`443` заняты чужим reverse-proxy | Не публиковать их из проекта. Подключить сервис в сеть существующего прокси |
| Порт нужен только соседним контейнерам | `expose:` вместо `ports:` — наружу он не нужен |

## Анти-паттерны

| Анти-паттерн | Почему плохо |
|---|---|
| `ports: ["80:80"]` числом в compose | Первая же машина с nginx/Caddy — и стек не поднимается |
| Публиковать порт БД наружу «чтобы подключиться клиентом» | Занятая дверь + открытая поверхность; для отладки хватает `docker exec` |
| Менять порт ВНУТРИ контейнера при конфликте | Ломает `depends_on`, healthcheck и внутренние адреса. Конфликтует только хостовая часть |
| Проверять занятость после падения `up` | Docker называет по одному порту за раз, а стек уже частично поднят |
