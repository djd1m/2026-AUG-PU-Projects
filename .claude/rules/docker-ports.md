# Порты в Docker: проверять занятость ДО запуска

Правило для **всех** проектов репозитория. Применяется в двух моментах:
при **генерации** `docker-compose.yml` (Phase 3 `/replicate`, `/start`) и перед
**каждым** `docker compose up`.

## Почему это правило существует

Эта машина держит несколько проектов одновременно. На момент написания правила уже
заняты `80`, `443`, `3002`, `5480`, `8080`, `8081`, `8088`, `11000`, `11001`, `11379`,
`11432` — и список растёт с каждым новым проектом курса.

Найдено на проекте 01: сгенерированный `docker-compose.yml` просил `80:80` и `443:443`
под Caddy, а обе эти двери уже держал контейнер `ai-hub-tls-proxy`. Документы были
согласованы, тесты зелёные, сборка проходила — и `docker compose up` всё равно упал бы
на первой же машине, где его запустят. Дефект не в коде: он в допущении, что машина пустая.

`80` и `443` — самый частый случай: их почти всегда уже слушает чужой reverse-proxy.

## Правило генерации

Генератор `docker-compose.yml` **обязан**:

1. **Не зашивать хостовый порт числом.** Только через переменную с умолчанием:

   ```yaml
   ports: ["${WEB_PORT:-3000}:3000"]
   ```

   Конфликтует **только левая (хостовая) часть**. Номер внутри контейнера менять не нужно
   и не следует — на него ссылаются `depends_on`, healthcheck'и и адреса вида
   `http://transcribe:7331`.

2. **Объявить эти переменные в `.env.example`** с комментарием, что правятся они под машину,
   а не в общем compose.

3. **Не публиковать наружу то, что нужно только внутри.** `expose:` вместо `ports:` —
   у Postgres, MinIO, внутренних сервисов. Опубликованный порт — это не «удобно
   подключиться», а занятая дверь и открытая поверхность.

4. **Проверить занятость до того, как отдать результат:**

   ```bash
   bash scripts/check-port-conflicts.sh <путь-к-проекту>
   ```

## Правило запуска

Перед **любым** `docker compose up` — и перед `docker run` тоже:

```bash
bash scripts/check-port-conflicts.sh .    # 0 — чисто, 1 — конфликт
```

Скрипт берёт занятые порты из `docker ps` и из слушающих сокетов хоста (`ss`), а желаемые —
из `docker compose config` (он разворачивает `${VAR:-default}` и `.env` сам). Проверка
детерминированная — **слой 1** по лестнице стоимости обнаружения (корневой `CLAUDE.md`).

Полагаться на «увижу при запуске» нельзя по двум причинам: docker называет **один** порт
за прогон, так что конфликты вскрываются по одному, и часть стека к этому моменту уже
поднята — состояние грязное.

### Разовые контейнеры для тестов

То же самое касается `docker run -p` в отладке. Занимать порт «на минутку» на машине с
десятком чужих контейнеров — это отложенный конфликт. Проверить: `ss -tlnH | grep :ПОРТ`.

## Как чинить конфликт

| Ситуация | Решение |
|---|---|
| Порт занят другим проектом | Задать свободное значение в `.env` этой машины. Compose не трогать |
| `80`/`443` заняты чужим reverse-proxy | Не публиковать их из проекта. Подключить сервис в сеть существующего прокси |
| Порт нужен только соседним контейнерам | `expose:` вместо `ports:` — наружу он не нужен |

## Анти-паттерны

| Анти-паттерн | Почему плохо |
|---|---|
| `ports: ["80:80"]` числом в compose | Первая же машина с nginx/Caddy — и стек не поднимается |
| Публиковать порт БД наружу «чтобы подключиться клиентом» | Занятая дверь + открытая поверхность; для отладки хватает `docker exec` |
| Менять порт ВНУТРИ контейнера при конфликте | Ломает `depends_on`, healthcheck и внутренние адреса. Конфликтует только хостовая часть |
| Проверять занятость после падения `up` | Docker называет по одному порту за раз, а стек уже частично поднят |
