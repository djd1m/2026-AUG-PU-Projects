# Документы SPARC: что зачем и в каком порядке читать

Объяснение для слушателей курса. Основано на разборе фактического пайплайна p-replicator,
а не на теории SPARC. Подробности: [`/research/docs-guide/`](../research/docs-guide/).

---

## Главный вопрос: дистилляция или комплект?

Естественная догадка: каждый следующий документ вбирает предыдущий и добавляет своё,
а в конце получается один файл, по которому пишут код.

**Это не так.** Проверено по коду пайплайна.

> **Документы не сжимаются один в другой. Они делят между собой ответственность.**
> К моменту написания кода нужны четыре файла одновременно, и ни один не заменяет остальные.

### Доказательство

`.claude/rules/feature-lifecycle.md:91-93`, фаза реализации:

> «Identify independent work units from Phase 1's **Architecture**»
> «Each Task: **read SPARC sections** + implement + test + commit»

Читаются *разделы* разных документов, а работа нарезается по **Architecture**, не по Specification.

`.claude/commands/plan.md:31-34` — лёгкий путь открывает **два файла сразу**:
`docs/Architecture.md` и `docs/Specification.md`.

`cc-toolkit-generator-enhanced/modules/01-detect-parse.md:24` — генератор тулкита:

> «Scan `docs_path` **recursively** and catalog **every file** by category»

### Проверка на живом примере

Возьмём одно требование — **FR-GROWTH-003**, badge на бесплатном тарифе. Что нужно, чтобы его написать:

| Файл | Что даёт | Без него |
|---|---|---|
| `Specification.md` | бизнес-правило и Gherkin-тесты | непонятно, что считать выполненным |
| `Architecture.md` | где вычисляется `badge_required` | непонятно, где писать код |
| `Pseudocode.md` | алгоритм рендера и слежения | непонятно, как это работает |
| `ADR.md` | почему `tier` нельзя отдавать клиенту | легко «упростить» и сломать защиту |

Четыре файла на одно требование. Ни один не лишний.

## Почему НЕ стоит нумеровать файлы 01, 02, 03

Нумерация подсказывает: «читай по порядку, последний — главный». Для этого пайплайна
это **вредная подсказка** — она внушит слушателям модель дистилляции, которой нет.

Порядок *создания* действительно есть: PRD → Specification → Pseudocode → Architecture.
Но порядок *чтения* другой: кодер открывает четыре файла одновременно и не читает
первые два вовсе.

Нумерация закрепила бы неверное поведение: студент прочитает «последний» документ
и решит, что этого достаточно.

**Что полезнее нумерации — деление по роли.** Три группы вместо десяти номеров:

```
docs/
├── [ДЛЯ КОДА]      Specification · Architecture · Pseudocode · ADR
├── [КОНТЕКСТ]      PRD · Solution_Strategy · Research_Findings · discovery/
└── [ПРОЦЕСС]       Refinement · Completion · validation/ · C4_Diagrams
```

Это можно донести одной фразой, и оно отражает реальность.

## Что каждый документ делает

### Группа 1 — обязательны для кода

| Документ | Одной фразой | Кто читает |
|---|---|---|
| **Specification.md** | Что реализуем: требования + Gherkin-сценарии | кодер, тестировщик, валидатор |
| **Architecture.md** | Где это живёт: схема БД, compose, деплой | кодер, DevOps |
| **Pseudocode.md** | Как это работает: алгоритмы | кодер, QE |
| **ADR.md** | Почему именно так: решения и отвергнутые альтернативы | кодер, будущий разработчик |

Полезная мнемоника: **что · где · как · почему**.

«Почему» нужно не для истории. Без ADR разработчик через месяц «упростит» решение,
не зная, что альтернатива уже была рассмотрена и отвергнута по конкретной причине.

### Группа 2 — контекст и обоснование

| Документ | Одной фразой | Когда открывают |
|---|---|---|
| **PRD.md** | Продукт, скоуп, метрика недели | при спорах о границах скоупа |
| **Solution_Strategy.md** | Почему выбран этот скоуп и этот loop | при пересмотре стратегии |
| **Research_Findings.md** | Сводка фактов о конкуренте + оценка достоверности | при проверке источника цифры |
| **discovery/** | Reverse-engineering оригинала, варианты пути пользователя | на старте, потом редко |

Эти документы **входят в генерацию**, но кодер их не открывает.

### Группа 3 — процесс

| Документ | Одной фразой | Когда работает |
|---|---|---|
| **Refinement.md** | Стратегия тестирования, техдолг | фаза Review |
| **Completion.md** | Definition of Done недели | приёмка |
| **validation/** | Отчёты валидаторов | Phase 2 |
| **C4_Diagrams.md** | Диаграммы ключевого потока | объяснение человеку |

## Что показал аудит

Честные наблюдения из разбора проекта 01 — их стоит проговорить слушателям.

**Дублирование.** `Research_Findings.md` почти дословно повторяет discovery-документы;
самостоятельной ценности там только раздел про достоверность источников. Граница применения
Claude под FTC сформулирована **трижды** — в PRD, в FR-003 и в FR-NFR-SEC-002.

**C4_Diagrams не сканируется генератором тулкита** в SPARC-ветке. Он для людей, не для машины.

**Артефакты рассинхронизируются.** `Refinement.md` и `C4_Diagrams.md` не были обновлены,
когда `Architecture.md` зафиксировала канонические имена — расхождение нашла отдельная проверка.

**CJM и ADR не имеют механической связи со спецификацией.** Элемент CJM «Core Loop»
(еженедельный дайджест) молча выпал из требований проекта 01 — в отличие от Onboarding,
который исключён явно и с обоснованием. Из семи ADR шесть не имеют обратной ссылки
из `Specification.md`.

Заявки на исправление — в [`/harness-forge/`](../harness-forge/), PR-006 и PR-007.

## Как объяснить это за минуту

> Документы не пересказывают друг друга — они делят работу.
> Спецификация говорит **что** сделать, архитектура — **где** это живёт,
> псевдокод — **как** это работает, ADR — **почему** решили именно так.
>
> Когда садишься писать код, открываешь все четыре. Остальные документы —
> это контекст, откуда всё выросло, и процесс, которым проверяем результат.
>
> Поэтому у них нет номеров: это не главы книги, которые читают подряд,
> а разные проекции одного продукта.
